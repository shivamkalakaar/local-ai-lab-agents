## Learning objective
- Learn when to search, when to split a task, how to spend calls wider or deeper, and how to turn logged steps into training data.

## Why planning?
- A greedy chain commits to its first idea and never looks back.
- Hard tasks need more than one straight pass.
- Five tools from this lecture:
  - Tree search: back up from dead ends (LATS)
  - Split only on failure (ADaPT)
  - Wider vs deeper budget (AB-MCTS)
  - Parallel independent steps (SPRINT)
  - Step-level training data (SWiRL)

## Greedy chain vs tree search
| Greedy chain | Tree search |
|---|---|
| One next step, no going back | Several candidate steps, scored |
| Dead end → fail | Dead end → back up to a better branch |
| Fewest calls | More calls |

- Tree search: explore several next steps, score them, return to a better branch when one fails.
- Value function: a score for how promising a partial solution is.

## LATS: tree search for agents (Zhou et al. 2023)
- Monte Carlo Tree Search over agent actions.
  - Select: pick a promising node
  - Expand: sample n actions (n = 5 by default) and run them
  - Evaluate: value = LM's own rating mixed with self-consistency
  - Backpropagate, and write a reflection after a failure
- Needs states you can return to. A sent email can't be undone.

## LATS results
| Benchmark | LATS | Baseline |
|---|---|---|
| HumanEval pass@1 (GPT-3.5) | 83.8% | 68.1% Reflexion |
| HotPotQA EM (GPT-3.5) | 0.63 | 0.32 ReAct |
| Game of 24 | 0.44 | 0.20 Tree-of-Thoughts |

- With GPT-4: 92.7% on HumanEval.
- Costs more than ReAct or Reflexion.

## ADaPT: decompose only when needed (Prasad et al. 2024)
- As-needed decomposition: split a task only after a direct try fails.
- Executor tries the whole task first.
- On failure, a planner splits it into sub-tasks; recurse on each, up to a max depth.
- Easy tasks cost one call. Only hard ones pay for planning.
- Watch out: the executor's self-reported success was over 30 points too high on WebShop.

## ADaPT results (GPT-3.5)
| Benchmark | ADaPT | ReAct |
|---|---|---|
| ALFWorld | 71.6% | 43.3% |
| WebShop | 44.0% | 32.0% |
| TextCraft | 52.0% | 19.0% |

## Wider or deeper? (AB-MCTS, Inoue et al. 2025)
- Wider: spend the next call on a brand-new answer.
- Deeper: refine an existing answer with feedback.
- Thompson sampling: picks the option whose random draw from its scores is highest; balances new vs proven.
- AB-MCTS makes this choice at every node.

## AB-MCTS results
| CodeContests, GPT-4o, 128 calls | Solved |
|---|---|
| Pure refinement (deeper only) | 30.1% |
| Standard MCTS | 37.5% |
| Repeated sampling (wider only) | 37.9% |
| AB-MCTS-M | 40.6% |

- On ARC-AGI, repeated sampling still led at 128 calls; AB-MCTS kept improving up to 512.
- Gains show up at large budgets.

## SPRINT: run independent steps at once (Biju et al. 2025)
- Critical path: the steps that must happen one after another. It sets the latency.
- SPRINT trains a model to alternate a plan (independent subtasks) with parallel execution.
- About 1,700 examples fine-tune a 7B reasoning model.
- MATH-500: 92.5% vs 91.0%, with up to 39% fewer sequential tokens on long problems.
  - Up to 45% fewer on GPQA, 65% on Countdown

## A parallel contract review plan
```python
PLAN = {"liability_cap": [], "governing_law": [], "auto_renewal": [], "termination_notice": [],
        "summary": ["liability_cap", "governing_law", "auto_renewal", "termination_notice"]}
print("plan rounds:", stages(PLAN))
```
- Each step lists what it depends on.
- The four rule checks depend on nothing; the summary needs all four.
- `stages` groups steps into rounds: round 1 = four checks, round 2 = summary.
- With 2 parallel slots, 4 checks take about 2 rounds instead of 4.

## SWiRL: train on steps, not runs (Goldie et al. 2025)
- Sub-trajectory: cut a run with k actions into k examples (context so far → next action).
- Process filtering: keep steps a judge calls reasonable, even if the final answer was wrong.
- Gemma 2 27B, relative gains: 21.5% GSM8K, 12.3% HotPotQA.

| Filter | Keeps |
|---|---|
| Outcome only | Steps from runs with the right final answer |
| Process only | Good steps, even inside failed runs. Best for RL |

## How this applies to us
- Independent playbook checks can run in parallel on the firm's machine; the summary waits for all.
- Try a direct review first; split into per-rule checks only when it fails.
- Log every step. A failed review still has good steps to train a local model on.

## Common mistakes
- Searching where actions can't be undone → only search over states you can return to.
- Planning everything up front → try directly, split only what fails.
- Trusting self-reported success → use a real checker.
- Parallelizing dependent steps → map dependencies first; the longest chain sets latency.

## Check your understanding
**Q: What does ADaPT do differently from plan-and-execute?**
A: It tries the whole task first and splits it only when the executor fails, so easy tasks cost one call.

**Q: In AB-MCTS, what choice is made at each node, and what decides it?**
A: Whether to generate a new answer (wider) or refine an existing one (deeper). Thompson sampling on the feedback scores decides.

**Q: Why might SWiRL keep a step from a run whose final answer was wrong?**
A: The step itself was judged reasonable. Process-only filtering gave the best RL results.
