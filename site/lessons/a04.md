## The big idea

Some tasks can't be done in one straight pass. The first idea may lead to a dead end. A plain chain of steps commits early and never looks back.

Think of finding your way through an unfamiliar office building. You try a corridor. If it ends at a locked door, you go back and try another. You don't map the whole building first. You split the trip into parts only where you get lost. And if two colleagues are free, you send them down two corridors at once.

This module covers those habits for agents. Search a tree of steps and back up. Split a task only when a direct try fails. Choose between new ideas and fixing old ones. Run independent steps at the same time. And log every step, so it can become training data.

## Why it matters for us

- Contract review is many steps: find clauses, check rules, compute figures, write a summary. Some depend on each other, some don't. Knowing which is which saves time.
- Local models are slower than cloud ones. Running independent checks at once, and not over-planning easy tasks, keeps waiting time down.
- Search only works where steps can be undone. Reading a clause can be undone. Sending an email cannot. A firm must know the difference.

## How it works, step by step

1. **Tree search with backtracking (LATS).** The LATS paper (2023) runs a tree search over agent steps. Select a promising step. Expand it into several possible next steps (5 by default). Evaluate each with a value score: how promising it looks. LATS mixes the model's own rating with how often the same step was proposed. If a path fails, write a short note on why, and try another branch. On a number puzzle, LATS scored 0.44 against 0.20 for an earlier tree method. The cost: more calls than a single chain, and it needs states you can go back to.

2. **Split only when needed (ADaPT).** The ADaPT paper (2024) first lets the model try the whole task. Only if that fails does a planner split it into smaller parts. Then it repeats on each part, up to a set depth. Easy tasks cost one call. With GPT-3.5, it reached 71.6% on a household-task benchmark, against 43.3% for ReAct. A warning: the model judged its own success, and overrated it by more than 30 points on a shopping benchmark. Use a real checker when you can.

3. **Wider or deeper (AB-MCTS).** With a fixed budget, the next call can make a brand-new answer (wider) or improve the best one so far using feedback (deeper). The AB-MCTS paper (2025) lets the scores decide, using Thompson sampling: a method that mostly picks what has worked, but still tries the other option sometimes. On a coding benchmark with 128 calls, pure refinement scored 30.1%, repeated sampling 37.9%, and AB-MCTS 40.6%. The gains showed up at large budgets.

4. **Run independent steps at once (SPRINT).** Reasoning models usually think in one long line. The SPRINT paper (2025) trained a model to write a plan of independent subtasks, then run them in parallel. It matched its baselines on math while cutting sequential tokens (the text that must be written one piece after another) by up to 39% on long problems. The key point: waiting time is set by the longest chain of dependent steps, called the critical path, not by the total work.

5. **Learn from steps, not just outcomes (SWiRL).** The SWiRL paper (2025) cut each multi-step run into one example per action: the context so far, then the next action. A judge model kept steps it found reasonable, even when the final answer was wrong. This process filtering beat keeping only runs with correct answers. A failed run still contains good steps.

## Worked example

A contract review plan has four rule checks, then a summary. The checks don't depend on each other. The summary needs all four.

```python
PLAN = {"liability_cap": [], "governing_law": [], "auto_renewal": [], "termination_notice": [],
        "summary": ["liability_cap", "governing_law", "auto_renewal", "termination_notice"]}
print("plan rounds:", stages(PLAN))
```

In plain words:

- Line 1–2: each step lists what it depends on. The four checks depend on nothing. The summary depends on all four.
- Line 3: `stages` groups steps into rounds. A step runs once everything it needs is done. So round 1 holds all four checks, and round 2 holds the summary.

Now run it on contract msa_15. Each check asks the model: "Does this clause follow this rule? PASS or FAIL." With two parallel slots, the four checks take about two rounds instead of four. The summary then lists every FAIL: "Cannot sign as written: ..."

```
round 1:  [liability_cap] [governing_law] [auto_renewal] [termination_notice]
round 2:              [summary]
```

Add one more step, say "compute the dollar cap," which needs the liability check. Now the chain gets longer. No number of parallel slots can beat that longest chain.

## Common mistakes

- **Searching where actions can't be undone.** A sent email or a database write can't be rewound. Only search over safe, reversible steps.
- **Trusting the model's own value scores.** They are noisy. Use a real checker when one exists.
- **Planning everything up front.** A long fixed plan breaks when any step fails. Try first, and split only what fails.
- **Running dependent steps in parallel.** Map what depends on what first. Otherwise a step runs before its inputs exist.
- **Keeping only successful runs as training data.** Good steps inside failed runs are lost. Label steps, not just outcomes.

## Check your understanding

**Q: What does ADaPT do differently from planning everything first?**
A: It tries the whole task first. It only plans and splits when that fails, and repeats on the failed parts, so easy tasks cost one call.

**Q: In AB-MCTS, what choice is made at each step, and what decides it?**
A: Whether to make a new answer (wider) or improve an existing one (deeper). Thompson sampling on the feedback scores decides.

**Q: Why might SWiRL keep a step from a run whose final answer was wrong?**
A: The step itself was judged reasonable. Keeping such steps gave better training results than keeping only successful runs.
