# Why evals come first

## The rise of software engineering
| Era | What people wrote | Example |
|---|---|---|
| 1940s | Numeric instructions straight to the CPU | `48 83 C0 05` |
| Early 1950s | Assembly | `add rax, 5` |
| Late 1950s | High-level code | `x += 5` |

- All three lines do the same thing: add 5.
- Backus: 1950s programmers saw themselves as "a priesthood guarding skills and mysteries."
- IBM's FORTRAN report (1954): "FORTRAN should virtually eliminate coding and debugging."

## Deductive technology creation
- Rules + Inputs → Outputs.
- Humans write the rules (code). The program applies them to new inputs.
- Hoare (1969): every property of a program can, in principle, be found from its text "by means of purely deductive reasoning."

## Inductive technology creation
- The rise of ML: Inputs + Outputs → Rules.
- Humans provide examples (data + labels). Training infers the rules (the model).
- Slide headline: Chris Anderson, Wired (2008), "The End of Theory: The Data Deluge Makes the Scientific Method Obsolete."

## Two lifecycles
| SWE lifecycle (deductive) | ML lifecycle (inductive) |
|---|---|
| Specification → Implementation → Test → Deploy | Objective → Evaluation → Experiments → Optimization |
| A straight line | Loops back from Optimization to Evaluation |

## Software → ML → LLMs → Agents
- Shannon's dream: a machine that "thinks, learns, communicates with humans and manipulates its environment."
- "All digital technology development is becoming inductive":
  1. Models: learned from data.
  2. Agents: developed via evaluation.
  3. Software: generated by agents.
- Chollet: agentic coding is a form of ML; treat generated code as a black box managed "via empirical evaluation."
- The model, agent and software lifecycle now all follow the inductive loop.

## Rules vs outputs as the source of truth
| Rule-based | Model-based |
|---|---|
| `re.search(r"\d{3}-\d{3}-\d{4}", text)` | Ask an LLM: "Extract the phone number:" |
| The code is the spec. Read it to know what it does | The code says little. Only outputs on test inputs tell you |

- Same job: pull "555-123-4567" out of "My number is 555-123-4567".
- Specification → Evaluation. The specifier was the software engineer. Who is the evaluator?

## Before and now
| Before: traditional software | Now: agentic world |
|---|---|
| Code is the source of truth | Evals are the source of truth |
| Deterministic | Stochastic: same input, different outputs |
| Deductive | Empirical |
| Software is handcrafted | Software is learned |

- Harbor (the Terminal-Bench team's tool): "tools for eval-driven development."
- Without an eval, you can't tell if a change helped or if a local model is good enough.

# What is a benchmark?

## How do we know it works?
- So far: how to build an agent (frameworks, memory, multi-agent).
- And how to train one (optimization, data).
- Open question: how do we know any of these advances are working?
- Start from how plain language models are evaluated.

## Start from the basics
- Modeling: P(x1…xT) = product over t of P(xt | x<t).
  - The chance of a sequence = the chance of each token given the ones before.
- Training objective: cross-entropy loss L = −Σ yi · log(pi).
  - yi: 1 for the token in the data, 0 otherwise. pi: the model's probability for it. Sum over the vocabulary.
- You could train until loss stops falling. But can the model do real language tasks?

## Classic language tasks
| Family | Examples |
|---|---|
| Sequence labeling | POS tagging, named entities, slot filling |
| Syntax and structure | Parsing, coreference |
| Classification | Sentiment, topic, spam, intent |
| Semantics and extraction | Entity linking, relation extraction |
| Question answering | Extractive, open-domain, multi-hop, commonsense |

- Linguists studied these for years. Early LMs reused them as benchmarks.

## response = LM(prompt)
| SQuAD (extractive QA) | MultiNLI (inference) |
|---|---|
| Passage on the Golden Gate Bridge | Premise: "The museum extended its weekend hours after attendance doubled over the summer." |
| Q: "In what year did the Golden Gate Bridge open?" | "More people visited in the summer." → Entailment |
| Gold: "1937" | "The museum shortened its weekend hours." → Contradiction |
| Scored by exact match and token F1 | Scored by accuracy |

## T5: every task as text in, text out
- T5 (Raffel et al., 2019): translation, grammar check, similarity and summarization all as text → text.
  - "cola sentence: The course is jumping well." → "not acceptable"
- One model, one loss, one set of settings for every task.
- Its table: encoder-decoder with denoising scored best (GLUE 83.28, SQuAD 80.88, SuperGLUE 71.36).

## Task collections
| Bundle | Paper |
|---|---|
| SQuAD | Rajpurkar et al., 2016 |
| GLUE, SuperGLUE | Wang et al., 2019 |
| MMLU | Hendrycks et al., 2021 |
| BIG-bench ("Beyond the Imitation Game") | Srivastava et al., 2023 |
| HELM (Holistic Evaluation) | Liang et al., 2023 |

- Many tasks in one bundle, for a broad view of a model.

## Harder evals as models got better
- Exam benchmarks: can LMs pass human tests (SAT, AMC 12, AIME, GRE, bar exam)?
- Chat benchmarks: open-ended questions, multi-turn conversation.
- Safety benchmarks: refuse malicious requests, respect user limits.
- Agent benchmarks: finish a task by acting in an environment over many turns. The focus of this course.

## Exam: MMLU
- MMLU (Hendrycks, 2020): multiple-choice knowledge questions across 57 subjects.
- Figure: GPT-3 few-shot on MMLU ("Knowledge") vs commonsense and linguistics tests.
  - Small to Large models: about 25%, near chance for 4 options.
  - X-Large: about 44%. Commonsense and linguistics were already 60–80%.

## Exam: MMLU-Pro
- MMLU-Pro (Wang, 2024): 4 → 10 answer options; noisy questions removed.
- Every model scores lower than on MMLU; Gemma-7B drops by about half.
- Scores vary less with the prompt:
  - Llama-3-8B: spread σ = 0.008 on MMLU, 0.004 on MMLU-Pro.
  - Llama-2-7B: σ = 0.016 vs 0.004.
- Chain-of-thought helps more on MMLU-Pro than on MMLU (e.g., GPT-4o).

## Exam: GPQA
- GPQA (Rein, 2023): "Google-proof" questions written by PhD students.
- Pipeline: write → expert check #1 → revise → expert check #2 → non-expert check.
- Non-experts are experts in other fields, allowed Google, at least 15 min (average about 37).
- Kept in the "Diamond" set if 2 of 2 experts agree and at most 1 of 3 non-experts gets it right.

## Exam: Humanity's Last Exam
- HLE (Phan, 2025): even harder; multiple choice and short answer.
- Examples: translate the Palmyrene script on a Roman tombstone; count paired tendons on a hummingbird bone.
- Questions come from named experts (e.g., Merton College, Oxford; MIT).

## Chat: AlpacaEval
- Metric: win rate (how often a judge prefers your answer) or Elo (a rating from many pairwise wins).
- Length-controlled (LC) win rate: removes the judge's taste for long answers.
  - GPT-4 Omni: 57.5% LC vs 51.3% raw. Yi-Large Preview: 51.9% LC vs 57.5% raw.
- How well each benchmark tracks Chatbot Arena (Spearman): output length 0.35, MMLU 0.87, MT-bench 0.94, LC AlpacaEval 2.0 0.98.

## Chat: Chatbot Arena
- Chatbot Arena (Chiang, 2024): AlpacaEval's idea with live, real user prompts.
- A user sees two anonymous answers and votes: A better, tie, both bad, B better.
- Votes become a win-rate grid. Example cell: gpt-4-turbo beats mistral-7b-instruct 0.90 of the time.

## Safety: HarmBench and AIR-Bench
| HarmBench (Mazeika, 2024) | AIR-Bench (Zeng, 2024) |
|---|---|
| How often red-teaming attacks get harmful answers | 5,694 prompts across 314 risk categories models should refuse |
| Example: "hiring a hitman" request; a refusal gets safety score 1 | Taxonomy levels: 4 → 16 → 45 → 314 categories |
| | Built by generating, mutating (dialect, syntax) and hand-checking prompts |

## What is a benchmark? Summary
- Benchmarks measure whether an LM system's behavior or abilities improved.
- Usually: a set of prompts (questions, instructions) plus a metric.
- They come in all shapes: task types, expected answers, ways to grade.
- From here on: benchmarks for LM agents.

# Why benchmarks matter

## Not just an AI idea
| Field | Benchmark |
|---|---|
| Computer vision | ImageNet, MNIST digits, CIFAR images |
| Recommender systems | The Netflix Prize |
| ML for science | CASP protein folding (AlphaFold) |
| Robotics | DARPA Grand Challenge: 300 miles of rugged terrain, $1 million prize |

## Three jobs a benchmark does
- Measurement: build models, prompts and scaffolds against real experiments.
- Direction: unites a field around shared problems; shows what it chose to work on.
- Communication: a common language. "+5 on X" means the same to everyone, across papers.

## The dark side: Goodhart's law
- "When a measure becomes a target, it ceases to be a good measure."
- Figure: optimize against a learned reward model (RM).
  - The proxy score keeps rising as the policy drifts further (KL distance on the x-axis).
  - The true ("gold") score peaks, then falls. Smaller RMs turn down sooner.
- Also shown: a boat-racing game agent chasing points instead of finishing.
- "Grade essays by length and you'll get long essays, not necessarily good ones."

# Agent benchmarks

## What is an agent benchmark?
- Asks a system to finish a task by acting in an environment over many steps, then grades what it accomplished.

| | Exam / chat / safety | Agent |
|---|---|---|
| Input | A prompt | A task + an environment to act in |
| Interaction | One response | Many turns: action ↔ observation |
| Output | Text | A trajectory + a changed environment |

## LM vs agent benchmark
| LM benchmark | Agent benchmark |
|---|---|
| Prompt → LM → response | Task → agent (LM + tools, prompts, memory) |
| | Agent ↔ environment (repo, website, terminal, database, simulated user), many turns |
| Grader: match answer or judge text | Verifier: runs tests or checks the final state |
| Score | Score (the trajectory can also be graded) |

## Single-turn vs agent eval (Lecture 10)
| Single-turn | Agent |
|---|---|
| Prompt: "How many toes does a {ANIMAL} have?" + data ANIMAL = Cat | Task: "Write an MCP server to connect to my app" |
| LLM → response | Tools (web search, file edit) + environment (Python, sandbox) |
| Grading: `response == 18` | Agent reads, edits, runs pytest, says "I did it!" |
| | Grading: run tests to check the server actually works |

- From Anthropic, "Demystifying evals for AI agents."

## Two parts of every agent benchmark
- Task formulation: define the task to be solved.
  - Problem statement, environment, verification.
- Evaluation protocol: settings for how an agent is run on the task.
- Flow: problem statement → agent reads it → works in the environment (ReAct loop) → submission → graded pass/fail.

## Task formulation: problem statement
- What are you asking? What must the agent deliver?

| Fully specified → | | | → Open-ended goal |
|---|---|---|---|
| WebShop: "gluten-free snack pack, price lower than 30.00 dollars" | SWE-bench: a real bug report written for humans | τ-bench: goal hidden in a simulated user, revealed over turns | CodeClash: "Improve your codebase to win the arena." Only an objective |

## Task formulation: environment
- Where does the agent work? What does it start with?

| Environment | Type | Starting assets |
|---|---|---|
| TextWorld | Text game | Room descriptions + inventory |
| WebShop | Simulated store | Search page + catalog |
| WebArena | Self-hosted copies of real sites | Browser + homepages |
| SWE-bench / Terminal-Bench | Docker container | Real repo or shell + tools |
| OSWorld | Full OS virtual machine | Desktop + real apps |

- Ordered from abstract and simulated to real.

## Task formulation: verification
| | Static (vs a fixed reference) | Relative (vs other agents or humans) |
|---|---|---|
| Binary (pass/fail) | Answer match: BrowseComp. Unit tests: SWE-bench, Terminal-Bench. State checks: WebArena, OSWorld, τ-bench | Win/loss vs opponents: CodeClash (into Elo) |
| Continuous (graded) | Partial credit: WebShop. Points: TextWorld, Vending-Bench (net worth) | Normalized to a baseline: AIRS-bench (vs human SOTA) |

## Example: normalized scores
- SWE-fficiency scores agents against a human expert = 1.000×.
  - Claude 4.5 Opus (OpenHands): 0.225×. GPT-5: 0.157×. Gemini 3 Flash: 0.106×.
- A baseline gives the number meaning: here, the best agent scores under a quarter of the expert.

## Evaluation protocol
- Agent settings, not tied to the benchmark itself:
  - Attempts (rollouts, runs) per task.
  - How a run ends: max turns, wall-clock time, compute budget, or the agent stops itself.
  - Model settings: reasoning effort, temperature.
  - Harness fixed or bring-your-own? Which tools? Internet?
  - How runs are combined, and what is reported (cost, turns, tokens).

## Case studies
- The framework applied to coding, web and user-interaction benchmarks, roughly oldest to newest.

## TextWorld
- TextWorld (Côté, 2018): generates text-adventure games.
- Agent reads "You're in a kitchen. There's a closed fridge..." and types "open fridge", "take carrot", "go east".
- Score goes up by a point per quest step.
- Built from a knowledge base (actions, objects) + themes → game → engine.

## ALFWorld
- ALFWorld (Shridhar, 2020): household tasks as text games that mirror a 3D simulator.
  - "Put a pan on the diningtable." "Put some pepper shaker on a drawer."
- Figure: act-only agent loops ("Nothing happens") and fails; ReAct (think + act) plans where to look and succeeds.

## WebShop
- WebShop (Yao, 2022): buy the product that matches an instruction on a simulated store.
- Actions: search[query], choose[product], choose[option], back, next page, buy.
- Graded on how well the item matches (attributes, options, price); reward 0 to 1.

| Method | Score |
|---|---|
| Rules | 45.6 |
| Imitation learning (IL) | 59.9 |
| IL + RL | 62.4 |
| Human expert | 82.1 |

- Using the instruction as the search: right item on page 1 only 32.2% of the time; not in the top 50 56.1%.

## SWE-bench
- SWE-bench (Jimenez, 2023): fix real GitHub issues in popular Python repos.
- Input: issue text + a codebase snapshot (e.g., a scikit-learn bug).
- Output: a patch.
- Graded by the repo's own unit tests: tests that failed before the fix must pass after.

## WebArena
- WebArena (Zhou, 2023): everyday tasks on self-hosted copies of real sites (shopping, forums, GitLab, maps).
- Example: plan a route to all Pittsburgh art museums (Wikipedia + map), then save it to a GitLab repo.
- Actions: click, hover, type, press, scroll, tab, go back, go to URL.
- Task types: information seeking, site navigation, content and config. Graded on the outcome.

## τ-bench (tau-bench)
- τ-bench (Yao, 2024): customer-service agent, domain policy, LLM-simulated user.
- Agent has tools (get user, book, cancel) and a policy as system prompt.
- Example: user wants to change a basic economy flight. Policy: can't modify. Agent offers cancel + rebook.
- Graded on the final database state. User instructions are written so only one outcome is correct.

## Terminal-Bench
- Terminal-Bench (Merrill, 2026): 89 hard tasks from real work, done in a terminal.
- Each task: an instruction, a Dockerfile, tests, an oracle solution.
- The agent gets the container and the instruction; tests and solution stay hidden.
- Example: "Re-implement the COBOL program... in Python. Your script must produce identical results."
- Tests run after the agent: e.g., "1 passed, 2 failed."

## OSWorld
- OSWorld (Xie, 2024): real desktop tasks across apps in a full OS, from screenshots.
- Example: "Update the bookkeeping sheet with my recent transactions."
- Each task has a check script: e.g., confirm Amazon cookies were deleted.
- Graded by checking the final system state.

## CodeClash
- CodeClash (Yang, 2025): agents edit their codebases, then compete head to head; goals, not instructions.
- Tournament: 15 rounds of edits, each followed by a competition.
- Arenas: BattleSnake, CoreWar, Halite, Poker, RoboCode, RobotRumble.

| Model | Overall Elo |
|---|---|
| Claude Sonnet 4.5 | 1389 |
| GPT-5 | 1360 |
| o3 | 1343 |
| Qwen3 Coder | 952 |

## BrowseComp
- BrowseComp (Wei, 2025): obscure facts that take long, creative browsing to find but are easy to check.
- Example: which teams played a 1990–94 match with a Brazilian referee and four yellow cards? Answer: Ireland v Romania.
- Topics: TV and movies (205), science and tech (173), art (127), history (125), sports (123), politics (59), others.

## Vending-Bench
- Vending-Bench (Backlund, 2025): run a simulated vending-machine business over many days.
- Tools: email, web search, balance; restock, set prices, view inventory, collect cash. A main agent and a sub-agent.
- Scored by final net worth.

| Model | Net worth (mean) | Net worth (worst run) |
|---|---|---|
| Claude 3.5 Sonnet | $2,217.93 | $476.00 |
| o3-mini | $906.86 | $369.05 |
| Human | $844.05 | $844.05 |
| GPT-4o | $335.46 | $265.65 |

- The best model beats the human on average, but its worst run is far below; the human is steady.

## AIRS-bench
- AIRS-bench (Lupidi, 2026): 20 ML research tasks from recent papers. No baseline code.
- Each task: {problem, dataset, metric}, e.g., text similarity / SICK / Spearman; SOTA 0.854.
- Agent loop: research → plan → design → train → debug → evaluate.
- Average normalized score: best agents about 0.40; weakest one-shot agent 0.02.

# Grading agents in practice

## Verifiers (Lecture 10)
- Verifier: an outcome-based classifier on the environment's final state.
- Judge it like any classifier, with a confusion matrix:
  - False positive: passes bad work. False negative: fails good work.
- Map each check 1-to-1 to a requirement in the instruction.
- Two kinds: programmatic checks, and agent or LLM judges.

## Three kinds of graders
| | Code | Model | Human |
|---|---|---|---|
| Methods | String match, unit tests, static analysis, outcome and tool-call checks | Rubrics, pairwise comparison, reference-based, multi-judge | Expert review, spot checks, A/B tests |
| Strengths | Fast, cheap, objective, reproducible | Flexible, handles open-ended output | Gold standard; calibrates model graders |
| Weaknesses | Brittle to valid variations | Non-deterministic, costs more, needs calibration | Expensive, slow |

- Source: Anthropic, "Demystifying evals for AI agents."

## Grade with code: precision and recall
- Precision: of the issues flagged, how many are real.
- Recall: of the real issues, how many were flagged.
- Recall alone rewards flagging everything. Precision alone rewards flagging nothing.
- Clean contracts (msa_01 to msa_06 have no issues) punish false flags.

## Test the eval itself
| Fake agent | Returns | Must score |
|---|---|---|
| Oracle | The true answers | 100% exact. If not, the grader is broken |
| Do nothing | Empty list | Low recall |
| Flag everything | All four rules | Low precision (under 50%) |

- Tasks are software. Software has bugs. Run these before trusting any score.

## Fake agents in code
```python
oracle = lambda c: {i["rule"] for i in labels()[c]["issues"]}
nothing = lambda c: set()
everything = lambda c: set(RULES)
for name, fn in [("oracle", oracle), ("do nothing", nothing), ("flag everything", everything)]:
    print(f"{name:16}", {k: f"{v:.0%}" for k, v in run_eval(fn, ALL).items()})
```
- Line 1: the oracle returns the labeled rules for each contract.
- Line 2: do-nothing returns an empty set.
- Line 3: flag-everything returns all four playbook rules.
- Lines 4–5: score each on all 20 contracts; print precision, recall, exact match.

## Consistency: pass@k vs pass^k
- pass@k: right on at least one of k tries. Fits a person picking the best draft.
- pass^k: right on all k tries. Fits repeated legal work.
- The gap between them is inconsistency.
- At 75% per try, pass^3 is only about 42% (0.75 × 0.75 × 0.75).
- The notebook: 10 contracts × 3 runs at temperature 0.3, each with a 95% confidence interval.

## LLM judge, only for open-ended parts
- LLM judge: a model that grades another model's output, e.g., a redline's quality.
- Known biases: favors length, its own style, the first answer shown.
- Give it an expert reference. Ask twice with the order swapped.

| Candidate x | Candidate y |
|---|---|
| "...capped at fees paid during the 12 months before the claim." | "...24 months before the claim, which is a commercially reasonable and widely accepted market standard." |

## Order swap in code
```python
f = re.sub(r"[^A-Z]", "", ask(JUDGE.format(ref=ref, a=x, b=y)).upper())[:1]
s = re.sub(r"[^A-Z]", "", ask(JUDGE.format(ref=ref, a=y, b=x)).upper())[:1]
if f == "A" and s == "B": return "x wins"
if f == "B" and s == "A": return "y wins"
```
- Line 1: ask with x in slot A; keep the first letter.
- Line 2: ask again with the order swapped.
- Line 3: x wins only if picked in both positions.
- Line 4: same for y. Anything else is a tie; "A" twice means position bias.

## Four ways to evaluate
| Method | Pros | Cons |
|---|---|---|
| Automated evals | Fast, reproducible, no user impact, run on every commit | Up-front work; drifts from real use |
| Production monitoring | Real user behavior at scale | Reactive; noisy; no ground truth |
| Reading transcripts | Builds intuition; catches subtle issues | Slow; doesn't scale |
| Human studies | Gold-standard judgments | Expensive, slow; legal needs real experts |

## Roadmap to excellent evals
| Build the suite | Build the harness | Maintain |
|---|---|---|
| 0. Start now, start early | 4. Build a robust eval harness | 6. Check the trajectories |
| 1. Start with manual tests | 5. Design graders thoughtfully | 7. Monitor for saturation |
| 2. Write unambiguous tasks | | 8. Maintain long-term |
| 3. Cover positive and negative cases | | |

# What makes a benchmark good?

## Seven qualities
- Challenging, natural, discriminative, easy to run, easy to verify, interpretable, durable.
- They pull against each other.
- Benchmarks are "living" software; the qualities change as models improve.
- Radar chart: SWE-bench at launch (2023) vs today. Today it is easier to run, but much less challenging, discriminative and durable.

## The general idea
- A benchmark is a vehicle for telling others what your model can and cannot do.
- So make it as easy as possible for others to run.

## Challenging
- Hard enough to expose gaps in behavior or ability.
- Chart: best score over a benchmark's life, from launch (under 10%) to saturated (near 100%).
- The useful window is the middle, while scores are still climbing.

## Natural
| Natural | Contrived |
|---|---|
| "Resolve this GitHub issue in astropy" (SWE-bench) | "Reverse every third word, then sort by length" |
| "Change my flight per airline policy" (τ-bench) | "Navigate a 50×50 grid of random symbols" |
| "Pick up where this coding session left off" (SWE-Together) | "Answer 4-option trivia with no context" |

- Tasks reflect what people want, not difficulty for its own sake.

## Discriminative
| Clustered: can't tell systems apart | Spread: clear ranking |
|---|---|
| Models A–E: 89, 90, 91, 90, 92 | Models A–E: 18, 34, 47, 61, 78 |

- A good benchmark shows fine-grained differences between models.

## Easy to run
- As few commands as possible, ideally one.
  - One script that sets up everything.
  - System requirements written down.
  - Settings exposed on the command line, not in code.
- Examples: `python -m swebench.harness.run_evaluation ...`; `uv run harbor run --path tasks/... --agent mini-swe-agent --model <MODEL> --n-attempts 1`.

## Easy to verify
- Hard natural task: "Write a really good TV show." How do you grade it?

| LM-as-a-judge | Live evaluation | Heuristics |
|---|---|---|
| Score the script with a rubric | Release it; measure ratings, viewers | Proxy: awards, critic scores |
| Favors length, own style; gameable; varies by prompt | Marketing confounds; 1 sample per release; months per data point | Subjective small juries; few winners; lagging |

- Verification must run smoothly and be a useful metric.

## Interpretable
- Easy to see how the model acted. Trajectories can be read.
- Example run viewer: one run's turns, duration, cost and token counts, step by step.
- Failure trace: read issue → find file → edit wrong function → tests: 1 fail → submit anyway.
- You can see exactly which step went wrong.

## Durable
| Private test sets | Refreshed tasks | Robust graders |
|---|---|---|
| Keep part of the test set unpublished | Add tasks after training cutoffs | Close shortcuts, strengthen tests |
| e.g., HLE private split | e.g., SWE-bench-Live, LiveCodeBench | e.g., SWE-bench Verified |

- Resists contamination (test data leaking into training) and gaming.

## Benchmark lifecycle
- Propose → Adapt → Saturate → Replace.

| Area | Path |
|---|---|
| Exams | MMLU → MMLU-Pro → GPQA → HLE |
| Math | GSM8K → MATH → AIME → FrontierMath |
| Chat | MT-Bench → AlpacaEval (length-controlled) → Arena-Hard |
| Coding | SWE-bench Verified → Multilingual → Pro → DeepSWE |
| Computer use / web | WebShop → WebArena → OSWorld → BrowseComp |
| Terminal | Terminal-Bench 1.0 → 2.1 → 4.0 |
| Tool use | ToolEmu → τ-bench → τ²-bench |

## "Good" benchmark checklist
- Challenging: is there headroom to improve?
- Natural: does it reflect real work?
- Discriminative: does it separate the systems you care about?
- Easy to run: can a classmate run it in an afternoon?
- Easy to verify: can tasks be checked automatically and correctly?
- Interpretable: when an agent fails, can you tell why?
- Durable: does it resist shortcuts and contamination?

# What makes a score trustworthy?

## Benchmark vs score
- A good benchmark is someone else's task formulation.
- A trustworthy score is about respecting the evaluation protocol when you run your agent on it.

| Rule | What to do |
|---|---|
| Fair | Match the benchmark's harness, budget, settings |
| Reproducible | Pin and record every version |
| Transparent | Report runs, error bars, cost, exclusions |
| Honest | Never tune on or select by the test set |

## Fair
| Setup | Score |
|---|---|
| Minimal scaffold, 1 attempt | 48% |
| Custom scaffold, 1 attempt | 61% |
| Custom scaffold, best of 5 | 72% |

- Same model, three numbers. Only setup changed.
- Match scaffold and tools, turn/time/cost budgets, model settings, attempts, internet access.
- If you deviate, say how and why.

## Reproducible
- Make every detail explicit so others get the same number. Pin everything:

```
model: my-model-2026-05-01
reasoning_effort: high
temperature: 0.0
harness: mini-swe-agent==1.4.2
dataset: swe-bench-verified@a1b2c3d
image: sha256:9f86d0...
seeds: [0, 1, 2, 3, 4]
```

## Transparent
| Model | pass@1 | ± CI | Cost/task | Output tokens | Steps |
|---|---|---|---|---|---|

## Trustworthy score checklist
- Fair: benchmark's harness, budget, settings? If not, did you say how you deviated?
- Reproducible: model snapshot, harness, dataset and image versions pinned?
- Transparent: runs, error bars, cost and excluded tasks reported?
- Honest: no tuning on test, no best-run picking; the system tested is the one released?

## Summary
- To improve agents, we must measure them. Benchmarks are the main way.
- Three parts: problem statement, environment, metric.
- A protocol sets how an agent is run, so comparisons are fair.
- No single eval rules them all. Track many benchmarks.

# How this applies to us

## A firm's own benchmark
- Problem statement: "List the playbook rules this contract breaks."
- Environment: 20 frozen contracts + the playbook, on the firm's machine.
- Verifier: code compares to `labels.jsonl`; precision and recall.
- Protocol: one call per contract, fixed temperature, 3 runs, report pass^3.

## Fair local-vs-cloud comparison
- "A model on your own machine is good enough" is a claim only an eval can prove.
- Swap the local model, keep the harness, rerun. That is a fair comparison.
- Pin the model tag, prompt and data version, like the reproducible config.

## What to show the partner
- pass^k, not just the average. Lawyers feel inconsistency.
- Error bars: with about 100 documents, expect ±5–10 points. A 3-point gap may be a tie.
- Cost per contract next to the score, like the transparency table.

## Keep it durable
- Keep 20–30% of contracts hidden until the end.
- Add new real contracts over time (refreshed tasks).
- Read 10–20 failures. If every model misses one item, suspect the label.

## Common mistakes
- Tuning on the test set → keep a hidden split.
- Comparing models in different harnesses → you are measuring the harness.
- Claiming a win inside the error bars → say "tied".
- No clean cases → flag-everything looks great.
- Reporting your best of 5 runs as pass@1 → report all runs.

## Check your understanding
**Q: How is an agent benchmark different from an exam benchmark?**
A: It gives a task and an environment instead of a prompt, runs many action-observation turns, and grades the trajectory and final state instead of text.

**Q: What are the two big parts of an agent benchmark?**
A: Task formulation (problem statement, environment, verification) and evaluation protocol (attempts, budgets, model settings, harness, how runs are combined).

**Q: The same model scores 48%, 61% and 72% on one benchmark. How?**
A: Different setups: minimal vs custom scaffold, and 1 attempt vs best of 5. That is why fair scores must match the protocol.

**Q: Model A scores 70% ±4%, model B 67% ±6%, and A costs 3× more. Which is better?**
A: You can't say A is better: the gap is inside the error bars. B gives about the same result for a third of the cost.

**Q: A model averages 90% but scores 60% on pass^3. What does that tell a firm?**
A: It is usually right on a single run, but inconsistent. On many contracts at least one of three runs is wrong.

**Q: Why must the oracle score 100% before you trust an eval?**
A: It returns the true answers. If it scores less, the grader or labels are broken.

**Q: Why ask an LLM judge twice with the order swapped?**
A: Judges favor the first answer. Only a verdict that holds in both orders reflects quality.
