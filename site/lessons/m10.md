## Learning objective
- Build an eval for contract review: four task parts, a code grader, sanity checks, and a consistency score.

## Why evals first
- Before: code is the source of truth. Now: evals are the source of truth.
- Agents are stochastic: the same input can give different outputs.
- Without an eval you can't tell if a change helped, or if a local model is good enough.
- Goodhart's law: when a measure becomes a target, it stops being a good measure.

## Definitions
- Task: one test with defined inputs and success criteria.
- Trial: one attempt at a task.
- Verifier (grader): the logic that scores the agent's work.
- Trajectory (trace): the full record of one trial.
- Agent harness: the code that lets a model act as an agent (prompts, tools, limits).

## The four parts of a task
| Part | Terminal-Bench | Our contract eval |
|---|---|---|
| Request | `instruction.md`: "output a STEP file..." | "List the rules this contract breaks." |
| Environment | `Dockerfile` with the input files | 20 frozen contracts + playbook |
| Stopping rule | turn / time / cost budget | one call per contract |
| Scorer | `test_outputs.py` asserts | code compares to `labels.jsonl` |

- Score the final result, not the steps taken.

## Grade with code: precision and recall
- Precision: of the issues flagged, how many are real.
- Recall: of the real issues, how many were flagged.
- Recall alone rewards flagging everything. Precision alone rewards flagging nothing.
- Clean contracts (msa_01 to msa_06 have no issues) punish false flags.

## Test the eval itself
| Fake agent | Returns | Must score |
|---|---|---|
| Oracle | The true answers | 100% exact. If not, the grader is broken |
| Do nothing | Empty list | Low recall |
| Flag everything | All four rules | Low precision (under 50%) |

- Tasks are software. Software has bugs. Run these before trusting any score.

## Consistency: pass@k vs pass^k
- pass@k: right on at least one of k tries. Fits a person picking the best draft.
- pass^k: right on all k tries. Fits repeated legal work.
- The gap between them is inconsistency.
- At 75% per try, pass^3 is only about 42%.
- The notebook: 10 contracts × 3 runs at temperature 0.3, each with a 95% confidence interval.

## LLM judge, only for open-ended parts
- LLM judge: a model that grades another model's output, e.g. a redline's quality.
- Known biases: favors length, its own style, the first answer shown.
- Give it an expert reference. Ask twice with the order swapped.

| Candidate x | Candidate y |
|---|---|
| "...capped at fees paid during the 12 months before the claim." | "...24 months before the claim, which is a commercially reasonable and widely accepted market standard." |

## Order swap in code
```python
f = re.sub(r"[^A-Z]", "", ask(JUDGE.format(ref=ref, a=x, b=y)).upper())[:1]
s = re.sub(r"[^A-Z]", "", ask(JUDGE.format(ref=ref, a=y, b=x)).upper())[:1]
if f == "A" and s == "B": return "x wins"
if f == "B" and s == "A": return "y wins"
```
- Line 1: ask with x in slot A; keep the first letter.
- Line 2: ask again with the order swapped.
- Line 3: x wins only if picked in both positions.
- Line 4: same for y. Anything else is a tie; "A" twice means position bias.

## A trustworthy score
- Fair: same harness, budget and settings for every model compared.
- Reproducible: pin the model, harness and data versions.
- Transparent: report runs, error bars, cost. With about 100 documents, expect ±5–10 points.
- Honest: never tune on the test set. Keep 20–30% hidden until the end.

## How this applies to us
- "A model on your own machine is good enough" is a claim only an eval can prove.
- Swap the local model, keep the harness, rerun. That is a fair comparison.
- Report pass^k, not just the average. Lawyers feel inconsistency.

## Common mistakes
- Tuning on the test set → keep a hidden split.
- Comparing models in different harnesses → you are measuring the harness.
- Claiming a win inside the error bars → say "tied".
- No clean cases → flag-everything looks great.
- Not reading failures → read 10–20. If every model misses one item, suspect the label.

## Check your understanding
**Q: A model averages 90% but scores 60% on pass^3. What does that tell a firm?**
A: It is usually right on a single run, but inconsistent. On many contracts at least one of three runs is wrong.

**Q: Why must the oracle score 100% before you trust an eval?**
A: It returns the true answers. If it scores less, the grader or labels are broken.

**Q: Why ask an LLM judge twice with the order swapped?**
A: Judges favor the first answer. Only a verdict that holds in both orders reflects quality.
