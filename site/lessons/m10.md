## The big idea

An eval (short for evaluation) is a test set for your agent. It is a list of tasks with known right answers and a way to grade the agent's work.

Think of a bar exam. Before you let a new lawyer loose on clients, you test them on questions where the answers are known. You also make sure the exam itself is fair. A question nobody can answer, or one anyone can pass by guessing, tells you nothing.

The key habit is this: build the eval before the agent. Without it, you can't tell whether a change helped. You can't tell whether a cheap local model is good enough. And you have nothing honest to tell a customer.

## Why it matters for us

- Our pitch to a firm is "a model on your own computers is good enough for this work." Only an eval can prove that.
- Legal work repeats. A reviewer that is right on most runs but wrong on some will feel unreliable. We need a number for consistency, not only an average.
- A good eval lets us compare models fairly. Swap the model, keep everything else the same, and rerun.

## How it works, step by step

1. **Define the four parts of each task.**
   - Request: the instruction, written the way real users write it.
   - Environment: the documents and tools, frozen so they don't change between runs.
   - Stopping rule: time and token limits (a token is roughly a word piece).
   - Scorer: how you decide right or wrong. Check the final result, not the steps taken.

2. **Grade with code wherever you can.** Code is exact and never in a mood. For contract review, compare the list of broken rules the agent found to the true list. Use two numbers:
   - Precision: of the issues the agent flagged, how many were real.
   - Recall: of the real issues, how many the agent flagged.
   You need both. Recall alone rewards flagging everything. Precision alone rewards flagging nothing.

3. **Test the eval itself.** Run three fake agents first:
   - The oracle, which returns the true answers. It must score 100%. If not, your grader is broken.
   - Do nothing. It must score low on recall.
   - Flag everything. It must score low on precision. Clean contracts in the set make sure of that.

4. **Run each task several times.** Models give slightly different answers each run, especially at higher temperature (a setting that adds randomness). Then report two numbers:
   - pass@k: right on at least one of k tries. Fits when a person picks the best of several drafts.
   - pass^k: right on all k tries. Fits repeated business work, where it must be right every time.
   The gap between them is inconsistency. At 75% per try, pass^3 is only about 42%.

5. **Use an LLM judge only for open-ended parts.** An LLM judge is a model that grades another model's output, for example the quality of a rewritten clause. Judges have known biases. They favor whichever answer comes first, and longer answers. So give the judge an expert reference answer, and ask twice with the order swapped.

## Worked example

The firm's rules: liability cap at most 12 months of fees, governing law California or Delaware, renewals at most 1 year, notice at least 30 days. The eval has 20 contracts with known issues, including clean ones.

First, the notebook tests the eval with the three fake agents. The oracle scores 100%. Flag-everything scores low on precision. Good: the eval can tell them apart.

Then the real reviewer runs 3 times per contract at temperature 0.3. The notebook prints the average, pass@3 and pass^3, each with a confidence interval (a range showing how sure we are, given only a handful of contracts).

For redlines, the judge sees an expert rewrite and two candidates. One caps liability at 12 months. The other says 24 months and adds a long sales pitch. The judge is asked twice, in both orders:

```python
f = re.sub(r"[^A-Z]", "", ask(JUDGE.format(ref=ref, a=x, b=y)).upper())[:1]
s = re.sub(r"[^A-Z]", "", ask(JUDGE.format(ref=ref, a=y, b=x)).upper())[:1]
if f == "A" and s == "B": return "x wins"
if f == "B" and s == "A": return "y wins"
```

Line by line: the first line asks the judge with x in slot A, and keeps just the first letter of the answer. The second line asks again with the order swapped. The third line says x wins only if the judge picked x both times, once as A and once as B. The fourth line is the same for y. Any other result is a tie. If the judge picked "A" both times, it was choosing by position, not quality.

## Common mistakes

- **Tuning on the test set.** If you tweak prompts while watching the test scores, the score stops meaning anything. Keep 20–30% of tasks hidden until the end.
- **Comparing models in different harnesses.** The harness is the code around the model: prompts, tools, limits. Change it and you are measuring the harness, not the model.
- **Claiming a win inside the error bars.** With about 100 documents, expect scores to wobble by 5–10 points. If two results overlap, say "tied".
- **No clean cases.** Without contracts that have no issues, a model that flags everything looks great.
- **Not reading failures.** Look at 10–20 failures per model. If every model misses the same item, suspect the label, not the model.

## Check your understanding

**Q: A model scores 90% on average but 60% on pass^3. What does that tell a law firm?**
A: It is right most of the time on any single run, but inconsistent. On many contracts at least one of three runs gets it wrong, and lawyers will feel that.

**Q: Why should the oracle score 100% before you trust an eval?**
A: The oracle returns the true answers. If it can't score 100%, the grader or the labels are broken, and every other score is suspect.

**Q: Why ask an LLM judge twice with the order swapped?**
A: Judges tend to favor whichever answer comes first. Only a verdict that holds in both orders reflects quality rather than position.
