## Learning objective
- Decide when to use one agent or a team, and build the one-agent-plus-checker design that usually wins.

## What is a multi-agent system?
- Multi-agent system (MAS): several agents working on one shared task.
- Orchestration: who assigns work to whom.
- Communication: how agents pass information.
- Coordination: who owns each task, and what must happen first.

## Benefits vs drawbacks
| Benefits | Drawbacks |
|---|---|
| Parallel execution of separable subtasks | Coordination overhead: time and tokens |
| Specialization: own prompt, model, tools | Information loss in handoffs |
| Focused context per agent | Conflicting actions, duplicated work |
| Broader exploration | Error propagation: one mistake misleads others |

- Collaboration helps only when its benefits outweigh the coordination costs.

## The numbers
- Across 260 setups, multi-agent systems averaged −0.3% vs a single agent.
- They helped on wide, separable work. They hurt on step-by-step work.
- CooperBench: one agent solving both tasks beat two agents coordinating.
- On one local GPU, every extra agent is another model call: more waiting.

## When to use SAS vs MAS
| Prefer a single agent when... | Try multiple agents when... |
|---|---|
| Steps depend on each other | Subtasks need little syncing |
| Work shares one state | Information splits into focused contexts |
| One agent meets quality, cost and speed goals | Parallel work fixes a measured bottleneck |
| Check five clauses of one contract | Review 20 separate contracts |

- Start with a strong single-agent baseline. Add agents for a purpose, and measure.

## Orchestration patterns
- Independent: agents work alone; a final step merges outputs.
- Centralized (orchestrator): one agent assigns work and decides what is next.
- Decentralized (swarm): all agents talk to all others.
- Hybrid: an orchestrator, plus limited peer messages.
- Cost: single agent < orchestrated < swarm.

## Handoff vs agent-as-tool
| Handoff | Agent-as-tool |
|---|---|
| Control moves to the receiving agent | Caller keeps control |
| Conversation history follows | Sends a bounded request and selected context |
| Specialist talks to the user next | Result comes back; caller writes the final answer |

- Our default: agent-as-tool. The brief says goal, output format, limits, and when to stop.

## Why teams fail (MAST)
| Cause | Share | Looks like |
|---|---|---|
| System design | 44.2% | Ignoring the task, repeating steps, not knowing when to stop |
| Misalignment between agents | 32.3% | Context lost in handoffs, ignoring each other |
| Weak checking | 23.5% | No verification, or a shallow final check |

- Error amplification: naive merge 17.2×; with a central checker 4.4×.

## Our test: two designs on 8 contracts
- Design A: one call judges all four playbook rules, then code re-checks the numbers.
- Design B: four specialist agents (one per rule) plus a lead agent that merges. 5 calls per contract.
- The notebook prints precision, recall, time and model calls for each.
- Then: 4 parallel copies of Design A review all 20 contracts. That is where a team fits.

## The checker in code
```python
renew = next(x for t, x in secs.items() if "Renewal" in t)
years = re.search(r"\((\d+)\) year", renew); days = re.search(r"(\d+)\)? days", renew)
if years: flags = (flags - {"auto_renewal"}) | ({"auto_renewal"} if int(years.group(1)) > 1 else set())
if days: flags = (flags - {"termination_notice"}) | ({"termination_notice"} if int(days.group(1)) < 30 else set())
```
- Line 1: find the renewal clause.
- Line 2: pull out the years, e.g. "three (3) year", and the notice days.
- Line 3: drop the model's renewal verdict; flag only if renewal is over 1 year.
- Line 4: same for notice: flag only if under 30 days.

## How this applies to us
- Contract review is linked work. Use one agent plus a code checker.
- On one local machine, five agents means five model calls per contract.
- A team fits batch work: many separate contracts, each worker with a written brief.

## Common mistakes
- "More agents is better" → on average it isn't, and costs several times the tokens.
- One-line delegation ("Review this") → brief with goal, format, limits, stop rule.
- Linked steps split into chatty agents → build one fixed workflow.
- No checker → put a code check after the model wherever you can.

## Check your understanding
**Q: Should we split review into an extractor agent, a risk agent and a redline agent that chat?**
A: No. Those steps are linked, so use one workflow with a checker. Split only independent work, like separate contracts.

**Q: Why does a central checker reduce error amplification?**
A: It catches each agent's mistakes before they are merged. In the study, errors grew 4.4× with a checker vs 17.2× without.

**Q: What four things go in a brief for a worker agent?**
A: The goal, the output format, the limits, and when to stop.
