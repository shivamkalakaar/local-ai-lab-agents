## The big idea

A multi-agent system is several AI agents, each with its own role, passing messages to solve one task. It sounds powerful. Picture a team of specialists, each an expert in one thing.

But think about how real teams work. If you need 50 letters stuffed into envelopes, five people finish faster than one. If you need one tricky contract read carefully, five people passing notes will do worse than one careful reader. Each handoff loses detail. Each person's mistake gets passed along.

The research matches this. Across 260 setups, multi-agent systems averaged about the same as a single agent: −0.3%. They helped on wide work that splits cleanly into separate pieces. They hurt on step-by-step work where each step depends on the last.

So the rule is simple. Start with one strong agent plus a separate checker. Add more agents only for wide, separable work, and only when your tests show a gain.

## Why it matters for us

- On one local GPU (the chip that runs the model), agents do not truly run side by side for free. Every extra agent is another model call, and that means more waiting.
- Contract review is mostly linked work. Reading the renewal clause, checking the notice period and drafting a fix all depend on each other. That is exactly where teams struggle.
- Where teams do fit: reviewing 20 separate contracts at once. Each contract is its own job.

## How it works, step by step

1. **Ask: is the work separable?** Can the pieces be done without talking to each other? Twenty contracts, yes. Five clauses that must agree on dates and parties, no.
2. **If not separable, use one agent plus a checker.** One model call does the reading and judging. A checker then re-verifies what can be verified. The best checker is plain code, because code does not guess.
3. **If separable, give each worker a written brief.** A brief says the goal, the output format, the limits, and when to stop. "Review this" is not a brief.
4. **Treat sub-agents like tools.** Call a sub-agent like a function: send a bounded brief, get a short result back. The caller stays in charge. This is called agent-as-tool.
5. **Pass files, not retellings.** When one agent hands work to another, pass the actual document or result. Summaries in messages lose detail.

Why teams fail, according to the MAST study (2025), which sorted failures into three groups:

| Cause | Share of failures | What it looks like |
|---|---|---|
| System design | 44.2% | Ignoring the task, repeating steps, not knowing when to stop |
| Agents misaligned | 32.3% | Context lost in handoffs, ignoring each other |
| Weak checking | 23.5% | No verification, or only a shallow final check |

Another study (Kim et al., 2025) measured error amplification, meaning how much mistakes grow as they pass between agents. Independent agents with a naive merge amplified errors 17.2 times. With a central checker, it was 4.4 times.

## Worked example

The notebook compares two designs on 8 contracts. The playbook has four rules: liability cap, governing law, auto-renewal length, and termination notice.

**Design A** is one agent plus a checker. One call reads the relevant clauses and judges all four rules. Then code re-checks the two number rules directly:

```python
renew = next(x for t, x in secs.items() if "Renewal" in t)
years = re.search(r"\((\d+)\) year", renew); days = re.search(r"(\d+)\)? days", renew)
if years: flags = (flags - {"auto_renewal"}) | ({"auto_renewal"} if int(years.group(1)) > 1 else set())
if days: flags = (flags - {"termination_notice"}) | ({"termination_notice"} if int(days.group(1)) < 30 else set())
```

Line by line: the first line finds the renewal clause. The second line uses a pattern search to pull out the number of years, like "(4) year", and the number of days. The third line says: forget what the model said about renewal; flag it only if the renewal is longer than 1 year. The fourth line does the same for notice: flag it only if notice is under 30 days. The model's opinion is replaced by a fact the code can check.

**Design B** is a team of five. Four specialist agents each judge one rule. A fifth "lead" agent reads their reports and writes the final list. That is five model calls per contract instead of one. The lead also has to turn prose back into rule names, which is another chance to slip.

The notebook prints precision (how many flags were real), recall (how many real issues were found), time and calls for each design. Run it and compare. Then it shows where a team does fit: four parallel copies of Design A reviewing all 20 contracts at once.

## Common mistakes

- **"More agents is better."** On average it isn't, and it costs several times the tokens. On a local box it also costs several times the wait.
- **One-line delegation.** "Review this" gives no rule, no format, no stopping point. The notebook shows a vague team that comments on anything and can't map its prose back to rules.
- **Splitting linked steps into chatty agents.** An "extractor agent", a "risk agent" and a "redline agent" talking to each other is a fixed workflow in disguise. Build it as one.
- **Skipping the checker.** Weak verification is a whole category of failure. Put a code check after the model wherever you can.

## Check your understanding

**Q: Should we split contract review into an extractor agent, a risk agent and a redline agent that chat with each other?**
A: No. Those steps are linked, so use a fixed workflow with one checker. Split only independent work, like many separate contracts in parallel.

**Q: Why does a central checker reduce error amplification?**
A: Without one, each agent's mistake flows straight into the final answer. A checker catches errors before they are merged, so they don't pile up.

**Q: What four things belong in a brief for a worker agent?**
A: The goal, the output format, the limits, and when to stop.
