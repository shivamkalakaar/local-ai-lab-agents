## The big idea

An agent is a language model in a loop. It looks at the task, picks a next step, uses a tool, reads the result, and repeats. It stops when it thinks it can answer.

Picture a new intern with a filing cabinet. You ask, "What is the liability cap in the Acme contract?" The intern opens the index, picks a section, reads it, and decides what to read next. Nobody told them the exact steps. They figured it out as they went. That is an agent.

Now picture a checklist instead. "Open section 7. Read the cap. Write down the number." The intern still reads and thinks, but you fixed the steps. That is a workflow (a process where your code decides the steps and the model only fills in the fuzzy parts).

The main lesson of this module is simple. Most business tasks should be workflows, not agents. Use an agent only when the steps truly depend on what you find.

## Why it matters for us

A law firm checking contracts against its playbook knows the steps. Find the liability clause. Read the cap. Compare it to 12 months. The steps are the same every time. That is a workflow.

This matters even more on a firm's own computers. Local models are smaller. Every choice you hand to a small model is a chance for it to go wrong. Fewer choices means fewer mistakes.

Cost matters too. In one study, a complex agent cost over 50 times more than simple baselines and still scored lower (the "AI Agents That Matter" paper). Always report accuracy together with cost.

## How it works, step by step

An agent has a few parts:

- **The model**, which reads the situation and decides what to do.
- **Tools**, which are plain functions it can ask to run, like "read clause 7.1".
- **Memory**, which here is just the growing list of messages.
- **The environment**, the world it acts on. Here, the contract files.

The loop itself runs like this:

1. Give the model the task, plus a list of tools with short descriptions.
2. The model replies. Either it asks for a tool (a "tool call") or it gives a final answer.
3. If it asked for a tool, your code runs that function and adds the result to the messages.
4. Go back to step 2.
5. Stop when the model answers, or when a safety limit hits.

Four safety limits matter most:

- **A turn cap.** Stop after a set number of rounds. Loops are the most common agent failure.
- **A stuck detector.** If the model makes the exact same call twice, tell it to stop repeating.
- **Errors returned as results.** If a tool fails, send the error message back. The model can often fix its own mistake.
- **A format check.** Small local models sometimes write a tool call as plain text instead of making it. Send that back as an error.

## Worked example

The notebook gives the agent two tools: `list_sections` (show the headings) and `get_clause` (read one numbered clause). Then it asks: "In contract msa_07, what is the liability cap? Quote the clause."

The agent first lists the sections. It sees "7. Limitation of Liability." It then reads clause 7.1. It answers with the cap and the quote. You can watch each turn print out.

Here is the heart of the loop:

```python
for turn in range(max_turns):
    msg = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS, temperature=0).choices[0].message
    messages.append(msg)
    if not msg.tool_calls:
        return {"answer": msg.content, "turns": turn + 1, "tool_calls": calls}
```

- The `for` line is the turn cap. The loop can run only `max_turns` times.
- The next line sends all messages so far, plus the tool list, and gets the model's reply.
- We add that reply to the message list, so the model remembers it next turn.
- If the reply has no tool calls, the model is done. We return its answer.

Then the notebook builds the same task as a workflow:

```python
sec = next(s for s in sections(contract(cid)) if "Liability" in s["title"])
return ask(f"{sec['text']}\n\nWhat is the liability cap, in months of fees? ...")
```

- The first line is plain code. It finds the section whose title says "Liability".
- The second line hands only that one section to the model and asks one narrow question.

The model makes no decisions about where to look. It just reads one clause. The notebook compares both on five contracts and checks the workflow gets at least four right. The workflow is usually faster too.

## Common mistakes

- **Building an agent because it sounds impressive.** If you know the steps, write a workflow.
- **No turn limit.** Without one, a confused agent can loop forever, rereading the same clauses.
- **Crashing on tool errors.** Return the error as text instead. A clear message like "NOT FOUND. Valid clauses: ..." lets the model recover.
- **Reporting accuracy without cost.** Retries can buy accuracy. Show time and cost next to every score.
- **Skipping simple baselines.** Try retrying, or a cheap model first with escalation to a stronger one. These often match complex agents.

## Check your understanding

**Q: A firm wants every NDA checked against its 12-point playbook. Agent or workflow?**
A: Workflow. The steps are known and the same every time. Use the model to read clauses, and do the checks in code where you can.

**Q: What does the stuck detector do?**
A: It notices when the model makes the exact same tool call twice. Instead of running it again, it tells the model to use what it has or answer.

**Q: When does an agent make sense?**
A: When the steps depend on what you find, so you can't write them down in advance. For example, "research this counterparty and tell me what to worry about."
