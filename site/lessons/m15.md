## The big idea

This is where everything comes together. We build one contract reviewer that runs on a local box, hands a lawyer a review packet, and proves itself with an eval.

The design is a fixed workflow, not a free-roaming agent. Think of an assembly line in a careful workshop. Each station does one job. Some stations are skilled workers (the model). Others are gauges and stamps (plain code) that measure and decide. Nothing leaves the line without an inspector's sign-off, and here the inspector is a lawyer.

The model does what it is good at: reading messy text and pulling out terms. Code does what it is good at: comparing numbers to rules, and checking quotes. A person makes the final call.

## Why it matters for us

- This is the product in miniature. A firm can watch it review their contracts, on their computers, with no data leaving the building.
- Every choice traces back to an earlier lesson. That makes the system easy to explain to a partner or an auditor.
- The eval at the end is how we answer the firm's real question: is this good enough, compared with what we use today?

## How it works, step by step

```
contract -> split by section -> read terms (forced form, no tools) -> playbook rules in code
         -> citation check -> draft redlines (writer + code checker) -> review packet
```

1. **Split the contract by section.** Only the sections we need go to the model: renewal, liability, governing law. Less text means fewer chances to get confused (Module 03).
2. **Read terms into a forced form.** The model fills in fixed fields: cap in months, governing law, renewal years, notice days, and an exact quote for each. It has no tools, and copies any instructions aimed at an AI into a "suspicious" field (Modules 02 and 13).
3. **Apply the playbook in code.** Plain code compares the numbers to the firm's rules. Cap at most 12 months, law California or Delaware, renewals at most 1 year, notice at least 30 days. No model judgment here.
4. **Check every citation.** Code confirms each quote really appears in the contract. If it doesn't, the item goes on hold for a person (Module 04).
5. **Draft redlines with a checker.** A redline is a proposed rewrite of a clause. The model writes one, and code checks it contains the fix, such as "twelve" or "12" for the cap. If it fails twice, it's marked "needs a person" (Module 06).
6. **Hand over a review packet.** Issues with exact quotes, proposed redlines, items on hold, suspicious text, the model used, and the time taken. Status: ready for lawyer sign-off.
7. **Evaluate.** All 20 contracts, 3 runs each. Report precision, recall, pass^3 (right on all three runs) and seconds per contract (Module 10).

## Worked example

Take one contract from the set. The reader returns its terms, each with a quote. Then code applies the rules. Here is the liability check:

```python
if need(t.cap_quote, "liability_cap") and (t.cap_unlimited or t.liability_cap_months is None or t.liability_cap_months > PB["max_cap_months"]):
    issues.append({"rule": "liability_cap", "quote": t.cap_quote})
```

In plain words: first, `need` checks that the model's quote is really in the contract; if not, it puts the item on hold. Then the rule flags an issue if liability is unlimited, if no cap was found, or if the cap is more than the playbook's maximum of 12 months. The issue is saved with its quote, so the lawyer can see the exact words.

Suppose the contract caps liability at 24 months and picks New York law. Code flags both. The redline step drafts new text for each, and code checks the cap rewrite mentions twelve months and the law rewrite says Delaware. The packet lists both issues, quotes, redlines, and "READY FOR LAWYER SIGN-OFF".

Then the notebook runs the full eval and prints one line: precision, recall, pass^3 with a confidence range, and seconds per contract. The built-in checks want precision and recall of at least 80%.

**Proving it to a firm.** The pilot plan runs four weeks. First, label 50 contracts with the firm, including clean ones and near-misses, and hide 15. Have two lawyers label the same 20, to see how often experts agree. Then build the workflow, try open models in the same harness, and tune the best small one with GEPA (Module 11). Report results next to the firm's current tool. This is the three-way test: our local box, their current tool, and the same open model rented in the cloud, all on the same contracts and grader.

## Common mistakes

- **A team of agents for the review itself.** The steps are linked. Use one workflow with one checker (Module 09).
- **A memory product that edits itself.** Use logged corrections and approved, versioned lessons (Module 08).
- **Privacy by prompt.** Remove tools and network instead (Module 13).
- **Choosing the model from a leaderboard.** Compare models in the same harness on the firm's own contracts.
- **Training on the eval set, or self-critique with no outside check.** Keep the test hidden, and check with code.

## Check your understanding

**Q: Why does code, not the model, decide whether a clause breaks the playbook?**
A: Comparing a number to a rule is exact work. Code never guesses, so the decision is consistent and easy to explain.

**Q: What happens if the model gives a quote that isn't in the contract?**
A: The citation check fails, and the item is put on hold for a person instead of being reported as an issue.

**Q: What is the three-way test?**
A: Running our local box, the firm's current tool, and the same open model in the cloud on the same contracts with the same grader. It shows whether local is good enough.
