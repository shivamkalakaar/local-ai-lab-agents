## Learning objective
- Define the common design patterns for workflows and agents, and pick the simplest one for a task.

## Workflows vs agents
| | Workflows | Agents |
|---|---|---|
| Control flow | Code | LLM |
| Adaptation | Fixed branches, routes, loops | Chooses next step from observations |
| Best fit | Clear, repeatable structure | Exploration, flexible decisions |
| Example | Classify ticket → retrieve policy → draft reply | Resolve ticket using tools |

- Real systems often combine both.

## Five workflow patterns
| Pattern | What it does | Contract example |
|---|---|---|
| Prompt chaining | Fixed steps, checks between | Extract cap → check → flag |
| Routing | Classify, send to the right handler | Easy clause → code; odd one → model |
| Parallelization | Independent work at once, or voting | All 4 playbook rules at once |
| Orchestrator-workers | One LLM creates subtasks at runtime | Review unknown documents |
| Evaluator-optimizer | Generate, critique, revise | Draft a redline, check, fix |

## Prompt chaining in code
```python
cap = structured(f"{s['text']}\n\nExtract the cap in months of fees (null if unlimited) and quote the sentence.", Cap)   # step 1: LLM
if not quote_is_in_doc(cap.quote, contract(cid)):                                                                     # gate: code
    return {"status": "HOLD", "why": "quote not found in contract"}
ok = cap.months is not None and cap.months <= PB["max_cap_months"]                                                    # step 2: rule in code
return {"status": "OK" if ok else "ISSUE", "months": cap.months}
```
- Line 1: the model extracts the cap and quotes it.
- Lines 2–3: quote not in the contract → HOLD for a person.
- Line 4: the 12-month rule, in code. No cap counts as not OK.
- Line 5: OK or ISSUE. The notebook's check expects ISSUE on msa_07 (24 months).

## Routing and parallelization
- Routing: classify the input first, then send it to the right handler. Saves time and money.
  - Notebook: a regex finds "State of ..." → code answers, no model call. Otherwise → model.
- Sectioning: split independent work and run it together.
  - Notebook: 4 playbook rules on msa_15 in parallel threads. Truth: liability_cap and governing_law fail.
- Voting: run the same input several times; an aggregator decides.

## Evaluator-optimizer
- One LLM generates; another step gives feedback; repeat.
- Two conditions: (1) clear, stateable feedback; (2) something able to give it.
- Notebook: rewrite msa_08's cap (36 months). Code reads the new text, finds every "N months," checks the largest ≤ 12.
- Feedback is specific: "the text says {N} months; the playbook max is 12."

## Who should check: the model or code?
| LLM checker | Code checker |
|---|---|
| "Does the clause meet the playbook? Answer YES or NO only." | Regex finds "N months" / "N years", checks max ≤ 12 |
| A model judging, with no outside signal | Reads the draft text itself, same answer every time |

- Asking an LLM to judge its own responses can lower performance.
- CRITIC: a checker that uses tools (search, code) scored about 75 vs 67 F1 without.

## Four agent patterns
| Pattern | Key insight |
|---|---|
| ReAct | Reason before taking actions |
| Reflexion | Turn feedback from the environment into a short lesson, retry with it |
| CodeAct | Code is the right form for actions |
| ReWOO / LLMCompiler | Plan first, then execute; turns agent work back into a workflow |

## JSON actions vs code actions
| JSON tool call (ReAct) | Code action (CodeAct) |
|---|---|
| One call per turn: read msa_01, then msa_02, ... | One snippet loops over `ids()` and filters by governing law |
| Many turns | Fewer turns when the task needs loops |

- Question: "Which contract ids are governed by Texas, Florida or New York law?" Truth: msa_09, msa_10, msa_15.
- Runs in a restricted namespace: a toy sandbox. Real systems use containers.

## Plan then execute
- One call writes the plan: a list of checks from a fixed menu (`Literal["liability_cap", "governing_law", "auto_renewal", "termination_notice"]`).
- Code runs each check.
- ReWOO: about 40–60% fewer tokens.
- Today, planning shows up mostly as parallel tool calls.

## How this applies to us
- Contract review has known steps. Most of it is chaining plus parallel checks.
- Each step asks the small local model one narrow question; code does the rest.
- Playbook rules live in code, so checks are exact and repeatable.

## Common mistakes
- Checker = same model asking "is this good?" → use code, rules or tools.
- Orchestrator-workers for known steps → if you can list the steps, write a chain.
- Starting complex → begin with a chain; add patterns when your eval shows a gain.
- Checking the model's claim (`d.months`) → check the draft text itself.

## Check your understanding
**Q: When does an evaluator-optimizer loop help?**
A: When the feedback can be stated clearly, something can give it reliably (tests, rules, a tool), and the generator can act on it.

**Q: Why does the chain put a contract on HOLD instead of guessing?**
A: The model's quote wasn't found in the contract, a sign the answer may be wrong, so a person looks.

**Q: How does plan then execute help a small local model?**
A: One planning call, then fixed steps run by code. Fewer open decisions and fewer tokens.
