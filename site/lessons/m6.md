## The big idea

Most AI systems are built from a few standard shapes. Learn them, and you can sketch almost any system on a napkin.

Think of a kitchen. There are a few ways to run it. One cook does steps in order. A host sends each order to the right station. Several cooks work on different dishes at once. A head chef tastes each plate and sends it back if it's wrong. You choose based on the menu, not on what looks fancy.

The five workflow shapes are chaining, routing, parallel, orchestrator-workers, and generator plus checker. On top of these sit a few agent shapes. The rule is always the same. Start with the simplest one that works. Add more only when your tests show it helps.

## Why it matters for us

Contract review has known steps, so most of it fits simple shapes. A chain extracts the cap, checks it, then drafts a fix. Parallel checks each playbook rule at once.

Simple shapes suit small local models. Each step asks the model one narrow question. Code handles the rest. Fewer open choices means fewer chances to drift.

One finding matters a lot. Asking a model "is this good?" with no outside signal does not help. It even made GPT-4-class models worse (course Lecture 6). Checkers should be real checks: code, rules, or tools.

## How it works, step by step

| Shape | What it does | Contract example |
|---|---|---|
| Chaining | Fixed steps, with checks between them | Extract cap, then check it, then draft a fix |
| Routing | Sort the input, send it to the right handler | Easy clause to code, hard one to the model |
| Parallel | Run independent checks at once | Check all four playbook rules together |
| Orchestrator-workers | A model splits the job and hands out parts | Review a pile of unknown documents |
| Generator + checker | Draft, check, revise in a loop | Draft a redline, check it meets 12 months |

And the agent shapes:

1. **ReAct.** Think, act, look at the result, repeat. This is the basic agent loop from module 01 (the ReAct paper, 2023).
2. **Reflexion.** After a clear failure, like a failed test, write a short lesson and retry with it.
3. **CodeAct.** Instead of one tool call per turn, the model writes a small Python program that does several steps at once. Good when a task needs loops over data.
4. **Plan then execute.** One call writes the full plan. Then code runs each step. The course reports about 40 to 60% fewer tokens. This turns agent work back into a workflow.

## Worked example

**Chaining.** The notebook finds the liability section. The model pulls out the cap and quotes the sentence. Then two code gates run:

```python
if not quote_is_in_doc(cap.quote, contract(cid)):
    return {"status": "HOLD", "why": "quote not found in contract"}
ok = cap.months is not None and cap.months <= PB["max_cap_months"]
return {"status": "OK" if ok else "ISSUE", "months": cap.months}
```

- The first line checks the model's quote is really in the contract.
- If not, the contract goes on HOLD. A person looks at it. We don't guess.
- The third line applies the playbook rule in code. No cap, or a cap over 12 months, is not OK.
- The last line returns OK or ISSUE, plus the number.

On msa_07, which has a 24-month cap, the result is ISSUE.

**Routing.** For governing law, a simple text pattern looks for "State of ...". If it matches, code answers with no model call. Only odd cases go to the model.

**Parallel.** The four playbook rules don't depend on each other. The notebook checks them for msa_15 at the same time, each asking the model "PASS or FAIL?" for one clause.

**Generator + checker.** The model rewrites msa_08's cap clause. Code then reads the new text, finds every "N months," and checks the largest is at most 12. If not, it sends back specific feedback, like "the text says 24 months; the playbook max is 12." Note that code checks the text itself, not the model's own claim about it.

**CodeAct.** Asked which contracts use Texas, Florida or New York law, the model writes a short program that loops over all contracts. The notebook runs it in a limited space, a toy sandbox (a fenced-off area for running untrusted code).

## Common mistakes

- **A checker that is just the same model asking "is this good?"** Without an outside signal it burns tokens. Use code or rules.
- **Orchestrator-workers for known steps.** If you can list the steps, write a chain.
- **Starting complex.** Begin with a chain. Add routing, parallel or loops only when tests show a gain.
- **Checking the model's claim instead of its output.** Read the draft text yourself, in code.

## Check your understanding

**Q: When does a generator plus checker loop help?**
A: When the feedback can be stated clearly, something can give it reliably (tests, rules, a tool-using critic), and the generator can act on it.

**Q: How does plan then execute help a small local model?**
A: It makes one planning call, then runs simple fixed steps. Fewer open decisions means fewer chances to drift, and it uses fewer tokens.

**Q: Why does the chain put a contract on HOLD instead of guessing?**
A: Because the model's quote wasn't found in the contract. That is a sign the answer may be wrong, so a person should look.
