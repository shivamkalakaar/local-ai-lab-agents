# Review: Workflows vs Agents

## Where does the control flow lie?
| Model | Workflow / compound AI system | Agent |
|---|---|---|
| A small part of a larger system | Logic and orchestration live in the program | Control flow is the AI model's job |
| e.g. GPT-6 Sol, Claude Fable 5.1 | e.g. email categorizer, news feed summarizer | e.g. customer service agent, coding agent |

- Contract example: "extract the cap, then check it" is a workflow. "Review this data room" is an agent.

## Predictability vs agency
- Chart (LangChain): y-axis predictability, x-axis agency.
  - Workflows sit top-left: high predictability, low agency.
  - Agents sit bottom-right: the curve drops sharply as agency grows.
- Workflows are more predictable: the control flow is in the program logic.
- Agents are more adaptable: the control flow is in the LLM's decisions.

## Workflows vs agents (example graphs)
| Workflow graph | Agent graph |
|---|---|
| start → extract → pick_emoji → add_to_calendar → end | start → model ⇄ tools; model → end |
| A dotted edge from extract can skip straight to end | The model decides each turn: call a tool or stop |

- Same graph tools (LangGraph, module 07) draw both.

## Workflows vs agents (table)
| | Workflows | Agents |
|---|---|---|
| Control flow | Code | LLM |
| Adaptation | Fixed (programmed) branches, routes, loops | Chooses next step from observations |
| Best fit | Clear, repeatable structure | Exploration and flexible decisions |
| Example | Classify ticket → retrieve policy → draft reply | Resolve ticket using tools to investigate |

- Real systems often combine workflows and agents.

# Workflow Design Patterns

## Anthropic's workflow taxonomy
- Source: Anthropic, "Building Effective Agents" (anthropic.com/engineering/building-effective-agents).
- Prompt chaining: break the problem into smaller steps.
- Routing: send the task to the right LLM.
- Parallelization: split the work across several threads.
- Orchestrator-workers: find subtasks, send workers to do them.
- Evaluator-optimizer: generate, critique, iterate on the output.

## Prompt chaining
```
In → LLM call 1 → Gate ─pass→ LLM call 2 → LLM call 3 → Out
                       └fail→ Exit
```
- Split a larger task into a series of smaller steps.
- Gate: a check between steps; on fail, stop early.
- Trades latency for accuracy.
- Use when a task is complicated and gains from being split.

## Prompt chaining in code
```python
cap = structured(f"{s['text']}\n\nExtract the cap in months of fees (null if unlimited) and quote the sentence.", Cap)   # step 1: LLM
if not quote_is_in_doc(cap.quote, contract(cid)):                                                                     # gate: code
    return {"status": "HOLD", "why": "quote not found in contract"}
ok = cap.months is not None and cap.months <= PB["max_cap_months"]                                                    # step 2: rule in code
return {"status": "OK" if ok else "ISSUE", "months": cap.months}
```
- Line 1: the model extracts the cap and quotes the sentence.
- Lines 2–3: the gate. Quote not in the contract → HOLD for a person.
- Line 4: the 12-month rule, in code. No cap counts as not OK.
- Line 5: OK or ISSUE. The notebook's check expects ISSUE on msa_07 (24 months).

## Routing
```
In → LLM router → LLM call 1 / LLM call 2 / LLM call 3 → Out
```
- Classify the input, then send it to the right LLM (different model or prompt per case).
- Helps when a complex task has several categories that are best handled differently.
- Saves money and time: a weaker model for easier cases.
- Notebook: a regex finds "State of ..." → code answers, no model call. No match → model.

## Parallelization
```
In → LLM call 1 / 2 / 3 (at once) → Aggregator → Out
```
- Sectioning: split independent work and run it in parallel (e.g. flag a query safe/unsafe while also answering it).
- Voting: inference-time scaling. Run the same input several times; the aggregator decides.
- Each call can focus on one aspect.
- Notebook: 4 playbook rules on msa_15 in parallel threads. Truth: liability_cap and governing_law fail.

## Orchestrator-workers
```
In → Orchestrator → LLM call 1 / 2 / 3 → Synthesizer → Out
```
- One LLM breaks the task down at runtime and hands parts to worker LLMs.
- Use when you can't predict the kind or number of subtasks.
- Like parallelization, but the subtasks are created on the fly.
- Contract example: a data room with unknown documents. A fixed playbook check doesn't need it.

## Evaluator-optimizer
```
In → Generator ─solution→ Evaluator ─accepted→ Out
         ↑───rejected + feedback───┘
```
- One LLM generates; another evaluates and gives feedback, in a loop.
- Two necessary conditions: (1) clear, stateable feedback; (2) something able to give it.
- Also needed: the generator can improve from the feedback.
- Notebook: rewrite msa_08's 36-month cap. Code reads the new text, finds every "N months", checks the largest ≤ 12.

## Who should check: the model or code?
| LLM checker | Code checker |
|---|---|
| "Does the clause meet the playbook? Answer YES or NO only." | Regex finds "N months" / "N years", checks the max ≤ 12 |
| A model judging with no outside signal | Reads the draft text itself, same answer every time |

- Notebook feedback is specific: "the text says {N} months; the playbook max is 12."
- The checker reads the draft text, not the model's own claim (`d.months`).

## Composition of workflow patterns
- Real systems are compositions of these basic patterns.
- Two examples from the lecture: STORM (writing) and Archon (inference-time search).

## Example: STORM, the task
- STORM (Shao et al., 2024): writes a Wikipedia-style article on a topic from scratch.
- Input: "I'd like to know more about: 2024 Hualien City earthquake."
- Output: a table of contents (background, the earthquake, impact, response, aftermath) and a full cited article.

## Example: STORM, the pipeline
- ① Survey related articles on topic t.
- ② Identify perspectives (several writer personas).
- ③ Read & ask: a Wikipedia-writer agent asks questions to an expert agent.
- ④ Split queries, ⑤ search & sift, ⑥ synthesize: the expert answers from trusted sources.
- Gather all conversations; ⑦ direct-generate a draft outline; ⑧ refine into the final outline, with references.

## STORM as composed patterns
| Part of STORM | Pattern |
|---|---|
| Survey → draft outline | Prompt chaining |
| Writer asks, expert answers, repeat | Roughly evaluator-optimizer |
| Several perspectives each run a conversation | Orchestrator-workers (close to parallelization here) |
| Gather conversations, refine outline | Parallelization + aggregation |

## STORM results
| Method | ROUGE-1 | ROUGE-L | Entity recall | Interest | Organization | Relevance | Coverage |
|---|---|---|---|---|---|---|---|
| Direct Gen | 25.62 | 12.63 | 5.08 | 2.87 | 4.60 | 3.10 | 4.16 |
| RAG | 28.52 | 13.18 | 7.57 | 3.14 | 4.22 | 3.05 | 4.08 |
| oRAG | 44.26 | 16.51 | 12.57 | 3.90 | 4.79 | 4.09 | 4.70 |
| STORM | 45.82 | 16.70 | 14.10 | 3.99 | 4.82 | 4.45 | 4.88 |
| STORM w/o outline stage | 26.77 | 12.77 | 7.39 | 3.33 | 4.87 | 3.35 | 4.37 |

- ROUGE / entity recall: overlap with human-written articles. Rubric grading: 1–5 scale.
- Dropping the outline stage loses most of the gain: each piece of the composition matters.

## Archon: architecture search over inference-time techniques
- Archon (Saad-Falcon et al., 2024): searches for the best way to combine LLM calls.
- Inputs: target benchmarks, an inference-call budget, available LLMs, available techniques.
- Optimizer: Bayesian optimization proposes an architecture, scores it on sample benchmark results, repeats.
- Output: an optimized stack of layers (e.g. generators → critic → ranker → fuser).

## Archon's building blocks
| Technique | What it does | Cost | Domains |
|---|---|---|---|
| Generator | Writes a candidate response from the prompt | 1 call per candidate | All |
| Fuser | Merges several candidates into one | 1 call per output | All |
| Critic | Lists strengths/weaknesses of each candidate | 1 call | All |
| Ranker | Returns the top-K candidates | 1 call | All |
| Verifier | Keeps candidates whose reasoning checks out | 2 calls per candidate | Reasoning |
| Unit test generator | Writes unit tests for the prompt | 1 call | Reasoning |
| Unit test evaluator | Scores each candidate with those tests | 1 call per candidate | Reasoning |

## Archon's architecture for math
- Found by search; worked across the MATH benchmarks explored.
- Layer 1: 4 generators (GPT-4o, Llama 3.1 405B, Qwen 2.5 72B, Wizard 8x22B), n = 5 samples each.
- Then: critic (Claude 3.5 Sonnet) → ranker (Claude 3.5 Sonnet).
- Then: 4 fusers (same four models) → verifier (GPT-4o) → final fuser (Claude 3.5 Sonnet).
- It is parallelization + evaluator steps + aggregation, stacked.

## Archon scales with budget
- Chart: average score on ArenaHardAuto, MATH, CodeContests vs max input/output token budget (10K–100K).
- Archon: about 52–53% at 10K, about 69% at 50K, about 76% at 100K. Highest from 25K on.
- ADAS and AFlow (other search methods) level off around 63–65%.
- Flat lines for reference: MoA about 61%, o1 about 68–69%.
- Archon passes o1 around the 50K budget.

## Workflow recap
- Workflows are simpler to reproduce and debug than agents.
- Five common patterns: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.
- Real workflows are usually larger compositions of these pieces.

# Agent Design Patterns: Reasoning/Acting

## Agents: design how the LLM reasons
```
Human ⇢ LLM call ─action→ Environment
            ↑──feedback────┘
            ⇣ stop
```
- Beyond the tools, we design *how* the LLM reasons and interacts with the environment.
- Four ideas follow, each with one key insight.

| Pattern | Key insight |
|---|---|
| ReAct | Reason before taking actions |
| Reflexion | Self-reflection is useful |
| CodeAct | Code is the right form for actions |
| ReWOO / LLMCompiler | Planning turns agent action back into a workflow |

## ReAct (Yao et al., 2023): reason + act
- Question (HotpotQA): "Aside from the Apple Remote, what other device can control the program Apple Remote was originally designed to interact with?"

| Method | What happens | Result |
|---|---|---|
| Standard | Answers "iPod" | Wrong |
| CoT (reason only) | Reasons from memory: "Apple TV… iPhone, iPad, iPod Touch" | Wrong |
| Act only | Searches, but never thinks; finishes with "yes" | Wrong |
| ReAct | Thought → Search[Apple Remote] → Front Row → Search[Front Row (software)] → "keyboard function keys" | Right |

## ReAct: fine-tuning for agents
- Chart: HotpotQA exact match (EM) by model size (8B, 62B, 540B), prompting vs fine-tuning.
- Prompting, 8B: ReAct about 5, worse than standard (about 16).
- Prompting, 540B: all four methods about 26–29.
- Fine-tuned, 62B: ReAct about 33, best of all; Act about 31.
- The paper found you need fine-tuning for best results. Now fine-tuning models to act as agents is common in post-training.

## ReAct: importance of reasoning
| Prompt method (PaLM-540B) | HotpotQA (EM) | Fever (accuracy) |
|---|---|---|
| Act | 25.7 | 58.9 |
| ReAct | 27.4 | 60.9 |

- Thinking before acting helps on both tasks.
- Thoughts before actions are still very common today.

## Reflexion (Shinn et al., 2023): the algorithm
- Three LMs: Actor (acts), Evaluator (scores the try), Self-reflection (writes a lesson).
- Trajectory = short-term memory. Reflections = long-term memory ("experience").
- Loop: act → evaluate → reflect → append the reflection to memory → try again, until pass or max trials.
- Key insight: turn evaluations and reflections into "memory" (context) for the actor.

## Reflexion: example trajectories
| Task | Evaluation signal | Reflection | Next try |
|---|---|---|---|
| Decision making: "clean some pan, put it on countertop" | Rule/LM heuristic: hallucination | "Pan was not in stoveburner 1" | Takes pan from stoveburner 2; succeeds |
| Programming: match parentheses | Self-written unit tests fail | "Only checks counts, not order" | Checks order; returns correct answer |
| Reasoning: Lanchester and Foster's shared profession | Environment reward: 0 | "Wrongly assumed both had several professions" | Answers "novelist" |

## Reflexion: results
| HotpotQA success (chart) | Start | After trials |
|---|---|---|
| CoT only / ReAct only | about 0.32–0.34 | flat |
| CoT + Reflexion | about 0.32 | about 0.40 by trial 2, then flat |
| ReAct + Reflexion | about 0.32 | about 0.54 by trial 5 |

- Second chart (episodic memory): CoT (GT) only stays about 0.61; adding past trajectories (EPM) reaches about 0.66; EPM + Reflexion reaches about 0.74.
- It's the written reflection that helps, not just replaying past tries.

## Limitations of self-reflection
- Huang et al. (Google DeepMind, 2024), "Large Language Models Cannot Self-Correct Reasoning Yet."

| GPT-4-Turbo | Calls | GSM8K | CommonSenseQA |
|---|---|---|---|
| Standard prompting | 1 | 91.5 | 84.0 |
| "Assume it could be wrong; report problems", round 1 / 2 | 3 / 5 | 88.0 / 90.0 | 81.5 / 83.0 |
| "Review your answer; find problems", round 1 / 2 | 3 / 5 | 90.0 / 90.0 | 74.5 / 81.0 |
| "Verify your answer, explain", round 1 / 2 | 3 / 5 | 91.0 / 91.0 | 81.5 / 83.5 |

- Asking an LLM to judge its own answers lowered scores in every row.
- Reflexion avoids this by using outside feedback from the environment.

## Self-reflection today
- The Huang finding predates reasoning models, which self-correct well while reasoning.
- Today, self-reflection is usually built into the model's reasoning, not forced by the harness.
- Contract example: the model checking "is my 12-month answer right?" adds little. A code check against the contract text adds a real signal.

## CRITIC (Gou et al., 2024): give the verifier tools
- Loop: output → verify → critiques → correct → output.
- The verifier calls external tools: knowledge base (Wikipedia), code interpreter, calculator, text APIs, search engine.
- Chart, AmbigNQ (F1) over 3 iterations:
  - CRITIC (with tools): about 64 → about 75.
  - CRITIC without tools: about 64 → about 67.
  - CRITIC with an oracle: about 80. ReAct baseline: about 65.
- Adding external tools to the verifier helps. Make the verifier an agent.

## CodeAct (Wang et al., 2024): JSON actions
- Task: find the cheapest country (USA, Japan, Germany, India) to buy the phone "CodeAct 1".
- Tools: lookup_rates, lookup_phone_price, convert_and_tax, estimate_shipping_cost, estimate_final_price.
- With JSON actions, one tool call per turn: `{"tool": "lookup_rates", "country": "Germany"}` → 1.1, 0.19 → next call → ...
- Many turns, repeated for every country.
- Answer: Japan, 904.00 USD.

## CodeAct: code actions
```python
for country in countries:
    exchange_rate, tax_rate = lookup_rates(country)
    ...
most_cost_effective_country = min(final_prices, key=final_prices.get)
```
- One action holds the whole loop over four countries.
- Control and data flow of code simplify complex operations.
- Reuses `min` from the Python library.
- Environment returns "Japan 904.0" in one turn.

## CodeAct: more accurate and more efficient
- Chart: success rate and average turns for 8 models, code vs JSON vs text actions.
- gpt-4-1106-preview: about 74% success with code vs about 52% JSON; about 5.5 turns vs about 7.6.
- gpt-3.5-turbo-0613: about 51% with code vs about 27% JSON.
- Llama-2-70b-chat: about 11% with code vs about 4% JSON.
- Code as action: higher success and fewer turns.

## JSON actions vs code actions (our notebook)
| JSON tool call (ReAct) | Code action (CodeAct) |
|---|---|
| One call per turn: read msa_01, then msa_02, ... | One snippet loops over `ids()` and filters by governing law |
| Many turns | Fewer turns when the task needs loops |

- Question: "Which contract ids are governed by Texas, Florida or New York law?" Truth: msa_09, msa_10, msa_15.
- Runs in a restricted namespace: a toy sandbox. Real systems use containers.

## Planning then executing
- Key insight: planning turns the agent's actions back into a workflow.
- Plan all tool calls first; run them without asking the model after each step.

## ReWOO (Xu et al., 2023): reasoning without observation
- Planner: writes the full plan with placeholders. `#E1 = Wikipedia[The Hennchata]`, `#E2 = LLM[main ingredient? Given #E1]`, `#E3 = Wikipedia[#E2]`, `#E4 = LLM[cognac house? Given #E3]`.
- Worker: runs each step, fills in the evidence.
- Solver: reads the plans plus evidence, gives the answer: "Jas Hennessy & Co."
- The model is not called between tool steps.

## ReWOO: fewer tokens, higher accuracy
| Benchmark | ReAct | ReWOO |
|---|---|---|
| Curated | about 0.65 accuracy, about 1,850 tokens | about 0.70, about 1,050 tokens |
| Public | about 0.58, about 3,600 tokens | about 0.61, about 1,300 tokens |

- Read from the chart. Direct answers: about 0.53–0.55 with almost no tokens; CoT: about 0.60.
- Planning, then executing, gives higher accuracy with fewer tokens.

## Plan then execute (our notebook)
```python
class Plan(BaseModel):
    checks: list[Literal["liability_cap", "governing_law", "auto_renewal", "termination_notice"]]
```
- `Plan`: the plan's shape. A list of checks from a fixed menu.
- `Literal[...]`: the model can only pick these four names.
- One call writes the plan; code runs `check_rule` for each check.

## LLMCompiler (Kim et al., 2024)
- Question: "How much does Microsoft's market cap need to increase to exceed Apple's?"
- Function-calling planner writes a DAG (graph of tasks): `$1 = search(Microsoft)`, `$2 = search(Apple)`, `$3 = math($1 / $2)`, `$4 = llm($3)`.
- Task fetching unit sends ready tasks to the executor and resolves dependencies.
- Differences from ReWOO: parallel execution and dynamic replanning.

## LLMCompiler vs ReAct
| ReAct | LLMCompiler |
|---|---|
| Thought → search(Scott Derrickson) → observe | Plan: `$1 = search(Scott Derrickson)`, `$2 = search(Ed Wood)` |
| Thought → search(Ed Wood) → observe | Both searches run in parallel |
| Thought → finish(yes) | One LLM step → finish(yes) |

- Question: "Were Scott Derrickson and Ed Wood of the same nationality?"
- Latency speedup: 1.8x.

## LLMCompiler results
| Benchmark | Method | GPT acc. | GPT latency (s) | Speedup | LLaMA-2 70B acc. | Speedup |
|---|---|---|---|---|---|---|
| HotpotQA | ReAct† | 62.47 | 7.12 | 1.00x | 54.40 | 1.00x |
| HotpotQA | LLMCompiler | 62.00 | 3.95 | 1.80x | 57.83 | 1.40x |
| Movie Rec. | ReAct† | 72.47 | 20.47 | 1.00x | 70.60 | 1.00x |
| Movie Rec. | LLMCompiler | 77.13 | 5.47 | 3.74x | 77.80 | 2.82x |
| ParallelQA | ReAct | 89.09 | 35.90 | 1.00x | 59.59 | 1.00x |
| ParallelQA | LLMCompiler | 89.38 | 16.69 | 2.15x | 68.14 | 2.27x |
| Game of 24 | Tree-of-Thoughts | 74.00 | 241.2 | 1.00x | 30.00 | 1.00x |
| Game of 24 | LLMCompiler | 75.33 | 83.6 | 2.89x | 32.00 | 2.09x |

- OpenAI parallel function calling sat in between (e.g. HotpotQA 4.42 s, 1.61x).

## Reasoning/acting recap
- ReAct: reasoning before acting is useful.
- Reflexion: self-reflection is now part of the model's reasoning.
- CodeAct: code is a good form for actions.
- ReWOO / LLMCompiler: today this is mostly parallel tool calls. Planning still matters.
  - Workflows are still sometimes used to orchestrate sub-agents.

# Agent Design Patterns: Context

## Agents: the context manager
```
Human ⇢ [ Context manager ( LLM call ) ] ─action→ Environment
                    ↑──────feedback─────────┘
```
- Context manager: the code that decides what goes into each LLM call.
- It sits around the LLM call, inside the agent loop.

## Prompt engineering vs context engineering
| Prompt engineering (single turn) | Context engineering (agents) |
|---|---|
| Context window holds a system prompt and a user message | Many possible inputs: docs, tools, memory files, instructions, domain knowledge, message history |
| One answer comes back | Curation picks what fits in the window each turn; tool results feed back into history |

- Source: Anthropic, "Effective context engineering for AI agents."

## Why focus matters: needle in a haystack
- Test: hide a fact in a document; ask Claude 2.1 (200K window) to retrieve it.
- Run at 35 document depths × 35 context lengths (1K to 200K tokens); GPT-4 graded the answers.
- Heatmap: almost all green (correct) at short lengths; more and more red (missed) as length grows.
- Retrieval accuracy dropped as the context got longer.

## Context engineering: two principles
| Focus the context | Preserve continuity |
|---|---|
| Keep only what the task needs in the window | Keep requirements, goals, constraints and progress across turns |
| The whole history does not need to be there | In practice, also preserve the KV cache (the model's saved work on the prompt prefix) |
| Too much information is context bloat | |

## Five context patterns
- Persistent event log: rebuild the context from the system's events.
- Memory offloading: store knowledge in memory so the context can be pruned.
- Compaction: summarize earlier context into a short description.
- Observation masking: hide or cut old tool outputs.
- Context isolation: sub-agents for specific tasks; each sees only what it needs.

## Persistent event log: OpenHands
- Event stream: every action and observation, in order (user message, run code, file created, run server, browse page, ...).
- Agent: event history → new action. Runtime: action → observation (Docker sandbox with Python, bash, browser).
- Abstraction: event stream = list of actions and observations.

## Event log → LLM input
```
Event list → filter LLM-convertible events → group action events by llm_response_id → convert to messages → LLM input
```
- Everything is kept exactly as it happened, even if the LLM input must change. The log can be append-only.
- Every LLM call rebuilds its input from the log.
- Outside observers can hook into the log to monitor the system.

## Memory offloading: MemGPT
| Write to memory | Read from memory |
|---|---|
| User: "my bf james baked me a birthday cake" | User: "yeah we went to six flags!" |
| System alert: memory pressure | `recall_storage.search("six flags")` → 3 old messages |
| `working_context.append("Birthday is February 7")`, `("Boyfriend named James")` | Agent: "Did you go with James? It's so cute how you both met there!" |

- MemGPT (Packer et al., 2023): storing facts in memory or files frees parts of the context to prune.
- Module 08 covers memory in depth.

## Compaction
| Raw agent | LLM summary |
|---|---|
| System prompt, user prompt | System prompt, user prompt |
| Reasoning 1, action 1, observation 1 | Summary 1 (of turns 1–2) |
| Reasoning 2, action 2, observation 2 | |
| Reasoning 3, action 3, observation 3 | Reasoning 3, action 3, observation 3 |

- Have the LLM summarize earlier reasoning, actions and observations.
- Fewer tokens for the same history.
- The compaction step itself can be an agent.

## Observation masking: where the tokens go
- Pie chart (raw coding agent, arxiv 2508.21433): observations 83.9%, reasoning 9.6%, actions 6.5% of tokens.
- Tool outputs are most of the context.

## Observation masking: how it works
| Raw agent | Observation masking | LLM summary |
|---|---|---|
| Keep everything | Keep reasoning and actions; replace old observations with a short mask | Replace old turns with one summary |

- Instead of an LLM summary, cut old observations.
- Especially useful for coding agents, where observations can be very long.

## Observation masking: results
| Model (chart) | Raw agent | Observation masking | LLM summary |
|---|---|---|---|
| Gemini 2.5 Flash | about 33% at about $0.42 | about 35–36% at about $0.18 | about 36% at about $0.25 |
| Gemini 2.5 Flash (thinking) | about 40% at about $0.56 | about 36–37% at about $0.24 | about 31–32% at about $0.25 |
| Qwen3-Coder 480B | about 53–54% at about $1.29 | about 55% at about $0.61 | about 54% at about $0.64 |

- Solve rate vs cost per task. Masking cut cost about in half; solve rate held or rose in 2 of 3 models.
- A simple cut can match an LLM summary.

## Context isolation
- A planner sends work to Agent 1 and Agent 2; each has its own context window.
- Parallelize work with isolated context windows.
- Each sub-agent sees only what its task needs.

## Context isolation: progressive disclosure
- You don't need every tool and document in the first prompt. Reveal them when needed.
- Example: a skill file, `pdf/SKILL.md`.
  - YAML front matter: `name: pdf`, a one-line description. Always loaded.
  - Markdown body: how-to and code. Read only when the task needs PDFs.
  - Further files (`./reference.md`, `./forms.md`) loaded only if needed.

## Patterns combine
- These strategies are all compatible.
- Offload knowledge to memory, then compact the context.
- Build the context from an event log and also truncate observations.
- Real systems combine many or all of them.

## Context management taxonomy (LangChain)
| Write | Select | Compress | Isolate |
|---|---|---|---|
| Long-term memories (across sessions) | Retrieve relevant tools | Summarize to keep relevant tokens | Partition context in state |
| Scratchpad (within a session) | Retrieve from scratchpad | Trim to remove irrelevant tokens | Hold in environment / sandbox |
| State (within a session) | Retrieve long-term memory | | Partition across multi-agent |
| | Retrieve relevant knowledge | | |

- Long-term memory → module 08 (memory). Multi-agent partitioning → module 09.

## Context recap
- Event logs, memory, compaction, observation masking and context isolation are key context patterns.
- Real systems combine them.
- Two principles drive them: keep the context focused, and preserve continuity.

# Case Study: Pi

## Pi: design philosophy
- "Pi is a minimal agent harness. Adapt Pi to your workflows, not the other way around."
- Very basic; people build many extensions on top to add features of mainstream harnesses.
- What Pi lacks: no sub-agents, no permission checks, no plan mode, no agent to-do lists, no bash in the background.

## Pi tools
| Built-in | Purpose |
|---|---|
| read | Read text files and supported images |
| bash | Run shell commands |
| powershell | Run PowerShell commands on Windows |
| edit | Apply exact text replacements to a file |
| write | Create or overwrite a file |
| grep / find / ls | Search contents / find paths by glob / list a directory |

- Only read, bash, edit and write are on by default. Minimal tool bloat.
- All other tools are subsets of bash.

## Pi agent loop
- ReAct-style: reason before acting, with JSON tool calls.
- Context is a tree, not a list: go back to an earlier message and branch to a different thread.

## Pi context management
- Uses three patterns from this lesson:
  1. Event log → LLM input conversion.
  2. Progressive disclosure through skill files.
  3. Compaction.
- What the LLM sees: `system | summary | usr | ass | tool | tool | ass | tool`.
  - system: the prompt. summary: from compaction. The rest: messages kept since the cut point (`firstKeptEntryId`).

## Pi safety
- Pi runs with the same permissions as its process.
- No pop-ups asking for permission.
- Treat it as always on auto-mode with no protections.
- Module 13 covers guardrails.

## Pi recap
- Minimalist harness; the community has built many extensions.
- Default tools: bash, read, write, edit.
- ReAct-style agent.
- Context: event log, progressive disclosure, compaction.
- No safeguards built in.

# How this applies to us

## Contract review is mostly a workflow
- The steps are known: find the clause, extract the term, check the rule, flag or draft.
- So most of it is chaining plus parallel checks. No orchestrator needed.
- Routing sends easy clauses ("State of Delaware") to code and only odd ones to the model.

## Narrow questions for a small local model
- Each step asks the local model one narrow question; code does the rest.
- Plan then execute: one planning call, then fixed steps. Fewer open decisions and fewer tokens.
- LLMCompiler's numbers held on an open model too (LLaMA-2 70B ran 1.4x–2.8x faster).

## Checkers that use outside signals
- Playbook rules live in code: exact and repeatable.
- The code checker reads the draft text, like CRITIC's tool-using verifier.
- Don't ask the same small model "is this good?": Huang et al. showed that lowers scores.

## Context on a firm's own machine
- Local models have smaller windows; focus matters more.
- Mask old tool outputs (whole contract texts) once a clause is extracted.
- Keep an append-only event log of every step: an audit trail for the firm.

## Common mistakes
- Checker = same model asking "is this good?" → use code, rules or tools.
- Orchestrator-workers for known steps → if you can list the steps, write a chain.
- Starting complex → begin with a chain; add patterns when your eval shows a gain.
- Checking the model's claim (`d.months`) → check the draft text itself.
- Keeping every tool output in context → mask or compact old observations.

## Check your understanding
**Q: When does an evaluator-optimizer loop help?**
A: When feedback can be stated clearly, something can give it reliably (tests, rules, a tool), and the generator can act on it.

**Q: Why does the chain put a contract on HOLD instead of guessing?**
A: The model's quote wasn't found in the contract, a sign the answer may be wrong, so a person looks.

**Q: Reflexion and the Huang et al. study both ask a model to reflect. Why does one help and the other hurt?**
A: Reflexion reflects on outside feedback (test results, environment reward). Huang et al. asked the model to judge itself with no outside signal, and scores dropped.

**Q: Why do code actions take fewer turns than JSON actions?**
A: One code snippet can loop, store values and call `min`, so it does many tool calls in one turn. JSON allows one call per turn.

**Q: How do ReWOO and LLMCompiler differ?**
A: Both plan first. LLMCompiler also runs independent steps in parallel and can replan.

**Q: What is the difference between compaction and observation masking?**
A: Compaction has an LLM summarize old turns. Masking just cuts old tool outputs and keeps reasoning and actions.

**Q: Name the three context patterns Pi uses.**
A: Event log to LLM input, progressive disclosure through skill files, and compaction.
