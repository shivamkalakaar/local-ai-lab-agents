# What is a Language Model?

## A language model is a probability
- Language model: gives the probability of a sequence of tokens.
- Token: a word or piece of a word, the unit the model reads and writes.
- Formula: `P(x_1..x_T) = P(x_1) × P(x_2 | x_1) × ... × P(x_T | x_1..x_T-1)`
  - Left side: probability of the whole sequence.
  - Right side: product, from first to last token, of each token's probability given the tokens before it.

## Worked example: "The class was about agents."
| Step | Probability |
|---|---|
| P(The) | 0.0377 |
| P(class \| The) | 0.0001 |
| P(was \| The, class) | 0.0344 |
| ... | ... |
| P(. \| The, class, was, about, agents) | 0.0252 |
| Product of all steps | 1.2e-17 |

- Numbers this small underflow. In practice we add log probabilities instead of multiplying.

## Generative vs discriminative models
| Discriminative | Generative |
|---|---|
| Learns to tell classes apart (draws a boundary) | Learns the distribution of the data itself |
| Logistic regression, SVM | Naive Bayes, diffusion models |

- Knowledge check: is a model of `P(x_1..x_T)` generative or discriminative?

## LMs are generative
- `P(x_1..x_T)` is a joint probability over all tokens: a distribution over text.
- So a language model is generative.
- Generative means we can sample from it: draw new text one token at a time.

## Sampling the next token
"The class was about ___"

| Next token | Probability |
|---|---|
| to | 0.3171 |
| as | 0.0491 |
| the | 0.036 |
| a | 0.033 |
| two | 0.0147 |
| how | 0.0124 |
| getting | 0.0101 |
| three | 0.01 |
| time | 0.0091 |
| " | 0.0081 |

- The model scores every token in its vocabulary. Here "to" is most likely.

## You don't have to pick the most likely token
"The class was about to ___"

| be | begin | go | start | get | become | enter | take | end | graduate |
|---|---|---|---|---|---|---|---|---|---|
| 0.1501 | 0.0855 | 0.0627 | 0.0496 | 0.0390 | 0.0342 | 0.0313 | 0.0220 | 0.0192 | 0.0180 |

- The slide samples "begin", the second choice, then "." → "The class was about to begin."
- How you pick is the sampling (decoding) strategy.

## Decoding strategies
- Greedy: always take the most likely token.
- Top-k: sample only from the k most likely tokens.
- Nucleus (top-p): sample from the smallest set of tokens whose probabilities add up to p.
- Beam search: keep several partial sentences at once (next slide).

## Temperature
- Temperature T: divide the scores by T, then renormalize so they sum to 1.
- Example: next token for "I am tired, I will take a ___" (nap, break, rest, bath, shower).

| T | "nap" | Shape |
|---|---|---|
| 0.1 | about 100% | Almost always "nap" |
| 0.5 | about 75% | "break" about 18%, rest tiny |
| 1.0 | about 50% | break ~25%, rest ~11%, bath ~8%, shower ~7% |
| 2.0 | about 34% | All five between ~12% and ~34% |

- Low T = predictable. High T = varied.

## Beam search
- Keep the best few partial sequences ("beams") at each step, not just one.
- Each beam grows by its likely next tokens; keep the top few overall.
- Slide example: from "start", beams "the" and "arrived" grow into "the green witch", "the witch who", ...
- Finds higher-probability sentences than greedy, but costs more time and memory.

## Considerations for sampling
- Each strategy has trade-offs.
- Temperature and top-p / top-k add diversity.
- Pick by task:
  - Math and code are predictable: use lower temperature.
  - Creative writing may benefit from more diversity.
- Pick by budget: beam search costs more time and memory.
- Our rule: temperature 0–0.3 for extraction and structured output.

# Language Model Architecture

## A brief history of LM architectures
| Model | When |
|---|---|
| N-gram models | Before the 2010s |
| First neural language model | 2003 |
| Recurrent neural network (RNN) LMs | 2010 |
| Long short-term memory (LSTM) | Invented 1997, popular for LMs from 2014 |
| Transformer | 2017 |

## Transformers: Attention Is All You Need (2017)
- Vaswani, Shazeer, Parmar, Uszkoreit, Jones, Gomez, Kaiser, Polosukhin.
- The original has an encoder (reads input) and a decoder (writes output).
- Decoder parts: masked multi-head attention, feed forward, "add & norm", repeated N times, then linear + softmax → output probabilities.
- Today's LLMs keep only the decoder: a decoder-only transformer.

## Decoder-only: from tokens to vectors
- Input: "The class was about".
- Embedding: each token becomes a vector (a list of numbers).
- Positional embedding: a second vector that encodes the token's position.
- Add the two. Each token is now one vector that knows "what" and "where".
- The lecture warns: pay close attention to the next part, the rest depends on it.

## Attention, step 1: queries, keys, values
- Layer norm: rescale each token's vector first.
- Multiply by three weight matrices to get three activations per token:
  - Query (Q = x·W_Q): what this token is looking for.
  - Key (K = x·W_K): what this token offers.
  - Value (V = x·W_V): the content it passes on.

## Attention, step 2: mix information across tokens
- Formula: `Attention(Q, K, V) = softmax(Q·Kᵀ / √d_k) · V`
  - `Q·Kᵀ`: how well each query matches each key; one score per token pair.
  - Causal mask: a token may only look at itself and earlier tokens, never later ones.
  - `÷ √d_k`: scale scores by the key size so they don't get too large.
  - `softmax`: turn each row of scores into weights that sum to 1.
  - `· V`: each token's output is a weighted mix of earlier tokens' values.

## Attention, step 3: project back and add
- W_O: multiply to project back to the model's vector size.
- Residual connection: add the result to the token's original vector.
  - The layer only adds new information; nothing is overwritten.

## Multi-head attention
- 1. Multiple weight matrices: several sets of W_Q, W_K, W_V ("heads"), each with its own attention pattern.
- 2. Concatenate the heads' outputs.
- 3. A bigger projection matrix W_O maps them back to model size.
- Result: a multi-head, causal self-attention layer.

## The transformer block
- Layer norm → multi-head causal self-attention → add (residual).
- Layer norm → feed forward → add (residual).
  - Feed forward: a small network applied to each token on its own.
- Stack the block N times.

## From vectors to next-token probabilities
- Final layer norm, then the LM head: a matrix that maps each vector to one score per vocabulary token.
- Softmax turns the scores into probabilities.
- This happens at every position at once: each token predicts the token after it.
- The last position gives the distribution we sample from ("to" 0.3171, ...).

## Attention vs recurrence
| Layer type | Work per layer | Sequential steps | Max path length |
|---|---|---|---|
| Self-attention | O(n²·d) | O(1) | O(1) |
| Recurrent | O(n·d²) | O(n) | O(n) |
| Convolutional | O(k·n·d²) | O(1) | O(log_k(n)) |
| Self-attention (restricted) | O(r·n·d) | O(1) | O(n/r) |

- n = sequence length, d = vector size. Table from Attention Is All You Need.
- O(1) sequential steps: all tokens train in parallel on GPUs. A huge deal.
- O(n²) in length: long context becomes expensive.

## Linear attention: drop the softmax
- Idea: remove the softmax from attention.
- Then everything is linear, so we can change the order of multiplication.
  - Softmax attention: `(Q·Kᵀ)·V`, an n × n score table.
  - Linear attention: `Q·(Kᵀ·V)`, multiply K and V first.
- `Kᵀ·V` is a fixed-size matrix, the state S, no matter how long the text is.

## Linear attention: the update rule
- Process tokens one at a time, like an RNN (recurrent network).
- Each new token adds its key × value into the state: S1 → S2 → S3 → S4.
- The query reads from the state to make the output.
- Clear unimportant memory: the update can fade or overwrite old content in S.
- Save the state and carry it to the next token. Memory stays constant.

## Linear attention is faster and uses less memory
- Figure (Transformers are RNNs): forward + backward pass time and GPU memory vs sequence length, 2^9 to 2^16 tokens, log scale.

| | Softmax attention | Linear attention |
|---|---|---|
| Growth with length | Square (time and memory) | Linear |
| Longest length shown | Stops at 2^12 tokens | Runs to 2^16 tokens |
| At 2^12 tokens | More than 10× slower, more than 20× the memory of linear | Fastest and smallest of all methods |

- Reformer (lsh-X, another efficient method) also scales linearly but sits above linear attention.

## Full softmax attention vs linear attention
| Full softmax attention | Linear attention |
|---|---|
| O(n²) in context length | O(n) in context length |
| Every token can refer back to every earlier token | New tokens interact with a compressed state |
| Helps long context | Harder for long context (results in module 03) |
| KV cache (memory) grows O(n) | State uses constant memory |

## In practice: mix global and linear attention
- Figure (DeltaNet Explained, Songlin Yang): two hybrid stacks.
  - Alternate SWA and DeltaNet layers. SWA = sliding-window attention, each token sees only nearby tokens.
  - Mostly DeltaNet layers, with a global (full) attention layer every few layers.
- DeltaNet: a linear-attention layer with a smarter state update.

## Hybrids help retrieval most
| Model | Wiki perplexity ↓ | Avg. common-sense ↑ | Avg. retrieval ↑ |
|---|---|---|---|
| DeltaNet | 28.24 | 42.1 | 22.7 |
| + Sliding attention | 27.06 | 42.1 | 30.2 |
| + Global attention | 27.51 | 42.1 | 32.7 |

- Perplexity: how surprised the model is by real text, lower is better.
- Common sense stays the same. Retrieval (finding facts in the context) gains the most from a little full attention.

## Kimi K3: a real hybrid
- Each repeating unit (figure from the Kimi K3 paper):
  - 3× linear attention (Kimi Delta Attention) + feed forward.
  - 1× multi-head latent attention (Gated MLA, a full-attention layer) + feed forward.
- Feed forward is a mixture of experts (MoE): a router sends each token to a few expert networks, plus shared experts.
- So most layers are cheap linear attention; a few are full attention.

## Why does architecture matter for agents?
- Agents deal with extremely long contexts.
- Inference efficiency is a design choice when building agentic systems.
- Knowing the architecture helps you pick the right model for your agent.
- Build the harness and scaffolding around your model's strengths and weaknesses.

# Training

## Defining the loss: the data
- Training data example: "The class was about how agents work, and how to build AI systems that use tools, retrieve information, and carry out tasks across multiple steps…"
- Feed "The class was about" and ask the model for the next token.
- The model predicts its distribution: "to" 0.3171, "as" 0.0491, ..., "how" 0.0124.
- The data says the real next token is "how".

## Defining the loss: one token
- Look only at the probability the model gave the true token: "how" = 0.0124.
- Loss = −log(0.0124) = 1.907 on the slide (that value uses log base 10).
- Low probability on the true token → high loss. Training pushes it up.

## Cross-entropy loss
- Formula: `L = − Σ_{i=1..V} y_i · log(p_i)`
  - `Σ over V`: for every token in the vocabulary.
  - `y_i`: 1 if this is the token in the data, 0 if not.
  - `log(p_i)`: the log probability the model gave that token.
- Only the true token's term survives, so `L = −log(p_true)`.

## Pretraining data pipeline
```
HTML → text extraction → language ID → rule-based filters → quality filters → deduplication → final training data
```
- Language ID: keep the languages you want.
- Rule-based filters: drop pages by simple rules (length, repetition, bad words).
- Quality filters: a model scores how useful a page is.
- Deduplication: remove repeated documents.

## Data mixing: how much of each source?
- Olmix (arXiv 2602.12237), three steps:
  - 1. Swarm: train many small proxy models, each on a different mix p; record performance.
  - 2. Regression: fit a model that predicts performance f(p) from the mix.
  - 3. Optimization: pick the mix p* that the fitted model says is best.

## Midtraining
- Midtraining: late in pretraining, shift the data mix toward your target domains (math, code, etc.).
- Example (OpenAthena, "Curating 25 Trillion Tokens"): data sorted by domain and quality band Q0–Q4.
  - The pretraining mix and the cooldown (final phase) mix weight each domain and quality band differently.

## Put domain data into pretraining
- The Finetuner's Fallacy (arXiv 2603.16177): mix 10–50× repeats of the domain dataset into general pretraining data.
- Test: base models with 200B pretraining tokens, then finetune.
  - Specialized pretraining (33× domain data) vs general pretraining.
- The specialized model reaches a lower domain test loss and forgets less general skill during finetuning.

## Why midtraining helps
- Midtraining Bridges Pretraining and Posttraining Distributions (arXiv 2510.14865).
- Schematic: standard finetuning jumps straight from the pretrained model to the target, across a region where the training signals conflict.
- Midtraining takes a path through a middle point (θ_mid) where they agree.

## Posttraining: instruction finetuning
- Instruction finetuning: train on (instruction, good answer) pairs.
- Flan (Scaling Instruction-Finetuned LMs, arXiv 2210.11416): 1.8K tasks.
  - "What is the boiling point of Nitrogen?" → "-320.4F"
  - Chain-of-thought finetuning: answers with step-by-step reasoning.
- The model then generalizes to unseen tasks, e.g. "Can Geoffrey Hinton have a conversation with George Washington?" → reasons → "no".

## Learning from human preferences (RLHF)
- InstructGPT (arXiv 2203.02155), three steps:
  - 1. Labelers write good answers; finetune with supervised learning (SFT).
  - 2. Labelers rank several model outputs (D > C > A = B); train a reward model.
  - 3. Optimize the model against the reward model with reinforcement learning (PPO).
- PPO: a standard RL algorithm that updates the model in small steps.

## Problems with human feedback
- Human annotators can be unreliable.
- Everyone has different preferences.
- It creates bad incentives: sycophancy (agreeing with the user) and sounding authoritative.
- The data itself can be sourced unethically.

## RL with verifiable rewards (RLVR)
- Make the reward checkable by a program, not a person.
- Verifiable rewards: unit tests, Lean proofs, exact match, system state, ...
- Great for math and code. Be careful how you design the verifier.
- GRPO (DeepSeekMath, arXiv 2402.03300): sample a group of outputs per question, score each, and push up the ones that beat the group average. A KL term keeps the model close to a reference.

## Agent-specific training: SWE-smith
- SWE-smith (arXiv 2504.21798) makes training tasks for coding agents.
  - Real repositories with passing unit tests.
  - Environment: SWE-agent installs the repo and runs tests; a developer writes a Dockerfile.
  - Task generation: procedural changes, LM-generated bugs, combined bugs, PR mirroring.
  - Output: environment image + synthetic tasks (generated issue, bugged patch, verified tests).

# Inference

## Prefill and decode
- Prefill: read the whole prompt at once and store each token's key and value vectors.
  - "The quick brown fox" → first output "jumps".
- Decode: write one new token at a time, reusing the stored (cached) vectors.
  - "jumps" → "over" → ...

## GPUs
| CPU | GPU |
|---|---|
| A few powerful compute units (ALUs) | Thousands of small compute units |
| Large control logic and cache | Little control logic per unit |
| Good at varied, sequential work | Good at the same math on lots of data at once |

- Both read from DRAM (main memory). Moving data from memory is often the bottleneck.

## Roofline performance model
- X axis: arithmetic intensity, FLOPs done per byte read from memory.
- Y axis: attainable FLOPs per second.
- Low intensity: bandwidth-bound. Speed is limited by memory reads (sloped line).
- High intensity: compute-bound. Speed hits the chip's peak FLOP/s (flat line).

## Prefill: all prompt tokens in parallel
- All prompt tokens go through attention together as big matrix multiplications.
- The causal mask makes each token see only earlier tokens.
- Lots of math per byte loaded → compute-bound.

## Decode: one token at a time
- Only the newest token runs through the layers.
- Its query attends over the keys and values of all earlier tokens.
- Queries and outputs for earlier tokens are no longer needed: clear them.
- Repeat for each new token: "The" → "class" → "was" → "about".

## The KV cache
- KV cache: the stored keys and values of every earlier token, kept on the GPU.
- Decode reads the whole cache for every new token, but computes only one row.
- It grows with context length: longer prompts use more GPU memory.

## Prefill vs decode on the roofline
| Prefill | Decode |
|---|---|
| Many tokens at once | One token at a time |
| Compute-bound | Bandwidth-bound (reads weights and KV cache for little math) |
| Sets time to first token | Sets time per output token |

## Metrics
- Time to first token (TTFT): how long prefill takes. Grows with prompt length.
- Time per output token (TPOT): the gap between decoded tokens.
- Total time ≈ TTFT + (output tokens × TPOT).

## Speculative decoding
- A small draft model guesses several tokens: "Once" → "upon a time there".
- The big target model checks all the guesses in one parallel pass (like prefill).
- Keep the guesses until the first one it rejects: "upon", "a", "time" ✓, "there" ✗.
- Same output as the big model alone, in fewer slow steps.

## Some domains are more predictable
- Accelerating LLM Decoding with Speculative Sampling (arXiv 2302.01318), draft length K = 0–7:

| | HumanEval (code) | XSum (summaries) |
|---|---|---|
| Time for 128 tokens, K = 0 | about 1800 ms | about 1800 ms |
| Best time shown | about 680 ms at K = 7 | about 940 ms at K = 3 |
| Acceptance rate at K = 7 | about 0.68 | about 0.46 |

- Each loop costs more as K grows (about 14 ms → 28 ms). Code is easier to guess than summaries.

## Inference-time scaling
- Inference-time (test-time) scaling: spend more compute when answering, not when training.
- Ways: write out reasoning, reason longer, or sample many answers and pick one.

## Chain of thought
- Chain-of-Thought Prompting (Wei et al., arXiv 2201.11903).

| Standard prompting | Chain-of-thought prompting |
|---|---|
| Example answer: "The answer is 11." | Example answer: "Roger started with 5 balls. 2 cans of 3 tennis balls each is 6 tennis balls. 5 + 6 = 11." |
| Cafeteria: 23 apples, used 20, bought 6 → "The answer is 27." ✗ | "23 − 20 = 3 ... 3 + 6 = 9. The answer is 9." ✓ |

## Reasoning LLMs
Query: a jacket costs $80, the price rises 25%, then a 25% discount on the new price. Final price?

| Traditional LLM | Reasoning LLM |
|---|---|
| "$80 × 1.25 = $100. $100 × 0.75 = $75." | First guess: +25% and −25% cancel → $80. "Wait… the discount applies to the increased price." Recomputes $75, then checks: $80 + $20 − $25 = $75. |

- A reasoning model writes a long chain of thought before answering, and checks itself.

## "Aha" moments
- Prompt: a ticket and a popcorn cost $18; the ticket costs $6 more. Ticket price?
- Inside `<think>`: sets p + 6 = 18 → ticket 18. "Wait, that can't be right."
- Fixes it: p + (p + 6) = 18 → p = 6 → ticket = 12. Answer: 12.
- The model learns to self-correct during training.

## Reasoning effort trades cost for score
- Chart (Agents' Last Exam): score vs cost per task. Each model's effort levels form a line.
- GPT-6 Astra: Low ≈ 53%, Medium and High higher, Max ≈ 59%. Each step up costs more per task.
- Apps expose this as an effort setting (Low / Medium / High / Max).

## Setting the reasoning level (GPT-OSS)
| System prompt | User prompt |
|---|---|
| `Reasoning: low` | Solve this math problem... |
| `Reasoning: medium` | Solve this math problem... |
| `Reasoning: high` | Solve this math problem... |

- One line in the system prompt sets how long the model thinks.

## How effort control is trained
| Inkling (Thinking Machines) | Kimi K3 (Moonshot) |
|---|---|
| `R(e) = R_task − λ(e) · N_tokens` | Reward 1 if correct, 0 if wrong, −1 if wrong and over budget |
| Penalty per token used; λ higher for low effort, lower for high effort | Multi-teacher distillation: 9 teachers (general task, general agent, coding agent × high, medium, low) train one student |

## Scaling with repeated sampling
- Large Language Monkeys (arXiv 2407.21787).
- Step 1: generate many candidate solutions.
- Step 2: a verifier picks the final answer (unit tests, proof checkers, majority voting).
- Coverage: can we generate a correct answer at all?
- Precision: can we pick the correct one out of the samples?

## Small models + many samples beat one big answer
- Coverage (pass@k: at least one of k samples correct) for Llama-3-8B and -70B vs a single GPT-4o attempt:

| Benchmark | Single-attempt GPT-4o | Llama-3 with up to 10,000 samples |
|---|---|---|
| MATH (oracle verifier) | about 0.64 | 8B: about 0.27 at 1 sample → near 1.0 |
| CodeContests | about 0.21 | 70B passes GPT-4o near 100 samples, reaches about 0.38 |
| MiniF2F-MATH (formal proofs) | about 0.27 | Both reach about 0.5 |
| GSM8K (oracle verifier) | about 0.93 | Both reach near 1.0 |

## No verifier? Self-consistency
- Self-Consistency (Wang et al., arXiv 2203.11171).
- Greedy chain of thought on Janet's ducks: "3 + 4 = 7 eggs ... $14." ✗
- Self-consistency: sample many reasoning paths, then take the majority answer.
  - "$18", "$26", "$18" → majority: "The answer is $18." ✓

| 5 | about 43% | about 39% | about 47% |
| 10 | about 43% | about 42% | about 50% |
| 40 | about 43% | about 44% | about 54% |

- Majority vote beats ranking samples by the model's own probability.

| You have... | Use | In the notebook |
|---|---|---|
| A code check | Best-of-n: sample until one passes | Up to 4 tries at temperature 0.7 on msa_12; keep the first whose quote is in the contract |
| No checker, short answers | Majority vote: most common answer wins | 5 yes/no answers at temperature 0.8 on msa_08's cap clause |

- Agreement rate = confidence. Low agreement → send to a person.
- Nothing passes best-of-n → escalate, don't guess.

## Best-of-n in code
```python
def best_of_n(cid, n=4):
    for i in range(n):
        t = structured([{"role": "system", "content": SYSTEM}, {"role": "user", "content": contract(cid)}], Terms, temperature=0.7)
        if quote_is_in_doc(t.cap_quote, contract(cid)):
            return t, i + 1
    return None, n   # nothing passed: escalate to a person instead of guessing
```
- Line 2: try up to n times.
- Line 3: one extraction at temperature 0.7, so each try can differ.
- Lines 4–5: keep the first answer whose quote is really in the contract.
- Line 6: none passed, so hand it to a person.

# LLMs for Agents: Structured I/O

## The LLM is the core of an agent
- Agent parts: planning & reasoning, memory, tools (retrieval, calculator, code, search, file operations).
- All feed the LLM core, which picks actions: tool calls, interactions, responses to users.
- The agent observes the environment (desktop OS, browser, apps, games, databases) and acts on it.

## Motivating structured I/O
- More and more AI results come from compound systems: model calls, retrievers, databases, calculators, terminals working together.
- Those parts need a shared contract for how they talk to each other.
- Free text breaks the next step. Typed fields don't.

## Constrained decoding
- Constrained decoding: the server forces the model to output a set structure.
- SGLang (arXiv 2312.07104) turns the structure into a finite state machine (FSM): a map of which characters may come next.
- Example: the fixed text `{"summary": "`

| Normal FSM | Compressed FSM |
|---|---|
| 13 states, one character at a time | Fixed text jumps in one step |
| Calls the LLM between pieces | Calls the LLM only where a real choice exists |

## SGLang throughput
- Normalized throughput on Llama-7B, higher is better (SGLang = 1.0).
- Compared with vLLM, Guidance and LMQL on 11 workloads (MMLU, ReAct agents, JSON decoding, DSPy RAG, multi-turn chat, ...).
- SGLang was fastest on every workload; vLLM came close only on Generative Agents and long multi-turn chat.
- FSM decoding is one of several SGLang optimizations.

## DSPy signatures
```python
class Extract(dspy.Signature):
    """Extract contact info."""
    message: str = dspy.InputField()
    name: str = dspy.OutputField()
    email: Optional[str] = dspy.OutputField()
    intent: Literal["meeting", "intro", "follow-up"] = dspy.OutputField()
```
- Signature: declares the task's inputs and typed outputs. DSPy writes the prompt.
- `extract(message="I'm Sarah(sarah@acme.co). Meet Thursday?")` → `name="Sarah", email="sarah@acme.co", intent="meeting"`.

## DSPy signatures: peek inside
- The system prompt DSPy builds lists the input and output fields with types.
- It sets a format with markers: `[[ ## message ## ]]`, `[[ ## name ## ]]`, ..., `[[ ## completed ## ]]`.
- Per-field notes: email "must adhere to the JSON schema" string or null; intent "must exactly match one of: meeting; intro; follow-up".
- It ends with the objective: "Extract contact info."

## A typed contract with Pydantic (our notebook)
```python
class Terms(BaseModel):
    governing_law: str | None = Field(description="US state name, e.g. 'Delaware', or null")
    liability_cap_months: int | None = Field(description="Cap as months of fees, e.g. 12. null if liability is unlimited")
    renewal_years: int | None = Field(description="Length of each automatic renewal period in years")
    notice_days: int | None = Field(description="Days of notice needed to stop renewal")
    cap_quote: str | None = Field(description="Exact sentence from the contract stating the liability cap")
```
- Line 1: a schema named `Terms`. Pydantic: Python library for typed data.
- Lines 2–5: each field has a type; `| None` = may be empty.
- `description` tells the model what to write.
- Line 6: an exact quote, so code can check it.

## Always give an "absent" option
| Schema allows null | Schema forces a number |
|---|---|
| `int` or `None` | `int` only (`CapForced` in the solutions) |
| msa_16 → null is a valid answer | msa_16 → the model has to invent a cap |

- msa_16, clause 7.1: "IN NO EVENT SHALL EITHER PARTY'S TOTAL LIABILITY UNDER THIS AGREEMENT BE LIMITED..."
- System prompt: "If a term is absent, use null. Never guess."

## Valid format is not correct content
- Constrained decoding: output is always valid JSON. Parsing never fails.
- The value can still be wrong, made up, or in the wrong unit.

| Quote | `quote_is_in_doc(..., contract("msa_07"))` |
|---|---|
| The cap quote the model extracted | True only if it matches the contract text |
| "Liability is capped at $1 million." (made up) | False |

- The notebook also scores each field on 8 contracts against the known answers.

## Fixed choices: use a list, not free text
| Free text | `Literal[...]` list |
|---|---|
| "State of Delaware", "DE", "Delaware law" | "Delaware" only |
| Grading needs fuzzy matching | Grading is exact |

- `Literal["California", "Delaware", "New York", "Texas", "Florida", "Nevada", "Other"]`
- Off-menu answers become impossible.

## Constrain the model: classifiers
- Train a small head on top of embeddings to map text to class labels.
- Slide example: DistilBERT turns "a visually stunning rumination on love" into a vector; logistic regression on top outputs 85% positive, 15% negative → positive.
- The output can only be one of the labels.

## Constrain the model: "System One" models
- A popular term, but roughly: classifiers with adaptable options, for fast decisions.
- Contrastive state-action pretraining: a state encoder and an action encoder learn to match states with the right actions.
- At use time, write the options as text ("Mario should {action}") and score each against the current state.
- Mario example: left 5%, jump 80%, right run 15% → "Mario should jump!"

## Example: tool calling
- Toolformer (arXiv 2302.04761): the model writes tool calls inside its own text.

| Tool | Call in the text |
|---|---|
| QA | `[QA("Who is the publisher of The New England Journal of Medicine?") → Massachusetts Medical Society]` |
| Calculator | `[Calculator(400 / 1400) → 0.29]` 29% passed |
| Translation | `[MT("tortuga") → turtle]` |
| Wiki search | `[WikiSearch("Brown Act") → The Ralph M. Brown Act is an act of the California State Legislature ...]` |

- A tool call is structured output: a name plus arguments that code can run.

# How this applies to us

## Running it on the firm's own machine
- A local GPU has limited memory. The KV cache grows with the prompt, so long contracts cost memory and time to first token.
- Decode is bandwidth-bound: output tokens come at a steady pace, so short structured answers are faster than prose.
- Hybrid (linear + full attention) models are cheaper on long inputs; test their retrieval on your own contracts.

## Sampling settings for contract review
- Extraction and yes/no checks: temperature 0–0.3.
- Generating candidates for best-of-n: higher temperature (0.7 in the notebook), so tries differ.
- Reasoning effort: start low; raise it only where the eval shows a gain.

## Typed output the next step can use
- A review is only useful if the next step can rely on it: a number, not prose.
- `liability_cap_months` = 24 for msa_07 ("TWENTY-FOUR (24) MONTHS"). Code can compare it to our 12-month rule.
- The quote check gives the lawyer a sentence they can find in the contract.

## Small local models + a checker
- Small local models make more mistakes. Sampling plus a checker closes much of the gap (Large Language Monkeys).
- Our checker: the quote must appear in the contract text.
- No checker for a judgment call ("is this clause favorable?"): majority vote, and send low agreement to a person.

## Common mistakes
- Asking for JSON in the prompt and hoping → use the server's schema mode.
- No "absent" option → the model invents values. See msa_16.
- Free text for fixed choices → use `Literal`.
- Trusting the model's own confidence → use agreement across samples or a code check.
- High temperature for extraction → keep it at 0–0.3.

## Check your understanding
**Q: Why can we sample from a language model at all?**
A: It models the probability of whole token sequences, so it is generative. We draw each next token from its predicted distribution.

**Q: What does the causal mask do in attention?**
A: It stops a token from looking at later tokens. Each token's output mixes only itself and earlier tokens.

**Q: Why is decode slower per token than prefill?**
A: Prefill processes all prompt tokens in parallel and is compute-bound. Decode makes one token at a time and must re-read the weights and KV cache each step, so it is bandwidth-bound.

**Q: What does linear attention give up for its speed?**
A: New tokens see only a compressed, fixed-size state, not every earlier token. That makes long-context recall harder, so real models mix in some full attention.

**Q: Constrained decoding guarantees valid JSON. Why check the answer anyway?**
A: Valid format is not correct content. Check it against the source, for example that the quote is really in the document.

**Q: When do you use majority vote instead of best-of-n?**
A: When you have no checker. Majority vote works for short answers you can compare, like yes/no or a number.

**Q: Why can every field in `Terms` be null?**
A: So the model has an honest way to say "not in this contract" instead of inventing a value.
