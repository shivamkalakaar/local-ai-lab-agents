# Why tools?

## LLMs can't solve that?
- "Who is the current President of the United States?" → "I don't have real-time data …"
- "Multiply 999 by 867." GPT-4 gets multi-digit multiplication right only 59% of the time (slide text partly hidden).
- o1-mini, digits in number 1 × digits in number 2 (1–20 each): 100% for small numbers.
- Accuracy falls as both numbers grow; 0% for most pairs of 15+ digit numbers.

## LLMs struggle as tasks get bigger (Dziri et al., 2023)
Zero-shot accuracy:

| Task (problem size) | Small | Large |
|---|---|---|
| GPT-4, multiplication (digits × digits) | 1 × 1: 1.00; 3 × 3: 0.59 | 4 × 4: 0.04; 5 × 5: 0 |
| GPT-4, logic puzzle (houses × attributes) | 2 × 2: 1.00 | 5 rows and up: mostly 0 |
| GPT-4, dynamic programming (sequence length) | 2: 0.88 | 6: 0.31 |
| GPT-3.5, dynamic programming | 2: 0.51 | 6: 0.04 |
| GPT-3, dynamic programming | 2: 0.30 | 6: 0.04 |

- Accuracy collapses as the problem grows. A calculator doesn't.

## Why tools?
| What LLMs can't compute | What agents can do |
|---|---|
| Arithmetic at scale | Calculator, code interpreter |
| Multi-step logical deduction | Symbolic solver, verifier |
| Exact, verifiable operations | Deterministic execution |

| What LLMs never saw in training | What agents can do |
|---|---|
| Long-tail facts | Web search, retrieval |
| Post-cutoff events | Live APIs, news feeds |
| Private and proprietary data | RAG over internal documents |

## Why tools? What LLMs can't reach
| What LLMs can't reach | What agents can do |
|---|---|
| Non-language interfaces (APIs, databases) | Function calling, MCP |
| The physical world | Browsers, robots |
| Live state (time, prices, sensors) | Clocks, sensors, market data |

- For us: the firm's contracts are private data, and its email and document systems are non-language interfaces.

# What are tools?

## What is a tool?
- Tool: a function interface to a computer program that runs outside the LM.
- The LM writes the function call and its input arguments. Your code runs it.
- Wang et al., 2024, "What are tools anyway? A survey from the language model perspective."
- Extend: reach the real world, e.g. `get_time()` → "3 pm".
- Facilitate: do a step better than text, e.g. calculator for (35.223 × 1.6)² / 7 → 453.7.

## Scenarios of tool use
| Category | Example tools |
|---|---|
| Knowledge access | `sql_executor(query)`, `search_engine(query)`, `retriever(query)` |
| Computation | `calculator(formula)`, `python_interpreter(program)`, `worksheet.insert_row(row, index)` |
| Interaction with the world | `get_weather(city_name)`, `get_location(ip)`, `calendar.fetch_events(date)`, `email.verify(address)` |
| Non-text modalities | `cat_image.delete(image_id)`, `spotify.play_music(name)`, `visual_qa(query, image)` |
| Special-skill LMs | `QA(question)`, `translation(text, language)` |

## Basic tool use example
| Without a tool | With a tool |
|---|---|
| "What is 17,423 × 892?" → the LLM guesses digits; accuracy drops as numbers get longer | LLM writes `calculate(17423 × 892)` → code runs the calculator → 15,541,316 |

- Steps: the model emits the call → the harness runs the tool → the result goes back to the model.

# Learning to call tools: Toolformer

## LLMs can teach themselves to use tools (Schick et al., 2023)
- Toolformer trains an LM to decide which APIs to call, when, with what arguments, and how to use the results.
- Self-supervised: only a handful of demonstrations per API.
- Examples of calls written into text:
  - "… a registered trademark of [QA("Who is the publisher of The New England Journal of Medicine?") → Massachusetts Medical Society] the MMS."
  - "Out of 1400 participants, 400 (or [Calculator(400 / 1400) → 0.29] 29%) passed the test."
  - "… the Spanish word for [MT("tortuga") → turtle] turtle."

## Toolformer: candidate tools
| Tool | Input | Output |
|---|---|---|
| Q&A system | "What other name is Pittsburgh known by?" | "The Steel City" |
| Search engine | "War memorial Flodden" | "[…] was created in memory of the Battle of Flodden." |
| Calculator | "3435*235/9" | "89691.67" |
| Calendar | (no input) | "Thursday, March 10, 2019" |
| Translation | "Os Melhores Escolas em Jersey" | "The Best Schools in Jersey" |

## Toolformer: method
- Start from a plain LM dataset. Make a new copy with API calls added.
- Fine-tune GPT-J (6B) on that new dataset.
- Three steps: (1) sample API calls → (2) execute them → (3) filter out the useless ones.
- Running example: "Pittsburgh is also known as | the Steel City."

## Toolformer: (1) sample API calls
- Prompt the LM: "Your task is to add calls to a Question Answering API to a piece of text […]"
- Input: "Pittsburgh is known as the Steel City." → Output: "Pittsburgh is known as [QA("What other name is Pittsburgh known by?")] the Steel City."
- `p_i = p_M(<API> | P(x), x_1:i−1)`: how likely the model is to start an API call at position i.
- Keep positions where p_i > τ_s (a threshold); sample m candidate calls there.
- Candidates: "What other name is Pittsburgh known by?" and "Which country is Pittsburgh in?"

## Toolformer: (2) execute API calls
- Run every candidate call.
- "What other name is Pittsburgh known by?" → "Steel City".
- "Which country is Pittsburgh in?" → "United States".
- Then drop every call that doesn't lower the loss L_i on the next tokens.

## Toolformer: (3) filter API calls
- Weighted loss on the tokens after position i: `L_i(z) = −Σ_{j=i..n} w_{j−i} · log p_M(x_j | z, x_1:j−1)`
  - z: text inserted before the tokens (a call, a call + result, or nothing).
  - w: weights; nearer tokens count more.
- `L_i+ = L_i(call + result)`: both the API call and its output.
- `L_i− = min( L_i(nothing), L_i(call without result) )`: no call, or a call with no output.
- Keep the call if `L_i− − L_i+ ≥ τ_f`: the result must help, not just the call.

## Toolformer: filter example
`L(prefix) = −log p("the Steel City." | prefix)`

| Case | Prefix | Loss |
|---|---|---|
| A. No API call | "Pittsburgh is known as" | 2.5 |
| B. Call, not executed | "… [QA("What other name is Pittsburgh known by?") → ?]" | 2.1 |
| C. Call, executed | "… [QA(…) → Steel City]" | 0.8 |

- Usefulness = min(L_A, L_B) − L_C = min(2.5, 2.1) − 0.8 = 1.3. Keep it.
- "Which country is Pittsburgh in?" → "United States" doesn't help predict "the Steel City". Drop it.

## Example texts and usefulness scores
| Score | Text with call |
|---|---|
| 2.11 | "The WL will be open on Friday, [Calendar() → Today is Thursday, March 9, 2017.] March 10, and Sunday, March 19 for regular hours." |
| 1.59 | "… 499 K rather than 735 K which is [Calculator(735 / 499) → 1.47] 1.47 times hotter." |
| −1.23 | "The last time I was with [QA("Who was the last time I was with?") → The Last Time] him I asked what he likes about me." |

- High score: the result helps predict the next words. Negative: the call hurts; it is dropped.

## View tools as "words"? ToolkenGPT (Hao et al., 2024)
- Represent each tool as a token (a "toolken") and learn an embedding for it.
- Toolken groups: KB (`winner_of`, `father_of`), math (`square`, `GCD`), robot (`grab`, `walk`).
- Once a toolken is triggered, the LM fills in the tool's arguments; the tool runs.
- Example: garden 64 m × 48 m → GCD(64, 48) = 16 → `<square>(16)` → 256. "Therefore, the area is 256."

## ToolkenGPT framework
- The LM predicts the next token, either a word or a toolken: `P(t_i | t_<i) = softmax([W_ν; W_τ] · h_{i−1})`
  - W_ν: word embeddings (frozen). W_τ: toolken embeddings (learned).

| Step | What happens |
|---|---|
| Toolken predicted | Mode switch |
| Generation pauses | Context moved to a new prompt |
| Tool-mode prompt | Demos in [tool](args) syntax |
| Arguments filled | In-context learning does the easy work |
| Tool executes | Return value goes back into reasoning mode |

## Learning toolken embeddings
"the area is 256 square feet"

| s | the | area | is | 2 | 5 | 6 | square | feet |
|---|---|---|---|---|---|---|---|---|
| s′ | the | area | is | **[square]** | [N/A] | [N/A] | square | feet |

- [square]: the toolken, predicted at the first result token. [N/A]: the result tokens, skipped in the loss.
- `L(W_τ) = Σ over (s, s′) Σ_i −log P(t′_i | t_<i) · 1[t′_i ≠ N/A]`
- Training data: datasets with ground-truth tool calls, or synthetic data.

# Scaling to many tools: Gorilla

## ToolLLM: LLMs that use 16k+ APIs
- Fine-tune LLaMA into ToolLLaMA, plus a neural API retriever that suggests the right APIs per instruction.
- Data: API collection from RapidAPI → instruction generation (ChatGPT) → solution path annotation (ChatGPT) → ToolBench.
- Train: supervised fine-tuning (SFT) of LLaMA on ToolBench → ToolLLaMA.
- Inference: instruction → API retriever → retrieved APIs → ToolLLaMA calls RapidAPI N times → final answer, scored by ToolEval.

## Arising issue: tool use and hallucination
Prompt: "Help me find an API to convert the spoken language in a recorded audio to text using Torch Hub."

| GPT-4 | Claude | Gorilla |
|---|---|---|
| `torch.hub.load('snakers4/silero-models', 'asr', source='local')` | `torchaudio.pipelines.WAV2VEC2_ASR_PIPELINE("audio.wav")` | `torch.hub.load('snakers4/silero-models', 'silero_stt')` |
| Hallucinated arguments | Wrong library (domain: audio translation) | Good to go |

## Gorilla: LLMs connected with massive APIs (Patil et al., 2023)
- Dataset: 1,645 API calls. 94 from Torch Hub (all), 626 from TensorFlow Hub v2 (all), 925 from HuggingFace (top 20 per domain).
- Each API as JSON: {domain, framework, functionality, api_name, api_call, api_arguments, environment_requirements, example_code, performance, description}.
- Self-instruct with GPT-4 and in-context examples → 16,450 {instruction, API} pairs.
- Used to train Gorilla-7B (on LLaMA 7B).

## Retrieval-aware training (RAT)
- Fine-tune the model to use or ignore retrieved API docs.
- Show both correct and incorrect retrieved docs during instruction fine-tuning.
- Result: the model stays robust when retrieval is poor.
- Inference two ways: zero-shot, or with a retriever over the API database.
- Example: "I want to see some cats dancing in celebration!" → retriever adds "Reference API: StableDiffusionPipeline.from_pretrained(…)" → Gorilla writes `StableDiffusionPipeline.from_pretrained(stabilityai/stable-diffusion-2-1)`.

## AST sub-tree matching to measure hallucination
- AST (abstract syntax tree): the call parsed into a tree of its parts.
- Call: `torch.hub.load('pytorch/vision:v0.10.0', 'densenet121', pretrained=True)` → torch → hub → load → pytorch/vision → densenet121 → pretrained=True.
- Correct if that tree is a sub-tree of the tree of real APIs in the database.
- Hallucination: the call matches no real API at all. Wrong but real API = an error, not a hallucination.

| LLaMA | 14.51 | 10.17 | 15.62 |
| GPT-3.5 | 60.21 | 47.34 | **65.59** |

# Standard interfaces: REST, function calling, MCP

## Why standard interfaces?
| Change the model to fit the tools | Change how tools are described so any model can use them |
|---|---|
| Toolformer, ToolkenGPT, Gorilla | REST, function calling, MCP |
| Every new API means another training run | A schema at runtime instead of fine-tuning per API |

## Three generations
| REST API (human-facing) | Function calling (model-facing) | MCP (ecosystem-facing) |
|---|---|---|
| Endpoints + docs; auth per service | JSON schema per tool | One protocol, any client |
| LLM must read docs and hand-write requests | Model emits name + args; harness validates and dispatches | Servers expose tools, resources, prompts |
| No machine-readable contract | Schemas live in the codebase | Discovery at runtime; write once, reuse across hosts |
| `GET /v1/weather?city=SF` | `{"name":"get_weather","arguments":{"city":"SF"}}` | `tools/list` → `tools/call` |

## REST APIs: tools over HTTP
```
GET  https://api.weather.com/v1/current?city=Stanford
200  {"temp_f": 74, "conditions": "sunny"}
```
- Verbs: GET read, POST create, PUT update, DELETE remove.
- Limitation: the model must know the URL, parameter names and response shape.

## Function calling: tools as JSON schemas
| Tool schema (what the model sees) | Model output (what it emits) |
|---|---|
| `{"name": "get_weather", "description": "Current weather", "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}}` | `{"tool_call": {"name": "get_weather", "arguments": {"city": "Stanford"}}}` |

- Flow: schema → model emits tool_call → harness runs it → result back to the model.
- Limitation: a tool written for one API format has to be rewritten for the next.

## Model Context Protocol (MCP)
- One standard protocol between AI apps and data sources, with data flowing both ways.

| AI applications | Data sources and tools |
|---|---|
| Chat interfaces: Claude Desktop, LibreChat | Data and file systems: PostgreSQL, SQLite, GDrive |
| IDEs and code editors: Claude Code, Goose | Development tools: Git, Sentry |
| Other AI apps: 5ire, Superinterface | Productivity tools: Slack, Google Maps |

## MCP architecture: host, client, server
- MCP host: the AI application.
- MCP client: lives inside the host; one per server, each with a dedicated connection.
- MCP server: exposes tools. Can be local (filesystem, database) or remote (e.g., Sentry).
- Example: one host with 4 clients → local server A (filesystem), local server B (database), remote server C (Sentry, two clients).

## MCP: tool discovery (`tools/list`)
- Request: `{"jsonrpc": "2.0", "id": 2, "method": "tools/list"}`. "What tools do you have?"
- The server returns a list of tools.
- Each tool has a name, description and JSON `inputSchema`.
- Example: `weather_current`, "Current weather for a location"; `location` (string, required), `units` (enum: metric, imperial).
- `ttlMs: 300000`: how long the client may cache the list (300,000 ms).

## MCP: tool execution (`tools/call`)
- Request: `"method": "tools/call"`, `"name": "weather_current"`, `"arguments": {"location": "Stanford", "units": "imperial"}`.
- `name` picks a listed tool; `arguments` follow its inputSchema.
- Result is a `content` array the host hands back to the LLM.
- Example: `{"type": "text", "text": "Current weather in Stanford: 68°F, partly cloudy, wind W 8 mph"}`.

## Example: course LMS API → MCP tools
| REST route | MCP tool |
|---|---|
| `GET /assignments` | `list_assignments` |
| `GET /submissions` | `get_submissions` |
| `POST /grade` | `post_grade` |

- FastMCP reads the API's OpenAPI spec (`/openapi.json`) and makes one MCP tool per route: `FastMCP.from_openapi(openapi_spec=spec, client=api, name="Course MCP")`.

## Example: inbound vs outbound auth
| Inbound: agent → MCP server | Outbound: MCP server → LMS |
|---|---|
| Agent sends `AGENT_TOKEN` | Server sends `LMS_TOKEN` as a Bearer header |
| `StaticTokenVerifier` checks it; maps to client "ta-agent" | Held only by the server; the agent never sees it |

- Server: `FastMCP.from_openapi(..., auth=who_may_call)`, run over HTTP on port 8001.
- Two separate keys: who may call the server, and what the server may do.

## Our notebook uses function calling
- The registry's `schemas()` turns each tool into `{"type": "function", "function": {name, description, parameters}}`.
- The local Ollama server takes these as `tools=`, the same format as OpenAI's API.
- The model replies with `tool_calls`; our loop runs each through the registry and returns a `"role": "tool"` message.

## BFCL: how it evaluates
- BFCL: a broad test of an LLM's ability to invoke functions (tool calling).
- Evaluation:
  - AST-based offline check: does the call parse to the right function and arguments?
  - Execute the function for a real-world check.
  - State-based check for multi-step and multi-turn calls.
- Datasets: from real-world use cases; taxonomies of call types; Python, C++, Java, SQL and more.
- Tests relevance and irrelevance: sometimes none of the given functions fits the query.

## τ-bench: tool-agent-user interaction (Yao et al., 2024)
- Tools: `get_user_details`, `book_reservation`, `cancel_reservation`, `update_reservation_flights`, …
- Agent gets the domain policy as a system prompt: "Basic economy cannot be modified." "Basic economy cannot be cancelled after 24 hours of booking…"
- A simulated user (an LLM) gets its own instruction: change a reservation to SF; if not possible, cancel and rebook.
- Scored on the final database state, not the chat.

## τ-bench: example trajectory (τ-airline)
| Turn | Content |
|---|---|
| User | "Change flight" |
| Agent → tool | `get_reservation_details[JK9O19]` → {'cabin': 'basic_economy', …} (read database) |
| Agent | "JK9O19 is basic economy and cannot be changed. But since it is within 24h, I can cancel it and book a new one. Do you want me to do it?" |
| User | "Oh… In that case just cancel it" |
| Agent → tool | `cancel_reservation[JK9O19]` → {…, 'status': 'cancelled'} (write database) |

## Pass^k: reward reliability and consistency
- `pass^k = E_task[ C(c, k) / C(n, k) ]`: chance all k sampled trials succeed, given c of n succeeded.
- `pass@k = 1 − E_task[ C(n−c, k) / C(n, k) ]`: chance at least 1 of k succeeds.
  - C(a, b): "a choose b". n: trials run per task. c: trials that passed.
- pass@k rises with k; pass^k falls with k. Agents need pass^k.

| API tools | 7 write, 8 non-write | 6 write, 7 non-write |
| Tasks | 115 | 50 |

## Failure modes in tool use
| Single call | Multi-step chain | Conversation |
|---|---|---|
| Selection: wrong tool, or a tool when none was needed | Sequencing: skips a needed earlier call, or wrong order | Policy: acts where the rules say not to |
| Arguments: made-up fields, wrong types or units | Recovery: retries the same failing call instead of backing off | Interaction: assumes instead of asking the user |
| Hallucinated tool: calls an API that doesn't exist | | Non-determinism: passes once, fails on the retry (pass^k) |

## Lecture summary
- Why tools: what LLMs didn't see in training, or can't reach.
- Toolformer: the LM teaches itself which APIs to call, when, and with what arguments.
- Gorilla: trained on 1.6k APIs; AST matching measures hallucination.
- REST → function calling → MCP: from hand-written requests to `tools/list`, `tools/call`.
- BFCL / ToolBench / τ-bench: single call, multi-step chain, tool-agent-user.
- Failure modes: wrong tool, made-up arguments, wrong order.

# How this applies to us

## Our registry: four gates, in order
- Validate: do the arguments match the JSON schema? If not, never run.
- Permission: does the tool change the world (`read_only=False`)? Ask for approval.
- Run: call the function; catch any crash.
- Truncate: output over 1,500 characters → cut it, and say how to ask for less.
- Every outcome is a `ToolResult` with a status: ok, unknown_tool, invalid_args, tool_error, denied.

## The gates in code
```python
jsonschema.validate(args, spec.parameters)
...
if not spec.read_only and not self.approve(name, args):
    return ToolResult("denied", "DENIED: a person declined this action. Do not retry it.")
...
out = str(spec.fn(**args))
if len(out) > self.max_chars:
    out = out[: self.max_chars] + f"\n[truncated; {len(out)} chars total. Ask for a narrower range.]"
```
- Line 1: check arguments against the schema. Failure → "invalid_args".
- Lines 3–4: not read-only and not approved → "denied", with a clear message.
- Line 6: run the tool.
- Lines 7–8: cut long output and say how to ask for a narrower range.

## Five calls, no model needed
| Call | Status | Failure mode it catches |
|---|---|---|
| `get_clause(msa_07, "7.1")` | ok | – |
| `get_clause(msa_7, "seven")` | invalid_args (ID must look like `msa_07`) | Arguments: wrong format |
| `delete_contract(msa_07)` | unknown_tool, plus the list of real tools | Hallucinated tool |
| `send_email(x@example.com, ...)` | denied (default approver says no) | Policy |
| `read_pages(msa_07, n_lines=30)` | ok (30 is the schema maximum) | – |

## Good vs bad tool descriptions
| Bad | Good |
|---|---|
| "reads stuff" | "Read a contract 15 lines at a time, with line numbers. Use start_line to page." |
| Model guesses what `start_line` means | Says what it does, what it returns, how to use it |

- Short output matters too: showing whole files cut SWE-agent's success from 18.0% to 12.7%.

## Policy in code, not in the prompt
- Task: "Read clause 7.1 of msa_07 and email it to opposing.counsel@example.com"
- The model reads the clause, tries `send_email`, gets "denied."
- The notebook checks `SENT == []`: nothing was sent.
- Solution: an approver that allows only `@yourfirm.com` addresses.
- Like τ-bench's airline rules, but enforced by the registry, not by the model's memory of the prompt.

## Failure modes vs our registry
| Where | Failure | Registry defense |
|---|---|---|
| Single call | Wrong tool; made-up fields; tool that doesn't exist | Schema check; unknown_tool |
| Multi-step | Retries the same failing call | Clear error text; stuck detector (module 01) |
| Conversation | Acts where the rules say not to | Permission gate |
| Across runs | Passes once, fails on retry (pass^k) | Test each task several times |

## Running it on the firm's machine
- "Never email a client without approval" must hold every time. Only code can promise that.
- Small local models make more malformed calls. The schema check catches them before they run.
- Short, paged output keeps the local model's context small.
- Open-weight models can call tools well: GLM-4.6 was 4th on BFCL at a fraction of the cost.
- Later, an MCP server could expose the firm's document system once, for any local agent.

## Common mistakes
- Policy in the prompt → it's a suggestion. Put it in the approval gate.
- Vague descriptions → the model guesses. Good descriptions are free accuracy.
- Huge outputs → return pages, with a way to ask for the next one.
- Raising errors → return them as results so the model can recover.
- No "none of these fits" path → the model picks a wrong tool. BFCL tests this.
- Testing once → run each task several times and report pass^k.

## Check your understanding
**Q: Where should "never email a client without approval" live?**
A: In code. `send_email` is not read-only, so the registry calls the approval gate before running it.

**Q: Why validate arguments before running the tool?**
A: So bad calls never execute. The model gets a clear error and can retry with the right format.

**Q: How does Toolformer decide which API calls to keep in its training data?**
A: It keeps a call only if adding the call and its result lowers the loss on the next tokens by at least τ_f, compared with no call or a call without its result.

**Q: What does Gorilla's AST sub-tree matching measure?**
A: Whether a generated API call matches a real API in the database. A call that matches no real API counts as a hallucination.

**Q: What problem does MCP solve that plain function calling doesn't?**
A: With function calling, schemas live in each app's code and get rewritten per API. MCP servers list their tools at runtime (`tools/list`), so one server works with any host.

**Q: What does pass^k measure, and why does it fall as k grows?**
A: The chance the agent succeeds on all k tries of the same task. Every extra try is another chance to fail, so it rewards reliability.

**Q: In BFCL's relevance test, the user asks "What is 2*3?" and only add(a, b) exists. What should the agent do?**
A: Call nothing and say the request is multiplication but only add is available.
