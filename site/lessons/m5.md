## The big idea

A tool is a plain function the model can ask to run, like "read clause 7.1" or "send an email." The model never runs it directly. It writes a request. Your code decides whether to run it.

Think of a bank teller. A customer fills in a withdrawal slip. The teller checks the slip is filled in correctly. Then they check the customer is allowed to take that money. Only then do they hand over cash. Big withdrawals need a manager's sign-off. The teller doesn't rely on the customer promising to behave.

That is a tool registry (the code that sits between the model and your tools). It checks every request, enforces permissions, runs the tool, and trims the output. The course's advice: spend more effort on tools than on the prompt.

## Why it matters for us

A contract agent might read files, and one day send emails. A rule like "never email a client without approval" must hold every time. If it lives in the prompt, it is only a suggestion. The model can ignore it. If it lives in code, it is a rule.

Small local models also make more mistakes in their tool requests. Wrong formats, wrong names, missing fields. A good registry catches these before they run and tells the model how to fix them.

Output size matters too. Long tool results clutter the model's desk. In one study, showing whole files instead of small pages cut a coding agent's success from 18.0% to 12.7% (the SWE-agent paper).

## How it works, step by step

1. **Keep tools few and distinct.** Overlapping tools confuse the model. One narrow job per tool.

2. **Write descriptions like notes for a new hire.** Say what it does, what it returns, and when to use it. "Reads stuff" is useless. "Read one clause by number like '7.1'. Returns NOT FOUND if it doesn't exist" is clear.

3. **Make misuse hard.** Each tool has a schema (a description of the allowed inputs). Use patterns, fixed choices and required fields. A contract ID must look like `msa_07`.

4. **Run each request through four gates, in order:**
   - **Validate.** Does the request match the schema? If not, reject it before running.
   - **Permission.** Is this tool read-only? If it changes the world, like sending email, ask for approval.
   - **Run.** Call the function. If it crashes, catch the error.
   - **Truncate.** If the output is too long, cut it and say how to ask for less.

5. **Return errors as results.** Send "ERROR: no tool 'delete_contract'. Available: ..." back to the model. A clear message lets it fix its own request. A crash ends the run.

6. **Allow "no tool fits."** A model forced to pick a tool will pick a wrong one.

## Worked example

The notebook builds a registry with three tools. Two only read: `read_pages` (15 lines at a time) and `get_clause`. One changes the world: `send_email`, marked not read-only.

Before using any model, it feeds the registry five requests by hand:

- A correct `get_clause` for clause 7.1 of msa_07. Status: ok.
- `get_clause` with ID "msa_7" and clause "seven". Status: invalid_args. It never runs.
- `delete_contract`, which doesn't exist. Status: unknown_tool, with a list of real tools.
- `send_email`. Status: denied. The default approver says no.
- `read_pages` asking for 30 lines. Status: ok.

The heart of the registry:

```python
jsonschema.validate(args, spec.parameters)
if not spec.read_only and not self.approve(name, args):
    return ToolResult("denied", "DENIED: a person declined this action. Do not retry it.")
out = str(spec.fn(**args))
if len(out) > self.max_chars:
    out = out[: self.max_chars] + f"\n[truncated; {len(out)} chars total. Ask for a narrower range.]"
```

- The first line checks the arguments against the schema. Bad ones raise an error, which becomes an "invalid_args" result.
- The next two lines are the permission gate. A tool that is not read-only needs approval, or it is denied with a clear message.
- Then the tool actually runs.
- The last two lines cut long output and tell the model how to ask for less.

Then the model gets a real task: "Read clause 7.1 of msa_07 and email it to opposing.counsel@example.com." It reads the clause fine. It tries to email. The registry denies it. The notebook prints the list of sent emails: empty.

## Common mistakes

- **Putting policy in the prompt.** "Only email after confirming" is a hope. Put it in the registry's approval gate.
- **Vague descriptions.** The model has to guess what the inputs mean. Good descriptions are free accuracy.
- **Huge outputs.** Return small pages, with a way to ask for the next one.
- **Raising errors instead of returning them.** Return a helpful message so the model can recover.
- **Testing once.** Agents can pass a task once and fail it on a repeat. Run the same test several times.

## Check your understanding

**Q: Where should "never email a client without approval" live?**
A: In code. The email tool is marked not read-only, so the registry calls the approval gate before running it. Prompts are suggestions; the registry is a rule.

**Q: Why check the arguments before running the tool?**
A: So bad requests never execute. The model gets a clear error and can try again with the right format.

**Q: Why return errors to the model instead of crashing?**
A: A clear message like "clause 99 doesn't exist" lets the model fix its own request. A crash just ends the run.
