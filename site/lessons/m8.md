## The big idea

A language model forgets everything when a conversation ends. Memory is how we let an agent carry lessons from one job to the next.

Think of a new associate at a law firm. Each time a partner corrects her, she writes it in a notebook. After a few corrections on the same point, she drafts a rule: "This client is fine with New York law." She shows the rule to the partner before she starts using it.

That is the whole idea of this lesson. The agent keeps a log of what happened. It proposes lessons, and each lesson points to the log entries behind it. A person approves each lesson. Memory is saved in numbered versions, so nothing is ever silently overwritten.

The fancy part is not needed. In the course's benchmarks, plain files and plain search did better than dedicated memory products.

## Why it matters for us

- Law firms must explain their decisions. If an agent changes what it remembers on its own, nobody can say why it flagged a clause last March. Versioned, approved memory fixes that.
- Lessons are often client-specific. "Northwind accepts New York law" must never leak into a review for another client.
- Plain files fit a firm's own computers. There is no extra service to run, and everything stays on the box.

## How it works, step by step

The CoALA paper (2024) splits agent memory into four types. Here they are in law-firm terms.

| Type | What it holds | Our example | Who may write |
|---|---|---|---|
| Working | What the model is reading right now | The contract under review | The agent |
| Episodic | What happened | "Partner changed our flag on clause 10.1" | Append-only log |
| Semantic | Lessons and facts | "This client accepts New York law" | Agent proposes, person approves |
| Procedural | How to work | Prompts, checklists | Change control only |

1. **Log every correction.** Episodic memory (a record of events) goes in an append-only file. Append-only means you can add lines but never edit or delete old ones. Each record says who corrected what, and why.
2. **Propose a lesson with evidence.** Semantic memory (general lessons) is written by the agent only as a proposal. The proposal must list the IDs of the corrections that support it. No evidence, no proposal.
3. **A person approves.** Once approved, the lesson is saved as a new version file: v1, v2, v3. Old versions stay on disk.
4. **Use lessons, scoped to one client.** When the agent reviews for Northwind, it loads only Northwind's lessons.
5. **Record the version on every run.** Each review notes which memory version it used. Later you can replay the exact decision.

Procedural memory (the prompts and checklists themselves) is the riskiest to change. Treat it like a software release: test first, then ship.

## Worked example

The firm's playbook says governing law must be California or Delaware. The agent flags New York law on three Northwind contracts. Each time, a partner overrides it: "This client has an NY office; NY law is acceptable for them."

Each override goes into the log:

```python
rec = {"ts": time.time(), "client": client, "contract": cid, "rule": rule,
       "model": model_said, "human": human_said, "reason": reason, "by": by}
rec["id"] = hashlib.sha256(json.dumps(rec, sort_keys=True).encode()).hexdigest()[:10]
with open(MEM / client / "corrections.jsonl", "a") as f:
    f.write(json.dumps(rec) + "\n")
```

Line by line: the first line builds a record with the time, client, contract, rule, what the model said, what the human said, the reason, and who made the call. The second line gives the record a short ID made from its contents (a hash, like a fingerprint). The last two lines open the log in "a" mode, which means append, and add the record as one new line.

Next, the model reads the three corrections and drafts one short rule. The code refuses the proposal if it cites no corrections. The partner approves it, and it becomes memory version 1.

Now the same New York contract is reviewed twice. For a generic client, the agent says ISSUE. For Northwind with version 1, it says OK, and the output records `memory_version: 1`. If an auditor asks why, you can point to the lesson and the three corrections behind it.

## Common mistakes

- **Using a memory product that edits itself.** Auto-updating memory is fine for chat apps. For client work, every change needs a person's approval.
- **Keeping only summaries.** If you throw away the raw log, you can no longer check whether a lesson was justified. Keep the raw records.
- **Sharing lessons across clients.** Scope memory per client or matter. Add a guard in code that refuses to load another client's lessons.
- **Letting document text write to memory.** A contract could contain text designed to plant a false lesson. Only corrections from people should become evidence.

## Check your understanding

**Q: A partner overrides the agent on three contracts in the same way. What should happen?**
A: Each override is logged in the episodic log. The agent proposes one lesson that cites those three records. A person approves it, and it ships as the next memory version.

**Q: Why record a memory version on every run?**
A: So any past decision can be replayed exactly as it was made. If someone asks "why did it flag this in March?", you can show the lessons it used.

**Q: Why is procedural memory the riskiest kind to change?**
A: It is the prompts and checklists that shape every review. A bad change there affects all clients at once, so it should be tested before release.
