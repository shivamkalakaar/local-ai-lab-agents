## Learning objective
- Build a long-running review loop that survives crashes, does one checked step at a time, and can't finish early.

## Why long jobs are hard
- Context window: how much text the model can hold at once.
- Long-horizon: context grows and drifts (Lecture 1, key challenges).
- 200 contracts in a data room won't fit in one sitting.
- Each new session starts blank. Progress must live in files, not in the model.

## Terms (from the lecture)
- Task: a single test with defined inputs and success criteria.
- Trial: one attempt at a task.
- Verifier: logic that scores the agent's work.
- Trajectory: the complete record of a trial.
- Ours: one checklist item = one task; code is the verifier; git log is the trajectory.

## The pattern
```
setup:  checklist (all "not done") + progress file
loop:   read checklist → do ONE item → verify quote → mark done → commit
finish: only when every item has evidence
```
- Setup session: code writes the checklist. One item per contract per rule.
- Work session: one item, then save.

## Who may change what
| The code | The agent |
|---|---|
| Writes the checklist (scope is fixed) | May only flip `done` and attach evidence |
| Checks the quote is in the contract | Answers: does the clause break the rule? |
| Commits each step to git | Never adds, removes or rewords items |
| Blocks the final report until all items have evidence | Can't call the job finished |

## Our matter: 16 items
- 4 contracts × 4 playbook rules = 16 items, e.g. `msa_13:termination_notice`.
- msa_13, 4.1: "...at least 15 days' prior written notice..." → rule needs at least 30 → breaks.
- The model must quote the exact words that decide it.
- Retries get temperature 0.5 for variety. After 3 failed tries, the item is left for a person.

## Verifying evidence in code
```python
if not quote_is_in_doc(f.quote, contract(todo["contract"])):
    todo["tries"] = todo.get("tries", 0) + 1
    (WORK / "checklist.json").write_text(json.dumps(state, indent=1))
    return "RETRY"
todo.update(done=True, evidence={"breaks_rule": f.breaks_rule, "quote": f.quote})
```
- Line 1: is the model's quote really in the contract?
- Line 2: if not, add one to this item's try count.
- Line 3: save the checklist, so the count survives a crash.
- Line 4: return "RETRY"; the item stays not done.
- Line 5: quote is real: mark done, attach verdict and quote.

## Reliable runs
- Reliable (fault tolerant): a crash loses one item, not the job.
- Reproducible: each item is a git commit you can review and replay.
- Stop rule: the loop runs at most 16 + 4 times. Never forever.
- Stop hook: the final report refuses to run while any item lacks evidence.

## Crash vs restart
| Without a checklist file | With a checklist file |
|---|---|
| Crash at item 9: progress was in the model's context | Crash at item 9: items 1–8 are saved and committed |
| Restart redoes everything | Restart reads the file, runs only unfinished items |

## How this applies to us
- Due diligence is a long job. On a local machine it may run for hours.
- Saved progress means a crash or reboot costs one item.
- Every step is a commit a lawyer can review: "full receipts for every row."

## Common mistakes
- Letting the agent edit the checklist → it can make the job look finished.
- Many items per session → one item, verify, commit.
- Progress kept in the model's head → if it isn't in a file, it didn't happen.
- "Done" without evidence → require a quote; check it in code.
- No loop limit → cap loops and retries.

## Check your understanding
**Q: Why one item per session?**
A: Small steps with a commit each mean a failure loses one item, and every step can be reviewed.

**Q: The run crashes halfway. What happens on restart?**
A: It reads the checklist and continues with unfinished items. Finished items are not redone.

**Q: Why does code, not the model, write the checklist?**
A: So the job's scope is fixed. The model can only report on items, not change what the job covers.
