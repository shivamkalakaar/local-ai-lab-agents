## The big idea

A model can only read so much at once. That limit is the context window (the amount of text the model can hold in mind at one time). Some jobs are far bigger. Reviewing 200 contracts in a data room won't fit in one sitting.

So the agent has to work in sessions, and each new session starts with a blank mind. The fix is to write memory down outside the model.

Think of a night-shift nurse handing over to the day shift. The day nurse doesn't remember the night. She reads the chart: what was done, what is left, what to watch. The chart holds the progress, not anyone's head.

For agents, that chart is a checklist and a progress file. Each session reads them, does one item, marks it done only with evidence, and saves. The job can't be called finished until every item has evidence.

## Why it matters for us

- Due diligence and portfolio reviews are long jobs. A firm needs them done reliably, not in one fragile run.
- A local box may be slower than a cloud service. Long jobs will run for hours, and crashes happen. With saved progress, a crash loses one item, not the whole job.
- Lawyers need to see every step. A record after each item makes the work reviewable and replayable.

## How it works, step by step

1. **A setup session writes the checklist.** Code, not the model, writes one item per contract per rule. Every item starts as "not done". It also creates an empty progress file.
2. **The agent may only tick boxes.** It can flip an item to done and attach evidence. It can never add, remove or reword items. Otherwise it could quietly shrink the job.
3. **Each work session does one item.** Read the checklist, pick the next unfinished item, do it, save. One item per session keeps each step small and checkable.
4. **Evidence must be real.** The agent quotes the exact words that decide the item. Code checks that the quote really appears in the contract. If not, the item is retried later, up to a limit.
5. **Commit after each step.** Each finished item is saved as a commit in git (a tool that keeps a numbered history of file changes). You can see and replay every step.
6. **A stop hook guards the finish.** A stop hook is a rule that blocks the final report until every item has evidence.

```
setup:  checklist (all "not done") + progress file
loop:   read checklist -> do ONE item -> verify quote -> mark done -> commit
finish: only when every item has evidence
```

Line by line: the first line asks whether the model's quote really appears in the contract. If it doesn't, the second line adds one to the item's try count. The third line saves the checklist so the count survives a crash. The fourth line returns "retry", leaving the item not done. If the quote is real, the last line marks the item done and attaches the verdict and quote.

After each item, the progress file gets a line naming the item and "BREAKS" or "ok", and git gets a commit. The loop has a hard limit, so it can never run forever. Items that fail three times are skipped for a person to look at.

At the end, the notebook scores the finished items against the true answers. It also shows the git log, one commit per item.

## Common mistakes

- **Letting the agent edit the checklist.** It may only flip "done" with evidence. A model that can reword the list can make the job look finished.
- **Doing many items per session.** One item, verify, commit. Big steps mean big losses when something fails.
- **Keeping progress in the model's head.** The next session starts blank. If it isn't in a file, it didn't happen.
- **Accepting "done" without evidence.** Require a quote, and check it in code.
- **No stop limit.** Always cap the number of loops and retries.

## Check your understanding

**Q: Why one item per session?**
A: Each session starts with a clean context. Small steps with a commit each mean a failure loses one item, not the whole job, and every step can be reviewed.

**Q: The run crashes halfway. What happens when you restart it?**
A: It reads the checklist and continues with the unfinished items. The file holds the progress, so finished items are not redone.

**Q: Why does code, not the model, write the checklist?**
A: So the scope of the job is fixed and trusted. The model can only report on items, not change what the job covers.
