# Terminal-Bench: data for agents

## What does agent test data look like?
- For models, test data is inputs + labels.
- For agents, it is tasks: a goal, an environment to act in, and a check on the result.
- Lecture 10's example: Terminal-Bench, by Alex Shaw and Ryan Marten.

# Terms

## Definitions
- Task: a single test with defined inputs and success criteria.
- Trial: one attempt at a task.
- Benchmark (evaluation suite): a set of tasks measuring specific abilities.
- Verifier (grader): logic that scores the agent's work.
- Trajectory (trace, transcript): the complete record of a trial.
- Evaluation harness: infrastructure that runs evals end to end.
- Agent harness: the system that lets a model act as an agent.

## Agent harness vs evaluation harness
| Agent harness | Evaluation harness |
|---|---|
| Loop, tools, prompts, limits around the model | Starts sandboxes, runs trials, runs verifiers, stores results |
| Examples: Claude Code, Codex, mini-swe-agent | Example: Harbor |
| Swap it, and you test a different agent | Keep it fixed, so trials are comparable |

## Our terms
- Task: one checklist item, e.g. `msa_13:termination_notice`.
- Trial: one work session on that item.
- Verifier: code that checks the quote is really in the contract.
- Trajectory: the git log plus `progress.md`.

# The task format

## What a task should be
| Property | Meaning |
|---|---|
| Agent agnostic | Any agent harness can attempt it |
| Easy to define | A few plain files |
| Portable | Runs locally or in the cloud |
| Expressive | Any job a terminal can do |
| Independent | Each task stands alone |

## The task folder
```
my-task/
  instruction.md      what the agent is asked to do
  task.toml           task settings
  environment/
    Dockerfile        the starting machine
  solution/
    solve.sh          reference solution (oracle)
  tests/
    test.sh           the verifier
```
- The agent sees only the instruction and the environment.
- Solution and tests stay out of its reach. (Project 2 builds one of these.)

# Harness and infrastructure

## Eval infra
- Reliable (fault tolerant): one broken trial doesn't kill the run.
- Reproducible: the same task, agent and model give comparable results.
- Fast: run independent trials in parallel.
- Portable: local and cloud sandboxes.

## Rollout infra: test, train, prod
| Inputs | Harbor rollout engine | Outputs |
|---|---|---|
| Tasks, models, agents, sandboxes, skills | Runs every combination in parallel | Trajectory analysis, evaluation, optimization, task QA, artifacts |

- The same engine serves test (evals), train (rollouts for training) and prod.

# Keeping it reproducible

## CI/CD: continuous benchmarks
- Tasks are software. Software has bugs.
- Loop: new tasks → GitHub → Harbor (v1.1.0) → benchmark runs → tbench.ai → issues → back to GitHub.
- Usage turns into bug reports:
  - Flakiness; infra noise and compatibility.
  - New models = new behavior.
  - False negatives (good work marked failed); reward hacking.

## Versioning: what a change costs
| Version bump | Action | What changed |
|---|---|---|
| (x+1, y, z) | Rerun | Agent environment: new task, fix under- or over-specified prompt, change data, tools or resources |
| (x, y+1, z) | Regrade | Verifier: fix an overly strict check, close a reward hack, re-tune a judge, change the reward |
| (x, y, z+1) | Reuse | Metadata: docs, oracle flakiness, pin dependencies, fix a typo |

- Old trajectories can be regraded without rerunning the agent, if only the verifier changed.

# Long-running jobs

## Why long jobs are hard
- Context window: how much text the model can hold at once.
- Long-horizon: context grows and drifts over many steps (Lecture 1, key challenges).
- 200 contracts in a data room won't fit in one sitting.
- Each new session starts blank. Progress must live in files, not in the model.

## The pattern
```
setup:  checklist (all "not done") + progress file
loop:   read checklist → do ONE item → verify quote → mark done → commit
finish: only when every item has evidence
```
- Setup session: code writes the checklist. One item per contract per rule.
- Work session: read the progress file, do one item, then save.

## Who may change what
| The code | The agent |
|---|---|
| Writes the checklist (scope is fixed) | May only flip `done` and attach evidence |
| Checks the quote is in the contract | Answers: does the clause break the rule? |
| Commits each step to git | Never adds, removes or rewords items |
| Blocks the final report until all items have evidence | Can't call the job finished |

## Our matter: 16 items
- 4 contracts × 4 playbook rules = 16 items, e.g. `msa_13:termination_notice`.
- msa_13, 4.1: "...at least 15 days' prior written notice of non-renewal." Rule needs at least 30 → breaks.
- The model must quote the exact words that decide it.
- Retries get temperature 0.5 for variety. After 3 failed tries, the item is left for a person.

## Verifying evidence in code
```python
if not quote_is_in_doc(f.quote, contract(todo["contract"])):
    todo["tries"] = todo.get("tries", 0) + 1
    (WORK / "checklist.json").write_text(json.dumps(state, indent=1))
    return "RETRY"
todo.update(done=True, evidence={"breaks_rule": f.breaks_rule, "quote": f.quote})
```
- Line 1: is the model's quote really in the contract?
- Line 2: if not, add one to this item's try count.
- Line 3: save the checklist, so the count survives a crash.
- Line 4: return "RETRY"; the item stays not done.
- Line 5: quote is real: mark done, attach verdict and quote.

## Reliable runs
- Reliable (fault tolerant): a crash loses one item, not the job.
- Reproducible: each item is a git commit you can review and replay.
- Stop rule: the loop runs at most 16 + 4 times. Never forever.
- Stop hook: the final report refuses to run while any item lacks evidence.

## Crash vs restart
| Without a checklist file | With a checklist file |
|---|---|
| Crash at item 9: progress was in the model's context | Crash at item 9: items 1–8 are saved and committed |
| Restart redoes everything | Restart reads the file, runs only unfinished items |

## Tools built for agents (SWE-agent)
- Agent-computer interface: tools shaped for a model, not a person.
- A file viewer that shows 100 lines at a time, with line numbers.
- Search that returns a capped summary, not every match.
- An edit tool that rejects edits that break syntax and says why.

# How this applies to us

## A data room is a long task
- Due diligence is a long job. On a local machine it may run for hours.
- Saved progress means a crash or reboot costs one item.
- Every step is a commit a lawyer can review: "full receipts for every row."

## Use the benchmark habits
- Version the checklist and the checker like Terminal-Bench versions tasks.
- Changed only the checker? Regrade the saved evidence; don't rerun the model.
- Keep the agent harness fixed when comparing two local models.

## Common mistakes
- Letting the agent edit the checklist → it can make the job look finished.
- Many items per session → one item, verify, commit.
- Progress kept in the model's head → if it isn't in a file, it didn't happen.
- "Done" without evidence → require a quote; check it in code.
- No loop limit → cap loops and retries.

## Check your understanding
**Q: What is the difference between a task, a trial and a trajectory?**
A: A task is one test with inputs and success criteria. A trial is one attempt at it. The trajectory is the full record of that attempt.

**Q: You fix an overly strict verifier. Must you rerun every agent?**
A: No. That is a verifier change (x, y+1, z): regrade the saved trajectories and artifacts. Only agent-environment changes need a rerun.

**Q: Why one item per session?**
A: Small steps with a commit each mean a failure loses one item, and every step can be reviewed.

**Q: The run crashes halfway. What happens on restart?**
A: It reads the checklist and continues with unfinished items. Finished items are not redone.

**Q: Why does code, not the model, write the checklist?**
A: So the job's scope is fixed. The model can only report on items, not change what the job covers.
