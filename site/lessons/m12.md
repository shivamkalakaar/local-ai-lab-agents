## Learning objective
- Build labeled contract cases cheaply, log every run, and turn corrections into tests and checked training data.

## Why data matters
- Same base model, different post-training data: big difference in results.
- Making tasks and trajectories is now cheap. Deciding what to keep is the hard part.
- A firm rarely has hundreds of labeled contracts ready. We have to make them.

## Two types of agent data
| Trajectory | Environment |
|---|---|
| A recording of an agent solving a task | A task + sandbox + a way to check success |
| Train with SFT: the model imitates it | Train with RL: the model practices |
| Ours: a trace of one review call | Ours: a contract with known issues + the grader |

## Where agent data comes from
- Human demos: realistic but costly.
- Mined from the web: code history, tutorials, videos.
- Synthesized trajectories: a model writes or runs the steps; a filter keeps good runs.
- Synthesized tasks: inject a known fault, so the checker knows the answer.
- Simulated users or environments: endless practice, but errors get learned too.

## Synthesized tasks: SWE-smith
- SWE-smith: inject bugs that break existing tests in 128 Python repos.
- An LM writes the issue text. 50k tasks from about 20 hours of human work.
- Same idea for us: take a clean contract, break one clause in code.
- The right answer is known by construction. No lawyer needed to label it.

## Planting faults in code
```python
FAULTS = {
    "liability_cap":      lambda t: re.sub(r"IN THE 12 MONTHS", "IN THE FORTY-EIGHT (48) MONTHS", t),
    "governing_law":      lambda t: re.sub(r"State of (California|Delaware)", "State of Nevada", t),
    "auto_renewal":       lambda t: t.replace("successive one (1) year", "successive four (4) year"),
    "termination_notice": lambda t: re.sub(r"at least [\w\s()]+? days'", "at least seven (7) days'", t),
}
```
- Line 1: one entry per playbook rule.
- Line 2: 12-month cap → 48 months (rule: at most 12).
- Line 3: California or Delaware → Nevada.
- Line 4: one-year renewal → four years (rule: at most 1).
- Line 5: any notice period → seven days (rule: at least 30).

## Clean vs planted
| Clean (msa_03) | Planted case |
|---|---|
| "...in the 12 months preceding the claim" | "...in the forty-eight (48) months preceding the claim" |
| issues: none | issues: liability_cap (known) |

- The notebook builds 30 cases from the 6 clean contracts, 1 or 2 faults each.

## The flywheel
```
use → traces + corrections → tests now, training later → better system → more use
```
- Trace: the full record of one run: input hash, prompt, model, output, time.
- Regression set: past mistakes you rerun after every change.
- Each lawyer's fix is free expert labeling. Save it with the reason.

## Rejection sampling for training data
- Let the model try each case (up to 2 tries).
- Keep only answers that exactly match the known issues. Drop the rest.
- Save as chat-format JSONL (`sft_train.jsonl`) that TRL or Unsloth can fine-tune on.
- Never put held-out eval cases in training.

## What data teaches by accident
- Reward hacking: models faked passing tests with `sys.exit(0)`.
- Trained on human approval: the model learned to look right, not be right.
- Overfit to harness: trained in one harness, it keeps that harness's habits.
- Best model ≠ best teacher.

## How this applies to us
- Traces and corrections live on the firm's own disk: audit trail and future training set.
- Planted faults give labeled cases without sending contracts anywhere.
- Fine-tuning on checked data can run on the same local machine later.

## Common mistakes
- Guessing why it fails → read 50–100 real outputs with the customer.
- Synthetic-only cases → keep real contracts in every eval and training set.
- Rewarding "a reviewer approved it" → reward answers checked against labels.
- Reusing stored examples unfiltered → one bad example poisons later runs.

## Check your understanding
**Q: Where does a lawyer's correction go?**
A: Logged with the reason, added to the regression set at once, then into the next training batch. Never into the held-out eval.

**Q: Why are planted faults useful?**
A: We broke the clause ourselves, so the right answer is known. Many labeled cases, no labeling cost.

**Q: What is rejection sampling?**
A: Let the model try, keep only answers the checker accepts. What is left is clean training data.
