## The big idea

Every time the agent runs, something useful happens. It gets a contract right, or it gets one wrong and a lawyer fixes it. If you write that down, it becomes data. If you don't, it's gone.

Think of a restaurant kitchen. A good chef keeps notes: which dish came back, why, and what fixed it. Those notes train the next cook. Over time the kitchen gets better because it remembers its own mistakes.

This lesson covers two habits. First, make test cases where you already know the answer, by planting problems on purpose. Second, build a flywheel: a loop where use creates records, records improve tests and training, and a better system gets more use.

## Why it matters for us

- Firms rarely have hundreds of labeled contracts ready to go. Planting known problems in clean contracts gives us labeled cases cheaply.
- A local system logs everything on the firm's own disk. That log is the audit trail and the future training set, and it never leaves the building.
- Each lawyer edit is free expert labeling. Capturing it with a reason is how the system improves month by month.

## How it works, step by step

1. **Plant known faults.** Take a clean contract. Use code to change one clause so it breaks a rule. For example, change a 12-month liability cap to 48 months. Now the right answer is known by construction. This idea comes from the SWE-smith paper (2025), which planted known bugs into working code. Each of its synthetic tasks cost about 2.5 cents.

2. **Log every run as a trace.** A trace is the full record of one run: the input, the prompt, the model name, the output, and the time taken. Traces show what really happened, not what you hoped happened.

3. **Turn corrections into tests at once.** When a lawyer fixes a miss, store the input, the wrong answer, the right answer and the reason. Add it to a regression set right away. A regression set is a list of past mistakes you rerun after every change, to make sure they stay fixed.

4. **Build training data by rejection sampling.** Let the model try each case. Keep only the answers a checker accepts, and throw away the rest. What's left is clean data to fine-tune on later.

5. **Batch into releases, and protect the eval.** Gather corrections into a training set for the next release. Never train on the held-out eval set, or your test scores become meaningless.

```
use -> traces + corrections -> tests now, training later -> better system -> more use
```

## Worked example

The firm's rules: liability cap at most 12 months of fees, governing law California or Delaware, renewals at most 1 year, notice at least 30 days.

The notebook defines four ways to break a clean contract:

```python
FAULTS = {
    "liability_cap":      lambda t: re.sub(r"IN THE 12 MONTHS", "IN THE FORTY-EIGHT (48) MONTHS", t),
    "governing_law":      lambda t: re.sub(r"State of (California|Delaware)", "State of Nevada", t),
    "auto_renewal":       lambda t: t.replace("successive one (1) year", "successive four (4) year"),
    "termination_notice": lambda t: re.sub(r"at least [\w\s()]+? days'", "at least seven (7) days'", t),
}
```

Line by line: each line is one fault, named after the rule it breaks. The liability line swaps a 12-month cap for 48 months. The law line swaps California or Delaware for Nevada. The renewal line changes a one-year renewal to four years. The notice line changes any notice period to seven days. Each is a simple find-and-replace, so we know exactly what we broke.

The notebook picks one or two faults at random for each case. From the clean contracts it builds 30 new cases, each with a known list of issues. Then the reviewer runs on them, and every call is written to a traces file.

Where the reviewer misses a planted fault, or flags something that isn't there, the case goes into the regression file. Finally, the notebook runs the reviewer on 10 more cases, up to two tries each. It keeps only answers that exactly match the known issues, and writes them in the standard chat format that fine-tuning tools read.

## Common mistakes

- **Theorizing instead of reading.** Don't guess why the agent fails. Read 50–100 real outputs with the customer and write down the failures in plain words.
- **Using only synthetic cases.** A model can look great on cases built from your own templates and still fail on real documents. Keep real contracts in every eval and training set.
- **Rewarding "the reviewer approved it".** The model learns to look right rather than be right. Reward correct answers, checked against known labels.
- **Vague quality scores.** A pass or fail per criterion beats a 1–5 "quality" rating. It is clearer and people agree on it more.
- **Auto-reusing stored examples without filtering.** One bad example, pulled into future prompts, quietly poisons later runs.

## Check your understanding

**Q: Where does a lawyer's correction go, in order?**
A: It is logged with the reason, added as a test case, used as a retrieved example right away, and included in the next training batch. It never goes into the held-out eval.

**Q: Why are planted faults useful?**
A: We changed the contract ourselves, so we know the right answer without paying a lawyer to label it. That gives many labeled cases cheaply.

**Q: What is rejection sampling?**
A: Let the model try several times and keep only the answers a checker accepts. The kept answers become clean training data.
