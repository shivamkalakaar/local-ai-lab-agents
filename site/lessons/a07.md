## Learning objective
- Use two kinds of search to make an agent better without training: sample-filter-cluster over answers, and search in the middle of reasoning.

## Two kinds of search
| Search over answers | Search for knowledge |
|---|---|
| Draw many programs, keep the good ones | Pause mid-thought, look a fact up |
| Needs a cheap check (example tests) | Needs a search tool over your documents |
| AlphaCode (2022), AlphaCode 2 (2023) | Search-o1 (2025) |

- Both make the agent better with no change to the model.

## AlphaCode: sample, filter, cluster
- Sample: draw up to millions of programs per problem.
- Filter: run each on the example tests in the problem. Drop the ones that fail.
  - Removed about 99% of samples.
- Cluster: run survivors on new inputs; group programs with identical outputs.
  - The inputs need no known answers.
- Submit one program per cluster, biggest first, at most 10.

## Why the biggest cluster first
- Many ways to be wrong; correct programs tend to agree.
- So correct programs gather in the larger clusters.
- Random picks waste submissions on programs that look different but behave the same.
- Coverage: share of problems where at least one sample is correct. The ceiling for any picking method.

## Same tests, different behavior
| Correct `max_subarray` | Planted wrong version |
|---|---|
| `best = cur = nums[0]` | `best = cur = 0` |
| `cur = max(x, cur + x)` | `cur = max(0, cur + x)` |
| Passes both example tests | Also passes both example tests |
| All-negative list → largest number | All-negative list → 0 |

- Filtering can't catch it. On generated inputs it behaves differently, so it lands in another cluster.

## What the papers showed
| Paper | What it showed |
|---|---|
| AlphaCode (Li et al. 2022) | Top 54.3% in simulated Codeforces contests; 34.2% of held-out problems with 10 submissions |
| AlphaCode 2 (2023) | 43% of 77 recent Codeforces problems in 10 tries vs 25%; about 85th percentile |
| Search-o1 (Li et al. 2025) | GPQA diamond 63.6 vs 58.6 with standard RAG and 58.1 with no retrieval |

- AlphaCode 2 added a scoring model: predicts how likely a sample is correct; picks the best in each cluster.
- It needed about 100 samples to match AlphaCode with a million.

## Comparing ways to pick
| Method | What it does |
|---|---|
| random | pick K samples at random |
| filter + random | pick K at random from those passing the examples |
| filter + cluster | one sample from each of the K biggest clusters |
| oracle | any sample correct (coverage) |

- The gap to the oracle row is the selection problem.
- 10@k: share of problems solved when k samples are drawn but only 10 may be submitted.

## Naive RAG vs Search-o1
| Naive RAG | Search-o1 style |
|---|---|
| Search once, with the whole question | Model writes `<search>query</search>` when unsure |
| Paste the raw results in | Reason-in-Documents condenses results first |
| Often gets one hop, misses the other | Searches for one fact at a time |

- RAG (retrieval-augmented generation): search first, then answer from what you found.
- Agentic RAG: the model decides when and what to search, possibly many times.

## Reason-in-Documents
- A separate step: reads the retrieved pages, the reasoning so far and the query.
- Writes back only the useful facts (our notebook: 1–3 sentences).
- Why: long, noisy pages can push the reasoning off track.
- Search-o1 beat agentic RAG without this step by 4.7% averaged over five reasoning datasets.

## A two-hop question
- Question: "Under our procurement policy, who must approve the agreement between Bayview Health Partners and Brightline Data Corp.?"
- Hop 1 (contract msa_01, 2.1): "Customer shall pay Vendor $12,500 per month"
- Hop 2 (Procurement Policy PP-4): $5,000 up to and including $15,000 → Finance Director
- Answer: Finance Director. One search with the whole question may bring back only one hop.

## The Search-o1 loop in code
```python
out = ask_msgs(msgs, stop=["</search>"])
...
query = out[i_s + len("<search>"):].strip()[:200]
docs = search(query)
info = reason_in_documents(transcript, query, docs) if condense else "\n".join(d["text"] for d in docs)
transcript += f"</search>\n<result>{info}</result>"
```
- Line 1: the model reasons; generation stops right after it asks for a search.
- Line 3: cut out the query between the tags.
- Line 4: BM25 search (keyword scoring) over contract sections and policies, top 3.
- Line 5: condense the pages into a few facts (or paste raw pages if `condense=False`).
- Line 6: put the facts back inside `<result>` and let the model continue. At most 3 searches.

## How this applies to us
- A local model often fails on the first try. With a cheap exact check, drawing many and filtering is affordable on the firm's machine.
- A local model knows nothing about the firm's contracts or policies. It must look them up.
- Many firm questions need two facts from two places: the fee from the contract, the rule from the policy.

## Common mistakes
- "Passes the examples" = "correct" → many wrong programs pass; cluster and use hidden tests.
- Searching once with the whole question → let the model search one fact at a time.
- Pasting long raw results into the reasoning → condense to a few facts first.
- Reading only the score → a small model may never search, or search with vague words. Read the transcripts.
