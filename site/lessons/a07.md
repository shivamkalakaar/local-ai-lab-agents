## The big idea

You can make an agent better without changing the model at all. You make it search. There are two kinds of search, and they solve different problems.

The first is search over answers. Think of hiring. You don't interview one candidate and hope. You get many applications, throw out the ones that fail the basic screen, and then pick carefully from the rest. AlphaCode does this with computer programs.

The second is search for knowledge. Think of a lawyer drafting a memo. When they hit a fact they don't know, they stop, look it up, jot down the one line that matters, and keep writing. Search-o1 teaches a model to do this in the middle of its reasoning.

## Why it matters for us

- A small local model often gets things wrong on the first try. But if you can check answers cheaply, drawing many and filtering is affordable on your own machine.
- A local model knows nothing about the firm's contracts or internal policies. It must look them up. Doing that well is the difference between a useful assistant and a confident guesser.
- Many firm questions need two facts from two places. "Who must approve this contract?" needs the fee from the contract and the rule from the policy. Searching once rarely gets both.

## How it works, step by step

1. **Sample many answers** (the AlphaCode paper, 2022). For each coding problem, AlphaCode drew huge numbers of programs, up to millions. More tries means a better chance at least one is right. The share of problems where at least one try is right is called coverage. It is the ceiling for any picking method.

2. **Filter with the examples.** Each problem comes with a few example tests. Running every program on them threw away about 99% of samples. This is a cheap, exact check. But passing the examples is not the same as being correct. Many wrong programs still pass.

3. **Cluster by behavior.** Run the survivors on fresh inputs. These inputs need no known answers. Group programs that give the same outputs. Then submit one program from each group, biggest group first, with at most 10 submissions. Why biggest first? There are many ways to be wrong, but correct programs tend to agree. So they pile up in the largest group. AlphaCode 2 (2023) kept this pipeline and added a scoring model (a model that predicts how likely a program is correct) to choose inside each group. With a better base model, it needed about 100 samples to match what the original needed a million for.

4. **Search for knowledge: first, RAG from zero.** RAG (retrieval-augmented generation) means: before the model answers, a search tool finds relevant documents and pastes them into its prompt. It is like handing the intern a folder before they answer. Naive RAG searches once, with the whole question.

5. **Search-o1: search while thinking** (the Search-o1 paper, 2025). The model reasons step by step. When unsure, it writes a search query between special tags, like `<search>...</search>`. The system pauses, runs the search, and the model continues. This is agentic RAG: the model itself decides when and what to search, possibly several times.

6. **Condense before pasting back.** Raw search results are long and noisy. They can pull the reasoning off track. So a separate step, called Reason-in-Documents, reads the results and writes back only the few facts that matter. On a hard science quiz, this setup scored 63.6, against 58.6 for standard RAG with the same model.

```
model reasons ... <search>fee in Acme contract</search>
     -> search tool -> 3 pages -> Reason-in-Documents -> "Monthly fee is $8,000."
model continues ... <search>procurement approval tiers</search>
     -> ... -> "$5,000 to $15,000: Finance Director."
model: ANSWER: Finance Director
```

## Worked example

The notebook builds this exact case. The corpus has 20 contracts and a few internal policies. One policy, "Procurement Policy PP-4", says who approves vendor spending. Under $5,000 a month, the Department Head. From $5,000 up to $15,000, the Finance Director. Above that, the Chief Financial Officer.

The question: "Who must approve the agreement between this customer and this vendor?"

- **No search.** The model has never seen these documents. It guesses.
- **Naive RAG.** One search with the whole question. It often brings back the contract or the policy, but not both. Half the facts means a wrong answer.
- **Search-o1 style.** The model searches for the contract's fee first. The condensing step returns one sentence with the fee. Then it searches for the approval rule. It now has both hops and can answer.

The search tool itself is plain code:

```python
def search(query, k=3):
    scores = BM25.get_scores(tok(query))
    return [DOCS[i] for i in sorted(range(len(DOCS)), key=lambda i: -scores[i])[:k]]
```

- Line 1 defines a search that returns the top `k` documents, three by default.
- Line 2 scores every document with BM25, a classic keyword-matching method. More shared words, especially rare ones, means a higher score.
- Line 3 sorts documents from best to worst score and returns the top three.

The AlphaCode half of the notebook plants a wrong program that passes both example tests. Filtering can't catch it. But on fresh inputs it behaves differently, so it lands in a separate, smaller group.

## Common mistakes

- **Treating "passes the examples" as "correct".** Many wrong programs pass. Use clustering and hidden tests.
- **Picking survivors at random.** You waste your submission budget on programs that look different but behave the same.
- **Searching once with the whole question.** For two-step questions, let the model search for each fact on its own.
- **Pasting long raw results into the reasoning.** Condense them to a few facts first.
- **Only reading the score.** A small model may never search, or may search with vague words. Read the transcripts.
