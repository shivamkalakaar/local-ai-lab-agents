## The big idea

A model can only read so much at once. That limit is the context window (the amount of text the model can see in one go). Everything it knows about your task must fit there.

Think of it as a small desk. A lawyer with a clean desk, holding only the clause they need, works well. Pile twenty binders on it and they slow down and miss things. Models are the same. Quality drops well before the desk is full. The course saw measurable decline starting around 8K tokens (about a few thousand words) on one test.

Context engineering is the habit of choosing what goes on the desk at each step. Keep the goal, the rules and the recent work. File the rest away, where you can fetch it when needed.

## Why it matters for us

Local models have smaller useful desks than big cloud models. They also slow down as the prompt grows, because every extra word costs computing time on your own GPU. So a tidy desk means faster and better answers.

In an agent, the biggest clutter is old tool output. In one coding agent, about 84% of all tokens were tool results. Hiding the old ones roughly halved cost with equal or better results (course Lecture 6). For contract review, that means old clause text the agent already read.

There is also a safety point. Rules like "never send anything" must never fall off the desk.

## How it works, step by step

1. **Keep a full log, separately.** Store every step in an append-only event log (a list you only ever add to, never edit). This is your full record for audits and replays. What the model sees is rebuilt from this log each turn.

2. **Pin the hard rules.** Put critical rules in the system prompt (the standing instructions at the top). Never let them live only in chat history. One real agent deleted a user's inbox after "confirm before acting" got summarized away.

3. **Hide old tool outputs.** This is observation masking. Replace each old tool result with a one-line note like "[old tool output hidden, 400 chars]". Keep the last few turns word for word. It needs no extra model call. Try this first.

4. **Summarize the middle if you must.** This is compaction. When hiding isn't enough, ask the model to summarize the older history. Keep the rules, the goal and the recent turns out of the summary.

5. **Load just in time.** Don't paste every contract "just in case." Keep a list of IDs. Load the one contract you need, when you need it. Write progress to a notes file so it survives a reset.

6. **Keep the start stable.** If the system prompt and tool list stay identical across calls, the server can reuse work it already did on that opening text. This speeds up each call.

```
what the model sees each turn:
[pinned rules] [user's goal] [old steps, tool output hidden] [last 4 turns, in full]
          ^ rebuilt every turn from the full log, which is never edited
```

## Worked example

First, the notebook measures the desk problem. It asks "What governing law does msa_09 use?" with 1, then 5, then 10 contracts in the prompt. You see the token count and time climb, even though the answer is in one contract.

Next, it records an agent reviewing `msa_15`. The agent reads sections 3, 4, 7, 9 and 10. Each read is logged as a tool result. Then it builds a trimmed view:

```python
def build_context(events, keep_recent=4):
    msgs = [{"role": "system", "content": PINNED}, events[0]]
    for e in events[1:-keep_recent]:
        if e["kind"] == "tool":
            msgs.append({"role": e["role"], "content": f"[old tool output hidden, {len(e['content'])} chars]"})
        else:
            msgs.append(e)
    return msgs + events[-keep_recent:]
```

- The function takes the full log and how many recent events to keep in full.
- `msgs` starts with the pinned rules and the first event, which is the user's goal.
- The loop walks through the middle events, skipping the last four.
- If an event is a tool result, it is swapped for a short placeholder.
- Other events, like "Reading section 7," are kept as is.
- Finally, the last four events are added back word for word.

The notebook prints the full size and the trimmed size, so you can see how much smaller the context got. The full log is untouched.

Then compaction. The middle is summarized into at most 5 bullets, with clause numbers kept exact. The notebook checks that "never send" is still in the pinned rules afterward.

## Common mistakes

- **Stuffing every document in "just in case."** It makes answers worse, not better. Load what the step needs.
- **Summarizing first.** Summaries cost a model call and can lose details. Hide old tool output first, since it is free.
- **Keeping safety rules only in chat history.** Compaction can delete them. Pin them in the system prompt.
- **Editing earlier messages.** It breaks the server's reuse of the stable opening, so you pay to reprocess everything. Rebuild from the log instead.

## Check your understanding

**Q: Your local agent gets slow and worse after 20 turns. What do you try first?**
A: Hide old tool outputs. It is free, and tool outputs are most of the tokens. Summarize only if that isn't enough.

**Q: Why rebuild the context from a log instead of keeping one growing list?**
A: The log stays the complete record for audit and replay. Meanwhile, what the model sees can be trimmed freely. You get both.

**Q: Where should "never send, file or delete anything" live?**
A: In the pinned system prompt, outside anything that gets trimmed or summarized. Then no amount of compaction can remove it.
