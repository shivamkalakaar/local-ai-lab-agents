## Learning objective
- Choose between three ways to give an agent more memory: agent paging (MemGPT), KV-cache reuse (CacheBlend, LMCache), and trained memory (Cartridges).

# Why this lecture: the context window is the bottleneck

## Why memory?
- Context window: the text a model can see in one call. Everything else is invisible.
- Prefill: the model reads the whole prompt before writing. Longer prompt, longer wait.
- A contract archive is far bigger than any window.
- The same playbook and contracts are sent again and again.

## Two costs of long context
| Problem | Example from the papers |
|---|---|
| Doesn't fit | SEC 10-K filings "can easily pass the million token mark" (MemGPT) |
| Fits, but slow | Prefill of a 4,000-token input: about 3 s (Llama-34B) or 6 s (Llama-70B) on one A40 GPU (CacheBlend) |
| Fits, but uses lots of memory | LLaMA 70B needs 84 GB at 16-bit for one question over 128k tokens (Cartridges) |
| Fits, but used badly | Long-context models recall the start and end better than the middle (Liu et al. 2023, cited by MemGPT) |

## Three layers
| Tool | Layer | Best when |
|---|---|---|
| MemGPT paging | the agent | many documents; the agent picks what to read; you want an audit trail |
| Prefix / KV caching (CacheBlend, LMCache) | the server | the same long text is sent again and again |
| Cartridges | trained ahead | one big corpus, queried thousands of times |

## The four papers
| Paper | Main idea | Headline result |
|---|---|---|
| MemGPT (Packer et al., UC Berkeley, 2023) | OS-style memory tiers; the LLM pages data with function calls | Deep memory retrieval, GPT-4: 32.1% → 92.5% (Table 2) |
| CacheBlend (Yao et al., UChicago, EuroSys 2025) | Reuse KV caches of RAG chunks anywhere; recompute ~15% of tokens | TTFT 2.2–3.3x lower, throughput 2.8–5x higher |
| LMCache (Liu, Yao, Cheng et al., 2025; background, not assigned) | Open-source KV cache layer outside the GPU | Up to 15x throughput with vLLM (authors' report) |
| Cartridges (Eyuboglu, Ehrlich, Arora et al., Stanford, 2025) | Train a small KV cache per corpus with self-study | ICL quality with 38.6x less memory, 26.4x more throughput |

# MemGPT (Packer et al. 2023)

## The problem
- LLMs support only a few dozen messages or a short document before the window fills.
- Longer context costs quadratic time and memory in self-attention.
- Even long-context models struggle to use extra context well.
- Idea: give the illusion of infinite context while keeping a fixed-context model.
- Borrowed from operating systems: virtual memory pages data between RAM and disk.

## The OS analogy
| Operating system | MemGPT |
|---|---|
| Physical memory (RAM) | Main context: the prompt tokens |
| Disk | External context: databases outside the window |
| Page fault: load data back from disk | Function call: search and pull data into the prompt |
| Interrupts and events | User messages, system alerts, timers trigger the LLM |

## Memory tiers (Figure 3)
| Main context (in the prompt) | External context (outside) |
|---|---|
| System instructions (read-only) | Recall storage: every message ever |
| Working context: writable notes | Archival storage: searchable documents (any length text) |
| FIFO queue of recent messages | Fetched only with a function call |

- FIFO: first in, first out. Oldest messages leave first.
- Queue slot 0: a recursive summary of all evicted messages.
- Working context: key facts, user preferences, the agent's persona. Writable only via function calls.

## Queue manager: eviction policy
- Each new message: append to the FIFO queue, run the LLM, write input and output to recall storage.
- Warning token count (e.g. 70% of the window): insert a "memory pressure" system message.
  - The agent should save important facts to working context or archival storage
- Flush token count (e.g. 100%): evict a set of messages (e.g. 50% of the window).
  - Write a new recursive summary from the old summary + evicted messages
- Evicted messages stay in recall storage forever, searchable.

## Function executor
- LLM output is parsed as a function call; arguments checked; function run.
- Results and errors (e.g. "main context is full") go back to the LLM: a feedback loop.
- Memory edits and searches are self-directed: the model decides what to save and fetch.
- System instructions describe the memory tiers and give a function schema.
- Retrieval is paginated, so one search can't overflow the window.

## Control flow and function chaining
- Events trigger inference: user messages, system warnings, user actions (logged in, upload done), scheduled timers.
- Function chaining: a call with `request_heartbeat=true` returns control to the LLM right away.
  - Lets the agent page through results or combine several searches before replying
- No heartbeat flag = yield: wait for the next outside event.

## Memory in action (Figures 1, 2, 4)
- Memory pressure alert → `working_context.append("Birthday is February 7")`, `append("Boyfriend named James")`.
- User mentions Six Flags → `recall_storage.search("six flags")` finds "james and I actually first met at six flags".
- User says they broke up → `working_context.replace("Boyfriend named James", "Ex-boyfriend named James")`.
- The agent edits its own memory as facts change.

## Document QA (Figures 5, 6)
- Task: NaturalQuestions-Open question; a retriever finds Wikipedia passages; the LLM answers.
- 50 sampled questions; late-2018 Wikipedia dump; OpenAI text-embedding-ada-002; PostgreSQL + pgvector with an HNSW index.
- Fixed-context baselines: capped by the retriever. If the gold passage isn't in the top K, they never see it.
- Baselines past their window: truncate passages → accuracy drops.
- MemGPT pages through archival search; accuracy stays flat as documents increase.
  - Example: `archival_storage.search("nobel physics", page=2)` → "Wilhelm Conrad Rontgen"

## Document QA: caveats
- Gold passage often appears outside the first dozen results.
- MemGPT often stops paging before exhausting the retriever.
- MemGPT with GPT-3.5 does much worse: weak function calling.
- MemGPT with GPT-4 and GPT-4 Turbo: equivalent results.

## Nested key-value retrieval (Figures 7, 8)
- Keys and values are 128-bit UUIDs; a value can itself be a key (multi-hop lookup).
- 140 UUID pairs, about 8k tokens; nesting levels 0 to 4; 30 orderings.
- Results:
  - GPT-3.5: 0% at 1 nesting level (returns the first value)
  - GPT-4 and GPT-4 Turbo: 0% by 3 nesting levels
  - MemGPT + GPT-4: unaffected by depth
  - MemGPT + GPT-4 Turbo and GPT-3.5: better than baselines, but drop at 2 levels
- MemGPT stops when a search for the value returns only one result (so it is not also a key).

## Limitations
- Depends on the model's function-calling skill (GPT-3.5 struggles).
- The model decides what to save: if it skips a note, the fact leaves the window.
- Stops searching early on document QA.
- Future work named: other domains, other memory tiers (databases, caches), better memory policies.

# CacheBlend (Yao et al. 2024)

## KV cache basics
- KV cache: key and value vectors the model computes for every prompt token at every layer.
- Prefill: compute the KV cache for the whole input, layer by layer.
- Decode: generate tokens one by one, appending new K and V.
- Time to first token (TTFT): how long until the first word appears; set by prefill on long prompts.
- Prefill time grows super-linearly with input length.

## Three existing options (Figure 1)
| Method | Speed | Quality | Why |
|---|---|---|---|
| Full KV recompute | Slowest | Good | Prefill everything every time |
| Prefix caching | Marginally faster for RAG | Good | Reuses KV only for an exact matching start; only chunk 1 is a prefix |
| Full KV reuse (PromptCache) | Much faster | Low | Reuses each chunk's KV but ignores cross-attention |
| CacheBlend | Much faster | Good | Reuses all chunks, recomputes a small share of tokens |

## Why RAG needs many chunks (Figure 2)
- Chunk queries into 128-token chunks; retrieve top-k by embedding distance.
- On Musique and 2WikiMQA: F1 rises a lot as more chunks are added.
- Too many chunks hurts again ("lost in the middle").
- The gap between full recompute and full reuse grows with more chunks: more cross-attention.

## Why cross-attention matters (Figure 3)
| Full KV recompute | Full KV reuse |
|---|---|
| Chunk 1: "Lionel Messi scored 13 goals at FIFA World Cups." | Same chunks, KV computed separately |
| Chunk 2: "Cristiano scored 8 goals at FIFA World Cups." | Chunk 2 never "saw" chunk 1 |
| "Lionel Messi scored more goals ... than Cristiano Ronaldo." ✓ | "The question is asking for information about FIFA World Cups..." ✗ |

- Cross-attention: attention from one chunk's tokens to earlier chunks. Can't be precomputed, since the earlier chunks aren't known in advance.

## Definitions (Table 1)
- KV deviation: Δkv(KV_i, KV_i^full)[j] = absolute difference between token j's KV on layer i and its fully recomputed KV.
- Attention deviation: Δattn(A_i, A_i^full) = L2 norm of the difference between forward attention matrices.
  - Forward attention: attention from the last tokens (the query) to the context; directly sets the output
- Goal: update KV^pre to KV^new so attention deviation is as small as possible on every layer.

## Selective KV recompute (Figure 5)
- Per layer:
  - Mask the input down to the selected tokens
  - Compute Q, K, V only for those tokens
  - Fill in K and V for the other tokens from the cache
  - Run attention as usual; output feeds the next layer
- Cost: recomputing r% of tokens costs about r% of a full prefill.
- Positions fixed with RoPE: multiply K by a rotation matrix once (negligible cost).

## Which tokens to recompute
- Insight 1: recomputing tokens with higher KV deviation cuts attention deviation the most (Figure 6).
  - Biggest drop from the first few top-deviation tokens
- HKVD tokens: high-KV-deviation tokens on a layer.
- Attention is sparse: only about 10–15% of tokens have much higher KV deviation (Figure 7).
- So recomputing 10–20% of tokens is enough.

## Finding HKVD tokens cheaply
- Problem: you'd need the full KV to measure deviation, which defeats the purpose.
- Insight 2: tokens with high deviation on one layer tend to have high deviation on the next (high Spearman rank correlation, Figure 8).
- Gradual filtering (Figure 9):
  - Layer 1: recompute all, pick r1% (a bit more than r)
  - Layer 2: recompute those, pick r2% (a bit less than r1)
  - Continue layer by layer
- Extra memory is negligible: layer i's old KV is dropped when moving to layer i+1.

## Pipelining with KV loading (Figure 10)
- Recompute layer i while loading layer i+1's KV from storage.
- Llama-7B, 4K context: recompute 15% takes 3 ms per layer; loading one layer from NVMe SSD takes 16 ms → no extra delay.
- Llama-70B: recompute 15% takes 7 ms; loading 4 ms → recompute not fully hidden.
- So KV caches can live on slower, bigger, cheaper storage.

## Loading controller
- Formula: T_recompute(r%, LLM, L) = r% × Prefill(LLM, L)
- Formula: T_load(LLM, L, device) = PerTokenKVSize(LLM) × L ÷ Throughput(device)
  - L: context length; both prefill time and device throughput profiled offline
- Pick r so T_recompute ≈ T_load, but never below r* = 15% (minimum for quality, from Figure 16).
- Or fix r = 15% and pick the cheapest storage device where T_recompute ≥ T_load.

## System design (Figure 11)
- KV cache store: split input into chunks, hash each, look up its KV (like vLLM block hashing). Evict least recently used.
- Fusor: merges cached KVs with selective recompute, layer by layer.
- Built on vLLM, about 3K lines of Python (PyTorch v2.0).
- Interfaces: `fetch_kv(text, layer_id)`, `prefill_layer(input_dict, KVCache)`, `synchronize()`.
- Hash tables kept in CPU memory: 16MB for one million chunks.

## Evaluation setup
- Models: Mistral-7B, Yi-34B, Llama-70B (8-bit quantization for Yi-34B and Llama-70B).
- Hardware: 2 Nvidia A40 GPUs, 128 GB RAM, 1TB NVMe SSD (4.8 GB/s).
- Datasets: 2WikiMQA (200 cases), Musique (150), SAMSum (200), MultiNews (60).
- 512-token chunks; top-6 chunks per request.
- Metrics: F1 for QA, Rouge-L for summarization.
- Baselines: full recompute, prefix caching (assumed zero loading delay, a favorable assumption), full KV reuse, MapReduce, MapRerank.

## Main results (Figures 12, 14)
- vs full recompute and prefix caching: TTFT 2.2–3.3x lower; F1 / Rouge-L within 0.02.
- vs full KV reuse: slightly slower, but quality far better (often more than 2x).
  - Intro: 0.1–0.2 higher F1 on QA, 0.03–0.25 higher Rouge-L on summarization
- Throughput at the same delay: 2.8–5x higher than baselines.
- Prefix caching also wastes storage: one chunk needs a separate KV copy per distinct prefix.

## Versus other RAG methods (Figure 13)
| Method | How | Result vs CacheBlend |
|---|---|---|
| MapReduce | Summarize each chunk, then answer from summaries | 2–5x higher TTFT, lower F1 |
| MapRerank | Answer from each chunk alone, pick the most confident | Slightly lower TTFT, much worse quality |

## Sensitivity (Figures 15–17)
- Recompute ratio 5–18% (Yi-34B): quality loss at most 0.002 F1 / Rouge-L.
  - That gives 4.1–6.6x lower TTFT than full recompute and 3.4–6.1x lower than prefix caching
- Gains stay similar across chunk counts and chunk lengths.
- Larger batches: prefill dominates more, so CacheBlend helps more.
- Works with KV in CPU RAM or a slower disk; gap to full reuse shrinks on slow disks (loading dominates).

## Limitations
- Only transformer models; not Mamba or Griffin.
- Not tested with more models, datasets or quantization settings.
- Only vLLM; not newer engines (DistServe, StableGen).
- Not studied: sharing KV caches across compute nodes.

# LMCache (background reading, our pick)

## Why move KV caches out of the GPU
- Traditional: KV cache lives in GPU memory for one query only.
- Two new needs:
  - Cross-query caching: keep KV for a shared prefix for later queries
  - Prefill–decode (PD) disaggregation: prefill on some GPUs, decode on others; KV must move between them
- Usage data: stored KV cache grows far beyond GPU memory (Figure 3).
- Over 19% of users reuse stored tokens more than 1.5 times (Figure 4).

## What LMCache does
- Extracts KV caches from vLLM and SGLang; stores them in CPU memory, local disk, remote disk, Redis; moves them over Ethernet, RDMA, NVLink.
- Three contributions:
  - Fast data movement: batching, compute–I/O pipelining
  - A modular connector that survives fast engine changes (15–20 new open-weight models a week in 2025)
  - Control API: pin, lookup, cleanup, move, compress KV caches
- From the same group as CacheBlend; CacheBlend's code is in the LMCache repo.

## Performance tricks
- Chunks, not pages: vLLM pages are 16 tokens per layer (20 KB–63 KB); LMCache moves 256-token chunks by default.
  - Small transfers can't fill the link (Table 1: 64KB → 4GBps; 16MB → 49GBps)
- Layer-wise pipelining: load layer i+1's KV while layer i computes (separate CUDA streams).
- Delayed decode storing: buffer new tokens' KV and write a full chunk at once.
- Zero-copy moves between tiers.

## Lessons from deployment
- Remote storage can beat prefill: one user loading KV from their object store saw 22–32% lower TTFT than full prefill.
- Context truncation kills prefix hits: real traces showed hit ratio drop from roughly 85% to 45% when keeping only the latest tokens.
- Hit rates higher than expected: e.g. 50% at one company; reuse comes from chat histories, coding assistants, RAG.
- Reported: up to 15x throughput with vLLM on multi-round QA and document analysis.

# Cartridges (Eyuboglu et al. 2025)

## The problem
- Users ask many questions over one big corpus: codebases, legal texts, 10-K filings, medical records.
- In-context learning (ICL): put the whole corpus in the prompt. Flexible but costly.
- KV cache grows linearly with input length.
  - LLaMA 8B on one H100: peak throughput drops 77x from 1k to 120k tokens of context
- Prompt and KV-cache compression: quality drops fast beyond 2x compression (Figure 4).

## The idea: train the cache offline
- Cartridge: a small trained KV cache Z that stands in for the corpus C.
- Freeze the LLM; train only the key and value vectors (a simplified prefix-tuning).
- At question time: load the Cartridge, append the question, decode.
- Training cost is paid once and shared by every query on that corpus.

## What a Cartridge must do
- Generality: answer many query types (facts, math, summaries, creative) unknown at training time.
- Long-range structure: understand how distant parts of the corpus relate.
- Composition: two Cartridges concatenated should act like two documents in context.

## Parameterization
| ICL KV cache | Cartridge KV cache |
|---|---|
| (k[1], v[1]) ... (k[n_C], v[n_C]) for the corpus | (z_k[1], z_v[1]) ... (z_k[p], z_v[p]) trainable |
| then KV pairs for the query | then KV pairs for the query |

- Size: Z ∈ R^(L × p × d × 2): L layers, p virtual tokens, d dimension, keys and values.
- Memory = a KV cache for a p-token prompt. p is the knob.
- Served like a cached prefix: works with existing servers (unlike LoRA, which needs custom serving).

## Initialization
- Random init of prefix-tuning is unstable; earlier work used an MLP re-projection.
- Cartridges: initialize Z to the KV cache of the first p tokens of the corpus.
- LongHealth accuracy (Section 5.3):

| Initialization | Accuracy |
|---|---|
| Random vectors | 29.9% |
| KV of random tokens | 51.3% |
| KV of first p corpus tokens | 55.3% |

- Freezing the attention sink (first token) also helps stability.

## Naive training fails (Figure 3)
- Next-token prediction on the raw corpus:
  - Memorizes with near-perfect perplexity, 107x less memory than ICL
  - Fails to generalize to other query types (synthesis, reasoning, creative)
- Tested on GenConvo, built from FinanceBench (e.g. AMD's 10-K, almost 100k tokens).

## Self-study, step 1: synthetic conversations
```
c̃ = chunk(C)                      # 512–4096 tokens of the corpus
s = get_seed_prompt()
for i in 1..k:
  a_i ~ F(· | c̃ ⊕ s ⊕ a_1 ⊕ ... ⊕ b_(i-1))   # A asks, sees the seed
  b_i ~ F(· | c̃ ⊕ a_1 ⊕ ... ⊕ a_i)           # B answers, no seed
```
- A and B are the same model; both see the chunk in the system prompt.
- Main experiments use k = 1 (one question, one answer).
- Chunking lets it cover corpora longer than the context window.

## Seed prompts
- Five generic types: structuring, summarization, question, use cases, creative.
- Same seeds for every corpus; never mention the domain.
- Single seed example: "Please generate a single chat message to begin a conversation about the information in the corpus. Ask a question about the corpus or make a request."

| Dataset | 1 seed prompt | 5 seed types |
|---|---|---|
| MTOB (chrF) | 24.1 | 32.0 |
| LongHealth (accuracy) | 43.6 | 48.4 |
| QASPER | no significant gain | |

## Self-study, step 2: context distillation
- Teacher: the model with the chunk in context, F(· | c̃ ⊕ x).
- Student: the same model with the Cartridge, F_Z(· | x).
- Formula (Eq. 3): minimize Σ over (x, c̃) Σ over positions i of KL( F(·|c̃ ⊕ x[:i]) || F_Z(·|x[:i]) )
  - KL: how different two next-token distributions are
  - Sum over every token position of every synthetic conversation
- Result on MTOB: chrF 24.9 (next-token) → 33.5 (distillation), same data.
- LongHealth: +3.7 accuracy points at equal data (Appendix A).

## Datasets
| Dataset | Corpus | Metric |
|---|---|---|
| LongHealth | Patient medical records | Accuracy |
| QASPER | Scientific papers | Log perplexity |
| MTOB | Kalamang grammar book (translate Kalamang → English) | chrF (character n-gram score) |

- Corpora from 100k to 484k tokens; one Cartridge per dataset.

## Quality vs memory (Figure 4)
- Baselines: ICL, truncated prompt, GPT-4o summary, DuoAttention (KV compression).
- Cartridges beat ICL at some cache sizes on LongHealth and QASPER (Llama-3B).
- Memory savings at similar quality: up to 10x (LongHealth), up to 100x (QASPER).
- Compression baselines drop at only 2x compression.
- Average across benchmarks: 38.6x less memory, 26.4x higher peak throughput.

## More compute, better Cartridge (Figure 5)
- Sizes p ∈ {128, 512, 2048, 8192}; batch 64, max length 1024, one epoch (no data reused).
- Quality rises steadily with training steps for every size.
- Larger Cartridges reach higher quality.

## Beyond the context window (Section 5.2)
- MTOB: full textbook is 484k tokens; Llama-8B window is 128k (356k tokens too long).
- Chunked self-study builds a Cartridge from the full book anyway.
- Matches ICL on the hand-curated 60k-token version, with much less memory.
- Beats ICL on the first 130,000 tokens of the book by 11.0 chrF.
- Effective context: 128k → 484k tokens.

## Prefix-tuning vs LoRA (Figure 6, 8)
| | Prefix-tuning Cartridge | LoRA Cartridge |
|---|---|---|
| MTOB at ∼0.6 GB | +4.5 chrF over LoRA | baseline |
| MMLU as size grows | 54.7 → 54.3 (0.15 → 0.96 GB) | 54.7 → 45.3 (0.15 → 1.06 GB) |

- Prefix-tuning keeps the model's general skills; LoRA damages them as it grows.

## Composition (Figure 7)
- Train Cartridges on 10-Ks of AMD, Pepsi, AMEX, Boeing; sizes {512, 1024, 2048, 4096}.
- Concatenate two, no joint training; ask questions needing both (6 pairs per size).
- Beats one Cartridge alone and truncated ICL on multi-document questions.
- Example: "Who audited the Boeing and AMD statements?" → Ernst & Young LLP (AMD), Deloitte & Touche LLP (Boeing).

## Limitations
- Training is far costlier than a prefill: about 30 minutes on one 8×H100 node for an ICL-quality Llama-8B Cartridge.
- Not a drop-in replacement for ICL; a trade of compute for memory.
- Pays off when many queries hit the same corpus, and training can run on idle compute (e.g. at night).
- Room for faster training (better shared-prefix attention kernels).

# Our notebook

## Example: four contracts, small window
| The problem | The fix |
|---|---|
| Task: total monthly fee across msa_03, msa_07, msa_12, msa_18 | Search one contract at a time |
| Window: 2,500 characters | After each search, save a note like "msa_07 fee = 4500" |
| Four contracts in full: about 7,000 characters | Old results are evicted; the notes survive |

- msa_07, 2.1: "Customer shall pay Vendor $4,500 per month".
- Weak spot: if the agent skips a note, the fact is gone from view. The model decides what to remember.

## Eviction in code
```python
def add(self, unit):
    self.queue.append(unit)
    self.recall.extend(unit)
    while self.size() > self.budget and len(self.queue) > 2:
        self.queue.pop(1)
        self.evicted += 1
```
- Line 2: new step goes on the queue.
- Line 3: also into recall storage, which is never deleted.
- Line 4: while over budget, keep at least the task and the newest step.
- Line 5: drop the oldest step after the task (`queue[0]` is never evicted).
- Line 6: count it, so the agent can be told "older steps were evicted".

## Same contracts, four requests
| Request | Cache |
|---|---|
| 8 contracts + question A | Cold: nothing cached |
| Same 8 contracts + question B | Warm: prefix reused, much faster |
| "NOTE. " + 8 contracts + question A | Changed first word: slow again |
| 8 contracts + "(end of documents)" + question A | Changed end: most of the prefix reusable |

- Prefix caching: all or nothing from the first change. Ollama does it automatically within one model slot.
- Rule: stable text first (rules, playbook, contract), the question last. No timestamp at the top.

## Our "cartridge"
- Study the 6 contracts once; save compact notes; answer questions from the notes.
- Compare answers and size against putting all 6 contracts in the prompt.
- Ours is text notes; the real Cartridge is trained key/value vectors.

# How this applies to us

## Paging on the firm's machine
- A local model on a modest GPU has a small window. Paging lets it work across the whole contract archive.
- MemGPT's lesson: the model must be good at tool calls. Test the local model's function calling first.
- Keep recall storage: every message is logged, which is also an audit trail for the firm.

## Caching on the firm's machine
- Reusing the KV cache for the playbook and contract is often the cheapest speed-up, before buying more GPUs.
- Order prompts: playbook, then contract, then the question ("liability cap at most 12 months of fees?").
- LMCache's lesson: never trim the start of a long prompt; truncation dropped hit rates from about 85% to 45%.

## Trained memory on the firm's machine
- One big archive queried thousands of times is where a Cartridge pays off.
- Train overnight on idle GPUs, as the Cartridges paper suggests.
- Use prefix-tuning style memory, not LoRA, to keep the model's general skills (MMLU 54.3 vs 45.3).

## Common mistakes
- Timestamp or request ID at the top of the prompt → the prefix never matches. Put it last.
- Trusting the agent to save notes → log every message and test recall.
- Reusing chunk caches with no recompute → cross-attention lost; recompute ~15% (CacheBlend).
- Training a compact memory on raw text → use varied self-study conversations and distillation.
- Timing the first call after loading the model → warm up first; load time swamps everything.

## Check your understanding
**Q: In MemGPT, what are main context and external context?**
A: Main context is the prompt: system instructions, working context and the FIFO queue. External context is recall storage and archival storage, reached only through function calls.

**Q: In MemGPT, what survives when old messages are evicted?**
A: The working-context notes, a recursive summary, and the full messages in recall storage, which the agent can search.

**Q: Why does changing the first word of a long prompt make it slow again?**
A: Prefix caching only reuses an exact matching start. A change at the start breaks everything after it, so the whole prompt is prefilled again.

**Q: What does CacheBlend recompute, and why not nothing?**
A: A small share of tokens (15% per layer by default) with the highest KV deviation. Recomputing nothing ignores how chunks affect each other, and quality drops.

**Q: How does CacheBlend hide the cost of recomputing?**
A: It recomputes one layer while loading the next layer's KV cache from storage. If loading is slower, recompute adds no delay.

**Q: Why did Cartridges trained with next-token prediction fail?**
A: They memorized the raw text but could not answer other kinds of questions. Self-study conversations plus context distillation fixed this.

**Q: Why initialize a Cartridge from the first p tokens of the corpus?**
A: Random vectors trained poorly (29.9% on LongHealth). Real-token KV vectors worked much better (55.3% with the first p tokens).
