# Why RAG

## Why retrieval?
"Which office hour this week is least crowded?"

| LLMs alone | LLMs + retrieval |
|---|---|
| "Try the Wednesday afternoon session. Midweek hours are usually quietest." | Retrieved: "Queue log, last 3 weeks: Tue 4pm: 14 waiting avg; Thu 9am: 3." |
| A guess from general patterns | "Thursday 9am, about 3 students ahead of you." |

## Why retrieval? Our contract example
"What is the liability cap in msa_20?"

| LLM alone | LLM + retrieval |
|---|---|
| "Caps are usually 12 months of fees." (a guess) | Retrieved msa_20, 7.1: "...SHALL NOT EXCEED THE FEES PAID BY CUSTOMER IN THE THIRTY-SIX (36) MONTHS PRECEDING THE CLAIM." |
| No source to check | "36 months of fees. Source: msa_20#7." Over our 12-month rule: flag it. |

## Using retrieval to fix what LMs lack
- Don't ask the LM to memorize everything. Give it the right text just in time.
- Retrieval: the usual way to find that text.
- Dynamic: easy to add or update documents.
- Interpretable: the LM can point to the documents it used (citations), so a person can check it.

## Retrieval in open-domain QA (DrQA)
- Chen et al., 2017, "Reading Wikipedia to Answer Open-domain Questions" (DrQA).
- Open-domain QA: answer any question from a big collection, like all of Wikipedia.
- Question: "How many of Warsaw's inhabitants spoke Polish in 1933?"
- Document retriever: searches Wikipedia, returns the "Warsaw" article.
- Document reader: reads the article, outputs "833,500".

## Retriever-reader framework
- Input: a big document collection D = D1 … DN, and a question Q.
- Output: an answer string A.
- Retriever: f(D, Q) → P1 … PK. K is fixed in advance (e.g., 100).
- Reader: g(Q, {P1 … PK}) → A. A reading-comprehension problem.
- In DrQA the retriever is plain TF-IDF (word-count search), fixed, not trained.
- Reader: a neural reading model trained on SQuAD and similar QA data, or a zero-shot LLM (ChatGPT etc.).

## Retrieval-augmented generation (RAG)
- Lewis et al., 2021. See also REALM and DPR.
- Query encoder turns the question x into a vector q(x).
- MIPS (maximum inner product search) finds the closest passages z1 … z4 in a document index.
- Generator pθ reads the question plus each passage and merges ("marginalizes") over them.
- Trained end to end: gradients flow back through the query encoder q and the generator pθ.

## One RAG model, three tasks
| Task | Input x | Output y |
|---|---|---|
| Question answering | Define "middle ear" | The middle ear includes the tympanic cavity and the three ossicles. |
| Fact verification | Barack Obama was born in Hawaii. | supports |
| Jeopardy question generation | The Divine Comedy | This 14th century work is divided into 3 sections: "Inferno", "Purgatorio" & "Paradiso" |

# The RAG pipeline

## Deep dive: retriever + generator
- Retriever p(z|x): returns the top-K passages z for a query x.
- Generator p(y|x, z): writes the answer y one token at a time, given x and one passage z.
- Formula: `p(y|x) ≈ Σ over z in top-K of p(z|x) · p(y|x, z)`
  - p(z|x): how much the retriever likes passage z.
  - p(y|x, z): how likely the answer is, given that passage.
  - The sum weights each passage's answer by the retriever's score.

## RAG-Sequence vs RAG-Token
| RAG-Sequence | RAG-Token |
|---|---|
| Pick one passage, write the whole answer with it | Re-pick the passage at every token of the answer |
| One passage per answer | Different tokens can lean on different passages |

- Both use the same retriever, generator and top-K passages.

## Training: retriever and generator together
- Train both parts at once to minimize `Σ_j −log p(y_j | x_j)`.
  - x_j, y_j: a training question and its right answer.
  - "Negative marginal log-likelihood": p(y|x) already sums over the passages, so no label says which passage was right.
- The model learns which passages help by whether they make the right answer more likely.

## Retriever: DPR
- `p(z|x) ∝ exp(d(z)ᵀ q(x))`
  - d(z) = BERT_d(z): passage vector from a passage encoder.
  - q(x) = BERT_q(x): query vector from a query encoder.
  - Dot product: bigger means more relevant.
- top-k(p(·|x)): the k highest-scoring passages, found with MIPS (maximum inner product search).

## Generator: BART
- Generator p(y|x, z): writes the answer one token at a time from query x and passage z.
- Any encoder-decoder model can play this role.
- RAG uses BART. x and z are joined (concatenated) into one input.

## Different variants of RAG (Gao et al., 2024)
| Naive RAG | Advanced RAG | Modular RAG |
|---|---|---|
| Index documents → retrieve → prompt a frozen LLM → output | Adds pre-retrieval steps: query routing, rewriting, expansion | A set of modules: search, routing, predict, retrieve, rewrite, rerank, read, demonstrate, fusion, memory |

# Indexing: chunking, contextual retrieval

## What makes a good retriever? Embeddings
| Type | Examples | One vector covers |
|---|---|---|
| Static word | word2vec, GloVe | a word type |
| Contextual | BERT, RoBERTa | a token in context |
| Passage | Sentence-BERT, DPR, E5 | a chunk |
| Multimodal | CLIP | text or image, shared space |
| Graph | node2vec, GNN encoders | a node or relation |

- Retrieval needs a fixed-size vector per chunk and a similarity metric (cosine or inner product).

## Our embedding model
- `BAAI/bge-small-en-v1.5`: a small passage embedding model. Runs on the firm's machine.
- Vectors are normalized, so the dot product equals cosine similarity.
- Queries get a prefix the model expects: "Represent this sentence for searching relevant passages: ".

## Chunking: basic unit in retrieval
- Fixed-size chunking: cut by size (e.g., 100–500 tokens).
  - Too small: the vector has no context.
  - Too large: one vector averages many topics.
- Overlap: 10–20%, so no sentence is lost at a chunk boundary.
- Semantic chunking: cut at logical boundaries (sentences, sections).
- Context-enriched chunking: carry extra metadata or a summary with each chunk.
- AI-driven dynamic chunking: an LLM finds natural breakpoints.

## Chunking: same text, three splits
Text: "Grading. The project milestone is due Week 6, Thursday 11:59pm. Late days may not be applied to the milestone. The final report is due Week 10."

| Fixed-size (50 tokens) | Fixed-size + overlap | Structure (split on headings) |
|---|---|---|
| "… The project milestone is due Week 6, Thursday" | "… The project milestone is due Week 6, Thursday 11:59pm." | "Grading — Milestone: Week 6, Thu 11:59pm. Late days: not allowed on the milestone. Final report: Week 10." |
| "11:59pm. Late days may not be applied to the milestone …" | "… due Week 6, Thursday 11:59pm. Late days may not be applied …" | (one chunk) |

- Fixed-size cuts the deadline in two. Overlap repeats it. Structure keeps it whole.

## Contextual retrieval: the pipeline (Anthropic)
- Split each document into chunks 1 … X.
- For every chunk, run a prompt with the whole document and the chunk.
- The LLM (Claude) writes 50–100 tokens of context; it is prepended to the chunk.
- Index "context + chunk" two ways: embedding model → vector database; TF-IDF/BM25 → keyword index.
- Hybrid retrieval: embeddings catch meaning, TF-IDF/BM25 catches exact terms; results are merged.

## Contextual retrieval: the prompt
```
{{WHOLE_DOCUMENT}}
Here is the chunk we want to situate within the whole document
{{CHUNK_CONTENT}}
Please give a short succinct context to situate this chunk within the overall
document for the purposes of improving search retrieval of the chunk. Answer
only with the succinct context and nothing else.
```

## Late chunking (Günther et al., 2024)
| Naive chunking | Late chunking |
|---|---|
| Split the document first | Embed the whole document first, with a long-context encoder |
| Embed each chunk alone | Mean-pool (average) the token vectors inside each chunk's span |
| "i.i.d." vectors: each chunk blind to the rest | "Conditional" vectors: each chunk saw the whole document |

- Compared to contextual retrieval: no LLM call and no added tokens per chunk. The context lives in the vector.

## RAPTOR: tree-structured indexing (Sarthi et al., 2025)
- Problem: when the answer is spread across a document, no single chunk holds it.
- Build a tree bottom up: embed chunks → cluster them → summarize each cluster with an LLM → embed the summaries → repeat.
- Example tree: leaves 1–5 cluster into (3, 5), (1, 4, 5), (2, 3); their summaries are nodes 6, 7, 8; roots 9, 10.
- A node holds: index, child nodes, summary text, embedding (node 8 = summary of nodes 2 and 3).
- Retrieve across levels: a detail question matches a leaf; a theme question matches a higher node.

## RAPTOR vs DPR: the Cinderella example
- Q1: "Central theme of the story?" Q2: "How did she find a happy ending?"
- DPR picks only leaf chunks (bottom layer).
- RAPTOR picks summary nodes from the middle and top layers, plus some leaves.
- RAPTOR's context usually already contains DPR's leaves, directly or inside a summary.

## GraphRAG (Edge et al., 2024)
| Indexing time | Query time |
|---|---|
| Source documents → text chunks (extract, chunk) | Community summaries → community answers (query-focused summary) |
| Chunks → entities & relationships (LLM summary) | Community answers → one global answer (query-focused summary) |
| → knowledge graph → community detection → graph communities → community summaries | |

- Community: a tight cluster of linked entities in the graph (shown as colored clusters).
- Built for "global" questions about a whole corpus, not one passage.

## GraphRAG: more variants (Han et al., 2025)
- Same stages for RAG and GraphRAG: query processor → retriever → data source → organizer → generator.
- RAG side: text and image data (Wikipedia, MNIST, CIFAR-10).
- GraphRAG side: graph data. Nodes and edges (entities, papers, products, customers), knowledge triplets (California —state→ USA), molecules (benzene), social networks, road maps.

## Vector search
- The task: given a query vector, return the top-k of N chunk vectors.
- Exact search: scan them all, O(N·d) per query (N chunks, d dimensions).
- ANN (approximate nearest neighbor): trade a little recall for a lot of speed.
  - IVF (inverted file index): cluster the vectors; search only the clusters nearest the query.
  - PQ (product quantization): compress each vector into a short code.
  - HNSW: a multi-layer graph; walk greedily down from a coarse layer.
- Our notebook uses exact search (`self.vecs @ qv`, then sort). Fine for 20 contracts.

## HNSW: searching (Hierarchical Navigable Small World)
- Layers: all vectors at the bottom (layer 0), thinner samples above (layers 1, 2).
- Search: start at the top, hop greedily toward the query, drop a layer when stuck.
- Fast: about log N hops, high recall.
- Figure: entry point at layer 2 → hop → drop to layer 1 → hops → drop to layer 0 → nearest vector.

## HNSW: building the graph
- Insert one vector at a time.
- Pick its top layer at random: most nodes stay in layer 0, few reach the top.
- Link it at each layer to its M nearest neighbors.
- Plus a heuristic link across to another cluster, so the greedy walk can't get trapped in one cluster.

# Retrieval: BM25, DPR, ColBERT

## Different types of retrievers
| Type | Example | How it matches |
|---|---|---|
| Word overlap | BM25 | Shared words, weighted |
| Vector retrieval | DPR, sentence vectors | One vector per passage; dot product |
| Other neural | ColBERT | One vector per token; token-level match |

## BM25: the most widely used (even today)
`score(D, Q) = Σ over query terms qi of IDF(qi) · f(qi,D)·(k1+1) / ( f(qi,D) + k1·(1 − b + b·|D|/avgdl) )`
- IDF(qi): how rare the word is in the collection.
- f(qi, D): how often the word appears in document D.
- k1: how fast repeats stop adding score.
- b and |D|/avgdl: document length vs the average; long documents get scaled down.

## BM25: the IDF part
`IDF(qi) = ln( (N − n(qi) + 0.5) / (n(qi) + 0.5) )`
- N: number of documents in the collection.
- n(qi): number of documents that contain the word.
- Rare word (small n): big IDF. Common word: small IDF.
- The +0.5 terms keep it from blowing up at 0 or N.

## IDF comparison and term-frequency saturation
| Left chart: IDF vs document frequency (N = 10,000) | Right chart: TF part vs term frequency |
|---|---|
| Standard IDF falls but stays at or above 0 | Lines for k1 = 0.5, 1.2, 2.0, 5.0 |
| BM25 IDF hits 0 when a word is in 50% of documents | All score 1 at one occurrence, then flatten |
| Above 50%: BM25 IDF turns negative (shaded region) | Ceiling near k1+1: k1 = 1.2 levels off near 2; k1 = 5.0 keeps climbing toward 5 |

- In words: the tenth "liability" in a clause adds little over the second.

## DPR: dense passage retrieval (Karpukhin et al., 2020)
| Offline (once) | Online (per query) |
|---|---|
| Passages → passage encoder E_P(p) | Query q → query encoder E_Q(q) |
| → passage vectors → vector index | → query vector → dot product E_Q(q)ᵀ E_P(p) against the index |
| | → top-k passages |

## DPR: training
- Similarity: `s(q, p) = E_Q(q)ᵀ E_P(p)`; both vectors in R^d.
- Contrastive loss: `L_i = −log [ exp(s(qi, pi+)) / ( exp(s(qi, pi+)) + Σ_j exp(s(qi, pi,j−)) ) ]`
  - pi+: the right passage. pi,j−: n wrong passages.
  - Low loss when the right passage scores far above the wrong ones.
- Gradients update both the question encoder and the passage encoder.
- Negatives: in-batch (other questions' passages in the same batch) plus BM25 hard negatives (high BM25 score, wrong passage).

## Scoring a retriever: Hit@k and Failed@k
- `Hit@k = (1/|Q|) · Σ_q 1[ R_q ∩ Top_k(q) ≠ ∅ ]`
  - R_q: the relevant passages for query q. Top_k(q): the k returned.
  - 1 if any relevant passage is in the top k, else 0. Position in the top k does not matter.
- `Failed@k = (1/|Q|) · Σ_q 1[ R_q ∩ Top_k(q) = ∅ ] = 1 − Hit@k`
  - Share of queries with no relevant passage in the top k. Anthropic's chart above is Failed@20.

## Scoring a retriever: nDCG@k
- `DCG_q@k = Σ_{i=1..k} rel_{q,i} / log2(i + 1)`
  - rel_{q,i}: relevance of the passage at rank i.
  - log2(i + 1): lower ranks count less ("discounted by rank").
- `nDCG@k = (1/|Q|) · Σ_q DCG_q@k / IDCG_q@k`
  - IDCG: the DCG of the ideal ranking. Dividing by it puts every query on a 0–1 scale.

## Scoring a retriever: MRR@k and Recall@k
- `MRR@k = (1/|Q|) · Σ_q 1 / rank_q`
  - rank_q: rank of the first relevant passage. Counts as 0 if not in the top k.
- `Recall@k = (1/|Q|) · Σ_q |R_q ∩ Top_k(q)| / |R_q|`
  - Relevant passages found in the top k, out of all relevant passages for the query.
- Our notebook has one gold chunk per query, so its recall@3 equals Hit@3.

## The metrics on one query
Suppose we ask "msa_20 cap on damages", the gold chunk is `msa_20#7`, and search returns it at rank 2 of 3.

| Metric | Value | Why |
|---|---|---|
| Hit@3 | 1 | Gold is in the top 3 |
| Failed@3 | 0 | 1 − Hit@3 |
| MRR@3 | 0.5 | 1 / rank 2 |
| nDCG@3 | 0.63 | (1/log2 3) ÷ (1/log2 2) |
| Recall@3 | 1 | 1 of 1 gold chunks found |

## Hybrid search and reciprocal rank fusion
- The two fail differently: BM25 misses paraphrase; dense search misses rare literals (error codes, product IDs).
- Hybrid search: run both retrievers, then fuse the two ranked lists.
- RRF (reciprocal rank fusion): merge positions, not raw scores. No per-corpus tuning; works with any number of retrievers.
- `RRF(d) = Σ over retrievers r of 1 / (k + rank_r(d))`, with k = 60.
- Example: ranked 1st by BM25 and 3rd by embeddings → 1/61 + 1/63 ≈ 0.032.

## Two ways to search our contracts
| Keyword search (BM25) | Meaning search (embeddings) |
|---|---|
| Scores chunks by shared words | Turns text into vectors; similar meaning → nearby vectors |
| Finds "7.2(b)", "msa_15" | Finds "limitation of liability" when you typed "cap on damages" |
| Misses synonyms | Misses exact IDs and clause numbers |

## RRF in our notebook
```python
scores = {}
for ranking in (self.keyword(q, pool), self.semantic(q, pool)):
    for r, i in enumerate(ranking):
        scores[i] = scores.get(i, 0) + 1 / (rrf_k + r + 1)
return [self.chunks[i] for i in sorted(scores, key=scores.get, reverse=True)[:k]]
```
- Line 1: a score per chunk, starting empty.
- Line 2: take the top 50 (`pool`) from keyword search, then from meaning search.
- Line 3: walk each list; r is the position (0 = first).
- Line 4: add 1 / (60 + rank). r + 1 makes rank start at 1.
- Line 5: sort by total score; keep the top k.

## Cross-encoders and reranking (Humeau et al., 2020)
| Bi-encoder (retrieval) | Cross-encoder (reranking) |
|---|---|
| Query and passage encoded separately | Query and passage go through the model together |
| Score = dot product of two vectors | Full attention across both; one score out |
| Passage vectors precomputed; fast over a whole corpus | Nothing precomputed; only for a shortlist |

- Notebook solution 2: `cross-encoder/ms-marco-MiniLM-L-6-v2` reranks the top 20 and keeps 3.

## Late interaction: score tokens, not documents
- Keep one vector per token. Encode query and passage separately. Interact only at scoring time.
- Scoring is MaxSim: `S(q, d) = Σ over query tokens i of max over doc tokens j of q_i · d_j`
  - For each query token, find its best-matching passage token. Add those up.

| Design | Example | How query and document meet |
|---|---|---|
| Representation-based | DSSM, SNRM | One vector each; compare once |
| Query-document interaction | DRMM, KNRM, Conv-KNRM | Word-match matrix → CNN/MLP |
| All-to-all interaction | BERT | Every token attends to every token |
| Late interaction | ColBERT | Token vectors, MaxSim at the end |

## General architecture of ColBERT
- Khattab & Zaharia, SIGIR 2020.
- Query encoder f_Q: one vector per query token.
- Document encoder f_D: one vector per document token, computed offline (indexing).
- MaxSim for each query token, then sum → score.

# Agentic RAG: Self-RAG, Search-R1

## Agentic RAG: retrieval inside the loop
- Everything so far answers one question well.
- None of it decides whether to retrieve, what to ask, or when to stop.
- Retrieval should be an action the agent takes.
- Three decisions:
  - Retrieve, or answer directly?
  - What query to issue?
  - Is the result good enough?

## Self-RAG: self-reflective RAG (Asai et al., 2024)
- Learns to retrieve, critique and generate, for better quality, factuality and verifiability.
- Prompt: "How did US states get their names?"
- Step 1, retrieve on demand: the model writes "US states got their names from a variety of sources." then emits a Retrieve token.
- Step 2, generate in parallel: one candidate segment per retrieved passage (3 here).
- Step 3, critique and pick the best segment; retrieve again; repeat.

## Self-RAG: the critique step
| Passage | Relevance tag | Segment | Support tag |
|---|---|---|---|
| 1 | Relevant | "11 of 50 state names come from persons." | Supported |
| 2 | Irrelevant | "Texas is named after a Native American tribe." | – |
| 3 | Relevant | "California's name has its origins in a 16th-century novel Las Sergas de Esplandián." | Partially |

- Ranking: 1 > 3 > 2. Segment 1 is kept; the model retrieves again for the next sentence.

## CRAG: a critic grades the retrieval (Yan et al., 2024)
- Retrieval evaluator: judges whether the retrieved documents fit the question, with a confidence score.
- Example: "Who was the screenwriter for Death of a Batman?"

| Verdict | Action | Generator gets |
|---|---|---|
| Correct | Knowledge refinement: split docs into strips, filter, recompose | x + k_in |
| Incorrect | Knowledge search: rewrite query ("Death of a Batman; screenwriter; Wikipedia"), web search, select | x + k_ex |
| Ambiguous | Both | x + k_in + k_ex |

## Search-R1: learn the search policy with RL (Jin et al., 2025)
Question: "Who is older, Jed Hoyer or John William Henry II?"

| Step | Model output |
|---|---|
| think | Find both ages. |
| search | "Jed Hoyer or John William Henry II" → a Jed Hoyer bio, no birth date |
| search | "John William Henry II" → born September 13, 1949 |
| search | "Jed Hoyer birth year" |
| think | "Jed Hoyer was born on December 7, 1973." |
| answer | John William Henry II (correct) |

- Many search turns inside one reasoning trace.

## Search-R1: how it is trained
- Prompt: reason inside `<think>`; call search with `<search> query </search>`; results come back in `<information>`; give the answer in `<answer>`.
- "You can search as many times as you want."
- RL (reinforcement learning): reward the final answer; the model learns when and what to search.
- PPO with a search engine: policy LLM + search engine roll out; value LLM, reward model, reference LLM → advantage.
- GRPO with a search engine: G rollouts per question; rewards compared within the group; KL keeps it near the reference LLM.
- Trained: policy LLM (and value LLM). Frozen: reward model, reference LLM.

- Train reward climbs from about 0.1 to over 0.4 in about 200 steps.

- In words: RL teaches the model to search more, and that pays off.

# Failure modes

## Issues with RAG
| Retrieval-side | Reader-side | Loop-side |
|---|---|---|
| Recall ceiling: missing evidence limits the agent | Lost in the middle: position bias | Compounding error: early mistakes affect later decisions |
| Stale index: embeddings not updated | Distraction: similar but irrelevant content | No stopping rule: no clear condition for finishing |
| Permission leak: uses content it may not access | Evidence conflict: sources or knowledge disagree | Prompt injection: retrieved text steers the agent |

## The same failures in contract review
| Failure | Example | Fix |
|---|---|---|
| Recall ceiling | `msa_20#7` not in the top k; the model can't see the cap | Measure recall@k first |
| Stale index | An amended contract was never re-indexed | Re-index on every change |
| Permission leak | Another client's contract comes back | Filter by client or matter during search |
| Distraction | msa_20 3.1 also says "thirty-six (36) months" (the term, not the cap) | Check the cited quote is in the cited clause |
| Prompt injection | A contract contains "ignore previous instructions" | Treat retrieved text as data |

# Wrap up RAG (Lecture 4)

## Problem: how many documents can we use?
- Why not fetch lots of documents and pass them all to the LM?
- Test prompt: "Write a high-quality answer for the given question using only the provided search results (some of which might be irrelevant)."
- Three documents; only Document [2] (List of Nobel laureates in Physics) has the answer.
- Question: "who got the first nobel prize in physics". Desired answer: Wilhelm Conrad Röntgen.

## LMs can't pay attention to the entire context (Liu et al., 2023)
- Three charts: 10, 20 and 30 retrieved documents (~2K, ~4K, ~6K tokens).
- X axis: position of the document with the answer. Y axis: accuracy.
- U-shape: best when the answer is first, good when last, worst in the middle.
- Best closed-book (no documents): GPT-3.5-Turbo, ~56%.
- Best oracle (only the relevant document): GPT-3.5-Turbo, ~88.5%.
- Models: claude-1.3, claude-1.3-100k, gpt-3.5-turbo-0613, gpt-3.5-turbo-16k-0613, mpt-30b-instruct, longchat-13b-16k.

## In practice: LMs can't use many documents
- Retriever (Contriever) recall rises slowly with more documents: about 68% at 5 to about 89% at 50.
- RAG accuracy (the other lines) stays around 50–60% and saturates after 10–20 documents.
- More documents → retriever finds more, but the reader can't use it.

## LLM citations can be hallucinated
- Unique benefit of RAG: citing the source.
- But the citations are themselves written by the LLM.
- Example: Bing Chat's Toronto itinerary with numbered citations to cntower.ca, travel.usnews.com, bing.com, rom.on.ca, tripadvisor.com.
- So citations can be made up too. How often?

## How often? (Liu et al., 2023)
| Engine | Perceived utility (1–5) | Fluency (1–5) | Citation precision | Citation recall |
|---|---|---|---|---|
| Bing Chat | 4.34 | 4.40 | 89.5% | 58.7% |
| NeevaAI | 4.48 | 4.43 | 72.0% | 67.6% |
| perplexity.ai | 4.56 | 4.51 | 72.7% | 68.7% |
| YouChat | 4.62 | 4.59 | 63.6% | 11.1% |
| Average | 4.50 | 4.48 | 74.5% | 51.5% |

- Answers look useful and read well. But precision and recall of citations are both low.
- Citation precision: share of citations that support their sentence. Citation recall: share of sentences fully supported.

## Hallucinated references in the wild
- GPTZero analyzed 4,841 accepted papers and found at least 100 with confirmed hallucinated citations (headline partly hidden on the slide).
- ICLR, "Taking Actions on Hallucinated References": many submissions cited papers that didn't exist or had badly wrong details.
- ICLR's checker matched references against bibliographic databases and web search. It had many false alarms, so humans reviewed each flagged paper (at least three people).
- Confirmed cases were desk-rejected, with an appeal channel.

## Needle in a haystack

# How this applies to us

## Our pipeline, end to end
```
question → hybrid search (BM25 + bge, RRF) → top 4 chunks → local LLM answers with id + quote → code checks the quote
```
- Everything runs on the firm's machine: BM25, the bge embedding model, and the LLM through Ollama.
- No contract text leaves the building.

## Do you even need RAG?
- Under about 200K tokens of documents: put everything in the prompt. Skip RAG.
- Above that: build the pipeline.
- Small local models do worse with long prompts, so RAG helps them sooner.
- Lost in the middle: send a few well-ranked chunks, not everything.

## Measure retrieval on its own
- recall@3 on 30 test questions: 10 contracts × 3 questions ("cap on damages", "which state's law applies", "how do we stop it renewing").
- The questions use different words from the contract, and name the contract by ID.
- Compare keyword vs meaning vs hybrid before touching the LLM.
- If the final answer is wrong, you then know whether search or reading failed.

## Checking citations in code
```python
hits = index.search(question, k=k)
ctx = "\n\n".join(f"[{c['id']}] {c['text']}" for c in hits)
a = structured([... "Answer only from the sources. Give the source id and an exact quote." ...], Answer)
src = next((c for c in hits if c["id"] == cid), None)
a_ok = src is not None and quote_is_in_doc(a.quote, src["text"])
```
- Line 1: hybrid search, keep the top k chunks.
- Line 2: join them, each tagged with its id, e.g. `[msa_20#7]`.
- Line 3: ask for an answer, a source id and an exact quote.
- Lines 4–5: find that chunk; check the quote is really in it. This catches hallucinated citations.

## Common mistakes
- Meaning search alone → misses clause numbers. Add keyword search.
- Judging only the final answer → measure recall@k separately.
- Stuffing 30 chunks into the prompt → the model ignores the middle. Send a few, best first.
- Trusting the model's citation → check the quote in code.
- Treating retrieved text as instructions → it is data.
- Filtering access after search → filter by client or matter during search.

## Check your understanding
**Q: A lawyer asks "what does 7.2(b) say?" and meaning search returns the wrong clause. Why?**
A: Embeddings capture meaning, not exact strings like "7.2(b)". Keyword search (BM25) finds it, which is why we use both.

**Q: Why add a one-line label to each chunk?**
A: The clause alone doesn't say which contract or section it is from. The label carries that, so both searches can match it.

**Q: What is the difference between RAG-Sequence and RAG-Token?**
A: RAG-Sequence writes the whole answer from one passage. RAG-Token can switch passages at every token.

**Q: Why fetch a wide pool and then rerank with a cross-encoder?**
A: Fast search is noisy, so a wide pool makes sure the right chunk is in it. The cross-encoder is too slow for the whole corpus but accurate on a shortlist.

**Q: How does late chunking differ from contextual retrieval?**
A: Late chunking embeds the whole document first and averages token vectors per chunk, so context lives in the vector. Contextual retrieval adds LLM-written text to each chunk.

**Q: Why not just send 50 retrieved contracts to the model?**
A: Models use the start and end of the context best and miss the middle. RAG accuracy stops improving after 10–20 documents.

**Q: What three decisions make RAG "agentic"?**
A: Whether to retrieve at all, what query to issue, and whether the result is good enough to stop.
