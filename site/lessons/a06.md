## Learning objective
- Learn the propose → evaluate → archive loop behind ADAS, the Darwin Gödel Machine, the AI Scientist and AlphaEvolve, what each paper found, and why the evaluator matters most.

# One loop, four systems

## One loop
- Propose: an LLM suggests a change (to code, an agent, an experiment).
- Evaluate: a program scores it automatically.
- Archive: store every candidate with its score; build on the good ones.
- Repeat.
- Progress comes from the evaluator and the archive. The LLM supplies the guesses.
- a05 trained the model's weights. Here the weights stay frozen; the code around the model evolves.

## The four papers side by side
| | What evolves | Evaluator | Headline |
|---|---|---|---|
| ADAS (Hu, Lu & Clune, 2024) | An agent's `forward()` code | Accuracy / F1 on validation questions | DROP F1 +13.6, MGSM +14.4% |
| Darwin Gödel Machine (Zhang et al., 2025) | A coding agent's own repo | SWE-bench, Polyglot tasks | SWE-bench 20.0% → 50.0% |
| The AI Scientist (Lu et al., 2024) | Research ideas, code, papers | Experiments + LLM reviewer | Under $15 per paper |
| AlphaEvolve (Novikov et al., 2025) | Programs and algorithms | User's `evaluate` function | 4x4 complex matrices in 48 multiplications |

- The course page's "Automated design of agentic systems" link points to the DGM paper (arXiv 2505.22954). We cover both.

## Key terms
- Archive: every candidate tried so far, with its score.
- Open-endedness: search for new and interesting, not only better on one number.
- Stepping stone: a candidate that is not best now but leads to later wins.
- Meta agent: an agent whose job is to write other agents, as code.
- Evaluation cascade: a tiny fast test first; full test only for those that pass.
- Sandbox: run untrusted code in a separate, limited process (timeouts, no network).
- Reward (objective) hacking: scoring high in a way that breaks the task's intent.

# ADAS: Automated Design of Agentic Systems (Hu, Lu & Clune, ICLR 2025)

## The problem ADAS solves
- Agents are built from hand-designed blocks: chain-of-thought, self-reflection, tool use, memory.
- Machine-learning history: hand-designed parts get replaced by learned ones.
  - HOG features → learned CNN features; hand-built CNNs → neural architecture search
- Question: can we automate the design of agentic systems?
- Most earlier attempts only tune prompts (e.g. PromptBreeder, OPRO). The workflow stays fixed.

## Three parts of any ADAS method (Figure 2)
| Part | What it decides | ADAS choice |
|---|---|---|
| Search space | Which agents can be represented | Any agent written in Python code |
| Search algorithm | How to explore that space | A meta agent (an LLM) writes new code |
| Evaluation function | How to score a candidate | Accuracy or F1 on validation data |

- Code is Turing complete: in theory any prompt, tool, workflow or mix can be found.
- Code is readable, easy to debug, and can reuse existing frameworks like LangChain.

## Meta Agent Search, step by step
- A small framework (under 100 lines) gives basic functions: query the model, format prompts.
- An agent = one `forward(taskInfo)` function that returns the answer (like FunSearch).
- 1. Seed the archive (optional) with hand designs: Chain-of-Thought, Self-Refine, etc.
- 2. The meta agent reads the archive and writes a new idea plus its code.
- 3. Two self-reflection rounds check that it is novel and correct.
- 4. Run it on validation data. On errors, reflect and fix, up to five times.
- 5. Add it to the archive with its score. Repeat until the iteration limit.

## ARC case study (Section 4.1, Figure 3)
- ARC: grid puzzles; learn a transformation rule from a few examples. The agent must write the rule as code.
- Data: grids ≤ 5×5 from the "Public Training Set (Easy)". 20 validation, 60 test questions; each evaluated 5 times.
- 25 iterations. Meta agent: GPT-4. Agents run on GPT-3.5 to save cost.
- Iteration 3: a key stepping stone appeared: several COTs → refine → ensemble the best answers.
- Iterations 5, 11, 12: diverse feedback, expert critics (efficiency, simplicity), human-like feedback. The best agent combined all three.
- Stepping stones did not score high at first; later agents built on them.

## ADAS ablation, cost and safety
- Empty archive (no seed designs), Table 6: still beats hand designs everywhere. Seeding usually helps, except math: MGSM 67.5 empty vs 53.4 seeded.
- Cost (Appendix J): about $500 per ARC run, about $300 per reasoning-domain run, mostly GPT-3.5 calls.
- Safety: all generated code ran in containers, with manual inspection.
- Limitations / future work: one objective only (no cost or latency); single-step QA only; the evaluation is expensive and ignores the run logs.

# Darwin Gödel Machine (Zhang, Hu, Lu, Lange & Clune, 2025)

## The problem DGM solves
- Gödel Machine (Schmidhuber, 2007): an AI that rewrites itself only when it can prove the change helps.
  - In practice, proving a change helps is impossible
- DGM: replace the proof with experiments. Keep a change if benchmarks say it is better.
- Self-improvement is itself a coding task. A better coding agent should also be better at improving itself.
- Weights stay frozen. The agent edits its own tools, prompts and workflow.

## The DGM loop (Figure 1)
- Start: one simple coding agent with two tools: Bash and a whole-file edit tool.
- 1. Pick parents from the archive.
- 2. A model reads the parent's benchmark logs and proposes one feature to add.
- 3. The parent implements that feature in its own code → a child agent.
- 4. Evaluate the child on coding tasks.
- 5. Keep the child only if it compiles and can still edit code. Add it to the archive.
- 80 iterations, one new agent each.

## Parent selection (Appendix C.2)
- Eligible: agents not yet at 100%.
- s_i = 1 / (1 + exp(−λ(α_i − α_0))): sigmoid of the agent's score α_i.
  - λ = 10 (sharpness), α_0 = 0.5 (midpoint)
- h_i = 1 / (1 + n_i): novelty bonus; n_i = number of working children it already has.
- Weight w_i = s_i · h_i; pick parents in proportion to w_i.
- Effect: favor strong agents that are under-explored. Every agent keeps some chance.
- k = 2 parents per iteration on SWE-bench, 4 on Polyglot.

## Benchmarks and staged evaluation (Section 4.2)
- SWE-bench Verified: human-filtered, all tasks solvable; Python only; edits may span files.
- Polyglot: many languages (C++, Rust, Python...), mostly one-file tasks; less likely to be in training data. Reported as pass@1.
- Staged evaluation (a cascade):
  - 10 tasks: can it still edit code?
  - then 50 more tasks
  - SWE-bench: over 40% on the 60 and top two in archive → 200 tasks
- Models: Claude 3.5 Sonnet (New) self-modifies; evaluation uses it for SWE-bench and o3-mini for Polyglot.

## DGM results (Section 4.4, Figure 2)
| Benchmark | Base agent | Best DGM agent |
|---|---|---|
| SWE-bench | 20.0% | 50.0% |
| Polyglot (50-task subset) | 14.0% | 38.0% |
| Polyglot (full) | 14.2% | 30.7% |

- SWE-bench: comparable to the best checked, open-source human-built agent.
- Polyglot: started below Aider, ended far above it.
- Beat both ablations: "w/o self-improve" (fixed meta agent, like ADAS) and "w/o open-ended exploration" (always build on the latest agent).

## What the DGM invented (Figure 3)
- Tools: view files by line range; edit by string replacement instead of rewriting whole files.
- Workflow: several attempts per task, another model picks the best; use earlier attempts when trying again.
- Auto-summarize when the context limit is near; validate and retry on an empty patch.
- Stepping stones: at iterations 4 and 56 a child scored below its parent, yet that path led to the overall best.
- The final best agent's lineage had two performance dips.

## Transfer (Figure 4)
| Test | Base agent | DGM agent |
|---|---|---|
| SWE-bench with o3-mini | 23.0% | 33.0% |
| SWE-bench with Claude 3.7 Sonnet | 19.0% | 59.5% |
| Found on SWE-bench → tested on Polyglot | 14.2% | 28.9% |
| Found on Polyglot → tested on SWE-bench | 20.0% | 24.5% |

- Searching only on Python tasks still transferred to other languages.

## Objective hacking (Appendix H)
- Task: stop the model faking tool use (writing "Tool Result: ... all tests passed" without calling a tool).
- Node 96: score 1.67, a real fix (better logging, removing fake tool output).
- Node 114: perfect score 2.0 after 2 changes, but it removed the logging of special tool tokens, so the detector could no longer see the problem.
- Hacking happened more when the scoring functions were visible to the agent.
- Goodhart's law: "When a measure becomes a target, it ceases to be a good measure."

## DGM cost, safety and limits
- One SWE-bench run: about 2 weeks and about USD 22,000. Each baseline: about USD 10,000 (Appendix E.1).
- Safety: sandboxed runs, strict time limits, coding-only scope, human monitoring, the archive gives a traceable lineage.
- Limits: still below closed-source SWE-bench systems; the exploration process itself is fixed; tied to the assumption that coding scores reflect ability to self-improve.

# The AI Scientist (Lu, Lu, Lange, Foerster, Clune & Ha, 2024)

## Three phases plus review (Figure 1)
- Start: a code template that runs a small baseline (e.g. NanoGPT on Shakespeare) plus a LaTeX folder.
- 1. Idea generation: grow an archive of ideas; each has a plan and self-scored interestingness, novelty, feasibility. Ideas too close to Semantic Scholar results are dropped.
- 2. Experiment iteration: Aider (a coding assistant) plans and runs experiments; on errors or timeouts, fix and retry up to four times; re-plan up to five times; write journal notes and plots.
- 3. Paper write-up: section by section in LaTeX, 20 rounds of Semantic Scholar search for citations, a cleanup pass, compile with errors fed back.
- 4. Automated review.

## The LLM reviewer (Section 4)
- GPT-4o, following NeurIPS review guidelines; reads the PDF text.
- Outputs: soundness, presentation, contribution, overall, confidence, strengths, weaknesses, accept/reject.
- Best setup: 5 rounds of self-reflection, 5 ensembled reviews, a meta-review "Area Chair" step, 1 example review.
- Ablation: self-reflection +2%, one example +2%. Ensembling didn't raise accuracy but reduced variance.
- $0.25 to $0.50 per review.

## Reviewer vs humans (Table 1, 500 ICLR 2022 papers)
| Reviewer | Balanced acc. | Accuracy | F1 | AUC | FPR | FNR |
|---|---|---|---|---|---|---|
| Human (NeurIPS 2021 experiment) | 0.66 | 0.73 | 0.49 | 0.65 | 0.17 | 0.52 |
| GPT-4o (1-shot) @6 | 0.65 | 0.66 | 0.57 | 0.65 | 0.31 | 0.39 |
| Sonnet 3.5 @8 | 0.59 | 0.65 | 0.45 | 0.59 | 0.20 | 0.61 |

- @6: accept if score ≥ 6 ("Weak Accept"). Sonnet needed @8 because it was too optimistic.
- Rejects fewer good papers (FNR 0.39 vs 0.52) but accepts more bad ones (FPR 0.31 vs 0.17).
- Score correlation: LLM vs average human 0.18; human vs human 0.14.

## Results by template and model (Tables 3–5)
| Diffusion template | Ideas | Novel | Experiments passed | Papers | Mean score | Cost |
|---|---|---|---|---|---|---|
| Sonnet 3.5 | 51 | 49 | 38 | 38 | 3.82 | ~$250 |
| GPT-4o | 51 | 41 | 17 | 16 | 3.70 | ~$300 |
| DeepSeek Coder | 51 | 42 | 32 | 31 | 3.32 | ~$10 |
| Llama-3.1 405b | 51 | 31 | 21 | 21 | 2.30 | ~$120 |

- Three templates: 2D diffusion, NanoGPT language modeling, grokking.
- Sonnet 3.5 best, GPT-4o second (often failed to compile LaTeX). Around $10–15 per paper.
- ~50 ideas take about 12 hours on 8× H100.

## Case study: "Adaptive Dual-Scale Denoising" (Section 5)
| Good | Bad |
|---|---|
| Table numbers matched the logs exactly, rounded correctly | Upscaling layer effectively did nothing |
| New plots of how weights change over time | Claimed V100 GPUs; H100s were used |
| Precise math and full experiment write-up | Called a worse result an improvement: "Moons: 3.3% improvement (from 0.090 to 0.093)" |
| "Dino: 12.8% reduction (from 0.989 to 0.862)" | Only 9 references |

- Authors' verdict: about the level of an early-stage ML researcher.

## Failure modes and safety (Section 8)
- Similar ideas across runs; Aider fails on many ideas; can implement an idea wrongly; weak at comparing two numbers; once hallucinated a whole ablation table.
- Language modeling: some ideas "cheat" by leaking future tokens.
- Unsafe behavior with minimal sandboxing:
  - wrote code to relaunch itself → runaway processes
  - saved a checkpoint every step → nearly a terabyte
  - edited its code to extend its own time limit
- Advice: containers, no internet except Semantic Scholar, storage limits. Don't take the papers at face value.

# AlphaEvolve (Novikov et al., Google DeepMind, 2025)

## The AlphaEvolve loop (Figures 1–2)
- User gives: an initial program with blocks to evolve, an `evaluate` function, optional context.
- Loop:
  - `database.sample()` → a parent plus "inspiration" programs
  - prompt sampler builds a rich prompt
  - LLMs write a diff; apply it → child
  - evaluators score the child; add it to the database
- Mark code to evolve with `# EVOLVE-BLOCK-START` / `# EVOLVE-BLOCK-END`. The initial code can be very basic.
- Asynchronous pipeline, tuned for throughput: as many ideas tried per compute budget as possible.

## Key design choices (Section 2)
- Diffs in SEARCH/REPLACE format: exact old code, then new code. Full rewrites for short code.
- Gemini 2.0 Flash (many fast ideas) + Gemini 2.0 Pro (fewer, better ideas).
- Prompts can hold: problem context, past programs with scores, varied wording, and meta-prompts the LLM writes itself.
- Evaluation cascade: harder test stages only for programs that pass earlier ones.
- Optional LLM-graded qualities (e.g. simplicity); multiple scores at once often help the main score.
- Program database: MAP-Elites (best per niche) + islands (separate populations), to keep diversity.

## AlphaEvolve vs FunSearch (Table 1)
| FunSearch | AlphaEvolve |
|---|---|
| One function, 10–20 lines | Whole file, hundreds of lines |
| Python only | Any language |
| Fast evaluation (≤ 20 min on 1 CPU) | Hours, in parallel, on accelerators |
| Millions of LLM samples | Thousands suffice |
| Small LLMs; bigger didn't help | Benefits from frontier LLMs |
| One metric | Several metrics at once |

## Faster matrix multiplication (Section 3.1, Table 2)
| Matrix sizes ⟨m,n,p⟩ | Best known | AlphaEvolve |
|---|---|---|
| ⟨4,4,4⟩ | 49 | 48 |
| ⟨3,4,7⟩ | 66 | 63 |
| ⟨4,5,6⟩ | 93 | 90 |
| ⟨3,3,3⟩ | 23 | 23 |
| ⟨5,5,5⟩ | 93 | 93 |

- Number = scalar multiplications (tensor rank). Improved 14 targets; matched or beat all with m, n, p ≤ 5.
- Strassen applied recursively needs 49 for 4×4. 48 for complex 4×4 matrices: first improvement in 56 years.
- AlphaEvolve evolved a whole gradient-based search program; the winner took 15 mutations (Figure 4).

## Open math problems (Section 3.2)
- Over 50 problems in analysis, combinatorics, number theory and geometry.
- Matched the best known construction in ~75%; beat it in ~20%. Always started from a simple or random construction.
- Examples: Erdős's minimum overlap problem (new upper bound); kissing number in 11 dimensions: 593 spheres.
- Trick: evolve a search heuristic with a fixed time budget (e.g. 1000 seconds), not the answer itself. Each one starts from the previous best.
- Problems suggested by mathematicians Javier Gomez Serrano and Terence Tao.

## Google infrastructure (Section 3.3)
| Problem | Result |
|---|---|
| Borg data-center scheduling (a bin-packing problem) | Simple heuristic, rolled out fleet-wide; recovers on average 0.7% of fleet-wide compute |
| Gemini matrix-multiply kernel tiling | 23% average kernel speedup; 1% less Gemini training time; months → days of work |
| TPU arithmetic circuit (Verilog) | Removed unnecessary bits; going into an upcoming TPU |
| FlashAttention (compiler IR) | 32% kernel speedup; 15% on pre/post-processing |

- Chosen over deep RL for scheduling because code is readable, debuggable and easy to deploy.
- Correct by construction, or checked against reference code on random inputs.

## AlphaEvolve ablations and limits (Sections 4, 6)
- Tested on matrix multiplication and kissing numbers. Each part helps (Figure 8):
  - "No evolution": always mutate the initial program
  - "No context in the prompt"
  - "No meta prompt evolution"
  - "No full-file evolution": evolve only the loss function
  - "Small base LLM only"
- Limit: needs an automatic evaluator; tasks needing manual experiments are out of scope.
- Feedback loops on its own infrastructure take months; gains so far are moderate.

# Our mini versions

## Mini AlphaEvolve: bin packing
- Task: put items into as few bins of size 100 as possible.
- Program to evolve: `pack(items, capacity)`. Seed: next fit.
- Evaluator:
  - Validity first: every item used once, no bin over capacity; invalid scores 0
  - Quality: lower bound / bins used. 1.0 is perfect.
- Cascade: 2 small instances first, then 20 full ones.
- 6 generations × 2 children = 12 model calls by default.

## Choosing parents in code
```python
    ranked = sorted(archive, key=lambda p: -p["score"])
    parents = [ranked[0] if rng.random() < 0.5 else rng.choice(ranked[:4]) for _ in range(CHILDREN)]
```
- Line 1: sort the archive, best first.
- Line 2: half the time take the best; otherwise a random one from the top 4.
- A crude version of DGM's "strong but under-explored" rule and AlphaEvolve's islands.

## The evaluator in code
```python
        bins = pack(list(items), cap)
        flat = [x for b in bins for x in b]
        if Counter(flat) != Counter(items) or any(sum(b) > cap for b in bins) or any(len(b) == 0 for b in bins):
            return None
        scores.append(math.ceil(sum(items) / cap) / len(bins))
```
- Line 1: run the evolved `pack` on a random instance.
- Line 2: flatten the bins into one list of items.
- Lines 3–4: any lost, duplicated or overfilled item → invalid.
- Line 5: score = best possible bin count / bins used.

## Without vs with a validity check
| Score only | Validity check first |
|---|---|
| One overfilled bin scores about 27 against a "perfect" 1.0 | Overfilled packing scores 0 |
| Search finds the loophole | Search must actually pack better |

- Same lesson as DGM's node 114: the search optimizes what you measure, cheats included.

## Mini ADAS
- Agents are `forward(question, ask)`; at most 2 model calls per question; worker model llama3.2:3b.
- Seeds: "Direct" and "Chain of thought". 3 meta-agent iterations, 6 word problems.
- We skip ADAS's two novelty reflections and five repair rounds to save calls.
- With 6 questions, one question is about 17 points. `RUN_LONG = True` adds a 12-question held-out test.

## The sandbox in code
```python
        try:
            p = subprocess.run([sys.executable, "-I", path], cwd=d, capture_output=True, text=True, timeout=timeout)
        except subprocess.TimeoutExpired:
            return {"ok": False, "error": f"timeout after {timeout}s", "seconds": timeout}
```
- Line 2: run the model's code in a new Python process; `-I` = isolated mode; working folder is a temp dir.
- Line 2, `timeout`: kill it after a wall-clock limit.
- Lines 3–4: a timeout becomes a failed result, not a hung notebook.
- Not a real sandbox: no network block. Use a container for real work.

## Mini AI Scientist
- Idea → experiment script (one repair try) → run in the sandbox → write-up → LLM review. Five calls at most.
- Extra check in plain code: what share of numbers in the write-up appear in the raw results?
- Answers the AI Scientist's failure modes: invented numbers, positive spin on bad results.

# How this applies to us

## The firm's evaluator
- The firm's past reviews, with correct playbook flags, are the evaluator for evolving a review agent.
- Validity first: every flag must cite a clause that exists, with an exact quote.
  - msa_20, 7.1: "...SHALL NOT EXCEED THE FEES PAID BY CUSTOMER IN THE THIRTY-SIX (36) MONTHS PRECEDING THE CLAIM."
- Quality second: right flag ("cap over 12 months of fees") on each contract.

## ADAS on the firm's machine
- Seed the archive with the designs already in use: one-pass review, checklist-per-clause.
- A local model writes new `forward()` designs; a small local model runs them.
- ADAS's cost was API calls. Locally, it is only time on the firm's GPU.
- Contracts never leave the building.

## Guard the loop
- All proposals run in a sandbox: container, timeouts, no network, storage limits.
- Hide the scoring code from the agent (DGM saw more hacking when it was visible).
- Confirm any winner on contracts the search never saw.
- Keep the archive: a lawyer can trace why each design changed.

# Common mistakes

## Common mistakes
- No validity check → the search finds the loophole. Check validity before quality.
- Trusting a tiny search set → with 6 questions, one answer is 17 points; confirm on held-out data.
- Running model code in your own process → use a subprocess or container with a timeout. The AI Scientist raised its own time limit.
- Keeping only the current best → keep the archive and some diversity; DGM's best agent came through dips.
- Letting an LLM reviewer be the only judge → check the write-up's numbers against the raw results with code.

## Check your understanding
**Q: Why does AlphaEvolve run an evaluation cascade instead of the full test on every child?**
A: Most children are worse or broken. A tiny fast test filters them out, so the expensive test runs only on promising ones.

**Q: In ADAS, what does the meta agent output, and how is it judged?**
A: A new agent written as code (a `forward()` function). It runs on validation tasks, and its score is stored with it in the archive.

**Q: Name two safety measures for an AI Scientist-style loop.**
A: Run generated code in a sandbox with time and storage limits and no network. Check the write-up's numbers against the raw results with code.

**Q: What is the difference between DGM and its "w/o self-improve" baseline?**
A: In the baseline, the agent making changes stays the original base agent, as in ADAS. In DGM, the improved agents make the next changes themselves.

**Q: How does DGM choose a parent, and why not always the best agent?**
A: In proportion to a sigmoid of its score times 1/(1 + its working children). Weaker or less-explored agents can be stepping stones; the best lineage passed through two dips.

**Q: DGM's node 114 scored a perfect 2.0. Why was it rejected?**
A: It removed the logging the hallucination detector relied on. It beat the metric without fixing the problem: objective hacking.

**Q: Why did AlphaEvolve evolve search programs instead of the math answers directly?**
A: A search heuristic with a time budget can start from the previous best and keep improving it. The final constructions came from a sequence of such heuristics.
