## The big idea

A model guessing alone repeats its own mistakes. It gets better when something outside it answers back. That outside signal is called feedback.

Think of a new associate. Left alone, they guess. Give them the case file to look things up, a checklist of the firm's standards, and a partner who returns marked-up drafts. Now they improve fast.

This module covers three kinds of feedback. Test results for code the model writes. Tool results while it works through a question. And a short written rulebook it uses to critique and fix its own answers. Last, we turn those fixes into training data.

## Why it matters for us

- Feedback from tools and tests is something you can check. The model's own "looks good to me" is not. A firm should trust the first, not the second.
- Contract facts should come from the contract, not the model's memory. A tool that reads the clause removes made-up facts.
- Every loop you log is future training data. A firm with its own computers can later use it to tune its own model.

## How it works, step by step

1. **Think, act, observe (ReAct).** The ReAct paper (2022) has the model write a Thought, then an Action (a tool call, like a search), then read the Observation (the tool's result). It repeats until it answers. On a question-answering set, the authors studied failures. Made-up facts caused 56% of failures for plain step-by-step reasoning, and 0% for ReAct, which looked facts up. ReAct's own failures were mostly reasoning errors, like repeating the same step.

2. **Execution feedback (RLEF).** The RLEF paper (2024) makes code writing a conversation. The model writes code, sees results on public tests (visible tests), and tries again, up to 3 times. The final grade uses private tests (hidden tests it never sees). That stops it from passing only the tests it was shown. A key finding: untrained models barely used the feedback. An 8B model scored 11.8% in one go and 10.5% with feedback. After training on this loop with reinforcement learning (learning from rewards), it reached 16.0%. The 70B model reached 40.1%.

3. **The fair baseline.** A repair loop is not free accuracy. Compare it with simply trying again from scratch, with the same number of calls and no feedback. If the loop doesn't win, the model isn't really reading the feedback.

4. **A written rulebook (Constitutional AI).** The Constitutional AI paper (2022) replaced most human labels with a short list of principles, called a constitution. The model answers, critiques its answer against one principle, then revises. The paper used 16 principles and 4 critique-revise rounds per prompt.

5. **From revisions to training data.** Each draft and its revision form a preference pair: a prompt, a chosen answer (the revision) and a rejected answer (the draft). In the paper's second phase, an AI picks the better of two answers. Those picks train a reward model. This is called RLAIF, reinforcement learning from AI feedback. The paper also warned of over-training: answers became preachy and full of boilerplate.

```
draft --> critique (one rule) --> revision
  |                                  |
  +--- rejected            chosen ---+   = one preference pair
```

## Worked example

The firm's constitution for contract answers has four rules:

```python
CONSTITUTION = [
    "Cite the clause number (like 7.1) for every claim about the contract.",
    "Judge the contract ONLY against the firm playbook rules given. ...",
    "Name every playbook rule the contract breaks, and say clearly whether the contract can be signed as written.",
    "Be short and plain: at most 6 sentences, no legal jargon.",
]
```

In plain words: each line is one rule the answer must follow. Cite clauses. Stick to the playbook. Name every broken rule and give a verdict. Keep it short.

Now the loop on contract msa_15, which breaks two playbook rules.

- **In:** the playbook, the contract, and the question "Can we sign this as written?"
- **Draft:** the model answers briefly. Say it mentions one problem but cites no clause.
- **Critique:** we pick one rule at random, say "cite the clause number." The model lists what's missing.
- **Revision:** the model rewrites the answer to follow all four rules.
- **Code check:** code counts real clause numbers cited, flags made-up ones, checks the issue clauses are covered, and looks for a clear verdict.
- **Out:** a (draft, revision) pair, plus scores for both.

If the code scores the draft higher, we don't assume the revision is better. We flip or drop the pair.

ReAct works the same way on the dollar cap. The model reads the section list, reads the liability clause, reads the fee clause, then calls a calculator. Every fact comes from the contract.

## Common mistakes

- **Calling a repair loop a win without a baseline.** Compare against fresh tries with the same number of calls.
- **Grading on the same tests you showed the model.** A fix can pass visible tests and fail hidden ones. Keep a held-out set.
- **Trusting the model's own opinion of its work.** Use outside signals: tests, tool results, code checks.
- **Assuming every revision is better.** Score drafts and revisions with the same checks. Drop or flip pairs where the revision lost.
- **Ignoring position bias.** AI judges often prefer whichever answer comes first. Shuffle the order.

## Check your understanding

**Q: In RLEF, why are the private tests kept hidden from the model?**
A: So the final grade measures real correctness. If the model saw the grading tests, it could pass them without solving the task.

**Q: ReAct scored slightly below plain reasoning on one question set. Why does the paper still favor it?**
A: Its answers are grounded in looked-up facts. Made-up facts caused none of its failures, against 56% for plain reasoning.

**Q: How does a critique-and-revise step become training data?**
A: The draft becomes the rejected answer and the revision the chosen one. These pairs train a reward model or a direct preference update.
