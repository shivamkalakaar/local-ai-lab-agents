## The big idea

There are two ways to make a model better at a task. You can change its instructions (the prompt). Or you can change the model itself by training it (changing its weights, the millions of numbers inside it). Changing instructions is far cheaper. Try it first.

GEPA (the GEPA paper, 2026) is a tool that rewrites instructions for you. Picture a junior associate drafting summaries, and a senior partner reviewing them. The partner doesn't just say "wrong". She writes "you said 30 days notice; the clause says 15." Then she rewrites the associate's checklist so the mistake doesn't happen again. Repeat a few dozen times, and the checklist gets very good.

In GEPA, the junior is a small fast model, called the student. The partner is a bigger model, called the reflection model. It reads the student's mistakes and the written feedback, and proposes better instructions. GEPA keeps the best versions and tries again.

In the course demo, this took Gemma 3 12B from 55% to 100% on a held-out set. Only the instruction text changed.

## Why it matters for us

- Small models run fast and cheap on a firm's own computers. But out of the box they make more mistakes. Prompt optimization closes much of that gap without any training.
- Both models can run locally. In our notebook, the student is Llama 3.2 3B and the reflection model is Llama 3.1 8B. No client data leaves the box.
- The result is just text. You can read it, version it, and roll it back.

## How it works, step by step

1. **Pick a narrow task with exact answers.** Ours: read the renewal and liability clauses, and pull out three numbers. Renewal years, notice days, and the liability cap in months.

2. **Write a metric that gives text feedback.** A metric is the grading function. Ours returns a score and a sentence like "notice_days: expected 15, got 30." That sentence is what GEPA learns from. A bare score tells the reflection model that something is wrong, not what.

3. **Split the data three ways.** Train (GEPA learns from these), validation (GEPA uses these to pick the best candidate), and test (hidden until the end). The test set is the honest score.

4. **Run GEPA with a budget.** The budget is how many times the metric may be called. Each attempt on one input is a rollout. GEPA tries the current instructions, collects failures, asks the reflection model for better instructions, and keeps a set of the strongest candidates.

5. **Freeze the winner.** Save the optimized instructions to a file, with a version.

6. **Climb the ladder only if needed.** If prompts plateau, move to training:
   - SFT (supervised fine-tuning): train on good examples, keeping only those a checker passes.
   - On-policy distillation: the student writes, and a teacher model scores every word. This needs a teacher you can run yourself, since closed APIs don't share those scores.
   - RL with GRPO: sample several answers, push toward the ones that beat the group average. Use it only where answers can be checked automatically.
   - Then re-tune the prompt on the new model.

## Worked example

Take a renewal clause: "renews for successive one (1) year terms unless either party gives at least fifteen (15) days' notice." The right answer is renewal_years = 1, notice_days = 15.

The baseline student, with a plain prompt, gets some fields wrong on the hidden test set. The notebook prints that score first.

Then GEPA runs:

```python
gepa = dspy.GEPA(metric=metric, max_metric_calls=60, reflection_lm=teacher, track_stats=True)
optimized = gepa.compile(program, trainset=train, valset=val)
after = evaluate(optimized, test)
print(f"held-out test: {before:.0%} -> {after:.0%}")
```

Line by line: the first line sets up GEPA with our metric, a budget of 60 metric calls, and the bigger model as the reflection model. The second line runs the optimization: it learns from the training contracts and picks the winner using the validation contracts. The third line scores the winner on the hidden test set. The last line prints the score before and after.

Finally, the notebook prints the new instructions. You will see plain sentences of guidance, written by the reflection model after reading the student's mistakes. That is the whole change. The model is the same.

The budget of 60 keeps the demo to about 10–15 minutes on a T4 (Colab's free GPU). Bigger budgets usually do better.

## Common mistakes

- **Optimizing without a trustworthy metric.** The optimizer will find every loophole in your grader. Fix the metric first (see Module 10).
- **Vague feedback.** A metric that only says "wrong" leaves the reflection model guessing. Say what was expected and what came back.
- **Looking at the test set during tuning.** Then the final score is no longer honest. GEPA uses train and validation only.
- **Jumping to training too early.** Training costs far more and can break other skills. In one course example, instruction-following fell from 85% to 45% after narrow training. Always run a general check after training.
- **Picking a teacher from a leaderboard.** The strongest model isn't always the best teacher. Judge a teacher by how good the student becomes.

## Check your understanding

**Q: Our local model gets 70% on clause extraction. What do we try first?**
A: GEPA prompt optimization, with a bigger model reflecting on mistakes and a metric that returns text feedback. Only if that plateaus do we build a training set.

**Q: Why does the metric return a sentence and not just a number?**
A: The reflection model needs to see what went wrong to fix the instructions. "Expected 15, got 30" points to the exact mistake; a number alone does not.

**Q: Why does on-policy distillation need an open-weight teacher?**
A: It needs the teacher's score for every word the student wrote. Closed APIs don't return those, so you need a teacher you can run yourself.
