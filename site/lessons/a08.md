## Learning objective
- Build a sample-then-select loop for bug fixes, grade "make it faster" with fast_p, and design an agent-system interface that gives useful feedback.

# Why this lecture: code grades itself

## Why code is easiest
- The computer grades the work: tests pass or fail, code runs faster or slower.
- So: sample many attempts, let tests pick the winner.
- Give the agent clear feedback from the system (errors, a profiler), not a bare number.
- Profiler: reports which functions used the most time; Python's built-in one is cProfile.

## The three papers
| Paper | Task | Main idea |
|---|---|---|
| CodeMonkeys (Ehrlich, Brown, Juravsky et al., Stanford/Oxford, 2025) | Fix real GitHub issues (SWE-bench Verified) | Scale serial + parallel compute, then select with tests and a model |
| KernelBench (Ouyang, Guo et al., Stanford/Princeton, 2025) | Rewrite PyTorch code as fast GPU kernels | A benchmark and metric (fast_p) for correct-and-fast code |
| Agent-System Interfaces (Wei, Nie et al., Stanford, ICML 2025) | Write mappers for parallel programs | A small language + AutoGuide feedback beat an RL autotuner |

## Two ways to spend test-time compute
| Serial | Parallel |
|---|---|
| More turns on one attempt | More independent attempts |
| Iterate on execution feedback | Sample with temperature > 0 |
| No selection problem | Must pick one at the end |
| Can get "stuck" after wrongly approving its work | Each new attempt is a fresh start |

- Test-time compute: compute spent while answering, not while training.
- All three papers use feedback loops; CodeMonkeys also samples in parallel.

# CodeMonkeys (Ehrlich et al. 2025)

## The problem: SWE-bench Verified
- SWE-bench instance: a GitHub issue + the code repository. Goal: edit files so the issue is fixed.
- Graded automatically by the repo's own test suite.
- Verified split: issues humans judged solvable (clear description, tests that don't reject correct fixes).
- Earlier work (Large Language Monkeys, same group): coverage rises log-linearly with samples, but no recipe for picking one.
- Question: how would you design a system if scaling test-time compute were the main goal?

## Three sub-tasks, three metrics
| Sub-task | Question | Metric |
|---|---|---|
| Context | Are the files that need editing in the prompt? | Recall: share of problems with all needed files |
| Generation | Is any sampled edit correct? | Coverage: share of problems with ≥1 correct edit |
| Selection | Did we submit a correct edit? | Score: share of problems resolved |

- Changing one step affects the others: more edits can raise coverage but make selection harder (Figure 2).

## System overview (Figure 1)
```
codebase → cheap model scans every file → rank → ~128k tokens of context
  → 10 parallel (testing state machine → editing state machine) → 10 (edit, test) pairs
  → run all tests on all edits → top-3 by votes → selection state machine → final edit
```
- Main model: Claude 3.5 Sonnet (claude-3-5-sonnet-20241022).
- File scanner: Qwen2.5-Coder-32B-Instruct, run locally.

## Step 1: context by reading every file
- SWE-bench repos hold millions of tokens: too big and too costly for a frontier model.
- Trick: context is shared by all 10 downstream edits, so its cost is paid once.
- Qwen2.5-Coder-32B reads every Python file (not test folders) and says relevant or not.
  - On average 2.94M tokens scanned per problem
  - Under 15% of total system cost
- Rerunning it for each of 10 edits would make it the most expensive step.

## Step 1b: ranking files
- During the scan, write a short summary of how each relevant file relates to the issue.
- Ranking prompt: each file's name, summary and token count; target about 60,000 tokens.
- Claude can be non-deterministic even at temperature 0: run the ranking 3 times, average the ranks.
- Include full files in rank order up to 128,000 tokens.
- Result: on average 74,570 tokens, a 50.5x reduction vs all relevant files.
- Recall at 128k limit: 92.6% of instances have all needed files (Figure 3).

## Step 2: edits with their own tests
- State machine: a fixed multi-turn loop where the model acts on execution feedback.
- Each attempt writes an edit and a standalone Python test script that reproduces the issue (result via exit code).
- Why tests: richer feedback for iterating, and imperfect verifiers for selection later.
- Two back-to-back state machines:
  - Testing state machine: iterate until the test script works and flags the bug on unedited code
  - Editing state machine: write an aider-style edit diff; may still revise the test
- Testing step skips the codebase files: shorter prompts, lower cache cost. Chat history cleared between the two.

## Two-sided debugging
| Test on code before the edit | Test on code after the edit |
|---|---|
| Should fail (bug reproduced) | Should pass (bug fixed) |

- Testing machine alone can produce tests that always fail, even on a correct fix.
- Letting the editing machine revise the test checks both sides.

## Serial vs parallel scaling (Figure 5)
- Setup: 10 state-machine pairs per issue, each capped at 8 iterations.
- Best: all 10 machines × 8 iterations → coverage 69.8%.
- First few serial iterations help a lot.
- After that: configurations with similar cost give similar coverage, however split.
- But equal coverage ≠ equal final score: more parallel candidates make selection harder.

## Cost breakdown (Table 1, USD)
| Stage | Total cost | Share |
|---|---|---|
| Relevance (local Qwen) | 334.02 | 14.6% |
| Ranking | 19.92 | 0.9% |
| Generate tests | 439.99 | 19.2% |
| Generate edits | 1366.02 | 59.6% |
| Selection | 131.95 | 5.8% |
| Total | 2291.90 | 100% |

- Prices used: $3/M input, $0.3/M cache read, $3.75/M cache write, $15/M output tokens.
- Biggest single item: cache reads in edit generation (the codebase files in the prompt).

## Step 3: selection, four methods
- Majority voting with tests: run all 10 tests on all 10 edits; pick the edit passing most (ties → expected score of a random pick).
- Model selection: model sees issue, context and all candidate diffs; picks one.
- Model selection after top-3 filtering: same, but only the 3 edits passing most tests (ties → shorter diff).
- Selection state machine after top-3: the model may write new tests to tell candidates apart; sees each test's output on every candidate and on unedited code; then picks.

## Selection results (Figure 6)
| Method | Score |
|---|---|
| Random selection | 45.8% |
| Model selection (all 10) | 52.0% |
| Majority voting with tests | 53.0% |
| Model selection after top-3 | 55.6% |
| Selection state machine after top-3 | 57.4% |
| Oracle selection (= coverage) | 69.8% |

- Judge on the whole pool loses to voting; after the top-3 filter it wins.
- Best method closes about half the gap from random to oracle; costs under 10% of the system.

## Final scores (Table 2, SWE-bench Verified)
| Method | Score |
|---|---|
| Barrel of Monkeys (oracle selection) | 80.8 |
| o3 (reported) | 71.7 |
| CodeMonkeys (oracle selection) | 69.8 |
| Barrel of Monkeys | 66.2 |
| Blackbox AI Agent | 62.8 |
| CodeStory | 62.2 |
| CodeMonkeys | 57.4 |

## Barrel of Monkeys: selecting across systems
- Pool: CodeMonkeys' final edit + the top-4 leaderboard submissions (Blackbox AI Agent, CodeStory, Learn-by-interact, devlo) as of January 15, 2025.
- 5 candidates per problem; combined coverage 80.8%.
- Skip the voting filter; send all 5 to the selection state machine.
- Score 66.2%, above the best single member (62.8%).
- But random selection here already gives 60.9%, so a smaller share of the gap is closed.

## Cheaper model check (Appendix A)
- DeepSeek-V3 on a random 100-issue subset, same context files.
- Claude 3.5 Sonnet: 45.74% (voting), 6.02% higher than DeepSeek-V3's best.
- DeepSeek-V3 reaches 86.8% of Claude's score at a fraction of the cost (API over 10x cheaper).
- Coverage for DeepSeek-V3 keeps rising with more compute.
- Lesson: many cheap samples can work, if selection is good.

## Limitations (Section 3)
- Context: the file filter still misses needed files for 7.4% of instances.
  - Assumes the model already knows the repo; private or new repos may need a different retrieval step
- Generation: feedback comes only from the model's own reproduction test, not regression tests.
  - Diversity only from temperature; parallel attempts don't know about each other
- Selection: recovers only about half of the random-to-oracle gap; ignores the repo's existing tests.

# KernelBench (Ouyang et al. 2025)

## The problem: fast GPU kernels are hard to write
- Kernel: a function that runs on the GPU; speed depends on hardware and tensor sizes.
- FlashAttention: released in 2022, 5 years after the Transformer; 2 more years to move it to Hopper GPUs.
- Experts use compiler feedback, profilers, hardware specs, tricks like tiling and fusion.
- CUDA is low-resource: only 0.073% of The Stack v1.2 code corpus.
- Question: can language models write correct and fast kernels?

## Task format (Figure 1)
- Input: PyTorch reference `Model` (an nn.Module) plus `get_inputs()` and `get_init_inputs()` for exact tensor shapes and types.
- Output: `ModelNew` with custom kernels (e.g. inline CUDA via the PyTorch CUDA-C extension).
- The model chooses which operations to optimize and how.
- Any tool allowed: CUDA, PTX, CUTLASS, Triton, ThunderKittens.

## Three levels, 250 tasks
| Level | Tasks | What | Hard because |
|---|---|---|---|
| 1 | 100 | Single operations: conv, matmul, losses, activations, norms | PyTorch already calls expert, often closed-source kernels |
| 2 | 100 | Sequences of 3–6 operations (e.g. conv + ReLU + bias) | Compilers are already good at fusion |
| 3 | 50 | Full architectures (e.g. AlexNet, MiniGPT) from GitHub | Needs algorithm changes beyond a compiler |

## How it grades
- Evaluation only: no reference kernels provided (users test on their own hardware).
- Correctness: compare `Model` and `ModelNew` outputs on 5 random inputs.
- Performance: wall-clock time of both, repeated trials.
- Speedup = PyTorch time ÷ generated kernel time.

## The metric: fast_p
- Formula: fast_p = (1/N) · Σ 1(correct_i AND speedup_i > p)
  - N: number of tasks
  - 1(...): 1 if the task's kernel is correct and more than p times faster, else 0
- fast_0 = plain correctness rate.
- fast_1 = correct and faster than PyTorch. The paper's main setting.
- Raise p as methods improve; p < 1 is useful for training (matching part of PyTorch's speed still counts).

## One-shot baseline (Table 1, fast_1 vs PyTorch Eager, L40S)
| Model | Level 1 | Level 2 | Level 3 |
|---|---|---|---|
| GPT-4o | 4% | 5% | 0% |
| OpenAI o1 | 10% | 24% | 12% |
| DeepSeek V3 | 6% | 4% | 8% |
| DeepSeek R1 | 12% | 36% | 2% |
| Claude 3.5 Sonnet | 10% | 7% | 2% |
| Llama 3.1-70B Inst. | 3% | 0% | 0% |
| Llama 3.1-405B Inst. | 3% | 0% | 2% |

- One example in the prompt (a simple add), greedy decoding.
- Speedup over PyTorch Eager in fewer than 20% of tasks on average.

## Why kernels fail (Figure 2)
- Execution failures: compile errors, CUDA memory violations, runtime errors.
- Correctness errors: wrong output shape or values.
- Reasoning models (o1, R1): under 55% incorrect; others: over 70%.
- The gap is mostly fewer execution failures. All models struggle similarly with correctness.

## Speed and hardware (Figure 3, Section 4.4)
- fast_p falls as p rises; at p = 1, under 15% of kernels beat PyTorch at every level.
- Reasoning models give more speedups.
- Level 1 winners transfer across GPUs; Level 2 varies more.
  - DeepSeek R1 Level 2 fast_1: 36% on L40S, 47% on A10G
- So one-shot kernels may not generalize across hardware.

## Repeated sampling (Figure 4)
- fast_p@k: share of tasks with at least one correct kernel p times faster, among k samples.
- High temperature helps explore: DeepSeek-V3 Level 2 fast_1 goes from 4% (one-shot) to 37% at k = 100.
- Limit: if the model almost never solves a task, more samples don't help.
  - DeepSeek-V3 never solved a group of 34 Level 1 convolution variants, even with 100 samples

## Iterative refinement with feedback (Figure 5)
- Each turn, the model gets:
  - G: its previous generation
  - E: compiler/execution feedback (errors, correctness, wall-clock time)
  - P: PyTorch profiler output (time per operator)
- Run N = 10 turns; fast_p@N = best kernel so far.
- Headline: DeepSeek-R1 Level 2 fast_1 from 36% to 72% with E + P (Figure 6).

## Sampling vs refinement, 10 calls each (Table 2, fast_1)
| Method | L1 V3 | L1 R1 | L2 V3 | L2 R1 | L3 V3 | L3 R1 |
|---|---|---|---|---|---|---|
| Single attempt | 6% | 12% | 4% | 36% | 8% | 2% |
| Repeated sampling @10 | 11% | N/A | 14% | N/A | 14% | N/A |
| Refine with G | 9% | 18% | 7% | 44% | 14% | 4% |
| Refine with G+E | 13% | 41% | 5% | 62% | 22% | 12% |
| Refine with G+E+P | 19% | 43% | 6% | 72% | 14% | 18% |

- Refinement beats sampling in 5 of 6 cases (R1 not sampled: its API had no temperature).
- Depends on the base model: R1 keeps gaining from E and P; V3 and Llama-3.1 70B don't always.

## What feedback fixes (Table 9)
- Execution feedback mostly fixes execution errors.
- DeepSeek-R1 gets a correct kernel on over 90% of Level 1 and 2 tasks within 10 turns (fast_0: 95% and 92% with G+E+P).
- Remaining failures: almost all functional incorrectness.
- Likely reason: "wrong output" is less specific feedback than a compiler error message.

## Hardware knowledge in the prompt (Section 5.2)
- Few-shot examples of fusion (GeLU), tiling (matmul), and a minimal FlashAttention:
  - Overall fast_1 drops: models try bolder tricks and fail more; o1's outputs 25% longer
  - But o1 applies tiling on 77% of Level 1 GEMM variants; on Level 2 beats PyTorch on 11 problems with shared-memory tricks
- Hardware specs (GPU type, bandwidth, TFLOPS, warps):
  - Little effect on Llama 3.1 70B and DeepSeek-V3
  - R1 tries tensor-core wmma instructions on about 50% of Level 1 matmuls; most fail to compile

## Interesting kernels found (Section 6.1)
| Trick | Example | Speedup |
|---|---|---|
| Operator fusion | GELU | 2.9x |
| Operator fusion | Softsign | 1.3x |
| Fused matmul + divide + sum + scale | Level 2 task | 2.6x |
| Shared memory | Cosine similarity | 2.8x |
| Shared memory | Triplet margin loss | 2.0x |
| Algorithm change | Dense × diagonal matrix: scale rows, skip zeros | 13x |

- No successful tensor-core use found. Many fusion chances missed.

## Limitations and future work
- Refinement experiments sample at temperature 0 (stated limitation, Appendix C.3).
- Models write raw CUDA; higher-level tools (ThunderKittens, CUTLASS, Triton) might make tensor cores easier.
- GPUs only so far; other accelerators next.
- CUDA data is scarce: more open, high-quality kernel data would help.

# Agent-System Interfaces (Wei et al. 2025)

## The problem: writing mappers
- Task-based programs (Legion framework): computation split into tasks; a separate mapper decides placement.
- Mapper: code that assigns tasks to processors and data to memories.
- Good mappers can give order-of-magnitude speedups.
- Writing one: hundreds of lines of low-level C++, days of expert tuning per application, input and machine.
- Search space grows exponentially with tasks and data arguments.

## The mapper search space
| Decision | Options |
|---|---|
| Processor selection | GPU, CPU, or OpenMP, per task |
| Memory placement | GPU FrameBuffer, ZeroCopy, or CPU system memory, per task and argument |
| Memory layout | SOA vs AOS, C vs Fortran order, alignment (e.g. 128-byte) |
| Index mapping | How partitioned tasks and data spread across processors |

## Agent-system interface (Figure 1)
- Agent-system interface (ASI): the layer between the agent and the system; what the agent writes and what feedback it gets.
- Two parts:
  - DSL (domain-specific language): high-level, declarative; a compiler turns it into C++
  - AutoGuide: turns raw execution output into explanations and suggestions
- The DSL also defines the search space.

## DSL vs C++ (Figure 2)
| DSL mapper | C++ mapper |
|---|---|
| `Task task0 GPU;` | `slice_task(...)` with targets, domains, iterators |
| `Region * ghost_region GPU ZCMEM` | 126 more lines of C++ omitted in the figure |
| `Layout * * * C_order SOA Align==64` | Imperative API calls for each constraint |
| Says what, not how | Says how, step by step |

- Average 14x fewer lines of code with the DSL.
- Every agent mapper that beat the experts was expressible in the DSL.

## AutoGuide (Table 1)
| Raw output | Explain | Suggest |
|---|---|---|
| "Assertion failed: stride does not match expected value." | Memory layout is unexpected. | Adjust the layout constraints or move tasks to different processor types. |
| "Execution time is 0.03s." | N/A | Move more tasks to GPU to reduce execution time. |

- Implemented by keyword matching over the raw output.
- Why: language feedback beats scalars; raw output is opaque; expert heuristics are easy to say in words.

## Generative optimization
- Problem: triplet (Θ, ω, T).
  - Θ: all possible mappers (program text)
  - ω: the objective, written as text
  - T: runs a mapper, returns feedback f (measured performance) and g (a trace of how it was made)
- Bandits, RL or Bayesian optimization struggle when Θ is huge and discrete (text).
- Generative optimization: an LLM proposes the next program from text feedback.
- Agent built in Trace; mapper split into independent code segments (like least-to-most prompting).

## Setup
- 9 benchmarks: Circuit, Stencil, Pennant (scientific), and 6 parallel matrix multiplication algorithms (Cannon's, SUMMA, PUMMA, Johnson's, Solomonik's, COSMA).
- Baselines: expert-written mappers; random mappers (10 seeds); Trace and OPRO (10 iterations, 5 runs); OpenTuner (RL autotuner, scalar time feedback, big penalty for failures).
- Hardware: one node, two 10-core Intel E5-2640 v4 CPUs, 256G memory, four NVIDIA Tesla P100 GPUs.
- LLM: gpt-4o-2024-08-06. Crashing mappers score throughput 0.

## Results (Figures 4, 5)
- Best Trace mappers match or beat the expert mappers on all 9 benchmarks.
- Up to 1.34x faster than experts (Circuit): two data collections moved from ZeroCopy to FrameBuffer memory.
- COSMA: 1.31x, from better index mapping (less inter-GPU communication).
- Random mappers: 74 of 90 (82.2%) crash with invalid mappings.
- Trace ≈ OPRO, both far ahead of OpenTuner.
- Trace vs OpenTuner: 11x at 10 iterations each; still 3.8x when OpenTuner runs 1000 iterations.

## DSL ablation (Table 2)
| Target | Success over 10 strategies |
|---|---|
| C++, single trial | 0% |
| DSL, single trial | 80% |
| C++, iterative refine (≤10 rounds) | 0% |
| DSL, iterative refine (≤10 rounds) | 100% |

- Same docs, examples and starting code for both; built with DSPy.
- Refinement fixed four C++ compile errors and two DSL ones, but no C++ mapper passed.
- The DSL has no training data at all; C++ has plenty. Still the DSL wins.
- Why: smaller gap from English to code ("align to 64 bytes, Fortran order" = one DSL line), and 14x less code.

## AutoGuide ablation (Figure 6)
| Feedback | Result on Circuit, COSMA, SUMMA |
|---|---|
| 0-shot, 5-shot (no feedback) | Worst |
| Execution output only | Better |
| + Explain | Better still |
| + Explain + Suggest (full AutoGuide) | Best, consistently |

- Gains come from the feedback loop, not just from prompting.

## Limits
- One framework (Legion), one node, 9 benchmarks.
- Results report the best mapper across runs (normal for offline tuning, but optimistic).
- The DSL might not express every optimization; the authors say they have not hit one.
- AutoGuide's rules are hand-written keyword matches: someone must know the domain.

# Our notebook, Part A: CodeMonkeys at small scale

## Coverage vs score
| Coverage | Score |
|---|---|
| Did any attempt fix the bug? | Did the attempt we picked fix it? |
| CodeMonkeys: 69.8% on SWE-bench Verified | CodeMonkeys: 57.4% |
| Rises with more samples | Limited by selection |

- The gap between them is the selection problem.
- Our notebook: 4 tiny buggy repos, 4 edits each, sampled in parallel.

## Filtering model-written tests
| Test fails on the buggy code | Test passes on the buggy code |
|---|---|
| Reproduces the issue | Doesn't reproduce the issue |
| Keep it | Drop it |
| e.g. `assert word_count("hello  world") == 2` (bug gives 3) | e.g. `assert word_count("one") == 1` |

- Model tests can be wrong. Never trust a single one.

## Selection in code
```python
v = votes(ri)
order = sorted(range(len(v)), key=lambda i: -v[i])
top3 = order[:3]
distinct = len({EDITS[ri][i] for i in top3}) > 1
SEL[ri] = {"votes": order[0], "votes + judge": judge(ri, top3) if distinct else order[0]}
```
- Line 1: for each edit, count the model tests it passes.
- Line 2: sort edits by votes; ties keep sampling order.
- Line 3: keep the 3 best.
- Line 4: are the top 3 actually different files?
- Line 5: vote pick vs judge pick (judge only if there is a real choice).

# Our notebook, Part B: KernelBench on a CPU

## Our version of KernelBench
- 4 slow Python/NumPy functions instead of 250 GPU workloads.
- Correctness: 5 random inputs, `np.allclose` (relative 1e-5, absolute 1e-6), same shape.
- Speed: best of 3 runs on one large input, in a subprocess with a timeout.
- Report fast_p for p = 0, 1, 2, 10, one-shot and after feedback.

## Scalar vs profiler feedback
| Scalar feedback | Profiler + guide |
|---|---|
| "Result: correct=..., speedup=...x." | Profile table of the code, plus a hint |
| Like a classic autotuner (OpenTuner) | "Hot spot: `per_user_totals` takes ...% of the time" |
| Says how good, not why | Says where the time goes and what to change |

- Our `guide()` is a tiny AutoGuide: crash → "fix this error first"; wrong → "compare on edge cases"; correct → profile + hot spot.

# How this applies to us

## Sample and select on the firm's machine
- The firm's own scripts have bugs. A local agent can try several fixes and let tests choose.
- Small local models make more mistakes per try. Fine, if a cheap exact check sorts good from bad.
- CodeMonkeys' DeepSeek-V3 check: a cheaper model got 86.8% of the score. Selection matters more than the model.

## Context once, reuse many times
- CodeMonkeys scanned every file once with a local 32B model, then shared it across 10 attempts.
- Same for the firm: index the contract set once, reuse it for every question.
- Prompt caching makes the shared part cheap on repeated calls.

## Design the interface, not just the prompt
- Clear feedback can matter more than a bigger model: good news for small models on the firm's machine.
- A narrow language helps: e.g. let the agent output `{"clause": "liability_cap", "months": 12}` instead of free text, then check it with code.
- Write an AutoGuide for the firm: turn "check failed" into "the cap quote is not in the contract text; copy it exactly."

## Common mistakes
- Coverage = score → more samples raise coverage but can make selection harder. Measure both.
- Model judge on the whole pool → cut to a top-3 short list with votes first.
- Checking speed on one input → the agent can game it. Check correctness on several random inputs.
- Bare scalar feedback → explain the error and suggest a change (AutoGuide).
- Running model code in your own process → subprocess, timeout, fresh folder.
