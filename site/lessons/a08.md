## The big idea

Most work is hard to grade. Was this memo good? People disagree. Code is different. The computer grades it for you. Tests pass or fail. The program runs faster or slower.

That makes software the friendliest place for an agent to improve itself. Try many fixes. Let tests pick the winner. Give the agent clear feedback from the system, not just a bare score.

Think of a mechanic with a test track. They can try three repairs, drive each car around the track, and keep the one that runs best. No one has to argue about which repair "feels" right.

## Why it matters for us

- A firm's own software, like a script that pulls clauses out of contracts, has bugs. A local agent can try several fixes overnight and let tests choose.
- Small local models make more mistakes per try. That's fine if a cheap, exact check can sort good tries from bad ones.
- How you show results to the agent matters a lot. Clear feedback can beat a bigger model. That is good news for anyone running small models on their own machines.

## How it works, step by step

1. **Split the job into three parts** (the CodeMonkeys paper, 2025). CodeMonkeys fixes real bugs from GitHub (a site where code projects live). Step one is context: find the files that matter. Step two is generation: run 10 attempts in parallel. Each attempt writes a code edit and a test script, then improves it using the results of running it. Step three is selection: choose one edit.

2. **Measure two numbers, not one.** Coverage is the share of problems where at least one attempt was correct. Score is the share where the attempt you picked was correct. The gap between them is the selection problem. CodeMonkeys reached 69.8% coverage but a final score of 57.4%. Some right answers were made but not chosen.

3. **Pick with test votes, then a judge.** Run every model-written test on every edit. Each edit gets one vote per test it passes. Keep the top 3 by votes. Then let a model look at those 3 and choose. A surprising finding: a model judge looking at the whole pool did worse than plain voting. With the top-3 short list first, it did better.

4. **Grade speed and correctness together** (the KernelBench paper, 2025). KernelBench asks a model to rewrite 250 programs as faster code for a GPU (a graphics chip used for AI math). Each rewrite is checked against the original on 5 random inputs, and both are timed. The score is fast_p: the share of tasks where the new code is correct and more than p times faster. So fast_1 means "correct and faster than the original". One-shot, the best models matched the original in fewer than 20% of cases.

5. **Give useful feedback.** A profiler is a tool that reports which parts of a program use the most time. When KernelBench fed models real run results and profiler output over 10 rounds, one strong model went from 36% to 72% on fast_1 for the middle level. Most of that gain came from fixing errors, not from clever speedups.

6. **Design what the agent sees** (the agent-system interfaces paper, 2024). This paper built two things. A small, narrow language for the agent to write in, which hides messy low-level code. And AutoGuide, a step that turns raw error messages and timings into plain advice. With this, an AI optimizer beat a classic tuning tool within 10 tries.

```
issue -> 10 attempts (edit + test each) -> run all tests on all edits
      -> top 3 by votes -> model judge picks 1 -> submit
```

## Worked example

The firm has a script that finds the liability cap in a contract and checks it against the playbook rule: "at most 12 months of fees". A bug report comes in. "Caps written as 'twelve (12) months' are missed."

Generation: the agent makes four attempts. Each returns a fixed file and a short test.

Filter the tests first. A good test must fail on the old, buggy code. Otherwise it doesn't reproduce the bug. Drop any test that already passes on the original.

Voting: run the surviving tests on all four edits. Edit A passes 3 tests. Edit B passes 3. Edit C passes 1. Edit D crashes. Keep the top 3: A, B, C.

Judge: the model reads the three diffs (the lines each edit changed) and picks A, because B also changes unrelated code.

Grading: a hidden test the agent never saw confirms whether A truly fixes the bug. That tells us both coverage (did any edit work?) and score (did the chosen one work?).

Every run happens in a fresh folder, in a separate process, with a time limit. Model-written code never runs inside your own program.

## Common mistakes

- **Confusing coverage with score.** More attempts raise coverage, but can make choosing harder. Measure both.
- **Trusting model-written tests blindly.** They can be wrong. Drop tests that pass on the buggy code, and never rely on one test alone.
- **Checking speed on a single input.** The agent can game it, for example code that only works for the timing input. Check correctness on several random inputs.
- **Picking the wrong bar for "fast".** Beating a slow Python loop is easy. Beating already-tuned code is hard. Choose p to fit your starting point.
- **Trusting one timing run.** Timing is noisy. Take the best of several runs.

## Check your understanding

**Q: What are CodeMonkeys' three steps?**
A: Context (find the relevant files), generation (make many edits and tests), and selection (choose one edit).

**Q: What does fast_1 measure?**
A: The share of tasks where the new code is both correct and faster than the original.

**Q: Why filter to a top-3 short list before asking a model judge?**
A: In CodeMonkeys, a judge looking at the whole pool did worse than plain test voting. Cutting the pool first with cheap votes let the judge do better.
