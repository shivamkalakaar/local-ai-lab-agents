## Learning objective
- Build a sample-then-select loop for bug fixes, and grade "make it faster" with fast_p and useful feedback.

## Why code is easiest
- The computer grades the work: tests pass or fail, code runs faster or slower.
- So: sample many attempts, let tests pick the winner.
- Give the agent clear feedback from the system (a profiler), not a bare number.
- Profiler: reports which functions used the most time; Python's built-in one is cProfile.

## CodeMonkeys: three steps
- Context: find the relevant files (a cheap model scans every file).
- Generation: 10 parallel attempts. Each writes a code edit and a test script, and iterates on execution feedback.
- Selection: run all model-written tests on all edits; keep the top 3 by votes; a model picks one.

```
issue → 10 attempts (edit + test each) → all tests on all edits
      → top 3 by votes → model judge picks 1
```

## Coverage vs score
| Coverage | Score |
|---|---|
| Did any attempt fix the bug? | Did the attempt we picked fix it? |
| CodeMonkeys: 69.8% on SWE-bench Verified | CodeMonkeys: 57.4% |
| Rises with more samples | Limited by selection |

- The gap between them is the selection problem.
- Serial compute: more turns fixing one attempt. Parallel: more attempts. Often gave similar coverage.

## Selection: votes, then a judge
- Test-based voting: each edit scores one point per model-written test it passes.
- Judge on the whole pool: did worse than plain voting.
- Judge on the top-3 short list: did better than voting.
- Selecting over edits from top leaderboard systems: 66.2%, above the best single member (62.8%).

## Filtering model-written tests
| Test fails on the buggy code | Test passes on the buggy code |
|---|---|
| Reproduces the issue | Doesn't reproduce the issue |
| Keep it | Drop it |
| e.g. `assert word_count("hello  world") == 2` (bug gives 3) | e.g. `assert word_count("one") == 1` |

- Model tests can be wrong. Never trust a single one.

## Selection in code
```python
v = votes(ri)
order = sorted(range(len(v)), key=lambda i: -v[i])
top3 = order[:3]
distinct = len({EDITS[ri][i] for i in top3}) > 1
SEL[ri] = {"votes": order[0], "votes + judge": judge(ri, top3) if distinct else order[0]}
```
- Line 1: for each edit, count the model tests it passes.
- Line 2: sort edits by votes; ties keep sampling order.
- Line 3: keep the 3 best.
- Line 4: are the top 3 actually different files?
- Line 5: vote pick vs judge pick (judge only if there is a real choice).

## KernelBench: grade speed and correctness
- 250 PyTorch workloads in three levels. Rewrite each as faster GPU code.
- Check output against the reference on 5 random inputs; time both.
- fast_p: share of tasks that are correct AND more than p times faster.
  - fast_0 = plain correctness; fast_1 = correct and faster.
- One-shot, frontier reasoning models matched PyTorch in fewer than 20% of cases.

## Scalar vs profiler feedback
| Scalar feedback | Profiler + guide |
|---|---|
| "Result: correct=..., speedup=...x." | Profile table of the code, plus a hint |
| Like a classic autotuner | "Hot spot: `per_user_totals` takes ...% of the time" |
| Says how good, not why | Says where the time goes and what to change |

- KernelBench with execution and profiler feedback, 10 turns: DeepSeek-R1 on Level 2, fast_1 from 36% to 72%.
- Feedback mostly fixed execution errors; correctness stayed hard.

## The agent-system interface
- Agent-system interface: what the agent can write, and what feedback it gets back.
- Wei et al. 2024, two parts:
  - A small language (DSL) that hides low-level C++ and defines the search space.
  - AutoGuide: turns raw output (errors, timings) into explanations and suggested changes.
- Beat OpenTuner by 3.8x: 10 iterations vs OpenTuner's 1000.
- Mappers up to 1.34x faster than expert-written ones.

## What the papers showed
| Paper | What it showed |
|---|---|
| CodeMonkeys (Ehrlich et al. 2025) | 57.4% of SWE-bench Verified for about 2,300 USD; 69.8% coverage |
| KernelBench (Ouyang et al. 2025) | Feedback over 10 turns doubled fast_1 for DeepSeek-R1 on Level 2 (36% → 72%) |
| Agent-system interfaces (Wei et al. 2024) | Narrow language + AutoGuide beat a 1000-iteration autotuner in 10 iterations |

## How this applies to us
- The firm's own scripts have bugs. A local agent can try several fixes and let tests choose.
- Small local models make more mistakes per try. Fine, if a cheap exact check sorts good from bad.
- Clear feedback can matter more than a bigger model: good news for small models on the firm's machine.

## Common mistakes
- Coverage = score → more samples raise coverage but can make selection harder. Measure both.
- Model judge on the whole pool → cut to a top-3 short list with votes first.
- Checking speed on one input → the agent can game it. Check correctness on several random inputs.
- Running model code in your own process → subprocess, timeout, fresh folder.

## Check your understanding
**Q: What are CodeMonkeys' three steps?**
A: Context (find the relevant files), generation (sample edits and tests), and selection (choose one edit).

**Q: What does fast_1 measure?**
A: The share of tasks where the new code is correct and faster than the reference.

**Q: Why cut to a top-3 short list before asking a model judge?**
A: A judge on the whole pool did worse than plain test voting. With the vote-filtered short list, it did better.
