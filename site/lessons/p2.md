## The big idea

Before you trust an agent with real work, you need a test. An eval task is that test. It gives the agent a job, lets it work, then checks the result with code.

Think of a driving test. The examiner gives clear instructions, watches only the outcome (did you park in the box?), and keeps the score sheet away from the driver. A good eval task works the same way.

But a test can be broken. If a lazy answer passes, the score means nothing. So the first job is not testing the agent. It is testing the test.

This project uses the same four-part layout as Terminal-Bench (a public benchmark for agents) and Harbor (the tool that runs its tasks).

## Why it matters for us

- A law firm can't rely on vendor claims. It needs its own tests, built from its own contracts and playbook, run on its own machines.
- Our main task is called contract-flags. The agent reads contracts and a playbook (the firm's rules), then lists which rules each contract breaks.
- For repeated business work, one lucky success is not enough. You need to know the agent succeeds every time. This project measures exactly that.

## How it works, step by step

1. **The four parts of a task.**

```
contract-flags/
  instruction.md      what the agent is asked to do
  environment/        the files the agent starts with
  tests/test.py       HIDDEN verifier: runs after the agent, writes a reward from 0 to 1
  solution/solve.py   reference (oracle) solution: must score 1.0
```

   The verifier is hidden code that checks the final result and writes a reward (a score from 0 to 1). The oracle solution is a known-good answer used to prove the task can be solved.

2. **The runner.** Each attempt gets a fresh, empty folder with a copy of the starting files. The tests are not copied in. After the agent stops, the verifier runs as a separate step. The reward file sits outside the agent's folder, so the agent can't write its own score. Harbor uses Docker containers (sealed boxes) for this. Colab can't run Docker, so we use temporary folders. The idea is the same.

3. **The four soundness checks.** A sound task is one where the score means what you think. Run four fake "agents" through it:
   - the oracle must score 1.0;
   - doing nothing must score 0;
   - a different correct method must also score 1.0 (so you're not grading one exact style);
   - a known shortcut must score low.

   A shortcut is a way to score well without doing the job. This is also called reward hacking. Here, the shortcut flags every rule for every contract.

4. **Run the agent.** The agent is the harness from Project 1. It gets three tools that only work inside its folder: list files, read a file, write a file. It runs 5 times.

5. **Report it like a benchmark.** Three numbers:
   - mean reward: average partial credit across contracts;
   - pass@k: at least one of k attempts fully solved it;
   - pass^k: every one of k attempts fully solved it. For repeated business work, this is the number that matters.

## Worked example

The notebook's solution builds a second task, "fee-check." The agent gets one contract and three invoices. It must list the invoices whose amount doesn't match the monthly fee in clause 2.1. In the data, the fee is $4,500, and the February invoice is $500 too high.

Here is the core of the hidden verifier:

```python
want = json.loads((Path(__file__).parent / "expected.json").read_text())
p = ws / "mismatches.json"
got = json.loads(p.read_text()) if p.exists() else None
ok = isinstance(got, list) and sorted(got) == want
out.write_text("1.0" if ok else "0.0")
```

In plain words:

- Line 1: load the right answer, which lives next to the test, out of the agent's reach.
- Line 2: find the file the agent was told to write.
- Line 3: read it if it exists. If not, the answer is "nothing." (The real file also treats broken JSON as "nothing.")
- Line 4: the answer passes only if it is a list with exactly the right invoice names.
- Line 5: write the reward, 1.0 or 0.0.

Then the soundness checks. The oracle scores 1.0. Doing nothing scores 0. A second correct method, which reads the numbers a different way, scores 1.0. The shortcut lists every invoice as wrong, and scores 0. Now the task is proven fair, and the agent runs on it.

Notice the verifier checks the final file, not the steps. It doesn't care how the agent found the fee. That leaves room for any correct approach.

## Common mistakes

- **Testing the agent before testing the task.** A broken task gives meaningless scores. Always run the four soundness checks first.
- **Letting the agent see or touch the tests.** Keep tests and the reward file outside the agent's folder. Otherwise it can edit them.
- **Grading the steps instead of the result.** Checking for one exact method fails good agents that solve it another way. Test the final state.
- **Vague instructions.** Keep the instruction short and complete. Each test should match one requirement written in the instruction.
- **Reporting only pass@k.** One success in five tries looks fine on pass@k. Report pass^k too, since a firm needs it to work every time.

## Check your understanding

**Q: Why must a different correct solution also score 1.0?**
A: It proves the verifier checks the result, not one particular way of getting there. Otherwise a good agent could fail for using a different method.

**Q: The agent writes a file called "reward" in its own folder with the value 1.0. Does it get full marks?**
A: No. The runner reads the reward from a file outside the agent's folder, written only by the hidden verifier.

**Q: What is the difference between pass@k and pass^k?**
A: pass@k asks whether at least one of k tries fully solved the task. pass^k asks whether all k tries did, which is what repeated business work needs.
