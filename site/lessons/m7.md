## The big idea

The harness is all the code around the model. The loop, the tools, the prompts, the limits, the logging. The model is the engine. The harness is the rest of the car.

A strong engine in a badly built car still drives poorly. A modest engine in a well-built car can do surprisingly well. For smaller models, the harness matters about as much as the model itself.

Frameworks are ready-made harness parts. This module covers two the course teaches, DSPy and LangGraph. It also covers one idea: crash-safe steps, so a long job can pick up where it stopped.

## Why it matters for us

The course shows this with a test called HarnessTax. The same smaller model, Haiku 4.5, scored 31.1%, 41.1% or 47.8% on a coding benchmark. Only the harness changed. Top models moved only 3 to 4 points across the same harnesses.

Local open models are in the "smaller model" group. So for a firm running AI on its own machines, the harness is a big part of the product. Pick it by measuring, not by reputation.

Long jobs also crash. The GPU runs out of memory. The session drops. If a firm is reviewing a hundred contracts, it should not start over from zero.

## How it works, step by step

1. **DSPy: describe inputs and outputs, not prompts.** A signature says what goes in and what comes out, with types. "Clause in. Cap in months and a yes/no out." DSPy writes the actual prompt for you. Later, an optimizer can improve that prompt against your test scores.

2. **DSPy modules mix model calls with plain Python.** A module is a small program. It can call a signature, then apply a rule in code, like "cap over 12 months is an issue."

3. **LangGraph: state, nodes and edges.** State is a shared record, like a form passed along a desk line. Nodes are steps that each fill in part of the form. Edges say which step comes next. Some edges are decisions made by code.

4. **Crash-safe steps.** Record each finished step with its result. On restart, look up the record first. If the step is done, reuse the saved result instead of calling the model again. This is the idea behind Temporal, a tool for durable execution (jobs that survive crashes).

```
LangGraph flow for governing law:
get clause --> read law (model) --decide (code)--> check law --> END
                                        \--------> needs human --> END
```

## Worked example

**DSPy.** The notebook writes a signature for the liability clause:

```python
class ExtractCap(dspy.Signature):
    """Read a limitation-of-liability clause and extract the cap."""
    clause: str = dspy.InputField()
    cap_months: int | None = dspy.OutputField(desc="months of fees the cap equals; None if liability is unlimited")
    favorable_to_customer: bool = dspy.OutputField()
```

- The class line names the task. The short sentence under it tells the model the goal.
- `clause` is the input: the clause text.
- `cap_months` is an output: a whole number, or None if there's no cap.
- `favorable_to_customer` is a yes/no output.

No prompt is written by hand. The notebook then wraps it in a module that flags an issue when the cap is missing or over 12 months. That rule lives in code. It also prints the exact prompt DSPy sent, so you can read it.

**LangGraph.** The graph handles governing law. One node fetches the clause. One asks the model which state's law applies. Then code decides. If the answer looks like a state name, go to the check. If not, send it to a person. The check marks California or Delaware as OK and anything else as ISSUE. On msa_10, which uses Florida law, the result is ISSUE.

**Crash-safe steps.** A small wrapper saves each step's result in a SQLite file (a simple database in one file). The notebook runs the law check on six contracts. Then it runs them again, as if after a crash. The second run reuses saved results. It is much faster, and the results match.

## Common mistakes

- **Trusting a framework's hidden prompt.** Read the prompt it actually sends. DSPy shows it with `inspect_history`.
- **Picking a harness by reputation.** Measure success and cost for your model on your task.
- **Scores that are only a number.** Return text like "expected 12, got 24." Optimizers learn from the reason.
- **Model calls inside Temporal's main workflow code.** Temporal replays that code to recover. Model calls give different answers each time, so they go in separate recorded steps.

## Check your understanding

**Q: What is a harness?**
A: All the code around the model: the loop, tools, prompts, limits and logging. For smaller models it matters about as much as the model.

**Q: In the LangGraph example, who decides whether a contract goes to a person?**
A: Code does. The decide step checks whether the model's answer looks like a state name. If not, it routes to "needs human."

**Q: How do crash-safe steps save time after a crash?**
A: Each finished step's result is saved. On restart, the code finds the saved result and reuses it instead of calling the model again.
