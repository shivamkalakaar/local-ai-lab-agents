The helper every notebook uses: lal/llm.py

A thin wrapper around the OpenAI-compatible API that Ollama and vLLM expose. Point LAL_BASE_URL somewhere else and the same notebooks run on another server.

lal/llm.py
"""One small wrapper around the OpenAI-compatible API that Ollama (and vLLM) expose.

Change LAL_BASE_URL to point the same code at vLLM or any other server.
"""
import json
import os
import time

from openai import OpenAI

client = OpenAI(base_url=os.getenv("LAL_BASE_URL", "http://localhost:11434/v1"),
                api_key=os.getenv("LAL_API_KEY", "local"))


def model() -> str:
    return os.getenv("LAL_MODEL", "llama3.1:8b")


def chat(messages, model_name=None, **kw):
    """One model call. Returns the assistant message object."""
    if isinstance(messages, str):
        messages = [{"role": "user", "content": messages}]
    kw.setdefault("temperature", 0)
    resp = client.chat.completions.create(model=model_name or model(), messages=messages, **kw)
    return resp.choices[0].message


def ask(prompt, system=None, **kw) -> str:
    """Shortcut: prompt in, text out."""
    msgs = ([{"role": "system", "content": system}] if system else []) + [{"role": "user", "content": prompt}]
    return chat(msgs, **kw).content or ""


def structured(messages, schema_model, model_name=None, retries=2, **kw):
    """Force the reply to match a Pydantic model (the server enforces the JSON schema), then validate.

    Small models occasionally return a cut-off or empty reply, so we retry a couple of times
    before giving up, and cap the length so a runaway reply can't hang the loop.
    """
    if isinstance(messages, str):
        messages = [{"role": "user", "content": messages}]
    kw.setdefault("temperature", 0)
    kw.setdefault("max_tokens", 1024)
    fmt = {"type": "json_schema", "json_schema": {"name": schema_model.__name__, "schema": schema_model.model_json_schema()}}
    last = None
    for _ in range(retries + 1):
        resp = client.chat.completions.create(model=model_name or model(), messages=messages, response_format=fmt, **kw)
        try:
            return schema_model.model_validate_json(resp.choices[0].message.content or "")
        except Exception as e:      # invalid or empty JSON: try again
            last = e
    raise last


def timed(fn, *a, **kw):
    """Run fn and print how long it took."""
    t0 = time.time()
    out = fn(*a, **kw)
    print(f"[{time.time() - t0:.1f}s]")
    return out

Module 01

What an agent is, and when you don't need one

Open in Colab

Lecture 1 · Zaharia et al., "Compound AI Systems" · Weng, "LLM Powered Autonomous Agents" · Kapoor et al., "AI Agents That Matter"

An agent is an LLM in a loop that picks its own next step, uses tools, and sees the results. Most real business tasks should not be agents. They should be workflows, where your code fixes the steps and the LLM fills in the fuzzy parts.

Key terms

Agent
An LLM running in a loop that chooses its own next action, calls tools, observes the results, and stops when it decides the task is done.Source: Weng, "LLM Powered Autonomous Agents" (2023); CS329Z Lecture 1
Compound AI system
A system that gets its results from several interacting parts (model calls, retrievers, tools, code) rather than one model call. Most production AI is built this way.Source: Zaharia et al., "The Shift from Models to Compound AI Systems", BAIR (2024)
Workflow
A compound system whose steps are fixed in code. The LLM fills in fuzzy parts but does not decide what happens next.Source: Schluntz & Zhang, "Building Effective Agents", Anthropic (2024)
ReAct
Reason + Act: the model alternates a short thought, an action (tool call) and an observation. Grounding reasoning in actions cut made-up facts compared with reasoning alone.Source: Yao et al., "ReAct", ICLR (2023)
Cost-controlled evaluation
Reporting accuracy together with cost, because retries can buy accuracy. Simple baselines (retry, escalate to a stronger model) often match complex agents.Source: Kapoor et al., "AI Agents That Matter", TMLR (2025)

The anatomy

  • LLM core: reads the situation and decides or writes.
  • Reasoning: thinking before acting (chain of thought, planning).
  • Tools: functions it can call, such as search, a database, or code.
  • Memory: what it keeps between steps and between sessions.
  • Environment: the world it acts on, which sends back results.

2. The agent loop

Four safety limits matter most: a turn cap, a stuck detector (the same call twice), errors returned as results so the model can fix its own mistakes, and a format check: small local models sometimes write a tool call as text instead of making it, so we send that back as an error.

01_agent_loop.ipynb · cell 3
def run_agent(task, max_turns=8, verbose=True):
    messages = [{"role": "system", "content": "You review contracts. Use the tools to read clauses before answering. Cite clause numbers."},
                {"role": "user", "content": task}]
    seen, calls = set(), 0
    for turn in range(max_turns):                                   # limit 1: turn cap
        msg = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS, temperature=0).choices[0].message
        messages.append(msg)
        if not msg.tool_calls:
            if '"name"' in (msg.content or "") and turn < max_turns - 1:     # limit 4: a tool call written as text
                messages.append({"role": "user", "content": "FORMAT ERROR: you wrote a tool call as text. "
                                 "Use the tool-calling interface, or give your final answer in plain words."})
                continue
            return {"answer": msg.content, "turns": turn + 1, "tool_calls": calls}
        for call in msg.tool_calls:
            calls += 1
            key = (call.function.name, call.function.arguments)
            if key in seen:                                         # limit 2: stuck detector
                result = "ERROR: you already made this exact call. Use the result you have, or answer."
            else:
                seen.add(key)
                try:
                    result = IMPL[call.function.name](**json.loads(call.function.arguments))
                except Exception as e:                              # limit 3: errors become results
                    result = f"ERROR: {type(e).__name__}: {e}. Check the tool name and arguments."
            if verbose:
                print(f"  turn {turn+1}: {call.function.name}({call.function.arguments}) -> {str(result)[:90]}")
            messages.append({"role": "tool", "tool_call_id": call.id, "content": str(result)})
    return {"answer": "STOPPED: turn limit reached.", "turns": max_turns, "tool_calls": calls}

t0 = time.time()
out = run_agent("In contract msa_07, what is the liability cap? Quote the clause.")
print("\nANSWER:", out["answer"])
print(f"{out['turns']} turns, {out['tool_calls']} tool calls, {time.time()-t0:.1f}s")

# Solution 2: add a search_text tool
STOP = {"of", "the", "a", "an", "to", "in", "for", "and", "or", "is", "how", "many", "what"}
def search_text(contract_id: str, phrase: str) -> str:
    """Return every clause containing ALL the meaningful words of the phrase ("days of notice" finds "days' prior written notice")."""
    words = [w for w in re.findall(r"[a-z0-9]+", phrase.lower()) if w not in STOP]
    hits = [f"{num}: {text}" for num, text in clauses(contract(contract_id)).items() if all(w in text.lower() for w in words)]
    return "\n".join(hits) or "No clause contains those words. Try one keyword."

Traps
  • Building an agent because it sounds impressive when a workflow would do.
  • Reporting accuracy without cost. Retries can buy accuracy, so always show both.
  • No turn limit. Loops are the most common agent failure (47% of ReAct's failures involved repeated or wrong reasoning steps).

Check yourself

A law firm wants every NDA checked against its 12-point playbook. Agent or workflow?

Workflow. The steps are known and the same every time. Use the LLM only to read clauses and spot unusual wording, and do the 12 checks in code wherever possible.

What should you try before building a complex agent?

Simple baselines: retrying, and running a cheap model first and escalating to a stronger one only when a check fails. They often match complex agents at a fraction of the cost.

Try it

Take one task from the Release Desk or the contract-review pilot. Write it as a list of steps, then mark each step C (code can do it) or L (needs an LLM). Most teams find 60–80% of steps are C.

Module 02

LLMs for builders

Open in Colab

Lecture 2 · DSPy · SGLang and vLLM structured output

Treat the model as an unreliable component with a typed interface. Force its output into a schema, and when you can check answers, sample several and keep the one that passes.

Key terms

Temperature
A setting that controls randomness when the model picks each next token. 0 is (nearly) the same answer every time; higher values give more varied answers.Source: CS329Z Lecture 2
Structured output
Asking the model to return data in a fixed schema (fields, types, allowed values) instead of free text, so code can use it.Source: CS329Z Lecture 2; DSPy signatures (Khattab et al., ICLR 2024)
Constrained decoding
The server only allows tokens that keep the output valid for a grammar or JSON schema, so the format can't break. The values can still be wrong.Source: CS329Z Lecture 2 (xgrammar / SGLang / vLLM structured outputs)
Test-time scaling
Spending more compute when answering (more samples, longer reasoning) instead of using a bigger model. With a checker, sampling many answers and verifying can beat a much larger model.Source: CS329Z Lecture 2
Self-consistency
Sample several reasoning paths and take the majority answer. Useful when no checker exists.Source: Wang et al., "Self-Consistency" (2023), cited in Lecture 2

Four things every builder should know

  1. Temperature. Use low temperature (0–0.3) for extraction, code and structured output. Use higher temperature only when you want variety, such as generating several candidates to check.
  2. Structured output. Give every component a typed contract: fields, types and fixed choice lists. Then the next step can rely on it.
  3. Constrained decoding. The server can force the model to produce valid JSON matching your schema, token by token (vLLM uses xgrammar for this). Parsing never fails. The content can still be wrong, so you still validate it.
  4. Test-time scaling. Spending more compute at answer time often beats a bigger model. With a checker, sample many answers and verify. Without a checker, take a majority vote.

Constrained decoding guarantees valid JSON. Why validate anyway?

Valid format is not correct content. The value can still be wrong, made up, or in the wrong unit. Check values against the source (for example, the quote must really appear in the document).

Module 03

Context engineering

Open in Colab

Lectures 2 and 6 · Anthropic, "Effective Context Engineering" · LangChain, "Context Engineering" · MemGPT

The context window is a small, expensive desk. Put only what the next step needs on it. Quality starts to drop well before the window is full.

Key terms

Context window
The maximum text (in tokens) a model can read at once. Everything the model knows about the current task must fit here.Source: CS329Z Lecture 2
Context rot
Answer quality drops as the context grows, often well before the window is full, and facts in the middle are used least.Source: Anthropic, "Effective Context Engineering for AI Agents" (2025); Lecture 2
Context engineering
Choosing the smallest set of high-value tokens to put in front of the model at each step: what to write down, select, compress or isolate.Source: Rajasekaran et al., Anthropic (2025); LangChain, "Context Engineering" (2025)
Observation masking
Replacing old tool outputs with a short placeholder. Cheap, needs no model call, and in coding agents roughly halved cost with equal or better results.Source: CS329Z Lecture 6
Compaction
Summarizing older history when nearing the window limit while keeping the system prompt, goal and recent turns word for word.Source: Lecture 6; MemGPT (Packer et al., 2023)
KV cache / prefix caching
The server keeps computed state for a prompt prefix it has seen. A stable prefix means the next call skips that work, which speeds up local inference.Source: Lecture 2
~84%

Share of a coding agent's tokens that are tool outputs. Hiding old ones roughly halved cost with equal or better results (L6).

51% vs 34%

A small model searching a 263K-token input with code beat a big model reading it all (L2 s.173).

8K

Context length where measurable quality decline began on the OOLONG test (L2).

The six techniques

  1. Append-only event log. Store every step forever. Rebuild what the model sees from the log each turn. You can then hide or summarize parts without losing the truth.
  2. Stable prefix. Keep the system prompt and tool list identical across calls and only add to the end. The server can then reuse its cache (vLLM --enable-prefix-caching), which cuts time to first token on your own GPU.
  3. Mask old observations. Replace old tool outputs with a one-line placeholder. It is cheap and needs no extra LLM call. Try this before summarizing.
  4. Compact near the limit. Summarize the middle of the history, but keep the system prompt, the user's goal and the last few turns word for word.
  5. Pin critical rules. Never let a rule like "confirm before acting" live only in the chat history. One agent deleted a user's inbox after that rule was summarized away (L2 s.171).
  6. Just-in-time loading and notes. Keep references (file paths, IDs) and load content when needed. Write progress to a notes file so it survives resets.

Module 04

Retrieval (RAG)

Open in Colab

Lecture 3 · Lewis et al. (RAG) · DPR · ColBERT · Anthropic, "Contextual Retrieval"

Retrieval finds the few passages the model needs. The default that works: search two ways (keywords and meaning), merge, rerank, and check every citation in code.

Key terms

RAG
Retrieval-augmented generation: first find relevant passages, then have the model answer from them.Source: Lewis et al., "Retrieval-Augmented Generation", NeurIPS (2020)
BM25
A classic keyword-matching score. Strong for exact strings such as clause numbers, IDs and names.Source: Lecture 3
Dense retrieval / embeddings
Turning text into vectors so passages with similar meaning are close together, even with different words.Source: Karpukhin et al., "Dense Passage Retrieval", EMNLP (2020)
Reciprocal rank fusion (RRF)
Merging ranked lists by adding 1/(k + rank) for each list (k ≈ 60). Simple and robust for hybrid search.Source: Lecture 3
Reranker / late interaction
A slower model that scores (query, passage) pairs more carefully to reorder the top candidates. ColBERT does this efficiently by comparing token-level vectors.Source: Khattab & Zaharia, "ColBERT", SIGIR (2020)
Contextual retrieval
Prepending a short note to each chunk saying where it comes from before indexing. Failed retrievals dropped from 5.7% to 1.9% with reranking.Source: Anthropic, "Contextual Retrieval" (2024), cited in Lecture 3
Recall@k
Share of questions where the right passage is in the top k results. Measures retrieval on its own.Source: Lecture 3

The decision

  • Under about 200K tokens of documents? Put it all in the prompt and skip retrieval.
  • More than that? Build the pipeline below.

The pipeline

  1. Chunk on structure. Split by headings or clauses first. Otherwise use 100–500 token chunks with 10–20% overlap.
  2. Add context to each chunk. Prepend a one-line note: "From the MSA with Acme, section 12, Limitation of Liability."
  3. Search two ways. Keyword search (BM25) catches exact strings like "12.3" or a lot number. Embedding search catches rewording like "cap on damages" vs. "limitation of liability."
  4. Merge with reciprocal rank fusion (RRF): score = Σ 1/(60 + rank).
  5. Rerank. Fetch about 150 candidates, rerank with a slower, more accurate model, and keep about 20.
  6. Verify citations. Every quote the model gives must appear in the source text, checked in code.
5.7% → 1.9%

Failed retrievals: plain chunks vs. contextual chunks with hybrid search and reranking (Anthropic).

10–20

Documents in the prompt beyond which accuracy stops improving; models also ignore the middle of long contexts (L4).

2. Two searches, merged with RRF

04_retrieval_rag.ipynb · cell 4
embedder = SentenceTransformer("BAAI/bge-small-en-v1.5")      # small, local embedding model
QUERY_PREFIX = "Represent this sentence for searching relevant passages: "   # what bge models expect on queries
tok = lambda s: re.findall(r"\w+", s.lower())                 # word tokens, so "msa_15," matches "msa_15"

class HybridIndex:
    def __init__(self, chunks):
        self.chunks = chunks
        docs = [f"{c['context']}\n{c['text']}" for c in chunks]
        self.bm25 = BM25Okapi([tok(d) for d in docs])
        self.vecs = embedder.encode(docs, normalize_embeddings=True, show_progress_bar=False)

    def keyword(self, q, n):
        return list(np.argsort(-self.bm25.get_scores(tok(q)))[:n])

    def semantic(self, q, n):
        qv = embedder.encode([QUERY_PREFIX + q], normalize_embeddings=True)[0]
        return list(np.argsort(-(self.vecs @ qv))[:n])

    def search(self, q, k=5, pool=50, mode="hybrid", rrf_k=60):
        if mode == "keyword": return [self.chunks[i] for i in self.keyword(q, k)]
        if mode == "semantic": return [self.chunks[i] for i in self.semantic(q, k)]
        scores = {}
        for ranking in (self.keyword(q, pool), self.semantic(q, pool)):
            for r, i in enumerate(ranking):
                scores[i] = scores.get(i, 0) + 1 / (rrf_k + r + 1)
        return [self.chunks[i] for i in sorted(scores, key=scores.get, reverse=True)[:k]]

index = HybridIndex(chunks)

Tools and function calling

Open in Colab

Lecture 4 · Toolformer · Gorilla · MCP spec · BFCL · τ-bench · SWE-agent

Spend more design effort on tools than on the prompt. A good tool is narrow, clearly described, hard to misuse, returns short output, and fails with a helpful message.

Key terms

Function (tool) calling
The model returns a structured request to run a named function with JSON arguments; your code runs it and returns the result.Source: Lecture 4
JSON Schema
A standard way to describe the allowed shape of JSON (types, required fields, patterns, enums). Used to validate tool arguments before running anything.Source: MCP specification (2025-06-18)
Model Context Protocol (MCP)
An open standard for exposing tools, resources and prompts to models through servers, with errors returned as results (isError).Source: modelcontextprotocol.io, spec revision 2025-06-18
Agent-computer interface (ACI)
The design of the tools and outputs an agent sees. Small changes (paged file views, edits that reject syntax errors) changed coding-agent success a lot.Source: Yang et al., "SWE-agent", NeurIPS (2024)
Toolformer / Gorilla
Research showing models can learn when and how to call APIs, and that retrieval of up-to-date API docs reduces made-up calls.Source: Schick et al., NeurIPS (2023); Patil et al., NeurIPS (2024)
τ-bench
A benchmark of tool-using agents talking to simulated users under policies; it popularized pass^k because agents were inconsistent across repeats.Source: Yao et al., τ-bench (2024), cited in Lecture 4

Tool design rules

  • Few and distinct. Overlapping tools confuse the model. The Pi harness used 4 tools and a prompt under 1,000 tokens and was among the most cost-effective.
  • Write descriptions like docs for a new hire. Say what it does, what it returns, and when not to use it.
  • Make misuse impossible. Use enums, required fields, and absolute paths. One fix like that removed a whole class of errors in SWE-agent.
  • Short, paged output. Showing whole files cut SWE-agent's success from 18.0% to 12.7%. Return 100 lines at a time.
  • Validate before running. Check the call against its schema first. Bad calls never execute.
  • Errors are results. Return "ERROR: clause '99' not found; valid clauses are 1–24" so the model can recover. MCP marks these with isError.
  • Allow "no tool fits". BFCL tests this. A model forced to pick a tool will pick a wrong one.
  • Prefer native function calling. On τ-bench it beat ReAct-style text calls for every model. On weak local servers, a strict text format plus a parser can be more reliable.

1. The registry

Order matters: validate → permission → run → truncate. Bad calls never run. Actions that change the world need approval.

05_tools.ipynb · cell 3
@dataclass
class ToolSpec:
    name: str
    description: str
    parameters: dict
    fn: Callable[..., Any]
    read_only: bool = True

@dataclass
class ToolResult:
    status: Literal["ok", "unknown_tool", "invalid_args", "tool_error", "denied"]
    content: str

class Registry:
    def __init__(self, specs, approve=lambda name, args: False, max_chars=1500):
        self.specs = {s.name: s for s in specs}
        self.approve, self.max_chars = approve, max_chars

    def schemas(self):
        return [{"type": "function", "function": {"name": s.name, "description": s.description,
                 "parameters": s.parameters}} for s in self.specs.values()]

    def execute(self, name, args) -> ToolResult:
        spec = self.specs.get(name)
        if spec is None:
            return ToolResult("unknown_tool", f"ERROR: no tool '{name}'. Available: {', '.join(self.specs)}")
        try:
            jsonschema.validate(args, spec.parameters)
        except jsonschema.ValidationError as e:
            return ToolResult("invalid_args", f"ERROR: bad arguments: {e.message}")
        if not spec.read_only and not self.approve(name, args):
            return ToolResult("denied", "DENIED: a person declined this action. Do not retry it.")
        try:
            out = str(spec.fn(**args))
        except Exception as e:
            return ToolResult("tool_error", f"ERROR: {type(e).__name__}: {e}")
        if len(out) > self.max_chars:
            out = out[: self.max_chars] + f"\n[truncated; {len(out)} chars total. Ask for a narrower range.]"
        return ToolResult("ok", out)

Design patterns

Open in Colab

Lecture 6 · Anthropic, "Building Effective Agents" · ReAct · Reflexion · CodeAct · ReWOO

Five workflow patterns and four agent patterns cover almost everything. Start with the simplest one that works and add complexity only when your eval shows it helps.

Key terms

Prompt chaining
Fixed sequence of calls, each using the previous output, with checks between steps.Source: Anthropic, "Building Effective Agents" (2024)
Routing
Classify the input first and send it to the best prompt, model or code path; easy cases can go to a cheaper path.Source: Anthropic (2024); Lecture 6
Orchestrator–workers
An LLM breaks a task into subtasks at run time and delegates them, then combines results.Source: Anthropic (2024)
Evaluator–optimizer
A generator and a checker in a loop. Works only when feedback is clear, reliable and actionable.Source: Anthropic (2024); Lecture 6
Reflexion
After a failure with an outside signal, the agent writes a short lesson and retries with it in context.Source: Shinn et al., "Reflexion", NeurIPS (2023)
CodeAct
The agent's actions are small programs instead of JSON tool calls, which handle loops and data better.Source: Wang et al., "Executable Code Actions Elicit Better LLM Agents", ICML (2024)
ReWOO (plan then execute)
Plan all steps in one call, then execute them without re-asking the model each step; fewer tokens.Source: Xu et al., ReWOO (2023), cited in Lecture 6

Four agent patterns

  • ReAct: think, act, observe, repeat. The default agent loop.
  • Reflexion: after a failure with an outside signal (a failing test), write a short lesson and retry with it. It added about 8 points over replaying raw history.
  • CodeAct: the model writes code as its action instead of JSON tool calls. Up to 20% higher success with fewer turns across 17 models, when tasks involve loops or data handling.
  • Plan then execute (ReWOO): plan all steps first, then run them. About 40–60% fewer tokens. This turns agent work back into a workflow.

def code_act(question):
    code = ask("You can use these Python functions: contract(cid) -> str, ids() -> list of ids, "
               "sections(text) -> list of {'id','title','text'}.\n"
               f"Write Python that computes the answer and stores it in a variable named result. Question: {question}\n"
               "Reply with only the code, no explanation, no backticks.")

    import builtins
    safe = {k: getattr(builtins, k) for k in ("len", "range", "sorted", "any", "all", "str", "int", "list", "set", "dict",

    try:
        exec(code, g)
        return g.get("result"), code
    except Exception as e:
        return f"ERROR {e}", code

def durable(step_name):
    def wrap(fn):

Key terms

Multi-agent system
Several LLM agents with separate roles or contexts that communicate to solve a task.Source: Wu et al., "AutoGen", COLM (2024)

Why multi-agent systems fail (MAST)

  • 44.2% system design: ignoring the task spec, repeating steps, not knowing when to stop.
  • 32.3% agents misaligned with each other: lost context in handoffs, ignored input from other agents.
  • 23.5% checking: no verification, or only a shallow final check. Adding a check against the overall goal gave +15.6%.

When to use more than one agent

  • Yes: many independent documents in parallel, broad research, separate checks that don't depend on each other.
  • No: tightly linked steps (cross-checking dates, parties and amounts across one contract), or when one agent already scores above about 45%.

Evaluation

Open in Colab

Lecture 10 (Terminal-Bench guest lecture) · Anthropic, "Demystifying Evals" · Zhu et al. agentic benchmark checklist · Zheng et al., LLM-as-a-Judge · tinyBenchmarks · τ-bench

Build the eval before the agent. It is the only way to know whether a change helped, whether a cheap local model is good enough, and what to tell a customer.

Key terms

Eval task (4-tuple)
A request, an environment, a stopping rule and a scorer. Designing each one carefully is most of benchmark quality.Source: Lecture 10; Press, "How to Build Good Language Modeling Benchmarks" (2024)
Oracle and null baselines
The reference answer must score ~100% and a do-nothing agent must score ~0%; otherwise the task or grader is broken.Source: Zhu et al., "Establishing Best Practices for Building Rigorous Agentic Benchmarks" (2025)
pass@k
Probability that at least one of k attempts succeeds.Source: Chen et al. (2021) estimator; Lecture 10
pass^k
Probability that all k attempts succeed: consistency, which matters for repeated business work.Source: Yao et al., τ-bench (2024); Anthropic, "Demystifying Evals for AI Agents" (2026)
LLM-as-judge
Using a model to grade outputs. Known biases: position, verbosity and self-preference; mitigate with swapped order, references and human calibration.Source: Zheng et al., "Judging LLM-as-a-Judge", NeurIPS (2023)
Precision and recall
Precision: share of flags that are real. Recall: share of real issues that were flagged. You need both.Source: Standard; Lecture 10

The four parts of every eval task

  1. Request: the instruction, written the way real users write it.
  2. Environment: the documents and tools, frozen and versioned.
  3. Stopping rule: time and token caps.
  4. Scorer: how you decide right or wrong. Check the final result, not the steps taken.

Graders, in order of preference

  1. Code: exact fields, numbers matching the source, required items present. Score precision (no false flags) and recall (nothing missed).
  2. LLM judge, only for open-ended parts like redline quality. Give it the expert's answer, use a different model family, ask about one thing at a time, allow "unknown".
  3. Humans, to calibrate: two experts label about 80–100 outputs. Measure how often experts agree with each other first.

Judge errors on math when given a reference answer (Zheng).

38%

Score an agent that does nothing got on one τ-bench task set. Always test a do-nothing baseline.

pass@k vs pass^k

pass@k: solved if any of k tries works. Fits when a person picks the best draft. pass^k: solved only if all k tries work. Fits repeated business work, where it must be right every time. At 75% per try, pass^3 is only about 42%.

Test the eval itself

  • Oracle: the expert's own answers must score about 100%. If not, the grader is too strict.
  • Do-nothing and flag-everything: both must score low.
  • Cheat probe: ask a strong model to game the grader (keyword stuffing, listing every issue type). Patch what works. In the Terminal-Bench lecture, a model found a known bug online and used it to fake a proof.
  • Read failures: look at 10–20 failures per model. If every model misses the same item, suspect the label.

def run_eval(system, cids):
    rows = [score(system(c), c) for c in cids]
    tp = sum(r["tp"] for r in rows); fp = sum(r["fp"] for r in rows); fn = sum(r["fn"] for r in rows)
    return {"precision": tp / max(tp + fp, 1), "recall": tp / max(tp + fn, 1), "exact": sum(r["exact"] for r in rows) / len(rows)}

Module 11

Optimization: prompts, then weights

Open in Colab

Lecture 9 · GEPA · MIPROv2 · DeepSeekMath (GRPO) · Thinking Machines, on-policy distillation · BetterTogether · FireAct

Improve prompts first; it's fast and cheap. Move to weights when prompts plateau on a small model. On-policy distillation from an open teacher is the most compute-efficient way to make a small model good at one task.

Key terms

Prompt optimization
Automatically improving instructions and examples against a metric without changing weights.Source: Opsahl-Ong et al., "MIPROv2", EMNLP (2024)
GEPA
Reflective prompt evolution: a model reads failures and their text feedback, proposes better instructions, and keeps a Pareto set of candidates. Beat GRPO with far fewer rollouts.Source: Agrawal et al., "GEPA", ICLR (2026)
SFT
Supervised fine-tuning: train the model on example inputs and the outputs you want.Source: Lecture 9
GRPO
Group Relative Policy Optimization: sample a group of answers per prompt, score them, and push toward those above the group average. No value model needed.Source: Shao et al., "DeepSeekMath" (2024)
On-policy distillation
The student generates; a teacher scores every token (reverse KL). Dense feedback at a fraction of RL's cost; needs teacher log-probabilities.Source: Thinking Machines (2025); Lecture 9
Rollout
One full attempt by the system on one input, used to compute a score or a training signal.Source: Lecture 9

The ladder

  1. Prompt optimization (GEPA, MIPROv2). Hundreds to a few thousand runs. Tells you whether you need training at all.
  2. Supervised fine-tuning (SFT) on a strong teacher's outputs, keeping only those your checker passes (rejection sampling).
  3. On-policy distillation: the student writes, the teacher scores every token. Fixes SFT's compounding errors.
  4. RL (GRPO) only where answers can be checked automatically, and the student already succeeds sometimes.
  5. Re-optimize prompts on the new model. Often a few more points.
GEPA > GRPO

On Qwen3-8B, GEPA peaked within a few thousand runs; GRPO was still below it after 24,000 (L9).

1,800 vs 17,920

GPU-hours: on-policy distillation reached 74.4% on AIME'24 vs. 67.6% for RL (Qwen3 report, L9).

Instruction-following after narrow training on documents. Always run a general check after training (L11).

def metric(gold, pred, trace=None, pred_name=None, pred_trace=None):
    wrong = [f"{f}: expected {getattr(gold, f)}, got {getattr(pred, f, None)}"
             for f in ("renewal_years", "notice_days", "cap_months") if getattr(pred, f, None) != getattr(gold, f)]
    return dspy.Prediction(score=1.0 - len(wrong) / 3, feedback="All correct." if not wrong else "Wrong -> " + "; ".join(wrong))

def evaluate(program, ds):
    scores = []
    for ex in ds:
        try: scores.append(metric(ex, program(clauses=ex.clauses)).score)
        except Exception: scores.append(0.0)
    return sum(scores) / len(scores)

Module 12

Data and flywheels

Open in Colab

Lecture 11 · Shankar, "Data Flywheels" · "Who Validates the Validators?" · SWE-smith · LIMA

Every run, every human correction and every failure is data. Store it with the reason, and it becomes a test today, an example tomorrow, and training data next month.

Key terms

Trace / trajectory
The full record of a run: inputs, prompts, model outputs, tool calls, results and timings.Source: Lecture 11
Data flywheel
Usage produces traces and corrections, which improve evals and training data, which improve the system, which earns more usage.Source: Shankar, "Data Flywheels for LLM Applications" (2024)
Synthetic task generation
Creating labeled cases by injecting known faults into real or clean data, so the answer is known by construction.Source: Yang et al., "SWE-smith", NeurIPS D&B (2025)
Rejection sampling
Generate several outputs and keep only those a checker accepts, to build clean training data.Source: Lecture 9 and 11
Criteria drift
Graders' standards change as they see more outputs; evaluation criteria must be revisited.Source: Shankar et al., "Who Validates the Validators?", UIST (2024)
Less is more
A small set of diverse, high-quality examples can align a strong model.Source: Zhou et al., "LIMA", NeurIPS (2023)

Three kinds of agent data

  • Traces: the full record of each run: inputs, model calls, tool calls, outputs.
  • Demonstrations: correct examples, from experts or from a teacher model whose output passed the checker.
  • Feedback: corrections and ratings from people. Binary pass/fail per criterion beats a 1–5 "quality" score.

The flywheel

  1. Read 50–100 real outputs with the customer. Write down failures in plain words.
  2. Turn each failure type into a binary check, in code where possible.
  3. Align any LLM judge to about 16+ human-graded examples. Expect your criteria to change as you grade.
  4. Log every correction with its reason. Use it right away as a test case and as a retrieved example.
  5. Batch corrections into a training set for the next release. Never train on the held-out eval.
1,000

Carefully chosen examples were enough to align a strong model (LIMA). Diversity beats volume.

2.5¢

Cost per synthetic task in SWE-smith, which injects known bugs into working code.

Module 13

Safety and guardrails

Open in Colab

PrivacyLens · Zhang & Yang, privacy risks via simulation · Contextualized Privacy Defense · OpenAI on prompt injection · Claude Code docs

Safety lives in the harness, not the prompt. Remove the ways data can leave and the actions that can do harm, treat every document as untrusted, and keep a person on every irreversible step.

Key terms

Prompt injection
Instructions hidden in content the agent reads (documents, web pages, tool results) that try to change its behavior. "Indirect" when the attacker never talks to the agent.Source: OpenAI, "Understanding Prompt Injections" (2025)
Contextual integrity
Privacy as appropriate information flow: whether sharing is OK depends on who, to whom, what, and under which norm.Source: Shao et al., "PrivacyLens", NeurIPS D&B (2024)
Least privilege
Give each component only the access it needs: read-only documents, no network, no send tools in the reviewer.Source: Claude Code docs; standard security practice
Human-in-the-loop
A person approves irreversible or high-stakes actions, shown the evidence.Source: Lecture on safety; Claude Code docs
Red-teaming
Searching for attacks on purpose and keeping them as regression tests. Fixed defenses were beaten by the next attack found by search.Source: Zhang & Yang, "Searching for Privacy Risks in LLM Agents via Simulation" (2025)
~99% vs 25–39%

Models answer "should I share this?" correctly, yet still leak in 25–39% of agent actions (PrivacyLens).

27.2% → 25.7%

Leak rate before and after adding a privacy prompt. Prompts barely help.

94% / 81%

Privacy and helpfulness when the agent is told what to drop, instead of being blocked (CDI).

87%

How often pop-up injections hijacked web agents (L1).

The design

  • Remove exits. No network for the agent process. No send or upload tools in the reviewer.
  • Split reading from acting. The step that reads documents can only output a typed schema. It cannot call any action tools, so injected text has nothing to trigger.
  • Least privilege. Read-only documents, write only to an output folder, scoped per client or matter.
  • Human on irreversible steps. Send, file, release: started by a person, with evidence shown. Ask at a few clear points to avoid approval fatigue.
  • Audit log. Append-only record of every step, with model version and input hashes.
  • Red-team continuously. Plant injections in test documents and rerun after every change.

Module 14

Long-running and coding agents

Open in Colab

SWE-agent · OpenHands · Anthropic, "Effective Harnesses for Long-Running Agents" · Claude Code best practices · Terminal-Bench

For jobs longer than one context window, the agent's memory must be written down: a checklist it can only mark done with evidence, a progress file, and a commit after each step.

Key terms

Long-running agent
An agent whose job spans many context windows or sessions, so progress must be written outside the model.Source: Anthropic, "Effective Harnesses for Long-Running Agents" (2025)
Initializer session
A first session that sets up the environment, a checklist and a progress file before any work starts.Source: Anthropic (2025)
Progress file / checklist
Files that hold what is done and what remains; the agent may only mark items done with evidence.Source: Anthropic (2025)
Incremental work
One item per session, verified and committed, so failures lose little and every step is reviewable.Source: Anthropic (2025); SWE-agent
Stop hook
A rule that prevents the run from finishing until required checks pass.Source: Claude Code docs

The long-running harness

  1. Setup session: write the full checklist (all items "not done"), an init.sh that starts the environment, and a progress file.
  2. Work sessions: start by reading the progress file and running a quick smoke test. Do one item. Mark it done only with evidence. Commit. Append to the progress file.
  3. Stop rule: the run can't finish until every item has a result and evidence.

Agent-computer interface (from SWE-agent)

  • A file viewer that shows 100 lines at a time, with line numbers.
  • Search that returns a capped summary, not every match.
  • An edit tool that rejects edits that break syntax and says why.

Open in Colab

A benchmark task has four parts: an instruction, a starting environment, a hidden verifier that writes a reward, and a reference solution. You prove the task itself is sound, then run an agent on it several times and report pass@k and pass^k.

Key terms

Verifier
Hidden code that runs after the agent and writes a reward from 0 to 1. Checks the final state, not the steps.Source: Merrill et al., "Terminal-Bench", ICLR (2026)
Oracle solution
A reference solution that must score 1.0 through the same verifier.Source: Terminal-Bench / Harbor task format
Shortcut / reward hacking
A way to score well without doing the task (flag everything, edit the tests). A sound task makes shortcuts fail.Source: Zhu et al. (2025); Lecture 10
Task soundness checks
Oracle passes, do-nothing fails, an alternative correct solution passes, and known shortcuts fail.Source: Zhu et al. (2025); CS329Z Homework 2 design

def run_attempt(task: Path, attempt_fn) -> float:
    ws = Path(tempfile.mkdtemp(prefix="attempt_"))
    shutil.copytree(task / "environment", ws, dirs_exist_ok=True)      # fresh copy every time; tests are NOT copied
    try:
        attempt_fn(ws, (task / "instruction.md").read_text())
    except Exception as e:
        print("attempt crashed:", type(e).__name__, e)
    # The reward file lives OUTSIDE the agent's workspace, so the agent can't write its own score.
    reward_file = Path(tempfile.mkdtemp(prefix="reward_")) / "reward"
    out = subprocess.run([sys.executable, str(task / "tests" / "test.py"), str(ws), str(reward_file)],
                         capture_output=True, text=True, timeout=120)
    print("  verifier:", out.stdout.strip() or out.stderr.strip()[-200:])
    reward = float(reward_file.read_text()) if out.returncode == 0 and reward_file.exists() else 0.0   # a crashed verifier scores 0
    shutil.rmtree(ws, ignore_errors=True)
    return reward

Glossary

Agent
An LLM in a loop that chooses its own next step and uses tools.
Workflow / compound AI system
Code fixes the steps; LLMs fill in parts.
Harness
All code around the model: loop, tools, prompts, limits, logs.
Constrained decoding
The server forces output to match a schema, token by token.
Context rot
Answers get worse as the context grows, starting early.
Observation masking
Hiding old tool outputs to keep the context small.
Compaction
Summarizing older history when nearing the context limit.
RAG
Retrieval-augmented generation: find relevant passages, then answer from them.
BM25
Classic keyword search scoring. Good for exact strings.
RRF
Reciprocal rank fusion: merging two ranked lists by 1/(60+rank).
Reranker
A slower, more accurate model that reorders search results.
MCP
Model Context Protocol: a standard way to expose tools and data to models.
ReAct
Think, act, observe, repeat.
Reflexion
Write a lesson after a failure and retry with it.
CodeAct
The model acts by writing code instead of JSON tool calls.
DSPy
Framework where you declare inputs/outputs and an optimizer tunes the prompts.
GEPA
Prompt optimizer that reflects on failures in text to evolve better instructions.
SFT
Supervised fine-tuning: train on example input/output pairs.
On-policy distillation
The student writes; a teacher scores each token; the student learns from that.
GRPO
RL method that compares a group of answers to the same prompt and favors the better ones.
pass@k / pass^k
Any of k tries succeeds / all k tries succeed.
LLM-as-judge
Using a model to grade outputs. Needs bias controls and human calibration.
Prompt injection
Instructions hidden in content (a document, a web page) that try to steer the agent.
Flywheel
Usage creates data, data improves the system, a better system gets more usage.
