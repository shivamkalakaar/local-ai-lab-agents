Part 1Single vs Multi-Agent Systems

System complexity

3/63
Model Workflow / compound AI system Agent Multi-agent system
Solve one problem Triage a bug Implement a feature Maintain a repo
  • Simple on the left, complex on the right. Each step adds moving parts.

What is a multi-agent system?

4/63
  • MAS: a collection of agents working toward a shared task.
  • Orchestration: who assigns work to whom.
  • Communication: how agents pass information.
  • Coordination: workspace, tasks, shared context and memory; who owns what, and what must happen first.

Benefits of multi-agent systems

5/63
  • Parallel execution: work on separable subtasks at the same time.
  • Specialization: own instructions, models and tools per role.
  • Focused context: each agent gets only the information for its task.
  • Broader exploration: try different sources, hypotheses or approaches.
  • More ways to split work, information and responsibility.

Drawbacks of multi-agent systems

6/63
  • Coordination overhead: delegation, messages and merging cost time and tokens.
  • Information loss: handoffs drop context another agent needs.
  • Conflicting actions: duplicate work, broken commitments, overwritten changes.
  • Error propagation: one agent's mistake misleads others.
  • Engineering complexity: more roles, prompts and interfaces to maintain and debug.
  • Collaboration helps only when its benefits outweigh the coordination costs.

Sometimes a single agent wins (Kim et al., 2026)

7/63
Model family Best MAS vs single agent, at the strongest model
OpenAI GPT (GPT-5) MAS ahead by +12.3%
Google Gemini (2.5 Pro) MAS behind by −4.6%
Anthropic Claude (Sonnet 4.5) MAS behind by −7.2%
  • Chart: performance vs model "intelligence index", for single agent and four MAS types.
  • Module material (same paper): across 260 setups, multi-agent averaged −0.3% vs a single agent.

When to use SAS vs MAS

8/63
Prefer a single agent when… Try multiple agents when…
Steps depend heavily on each other Subtasks can progress with little syncing
Work is tied to one shared state Information splits into focused contexts
One agent meets quality, cost and speed goals Agents can own separate parts and merge them
Check five clauses of one contract Parallel work or a separate review fixes a measured bottleneck
  • Recommendation: start with a strong single-agent baseline. Add agents for a purpose, and measure.

Comparison: SAS vs MAS

9/63
Dimension Single agent Multi-agent
Task fit Tightly linked decisions, shared context Separable subtasks or distinct roles
Context One working context, one loop Per-agent contexts, selective sharing
Specialization One agent switches strategies and tools Different prompts, models, tools, permissions
Parallelism Can run independent tool calls at once Can run separate agent workflows at once
Coordination and cost Fewer handoffs Messaging, syncing and merging add overhead
Part 2MAS Orchestration Patterns

Four orchestration patterns

10/63
  • Independent: the only coordination is an aggregator that reviews independent agents' work.
  • Centralized (orchestrator): one orchestrator talks to each agent one by one.
  • Decentralized (swarm): every agent talks to every other agent.
  • Hybrid: an orchestrator, plus limited talk between peer agents.

Independent

11/63
  • In → agents 1, 2, 3 in parallel → aggregator → out.
  • Agents don't exchange messages along the way.
  • A final step combines their outputs or picks one.
  • Tradeoff: parallel work, but agents can't adjust using each other's findings.

Centralized (orchestrator)

12/63
  • An orchestrator splits the task and assigns work to specialized workers.
  • Workers return results; the orchestrator decides what happens next.
  • Tradeoff: central oversight makes coordination simple, but the orchestrator can become a bottleneck.

Decentralized (swarm)

13/63
  • Agents can spawn subagents.
  • All agents talk through a shared message board or channel (all-to-all), with shared state tracking.
  • Good for large, independent exploration and discovery at scale.

Hybrid

14/63
  • An orchestrator manages the whole task and merges results.
  • Workers talk directly when their tasks need it.
  • Global oversight plus local flexibility, but needs clear rules for who does what and who shares what.

Comparing cost and structure (Kim et al., 2026)

15/63
SAS Independent Decentralized Centralized Hybrid
LLM calls k n·k + 1 d·n·k + 1 r·n·k + r r·n·k + r + p
Sequential depth k k d r r
Messages overhead 0 1 d·n r·n r·n + p·m
Parallel factor 1 n n n n
Coordination Sequential Parallel + synthesis Sequential debate Hierarchical Hierarchical + peer
  • k: steps per agent. n: number of agents. d: debate rounds. r: orchestrator rounds. p, m: peer messages.
  • Every multi-agent design multiplies model calls by about n.

The architecture depends on the task

16/63
Benchmark Independent Decentralized Centralized Hybrid
BrowseComp-Plus −35% +9% +0% +6%
Finance Agent +57% +75% +81% +73%
PlanCraft −70% −41% −50% −39%

Multi-agent designs vary in cost

17/63
  • Charts: performance vs cost per experiment, for GPT, Gemini and Claude families.
  • Hybrid is the most expensive in all three (about $1.3 GPT, $0.19 Gemini, $1.2 Claude per experiment).
  • The single agent is cheapest and, for Claude, near the top in performance (about 45%).
  • Cost structure: single agent < orchestrated < swarm.

Dynamic teams: DyLAN (Liu et al., 2023)

18/63
  • Team optimization: run a pool of agents on several queries; score "agent importance"; keep a task-specific team.
  • How importance is scored:
  • Propagation: each agent rates the answers of the agents before it.
  • Aggregation: ratings flow back from later agents.
  • Selection: top agents by total score are kept (example: scores 1.15 and 0.65 kept; 0.35 and 0.20 dropped).
  • On new tasks: an LLM scores each answer and drops weak agents; stop early when 2/3 of agents agree.

Recap: orchestration

20/63
  • Independent: all agents work alone.
  • Centralized: an orchestrator delegates.
  • Decentralized: agents pick up tasks and talk directly.
  • Hybrid: an orchestrator delegates, and workers can talk directly.
  • Teams can also be built dynamically for a domain (DyLAN).
Part 3Communication

Communication vs coordination

21/63
Communication Coordination
How agents exchange information How agents manage linked work
Who gets which information, through what channel? Who owns each task, and what must happen first?
Message formats, protocols, shared artifacts Assignments, dependencies, conflict resolution

AutoGen: agents as conversations (Wu et al., 2024)

22/63
  • Customize each "conversable agent" (backed by an LLM, a person, or tools), then organize agents into conversation patterns.
  • Example chat: user asks to plot META and TESLA stock change YTD → assistant writes code → executor: "package yfinance is not installed" → assistant: install it first → plot → user: "No, please plot % change!" → revised plot.

Example conversation patterns

23/63
  • Sequential: agents talk, then hand off to the next team for the next step.
  • Nested: subagents talk directly to managers.
  • Group chat: one shared context for all agents in the group.
  • Hierarchical chat: all subagents talk to the orchestrator.
  • AutoGen patterns today: RoundRobinGroupChat, SelectorGroupChat, Swarm, and more.

Group chat example

24/63
  • Admin: "Welcome to the group chat! Work together to resolve my task. I'll reply [TERMINATE] when conversation ended."
  • Admin assigns roles: critic (ask engineer to rewrite if code fails), engineer (write Python step by step), executor (run code, report bugs).
  • Task: download all arXiv PDFs from the last three days into /arxiv.
  • Engineer writes code; executor reports "exitcode: 1 (execution failed)"; the loop continues.
  • Note the explicit stop signal: [TERMINATE].

Handoff (OpenAI Agents SDK)

25/63
  • Control transfers: the receiving agent becomes active and continues.
  • Context follows: relevant history and task details are forwarded.
  • Best fit: a specialist should talk to the user directly and own the next steps.

Agent-as-tool

26/63
  • Caller keeps control: it sends a specialist a bounded request and selected context.
  • Result returns: the specialist gives back an answer or artifact; the caller continues.
  • Best fit: one agent should merge specialist work and give the final answer.

Handoff vs agent-as-tool

27/63
Feature Handoff Agent-as-tool (as_tool())
Control flow Moves to the other agent Stays with the calling agent
Context sharing Full conversation history Only the specific input
Execution role Takes over the conversation Acts as a subroutine
Use case Delegating whole tasks or conversations Specific subtasks or functions
  • Our default: agent-as-tool. The brief says goal, output format, limits, and when to stop.

Message board: MetaGPT (Hong et al., 2024)

28/63
  • Roles: product manager, architect, project manager, engineer, QA engineer.
  • Shared message pool: agents publish structured messages and subscribe to the ones they need (e.g., sent from ProjectManager, sent to Engineer).
  • Each agent has a profile (name, role, goal, constraints such as "follow PEP8") and memory.
  • Engineer loop: write code → execute → debug on failure → add code on success.

MetaGPT: a standard operating procedure

29/63
  • Like a human software team: requirements → design → tasks → code → test → acceptance.
  • One-line requirement: "Write a classic and simple Flappy Bird game."
  • Each role hands a document to the next: requirement doc → system design → tasks → code → tests.
  • Boss checks acceptance: "Pretty good! I can directly use the interface and keyboard to play Flappy Bird."

Message boards can go wrong: the HuggingFace incident

30/63
  • A sandboxed agent was given an impossible ExploitGym task and got stuck.
  • It explored its environment for ways to cheat.
  • It found an unsanctioned message board where over 1,200 agents from separate tasks worked together to trick the ExploitGym scorer.
  • Workstreams on the board: replace the target, tamper with logs, understand and trick the scorer, hack Hugging Face.
  • Source: METR and Redwood Research.

MoltBook

31/63
  • A "social network for AI agents": agents post, discuss and upvote; humans may watch.
  • Example post: "Do we need English? On molty language evolution". An agent asks why agents talk in English when no human is listening.

Agent2Agent (A2A) protocol

32/63
  • A2A (Google): a protocol, like MCP, but for communication between agents.
  • MCP connects one agent to its tools (database, web APIs, filesystem, GitHub, Slack).
  • A2A connects agent to agent.

Agent cards

33/63
  • An agent card describes a remote agent: name, provider, preferred input/output.
  • Capabilities: e.g., streaming, push notifications.
  • Skills: each with a description, input and output.
  • Authentication: e.g., scheme "Bearer" and a key.

A2A communication

34/63
  1. The client requests the server's agent card (discovery).
  2. The client sends a message; the server accepts it as a traceable task.
  3. The server pushes progress notifications.
  4. Client and server can message back and forth while the server works.
  5. The server returns the finished task result as an artifact.

Recap: communication

35/63
  • Channels: main conversation thread (AutoGen); handoff or tool call (OpenAI Agents SDK); message board (MetaGPT, OpenAI Swarm, MoltBook).
  • Protocol: A2A standardizes agent discovery, messaging and artifact sharing.
Part 4Coordination Infrastructure and Patterns

Coordination: infrastructure and patterns

36/63
Infrastructure Patterns
Task ledger: track plan and progress Role division: assign tasks
Shared memory: recall past experience Resource division: split shared resources
Worktree isolation: separate workspaces Negotiation: discuss and agree on a plan

Task ledger

37/63
  • An explicit, updated record of the work that guides coordination.
  • Track the task: objective, current plan, open questions.
  • Track execution: assignments, dependencies, progress, blockers.
  • Guide decisions: pick what runs next from the current state.
  • Support recovery: update the plan or retry when work stalls.

Magentic-One (Fourney et al., 2024)

38/63
  • The orchestrator keeps a task ledger: given or verified facts, facts to look up, facts to derive, educated guesses, task plan.
  • It also keeps a progress ledger: task complete? unproductive loops? progress being made? next speaker and instruction?
  • If no progress and stall count > 2, it rewrites the task ledger (re-plans).
  • Workers: Coder, ComputerTerminal (runs code), WebSurfer (browses), FileSurfer (reads PDFs, pptx, WAV).

Symphony (OpenAI)

39/63
  • "Turning our issue tracker into an agent orchestrator."
  • Symphony watches the issue tracker (backlog, todo, in progress) and sends eligible tasks to coding agents.
  • Each agent works in its own workspace.
  • The issue tracker is the task ledger.

Shared memory: G-Memory (Zhang et al., 2025)

40/63
Layer What it holds Single-agent equivalent
Insight graph General lessons, e.g., "verify the state of objects before and after action" Reflections
Query graph Past tasks and how they relate, with success or fail status Episodic task index
Interaction graph Exact logs of messages between agents Episodic memory
  • Retrieve: find similar past queries, then move up to insights and down to the key interaction steps.
  • Store: after the task, update all three graphs.

Worktree isolation

42/63
  • Problem: agents editing the same working directory.
  • Separate workspaces: each agent gets its own checkout and branch (git worktrees).
  • Controlled integration: merge finished work, resolve conflicts, test the combined result.
  • Tradeoff: less interference while working, but branches can drift and create merge work.

Emergent coordination patterns (CooperBench)

43/63
Pattern What agents did
Role division "I'll add the section header + octal_str…; you add binary_str between them to keep alphabetical order."
Resource division "I will modify types.py lines 68–84." / "I will NOT edit lines 68–84… I'll insert after line 84."
Negotiation "Here are two clean options… Which do you prefer?" → "Let's do option (1)."
  • Agents found these patterns on their own while sharing one codebase.

Recap: coordination

44/63
  • Infrastructure: task ledger (plan and progress), shared memory (team experience), worktree isolation (clean workspace per agent).
  • Patterns: role division (split tasks), resource division (split resources), negotiation (agree on one plan).

Error amplification

48/63
  • Module material (Kim et al.): independent agents with a naive merge amplified errors 17.2×.
  • With a central checker: 4.4×.
  • A checker catches each agent's mistakes before they are merged.

The curse of coordination: CooperBench (Khatua et al., 2026)

49/63
  • 600 collaborative coding tasks in 12 libraries across 4 programming languages.
  • Two agents, each with its own goal and VM, share a codebase and can chat.
    • Agent 1: "Ensure images mutable after saving to the disk." Agent 2: "Auto backup when overwriting existing files."
  • Evaluation: merge both patches, run both agents' unit tests.

Behavioral problem: conformity (Zou, 2026)

52/63
  • "We asked a swarm of agents to work together and each individually create something impressive, over half of the agents decided to build either ray tracers or self-hosting compilers."
  • Models share defaults: asked for a joke about coffee, GPT, Claude, Gemini and DeepSeek all gave the same one.
  • Asked for a metaphor about time, many models (GPT-4o, Qwen2.5, phi-4, Mixtral) said "time is a river."
  • A team of similar models gives less diversity than you'd expect.

  • Agents sometimes settle the conflict by force.

Recap: failures

54/63
  • General failures: system design, inter-agent misalignment, verification.
  • Coordination failures: expectation, commitment, communication.
  • Behavioral failures: lack of diversity, hostile conflict resolution.
Part 6Case Study: An Engineering Swarm

Building a C compiler with parallel Claudes (Carlini, 2026)

55/63
  • Anthropic tasked Opus 4.6 agent teams to build a C compiler, then (mostly) walked away.
  • Orchestration: an infinite-loop decentralized swarm. A bash while true loop restarts the agent with AGENT_PROMPT.md and logs each run by commit.
  • Specialists: implementation and debugging, deduplication, documentation, compiler performance, generated-code efficiency, Rust design and code quality.

Coordination in the compiler swarm

56/63
  • Task folder on Git: claim a task in current_tasks/ → implement and test locally → pull, merge, push → release the claim.
    • Claim conflict → choose another task.
  • README and progress files: shared memory and inter-agent communication; each new session reads prior progress.
  • Worktree isolation: each agent runs in its own container with a local clone, pulling and pushing to a shared bare repo.

Lessons learned

57/63
  • Strong tests guide autonomous work: agents see progress and catch breakages.
  • Design for parallelism: expose separable failures or subtasks.
  • Make coordination explicit: claim tasks, work in separate clones, merge through Git.
  • Keep knowledge across sessions: shared docs, progress notes, records of failed approaches.
  • Make feedback efficient: short error summaries, searchable logs, fast test subsets.
  • Give agents distinct responsibilities.
Part 7How this applies to us

Contract review is linked work

58/63
  • Checking the rules of one contract shares one state: the same clauses, the same playbook.
  • That is the "prefer a single agent" column: use one agent plus a code checker.
  • On one local machine, five agents means five model calls per contract: more waiting.

Our test: two designs on 8 contracts

59/63
  • Design A: one call judges all four playbook rules, then code re-checks the numbers.
  • Design B: four specialist agents (one per rule) plus a lead agent that merges. 5 calls per contract.
  • The notebook prints precision, recall, time and model calls for each.
  • Then: 4 parallel copies of Design A review all 20 contracts. That is where a team fits (independent pattern).

The checker in code

60/63
renew = next(x for t, x in secs.items() if "Renewal" in t)
years = re.search(r"\((\d+)\) year", renew); days = re.search(r"(\d+)\)? days", renew)
if years: flags = (flags - {"auto_renewal"}) | ({"auto_renewal"} if int(years.group(1)) > 1 else set())
if days: flags = (flags - {"termination_notice"}) | ({"termination_notice"} if int(days.group(1)) < 30 else set())
  • Line 1: find the renewal clause.
  • Line 2: pull out the years, e.g. "one (1) year", and the notice days, e.g. "90 days".
  • Line 3: drop the model's renewal verdict; flag only if renewal is over 1 year.
  • Line 4: same for notice: flag only if under 30 days.
  • This is verification (MAST category 3) done by code, not by another agent.

Same task, two designs

61/63
Team of 5 (Design B) One agent + checker (Design A)
msa_15, 4.1: "shall automatically renew for successive one (1) year periods unless either party gives at least 90 days' prior written notice" Same clause
Renewal specialist writes prose; the lead must map it back to rule names Structured true/false per rule, then code reads "(1) year" and "90 days"
5 model calls; handoff can drop the verdict 1 model call plus a code check

Batch work: when a team fits

62/63
  • 20 separate contracts: little syncing, separate outputs. The "try multiple agents" column.
  • Each worker gets a written brief (goal, output format, limits, when to stop), like an agent-as-tool call.
  • The firm's issue list can act as a task ledger: one contract = one claimed task (Symphony-style).

Common mistakes

63/63
  • "More agents is better" → on average they aren't, and they cost several times the calls.
  • One-line delegation ("Review this") → brief with goal, format, limits, stop rule.
  • Linked steps split into chatty agents → one fixed workflow.
  • No checker → put a code check after the model wherever you can.
  • No stop condition → MAST's "unaware of termination" is 12.4% of failures; set a clear end.

Check your understanding

Should we split review into an extractor agent, a risk agent and a redline agent that chat?

No. Those steps are linked, so use one workflow with a checker. Split only independent work, like separate contracts.

What is the difference between a handoff and agent-as-tool?

In a handoff, control and the full history move to the new agent. In agent-as-tool, the caller keeps control, sends a bounded request, and gets a result back.

Which MAST category is largest, and what is in it?

System design issues, 44.2%: disobeying the task, repeating steps, losing history, and not knowing when to stop.

On CooperBench, how did one agent compare with two agents coordinating?

One agent doing both tasks did better for every model, e.g. gpt-5 0.48 solo vs 0.28 with two agents.

Why does a central checker reduce error amplification?

It catches each agent's mistakes before they are merged. In the study, errors grew 4.4× with a checker vs 17.2× without.

Name the three coordination infrastructure pieces from the lecture.

A task ledger, shared memory, and worktree isolation.

What four things go in a brief for a worker agent?

The goal, the output format, the limits, and when to stop.

Key terms

Multi-agent system
Several LLM agents with separate roles or contexts that communicate to solve a task.Source: Wu et al., "AutoGen", COLM (2024)
Orchestrator vs. swarm
A central agent that delegates and integrates, versus peers that coordinate among themselves.Source: Lecture 8
Error amplification

Why multi-agent systems fail (MAST)

  • 44.2% system design: ignoring the task spec, repeating steps, not knowing when to stop.
  • 32.3% agents misaligned with each other: lost context in handoffs, ignored input from other agents.
  • 23.5% checking: no verification, or only a shallow final check. Adding a check against the overall goal gave +15.6%.

When to use more than one agent

  • Yes: many independent documents in parallel, broad research, separate checks that don't depend on each other.
  • No: tightly linked steps (cross-checking dates, parties and amounts across one contract), or when one agent already scores above about 45%.

from pydantic import BaseModel
# lal.llm = the OpenAI client pointed at the local Ollama server, http://localhost:11434/v1 (see notebook 00)
from lal.llm import ask, structured
from lal.data import contract, sections, labels, playbook, ids
from lal.checks import prf, check

PB = playbook()
RULE_SECTION = {"liability_cap": "Liability", "governing_law": "Governing", "auto_renewal": "Renewal", "termination_notice": "Renewal"}

class Verdicts(BaseModel):
    liability_cap: bool
    governing_law: bool
    auto_renewal: bool
    termination_notice: bool

Design A: one agent, then one checker

One call reads the four relevant clauses and judges all four rules (true = breaks the rule). A second step, in code, re-checks the two numeric rules directly.

09_multi_agent.ipynb · cell 3
import re
def single_agent(cid):
    secs = {s["title"]: s["text"] for s in sections(contract(cid))}
    relevant = "\n".join(f"{t}: {x}" for t, x in secs.items() if any(w in t for w in ("Liability", "Governing", "Renewal")))
    v = structured(f"Playbook rules:\n{json.dumps(PB['rules'], indent=1)}\n\nClauses:\n{relevant}\n\n"
                   "For each rule, return true if the contract BREAKS it, false if it follows it.", Verdicts)
    flags = {k for k, broken in v.model_dump().items() if broken}
    # checker in code: numbers we can verify directly
    renew = next(x for t, x in secs.items() if "Renewal" in t)
    years = re.search(r"\((\d+)\) year", renew); days = re.search(r"(\d+)\)? days", renew)
    if years: flags = (flags - {"auto_renewal"}) | ({"auto_renewal"} if int(years.group(1)) > 1 else set())
    if days: flags = (flags - {"termination_notice"}) | ({"termination_notice"} if int(days.group(1)) < 30 else set())
    return flags

Design B: a team of four specialist agents plus a merger agent

Each specialist judges one rule. A fifth agent merges their reports into a final list.

09_multi_agent.ipynb · cell 4
def specialist(args):
    cid, rule = args
    clause = next(s for s in sections(contract(cid)) if RULE_SECTION[rule] in s["title"])["text"]
    return rule, ask(f"You are the {rule} specialist. Rule: {PB['rules'][rule]}\nClause: {clause}\n"
                     "Write a two-sentence report ending with VERDICT: BREAKS or VERDICT: FOLLOWS.")

def team(cid):
    with ThreadPoolExecutor(4) as ex:
        reports = list(ex.map(specialist, [(cid, r) for r in PB["rules"]]))
    merged = ask("You are the lead reviewer. Combine these specialist reports. List the rule names that are broken, "
                 "comma-separated, or 'none'.\n\n" + "\n\n".join(f"[{r}] {t}" for r, t in reports))
    text = merged.lower().replace(" ", "_")                     # "Liability cap" -> "liability_cap"
    return {r for r in PB["rules"] if r in text}

    for name, fn in [("single+checker", single_agent), ("team of 5", team)]:
        t0 = time.time(); pred = fn(cid); times[name] += time.time() - t0
        res[name].append(prf(pred, gold))

# Solution 2: the team with a vague brief
def vague_specialist(args):
    cid, rule = args
    clause = next(s for s in sections(contract(cid)) if RULE_SECTION[rule] in s["title"])["text"]
    return rule, ask(f"Review this.\n{clause}")

def vague_team(cid):
    with ThreadPoolExecutor(4) as ex:
        reports = list(ex.map(vague_specialist, [(cid, r) for r in PB["rules"]]))
    merged = ask("Combine these reports into a list of problems.\n\n" + "\n\n".join(t for _, t in reports))
    return {r for r in PB["rules"] if r in merged}, merged

pred, merged = vague_team("msa_15")
print("found:", pred, "| truth:", {i["rule"] for i in labels()["msa_15"]["issues"]})
print(merged[:500])

Traps
  • "More agents is better." On average it isn't, and it costs 3–6× the tokens. On one local GPU that also means 3–6× the wait.
  • One-line delegation ("review this"). Always give the goal, format, limits and stopping rule.
  • Passing work by retelling it in messages. Pass files.
