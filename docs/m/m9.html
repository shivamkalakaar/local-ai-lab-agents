Module 09

Multi-agent systems

Open in Colab
8 min readSlides first, then the deeper material

When a team of agents helps and when it hurts. Default to one agent plus a checker; split only truly independent work.

Based on CS329Z Lecture 8 · Multi-Agent Systems · original slides (PDF)

Learning objective

1/12
  • Decide when to use one agent or a team, and build the one-agent-plus-checker design that usually wins.

What is a multi-agent system?

2/12
  • Multi-agent system (MAS): several agents working on one shared task.
  • Orchestration: who assigns work to whom.
  • Communication: how agents pass information.
  • Coordination: who owns each task, and what must happen first.

Benefits vs drawbacks

3/12
Benefits Drawbacks
Parallel execution of separable subtasks Coordination overhead: time and tokens
Specialization: own prompt, model, tools Information loss in handoffs
Focused context per agent Conflicting actions, duplicated work
Broader exploration Error propagation: one mistake misleads others
  • Collaboration helps only when its benefits outweigh the coordination costs.

The numbers

4/12
  • Across 260 setups, multi-agent systems averaged −0.3% vs a single agent.
  • They helped on wide, separable work. They hurt on step-by-step work.
  • CooperBench: one agent solving both tasks beat two agents coordinating.
  • On one local GPU, every extra agent is another model call: more waiting.

When to use SAS vs MAS

5/12
Prefer a single agent when... Try multiple agents when...
Steps depend on each other Subtasks need little syncing
Work shares one state Information splits into focused contexts
One agent meets quality, cost and speed goals Parallel work fixes a measured bottleneck
Check five clauses of one contract Review 20 separate contracts
  • Start with a strong single-agent baseline. Add agents for a purpose, and measure.

Orchestration patterns

6/12
  • Independent: agents work alone; a final step merges outputs.
  • Centralized (orchestrator): one agent assigns work and decides what is next.
  • Decentralized (swarm): all agents talk to all others.
  • Hybrid: an orchestrator, plus limited peer messages.
  • Cost: single agent < orchestrated < swarm.

Handoff vs agent-as-tool

7/12
Handoff Agent-as-tool
Control moves to the receiving agent Caller keeps control
Conversation history follows Sends a bounded request and selected context
Specialist talks to the user next Result comes back; caller writes the final answer
  • Our default: agent-as-tool. The brief says goal, output format, limits, and when to stop.

Why teams fail (MAST)

8/12
Cause Share Looks like
System design 44.2% Ignoring the task, repeating steps, not knowing when to stop
Misalignment between agents 32.3% Context lost in handoffs, ignoring each other
Weak checking 23.5% No verification, or a shallow final check
  • Error amplification: naive merge 17.2×; with a central checker 4.4×.

Our test: two designs on 8 contracts

9/12
  • Design A: one call judges all four playbook rules, then code re-checks the numbers.
  • Design B: four specialist agents (one per rule) plus a lead agent that merges. 5 calls per contract.
  • The notebook prints precision, recall, time and model calls for each.
  • Then: 4 parallel copies of Design A review all 20 contracts. That is where a team fits.

The checker in code

10/12

  • Line 1: find the renewal clause.
  • Line 2: pull out the years, e.g. "three (3) year", and the notice days.
  • Line 3: drop the model's renewal verdict; flag only if renewal is over 1 year.
  • Line 4: same for notice: flag only if under 30 days.

How this applies to us

11/12
  • Contract review is linked work. Use one agent plus a code checker.
  • On one local machine, five agents means five model calls per contract.
  • A team fits batch work: many separate contracts, each worker with a written brief.

Common mistakes

12/12
  • "More agents is better" → on average it isn't, and costs several times the tokens.
  • One-line delegation ("Review this") → brief with goal, format, limits, stop rule.
  • Linked steps split into chatty agents → build one fixed workflow.
  • No checker → put a code check after the model wherever you can.

Check your understanding

Should we split review into an extractor agent, a risk agent and a redline agent that chat?

No. Those steps are linked, so use one workflow with a checker. Split only independent work, like separate contracts.

Why does a central checker reduce error amplification?

It catches each agent's mistakes before they are merged. In the study, errors grew 4.4× with a checker vs 17.2× without.

What four things go in a brief for a worker agent?

The goal, the output format, the limits, and when to stop.

Default to one strong agent plus a separate checker. Add more agents only for wide, separable work, and only when your eval shows a gain.

Key terms

Multi-agent system
Several LLM agents with separate roles or contexts that communicate to solve a task.Source: Wu et al., "AutoGen", COLM (2024)
Orchestrator vs. swarm
A central agent that delegates and integrates, versus peers that coordinate among themselves.Source: Lecture 8
Error amplification
Mistakes compounding across agents. Independent agents with a naive merge amplified errors 17.2×; with a central checker, 4.4×.Source: Kim et al., "Towards a Science of Scaling Agent Systems" (2025)
MAST taxonomy
A catalog of why multi-agent systems fail: system design (44.2%), misalignment between agents (32.3%), and weak verification (23.5%).Source: Cemri et al., "Why Do Multi-Agent LLM Systems Fail?" (2025)
Agent-as-tool
Calling a sub-agent like a function with a bounded brief and getting a short result back, so the caller keeps control.Source: Lecture 8

Why multi-agent systems fail (MAST)

  • 44.2% system design: ignoring the task spec, repeating steps, not knowing when to stop.
  • 32.3% agents misaligned with each other: lost context in handoffs, ignored input from other agents.
  • 23.5% checking: no verification, or only a shallow final check. Adding a check against the overall goal gave +15.6%.

When to use more than one agent

  • Yes: many independent documents in parallel, broad research, separate checks that don't depend on each other.
  • No: tightly linked steps (cross-checking dates, parties and amounts across one contract), or when one agent already scores above about 45%.

09_multi_agent.ipynb · cell 2
import json, time
from concurrent.futures import ThreadPoolExecutor
from pydantic import BaseModel
# lal.llm = the OpenAI client pointed at the local Ollama server, http://localhost:11434/v1 (see notebook 00)
from lal.llm import ask, structured
from lal.data import contract, sections, labels, playbook, ids
from lal.checks import prf, check

PB = playbook()
RULE_SECTION = {"liability_cap": "Liability", "governing_law": "Governing", "auto_renewal": "Renewal", "termination_notice": "Renewal"}

class Verdicts(BaseModel):
    liability_cap: bool
    governing_law: bool
    auto_renewal: bool
    termination_notice: bool

Design A: one agent, then one checker

One call reads the four relevant clauses and judges all four rules (true = breaks the rule). A second step, in code, re-checks the two numeric rules directly.

09_multi_agent.ipynb · cell 3
import re
def single_agent(cid):
    secs = {s["title"]: s["text"] for s in sections(contract(cid))}
    relevant = "\n".join(f"{t}: {x}" for t, x in secs.items() if any(w in t for w in ("Liability", "Governing", "Renewal")))
    v = structured(f"Playbook rules:\n{json.dumps(PB['rules'], indent=1)}\n\nClauses:\n{relevant}\n\n"
                   "For each rule, return true if the contract BREAKS it, false if it follows it.", Verdicts)
    flags = {k for k, broken in v.model_dump().items() if broken}
    # checker in code: numbers we can verify directly
    renew = next(x for t, x in secs.items() if "Renewal" in t)
    years = re.search(r"\((\d+)\) year", renew); days = re.search(r"(\d+)\)? days", renew)
    if years: flags = (flags - {"auto_renewal"}) | ({"auto_renewal"} if int(years.group(1)) > 1 else set())
    if days: flags = (flags - {"termination_notice"}) | ({"termination_notice"} if int(days.group(1)) < 30 else set())
    return flags

Design B: a team of four specialist agents plus a merger agent

Each specialist judges one rule. A fifth agent merges their reports into a final list.

09_multi_agent.ipynb · cell 4
def specialist(args):
    cid, rule = args
    clause = next(s for s in sections(contract(cid)) if RULE_SECTION[rule] in s["title"])["text"]
    return rule, ask(f"You are the {rule} specialist. Rule: {PB['rules'][rule]}\nClause: {clause}\n"
                     "Write a two-sentence report ending with VERDICT: BREAKS or VERDICT: FOLLOWS.")

def team(cid):
    with ThreadPoolExecutor(4) as ex:
        reports = list(ex.map(specialist, [(cid, r) for r in PB["rules"]]))
    merged = ask("You are the lead reviewer. Combine these specialist reports. List the rule names that are broken, "
                 "comma-separated, or 'none'.\n\n" + "\n\n".join(f"[{r}] {t}" for r, t in reports))
    text = merged.lower().replace(" ", "_")                     # "Liability cap" -> "liability_cap"
    return {r for r in PB["rules"] if r in text}

Compare on 8 contracts: accuracy, time and model calls

09_multi_agent.ipynb · cell 5
sample = ["msa_01", "msa_05", "msa_07", "msa_09", "msa_12", "msa_14", "msa_15", "msa_18"]
res = {"single+checker": [], "team of 5": []}
times = {k: 0.0 for k in res}
for cid in sample:
    gold = {i["rule"] for i in labels()[cid]["issues"]}
    for name, fn in [("single+checker", single_agent), ("team of 5", team)]:
        t0 = time.time(); pred = fn(cid); times[name] += time.time() - t0
        res[name].append(prf(pred, gold))
calls = {"single+checker": 1, "team of 5": 5}
for name, rows in res.items():
    tp = sum(r["tp"] for r in rows); fp = sum(r["fp"] for r in rows); fn_ = sum(r["fn"] for r in rows)
    print(f"{name:15} precision {tp/max(tp+fp,1):.0%}  recall {tp/max(tp+fn_,1):.0%}  "
          f"time {times[name]:.0f}s  model calls/contract {calls[name]}")

When a team does make sense

Separable, wide work: 20 independent contracts at once. Each worker gets a written brief (goal, output format, limits, when to stop) and returns a short result. Here the "team" is parallel copies of the single agent.

def single_agent_no_checker(cid):
    secs = {s["title"]: s["text"] for s in sections(contract(cid))}
    relevant = "\n".join(f"{t}: {x}" for t, x in secs.items() if any(w in t for w in ("Liability", "Governing", "Renewal")))
    v = structured(f"Playbook rules:\n{json.dumps(PB['rules'], indent=1)}\n\nClauses:\n{relevant}\n\n"
                   "For each rule, return true if the contract BREAKS it, false if it follows it.", Verdicts)
    return {k for k, broken in v.model_dump().items() if broken}

for name, fn in [("with checker", single_agent), ("without checker", single_agent_no_checker)]:
    rows = [prf({r for r in fn(c) if r in ("auto_renewal", "termination_notice")},

# Solution 2: the team with a vague brief
def vague_specialist(args):
    cid, rule = args
    clause = next(s for s in sections(contract(cid)) if RULE_SECTION[rule] in s["title"])["text"]
    return rule, ask(f"Review this.\n{clause}")

def vague_team(cid):
    with ThreadPoolExecutor(4) as ex:
        reports = list(ex.map(vague_specialist, [(cid, r) for r in PB["rules"]]))
    merged = ask("Combine these reports into a list of problems.\n\n" + "\n\n".join(t for _, t in reports))
    return {r for r in PB["rules"] if r in merged}, merged

pred, merged = vague_team("msa_15")
print("found:", pred, "| truth:", {i["rule"] for i in labels()["msa_15"]["issues"]})
print(merged[:500])
# With no rule, no output format and no stopping point, the specialists comment on anything and the merger
# can't map their prose back to rule names. Most multi-agent failures are this kind of design problem.
Traps
  • "More agents is better." On average it isn't, and it costs 3–6× the tokens. On one local GPU that also means 3–6× the wait.
  • One-line delegation ("review this"). Always give the goal, format, limits and stopping rule.
  • Passing work by retelling it in messages. Pass files.
