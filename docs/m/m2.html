Module 02

LLMs for builders

Open in Colab
12 min readPlain-English lesson, then the deeper material

How to treat a language model like an unreliable part: force its answers into a fixed shape, check them against the source, and sample several when unsure.

The big idea

A language model is clever but unreliable. It can give a great answer, then a made-up one, in the same tone. So builders don't trust it. They wrap it.

Think of a temp worker filling in a paper form. You don't let them write a free-form essay. You give them boxes: "Governing law: _". "Cap in months: _". You add a box marked "not stated." Then you check their answers against the original document before anyone signs.

That is this whole module. Give the model a form (a schema). Make it fill in the boxes. Check the boxes. And when you can't check, ask several times and see if the answers agree.

Why it matters for us

A contract review is only useful if the next step can rely on it. If the model writes "about a year or so" when code expects the number 12, everything after breaks. A fixed shape fixes that.

Small local models make more mistakes than big cloud ones. But there is good news. Spending more effort at answer time, by sampling several answers and checking them, can close much of the gap. With enough samples and a checker, small Llama models beat GPT-4o's single answer on math problems (course Lecture 2). That is a strong reason to run small models well instead of big models badly.

How it works, step by step

  1. Set temperature low for facts. Temperature controls randomness. Use 0 to 0.3 for pulling out facts. Use higher values only when you want variety.

  2. Define a schema. A schema is a description of the exact fields you want, with types. For example, liability_cap_months must be a whole number. In Python we write this with Pydantic, a library for typed data.

  3. Always add an "absent" option. Let each field be None (empty) if the contract doesn't say. Without this, the model invents a value to fill the box.

  4. Let the server force the shape. Constrained decoding means the server only lets the model write words that fit the schema. The output is always valid JSON (a standard data format). Parsing never fails.

  5. Check the content anyway. Valid shape is not correct content. The number could still be wrong. So we check in code. For example: does the quoted sentence really appear in the contract?

  6. Sample when unsure. Two ways:

  7. Best-of-n, when you have a checker. Ask up to n times. Keep the first answer that passes the check.
  8. Majority vote, when you have no checker. Ask several times and take the most common answer. How often they agree is a confidence signal. Low agreement means "send to a person."

Worked example

The notebook defines the form for a contract:

class Terms(BaseModel):
    governing_law: str | None = Field(description="US state name, e.g. 'Delaware', or null")
    liability_cap_months: int | None = Field(description="Cap as months of fees, e.g. 12. null if liability is unlimited")
    cap_quote: str | None = Field(description="Exact sentence from the contract stating the liability cap")
  • class Terms(BaseModel) declares a new form called Terms.
  • governing_law is text, or None if absent. The description tells the model what to write.
  • liability_cap_months is a whole number, or None if liability is unlimited.
  • cap_quote asks for the exact sentence. This is what lets us check the answer.

The system prompt says: "Copy quotes exactly. If a term is absent, use null. Never guess."

We run it on msa_07. Out comes a neat record: a state, a cap in months, renewal years, notice days, and a quote. Then one line of code asks: is that quote really in the contract? For the real quote, yes. For a made-up quote like "Liability is capped at $1 million," no.

The notebook then scores each field on 8 contracts against the known answers. You see which fields the model gets right and how many quotes check out.

Finally, best-of-n. The code asks up to four times at a higher temperature. It returns the first answer whose quote is found in the contract. If none pass, it returns nothing. That means "escalate to a person," not "guess."

Common mistakes

  • Asking for JSON in the prompt and hoping. Use the server's schema mode so the shape is guaranteed.
  • No "absent" option. Force a number on a contract with unlimited liability, and the model will invent one. The notebook shows this on msa_16.
  • Free text for fixed choices. If the answer must be one of a few states, use a fixed list (Literal in Python). Then "DE" and "State of Delaware" can't sneak in.
  • Trusting the model's own confidence. Use agreement across samples, or an outside check, instead.

Check your understanding

Constrained decoding guarantees valid JSON. Why check the answer anyway?

Valid format is not correct content. The value can still be wrong or made up. Check it against the source, for example by confirming the quote is in the document.

When do you use majority vote instead of best-of-n?

When you have no checker. Majority vote works for short answers you can compare, like yes/no or a number. Best-of-n needs a check to decide which sample passes.

Why does the schema let every field be empty?

So the model has an honest way to say "not in this contract." Without it, the model fills required boxes with invented values.

Key terms, papers, evidence, the full notebook code and worked solutions.

Lecture 2 · DSPy · SGLang and vLLM structured output

Treat the model as an unreliable component with a typed interface. Force its output into a schema, and when you can check answers, sample several and keep the one that passes.

Key terms

Temperature
A setting that controls randomness when the model picks each next token. 0 is (nearly) the same answer every time; higher values give more varied answers.Source: CS329Z Lecture 2
Structured output
Asking the model to return data in a fixed schema (fields, types, allowed values) instead of free text, so code can use it.Source: CS329Z Lecture 2; DSPy signatures (Khattab et al., ICLR 2024)
Constrained decoding
The server only allows tokens that keep the output valid for a grammar or JSON schema, so the format can't break. The values can still be wrong.Source: CS329Z Lecture 2 (xgrammar / SGLang / vLLM structured outputs)
Test-time scaling
Spending more compute when answering (more samples, longer reasoning) instead of using a bigger model. With a checker, sampling many answers and verifying can beat a much larger model.Source: CS329Z Lecture 2
Self-consistency
Sample several reasoning paths and take the majority answer. Useful when no checker exists.Source: Wang et al., "Self-Consistency" (2023), cited in Lecture 2

Four things every builder should know

  1. Temperature. Use low temperature (0–0.3) for extraction, code and structured output. Use higher temperature only when you want variety, such as generating several candidates to check.
  2. Structured output. Give every component a typed contract: fields, types and fixed choice lists. Then the next step can rely on it.
  3. Constrained decoding. The server can force the model to produce valid JSON matching your schema, token by token (vLLM uses xgrammar for this). Parsing never fails. The content can still be wrong, so you still validate it.
  4. Test-time scaling. Spending more compute at answer time often beats a bigger model. With a checker, sample many answers and verify. Without a checker, take a majority vote.

The code, cell by cell

1. A typed contract with Pydantic

Note the "null if absent" option. Without it, models invent values to fill required fields.

02_llms_for_builders.ipynb · cell 2
from typing import Literal
from pydantic import BaseModel, Field
# lal.llm = the OpenAI client pointed at the local Ollama server, http://localhost:11434/v1 (see notebook 00)
from lal.llm import structured, ask
from lal.data import contract, labels, ids
from lal.checks import quote_is_in_doc, check

class Terms(BaseModel):
    governing_law: str | None = Field(description="US state name, e.g. 'Delaware', or null")
    liability_cap_months: int | None = Field(description="Cap as months of fees, e.g. 12. null if liability is unlimited")
    renewal_years: int | None = Field(description="Length of each automatic renewal period in years")
    notice_days: int | None = Field(description="Days of notice needed to stop renewal")
    cap_quote: str | None = Field(description="Exact sentence from the contract stating the liability cap")

SYSTEM = "Extract the requested terms from the contract. Copy quotes exactly. If a term is absent, use null. Never guess."

def extract(cid):
    return structured([{"role": "system", "content": SYSTEM}, {"role": "user", "content": contract(cid)}], Terms)

t = extract("msa_07")
print(t.model_dump_json(indent=2))
print("Truth:", labels()["msa_07"]["terms"])

3. Field accuracy on 8 contracts

02_llms_for_builders.ipynb · cell 4
FIELDS = ["governing_law", "liability_cap_months", "renewal_years", "notice_days"]
sample = ids()[:4] + ids()[-4:]
right = {f: 0 for f in FIELDS}
quotes_ok = 0
for cid in sample:
    t = extract(cid)
    truth = labels()[cid]["terms"]
    for f in FIELDS:
        right[f] += getattr(t, f) == truth[f]
    quotes_ok += quote_is_in_doc(t.cap_quote, contract(cid))
for f in FIELDS:
    print(f"{f:22} {right[f]}/{len(sample)}")
print(f"{'cap quote verified':22} {quotes_ok}/{len(sample)}")

4. Majority vote: when you have no checker

Ask several times at a higher temperature and take the most common answer. The agreement rate is a useful confidence signal; low agreement means "send to a human".

02_llms_for_builders.ipynb · cell 5
from collections import Counter
def vote(question, n=5):
    answers = [ask(question, temperature=0.8).strip().lower().rstrip(".") for _ in range(n)]
    label, count = Counter(answers).most_common(1)[0]
    return label, count / n, answers

q = ("Is this clause favorable to the customer? Answer only 'yes' or 'no'.\n\n"
     + contract("msa_08").split("7.1 ")[1].split("\n")[0])
label, agree, answers = vote(q)
print(f"vote: {label} (agreement {agree:.0%}) from {answers}")

5. Best-of-n: when you do have a checker

Sample until an answer passes a check. Here the check is code: the quote must be in the document.

02_llms_for_builders.ipynb · cell 6
def best_of_n(cid, n=4):
    for i in range(n):
        t = structured([{"role": "system", "content": SYSTEM}, {"role": "user", "content": contract(cid)}], Terms, temperature=0.7)
        if quote_is_in_doc(t.cap_quote, contract(cid)):
            return t, i + 1
    return None, n   # nothing passed: escalate to a person instead of guessing

t, tries = best_of_n("msa_12")
print(f"passed after {tries} tries:" if t else "no sample passed", t.cap_quote if t else "")

02_llms_for_builders.ipynb · cell 9
# Solution 2: governing law as a fixed list of choices
STATES = Literal["California", "Delaware", "New York", "Texas", "Florida", "Nevada", "Other"]
class LawOnly(BaseModel):
    governing_law: STATES

hits = sum(structured([{"role": "system", "content": SYSTEM}, {"role": "user", "content": contract(c)}], LawOnly).governing_law
           == labels()[c]["terms"]["governing_law"] for c in sample)
print(f"governing law with a fixed list: {hits}/{len(sample)}  (free text was {right['governing_law']}/{len(sample)})")
# A fixed list makes off-menu answers impossible ("State of Delaware", "DE", "Delaware law") and makes grading exact.
Traps
  • Asking for JSON in the prompt and hoping. Use the server's schema mode.
  • Free-text answers for fixed choices. Use an enum (Literal) or a small classifier, so the model can't answer off the menu.
  • Trusting the model's own confidence score. Use agreement across samples or an outside check instead.

Check yourself

Constrained decoding guarantees valid JSON. Why validate anyway?

Valid format is not correct content. The value can still be wrong, made up, or in the wrong unit. Check values against the source (for example, the quote must really appear in the document).

When does majority vote help and when does best-of-n help?

Best-of-n needs a checker (tests, rules, a schema plus source match). Majority vote works without a checker, but only for short answers you can compare, like labels or numbers.
