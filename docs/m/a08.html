Learning objective

1/54
  • Build a sample-then-select loop for bug fixes, grade "make it faster" with fast_p, and design an agent-system interface that gives useful feedback.
Part 1Why this lecture: code grades itself

Why code is easiest

2/54
  • The computer grades the work: tests pass or fail, code runs faster or slower.
  • So: sample many attempts, let tests pick the winner.
  • Give the agent clear feedback from the system (errors, a profiler), not a bare number.
  • Profiler: reports which functions used the most time; Python's built-in one is cProfile.

The three papers

3/54
Paper Task Main idea
CodeMonkeys (Ehrlich, Brown, Juravsky et al., Stanford/Oxford, 2025) Fix real GitHub issues (SWE-bench Verified) Scale serial + parallel compute, then select with tests and a model
KernelBench (Ouyang, Guo et al., Stanford/Princeton, 2025) Rewrite PyTorch code as fast GPU kernels A benchmark and metric (fast_p) for correct-and-fast code
Agent-System Interfaces (Wei, Nie et al., Stanford, ICML 2025) Write mappers for parallel programs A small language + AutoGuide feedback beat an RL autotuner

Two ways to spend test-time compute

4/54
Serial Parallel
More turns on one attempt More independent attempts
Iterate on execution feedback Sample with temperature > 0
No selection problem Must pick one at the end
Can get "stuck" after wrongly approving its work Each new attempt is a fresh start
  • Test-time compute: compute spent while answering, not while training.
  • All three papers use feedback loops; CodeMonkeys also samples in parallel.
Part 2CodeMonkeys (Ehrlich et al. 2025)

The problem: SWE-bench Verified

5/54
  • SWE-bench instance: a GitHub issue + the code repository. Goal: edit files so the issue is fixed.
  • Graded automatically by the repo's own test suite.
  • Verified split: issues humans judged solvable (clear description, tests that don't reject correct fixes).
  • Earlier work (Large Language Monkeys, same group): coverage rises log-linearly with samples, but no recipe for picking one.
  • Question: how would you design a system if scaling test-time compute were the main goal?

Three sub-tasks, three metrics

6/54
Sub-task Question Metric
Context Are the files that need editing in the prompt? Recall: share of problems with all needed files
Generation Is any sampled edit correct? Coverage: share of problems with ≥1 correct edit
Selection Did we submit a correct edit? Score: share of problems resolved
  • Changing one step affects the others: more edits can raise coverage but make selection harder (Figure 2).

System overview (Figure 1)

7/54
codebase → cheap model scans every file → rank → ~128k tokens of context
  → 10 parallel (testing state machine → editing state machine) → 10 (edit, test) pairs
  → run all tests on all edits → top-3 by votes → selection state machine → final edit
  • Main model: Claude 3.5 Sonnet (claude-3-5-sonnet-20241022).
  • File scanner: Qwen2.5-Coder-32B-Instruct, run locally.

Step 1: context by reading every file

8/54
  • SWE-bench repos hold millions of tokens: too big and too costly for a frontier model.
  • Trick: context is shared by all 10 downstream edits, so its cost is paid once.
  • Qwen2.5-Coder-32B reads every Python file (not test folders) and says relevant or not.
    • On average 2.94M tokens scanned per problem
    • Under 15% of total system cost
  • Rerunning it for each of 10 edits would make it the most expensive step.

Step 1b: ranking files

9/54
  • During the scan, write a short summary of how each relevant file relates to the issue.
  • Ranking prompt: each file's name, summary and token count; target about 60,000 tokens.
  • Claude can be non-deterministic even at temperature 0: run the ranking 3 times, average the ranks.
  • Include full files in rank order up to 128,000 tokens.
  • Result: on average 74,570 tokens, a 50.5x reduction vs all relevant files.
  • Recall at 128k limit: 92.6% of instances have all needed files (Figure 3).

Step 2: edits with their own tests

10/54
  • State machine: a fixed multi-turn loop where the model acts on execution feedback.
  • Each attempt writes an edit and a standalone Python test script that reproduces the issue (result via exit code).
  • Why tests: richer feedback for iterating, and imperfect verifiers for selection later.
  • Two back-to-back state machines:
    • Testing state machine: iterate until the test script works and flags the bug on unedited code
    • Editing state machine: write an aider-style edit diff; may still revise the test
  • Testing step skips the codebase files: shorter prompts, lower cache cost. Chat history cleared between the two.

Two-sided debugging

11/54
Test on code before the edit Test on code after the edit
Should fail (bug reproduced) Should pass (bug fixed)
  • Testing machine alone can produce tests that always fail, even on a correct fix.
  • Letting the editing machine revise the test checks both sides.

Serial vs parallel scaling (Figure 5)

12/54
  • Setup: 10 state-machine pairs per issue, each capped at 8 iterations.
  • Best: all 10 machines × 8 iterations → coverage 69.8%.
  • First few serial iterations help a lot.
  • After that: configurations with similar cost give similar coverage, however split.
  • But equal coverage ≠ equal final score: more parallel candidates make selection harder.

Cost breakdown (Table 1, USD)

13/54

  • Biggest single item: cache reads in edit generation (the codebase files in the prompt).

Step 3: selection, four methods

14/54
  • Majority voting with tests: run all 10 tests on all 10 edits; pick the edit passing most (ties → expected score of a random pick).
  • Model selection: model sees issue, context and all candidate diffs; picks one.
  • Model selection after top-3 filtering: same, but only the 3 edits passing most tests (ties → shorter diff).
  • Selection state machine after top-3: the model may write new tests to tell candidates apart; sees each test's output on every candidate and on unedited code; then picks.

Selection results (Figure 6)

  • Best method closes about half the gap from random to oracle; costs under 10% of the system.

Cheaper model check (Appendix A)

18/54
  • DeepSeek-V3 on a random 100-issue subset, same context files.
  • Claude 3.5 Sonnet: 45.74% (voting), 6.02% higher than DeepSeek-V3's best.
  • DeepSeek-V3 reaches 86.8% of Claude's score at a fraction of the cost (API over 10x cheaper).
  • Coverage for DeepSeek-V3 keeps rising with more compute.
  • Lesson: many cheap samples can work, if selection is good.

Limitations (Section 3)

19/54
  • Context: the file filter still misses needed files for 7.4% of instances.
    • Assumes the model already knows the repo; private or new repos may need a different retrieval step
  • Generation: feedback comes only from the model's own reproduction test, not regression tests.
    • Diversity only from temperature; parallel attempts don't know about each other
  • Selection: recovers only about half of the random-to-oracle gap; ignores the repo's existing tests.
Part 3KernelBench (Ouyang et al. 2025)

The problem: fast GPU kernels are hard to write

20/54
  • Kernel: a function that runs on the GPU; speed depends on hardware and tensor sizes.
  • FlashAttention: released in 2022, 5 years after the Transformer; 2 more years to move it to Hopper GPUs.
  • Experts use compiler feedback, profilers, hardware specs, tricks like tiling and fusion.
  • CUDA is low-resource: only 0.073% of The Stack v1.2 code corpus.
  • Question: can language models write correct and fast kernels?

Task format (Figure 1)

21/54
  • Input: PyTorch reference Model (an nn.Module) plus get_inputs() and get_init_inputs() for exact tensor shapes and types.
  • Output: ModelNew with custom kernels (e.g. inline CUDA via the PyTorch CUDA-C extension).
  • The model chooses which operations to optimize and how.
  • Any tool allowed: CUDA, PTX, CUTLASS, Triton, ThunderKittens.

Three levels, 250 tasks

22/54
Level Tasks What Hard because
1 100 Single operations: conv, matmul, losses, activations, norms PyTorch already calls expert, often closed-source kernels
2 100 Sequences of 3–6 operations (e.g. conv + ReLU + bias) Compilers are already good at fusion
3 50 Full architectures (e.g. AlexNet, MiniGPT) from GitHub Needs algorithm changes beyond a compiler

How it grades

23/54
  • Evaluation only: no reference kernels provided (users test on their own hardware).
  • Correctness: compare Model and ModelNew outputs on 5 random inputs.
  • Performance: wall-clock time of both, repeated trials.
  • Speedup = PyTorch time ÷ generated kernel time.

The metric: fast_p

24/54
  • Formula: fast_p = (1/N) · Σ 1(correct_i AND speedup_i > p)
    • N: number of tasks
    • 1(...): 1 if the task's kernel is correct and more than p times faster, else 0
  • fast_0 = plain correctness rate.
  • fast_1 = correct and faster than PyTorch. The paper's main setting.
  • Raise p as methods improve; p < 1 is useful for training (matching part of PyTorch's speed still counts).

One-shot baseline (Table 1, fast_1 vs PyTorch Eager, L40S)

25/54
Model Level 1 Level 2 Level 3
GPT-4o 4% 5% 0%
OpenAI o1 10% 24% 12%
DeepSeek V3 6% 4% 8%

Llama 3.1-405B Inst. 3% 0% 2%
  • One example in the prompt (a simple add), greedy decoding.
  • Speedup over PyTorch Eager in fewer than 20% of tasks on average.

Why kernels fail (Figure 2)

26/54
  • Execution failures: compile errors, CUDA memory violations, runtime errors.
  • Correctness errors: wrong output shape or values.
  • Reasoning models (o1, R1): under 55% incorrect; others: over 70%.
  • The gap is mostly fewer execution failures. All models struggle similarly with correctness.

Speed and hardware (Figure 3, Section 4.4)

27/54
  • fast_p falls as p rises; at p = 1, under 15% of kernels beat PyTorch at every level.
  • Reasoning models give more speedups.
  • Level 1 winners transfer across GPUs; Level 2 varies more.
    • DeepSeek R1 Level 2 fast_1: 36% on L40S, 47% on A10G
  • So one-shot kernels may not generalize across hardware.

Repeated sampling (Figure 4)

28/54
  • fast_p@k: share of tasks with at least one correct kernel p times faster, among k samples.
  • High temperature helps explore: DeepSeek-V3 Level 2 fast_1 goes from 4% (one-shot) to 37% at k = 100.
  • Limit: if the model almost never solves a task, more samples don't help.
    • DeepSeek-V3 never solved a group of 34 Level 1 convolution variants, even with 100 samples

Iterative refinement with feedback (Figure 5)

29/54
  • Each turn, the model gets:
    • G: its previous generation
    • E: compiler/execution feedback (errors, correctness, wall-clock time)
    • P: PyTorch profiler output (time per operator)
  • Run N = 10 turns; fast_p@N = best kernel so far.
  • Headline: DeepSeek-R1 Level 2 fast_1 from 36% to 72% with E + P (Figure 6).

  • Depends on the base model: R1 keeps gaining from E and P; V3 and Llama-3.1 70B don't always.

What feedback fixes (Table 9)

31/54
  • Execution feedback mostly fixes execution errors.
  • DeepSeek-R1 gets a correct kernel on over 90% of Level 1 and 2 tasks within 10 turns (fast_0: 95% and 92% with G+E+P).
  • Remaining failures: almost all functional incorrectness.
  • Likely reason: "wrong output" is less specific feedback than a compiler error message.

Hardware knowledge in the prompt (Section 5.2)

32/54
  • Few-shot examples of fusion (GeLU), tiling (matmul), and a minimal FlashAttention:
    • Overall fast_1 drops: models try bolder tricks and fail more; o1's outputs 25% longer
    • But o1 applies tiling on 77% of Level 1 GEMM variants; on Level 2 beats PyTorch on 11 problems with shared-memory tricks
  • Hardware specs (GPU type, bandwidth, TFLOPS, warps):
    • Little effect on Llama 3.1 70B and DeepSeek-V3
    • R1 tries tensor-core wmma instructions on about 50% of Level 1 matmuls; most fail to compile

Interesting kernels found (Section 6.1)

33/54
Trick Example Speedup
Operator fusion GELU 2.9x
Operator fusion Softsign 1.3x
Fused matmul + divide + sum + scale Level 2 task 2.6x
Shared memory Cosine similarity 2.8x

  • No successful tensor-core use found. Many fusion chances missed.

Limitations and future work

34/54
  • Refinement experiments sample at temperature 0 (stated limitation, Appendix C.3).
  • Models write raw CUDA; higher-level tools (ThunderKittens, CUTLASS, Triton) might make tensor cores easier.
  • GPUs only so far; other accelerators next.
  • CUDA data is scarce: more open, high-quality kernel data would help.
Part 4Agent-System Interfaces (Wei et al. 2025)

The problem: writing mappers

35/54
  • Task-based programs (Legion framework): computation split into tasks; a separate mapper decides placement.
  • Mapper: code that assigns tasks to processors and data to memories.
  • Good mappers can give order-of-magnitude speedups.
  • Writing one: hundreds of lines of low-level C++, days of expert tuning per application, input and machine.
  • Search space grows exponentially with tasks and data arguments.

The mapper search space

36/54
Decision Options
Processor selection GPU, CPU, or OpenMP, per task
Memory placement GPU FrameBuffer, ZeroCopy, or CPU system memory, per task and argument
Memory layout SOA vs AOS, C vs Fortran order, alignment (e.g. 128-byte)
Index mapping How partitioned tasks and data spread across processors

Agent-system interface (Figure 1)

37/54
  • Agent-system interface (ASI): the layer between the agent and the system; what the agent writes and what feedback it gets.
  • Two parts:
    • DSL (domain-specific language): high-level, declarative; a compiler turns it into C++
    • AutoGuide: turns raw execution output into explanations and suggestions
  • The DSL also defines the search space.

DSL vs C++ (Figure 2)

38/54
DSL mapper C++ mapper
Task task0 GPU; slice_task(...) with targets, domains, iterators
Region * ghost_region GPU ZCMEM 126 more lines of C++ omitted in the figure
Layout * * * C_order SOA Align==64 Imperative API calls for each constraint
Says what, not how Says how, step by step
  • Average 14x fewer lines of code with the DSL.
  • Every agent mapper that beat the experts was expressible in the DSL.

AutoGuide (Table 1)

39/54
Raw output Explain Suggest
"Assertion failed: stride does not match expected value." Memory layout is unexpected. Adjust the layout constraints or move tasks to different processor types.
"Execution time is 0.03s." N/A Move more tasks to GPU to reduce execution time.
  • Implemented by keyword matching over the raw output.
  • Why: language feedback beats scalars; raw output is opaque; expert heuristics are easy to say in words.

Generative optimization

40/54
  • Problem: triplet (Θ, ω, T).
    • Θ: all possible mappers (program text)
    • ω: the objective, written as text
    • T: runs a mapper, returns feedback f (measured performance) and g (a trace of how it was made)
  • Bandits, RL or Bayesian optimization struggle when Θ is huge and discrete (text).
  • Generative optimization: an LLM proposes the next program from text feedback.
  • Agent built in Trace; mapper split into independent code segments (like least-to-most prompting).

Setup

41/54
  • 9 benchmarks: Circuit, Stencil, Pennant (scientific), and 6 parallel matrix multiplication algorithms (Cannon's, SUMMA, PUMMA, Johnson's, Solomonik's, COSMA).
  • Baselines: expert-written mappers; random mappers (10 seeds); Trace and OPRO (10 iterations, 5 runs); OpenTuner (RL autotuner, scalar time feedback, big penalty for failures).
  • Hardware: one node, two 10-core Intel E5-2640 v4 CPUs, 256G memory, four NVIDIA Tesla P100 GPUs.
  • LLM: gpt-4o-2024-08-06. Crashing mappers score throughput 0.

Results (Figures 4, 5)

42/54
  • Best Trace mappers match or beat the expert mappers on all 9 benchmarks.
  • Up to 1.34x faster than experts (Circuit): two data collections moved from ZeroCopy to FrameBuffer memory.
  • COSMA: 1.31x, from better index mapping (less inter-GPU communication).
  • Random mappers: 74 of 90 (82.2%) crash with invalid mappings.
  • Trace ≈ OPRO, both far ahead of OpenTuner.
  • Trace vs OpenTuner: 11x at 10 iterations each; still 3.8x when OpenTuner runs 1000 iterations.

DSL ablation (Table 2)

43/54

DSL, single trial 80%
C++, iterative refine (≤10 rounds) 0%
DSL, iterative refine (≤10 rounds) 100%

  • The DSL has no training data at all; C++ has plenty. Still the DSL wins.
  • Why: smaller gap from English to code ("align to 64 bytes, Fortran order" = one DSL line), and 14x less code.

Limits

45/54
  • One framework (Legion), one node, 9 benchmarks.
  • Results report the best mapper across runs (normal for offline tuning, but optimistic).
  • The DSL might not express every optimization; the authors say they have not hit one.
  • AutoGuide's rules are hand-written keyword matches: someone must know the domain.

Selection in code

48/54
v = votes(ri)
order = sorted(range(len(v)), key=lambda i: -v[i])
top3 = order[:3]
distinct = len({EDITS[ri][i] for i in top3}) > 1
SEL[ri] = {"votes": order[0], "votes + judge": judge(ri, top3) if distinct else order[0]}
  • Line 1: for each edit, count the model tests it passes.
  • Line 2: sort edits by votes; ties keep sampling order.
  • Line 3: keep the 3 best.
  • Line 4: are the top 3 actually different files?
  • Line 5: vote pick vs judge pick (judge only if there is a real choice).
Part 6Our notebook, Part B: KernelBench on a CPU

Our version of KernelBench

49/54
  • 4 slow Python/NumPy functions instead of 250 GPU workloads.
  • Correctness: 5 random inputs, np.allclose (relative 1e-5, absolute 1e-6), same shape.
  • Speed: best of 3 runs on one large input, in a subprocess with a timeout.
  • Report fast_p for p = 0, 1, 2, 10, one-shot and after feedback.

Scalar vs profiler feedback

50/54
Scalar feedback Profiler + guide
"Result: correct=..., speedup=...x." Profile table of the code, plus a hint
Like a classic autotuner (OpenTuner) "Hot spot: per_user_totals takes ...% of the time"
Says how good, not why Says where the time goes and what to change
  • Our guide() is a tiny AutoGuide: crash → "fix this error first"; wrong → "compare on edge cases"; correct → profile + hot spot.
Part 7How this applies to us

Sample and select on the firm's machine

51/54
  • The firm's own scripts have bugs. A local agent can try several fixes and let tests choose.
  • Small local models make more mistakes per try. Fine, if a cheap exact check sorts good from bad.
  • CodeMonkeys' DeepSeek-V3 check: a cheaper model got 86.8% of the score. Selection matters more than the model.

Context once, reuse many times

52/54
  • CodeMonkeys scanned every file once with a local 32B model, then shared it across 10 attempts.
  • Same for the firm: index the contract set once, reuse it for every question.
  • Prompt caching makes the shared part cheap on repeated calls.

Design the interface, not just the prompt

53/54
  • Clear feedback can matter more than a bigger model: good news for small models on the firm's machine.
  • A narrow language helps: e.g. let the agent output {"clause": "liability_cap", "months": 12} instead of free text, then check it with code.
  • Write an AutoGuide for the firm: turn "check failed" into "the cap quote is not in the contract text; copy it exactly."

Common mistakes

54/54
  • Coverage = score → more samples raise coverage but can make selection harder. Measure both.
  • Model judge on the whole pool → cut to a top-3 short list with votes first.
  • Checking speed on one input → the agent can game it. Check correctness on several random inputs.
  • Bare scalar feedback → explain the error and suggest a change (AutoGuide).
  • Running model code in your own process → subprocess, timeout, fresh folder.

Check your understanding

What are CodeMonkeys' three steps and their metrics?

Context (recall), generation (coverage), and selection (final score).

Why could CodeMonkeys afford to have a model read every file?

The context is shared by all 10 attempts, so the scan is paid once. It was under 15% of total cost.

Why cut to a top-3 short list before asking a model judge?

A judge on the whole pool (52.0%) did worse than plain test voting (53.0%). With the vote-filtered short list it did better (55.6%, or 57.4% with the selection state machine).

What does fast_1 measure?

The share of tasks where the new code is correct and faster than the reference.

In KernelBench, what did execution feedback mostly fix, and what stayed hard?

It mostly fixed execution errors like compile and runtime failures. Functional correctness stayed hard.

What are the two parts of the agent-system interface in Wei et al.?

A small DSL that hides low-level C++ and defines the search space, and AutoGuide, which turns raw output into explanations and suggestions.

Why did the DSL beat C++ for code generation even with no training data?

It is much closer to the plain-English strategy and needs about 14x less code.

CS329A Lecture 13 (Nov 3)

Code is the easiest place to self-improve because the computer grades the work: tests pass or fail, and code runs faster or slower. Sample many attempts, let tests (even model-written ones) pick the winner, and give the agent clear feedback from the system, such as a profiler, instead of a bare number.

Run every model-written test on every candidate edit; the edit that passes the most tests wins.Source: Ehrlich et al. 2025
fast_p
Fraction of tasks where the new code is correct AND more than p times faster than the reference; fast_0 is plain correctness.Source: Ouyang et al. 2025
Agent-system interface
The layer between the agent and the system: what actions the agent can write and what feedback it gets back.Source: Wei et al. 2024
AutoGuide
A step that turns raw system output (errors, timings) into plain explanations and suggested changes for the agent.Source: Wei et al. 2024
Profiler
A tool that reports which functions used the most time; Python's built-in one is cProfile.Source: Python standard library

The papers

CodeMonkeys: Scaling Test-Time Compute for Software Engineering

Ehrlich, Brown, Juravsky et al. · 2025

What
A SWE-bench system in three steps: find relevant files (a cheap model scans every file), generate 10 parallel multi-turn attempts that each write a code edit and a test script and iterate on execution feedback, then select by running all model-written tests on all edits, keeping the top 3 by votes, and letting a model (which can write more tests) choose.
Result
57.4% of SWE-bench Verified resolved for about 2,300 USD, with 69.8% coverage (some attempt was correct). Selecting over an ensemble of edits from top leaderboard submissions reached 66.2%, above the best single member (62.8%). Different splits between serial and parallel compute often gave similar coverage. Model selection without the top-3 vote filter did worse than plain voting; with the filter it did better.
Takeaway
Treat generation and selection as separate problems and measure both (coverage vs final score). Cheap test-based voting to cut the pool, then a model judge on the short list, closes much of the gap.

KernelBench: Can LLMs Write Efficient GPU Kernels?

Ouyang, Guo et al. · 2025

What
250 PyTorch workloads in three levels. The model rewrites each as faster GPU code. Outputs are compared with the reference on 5 random inputs and both are timed. The metric fast_p is the fraction of tasks that are correct and faster than the reference by more than a factor p.
Result
One-shot, frontier reasoning models matched the PyTorch baseline in fewer than 20% of cases. With execution and profiler feedback over 10 refinement turns, the paper reports fast_1 rising from 12%, 36% and 12% to 43%, 72% and 18% across the three levels (the paper's Table 1 lists 2% as the Level 3 starting value; its introduction says 12%); the headline case is DeepSeek-R1 on Level 2, from 36% to 72%. Execution feedback mostly fixed execution errors; functional correctness stayed hard.
Takeaway
Grade speed and correctness together with one number (fast_p), check on several random inputs, and feed the model real execution and profiling output each turn.

Improving Parallel Program Performance with LLM Optimizers via Agent-System Interfaces

Wei, Nie et al. · 2024

What
An LLM optimizer (via the Trace framework, with GPT-4o) writes mappers that decide where tasks and data go in parallel programs. The agent-system interface has a small domain-specific language that hides low-level C++ and defines the search space, and AutoGuide, which turns raw execution output into explanations and suggested changes.
Result
Within 10 iterations it beat OpenTuner run for 1000 iterations, by 3.8x. Its mappers beat expert-written ones by up to 1.34x across nine benchmarks, cutting tuning from days to minutes. The DSL gave much higher code-generation success than raw C++.
Takeaway
Design what the agent sees and writes. A narrow action language plus feedback that explains errors and suggests fixes can matter more than a bigger model or more iterations.

Part A · CodeMonkeys at small scale

CodeMonkeys (Ehrlich, Brown, Juravsky et al. 2025, CodeMonkeys: Scaling Test-Time Compute for Software Engineering) solves real GitHub issues in three steps: 1. Context: find the files that matter. 2. Generation: run many attempts in parallel. Each attempt writes an edit and a test script. 3. Selection: run every model-written test on every edit, keep the top 3 edits by votes, and let a model pick among them.

Two numbers matter. Coverage: did any attempt fix the bug? Score: did the one we picked fix it? The gap between them is the selection problem.

A2. Run a test against a version of the file, safely

Every run gets a fresh folder with the file and one test script, in a separate process with a timeout. Exit code 0 means pass.

def run_test(repo, file_code, test_code, timeout=10):
    d = tempfile.mkdtemp(dir=WORK)
    open(os.path.join(d, repo["file"]), "w").write(file_code)
    open(os.path.join(d, "test_run.py"), "w").write(test_code)
    try:
        out = subprocess.run([sys.executable, "test_run.py"], cwd=d, capture_output=True, text=True, timeout=timeout)
        ok, msg = out.returncode == 0, (out.stderr or out.stdout).strip()[-300:]
    except subprocess.TimeoutExpired:
        ok, msg = False, "TIMEOUT"
    shutil.rmtree(d, ignore_errors=True)
    return ok, msg

A4. Coverage grows with the number of samples

Coverage@k is the chance that at least one of k attempts is correct. We estimate it with the unbiased pass@k formula. Large Language Monkeys (Brown et al. 2024) found coverage often grows roughly log-linearly with samples; CodeMonkeys reached 69.8% coverage on SWE-bench Verified.

a08_agentic_swe.ipynb · cell 6
COVERAGE = {}
for k in range(1, N_EDITS + 1):
    COVERAGE[k] = sum(pass_at_k(N_EDITS, sum(oks), k) for oks in HIDDEN.values()) / len(HIDDEN)
    print(f"coverage@{k}: {COVERAGE[k]:.0%}  " + "#" * round(40 * COVERAGE[k]))

We ask for 3 short test scripts per repo (12 calls). A useful test must fail on the buggy code; otherwise it doesn't reproduce the issue. We drop tests that pass on the original file (our own filter, in the spirit of CodeMonkeys running tests before and after an edit).

A6. Selection: test votes, then a model judge

  • Votes: each edit scores one point per model test it passes.
  • Top-3 + judge: keep the 3 best by votes and show their diffs to the model, which picks one. CodeMonkeys found that the model judge did worse than plain voting without the top-3 filter, and better with it.
a08_agentic_swe.ipynb · cell 8
def votes(ri):
    return [sum(run_test(REPOS[ri], e, t)[0] for t in GEN_TESTS[ri]) for e in EDITS[ri]]

def diff(a, b):
    return "".join(difflib.unified_diff(a.splitlines(True), b.splitlines(True), "before", "after", n=1))[:1500]

def judge(ri, idxs):
    r = REPOS[ri]
    cands = "\n\n".join(f"Candidate {n + 1}:\n```diff\n{diff(r['code'], EDITS[ri][i])}```" for n, i in enumerate(idxs))
    reply = ask(f"Issue:\n{r['issue']}\n\nThese are candidate fixes as diffs:\n\n{cands}\n\n"
                f"Which candidate fixes the issue correctly without breaking anything else? Reply with only the number (1-{len(idxs)}).",
                max_tokens=20)
    m = re.search(r"\d+", reply or "")
    n = int(m.group(0)) - 1 if m else 0
    return idxs[n] if 0 <= n < len(idxs) else idxs[0]

SEL = {}
for ri in range(len(REPOS)):
    v = votes(ri)
    order = sorted(range(len(v)), key=lambda i: -v[i])          # stable: ties keep the sampling order
    top3 = order[:3]
    distinct = len({EDITS[ri][i] for i in top3}) > 1
    SEL[ri] = {"votes": order[0], "votes + judge": judge(ri, top3) if distinct else order[0]}
    print(f"{REPOS[ri]['name']:11} votes {v} | vote pick {order[0]} | judge pick {SEL[ri]['votes + judge']}")

scores = {"random": sum(sum(o) / len(o) for o in HIDDEN.values()) / len(HIDDEN)}
for m in ("votes", "votes + judge"):
    scores[m] = sum(HIDDEN[ri][SEL[ri][m]] for ri in SEL) / len(SEL)
scores["oracle (coverage)"] = COVERAGE[N_EDITS]
for m, s in scores.items():
    print(f"{m:18} {s:.0%}")

Part B · KernelBench at CPU scale

KernelBench (Ouyang, Guo et al. 2025, KernelBench: Can LLMs Write Efficient GPU Kernels?) asks a model to rewrite a PyTorch program as faster GPU code. It checks the output against the reference on 5 random inputs and times both. Its metric is

$$\text{fast}_p = \frac{1}{N}\sum_i \mathbf{1}[\text{correct}_i \wedge \text{speedup}_i > p]$$

so fast_0 is just the correctness rate, and fast_1 means "correct and faster than the reference".

We have no GPU budget, so we do the same thing with slow Python/NumPy functions on the CPU.

B2. The evaluator: correctness on 5 random inputs, then timing

All of this runs in a subprocess with a timeout. Correctness uses np.allclose (relative 1e-5, absolute 1e-6) and requires the same shape. Timing takes the best of 3 runs on one large input. The profiler mode runs cProfile on the large input and returns the functions that used the most time.

a08_agentic_swe.ipynb · cell 10
KB_RUNNER = r'''
import copy, cProfile, json, os, pstats, sys, time, traceback
import numpy as np
mode, fn, ref_path, cand_path, gen_path = sys.argv[1:6]
def load(path):
    ns = {}
    exec(compile(open(path).read(), os.path.basename(path), "exec"), ns)
    return ns
gen = load(gen_path)["make_inputs"]
ref = load(ref_path)[fn]
res = {"correct": False, "speedup": 0.0, "error": None, "detail": None}
try:
    cand = load(cand_path)[fn]
    if mode == "profile":
        args = gen(np.random.default_rng(123), True, 0)
        prof = cProfile.Profile(); prof.enable(); cand(*args); prof.disable()
        st = pstats.Stats(prof).stats
        total = sum(v[2] for v in st.values()) or 1e-9
        rows = sorted(((k[2] if k[0] != "~" else "builtin " + k[2], os.path.basename(k[0]), v[1], v[2], v[3])
                       for k, v in st.items() if "disable" not in k[2]),
                      key=lambda r: -r[3])[:8]
        print(json.dumps({"total": total, "rows": rows})); sys.exit(0)
    for case in range(5):
        args = gen(np.random.default_rng(case), False, case)
        want, got = ref(*copy.deepcopy(args)), np.asarray(cand(*copy.deepcopy(args)), dtype=float)
        want = np.asarray(want, dtype=float)
        if got.shape != want.shape:
            res["detail"] = f"case {case}: shape {got.shape}, expected {want.shape}"; break
        if not np.allclose(got, want, rtol=1e-5, atol=1e-6):
            bad = ~np.isfinite(got)
            res["detail"] = (f"case {case}: {int(bad.sum())} non-finite values (inf/nan)" if bad.any() else
                             f"case {case}: max abs error {float(np.max(np.abs(got - want))):.3g}")
            break
    else:
        args = gen(np.random.default_rng(123), True, 0)
        def best(f):
            ts = []
            for _ in range(3):
                t0 = time.perf_counter(); out = f(*copy.deepcopy(args)); ts.append(time.perf_counter() - t0)
            return min(ts), out
        t_ref, want = best(ref)
        t_new, got = best(cand)
        if np.asarray(got).shape == np.asarray(want).shape and np.allclose(got, want, rtol=1e-5, atol=1e-6):
            res.update(correct=True, speedup=t_ref / max(t_new, 1e-9), t_ref=t_ref, t_new=t_new)
        else:
            res["detail"] = "wrong values on the large input"
except Exception as e:
    res["error"] = traceback.format_exc().strip().splitlines()[-1][:300]
print(json.dumps(res))
'''
RUNNER_PATH = os.path.join(WORK, "kb_runner.py")
open(RUNNER_PATH, "w").write(KB_RUNNER)

def kb_run(task, cand_code, mode="eval", timeout=90):
    d = tempfile.mkdtemp(dir=WORK)
    paths = {}
    for name, src in (("ref", task["ref"]), ("cand", cand_code), ("gen", task["gen"])):
        paths[name] = os.path.join(d, f"{name}.py")
        open(paths[name], "w").write(src)
    out = None
    try:
        out = subprocess.run([sys.executable, "-I", RUNNER_PATH, mode, task["fn"], paths["ref"], paths["cand"], paths["gen"]],
                             capture_output=True, text=True, timeout=timeout)
        return json.loads(out.stdout.strip().splitlines()[-1])
    except subprocess.TimeoutExpired:
        return {"correct": False, "speedup": 0.0, "error": f"timed out after {timeout}s", "detail": None}
    except Exception:
        return {"correct": False, "speedup": 0.0, "error": "runner failed: " + ((out.stderr or "")[-200:] if out else ""), "detail": None}
    finally:
        shutil.rmtree(d, ignore_errors=True)

def fast_p(results, p):
    return sum(r["correct"] and r["speedup"] > p for r in results) / len(results)

B3. The agent-system interface: scalar feedback vs. a profiler

Wei, Nie et al. (2024/2025, Improving Parallel Program Performance with LLM Optimizers via Agent-System Interfaces) found that what the optimizer sees matters as much as the model. Their interface had two parts: a small language that limits what the agent can write, and AutoGuide, which turns raw system output into plain advice. With it, an LLM optimizer beat OpenTuner (which only gets a number) within 10 iterations.

We compare two interfaces, 3 turns each (an attempt, then 2 rounds of feedback): - Scalar: the agent sees only "correct? speedup?", like a classic autotuner. - Profiler + guide: the agent also gets a cProfile table of the reference up front, and after each attempt a plain-language reading of the result: the error explained, which test case failed and how, and where its own code spends time.

a08_agentic_swe.ipynb · cell 11
def profile_text(task, code):
    p = kb_run(task, code, mode="profile")
    if "rows" not in p:
        return f"(profiler failed: {p.get('error')})", None
    lines = [f"{'function':40} {'calls':>8} {'own time s':>10} {'with callees s':>14}"]
    lines += [f"{f[:40]:40} {n:>8} {tt:>10.4f} {ct:>14.4f}" for f, _, n, tt, ct in p["rows"]]
    hot = p["rows"][0]
    return "\n".join(lines), (hot[0], hot[3] / p["total"], hot[2])

def guide(task, code, r):
    """A tiny AutoGuide: turn raw results into actionable advice."""
    if r.get("error"):
        return f"Your code crashed: {r['error']}. Fix this error first and keep the same function name."
    if not r["correct"]:
        return (f"Your code returns wrong results: {r['detail']}. Compare with the reference on that kind of input "
                "(edge cases, very large or very small values, window sizes, shapes).")
    table, hot = profile_text(task, code)
    tip = (f"Hot spot: `{hot[0]}` takes {hot[1]:.0%} of the time ({hot[2]} calls). If it loops over array elements in Python, "
           "replace the loop with whole-array NumPy operations." if hot else "")
    return f"Correct. Speedup {r['speedup']:.2f}x over the reference.\nProfile of your version:\n{table}\n{tip}"

def scalar_feedback(task, code, r):
    return f"Result: correct={r['correct']}, speedup={r['speedup']:.2f}x."

def optimize(task, interface, turns=3):
    intro = (f"Here is a slow Python function:\n```python\n{task['ref']}```\n"
             f"Write a faster version with the SAME function name `{task['fn']}` and the same arguments. Use NumPy. "
             "It must return the same values (within 1e-6) for any valid input. Return the complete code in one ```python block.")
    if interface == "profiler":
        intro += "\n\nProfiler output for the reference on a large input:\n" + profile_text(task, task["ref"])[0]
    msgs, best, history = [{"role": "user", "content": intro}], {"correct": False, "speedup": 0.0}, []
    for turn in range(turns):
        reply = chat(msgs, temperature=0.3, max_tokens=900).content or ""
        code = extract_code(reply)
        r = kb_run(task, code)
        if r["correct"] and r["speedup"] > best["speedup"]:
            best = r
        history.append(dict(best))                                # best-so-far after each turn
        if r["correct"] and r["speedup"] >= 20:                    # good enough: save calls
            history += [dict(best)] * (turns - turn - 1)
            break
        fb = guide(task, code, r) if interface == "profiler" else scalar_feedback(task, code, r)
        msgs += [{"role": "assistant", "content": reply}, {"role": "user", "content": fb + "\nWrite an improved version. Return the complete code in one ```python block."}]
    return history

RUNS = {}
for interface in ("scalar", "profiler"):
    RUNS[interface] = [optimize(t, interface) for t in KTASKS]     # up to 4 tasks x 3 turns = 12 calls per interface
    for t, h in zip(KTASKS, RUNS[interface]):
        print(f"{interface:8} {t['fn']:15} best speedup by turn: {[round(x['speedup'], 1) if x['correct'] else 'x' for x in h]}")

Traps
  • High coverage is not a high score. More parallel samples can make selection harder.
  • Model-written tests can be wrong. Drop tests that already pass on the buggy code, and don't trust a single test.
  • A model judge on the whole pool can do worse than plain voting; filter to a short list first.
  • Checking speed on one input invites gaming. Check correctness on several random inputs, including edge cases like large values.
  • A speedup threshold of 1x is easy when the baseline is a Python loop and hard when the baseline is already tuned. Pick p for your baseline.
  • Timing is noisy. Take the best of several runs and keep timing in a separate process.
  • Never run model-written code in your own process. Use a subprocess with a timeout and a fresh folder.

What are CodeMonkeys' three subtasks?

Context (find relevant files), generation (sample edits and tests), and selection (choose one edit).

How does CodeMonkeys select an edit?

It runs model-written tests on all edits, keeps the top 3 by votes, and a model picks among them, optionally writing more tests.

What does fast_1 measure?

The fraction of tasks where the generated code is correct and faster than the reference.

What did profiler and execution feedback do for DeepSeek-R1 on KernelBench Level 2?

Raised fast_1 from 36% to 72% over 10 turns of refinement.

What are the two parts of the agent-system interface in Wei et al.?

A domain-specific language for mappers, and AutoGuide, which turns raw execution output into actionable feedback.
