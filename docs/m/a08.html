Part 2 · A08

Agentic frameworks for software engineering

Open in Colab
12 min readPlain-English lesson, then the deeper material

Why code is the easiest place for agents to improve themselves. You'll see how CodeMonkeys picks the best of many bug fixes and how KernelBench grades faster code.

The big idea

Most work is hard to grade. Was this memo good? People disagree. Code is different. The computer grades it for you. Tests pass or fail. The program runs faster or slower.

That makes software the friendliest place for an agent to improve itself. Try many fixes. Let tests pick the winner. Give the agent clear feedback from the system, not just a bare score.

Think of a mechanic with a test track. They can try three repairs, drive each car around the track, and keep the one that runs best. No one has to argue about which repair "feels" right.

Why it matters for us

  • A firm's own software, like a script that pulls clauses out of contracts, has bugs. A local agent can try several fixes overnight and let tests choose.
  • Small local models make more mistakes per try. That's fine if a cheap, exact check can sort good tries from bad ones.
  • How you show results to the agent matters a lot. Clear feedback can beat a bigger model. That is good news for anyone running small models on their own machines.

How it works, step by step

  1. Split the job into three parts (the CodeMonkeys paper, 2025). CodeMonkeys fixes real bugs from GitHub (a site where code projects live). Step one is context: find the files that matter. Step two is generation: run 10 attempts in parallel. Each attempt writes a code edit and a test script, then improves it using the results of running it. Step three is selection: choose one edit.

  2. Measure two numbers, not one. Coverage is the share of problems where at least one attempt was correct. Score is the share where the attempt you picked was correct. The gap between them is the selection problem. CodeMonkeys reached 69.8% coverage but a final score of 57.4%. Some right answers were made but not chosen.

  3. Pick with test votes, then a judge. Run every model-written test on every edit. Each edit gets one vote per test it passes. Keep the top 3 by votes. Then let a model look at those 3 and choose. A surprising finding: a model judge looking at the whole pool did worse than plain voting. With the top-3 short list first, it did better.

  4. Grade speed and correctness together (the KernelBench paper, 2025). KernelBench asks a model to rewrite 250 programs as faster code for a GPU (a graphics chip used for AI math). Each rewrite is checked against the original on 5 random inputs, and both are timed. The score is fast_p: the share of tasks where the new code is correct and more than p times faster. So fast_1 means "correct and faster than the original". One-shot, the best models matched the original in fewer than 20% of cases.

  5. Give useful feedback. A profiler is a tool that reports which parts of a program use the most time. When KernelBench fed models real run results and profiler output over 10 rounds, one strong model went from 36% to 72% on fast_1 for the middle level. Most of that gain came from fixing errors, not from clever speedups.

  6. Design what the agent sees (the agent-system interfaces paper, 2024). This paper built two things. A small, narrow language for the agent to write in, which hides messy low-level code. And AutoGuide, a step that turns raw error messages and timings into plain advice. With this, an AI optimizer beat a classic tuning tool within 10 tries.

issue -> 10 attempts (edit + test each) -> run all tests on all edits
      -> top 3 by votes -> model judge picks 1 -> submit

Worked example

The firm has a script that finds the liability cap in a contract and checks it against the playbook rule: "at most 12 months of fees". A bug report comes in. "Caps written as 'twelve (12) months' are missed."

Generation: the agent makes four attempts. Each returns a fixed file and a short test.

Filter the tests first. A good test must fail on the old, buggy code. Otherwise it doesn't reproduce the bug. Drop any test that already passes on the original.

Voting: run the surviving tests on all four edits. Edit A passes 3 tests. Edit B passes 3. Edit C passes 1. Edit D crashes. Keep the top 3: A, B, C.

Judge: the model reads the three diffs (the lines each edit changed) and picks A, because B also changes unrelated code.

Grading: a hidden test the agent never saw confirms whether A truly fixes the bug. That tells us both coverage (did any edit work?) and score (did the chosen one work?).

Every run happens in a fresh folder, in a separate process, with a time limit. Model-written code never runs inside your own program.

Common mistakes

  • Confusing coverage with score. More attempts raise coverage, but can make choosing harder. Measure both.
  • Trusting model-written tests blindly. They can be wrong. Drop tests that pass on the buggy code, and never rely on one test alone.
  • Checking speed on a single input. The agent can game it, for example code that only works for the timing input. Check correctness on several random inputs.
  • Picking the wrong bar for "fast". Beating a slow Python loop is easy. Beating already-tuned code is hard. Choose p to fit your starting point.
  • Trusting one timing run. Timing is noisy. Take the best of several runs.

Code is the easiest place to self-improve because the computer grades the work: tests pass or fail, and code runs faster or slower. Sample many attempts, let tests (even model-written ones) pick the winner, and give the agent clear feedback from the system, such as a profiler, instead of a bare number.

Key terms

Coverage
Fraction of problems where at least one generated attempt is correct; the best any selector can do.Source: Ehrlich et al. 2025
Serial vs parallel test-time compute
Serial: more turns of fixing one attempt. Parallel: more independent attempts.Source: Ehrlich et al. 2025
Test-based voting
Run every model-written test on every candidate edit; the edit that passes the most tests wins.Source: Ehrlich et al. 2025
fast_p
Fraction of tasks where the new code is correct AND more than p times faster than the reference; fast_0 is plain correctness.Source: Ouyang et al. 2025
Agent-system interface
The layer between the agent and the system: what actions the agent can write and what feedback it gets back.Source: Wei et al. 2024
AutoGuide
A step that turns raw system output (errors, timings) into plain explanations and suggested changes for the agent.Source: Wei et al. 2024
Profiler
A tool that reports which functions used the most time; Python's built-in one is cProfile.Source: Python standard library

The papers

CodeMonkeys: Scaling Test-Time Compute for Software Engineering

Ehrlich, Brown, Juravsky et al. · 2025

What
A SWE-bench system in three steps: find relevant files (a cheap model scans every file), generate 10 parallel multi-turn attempts that each write a code edit and a test script and iterate on execution feedback, then select by running all model-written tests on all edits, keeping the top 3 by votes, and letting a model (which can write more tests) choose.
Result
57.4% of SWE-bench Verified resolved for about 2,300 USD, with 69.8% coverage (some attempt was correct). Selecting over an ensemble of edits from top leaderboard submissions reached 66.2%, above the best single member (62.8%). Different splits between serial and parallel compute often gave similar coverage. Model selection without the top-3 vote filter did worse than plain voting; with the filter it did better.
Takeaway
Treat generation and selection as separate problems and measure both (coverage vs final score). Cheap test-based voting to cut the pool, then a model judge on the short list, closes much of the gap.

KernelBench: Can LLMs Write Efficient GPU Kernels?

Ouyang, Guo et al. · 2025

What
250 PyTorch workloads in three levels. The model rewrites each as faster GPU code. Outputs are compared with the reference on 5 random inputs and both are timed. The metric fast_p is the fraction of tasks that are correct and faster than the reference by more than a factor p.
Result
One-shot, frontier reasoning models matched the PyTorch baseline in fewer than 20% of cases. With execution and profiler feedback over 10 refinement turns, the paper reports fast_1 rising from 12%, 36% and 12% to 43%, 72% and 18% across the three levels (the paper's Table 1 lists 2% as the Level 3 starting value; its introduction says 12%); the headline case is DeepSeek-R1 on Level 2, from 36% to 72%. Execution feedback mostly fixed execution errors; functional correctness stayed hard.
Takeaway
Grade speed and correctness together with one number (fast_p), check on several random inputs, and feed the model real execution and profiling output each turn.

Improving Parallel Program Performance with LLM Optimizers via Agent-System Interfaces

Wei, Nie et al. · 2024

What
An LLM optimizer (via the Trace framework, with GPT-4o) writes mappers that decide where tasks and data go in parallel programs. The agent-system interface has a small domain-specific language that hides low-level C++ and defines the search space, and AutoGuide, which turns raw execution output into explanations and suggested changes.
Result
Within 10 iterations it beat OpenTuner run for 1000 iterations, by 3.8x. Its mappers beat expert-written ones by up to 1.34x across nine benchmarks, cutting tuning from days to minutes. The DSL gave much higher code-generation success than raw C++.
Takeaway
Design what the agent sees and writes. A narrow action language plus feedback that explains errors and suggests fixes can matter more than a bigger model or more iterations.

Part A · CodeMonkeys at small scale

CodeMonkeys (Ehrlich, Brown, Juravsky et al. 2025, CodeMonkeys: Scaling Test-Time Compute for Software Engineering) solves real GitHub issues in three steps: 1. Context: find the files that matter. 2. Generation: run many attempts in parallel. Each attempt writes an edit and a test script. 3. Selection: run every model-written test on every edit, keep the top 3 edits by votes, and let a model pick among them.

Two numbers matter. Coverage: did any attempt fix the bug? Score: did the one we picked fix it? The gap between them is the selection problem.

A2. Run a test against a version of the file, safely

Every run gets a fresh folder with the file and one test script, in a separate process with a timeout. Exit code 0 means pass.

a08_agentic_swe.ipynb · cell 4
def run_test(repo, file_code, test_code, timeout=10):
    d = tempfile.mkdtemp(dir=WORK)
    open(os.path.join(d, repo["file"]), "w").write(file_code)
    open(os.path.join(d, "test_run.py"), "w").write(test_code)
    try:
        out = subprocess.run([sys.executable, "test_run.py"], cwd=d, capture_output=True, text=True, timeout=timeout)
        ok, msg = out.returncode == 0, (out.stderr or out.stdout).strip()[-300:]
    except subprocess.TimeoutExpired:
        ok, msg = False, "TIMEOUT"
    shutil.rmtree(d, ignore_errors=True)
    return ok, msg

# Prove each task is sound: the hidden test FAILS on the buggy code and PASSES on the reference fix.
sound = {r["name"]: (not run_test(r, r["code"], r["test"])[0], run_test(r, r["fixed"], r["test"])[0]) for r in REPOS}
print("(fails on bug, passes on fix):", sound)

A3. Generation: 4 edits per repo, in parallel

Each attempt sees the issue and the file and returns the whole fixed file. 16 calls, 2 at a time.

a08_agentic_swe.ipynb · cell 5
N_EDITS = 4

def edit_prompt(r):
    return (f"You are fixing a bug in a small Python repository.\n\nIssue:\n{r['issue']}\n\nFile `{r['file']}`:\n```python\n{r['code']}```\n\n"
            "Rewrite the file so the issue is fixed. Keep the same function and class names. "
            "Return the complete fixed file in one ```python block.")

def gen_edit(r):
    return extract_code(ask(edit_prompt(r), temperature=0.8, max_tokens=900))

jobs = [ri for ri in range(len(REPOS)) for _ in range(N_EDITS)]
with ThreadPoolExecutor(2) as ex:
    edits = list(ex.map(lambda ri: gen_edit(REPOS[ri]), jobs))
EDITS = {ri: [e for j, e in zip(jobs, edits) if j == ri] for ri in range(len(REPOS))}

# Ground truth, for grading only: does each edit pass the hidden test?
HIDDEN = {ri: [run_test(REPOS[ri], e, REPOS[ri]["test"])[0] for e in EDITS[ri]] for ri in EDITS}
for ri, oks in HIDDEN.items():
    print(f"{REPOS[ri]['name']:11} edits passing the hidden test: {oks}")

A4. Coverage grows with the number of samples

Coverage@k is the chance that at least one of k attempts is correct. We estimate it with the unbiased pass@k formula. Large Language Monkeys (Brown et al. 2024) found coverage often grows roughly log-linearly with samples; CodeMonkeys reached 69.8% coverage on SWE-bench Verified.

a08_agentic_swe.ipynb · cell 6
COVERAGE = {}
for k in range(1, N_EDITS + 1):
    COVERAGE[k] = sum(pass_at_k(N_EDITS, sum(oks), k) for oks in HIDDEN.values()) / len(HIDDEN)
    print(f"coverage@{k}: {COVERAGE[k]:.0%}  " + "#" * round(40 * COVERAGE[k]))

A5. The model writes its own tests

We ask for 3 short test scripts per repo (12 calls). A useful test must fail on the buggy code; otherwise it doesn't reproduce the issue. We drop tests that pass on the original file (our own filter, in the spirit of CodeMonkeys running tests before and after an edit).

a08_agentic_swe.ipynb · cell 7
N_TESTS = 3

def test_prompt(r):
    module = r["file"][:-3]
    return (f"Issue:\n{r['issue']}\n\nFile `{r['file']}`:\n```python\n{r['code']}```\n\n"
            f"Write a short Python test script that does `from {module} import ...` and uses plain assert statements to check "
            "the behavior the issue asks for. It must FAIL on the current buggy code and PASS once the bug is fixed. "
            "No test framework, no explanation. Return only code in one ```python block.")

tjobs = [ri for ri in range(len(REPOS)) for _ in range(N_TESTS)]
with ThreadPoolExecutor(2) as ex:
    tests = list(ex.map(lambda ri: extract_code(ask(test_prompt(REPOS[ri]), temperature=0.8, max_tokens=500)), tjobs))
GEN_TESTS = {}
for ri in range(len(REPOS)):
    mine = [t for j, t in zip(tjobs, tests) if j == ri]
    GEN_TESTS[ri] = [t for t in mine if not run_test(REPOS[ri], REPOS[ri]["code"], t)[0]]   # keep tests that fail on the bug
    print(f"{REPOS[ri]['name']:11} model tests kept: {len(GEN_TESTS[ri])}/{len(mine)}")

A6. Selection: test votes, then a model judge

  • Votes: each edit scores one point per model test it passes.
  • Top-3 + judge: keep the 3 best by votes and show their diffs to the model, which picks one. CodeMonkeys found that the model judge did worse than plain voting without the top-3 filter, and better with it.
a08_agentic_swe.ipynb · cell 8
def votes(ri):
    return [sum(run_test(REPOS[ri], e, t)[0] for t in GEN_TESTS[ri]) for e in EDITS[ri]]

def diff(a, b):
    return "".join(difflib.unified_diff(a.splitlines(True), b.splitlines(True), "before", "after", n=1))[:1500]

def judge(ri, idxs):
    r = REPOS[ri]
    cands = "\n\n".join(f"Candidate {n + 1}:\n```diff\n{diff(r['code'], EDITS[ri][i])}```" for n, i in enumerate(idxs))
    reply = ask(f"Issue:\n{r['issue']}\n\nThese are candidate fixes as diffs:\n\n{cands}\n\n"
                f"Which candidate fixes the issue correctly without breaking anything else? Reply with only the number (1-{len(idxs)}).",
                max_tokens=20)
    m = re.search(r"\d+", reply or "")
    n = int(m.group(0)) - 1 if m else 0
    return idxs[n] if 0 <= n < len(idxs) else idxs[0]

SEL = {}
for ri in range(len(REPOS)):
    v = votes(ri)
    order = sorted(range(len(v)), key=lambda i: -v[i])          # stable: ties keep the sampling order
    top3 = order[:3]
    distinct = len({EDITS[ri][i] for i in top3}) > 1
    SEL[ri] = {"votes": order[0], "votes + judge": judge(ri, top3) if distinct else order[0]}
    print(f"{REPOS[ri]['name']:11} votes {v} | vote pick {order[0]} | judge pick {SEL[ri]['votes + judge']}")

scores = {"random": sum(sum(o) / len(o) for o in HIDDEN.values()) / len(HIDDEN)}
for m in ("votes", "votes + judge"):
    scores[m] = sum(HIDDEN[ri][SEL[ri][m]] for ri in SEL) / len(SEL)
scores["oracle (coverage)"] = COVERAGE[N_EDITS]
for m, s in scores.items():
    print(f"{m:18} {s:.0%}")

Part B · KernelBench at CPU scale

KernelBench (Ouyang, Guo et al. 2025, KernelBench: Can LLMs Write Efficient GPU Kernels?) asks a model to rewrite a PyTorch program as faster GPU code. It checks the output against the reference on 5 random inputs and times both. Its metric is

$$\text{fast}_p = \frac{1}{N}\sum_i \mathbf{1}[\text{correct}_i \wedge \text{speedup}_i > p]$$

so fast_0 is just the correctness rate, and fast_1 means "correct and faster than the reference".

We have no GPU budget, so we do the same thing with slow Python/NumPy functions on the CPU.

B1. Four slow functions

B2. The evaluator: correctness on 5 random inputs, then timing

All of this runs in a subprocess with a timeout. Correctness uses np.allclose (relative 1e-5, absolute 1e-6) and requires the same shape. Timing takes the best of 3 runs on one large input. The profiler mode runs cProfile on the large input and returns the functions that used the most time.

KB_RUNNER = r'''

import numpy as np
mode, fn, ref_path, cand_path, gen_path = sys.argv[1:6]

        rows = sorted(((k[2] if k[0] != "~" else "builtin " + k[2], os.path.basename(k[0]), v[1], v[2], v[3])
                       for k, v in st.items() if "disable" not in k[2]),
                      key=lambda r: -r[3])[:8]

        args = gen(np.random.default_rng(case), False, case)
        want, got = ref(*copy.deepcopy(args)), np.asarray(cand(*copy.deepcopy(args)), dtype=float)
        want = np.asarray(want, dtype=float)
        if got.shape != want.shape:
            res["detail"] = f"case {case}: shape {got.shape}, expected {want.shape}"; break
        if not np.allclose(got, want, rtol=1e-5, atol=1e-6):
            bad = ~np.isfinite(got)
            res["detail"] = (f"case {case}: {int(bad.sum())} non-finite values (inf/nan)" if bad.any() else
                             f"case {case}: max abs error {float(np.max(np.abs(got - want))):.3g}")
            break
    else:
        args = gen(np.random.default_rng(123), True, 0)
        def best(f):
            ts = []
            for _ in range(3):
                t0 = time.perf_counter(); out = f(*copy.deepcopy(args)); ts.append(time.perf_counter() - t0)
            return min(ts), out
        t_ref, want = best(ref)
        t_new, got = best(cand)
        if np.asarray(got).shape == np.asarray(want).shape and np.allclose(got, want, rtol=1e-5, atol=1e-6):

            res["detail"] = "wrong values on the large input"

def kb_run(task, cand_code, mode="eval", timeout=90):
    d = tempfile.mkdtemp(dir=WORK)
    paths = {}
    for name, src in (("ref", task["ref"]), ("cand", cand_code), ("gen", task["gen"])):
        paths[name] = os.path.join(d, f"{name}.py")
        open(paths[name], "w").write(src)
    out = None
    try:
        out = subprocess.run([sys.executable, "-I", RUNNER_PATH, mode, task["fn"], paths["ref"], paths["cand"], paths["gen"]],
                             capture_output=True, text=True, timeout=timeout)

    except subprocess.TimeoutExpired:

B3. The agent-system interface: scalar feedback vs. a profiler

Wei, Nie et al. (2024/2025, Improving Parallel Program Performance with LLM Optimizers via Agent-System Interfaces) found that what the optimizer sees matters as much as the model. Their interface had two parts: a small language that limits what the agent can write, and AutoGuide, which turns raw system output into plain advice. With it, an LLM optimizer beat OpenTuner (which only gets a number) within 10 iterations.

We compare two interfaces, 3 turns each (an attempt, then 2 rounds of feedback): - Scalar: the agent sees only "correct? speedup?", like a classic autotuner. - Profiler + guide: the agent also gets a cProfile table of the reference up front, and after each attempt a plain-language reading of the result: the error explained, which test case failed and how, and where its own code spends time.

def profile_text(task, code):
    p = kb_run(task, code, mode="profile")
    if "rows" not in p:
        return f"(profiler failed: {p.get('error')})", None
    lines = [f"{'function':40} {'calls':>8} {'own time s':>10} {'with callees s':>14}"]
    lines += [f"{f[:40]:40} {n:>8} {tt:>10.4f} {ct:>14.4f}" for f, _, n, tt, ct in p["rows"]]
    hot = p["rows"][0]
    return "\n".join(lines), (hot[0], hot[3] / p["total"], hot[2])

def guide(task, code, r):
    """A tiny AutoGuide: turn raw results into actionable advice."""
    if r.get("error"):
        return f"Your code crashed: {r['error']}. Fix this error first and keep the same function name."
    if not r["correct"]:
        return (f"Your code returns wrong results: {r['detail']}. Compare with the reference on that kind of input "
                "(edge cases, very large or very small values, window sizes, shapes).")
    table, hot = profile_text(task, code)
    tip = (f"Hot spot: `{hot[0]}` takes {hot[1]:.0%} of the time ({hot[2]} calls). If it loops over array elements in Python, "
           "replace the loop with whole-array NumPy operations." if hot else "")
    return f"Correct. Speedup {r['speedup']:.2f}x over the reference.\nProfile of your version:\n{table}\n{tip}"

def scalar_feedback(task, code, r):
    return f"Result: correct={r['correct']}, speedup={r['speedup']:.2f}x."

def optimize(task, interface, turns=3):
    intro = (f"Here is a slow Python function:\n```python\n{task['ref']}```\n"
             f"Write a faster version with the SAME function name `{task['fn']}` and the same arguments. Use NumPy. "
             "It must return the same values (within 1e-6) for any valid input. Return the complete code in one ```python block.")
    if interface == "profiler":
        intro += "\n\nProfiler output for the reference on a large input:\n" + profile_text(task, task["ref"])[0]
    msgs, best, history = [{"role": "user", "content": intro}], {"correct": False, "speedup": 0.0}, []
    for turn in range(turns):
        reply = chat(msgs, temperature=0.3, max_tokens=900).content or ""
        code = extract_code(reply)
        r = kb_run(task, code)
        if r["correct"] and r["speedup"] > best["speedup"]:
            best = r
        history.append(dict(best))                                # best-so-far after each turn
        if r["correct"] and r["speedup"] >= 20:                    # good enough: save calls
            history += [dict(best)] * (turns - turn - 1)
            break
        fb = guide(task, code, r) if interface == "profiler" else scalar_feedback(task, code, r)
        msgs += [{"role": "assistant", "content": reply}, {"role": "user", "content": fb + "\nWrite an improved version. Return the complete code in one ```python block."}]
    return history

RUNS = {}
for interface in ("scalar", "profiler"):
    RUNS[interface] = [optimize(t, interface) for t in KTASKS]     # up to 4 tasks x 3 turns = 12 calls per interface
    for t, h in zip(KTASKS, RUNS[interface]):
        print(f"{interface:8} {t['fn']:15} best speedup by turn: {[round(x['speedup'], 1) if x['correct'] else 'x' for x in h]}")

Traps
  • High coverage is not a high score. More parallel samples can make selection harder.
  • Model-written tests can be wrong. Drop tests that already pass on the buggy code, and don't trust a single test.
  • A model judge on the whole pool can do worse than plain voting; filter to a short list first.
  • Checking speed on one input invites gaming. Check correctness on several random inputs, including edge cases like large values.
  • A speedup threshold of 1x is easy when the baseline is a Python loop and hard when the baseline is already tuned. Pick p for your baseline.
  • Timing is noisy. Take the best of several runs and keep timing in a separate process.
  • Never run model-written code in your own process. Use a subprocess with a timeout and a fresh folder.
