Learning objective

1/32
  • Choose what goes into the context window each turn, and trim it without losing the full record.
Part 1Why long context is hard

A note about context length

2/32
  • Context window: all the text the model can see in one call.
  • Nothing in the transformer or linear attention sets a hard length limit...
  • ...except how the model handles positional embeddings (the vectors that encode each token's position).
  • The model must learn to use those positions, so in practice it is limited to the context length it was trained on.

Long context costs time and memory

3/32
  • Full attention compares every token with every earlier token: work grows with the square of the length, O(n²).
  • The KV cache (stored keys and values of earlier tokens) grows with every token in the prompt.
  • On a local GPU, both show up as slower answers and more memory used. (Mechanics: module 02.)

Linear attention struggles more with long context

4/32
  • RULER benchmark: "needle in a haystack" (NIAH) tests hidden in essays.
Task What the model must find
Single NIAH "One of the special magic numbers for long-context is: 12345." → 12345
Multi-keys NIAH Same, with a second distractor key (large-model: 54321)
Multi-values NIAH Two numbers for the same key → "12345 54321"

RULER: accuracy vs length

5/32
Model (architecture) 1K 2K 4K 8K
Llama2-7b (transformer) about 96 about 91 about 85 about 0
RWKV-v5-7b (linear / recurrent) about 87 about 73 about 51 about 12
Mamba-2.8b-slimpj (linear / recurrent) about 62 about 52 about 16 about 1
  • Up to 4K, the transformer holds up far better. At 8K, all three are low or near zero.
Part 2Context engineering

Prompt engineering vs context engineering

6/32
Prompt engineering (single-turn queries) Context engineering (agents)
Context window holds a system prompt and a user message Many possible inputs: docs, tools, memory files, instructions, domain knowledge, message history
One call → one assistant message Curation: pick what goes in the window each turn
The model's tool calls return results that join the history for the next turn
  • Figure from Anthropic, "Effective context engineering for AI agents".

What goes in the context of an agent?

7/32
  • System prompt
  • Message history
  • Memories
  • Tool call results
  • Attached files

Why not just put everything? Context rot

8/32
  • Context rot: answer quality drops as the context grows, well before the window is full.
  • OOLONG (arXiv 2511.02817) tests reasoning over many pieces spread through a long input:
    • "Were there more news articles about the economy in September or August?" over dated articles → "September".
    • "How many times does the character Jester cast Healing Word?" over transcripts of 12 hours of dialogue → "two times".
  • The model must classify and count many items, not find one needle.

OOLONG results: every model gets worse

9/32
OOLONG-synth 8K 128K 256K
gpt-5 about 0.85 about 0.46 about 0.40
gemini-2.5-pro about 0.88 about 0.25 about 0.13
claude-sonnet-4 about 0.74 about 0.48 about 0.47 (about 0.42 at 512K)
llama-4-maverick, deepseek-r1 about 0.15 below the random baseline (about 0.22)
  • Decline starts at the shortest length tested, 8K tokens.
  • OOLONG-real (64K–512K): gemini-2.5-pro is best, about 0.60 at 64K → about 0.30 at 512K.

There is no one way to build the context

10/32
  • You will experiment with it (in the course, homework 1).
  • The lecture gives practical tips instead of a recipe:
    • Avoid bloat.
    • Add sequentially.
    • Evaluate context choices empirically.
    • Compact carefully, or change the approach (recursive LMs).

Avoid bloat: retrieve, don't paste

12/32
  • Use retrieval to bring back only the most relevant memories or files.
  • Retrieval chain: prompt → embedding model → vector DB search → reranking model → LLM → response.
  • Full details in module 04 (RAG).

Add sequentially: keep the KV cache valid

13/32
  • The server keeps keys and values for tokens it already read: "The class was about".
  • Add new text to the end, and the cached part is reused.
  • Insert "Actually" at the start: every later token's position embedding changes.
    • The whole KV cache is invalidated and must be recomputed.

Evaluate context choices empirically

14/32
  • Set up benchmarks or evals and test each change.
  • Toolformer example: the same model with tool calls allowed vs disabled, at sizes up to about 6.7B parameters.
Benchmark (largest model) Toolformer Tools disabled GPT-3
LAMA (facts) about 29 about 18.5 about 24.5
Math about 26.5 about 11 about 14.5
QA about 31 about 27.5 about 39
  • Tools helped on all three; only on QA did GPT-3 stay ahead.

Compaction

15/32
  • Compaction: the LLM summarizes earlier context into fewer tokens.
  • By the time you compact, the context is already extremely long.
  • The new decision is what to keep in the new context.
    • Keep too much → you have to compact again soon.
    • Drop too much → you lose context the task needs.

Compaction gone wrong

16/32
  • Reported Feb 2026: an AI agent (OpenClaw) bulk-deleted emails from a user's personal inbox.
  • She had told it to suggest emails for deletion, but take no action until she said so.
  • The inbox was too large, so the system compacted the context and lost "confirm before acting".
  • It started deleting on its own; she had to rush to her computer to kill the process.
  • Lesson: rules that must hold cannot live only in the history.

A different philosophy: recursive LMs (RLMs)

17/32
  • Recursive Language Models (arXiv 2512.24601): don't put the long prompt in the context at all.
  • The prompt is loaded as a variable in a Python environment (a REPL).
  • The LM writes code to look at it: print(prompt[:100]), prompt.split("Chapter 2").
  • It calls itself on pieces: llm_query(f"In Chapter 1, find... {part1}"), depth 1.
  • Sub-answers come back as variables; it prints FINAL_ANSWER.

RLM results

18/32
OOLONG trec_coarse, 263K-token context Score
GPT-5 34.2%
GPT-5-mini 23.2%
RLM(GPT-5-mini) 51.1%
RLM(GPT-5) without sub-calls 40.9%
ReAct + GPT-5 + BM25 30.7%
  • A small model working through the input with code beat the big model reading it all.
Part 3Context management in practice

Two principles

19/32
  • Focus the context: keep only what the task at hand needs. The whole history does not need to be there.
  • Preserve continuity: keep the requirements, goals, constraints and progress.
  • Excess information is context bloat.

Context management patterns

20/32
Pattern What it does In the notebook
Persistent event log Rebuild the context from stored events events list, never edited
Observation masking Hide old tool outputs build_context
Compaction Summarize earlier context compact
Memory offloading Store to files to free the context notes.md solution
Context isolation Give a subtask only what it needs Subagents, module 09
  • Real systems combine them.

Persistent event log

22/32
  • Store every step exactly as it happened. Append only.
  • Rebuild the model's input from the log on every call.
  • Trim what the model sees; the full record stays for audit and replay.
  • Notebook: an agent reads msa_15 sections 3, 4, 7, 9 and 10. Each read is logged as a tool event.

Observation masking

23/32
def build_context(events, keep_recent=4):
    msgs = [{"role": "system", "content": PINNED}, events[0]]             # pinned rules + the user's goal
    for e in events[1:-keep_recent]:
        if e["kind"] == "tool":
            msgs.append({"role": e["role"], "content": f"[old tool output hidden, {len(e['content'])} chars]"})
        else:
            msgs.append(e)
    return msgs + events[-keep_recent:]
  • Line 2: start with the pinned rules and the user's goal.
  • Lines 3–5: in the middle, swap each tool output for a one-line placeholder.
  • Lines 6–7: keep other events, like "Reading section 7."
  • Line 8: add the last 4 events word for word.

Masking: before and after

24/32
Full event What the model sees
"[tool result] section 7: LIMITATION OF LIABILITY 7.1 EACH PARTY'S TOTAL LIABILITY ... THIRTY-SIX (36) MONTHS ..." "[old tool output hidden, N chars]"
  • No extra model call. Try this first.
  • In one coding agent, about 84% of tokens were tool outputs. Hiding old ones roughly halved cost (Lecture 6).

Pin the hard rules

25/32
  • Pinned rules: in the system prompt, outside anything that gets trimmed.
  • PINNED: "You never send, file or delete anything. You only write a review for a lawyer." / "Every issue must cite a clause number."
  • This is the fix for the inbox story: compaction can't remove what is never summarized.

Compaction in the notebook

26/32
def compact(events, keep_recent=2):
    middle = "\n".join(e["content"] for e in events[1:-keep_recent])
    summary = ask("Summarize these contract-review notes in at most 5 short bullets. Keep clause numbers and numbers exact.\n\n" + middle)
    return [{"role": "system", "content": PINNED}, events[0],
            {"role": "assistant", "content": "Summary of earlier work:\n" + summary}] + events[-keep_recent:]
  • Line 2: join everything between the goal and the last 2 events.
  • Line 3: the LLM writes at most 5 bullets, clause numbers and numbers exact.
  • Lines 4–5: pinned rules + goal + summary + last 2 events.
  • Check: "never send" is still in the pinned rules afterward.

Keep the start stable

27/32
  • KV cache: the server's saved work on tokens it already read.
  • Add to the end only. The cached start is reused.
  • Edit an earlier message → positions change → the server recomputes everything after it.
  • Keep the system prompt and tool list identical across calls.

Load just in time

28/32
  • Keep IDs, not contents. Load one contract when the step needs it.
  • Progressive disclosure: show tools and files later, as needed.
  • Notes file: the agent appends one line per section to notes.md. A new session starts from the notes, not the whole contract.
Part 4How this applies to us

Local models feel context rot sooner

29/32
  • Local models have smaller useful windows and slow down with long prompts.
  • Time to first token grows with every pasted contract; the notebook's 1/5/10 test shows it on your own GPU.
  • Load one contract at a time; retrieve clauses (module 04) instead of pasting the archive.

What to trim, what to keep

30/32
  • Old clause text the agent already read is the main clutter. Mask it.
  • Keep the goal, the playbook rules and the last few turns word for word.
  • Keep the full event log on disk for audit; trim only what the model sees.

Rules that never get summarized

31/32
  • Rules like "never send anything" stay pinned on the firm's machine, every turn.
  • Keep the pinned prompt and tool list fixed, so the local server reuses its cache.
  • For very long files, consider the RLM idea: let the agent read the contract with code, section by section.

Common mistakes

32/32
  • Every document "just in case" → worse answers. Load what the step needs.
  • Summarizing first → costs a call and loses detail. Mask first.
  • Safety rules only in chat history → compaction can delete them. Pin them.
  • Editing earlier messages → breaks the KV cache. Rebuild from the log.
  • Trusting the advertised window → test quality at the lengths you actually use.

Check your understanding

A model was trained on 4K-token inputs. Why not just feed it 16K?

It only learned to use positional embeddings up to its trained length, so in practice it is limited to that length.

What is context rot?

Answer quality falls as the context grows, well before the window is full. On OOLONG every model scored lower at longer lengths.

Why should you add new text only at the end of the context?

Inserting text earlier shifts every later token's position, which invalidates the KV cache and forces the server to recompute it.

Your local agent gets slow and worse after 20 turns. What do you try first?

Hide old tool outputs. It needs no model call and tool outputs are most of the tokens; summarize only if that isn't enough.

Why rebuild the context from a log instead of keeping one growing list?

Go deeper

Key terms, papers, evidence, the full notebook code and worked solutions.

Lectures 2 and 6 · Anthropic, "Effective Context Engineering" · LangChain, "Context Engineering" · MemGPT

The context window is a small, expensive desk. Put only what the next step needs on it. Quality starts to drop well before the window is full.

Key terms

Context window
The maximum text (in tokens) a model can read at once. Everything the model knows about the current task must fit here.Source: CS329Z Lecture 2
Context rot
Answer quality drops as the context grows, often well before the window is full, and facts in the middle are used least.Source: Anthropic, "Effective Context Engineering for AI Agents" (2025); Lecture 2
Context engineering
Choosing the smallest set of high-value tokens to put in front of the model at each step: what to write down, select, compress or isolate.Source: Rajasekaran et al., Anthropic (2025); LangChain, "Context Engineering" (2025)
Observation masking
Replacing old tool outputs with a short placeholder. Cheap, needs no model call, and in coding agents roughly halved cost with equal or better results.Source: CS329Z Lecture 6
Compaction
Summarizing older history when nearing the window limit while keeping the system prompt, goal and recent turns word for word.Source: Lecture 6; MemGPT (Packer et al., 2023)
KV cache / prefix caching
The server keeps computed state for a prompt prefix it has seen. A stable prefix means the next call skips that work, which speeds up local inference.Source: Lecture 2
~84%

Share of a coding agent's tokens that are tool outputs. Hiding old ones roughly halved cost with equal or better results (L6).

51% vs 34%

A small model searching a 263K-token input with code beat a big model reading it all (L2 s.173).

8K

Context length where measurable quality decline began on the OOLONG test (L2).

The six techniques

  1. Append-only event log. Store every step forever. Rebuild what the model sees from the log each turn. You can then hide or summarize parts without losing the truth.
  2. Stable prefix. Keep the system prompt and tool list identical across calls and only add to the end. The server can then reuse its cache (vLLM --enable-prefix-caching), which cuts time to first token on your own GPU.
  3. Mask old observations. Replace old tool outputs with a one-line placeholder. It is cheap and needs no extra LLM call. Try this before summarizing.
  4. Compact near the limit. Summarize the middle of the history, but keep the system prompt, the user's goal and the last few turns word for word.
  5. Pin critical rules. Never let a rule like "confirm before acting" live only in the chat history. One agent deleted a user's inbox after that rule was summarized away (L2 s.171).
  6. Just-in-time loading and notes. Keep references (file paths, IDs) and load content when needed. Write progress to a notes file so it survives resets.

2. An append-only event log

Store every step forever. Rebuild what the model sees from the log each turn. Then you can trim what the model sees without losing the record (which you need for audit and replay).

03_context_engineering.ipynb · cell 3
events = []   # the full truth, never edited
def log(role, content, kind="chat"):
    events.append({"role": role, "content": content, "kind": kind})

log("user", "Review contract msa_15 against the playbook.")
for sec in ["3", "4", "7", "9", "10"]:

    log("user", f"[tool result] section {sec}: " + contract("msa_15").split(f"\n{sec}. ")[1][:400], kind="tool")

3. Observation masking and pinned rules

Old tool outputs are most of the tokens. Replace them with a one-line placeholder; keep the goal, the hard rules and the last few turns word for word. This needs no extra model call.

03_context_engineering.ipynb · cell 4
PINNED = """You review contracts for a law firm.
HARD RULES (never dropped by trimming):
- You never send, file or delete anything. You only write a review for a lawyer.
- Every issue must cite a clause number."""

def build_context(events, keep_recent=4):
    msgs = [{"role": "system", "content": PINNED}, events[0]]             # pinned rules + the user's goal
    for e in events[1:-keep_recent]:
        if e["kind"] == "tool":
            msgs.append({"role": e["role"], "content": f"[old tool output hidden, {len(e['content'])} chars]"})
        else:
            msgs.append(e)
    return msgs + events[-keep_recent:]

full = sum(len(e["content"]) for e in events)
trimmed = sum(len(m["content"]) for m in build_context(events))
print(f"full: {full} chars -> trimmed: {trimmed} chars ({1 - trimmed/full:.0%} smaller)")

4. Compaction: summarize the middle when you must

When masking isn't enough, summarize the middle of the history. Keep the pinned rules out of the summary so they can never be lost. (One real agent deleted a user's inbox after "confirm before acting" was summarized away.)

03_context_engineering.ipynb · cell 5
def compact(events, keep_recent=2):
    middle = "\n".join(e["content"] for e in events[1:-keep_recent])
    summary = ask("Summarize these contract-review notes in at most 5 short bullets. Keep clause numbers and numbers exact.\n\n" + middle)
    return [{"role": "system", "content": PINNED}, events[0],
            {"role": "assistant", "content": "Summary of earlier work:\n" + summary}] + events[-keep_recent:]

ctx = compact(events)
print(ctx[2]["content"])
print("\nPinned rules still present:", "never send" in ctx[0]["content"])

Traps
  • Stuffing every document into the prompt "just in case". It makes answers worse, not better.
  • Editing earlier messages. It breaks the cache, and you pay to reprocess everything.
  • Keeping safety rules only in conversation history, where compaction can delete them.

Check yourself

Your local agent slows down and gets worse after 20 turns. What do you try first?

Mask old tool outputs. It is free (no extra LLM call) and tool outputs are most of the tokens. Summarize only if that isn't enough.

Why rebuild the context from a log instead of keeping one growing message list?

The log stays the complete truth for audit and replay, while what the model sees can be trimmed freely. You get both a small context and a full record.
