Part 2Frameworks for Workflows and Programs

DSPy: three abstractions

9/54
  • Signature (what): strictly defines the inputs and outputs of an LM call.
  • Module (how): composes signatures and program logic into callable functions.
  • Optimizer: improves the prompts or weights of the program to raise a metric.
  • DSPy: Khattab et al., ICLR 2024, Stanford NLP.

String signatures

10/54
Signature What came back (lecture demo)
"message -> response" "Hello! I'm doing well, thanks for asking. How are you today?"
"message -> sentiment" on happy / angry / confused positive, Negative, negative
  • The simplest signatures are strings: inputs -> outputs.
  • dspy.Predict(signature) turns it into a callable.
  • Problem on the slide: the three answers don't follow the same format.

Typed signatures fix the format

11/54
  • Add types: "message: str -> sentiment: Literal['positive','negative','neutral'], confidence: float".
  • Same three messages now return:
Message sentiment confidence
"I am very happy today!" positive 0.98
"I am very angry today!" negative 0.9
"I am very confused today!" negative 0.86

Signature classes

12/54
  • For bigger signatures, use a class (lecture example ExtractEvent):
    • Docstring: "Extract event details from an email."
    • Input: email: str. Outputs: event_name, date, start ("24-hour clock"), duration_minutes, each allowed to be None.
  • Input: "We have a meeting scheduled for this Friday, October 9th at 10 AM PST."
  • Output: event_name='meeting', date=2026-10-09, start=10:00, duration_minutes=None.

A DSPy signature (our notebook)

13/54
class ExtractCap(dspy.Signature):
    """Read a limitation-of-liability clause and extract the cap."""
    clause: str = dspy.InputField()
    cap_months: int | None = dspy.OutputField(desc="months of fees the cap equals; None if liability is unlimited")
    favorable_to_customer: bool = dspy.OutputField()
  • Line 1: names the task.
  • Line 2: the docstring becomes the instruction.
  • Line 3: input, the clause text.
  • Line 4: output, a whole number or None (no cap).
  • Line 5: output, yes/no.
  • No prompt written by hand. lm.inspect_history(n=1) shows the one DSPy sent.

Modules: pick the inference strategy

14/54
dspy.Predict(ExtractEvent) dspy.ChainOfThought(ExtractEvent)
Fills the outputs directly Adds a reasoning field first
event_name='meeting' reasoning: "The email states there is a meeting 'this Friday, October 9th at 10 AM PST'..." then the same fields
  • Same signature, different strategy. Others: dspy.BestOfN.
  • A second tiny call: PickEmoji (event_name → one emoji). "Dentist" → a tooth emoji, with reasoning "a healthcare-related calendar event."

Modules compose with Python logic

15/54
  • UpdateCalendarFromEmail(dspy.Module):
    • LLM call 1: ChainOfThought(ExtractEvent).
    • Plain Python: if name, date or start is None → "no event found in email".
    • LLM call 2: ChainOfThought(PickEmoji), then tinycal.add_event(...).
  • Meeting email → "added to calendar" (Friday Oct 9, 10–11am; tinycal assumes 1 hour when duration is None).
  • "Thanks for sending the slides, they look great!" → "no event found in email".

DSPy module: model call + rule in code (our notebook)

16/54
  • CapReview runs dspy.ChainOfThought(ExtractCap) on the liability section.
  • Then code decides: issue = p.cap_months is None or p.cap_months > 12.
  • Notebook runs it on msa_02 (12 months) and msa_20 (36 months).
  • DSPy talks to the local server: api_base="http://localhost:11434/v1".

Optimizers: the data

17/54
  • Optimizers use all three pillars: data, the program, and a metric.
  • Data: 50 realistic emails with gold labels (data/emails.json).
    • e.g. "haircut with Jesse on Wednesday, October 28, 2026 at 2:45pm. It will run for one hour." → gold {date: 2026-10-28, start: 14:45, duration_minutes: 60}.
  • dspy.Example(**row).with_inputs("email"): input is the email; everything else is the label.
  • Shuffled with seed 0, split 30 train / 20 test.

Optimizers: the metric

18/54
  • event_metric: 1 if date, start time and duration all exactly match the gold label, else 0.
    • event_name is free text, so it is not graded.
  • It also returns feedback text, e.g. "Wrong -> start: expected '14:45', got '14:00'". GEPA shows this to its reflection model.
  • dspy.Evaluate(devset=testset, metric=event_metric, num_threads=8).

Agents in DSPy: ReAct

20/54
  • An agent in one line: dspy.ReAct("request -> summary", tools=tinycal.TOOLS).
  • Request: "Schedule a 30-minute coffee with John on Oct 7, 2026 in the afternoon after my lectures, and put a book emoji on every one of my lectures for that same week."
  • Result (8.3 s): book emoji added to the CS329Z lectures on Oct 5 and Oct 7 (13:30–14:50); coffee with John Oct 7, 15:00–15:30.
  • ReAct (Yao et al.): Thought → Act (Search) → Observation, repeated until Finish.

Agents in DSPy: RLM

21/54
  • RLM (recursive language model): the long prompt is loaded as a variable in a Python environment; the LM writes code to read it and calls sub-LMs on pieces (depth 1).
  • Lecture demo: all 50 emails joined into one inbox. dspy.RLM("inbox, question -> event_names: list[str], dates: list[str]", max_iters=8).
  • Question: "Which events are held in the Gates building, and on what dates?"
  • Answer (9.1 s): "The thesis defense for Wei Zhang", "Monday, December 7, 2026".
  • RLMs handle long-context prompts.

DSPy summary

22/54
  • Signatures define input/output contracts.
  • Modules compose and say how the contract is fulfilled: dspy.Predict, dspy.ChainOfThought, dspy.BestOfN, ...
  • Optimizers improve prompts or weights given data and a metric.
  • Built-in agent modules fulfill a signature: dspy.ReAct, dspy.RLM.

LangGraph: state, nodes, edges

23/54
  • State: a shared workspace for the graph; an object the graph modifies.
  • Every graph needs a Start node and an End node.
  • Node: a function that reads from and writes to the state.
  • Edge: defines control flow. Some edges are conditional.
LangGraph workflow LangGraph agent
Start → fixed nodes → End; dotted conditional edges can skip ahead Start → LLM ⇄ Tools; LLM → End
State: your fields State: can be the message history

LangGraph demo: one-node graph

24/54
  • Structured output: a Pydantic ExtractEvent with field descriptions, then langchain_llm.with_structured_output(ExtractEvent).
  • State: TypedDict with email: str and details: ExtractEvent | None.
  • Node: extract(state) returns only the part it changed: {"details": ...}.
  • Graph: StateGraph(State) → add_node("extract") → add_edge(START, "extract") → add_edge("extract", END) → compile().
  • graph.invoke({"email": ...}) → event_name='Meeting', date 2026-10-09, start 10:00.

LangGraph demo: conditional edges

25/54
  • CalendarState adds emoji and status.
  • Nodes: pick_emoji (LLM) and add_to_calendar (calls tinycal).
  • route(state): plain Python. Name, date and start all present → "pick_emoji"; else → END.
start → extract ─(route)→ pick_emoji → add_to_calendar → end
                   └──────────────────────────────────→ end
  • "Dentist Appointment Confirmed, Wednesday October 7th at 11am." → tooth emoji, "added to calendar".
  • "CS329Z Open Router Credits have arrived!" → all fields None, goes straight to end.

LangGraph agents: `create_agent`

26/54
  • Like DSPy, an agent in two lines: create_agent(langchain_llm, tools=tinycal.TOOLS).
  • Graph: start → model ⇄ tools; model → end.
  • "Please move my coffee with John on Oct 7th to be 30 minutes later" → coffee moved to 3:30–4:00pm.

LangGraph in our notebook

27/54
  • State: cid, clause, law, status.
get clause → read law (model) → decide (code) → check law → END
                                       └──────→ needs human → END
  • decide: answer looks like a state name (under 20 characters) → check; else → needs human.
  • check_law: California or Delaware → OK; anything else → ISSUE. msa_10 (Florida) should be ISSUE.

DSPy vs LangGraph

28/54
DSPy LangGraph
Signatures and modules State, nodes and edges
Optimizers built in (data + metric) Branching via conditional edges
ExtractCap → CapReview get → read → check or human
Agent: dspy.ReAct, dspy.RLM Agent: create_agent

Recap: workflow frameworks

29/54
  • Workflows compose model calls, tools and program logic into a larger AI system.
  • DSPy uses signatures and modules; LangGraph uses state, nodes and edges.
  • We design the control flow and choose where the model decides.
  • Improvement needs data and evaluation. DSPy makes this explicit with optimizers.
Part 3Open Source Agent Harnesses

What is an agent harness?

30/54
  • Harness: everything around the LLM core.
    • Planning and reasoning, memory, tools (retrieval, calculator, code, search, read/write memory), agent actions (tool call, interaction, reply).
  • It observes the environment (OS, browser, apps, databases) and acts on it.
  • Picture from Lecture 1, now boxed as "the harness."

What differentiates harnesses?

31/54
  • Building an agent means design choices: tools, memory, context management, execution.
  • Different harnesses make different trade-offs for their tasks and environments.
  • A good harness balances task success, cost, latency and user control. The right balance depends on the use case.

Four harnesses, side by side

32/54
Harness Design choices
Mini SWE-agent Only bash. Fully linear history (each step appends). Each action runs in subprocess.run, independent; no persistent shell
OpenHands One JSON file per event on disk; messages rebuilt each step. Persistent tmux terminal (cd, env vars, virtualenvs carry over). Stops after 4 repeats of the same action and result
Pi Four tools (read, write, edit, bash); system prompt under 1,000 tokens. No permission system. History is a tree you can branch. No plan mode, no sub-agent tool
OpenClaw Heartbeat turn every 30 minutes (replies NO_REPLY to stay silent). One long-lived Gateway process owns all chat channels. Identity from AGENTS.md, SOUL.md, IDENTITY.md, USER.md, MEMORY.md. At 3 AM a job moves the day's notes worth keeping into MEMORY.md

Meta-Harness: let a model write the harness

34/54

Part 4Orchestration and Telemetry

Why is orchestration needed?

37/54
  • METR chart: length of software tasks (in human time) that LLMs complete 50% of the time, by release date, log scale.
    • GPT-2 about 4 seconds; GPT-3.5 about 36 seconds; GPT-4 about 6 minutes; o1 about 30–40 minutes; o3 about 1.5 hours; Claude Opus 4.6 near 16 hours.
    • Above 16 hours, measurements are unreliable.
  • Agents run for long periods, so the infrastructure must be reliable.
  • Logs and observability tools help debugging. These are hard-won software engineering lessons.

Temporal execution model

38/54
Your code (client) Temporal server
Activities: functional units that can fail Task queue: an activity queue and a workflow queue
Workflows: link activities together Execution history and state, kept in storage
Workers: activity workers and workflow workers run them
  • Temporal: open-source durable execution engine.

Making a durable workflow

39/54
  • Activities (@activity.defn): extract_event (reuses the DSPy ChainOfThought module), select_emoji, add_to_calendar.
  • Workflow (@workflow.defn): calls each activity with execute_activity, start_to_close_timeout=1 minute, retry policy (1 s initial interval, at most 5 attempts).
    • It must be deterministic: no LLM calls, no I/O of its own. Temporal re-runs it from the record.
  • Worker: task queue "calendar", the workflow, the three activities, a 4-thread executor.
  • Run: "Office hours are Thursday October 8th at 3pm" → added; "Thanks for sending the slides" → no event found. Timeline UI at localhost:8233 shows each step.

Retrying flaky activities

40/54
  • A fake select_emoji raises "503 Service Unavailable" on attempts 1 and 2.
  • The server retries it under the retry policy; attempt 3 succeeds.
  • Output: "select_emoji attempt 1, 2, 3" → "added to calendar" (Go for a walk, Tue Oct 6, 9:00–9:30).
  • The workflow code never handled the error itself.

Server-based timing

41/54
  • ReminderWorkflow: run CalendarWorkflow as a child, then workflow.sleep(seconds). A workflow can sleep months or years in one line.
  • Demo: start it with a 20 s sleep, wait 10 s, kill the worker. Status is still RUNNING with no worker alive.
  • Bring a worker back: the timer fires, "Reminder! (Lab meeting ...)" prints.
  • LLM steps were not re-run: one "Lab meeting" on the calendar, not two.

Part 5Best Practices and Challenges

Keep it simple

45/54
  • You may not need an agent. Sometimes a workflow is right for the task.
  • If you build an agent, think hard about which tools to include.
  • With a lot of data, you might optimize a model end to end.

Make failures observable and recoverable

46/54
  • Trace model calls, tool calls, state changes and errors.
  • Set timeouts, retry limits and execution budgets.
  • Log outputs and diagnose failures. Monitor system state.
  • You can raise the error back to the agent so it tries again (slide shows a blocked command returning a message that tells the agent what to do instead).

Example: Shepherd

47/54
  • Shepherd (arXiv 2605.10913): a meta-agent (Opus) watches an agent (Haiku) and can observe, revert and fork its run: "If tests break, revert the agent and retry."
Use Result on the slide
Runtime intervention, CooperBench pair coding 28.8 without meta-agent → 45.3 (Sonnet 4.6) / 54.7 (Opus 4.7) with
Counterfactual optimization, LiveCodeBench Unoptimized 30.7%, MetaHarness 40.0%, GEPA 48.7%, CRO 51.0%
Meta-agent-guided Tree-GRPO, TerminalBench-2 Qwen3.5 35B-A3B: 26.1 → 34.2 → 39.4; Nemotron-3-Super 120B-A12B: 30.3 → 33.8 → 37.2 (base → FlatGRPO → Tree-GRPO)

Run evaluations

48/54
  • Ground design decisions in evals. Evals enable optimization.
  • Building a proper eval is one of the most important steps.
  • Choose metrics wisely: accuracy, cost, latency.
  • Test representative tasks, edge cases and failure scenarios.
  • Unless you build a general coding harness, don't climb Terminal-Bench, SWE-bench or DeepSWE. Build your custom domain eval.

Challenges and limitations

49/54
  • Abstractions lift you away from system details. Know what is under the hood ("show me the prompt").
  • In a complex system it is hard to find where failures come from. Look at the traces.
  • Frameworks add dependencies on outside libraries that must be maintained.

Recap: best practices

50/54
  • Engineering is a cycle: build → run → evaluate → improve.
  • Start simple; justify added complexity.
  • Design for failure and recovery.
  • Use evidence to judge quality, cost and latency.
  • Fully understand how your system works.
Part 6How this applies to us

Pick the harness by measuring

51/54
  • Local open models are the small-model row (Haiku): harness choice swung it almost 17 points.
  • So for a firm's local model, the harness is a big part of the product.
  • Measure success and cost on the firm's own contracts, not on coding benchmarks.

Rules in code, not in the framework prompt

52/54
  • Rules like "cap over 12 months is an issue" stay in code (CapReview, check_law).
  • The framework only asks the model narrow questions.
  • Read the prompt the framework sends (inspect_history) before trusting it.

Long jobs on one GPU

53/54
  • A firm reviewing many contracts should not restart from zero when the GPU runs out of memory.
  • Durable steps (SQLite here, Temporal at scale) skip finished contracts on restart.
  • Self-hosted Langfuse or MLflow keeps every trace on the firm's machine for audit.

Common mistakes

54/54
  • Trusting a framework's hidden prompt → read it with inspect_history.
  • Picking a harness by reputation → measure success and cost on your task.
  • Metrics that return only a number → return "expected 12, got 24"; optimizers learn from it.
  • Model calls inside Temporal workflow code → replay breaks. Put them in recorded activities.

Check your understanding

In DSPy, what is the difference between a signature and a module?

A signature says what goes in and out, with types. A module says how to fill it (Predict, ChainOfThought, ReAct) and can add Python logic.

What did GEPA change to take Gemma 3 12B from 55% to 100%?

Only the instruction text of the prompt. The small model's weights stayed the same.

In the LangGraph example, who decides whether a contract goes to a person?

Code. `decide` checks that the model's answer looks like a state name; if not, it routes to "needs human."

Why does the harness matter more for Haiku than for Opus on Terminal-Bench 2?

Haiku ranged from 31.1% to 47.8% across harnesses; the big models moved only a few points. Weaker models lean more on the harness.

Why must a Temporal workflow function avoid LLM calls?

Temporal replays workflow code to recover. LLM calls give different answers each time, so they go in activities whose results are recorded.

How do durable steps save time after a crash?

Each finished step's result is saved. On restart, the code reuses it instead of calling the model again.

Key terms, papers, evidence, the full notebook code and worked solutions.

Lecture 5 · DSPy · LangGraph · Temporal · Arena, "HarnessTax" · course repo lecture5-frameworks

The harness is all the code around the model: the loop, tools, prompts, limits and logging. For weaker models it matters as much as the model itself. Pick it by measuring.

Key terms

Harness
All the code around the model: the loop, tools, prompts, context handling, limits and logging.Source: Lecture 5; Arena, "HarnessTax" (2026)
DSPy signature
A typed declaration of what goes into and comes out of an LM call (for example clause: str -> cap_months: int | None). DSPy writes the prompt.Source: Khattab et al., "DSPy", ICLR (2024)
DSPy module / optimizer
A module composes signatures with Python; an optimizer (such as GEPA or MIPROv2) improves prompts or examples against your metric.Source: Khattab et al. (2024); Lecture 5
LangGraph
A library for agents as graphs: shared state, nodes that update it, and edges (including conditional ones) that decide what runs next.Source: LangChain, "LangGraph Overview"
Durable execution
Recording each finished step so a crashed run resumes without repeating work or side effects (Temporal workflows and activities).Source: Lecture 5 (Temporal demo)

The three frameworks the course teaches

  • DSPy: you declare inputs and outputs (signatures), compose them in Python (modules), and an optimizer improves the prompts against your metric. Best for pipelines you want to tune.
  • LangGraph: state plus nodes plus edges. Good when you mix fixed steps and agent steps and want checkpoints.
  • Temporal: durable execution. Each LLM call is a retryable step; after a crash the workflow resumes without redoing finished steps.

class CapReview(dspy.Module):
    def __init__(self):
        self.extract = dspy.ChainOfThought(ExtractCap)
    def forward(self, cid):
        s = next(x for x in sections(contract(cid)) if "Liability" in x["title"])
        p = self.extract(clause=s["text"])
        issue = p.cap_months is None or p.cap_months > 12            # the rule lives in code
        return dspy.Prediction(cap_months=p.cap_months, issue=issue)

2. LangGraph: state, nodes and edges

A graph with a fixed path plus one decision made by code: if extraction fails, skip straight to "needs human".

from typing import TypedDict
from langgraph.graph import StateGraph, END
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model=MODEL, base_url="http://localhost:11434/v1", api_key="local", temperature=0)

class State(TypedDict, total=False):
    cid: str; clause: str; law: str; status: str

def get_law_clause(state):
    s = next(x for x in sections(contract(state["cid"])) if "Governing" in x["title"])
    return {"clause": s["text"]}

def read_law(state):
    out = llm.invoke(f"{state['clause']}\nWhich US state's law governs? Reply with the state name only.").content.strip()
    return {"law": out.rstrip(".")}

def decide(state):
    return "check" if state["law"] and len(state["law"]) < 20 else "human"

def check_law(state):
    return {"status": "OK" if state["law"] in ("California", "Delaware") else "ISSUE"}

def human(state):
    return {"status": "NEEDS HUMAN"}

g = StateGraph(State)
for name, fn in [("get", get_law_clause), ("read", read_law), ("check", check_law), ("human", human)]:
    g.add_node(name, fn)
g.set_entry_point("get")
g.add_edge("get", "read")
g.add_conditional_edges("read", decide, {"check": "check", "human": "human"})
g.add_edge("check", END); g.add_edge("human", END)
app = g.compile()

for cid in ["msa_04", "msa_10"]:
    print(cid, app.invoke({"cid": cid}))

3. Crash-safe steps (the idea behind Temporal)

Long jobs crash: the GPU runs out of memory, the runtime disconnects. Record each finished step. On restart, reuse recorded results instead of calling the model again. The course demo used Temporal for this; here is the same idea in 20 lines with SQLite.

07_frameworks.ipynb · cell 6
from pathlib import Path
Path("steps.sqlite").unlink(missing_ok=True)          # start clean so the timing comparison is fair
db = sqlite3.connect("steps.sqlite", check_same_thread=False)
db.execute("create table if not exists steps (key text primary key, result text)")

def durable(step_name):
    def wrap(fn):
        def inner(*args):
            key = hashlib.sha256(json.dumps([step_name, args]).encode()).hexdigest()
            row = db.execute("select result from steps where key=?", (key,)).fetchone()
            if row:
                return json.loads(row[0])                            # already done: no repeat model call
            out = fn(*args)
            db.execute("insert into steps values (?,?)", (key, json.dumps(out))); db.commit()
            return out
        return inner
    return wrap

@durable("law")
def law_step(cid):
    return app.invoke({"cid": cid})["status"]

t0 = time.time(); first = [law_step(c) for c in ids()[:6]]; t1 = time.time() - t0
t0 = time.time(); again = [law_step(c) for c in ids()[:6]]; t2 = time.time() - t0
print(f"first run {t1:.1f}s, rerun after a 'crash' {t2:.2f}s, same results: {first == again}")

def redline(state):

    return {"redline": text}

Check yourself

In the GEPA demo, what changed: the model weights or the prompt?

Only the prompt's instruction text. The small model's weights stayed the same. The big model was used only to reflect on mistakes and suggest better instructions.

Why must a Temporal workflow function avoid LLM calls?

Temporal replays the workflow code from its history to recover. Code that gives different results each time (LLM calls, I/O) breaks replay, so it goes in activities whose results are recorded.
