2/27

Part 2Terms

Definitions

7/27
  • Task: a single test with defined inputs and success criteria.
  • Trial: one attempt at a task.
  • Benchmark (evaluation suite): a set of tasks measuring specific abilities.
  • Verifier (grader): logic that scores the agent's work.
  • Trajectory (trace, transcript): the complete record of a trial.
  • Evaluation harness: infrastructure that runs evals end to end.
  • Agent harness: the system that lets a model act as an agent.

Agent harness vs evaluation harness

8/27
Agent harness Evaluation harness
Loop, tools, prompts, limits around the model Starts sandboxes, runs trials, runs verifiers, stores results
Examples: Claude Code, Codex, mini-swe-agent Example: Harbor
Swap it, and you test a different agent Keep it fixed, so trials are comparable

Our terms

9/27
  • Task: one checklist item, e.g. msa_13:termination_notice.
  • Trial: one work session on that item.
  • Verifier: code that checks the quote is really in the contract.
  • Trajectory: the git log plus progress.md.

Part 5Keeping it reproducible

CI/CD: continuous benchmarks

14/27
  • Tasks are software. Software has bugs.
  • Loop: new tasks → GitHub → Harbor (v1.1.0) → benchmark runs → tbench.ai → issues → back to GitHub.
  • Usage turns into bug reports:
    • Flakiness; infra noise and compatibility.
    • New models = new behavior.
    • False negatives (good work marked failed); reward hacking.

Versioning: what a change costs

15/27
Version bump Action What changed
(x+1, y, z) Rerun Agent environment: new task, fix under- or over-specified prompt, change data, tools or resources
(x, y+1, z) Regrade Verifier: fix an overly strict check, close a reward hack, re-tune a judge, change the reward
(x, y, z+1) Reuse Metadata: docs, oracle flakiness, pin dependencies, fix a typo
  • Old trajectories can be regraded without rerunning the agent, if only the verifier changed.

Part 6Long-running jobs

Why long jobs are hard

17/27
  • Context window: how much text the model can hold at once.
  • Long-horizon: context grows and drifts over many steps (Lecture 1, key challenges).
  • 200 contracts in a data room won't fit in one sitting.
  • Each new session starts blank. Progress must live in files, not in the model.

The pattern

18/27
setup:  checklist (all "not done") + progress file
loop:   read checklist → do ONE item → verify quote → mark done → commit
finish: only when every item has evidence
  • Setup session: code writes the checklist. One item per contract per rule.
  • Work session: read the progress file, do one item, then save.

Who may change what

19/27
The code The agent
Writes the checklist (scope is fixed) May only flip done and attach evidence
Checks the quote is in the contract Answers: does the clause break the rule?
Commits each step to git Never adds, removes or rewords items
Blocks the final report until all items have evidence Can't call the job finished

Our matter: 16 items

20/27
  • 4 contracts × 4 playbook rules = 16 items, e.g. msa_13:termination_notice.
  • msa_13, 4.1: "...at least 15 days' prior written notice of non-renewal." Rule needs at least 30 → breaks.
  • The model must quote the exact words that decide it.
  • Retries get temperature 0.5 for variety. After 3 failed tries, the item is left for a person.

Verifying evidence in code

21/27
if not quote_is_in_doc(f.quote, contract(todo["contract"])):
    todo["tries"] = todo.get("tries", 0) + 1
    (WORK / "checklist.json").write_text(json.dumps(state, indent=1))
    return "RETRY"
todo.update(done=True, evidence={"breaks_rule": f.breaks_rule, "quote": f.quote})
  • Line 1: is the model's quote really in the contract?
  • Line 2: if not, add one to this item's try count.
  • Line 3: save the checklist, so the count survives a crash.
  • Line 4: return "RETRY"; the item stays not done.
  • Line 5: quote is real: mark done, attach verdict and quote.

Reliable runs

22/27
  • Reliable (fault tolerant): a crash loses one item, not the job.
  • Reproducible: each item is a git commit you can review and replay.
  • Stop rule: the loop runs at most 16 + 4 times. Never forever.
  • Stop hook: the final report refuses to run while any item lacks evidence.

Crash vs restart

23/27
Without a checklist file With a checklist file
Crash at item 9: progress was in the model's context Crash at item 9: items 1–8 are saved and committed
Restart redoes everything Restart reads the file, runs only unfinished items

Tools built for agents (SWE-agent)

24/27
  • Agent-computer interface: tools shaped for a model, not a person.
  • A file viewer that shows 100 lines at a time, with line numbers.
  • Search that returns a capped summary, not every match.
  • An edit tool that rejects edits that break syntax and says why.
Part 7How this applies to us

A data room is a long task

25/27
  • Due diligence is a long job. On a local machine it may run for hours.
  • Saved progress means a crash or reboot costs one item.
  • Every step is a commit a lawyer can review: "full receipts for every row."

Use the benchmark habits

26/27
  • Version the checklist and the checker like Terminal-Bench versions tasks.
  • Changed only the checker? Regrade the saved evidence; don't rerun the model.
  • Keep the agent harness fixed when comparing two local models.

Common mistakes

27/27
  • Letting the agent edit the checklist → it can make the job look finished.
  • Many items per session → one item, verify, commit.
  • Progress kept in the model's head → if it isn't in a file, it didn't happen.
  • "Done" without evidence → require a quote; check it in code.
  • No loop limit → cap loops and retries.

Check your understanding

What is the difference between a task, a trial and a trajectory?

A task is one test with inputs and success criteria. A trial is one attempt at it. The trajectory is the full record of that attempt.

You fix an overly strict verifier. Must you rerun every agent?

No. That is a verifier change (x, y+1, z): regrade the saved trajectories and artifacts. Only agent-environment changes need a rerun.

Why one item per session?

Small steps with a commit each mean a failure loses one item, and every step can be reviewed.

The run crashes halfway. What happens on restart?

It reads the checklist and continues with unfinished items. Finished items are not redone.

Why does code, not the model, write the checklist?

So the job's scope is fixed. The model can only report on items, not change what the job covers.

Go deeper

Key terms, papers, evidence, the full notebook code and worked solutions.

SWE-agent · OpenHands · Anthropic, "Effective Harnesses for Long-Running Agents" · Claude Code best practices · Terminal-Bench

For jobs longer than one context window, the agent's memory must be written down: a checklist it can only mark done with evidence, a progress file, and a commit after each step.

Key terms

Long-running agent
An agent whose job spans many context windows or sessions, so progress must be written outside the model.Source: Anthropic, "Effective Harnesses for Long-Running Agents" (2025)
Initializer session
A first session that sets up the environment, a checklist and a progress file before any work starts.Source: Anthropic (2025)
Progress file / checklist
Files that hold what is done and what remains; the agent may only mark items done with evidence.Source: Anthropic (2025)
Incremental work
One item per session, verified and committed, so failures lose little and every step is reviewable.Source: Anthropic (2025); SWE-agent
Stop hook
A rule that prevents the run from finishing until required checks pass.Source: Claude Code docs

The long-running harness

  1. Setup session: write the full checklist (all items "not done"), an init.sh that starts the environment, and a progress file.
  2. Work sessions: start by reading the progress file and running a quick smoke test. Do one item. Mark it done only with evidence. Commit. Append to the progress file.
  3. Stop rule: the run can't finish until every item has a result and evidence.

Agent-computer interface (from SWE-agent)

  • A file viewer that shows 100 lines at a time, with line numbers.
  • Search that returns a capped summary, not every match.
  • An edit tool that rejects edits that break syntax and says why.

# lal.llm = the OpenAI client pointed at the local Ollama server, http://localhost:11434/v1 (see notebook 00)
from lal.llm import structured

WORK = Path("matter_workspace"); shutil.rmtree(WORK, ignore_errors=True); WORK.mkdir()
subprocess.run(["git", "init", "-q"], cwd=WORK)
subprocess.run(["git", "config", "user.email", "agent@local"], cwd=WORK); subprocess.run(["git", "config", "user.name", "agent"], cwd=WORK)
PB = playbook()

1. Setup session: write the checklist

Code writes it (one item per contract per rule). The agent may only flip done and attach evidence; it may never edit the list itself.

14_long_running_agents.ipynb · cell 3
MATTER = ids()[12:16]           # 4 contracts x 4 rules = 16 items
items = [{"id": f"{c}:{r}", "contract": c, "rule": r, "done": False, "evidence": None}
         for c in MATTER for r in PB["rules"]]
(WORK / "checklist.json").write_text(json.dumps({"matter": "demo", "items": items}, indent=1))
(WORK / "progress.md").write_text("# Progress\n")
subprocess.run(["git", "add", "-A"], cwd=WORK); subprocess.run(["git", "commit", "-qm", "setup"], cwd=WORK)
print(len(items), "checklist items written")

2. One work session = one item, with evidence that code verifies

14_long_running_agents.ipynb · cell 4
WORD = {"liability_cap": "Liability", "governing_law": "Governing", "auto_renewal": "Renewal", "termination_notice": "Renewal"}

class Finding(BaseModel):
    breaks_rule: bool
    quote: str

def work_session():
    state = json.loads((WORK / "checklist.json").read_text())
    todo = next((i for i in state["items"] if not i["done"] and i.get("tries", 0) < 3), None)   # skip items that failed 3 times
    if todo is None:
        return "ALL DONE"
    clause = next(s for s in sections(contract(todo["contract"])) if WORD[todo["rule"]] in s["title"])["text"]
    f = structured(f"Rule: {PB['rules'][todo['rule']]}\nClause: {clause}\n"
                   "Does the clause break the rule? Quote the exact words that decide it.", Finding,
                   temperature=0.0 if todo.get("tries", 0) == 0 else 0.5)    # retries get some variety
    if not quote_is_in_doc(f.quote, contract(todo["contract"])):             # evidence must be real
        todo["tries"] = todo.get("tries", 0) + 1
        (WORK / "checklist.json").write_text(json.dumps(state, indent=1))
        with open(WORK / "progress.md", "a") as p: p.write(f"- {todo['id']}: evidence failed check, retry later\n")
        return "RETRY"
    todo.update(done=True, evidence={"breaks_rule": f.breaks_rule, "quote": f.quote})
    (WORK / "checklist.json").write_text(json.dumps(state, indent=1))
    with open(WORK / "progress.md", "a") as p: p.write(f"- {todo['id']}: {'BREAKS' if f.breaks_rule else 'ok'}\n")
    subprocess.run(["git", "add", "-A"], cwd=WORK); subprocess.run(["git", "commit", "-qm", f"check {todo['id']}"], cwd=WORK)
    return todo["id"]

for _ in range(len(items) + 4):               # a stop rule: never loop forever
    r = work_session()
    if r == "ALL DONE": break
print(open(WORK / "progress.md").read())

14_long_running_agents.ipynb · cell 8
# Solution 1: resume after a crash. Mark 3 items as not done (as if the run died) and rerun the loop.
state = json.loads((WORK / "checklist.json").read_text())
for i in state["items"][-3:]:
    i.update(done=False, evidence=None, tries=0)
(WORK / "checklist.json").write_text(json.dumps(state, indent=1))
redone = []
for _ in range(10):
    r = work_session()
    if r == "ALL DONE": break
    redone.append(r)
print("redone after restart:", redone)
# Only the unfinished items ran again. The checklist file, not the model's memory, holds the progress.
14_long_running_agents.ipynb · cell 9
# Solution 2: a stop hook. The final report refuses to run until every item has evidence.
def final_report():
    st = json.loads((WORK / "checklist.json").read_text())
    missing = [i["id"] for i in st["items"] if not (i["done"] and i["evidence"])]
    if missing:
        raise RuntimeError(f"Cannot finish: {len(missing)} items lack evidence: {missing[:5]}")
    broken = [i["id"] for i in st["items"] if i["evidence"]["breaks_rule"]]
    return f"Matter complete. {len(st['items'])} checks, {len(broken)} issues: {broken}"
try:
    print(final_report())
except RuntimeError as e:
    print(e)        # the stop hook doing its job: the matter can't be closed yet
Traps
  • Letting the agent edit the checklist itself. It may only flip "done" with evidence.
  • Doing many items per session. One item, verify, commit.
