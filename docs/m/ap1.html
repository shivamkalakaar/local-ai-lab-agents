AppBench: Benchmarking AI-Generated Web Applications

Open in Colab
9 min readSlides first, then the deeper material

How a Stanford team graded AI-built web apps by what a user can do, and how to check the grader first.

Based on CS329A past project · AppBench · main paper

Learning objective

1/13
  • Build a checklist grader for AI-built apps, and test the grader before you trust it.

The problem

2/13
  • AI tools can build a whole web app from one request.
  • Code benchmarks check single functions with unit tests.
  • Nothing checked if the app is usable:
    • Does navigation work?
    • Does saved state survive a refresh?
    • Are errors handled?

"It compiles" vs "a user can use it"

3/13
Unit test User check
tip(50, 20) returns 10 Type a bill, click Calculate, see the tip
The page loads Add two tasks, refresh, both are still there
Passes on the happy path A blank task is ignored

What the students built: AppBench

4/13
  • Team: Ethan Hellman, Brendan McLaughlin, Abhinav Lalwani, Belinda Mo (CS329A, Winter 2025).
  • 9 app requests, from L0 (static page) to L4 (live shared whiteboard).
  • Six axes: UI, features, state, API integration, cross-page navigation, data processing.
  • 7 builders, one shot each: Replit, Bolt, Cursor Agent, Lovable, Claude Sonnet 3.7, GPT-4.5, OpenHands CodeAct 2.1.

How the checklist works

5/13
  • Explicit check: what the user asked for.
  • Implicit check: what a good app would also do (a back button, ignore blank input).
  • Dependency graph: which check needs which other check to pass first.
    • Parent fails → children are skipped and score 0.
    • One root failure shows once, not ten times.
  • Weighted scores, scaled to 0–100.

How each check runs

6/13
  • Screenshot + multimodal LLM: a model that reads images judges the look.
  • LLM-driven browser (Stagehand on Playwright): clicks through the app.
  • Network interception: fakes server errors to test error handling.

What they found

7/13
Grader vs. 3 human raters Value
Pearson correlation 0.8173
Spearman correlation 0.6827
Mean MSE / MAE 0.0302 / 0.1313
  • All builders scored above 75% up to L2. Scores fell at L3 and dropped sharply at L4.
  • 2 of 7 builders failed to produce a compiling app for one L3 and one L4 task.
  • One-shot models were close to full agent products. Lovable and Bolt were top.

  • Each tuple: name, weight, explicit (True) or implicit (False), parents, test.
  • Line 1: does window.app exist? Everything depends on it.
  • Line 2: add two tasks, tick one, expect 1 left.
  • Line 3: look in localStorage (the browser's small storage) for the saved list.
  • Line 4: two inner lists = two page loads. Reload, expect 2 tasks.
  • Line 5: implicit; nobody asked, but blank tasks should be ignored.

Test the grader first

10/13
  • Known-good tip calculator: must score 100.
  • Known-broken one (no labels, wrong math, wrong button id): must score under 60.
  • Crashing script: behavior checks must fail.
  • Only then grade the model's apps.

One shot vs one fix round

11/13
One shot One fix round
Same prompt, one turn, no feedback Model gets the names of its failed checks, one chance to fix
1 call per app 1 more call per app (0 if nothing failed)
  • Our checks name the exact problem, so the fix round often helps.
  • AppBench agents got no such feedback.

How this applies to us

12/13
  • A firm will ask a local model for small tools: a deadline tracker, a fee calculator, a playbook-breach list.
  • Grade them on the firm's own machine with a checklist like this: "deadlines survive a refresh", "liability cap over 12 months is flagged".
  • Check the grader on a known-good and known-broken tool before trusting it.

Common mistakes

13/13
  • Grading by "it compiles" → test what a user does, including a refresh.
  • Only explicit checks → add implicit ones, weighted lower.
  • One failure cascades into ten → skip children of failed parents.
  • Trusting the grader blindly → known-good must score 100, known-broken low; then compare with a human.

Go deeper

Key terms, papers, evidence, the full notebook code and worked solutions.

CS329A Winter 2025 · Ethan Hellman, Brendan McLaughlin, Abhinav Lalwani, Belinda Mo

Paper · Poster

Problem
Code benchmarks check functions with unit tests. Nothing checked whether an AI-built web app is usable: does navigation work, does state survive a refresh, are errors handled?
Method
9 app requests from L0 (static page) to L4 (real-time collaborative whiteboard), spread over six axes (UI, features, state, API integration, cross-page navigation, data processing). Each request gets a checklist of explicit and implicit requirements, arranged as a dependency graph and turned into a scripted evaluator built from shared tools: screenshot + multimodal LLM judging, an LLM-driven browser (Stagehand on Playwright), and network interception for error states. Weighted scores scaled to 0-100. 7 builders tested one-shot: Replit, Bolt, Cursor Agent, Lovable, Claude Sonnet 3.7, GPT-4.5, OpenHands CodeAct 2.1.
Results
Grader vs. 3 human raters: mean MSE 0.0302, mean MAE 0.1313, Pearson 0.8173, Spearman 0.6827. Per-builder MSE from 0.0160 (Service 4) to 0.0501 (CodeAct); per-task MSE from 0.0042 (l2-add-to-cart) to 0.0751 (l3-food-order). All builder types scored above 75% up to L2, fell at L3 and dropped sharply at L4; 2 of 7 builders failed to produce a compiling app for one L3 and one L4 task. One-shot models were close to full agent products; Lovable and Bolt were the top builders.
Lessons
Grade AI-built software by what a user can do with it, not by whether it compiles. Split checks into what was asked and what a good result would also do, and skip checks whose prerequisites failed so one root failure doesn't look like ten. Validate your grader against humans (or at least known-good and known-broken examples) before trusting it. Don't assume an agent framework beats a strong one-shot model; measure it.
Our rebuild
The local model builds 5 single-file HTML apps (L0-L3: about page, theme switcher, tip calculator, food order, to-do list saved in localStorage). Python's HTML parser checks structure; Node.js runs each app's script in a fake page (subprocess with timeout) and calls the functions it exposes on window.app, including a 'page refresh' test for saved state. Checks are weighted, core vs. implicit, with dependencies. We validate the grader on known-good/broken apps, compare one-shot vs. one fix round with failure feedback, and (in the solutions) correlate the grader with a hand score and an LLM judge.

The original project

AppBench: Benchmarking AI-Generated Web Applications by Ethan Hellman, Brendan McLaughlin, Abhinav Lalwani and Belinda Mo (Stanford CS329A, Winter 2025). Paper · Poster

Problem. Code benchmarks check functions with unit tests. Nobody checked whether an AI-built web app is usable: does navigation work, does state survive a refresh, does the page handle errors?

Method. 9 app requests from L0 (static page) to L4 (real-time collaborative whiteboard), spread over six axes: UI complexity, features, state management, API integration, cross-page navigation, data processing. For each request the authors wrote a checklist of explicit requirements (what the user asked for) and implicit ones (what a good app would also do, like a back button). They arranged the checklist as a dependency graph: you can't test "add to cart" before the product page opens. Each node becomes a scripted test built from shared tools: screenshot + multimodal LLM judging, an LLM-driven browser (Stagehand on Playwright), and network interception to test error states. Scores are weighted and scaled to 0–100.

Setup. 7 builders: Replit, Bolt, Cursor Agent, Lovable, Claude Sonnet 3.7, GPT-4.5 and OpenHands CodeAct 2.1, each in one shot. Three humans scored every app without seeing the automatic scores.

Key results (as reported). - Grader vs. humans: mean MSE 0.0302, mean MAE 0.1313, Pearson 0.8173, Spearman 0.6827. - Per-builder MSE ranged from 0.0160 (Service 4) to 0.0501 (CodeAct); per-task MSE from 0.0042 (l2-add-to-cart) to 0.0751 (l3-food-order). - All builder types scored above 75% up to level L2; scores fell at L3 and dropped sharply at L4. 2 of 7 builders could not produce a compiling app for one L3 and one L4 task. - One-shot models were "surprisingly competitive" with full agent products; the gap narrowed at higher levels. Lovable and Bolt were the top builders.

Limitations they state. Only 9 tasks, so no strong general claims; the graders need more calibration with UX experts.

Our mini version. Their apps ran in a real browser. Colab has no browser, so each app must expose its logic as plain JavaScript functions on window.app. We check the page structure with Python's built-in HTML parser, and we run the app's own script in Node.js (which Colab has) inside a fake page, then call its functions. Same ideas: explicit vs. implicit checks, a dependency graph, weighted 0–100 scores, and "page refresh" tests for saved state.

1. Read the page like a browser would (pure Python)

Page collects tag counts, element ids, the text inside each tag, and the inline scripts.

ap1_appbench.ipynb · cell 3
VOID = {"area", "base", "br", "col", "embed", "hr", "img", "input", "link", "meta", "source", "track", "wbr"}

class Page(HTMLParser):
    def __init__(self, html: str):
        super().__init__(convert_charrefs=True)
        self.tags, self.ids, self.text = Counter(), {}, defaultdict(str)
        self.scripts, self.stack, self._script = [], [], False
        self.attrs = []
        try:
            self.feed(html or "")
        except Exception as e:                      # very broken HTML: keep what we parsed
            print("parse warning:", e)

    def handle_starttag(self, tag, attrs):
        a = {k: (v or "") for k, v in attrs}
        self.tags[tag] += 1
        self.attrs.append((tag, a))
        if a.get("id"):
            self.ids[a["id"]] = tag
        if tag == "script":
            self._script = not a.get("src")         # external scripts are not run
            if self._script:
                self.scripts.append("")
        if tag not in VOID:
            self.stack.append(tag)

    def handle_endtag(self, tag):
        if tag == "script":
            self._script = False
        if tag in self.stack:
            while self.stack and self.stack.pop() != tag:
                pass

    def handle_data(self, data):
        if self._script:
            self.scripts[-1] += data
            return
        for t in set(self.stack):
            self.text[t] += data + " "
        self.text["*"] += data + " "

    def has(self, tag, n=1):
        return self.tags[tag] >= n

    def text_has(self, tag, s):
        return s.lower() in re.sub(r"\s+", " ", self.text[tag]).lower()

p = Page("<html><head><title>Hi</title></head><body><header>Acme Labs</header><input id='x'><script>var a=1;</script></body></html>")
print(p.tags["input"], p.ids, p.text_has("header", "acme"), p.scripts)

2. Run the app's own JavaScript in a fake page (Node.js, in a subprocess with a timeout)

The fake page answers every DOM call with a harmless stand-in object, so the app's setup code doesn't crash. localStorage is real (a dictionary), so we can test saving. A phase is one page load: to test a refresh, we run phase 1, keep localStorage, and load the page again for phase 2. The value of the last expression in the last phase is the result.

ap1_appbench.ipynb · cell 4
HARNESS_JS = r"""
const vm = require('vm'), fs = require('fs');
const code = fs.readFileSync(process.argv[2], 'utf8');
const phases = JSON.parse(fs.readFileSync(process.argv[3], 'utf8'));
const store = {};
const TEXTY = ['value','textContent','innerHTML','innerText','className','id','src','href','checked'];
function any() {                       // a stand-in for any DOM object
  const props = {};
  return new Proxy(function(){}, {
    get(t, p) {
      if (p === Symbol.toPrimitive) return () => '';
      if (p in props) return props[p];
      if (p === 'toString' || p === 'valueOf') return () => '';
      if (TEXTY.includes(p)) return '';
      if (p === 'length') return 0;
      if (p === 'then') return undefined;
      if (p === Symbol.iterator) return function* () {};
      if (p === 'children' || p === 'childNodes') return [];
      const v = any(); props[p] = v; return v;
    },
    set(t, p, v) { props[p] = v; return true; },
    apply() { return any(); },
    construct() { return any(); },
  });
}
const localStorage = {
  getItem: k => (k in store ? store[k] : null),
  setItem: (k, v) => { store[k] = String(v); },
  removeItem: k => { delete store[k]; },
  clear: () => { for (const k in store) delete store[k]; },
  key: i => Object.keys(store)[i] ?? null,
  get length() { return Object.keys(store).length; },
};
let out = {load_error: null, error: null, value: null};
for (let i = 0; i < phases.length; i++) {
  const listeners = [];
  const document = any();
  document.readyState = 'loading';
  document.addEventListener = (ev, fn) => { if (typeof fn === 'function' && /load/i.test(ev)) listeners.push(fn); };
  const sb = {document, localStorage, console: {log(){}, error(){}, warn(){}, info(){}},
              alert(){}, confirm(){ return true; }, prompt(){ return ''; },
              setTimeout(){ return 0; }, clearTimeout(){}, setInterval(){ return 0; }, clearInterval(){},
              requestAnimationFrame(){ return 0; }, fetch(){ return new Promise(() => {}); },
              navigator: any(), location: any(), history: any()};
  sb.window = sb; sb.self = sb;
  sb.addEventListener = (ev, fn) => { if (typeof fn === 'function' && /load/i.test(ev)) listeners.push(fn); };
  const ctx = vm.createContext(sb);
  try {
    vm.runInContext(code, ctx, {timeout: 2000});
    for (const fn of listeners) fn.call(sb, any());
    if (typeof sb.onload === 'function') sb.onload(any());
  } catch (e) { out.load_error = String(e).slice(0, 200); }
  try {
    let v;
    for (const expr of phases[i]) v = vm.runInContext(expr, ctx, {timeout: 1000});
    out.value = (v === undefined) ? null : JSON.parse(JSON.stringify(v));
  } catch (e) { out.error = String(e).slice(0, 200); out.value = null; }
}
console.log(JSON.stringify(out));
"""
WORK = Path(tempfile.mkdtemp(prefix="ap1_"))
(WORK / "harness.js").write_text(HARNESS_JS)

def run_js(script: str, phases: list) -> dict:
    """Run the app's inline script in the fake page. Untrusted code: subprocess + timeout."""
    if not NODE:
        return {"skipped": True}
    d = Path(tempfile.mkdtemp(dir=WORK))
    (d / "app.js").write_text(script)
    (d / "phases.json").write_text(json.dumps(phases))
    try:
        r = subprocess.run([NODE, str(WORK / "harness.js"), str(d / "app.js"), str(d / "phases.json")],
                           capture_output=True, text=True, timeout=10)
        return json.loads(r.stdout.strip().splitlines()[-1])
    except subprocess.TimeoutExpired:
        return {"load_error": "timeout", "error": "timeout", "value": None}
    except Exception as e:
        return {"load_error": f"harness failed: {e}", "error": "harness failed", "value": None}

print(run_js("window.app = {double: x => 2*x}; localStorage.setItem('k','1');",
             [["app.double(21)"]]))
print(run_js("const app = {n: () => Number(localStorage.getItem('k') || 0), inc(){ localStorage.setItem('k', this.n()+1); }};",
             [["app.inc()", "app.inc()"], ["app.n()"]]))       # survives the "refresh"

3. The checklist as a dependency graph

Each check has a weight, a flag for core (explicitly asked) vs. implicit (a good app would do it), and a list of checks it depends on. If a parent fails, its children are skipped and score 0, the same "conditional test execution" AppBench uses so one missing button doesn't cause a pile of confusing failures.

ap1_appbench.ipynb · cell 5
def static(fn):
    return ("static", fn)

def js(phases, expected):
    return ("js", (phases, expected))

def same(got, want):
    if isinstance(want, (int, float)) and isinstance(got, (int, float)) and not isinstance(got, bool):
        return abs(got - want) < 0.011
    return got == want

def grade(name: str, html: str, verbose=False) -> dict:
    page = Page(html)
    script = "\n;\n".join(page.scripts)
    results, earned, total, core_earned, core_total = {}, 0, 0, 0, 0
    for cname, w, core, deps, (kind, arg) in SPECS[name]["checks"]:
        total += w; core_total += w if core else 0
        if any(not results.get(d, (False,))[0] for d in deps):
            results[cname] = (False, "skipped: depends on " + ", ".join(deps))
        elif kind == "static":
            try:
                ok = bool(arg(page))
            except Exception as e:
                ok = False
            results[cname] = (ok, "")
        else:
            phases, want = arg
            r = run_js(script, phases)
            if r.get("skipped"):                     # no node: weak fallback, function names must at least appear
                names = set(re.findall(r"app\.(\w+)\(", " ".join(sum(phases, []))))
                ok = bool(script) and all(re.search(rf"\b{n}\b", script) for n in names)
                results[cname] = (ok, "weak check (no node)")
            else:
                ok = r.get("error") is None and same(r.get("value"), want)
                why = "" if ok else f"got {r.get('value')!r}, want {want!r}" + (f"; error: {r['error']}" if r.get("error") else "") \
                      + (f"; page script error: {r['load_error']}" if r.get("load_error") else "")
                results[cname] = (ok, why)
        if results[cname][0]:
            earned += w; core_earned += w if core else 0
    out = {"score": round(100 * earned / total, 1), "core": round(100 * core_earned / max(core_total, 1), 1), "checks": results}
    if verbose:
        for c, (ok, why) in results.items():
            print(f"  {'✓' if ok else '✗'} {c}  {why}")
    return out

5. Let the model build the five apps (one shot)

Like the paper's "one-shot regime": same prompt shape for every task, one turn, no feedback.

BUILD = ("You are an expert front-end developer. Build this web app as ONE complete HTML file with all CSS and "
         "JavaScript inline. Do not load any external scripts, fonts or libraries.\n\nAPP REQUEST:\n{spec}\n\n"
         "Return only the file inside a ```html code block.")

def extract_html(text: str) -> str:
    m = re.search(r"```(?:html)?\s*(.*?)```", text or "", re.S | re.I)
    if m and "<" in m.group(1):
        return m.group(1).strip()
    m = re.search(r"(<!DOCTYPE.*?</html>|<html.*?</html>)", text or "", re.S | re.I)
    return m.group(1) if m else (text or "")

def build(name):
    try:
        return extract_html(ask(BUILD.format(spec=SPECS[name]["spec"]), temperature=0, max_tokens=3000))
    except Exception as e:
        print(name, "generation failed:", e)
        return ""

with ThreadPoolExecutor(2) as ex:
    apps = dict(zip(SPECS, ex.map(build, SPECS)))
one_shot = {}
for name, html in apps.items():
    (OUT / f"{name}.html").write_text(html)
    one_shot[name] = grade(name, html)
    print(f"\n{name} (L{SPECS[name]['level']}): score {one_shot[name]['score']} · core {one_shot[name]['core']}")
    grade(name, html, verbose=True)

6. Does an "agent loop" help? Build → grade → fix once

The paper found agent products only modestly better than one-shot models. Here the "agent" gets the names of its failed checks (not the hidden test code) and one chance to fix the file. Each fix is one more model call.

ap1_appbench.ipynb · cell 9
FIX = ("Here is a web app you built and the user tests it failed.\n\nAPP REQUEST:\n{spec}\n\nFAILED CHECKS:\n{fails}\n\n"
       "CURRENT FILE:\n```html\n{html}\n```\n\nReturn the complete corrected file inside a ```html code block.")

def fix(name):
    g = one_shot[name]
    fails = [f"- {c}: {why}" for c, (ok, why) in g["checks"].items() if not ok]
    if not fails:
        return apps[name]                            # nothing to fix, no call spent
    try:
        return extract_html(ask(FIX.format(spec=SPECS[name]["spec"], fails="\n".join(fails), html=apps[name][:12000]),
                                temperature=0, max_tokens=3000))
    except Exception as e:
        print(name, "fix failed:", e)
        return apps[name]

with ThreadPoolExecutor(2) as ex:
    fixed = dict(zip(SPECS, ex.map(fix, SPECS)))
with_fix = {n: grade(n, h) for n, h in fixed.items()}
print(f"{'task':20s} level  one-shot  after-fix")
for n in SPECS:
    print(f"{n:20s}  L{SPECS[n]['level']}    {one_shot[n]['score']:6.1f}    {with_fix[n]['score']:6.1f}")
mean = lambda d: sum(v["score"] for v in d.values()) / len(d)
print(f"mean                       {mean(one_shot):6.1f}    {mean(with_fix):6.1f}")

What to notice. Scores usually fall as the level goes up, as in the paper. Look at which checks fail: implicit checks (blank tasks, unknown items) and saved state across a refresh are the usual misses. A fix round with precise failure messages often helps a lot here, because our checks name the exact problem. In AppBench the agents got no such feedback, which is one reason their edge over one-shot was small.

# 2. Spearman correlation between your scores and the grader's. Replace my_scores with your own numbers.
def spearman(a, b):
    def ranks(x):
        order = sorted(range(len(x)), key=lambda i: x[i]); r = [0.0] * len(x)
        i = 0
        while i < len(x):                                  # average ranks for ties
            j = i
            while j + 1 < len(x) and x[order[j + 1]] == x[order[i]]:
                j += 1
            for k in range(i, j + 1):
                r[order[k]] = (i + j) / 2
            i = j + 1
        return r
    ra, rb = ranks(a), ranks(b); n = len(a)
    ma, mb = sum(ra) / n, sum(rb) / n
    cov = sum((x - ma) * (y - mb) for x, y in zip(ra, rb))
    sd = (sum((x - ma) ** 2 for x in ra) * sum((y - mb) ** 2 for y in rb)) ** 0.5
    return cov / sd if sd else 0.0

# 3. A text-only LLM judge (5 calls). Notice how often it gives high scores to apps whose logic is broken:
#    a judge that reads code can't "click", which is why AppBench simulated real interaction.
def judge(name):
    reply = ask(f"APP REQUEST:\n{SPECS[name]['spec']}\n\nHTML FILE:\n```html\n{fixed[name][:8000]}\n```\n\n"
                "Score how well this file meets the request, 0 to 10. End with a line 'SCORE: <number>'.", max_tokens=400)
    m = re.findall(r"SCORE:\s*(\d+(?:\.\d+)?)", reply or "")
    return float(m[-1]) * 10 if m else 50.0
with ThreadPoolExecutor(2) as ex:
