Augmenting agents with memory

Open in Colab
13 min readPlain-English lesson, then the deeper material

How to give an agent more memory than it can read at once. You'll understand MemGPT's paging, KV-cache reuse (CacheBlend, LMCache) and trained memories called Cartridges.

The big idea

A model only sees its context window (the text it can read in one call). Everything else is invisible to it. And long contexts are slow and costly, because the model must read every word before it answers.

Think of a lawyer with a small desk and a big filing room. Only a few pages fit on the desk. The rest live in the filing room. A good lawyer keeps sticky notes, fetches files when needed, and doesn't reread a contract from scratch every time someone asks a question about it.

This lesson gives an agent that same kind of memory, at three layers. The agent can manage its own desk and filing room (MemGPT). The server can keep its work on text it already read (KV-cache reuse). Or we can study a big document once, ahead of time, and keep a compact memory of it (Cartridges).

Why it matters for us

  • A firm's local model may have a small window and a modest GPU (graphics chip). Its contract archive is far bigger than any window.
  • The same playbook and the same contract get sent to the model again and again. Reusing work on that text is often the cheapest speed-up you can get, before buying more hardware.

How it works, step by step

  1. MemGPT: the agent manages its own memory (the MemGPT paper, 2023). It borrows an idea from computers, where fast RAM is small and the disk is big. Main context is what the model sees: fixed instructions, a small working context (a notepad the agent writes into), and a queue of recent messages. External context sits outside: every past message, plus a searchable store of documents. The agent moves things in and out by calling tools, like "search" and "save note". When the window is about 70% full, the system warns the agent to save what matters. When it is full, old messages drop off the desk but stay in storage. In the paper, GPT-4's accuracy at recalling facts from past chat sessions went from 32.1% to 92.5% with MemGPT.

  2. KV cache, from zero. Before writing its first word, a model reads the whole prompt. This is called prefill. As it reads, it writes a kind of margin note for every word, at every layer of the network. These notes are called keys and values, and together they are the KV cache. Think of them as the model's highlighted, annotated copy of the text. Prefill takes longer for longer prompts. That delay is the time to first token: how long the user waits for the answer to start.

  3. Prefix caching: reuse the annotated copy. If the next prompt starts with the exact same text, the server can reuse those notes and skip rereading. That is prefix caching. But it is all or nothing from the first change. Change one word at the very start and every note after it is useless. The model rereads everything.

  4. CacheBlend: reuse chunks anywhere (the CacheBlend paper, 2024). In RAG (where retrieved documents are pasted into the prompt), each request glues together different chunks in a different order. Prefix caching misses. CacheBlend reuses each chunk's saved notes wherever it sits. It then recomputes only a small share of words, 15% per layer by default. It picks the words whose notes would change most because of the text before them. This cut the wait for the first token 2.2 to 3.3 times, with about the same quality. LMCache (2025), from the guest lecturer's group, is open-source software that stores these caches outside GPU memory and shares them across servers.

  5. Cartridges: study once, answer many times (the Cartridges paper, 2025). Instead of rereading a huge corpus for every question, train a small KV cache for it ahead of time. Load that small "cartridge" at question time. The training recipe is self-study. The model asks itself varied questions about each chunk, like "summarize this" or "ask a question", and answers them with the chunk in view. The cartridge is then trained to make the model answer the same way without the chunk. The paper reports matching full-text quality with 38.6x less memory. Training on the raw text alone did not generalize well. The varied conversations are what made it work.

Tool Layer Best when
MemGPT paging the agent many documents, agent picks what to read
Prefix / KV caching the server the same long text is sent again and again
Cartridges trained ahead one big corpus, asked thousands of times

Worked example

The firm asks: "What is the total monthly fee across these four vendor contracts?" The notebook's agent has a window of 2,500 characters. The four contracts together are about 7,000 characters. They don't fit.

So the agent works like a lawyer at a small desk. It searches for contract one. The fee appears. It writes "Contract 1: fee X" in its working-context notepad. As it searches for contract two, the old search result falls off the desk. But the note stays. After four rounds it adds up its notes and answers.

The weak spot: if the agent forgets to write a note, that fee is gone from view. The model, not the system, decides what to remember.

Now the caching part. The notebook sends 8 contracts plus question A. That is slow, because nothing is cached. Then the same 8 contracts plus question B. That is much faster: the contracts' notes are reused. Then it changes one word at the start of the contracts. Slow again.

The rule you can use today: put stable text first (instructions, the playbook, the contract), and the changing question last. Never put a timestamp at the top of a prompt.

Common mistakes

  • A timestamp, request ID or user name at the top of the prompt. It changes the first words, so the cache never hits.
  • Trusting the agent to save notes. It may skip one. Keep every message in storage and test what it can recall.
  • Training a compact memory on raw text alone. It memorizes but doesn't generalize. Use varied self-study questions.
  • Timing the first call after loading the model. Load time swamps everything. Warm up first.

Check your understanding

Why does changing the first word of a long prompt make it slow again?

Prefix caching only reuses notes for an exact matching start. A change at the start breaks everything after it, so the whole prompt is read again.

In MemGPT, what survives when old messages drop out of the window?

The working-context notes, a running summary, and the full messages in storage, which the agent can search.

What does CacheBlend recompute, and why not nothing?

A small share of words whose notes change most because of earlier chunks. Recomputing nothing ignores how chunks affect each other, and quality drops.

A model only sees its context window, and long contexts are slow and costly. You can give an agent more memory at three layers: let the agent page facts in and out (MemGPT), let the server reuse work it already did on the same text (KV-cache reuse: CacheBlend, LMCache), or compress a corpus into a small trained memory ahead of time (Cartridges).

Key terms

Context window
The text a model can see in one call. Everything else is invisible to it.Source: general
Main context / external context
MemGPT's split: what is in the prompt now vs what is stored outside and must be fetched with a function call.Source: Packer et al. 2023
Working context
A small, writable block of notes inside the prompt that survives when old messages are evicted.Source: Packer et al. 2023
Archival storage
A searchable store of documents outside the window; the agent pages results in.Source: Packer et al. 2023
KV cache
The key and value vectors a transformer computes for every prompt token at every layer. Reusing them skips re-reading that text.Source: general
Prefill
The step where the model reads the whole prompt before writing; its time grows with prompt length.Source: general
Time to first token (TTFT)
How long a user waits before the first word appears; dominated by prefill on long prompts.Source: Yao et al. 2024
Prefix caching
Reusing the KV cache when a new prompt starts with exactly the same text as an earlier one.Source: general
KV deviation
How much a token's cached KV differs from what full recompute would give; CacheBlend recomputes the tokens with the largest deviation.Source: Yao et al. 2024
Cartridge
A small trained KV cache that stands in for a whole corpus at question time.Source: Eyuboglu et al. 2025
Self-study
Training data for a Cartridge: the model's own synthetic conversations about chunks of the corpus.Source: Eyuboglu et al. 2025
Context distillation
Training the model-with-Cartridge to match the next-token probabilities of the model-with-full-text.Source: Eyuboglu et al. 2025

The papers

Cartridges: Lightweight and general-purpose long context representations via self-study

Eyuboglu, Ehrlich, Arora, Guha, Zinsley, Liu, Tennien, Rudra, Zou, Mirhoseini, Ré · 2025

What
Train a small KV cache (a 'Cartridge') offline for each corpus and load it at question time instead of the whole corpus. Training on the raw text with next-token prediction generalized poorly, so they propose self-study: the model has synthetic conversations about chunks of the corpus (from generic seed prompts such as summarize, structure, ask a question), and the Cartridge is trained by context distillation to match the model's next-token distributions when the chunk is in context.
Result
Matched in-context learning quality on long-context benchmarks with 38.6x less memory and 26.4x higher throughput. Extended effective context on MTOB from 128k to 484k tokens. Distillation beat next-token training on MTOB (chrF 24.9 to 33.5). Initializing from the first p corpus tokens beat random vectors on LongHealth (55.3% vs 29.9%). Prefix-tuning kept MMLU near 54.7 while a memory-matched LoRA fell to 45.3. Cartridges can be composed at inference without retraining.
Takeaway
If one large corpus (a contract archive, a codebase) is queried thousands of times, paying once to train a compact memory can beat re-reading it each time. The training data must be varied synthetic Q&A, not the raw text.

MemGPT: Towards LLMs as Operating Systems

Packer, Wooders, Lin, Fang, Patil, Stoica, Gonzalez · 2023

What
Virtual context management modeled on an operating system's memory hierarchy. Main context = read-only system instructions, a writable working context, and a FIFO message queue headed by a recursive summary. External context = recall storage (all messages) and archival storage (vector-searched text). The model moves data with function calls; results are paginated; a memory-pressure warning fires at about 70% of the window and about half the queue is evicted at 100%.
Result
Deep memory retrieval in multi-session chat: GPT-4 accuracy 32.1% without MemGPT vs 92.5% with it (GPT-4 Turbo 35.3% vs 93.4%; GPT-3.5 Turbo 38.7% vs 66.9%). On nested key-value retrieval, GPT-4 and GPT-4 Turbo alone fell to 0% by 3 nesting levels, while MemGPT with GPT-4 was unaffected by depth. On document QA, MemGPT's accuracy stayed flat as more documents were retrieved, while fixed-context baselines were capped by the retriever.
Takeaway
Give the agent explicit memory tools (search, save a note) and a hard context budget, and keep every message in an append-only store. Check that the agent actually saves what it needs: the model decides what to remember.

CacheBlend: Fast Large Language Model Serving for RAG with Cached Knowledge Fusion

Yao, Li, Liu, Ray, Cheng, Zhang, Du, Lu, Jiang · 2024

What
Prefix caching only helps when a request starts with exactly the same text, which RAG rarely does. CacheBlend reuses each retrieved chunk's precomputed KV cache wherever it sits, and recomputes only a small share of tokens (15% per layer by default) chosen by KV deviation, the tokens whose KV values change most from cross-attention to earlier chunks. Recompute overlaps with loading caches from slower storage.
Result
Tested on Mistral-7B, Yi-34B and Llama-70B over 2WikiMQA, Musique, SAMSum and MultiNews. Versus full KV recompute: time to first token 2.2-3.3x lower and throughput 2.8-5x higher, with quality within 0.02 F1/Rouge-L. Recomputing 5-18% of tokens lost at most 0.002 F1/Rouge-L on Yi-34B. Full KV reuse without recompute was about as fast but lost 0.1-0.2 F1 on QA.
Takeaway
For RAG on your own GPUs, the prefill of retrieved chunks is the main latency cost. Cache chunk KV and use a serving stack that can blend it (LMCache with vLLM). Even without that, put stable text first so plain prefix caching hits.

LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference (background reading, our pick)

Cheng, Liu, et al. (with Junchen Jiang) · 2025

What
The open-source KV cache layer from the guest lecturer's group. It moves KV caches out of GPU memory into CPU, disk or network storage and shares them across vLLM/SGLang engines and queries, supporting both prefix reuse across queries and prefill-decode disaggregation. Not an assigned course paper; added because the guest lecture is about it.
Result
The authors report up to 15x higher throughput when combined with vLLM on workloads such as multi-round QA and document analysis, and observe that context truncation, common in industry, can cut prefix cache hit ratio by half.
Takeaway
If you self-host models for repeated document work, a KV cache layer is often the cheapest speed-up available, before buying more GPUs.

1. MemGPT: an agent that manages its own memory

MemGPT (Packer et al. 2023, MemGPT: Towards LLMs as Operating Systems) splits memory into tiers, like RAM and disk: - Main context (what the model sees): fixed system instructions, a small working context the agent writes notes into, and a FIFO queue (first in, first out) of recent messages. - External context (outside the window): recall storage, every message ever, and archival storage, a searchable store of documents.

The agent moves data between tiers by calling functions. When the prompt reaches about 70% of the window, the system adds a "memory pressure" warning so the agent saves what matters. When it is full, old messages are evicted (they stay in recall storage). Search results come back in pages, so one search can never flood the window.

First the pure-Python parts: an archival store with a small TF-IDF search (a word-overlap score that weights rare words more), and a main context with a character budget.

a09_memory.ipynb · cell 3
def tokenize(s):
    return re.findall(r"[a-z0-9_]+", s.lower())

class ArchivalStore:
    """Archival storage: text passages plus a tiny TF-IDF search. Results come back in pages."""
    def __init__(self, passages):
        self.passages = passages
        self.docs = [Counter(tokenize(p)) for p in passages]
        df = Counter(w for d in self.docs for w in d)
        self.idf = {w: math.log(1 + len(passages) / c) for w, c in df.items()}

    def search(self, query, page=0, page_size=3):
        q = set(tokenize(query))
        named = {w for w in q if re.fullmatch(r"msa_\d+", w)}      # a contract id in the query acts as a filter
        scores = [(sum(d[w] * self.idf.get(w, 0) for w in q) / (1 + sum(d.values())) ** 0.5, i)
                  for i, d in enumerate(self.docs) if not named or named & set(d)]
        ranked = [i for s, i in sorted(scores, reverse=True) if s > 0]
        hits = ranked[page * page_size:(page + 1) * page_size]
        more = len(ranked) > (page + 1) * page_size
        out = "\n".join(f"- {self.passages[i]}" for i in hits) or "(no results)"
        return out + (f"\n[page {page}; more results: call again with page={page + 1}]" if more else f"\n[page {page}; no more results]")

# One passage per contract section, tagged with the contract id so the search can find it.
PASSAGES = [f"[{cid} section {s['id']} {s['title']}] {s['text']}" for cid in ids() for s in sections(contract(cid))]
store = ArchivalStore(PASSAGES)
print(len(PASSAGES), "passages in archival storage")
print(store.search("msa_07 fees per month"))

class MainContext:
    """Main context = system prompt + working context + FIFO queue, kept under a character budget.
    The queue holds 'units' (one assistant turn plus its tool results), so we never split a tool call from its result."""
    def __init__(self, system, budget_chars=2500, warn_at=0.7):
        self.system, self.budget, self.warn_at = system, budget_chars, warn_at
        self.working = []          # notes the agent chose to keep (read/write via a tool)
        self.queue = []            # list of units; each unit is a list of messages
        self.recall = []           # recall storage: every message ever, never deleted
        self.evicted = 0

    def size(self):
        return len(self.render_system()) + sum(len(json.dumps(m)) for u in self.queue for m in u)

    def render_system(self):
        notes = "\n".join(f"- {n}" for n in self.working) or "(empty)"
        return f"{self.system}\n\nWORKING CONTEXT (your saved notes):\n{notes}"

    def add(self, unit):
        self.queue.append(unit)
        self.recall.extend(unit)
        while self.size() > self.budget and len(self.queue) > 2:   # keep the task and the newest unit
            self.queue.pop(1)                                      # queue[0] is the user's task: never evicted
            self.evicted += 1

    def messages(self):
        msgs = [{"role": "system", "content": self.render_system()}]
        msgs += [m for u in self.queue for m in u]
        if self.evicted:
            msgs.insert(2, {"role": "user", "content": f"[system note: {self.evicted} older steps were evicted to recall storage. Your notes are in WORKING CONTEXT.]"})
        if self.size() > self.warn_at * self.budget:
            msgs.append({"role": "user", "content": "[system warning: memory pressure. Save any facts you still need with working_context_append now.]"})
        return msgs

Now the agent. It has three tools: archival_search, working_context_append and finish. The task needs facts from four different contracts, but the window budget (2,500 characters, about 600 tokens) is far smaller than the four contracts together (about 7,000 characters). So the agent must search, write a note, and let old results be evicted.

TOOLS = [
    {"type": "function", "function": {"name": "archival_search",
        "description": "Search archival storage (all contract sections). Include the contract id and topic in the query, e.g. 'msa_07 fees'. Results are paged.",
        "parameters": {"type": "object", "properties": {"query": {"type": "string"}, "page": {"type": "integer"}}, "required": ["query"]}}},
    {"type": "function", "function": {"name": "working_context_append",
        "description": "Save one short fact to your working context so it survives eviction, e.g. 'msa_07 fee = 4500'.",
        "parameters": {"type": "object", "properties": {"fact": {"type": "string"}}, "required": ["fact"]}}},
    {"type": "function", "function": {"name": "finish",
        "description": "Give the final answer.",
        "parameters": {"type": "object", "properties": {"answer": {"type": "string"}}, "required": ["answer"]}}},
]
SYSTEM = ("You are an agent with a small memory. Facts live in archival storage; search it one contract at a time. "
          "After each search, save the key number with working_context_append, because old search results will be evicted. "
          "When you have every fact, call finish.")

def memgpt_agent(task, budget_chars=2500, max_steps=14, verbose=True):
    ctx = MainContext(SYSTEM, budget_chars)
    ctx.add([{"role": "user", "content": task}])
    peak = 0
    for step in range(max_steps):
        msgs = ctx.messages()
        peak = max(peak, sum(len(json.dumps(m)) for m in msgs))
        msg = chat(msgs, tools=TOOLS)
        calls = msg.tool_calls or []
        if not calls:                        # the model answered in plain text: treat it as final
            return {"answer": msg.content or "", "steps": step + 1, "peak_chars": peak, "notes": ctx.working, "evicted": ctx.evicted}
        unit = [{"role": "assistant", "content": msg.content or "",
                 "tool_calls": [{"id": c.id, "type": "function", "function": {"name": c.function.name, "arguments": c.function.arguments}} for c in calls]}]
        for c in calls:
            try:
                args = json.loads(c.function.arguments or "{}")
            except Exception:
                args = {}
            name = c.function.name
            if name == "finish":
                return {"answer": str(args.get("answer", "")), "steps": step + 1, "peak_chars": peak, "notes": ctx.working, "evicted": ctx.evicted}
            if name == "archival_search":
                try:
                    result = store.search(str(args.get("query", "")), int(args.get("page", 0) or 0))
                except Exception as e:
                    result = f"ERROR: {e}"
            elif name == "working_context_append":
                ctx.working.append(str(args.get("fact", ""))[:200])
                result = "saved"
            else:
                result = f"ERROR: unknown tool {name}"
            if verbose:
                print(f"  step {step+1}: {name}({c.function.arguments[:60]}) -> {result[:70]!r}")
            unit.append({"role": "tool", "tool_call_id": c.id, "content": result})
        ctx.add(unit)
    return {"answer": "STOPPED: step limit", "steps": max_steps, "peak_chars": peak, "notes": ctx.working, "evicted": ctx.evicted}

def first_number(s):
    m = re.findall(r"\d[\d,]*", s or "")
    return int(m[-1].replace(",", "")) if m else None

TARGETS = ["msa_03", "msa_07", "msa_12", "msa_18"]
TRUTH = sum(LAB[c]["terms"]["monthly_fee"] for c in TARGETS)
task = f"What is the total monthly fee, in dollars, across contracts {', '.join(TARGETS)}? Answer with one number."
t0 = time.time()
out = memgpt_agent(task)
print(f"\n{out['steps']} steps in {time.time()-t0:.0f}s | peak prompt {out['peak_chars']} chars | evicted {out['evicted']} units")
print("notes:", out["notes"])
print("answer:", out["answer"], "| truth:", TRUTH)
print("the 4 contracts in full would be", sum(len(contract(c)) for c in TARGETS), "chars")

What to notice: the prompt never grew past the budget, yet the agent used facts from four contracts. The working-context notes are what made that work: when a search result was evicted, the number survived as a note. The weak spot is also clear: if the agent forgets to save a note, the fact is gone from its view (it is still in recall storage, but only a search would bring it back).

2. KV-cache reuse: why CacheBlend and LMCache matter

Before a model writes its first word it must read the whole prompt (the prefill). While reading, it builds a KV cache: key and value vectors for every token at every layer. Prefill time grows with prompt length, so a long prompt means a long wait for the first token (time to first token, TTFT).

If the next request starts with the exact same text, the server can reuse the cached keys and values and skip that work. This is prefix caching. Ollama does it automatically within one model slot. We measure it: 1. a long shared prefix (8 contracts) + question A (cold: nothing cached); 2. the same prefix + question B (warm: the prefix is reused); 3. one changed word at the start of the prefix + question A (everything after the change must be recomputed); 4. one changed word at the end of the prefix + question A (most of the prefix is still reusable).

Caveat: Ollama runs 2 slots here. If a request lands in the other slot, it will look "cold". Run the cell twice if the numbers look odd.

a09_memory.ipynb · cell 6
def ttft(prompt, max_tokens=8):
    """Time to the first streamed token, in seconds."""
    t0 = time.time()
    stream = client.chat.completions.create(model=MODEL, messages=[{"role": "user", "content": prompt}],
                                            temperature=0, max_tokens=max_tokens, stream=True)
    first = None
    for chunk in stream:
        if first is None and chunk.choices and (chunk.choices[0].delta.content or ""):
            first = time.time() - t0
    return first if first is not None else time.time() - t0

DOCS = ids()[:8]
PREFIX = "\n\n".join(f"=== {c} ===\n{contract(c)}" for c in DOCS)
QA = "\n\nQuestion: What governing law does msa_03 use? Answer in one word."
QB = "\n\nQuestion: What is the monthly fee in msa_05? Answer with a number."
ask("Say OK.", max_tokens=2)                      # load the model so loading time is not counted
results = {}
results["1 cold: new prefix"] = ttft(PREFIX + QA)
results["2 warm: same prefix, new question"] = ttft(PREFIX + QB)
results["3 changed first word of prefix"] = ttft("NOTE. " + PREFIX + QA)
results["4 changed last part of prefix"] = ttft(PREFIX + "\n(end of documents)" + QA)
for k, v in results.items():
    print(f"{k:38} TTFT {v:5.2f}s")
print(f"prefix is about {len(PREFIX)//4} tokens")

What to notice: the warm request should be much faster than the cold one, and changing the very first word should make it slow again. Prefix caching is all or nothing from the point of change: one new word at the start throws away the whole cache.

That is the problem in RAG (retrieval-augmented generation), where each request glues together different retrieved chunks in a different order. Each chunk may have been seen before, but never with the same prefix, so prefix caching misses. CacheBlend (Yao et al. 2024, CacheBlend: Fast LLM Serving for RAG with Cached Knowledge Fusion) reuses each chunk's cached KV even when it is not at the start, and recomputes only a small share of tokens (15% per layer by default), the ones whose KV values would change most because of the text before them. It cut TTFT 2.2-3.3x versus full recompute with about the same quality. LMCache (Cheng et al. 2025, LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference) is the open-source layer that stores these caches outside GPU memory (CPU, disk, network) and shares them across vLLM/SGLang engines and queries.

Builder rule you can use today: put stable text first (system prompt, rules, documents) and changing text last (the question). Never put a timestamp at the top of a prompt.

3. Cartridges: study the document once, answer many questions cheaply

Cartridges (Eyuboglu et al. 2025, Cartridges: Lightweight and general-purpose long context representations via self-study) train a small KV cache for one document collection, offline. At question time the model loads this small cache instead of the whole document. The training recipe is self-study: 1. split the corpus into chunks; 2. the model talks to itself about each chunk: one copy asks (from generic seed prompts like "summarize", "structure", "ask a question"), another answers with the chunk in view; 3. train the small cache with context distillation: make the model with the cartridge produce the same next-token probabilities as the model with the full chunk in context.

The paper reports matching in-context quality with 38.6x less memory and 26.4x higher throughput. Training a cartridge needs gradient access to the KV vectors, which Ollama does not give us. So we build a text analogy: self-study generates Q&A, the Q&A becomes compact "study notes", and we compare answering from notes vs from the full document. The real method trains vectors, not text.

CORPUS = ids()[6:12]                           # 6 contracts, mostly ones with issues

def self_study(cid):
    """Self-study on one chunk: generic seed prompts, the chunk in view. Returns synthetic Q&A text."""
    chunk = f"=== {cid} ===\n{contract(cid)}"
    return cid, "\n".join(ask(f"{chunk}\n\n{p}", max_tokens=300) for p in SEEDS.values())

with ThreadPoolExecutor(2) as ex:                # 6 contracts x 2 seeds = 12 calls
    studied = dict(ex.map(self_study, CORPUS))

notes = []
for cid in CORPUS:                               # compress each chunk's study output into a short card (6 calls)
    card = ask(f"Study notes for contract {cid}:\n{studied[cid]}\n\nCompress these into at most 6 short lines of the form "
               f"'{cid} <term>: <value>'. Keep numbers and state names exact.", max_tokens=200)
    notes.append(card.strip())
CARTRIDGE = "\n".join(notes)
print(CARTRIDGE[:800])
print(f"\nfull document: {len(FULL_DOC)} chars | cartridge: {len(CARTRIDGE)} chars ({len(FULL_DOC)/max(len(CARTRIDGE),1):.1f}x smaller)")

def answer_with(context, q):
    return ask(f"{context}\n\n{q}", max_tokens=20).strip().lower()

def grade(pred, gold):
    words = re.sub(r"[^a-z0-9 ]", " ", pred).split()
    return gold in words if gold.isdigit() else gold in pred

def run(context):
    with ThreadPoolExecutor(2) as ex:
        preds = list(ex.map(lambda qg: answer_with(context, qg[0]), QS))
    return sum(grade(p, g) for p, (_, g) in zip(preds, QS)) / len(QS), preds

acc_full, _ = run(FULL_DOC)                       # 8 calls
acc_cart, preds_cart = run(CARTRIDGE)             # 8 calls
print(f"full document in context: {acc_full:.0%} | cartridge notes: {acc_cart:.0%} | size ratio {len(FULL_DOC)/max(len(CARTRIDGE),1):.1f}x")
for (q, g), p in zip(QS, preds_cart):
    print(f"  {'ok ' if grade(p, g) else 'MISS'} {q[:55]:55} -> {p[:25]!r} (truth {g})")

What to notice: the notes are several times smaller, and on facts that the generic seeds happened to cover, they do about as well. Facts that self-study never touched are simply missing. The paper saw the same thing in a sharper form: training on the raw text with plain next-token prediction memorized it but generalized poorly, and the varied synthetic conversations of self-study were what made cartridges work across question types. Composition also works there: two cartridges can be loaded together without retraining.

When is each tool right? - MemGPT-style paging: many documents, the agent decides what to look at, and you want an audit trail of what it read. - Prefix / KV caching: the same long text is sent again and again (system prompt, playbook, a contract under review). Free speed-up; just keep stable text first. - Cartridges: one large corpus queried thousands of times (a codebase, a company's contract archive). Pay once to train, then serve cheaply.

Traps
  • Putting a timestamp, request ID or user name at the top of the prompt. It changes the first tokens, so prefix caching never hits.
  • Trusting the agent to save notes. In MemGPT-style paging the model decides what to remember; if it skips a note, the fact is gone from view. Log everything and test recall.
  • Training a compact memory on the raw text with next-token prediction. Cartridges found it memorizes but does not generalize; the varied synthetic conversations are what make it work.
  • Measuring TTFT with the first call after loading the model. Load time swamps everything; warm up first.
  • Assuming two requests share a cache. Servers with several slots or replicas may route them apart; LMCache exists partly to share caches across engines.

Check yourself

Why does changing the first word of a long prompt make it slow again?

Prefix caching only reuses KV for an exact matching prefix; a change at the start invalidates everything after it, so the whole prompt is prefilled again.

In MemGPT, what survives when old messages are evicted from the FIFO queue?

The working context notes, a recursive summary, and the full messages in recall storage (retrievable by search).

What does CacheBlend recompute, and why not nothing?

A small share of tokens (15% per layer by default) with the highest KV deviation; reusing caches with no recompute ignores cross-attention between chunks and loses quality.

How is a Cartridge trained?

With self-study: the model generates synthetic conversations about corpus chunks, and a small KV cache is trained by context distillation to match the model's outputs when the chunk is in context.

Our notebook's 'cartridge' is text notes. What is the real one?

A set of trainable key and value vectors (a prefix-tuning style KV cache), trained with gradients while the model weights stay frozen.
