Augmenting agents with memory

Open in Colab

Give an agent more memory than its context window. MemGPT pages facts in and out, KV-cache reuse skips rereading (CacheBlend, LMCache), Cartridges study a corpus once.

Learning objective

1/64
  • Choose between three ways to give an agent more memory: agent paging (MemGPT), KV-cache reuse (CacheBlend, LMCache), and trained memory (Cartridges).
Part 1Why this lecture: the context window is the bottleneck

Why memory?

2/64
  • Context window: the text a model can see in one call. Everything else is invisible.
  • Prefill: the model reads the whole prompt before writing. Longer prompt, longer wait.
  • A contract archive is far bigger than any window.
  • The same playbook and contracts are sent again and again.

Two costs of long context

3/64
Problem Example from the papers
Doesn't fit SEC 10-K filings "can easily pass the million token mark" (MemGPT)
Fits, but slow Prefill of a 4,000-token input: about 3 s (Llama-34B) or 6 s (Llama-70B) on one A40 GPU (CacheBlend)
Fits, but uses lots of memory LLaMA 70B needs 84 GB at 16-bit for one question over 128k tokens (Cartridges)
Fits, but used badly Long-context models recall the start and end better than the middle (Liu et al. 2023, cited by MemGPT)

Three layers

4/64
Tool Layer Best when
MemGPT paging the agent many documents; the agent picks what to read; you want an audit trail
Prefix / KV caching (CacheBlend, LMCache) the server the same long text is sent again and again
Cartridges trained ahead one big corpus, queried thousands of times

The four papers

5/64
Paper Main idea Headline result
MemGPT (Packer et al., UC Berkeley, 2023) OS-style memory tiers; the LLM pages data with function calls Deep memory retrieval, GPT-4: 32.1% → 92.5% (Table 2)
CacheBlend (Yao et al., UChicago, EuroSys 2025) Reuse KV caches of RAG chunks anywhere; recompute ~15% of tokens TTFT 2.2–3.3x lower, throughput 2.8–5x higher
LMCache (Liu, Yao, Cheng et al., 2025; background, not assigned) Open-source KV cache layer outside the GPU Up to 15x throughput with vLLM (authors' report)
Cartridges (Eyuboglu, Ehrlich, Arora et al., Stanford, 2025) Train a small KV cache per corpus with self-study ICL quality with 38.6x less memory, 26.4x more throughput
Part 2MemGPT (Packer et al. 2023)

The problem

6/64
  • LLMs support only a few dozen messages or a short document before the window fills.
  • Longer context costs quadratic time and memory in self-attention.
  • Even long-context models struggle to use extra context well.
  • Idea: give the illusion of infinite context while keeping a fixed-context model.
  • Borrowed from operating systems: virtual memory pages data between RAM and disk.

The OS analogy

7/64
Operating system MemGPT
Physical memory (RAM) Main context: the prompt tokens
Disk External context: databases outside the window
Page fault: load data back from disk Function call: search and pull data into the prompt
Interrupts and events User messages, system alerts, timers trigger the LLM

Memory tiers (Figure 3)

8/64
Main context (in the prompt) External context (outside)
System instructions (read-only) Recall storage: every message ever
Working context: writable notes Archival storage: searchable documents (any length text)
FIFO queue of recent messages Fetched only with a function call
  • FIFO: first in, first out. Oldest messages leave first.
  • Queue slot 0: a recursive summary of all evicted messages.
  • Working context: key facts, user preferences, the agent's persona. Writable only via function calls.

Queue manager: eviction policy

9/64
  • Each new message: append to the FIFO queue, run the LLM, write input and output to recall storage.
  • Warning token count (e.g. 70% of the window): insert a "memory pressure" system message.
    • The agent should save important facts to working context or archival storage
  • Flush token count (e.g. 100%): evict a set of messages (e.g. 50% of the window).
    • Write a new recursive summary from the old summary + evicted messages
  • Evicted messages stay in recall storage forever, searchable.

Function executor

10/64
  • LLM output is parsed as a function call; arguments checked; function run.
  • Results and errors (e.g. "main context is full") go back to the LLM: a feedback loop.
  • Memory edits and searches are self-directed: the model decides what to save and fetch.
  • System instructions describe the memory tiers and give a function schema.
  • Retrieval is paginated, so one search can't overflow the window.

Control flow and function chaining

11/64
  • Events trigger inference: user messages, system warnings, user actions (logged in, upload done), scheduled timers.
  • Function chaining: a call with request_heartbeat=true returns control to the LLM right away.
    • Lets the agent page through results or combine several searches before replying
  • No heartbeat flag = yield: wait for the next outside event.

Memory in action (Figures 1, 2, 4)

12/64
  • Memory pressure alert → working_context.append("Birthday is February 7"), append("Boyfriend named James").
  • User mentions Six Flags → recall_storage.search("six flags") finds "james and I actually first met at six flags".
  • User says they broke up → working_context.replace("Boyfriend named James", "Ex-boyfriend named James").
  • The agent edits its own memory as facts change.

Conversational agents: setup

14/64
  • Two goals: consistency (remember facts and stay coherent) and engagement (use long-term knowledge to personalize).
  • Dataset: Multi-Session Chat (MSC): 5 sessions per chat, about a dozen messages each, consistent personas.
  • New session 6: one question-answer pair about earlier sessions.
  • Baselines see a lossy summary of the 5 sessions; MemGPT sees full history but only through paginated search.

Document QA (Figures 5, 6)

17/64
  • Task: NaturalQuestions-Open question; a retriever finds Wikipedia passages; the LLM answers.
  • 50 sampled questions; late-2018 Wikipedia dump; OpenAI text-embedding-ada-002; PostgreSQL + pgvector with an HNSW index.
  • Fixed-context baselines: capped by the retriever. If the gold passage isn't in the top K, they never see it.
  • Baselines past their window: truncate passages → accuracy drops.
  • MemGPT pages through archival search; accuracy stays flat as documents increase.
    • Example: archival_storage.search("nobel physics", page=2) → "Wilhelm Conrad Rontgen"

Document QA: caveats

18/64
  • Gold passage often appears outside the first dozen results.
  • MemGPT often stops paging before exhausting the retriever.
  • MemGPT with GPT-3.5 does much worse: weak function calling.
  • MemGPT with GPT-4 and GPT-4 Turbo: equivalent results.

Nested key-value retrieval (Figures 7, 8)

19/64
  • Keys and values are 128-bit UUIDs; a value can itself be a key (multi-hop lookup).
  • 140 UUID pairs, about 8k tokens; nesting levels 0 to 4; 30 orderings.
  • Results:
    • GPT-3.5: 0% at 1 nesting level (returns the first value)
    • GPT-4 and GPT-4 Turbo: 0% by 3 nesting levels
    • MemGPT + GPT-4: unaffected by depth
    • MemGPT + GPT-4 Turbo and GPT-3.5: better than baselines, but drop at 2 levels
  • MemGPT stops when a search for the value returns only one result (so it is not also a key).

Limitations

20/64
  • Depends on the model's function-calling skill (GPT-3.5 struggles).
  • The model decides what to save: if it skips a note, the fact leaves the window.
  • Stops searching early on document QA.
  • Future work named: other domains, other memory tiers (databases, caches), better memory policies.
Part 3CacheBlend (Yao et al. 2024)

KV cache basics

21/64
  • KV cache: key and value vectors the model computes for every prompt token at every layer.
  • Prefill: compute the KV cache for the whole input, layer by layer.
  • Decode: generate tokens one by one, appending new K and V.
  • Time to first token (TTFT): how long until the first word appears; set by prefill on long prompts.
  • Prefill time grows super-linearly with input length.

Three existing options (Figure 1)

22/64
Method Speed Quality Why
Full KV recompute Slowest Good Prefill everything every time
Prefix caching Marginally faster for RAG Good Reuses KV only for an exact matching start; only chunk 1 is a prefix
Full KV reuse (PromptCache) Much faster Low Reuses each chunk's KV but ignores cross-attention
CacheBlend Much faster Good Reuses all chunks, recomputes a small share of tokens

Why RAG needs many chunks (Figure 2)

23/64
  • Chunk queries into 128-token chunks; retrieve top-k by embedding distance.
  • On Musique and 2WikiMQA: F1 rises a lot as more chunks are added.
  • Too many chunks hurts again ("lost in the middle").
  • The gap between full recompute and full reuse grows with more chunks: more cross-attention.

Why cross-attention matters (Figure 3)

24/64
Full KV recompute Full KV reuse
Chunk 1: "Lionel Messi scored 13 goals at FIFA World Cups." Same chunks, KV computed separately
Chunk 2: "Cristiano scored 8 goals at FIFA World Cups." Chunk 2 never "saw" chunk 1
"Lionel Messi scored more goals ... than Cristiano Ronaldo." ✓ "The question is asking for information about FIFA World Cups..." ✗
  • Cross-attention: attention from one chunk's tokens to earlier chunks. Can't be precomputed, since the earlier chunks aren't known in advance.

Definitions (Table 1)

25/64
  • KV deviation: Δkv(KV_i, KV_i^full)[j] = absolute difference between token j's KV on layer i and its fully recomputed KV.
  • Attention deviation: Δattn(A_i, A_i^full) = L2 norm of the difference between forward attention matrices.
    • Forward attention: attention from the last tokens (the query) to the context; directly sets the output
  • Goal: update KV^pre to KV^new so attention deviation is as small as possible on every layer.

Selective KV recompute (Figure 5)

26/64
  • Per layer:
    • Mask the input down to the selected tokens
    • Compute Q, K, V only for those tokens
    • Fill in K and V for the other tokens from the cache
    • Run attention as usual; output feeds the next layer
  • Cost: recomputing r% of tokens costs about r% of a full prefill.
  • Positions fixed with RoPE: multiply K by a rotation matrix once (negligible cost).

Which tokens to recompute

27/64
  • Insight 1: recomputing tokens with higher KV deviation cuts attention deviation the most (Figure 6).
    • Biggest drop from the first few top-deviation tokens
  • HKVD tokens: high-KV-deviation tokens on a layer.
  • Attention is sparse: only about 10–15% of tokens have much higher KV deviation (Figure 7).
  • So recomputing 10–20% of tokens is enough.

Finding HKVD tokens cheaply

28/64
  • Problem: you'd need the full KV to measure deviation, which defeats the purpose.
  • Insight 2: tokens with high deviation on one layer tend to have high deviation on the next (high Spearman rank correlation, Figure 8).
  • Gradual filtering (Figure 9):
    • Layer 1: recompute all, pick r1% (a bit more than r)
    • Layer 2: recompute those, pick r2% (a bit less than r1)
    • Continue layer by layer
  • Extra memory is negligible: layer i's old KV is dropped when moving to layer i+1.

Pipelining with KV loading (Figure 10)

29/64
  • Recompute layer i while loading layer i+1's KV from storage.
  • Llama-7B, 4K context: recompute 15% takes 3 ms per layer; loading one layer from NVMe SSD takes 16 ms → no extra delay.
  • Llama-70B: recompute 15% takes 7 ms; loading 4 ms → recompute not fully hidden.
  • So KV caches can live on slower, bigger, cheaper storage.

Loading controller

30/64
  • Formula: T_recompute(r%, LLM, L) = r% × Prefill(LLM, L)
  • Formula: T_load(LLM, L, device) = PerTokenKVSize(LLM) × L ÷ Throughput(device)
    • L: context length; both prefill time and device throughput profiled offline
  • Pick r so T_recompute ≈ T_load, but never below r* = 15% (minimum for quality, from Figure 16).
  • Or fix r = 15% and pick the cheapest storage device where T_recompute ≥ T_load.

System design (Figure 11)

31/64
  • KV cache store: split input into chunks, hash each, look up its KV (like vLLM block hashing). Evict least recently used.
  • Fusor: merges cached KVs with selective recompute, layer by layer.
  • Built on vLLM, about 3K lines of Python (PyTorch v2.0).
  • Interfaces: fetch_kv(text, layer_id), prefill_layer(input_dict, KVCache), synchronize().
  • Hash tables kept in CPU memory: 16MB for one million chunks.

Evaluation setup

32/64
  • Models: Mistral-7B, Yi-34B, Llama-70B (8-bit quantization for Yi-34B and Llama-70B).
  • Hardware: 2 Nvidia A40 GPUs, 128 GB RAM, 1TB NVMe SSD (4.8 GB/s).
  • Datasets: 2WikiMQA (200 cases), Musique (150), SAMSum (200), MultiNews (60).
  • 512-token chunks; top-6 chunks per request.
  • Metrics: F1 for QA, Rouge-L for summarization.
  • Baselines: full recompute, prefix caching (assumed zero loading delay, a favorable assumption), full KV reuse, MapReduce, MapRerank.

Main results (Figures 12, 14)

33/64
  • vs full recompute and prefix caching: TTFT 2.2–3.3x lower; F1 / Rouge-L within 0.02.
  • vs full KV reuse: slightly slower, but quality far better (often more than 2x).
    • Intro: 0.1–0.2 higher F1 on QA, 0.03–0.25 higher Rouge-L on summarization
  • Throughput at the same delay: 2.8–5x higher than baselines.
  • Prefix caching also wastes storage: one chunk needs a separate KV copy per distinct prefix.

Versus other RAG methods (Figure 13)

34/64
Method How Result vs CacheBlend
MapReduce Summarize each chunk, then answer from summaries 2–5x higher TTFT, lower F1
MapRerank Answer from each chunk alone, pick the most confident Slightly lower TTFT, much worse quality

Sensitivity (Figures 15–17)

35/64
  • Recompute ratio 5–18% (Yi-34B): quality loss at most 0.002 F1 / Rouge-L.
    • That gives 4.1–6.6x lower TTFT than full recompute and 3.4–6.1x lower than prefix caching
  • Gains stay similar across chunk counts and chunk lengths.
  • Larger batches: prefill dominates more, so CacheBlend helps more.
  • Works with KV in CPU RAM or a slower disk; gap to full reuse shrinks on slow disks (loading dominates).

Limitations

36/64
  • Only transformer models; not Mamba or Griffin.
  • Not tested with more models, datasets or quantization settings.
  • Only vLLM; not newer engines (DistServe, StableGen).
  • Not studied: sharing KV caches across compute nodes.
Part 4LMCache (background reading, our pick)

Why move KV caches out of the GPU

37/64
  • Traditional: KV cache lives in GPU memory for one query only.
  • Two new needs:
    • Cross-query caching: keep KV for a shared prefix for later queries
    • Prefill–decode (PD) disaggregation: prefill on some GPUs, decode on others; KV must move between them
  • Usage data: stored KV cache grows far beyond GPU memory (Figure 3).
  • Over 19% of users reuse stored tokens more than 1.5 times (Figure 4).

What LMCache does

38/64
  • Extracts KV caches from vLLM and SGLang; stores them in CPU memory, local disk, remote disk, Redis; moves them over Ethernet, RDMA, NVLink.
  • Three contributions:
    • Fast data movement: batching, compute–I/O pipelining
    • A modular connector that survives fast engine changes (15–20 new open-weight models a week in 2025)
    • Control API: pin, lookup, cleanup, move, compress KV caches
  • From the same group as CacheBlend; CacheBlend's code is in the LMCache repo.

Performance tricks

39/64
  • Chunks, not pages: vLLM pages are 16 tokens per layer (20 KB–63 KB); LMCache moves 256-token chunks by default.
    • Small transfers can't fill the link (Table 1: 64KB → 4GBps; 16MB → 49GBps)
  • Layer-wise pipelining: load layer i+1's KV while layer i computes (separate CUDA streams).
  • Delayed decode storing: buffer new tokens' KV and write a full chunk at once.
  • Zero-copy moves between tiers.

Lessons from deployment

40/64
  • Remote storage can beat prefill: one user loading KV from their object store saw 22–32% lower TTFT than full prefill.
  • Context truncation kills prefix hits: real traces showed hit ratio drop from roughly 85% to 45% when keeping only the latest tokens.
  • Hit rates higher than expected: e.g. 50% at one company; reuse comes from chat histories, coding assistants, RAG.
  • Reported: up to 15x throughput with vLLM on multi-round QA and document analysis.
Part 5Cartridges (Eyuboglu et al. 2025)

The problem

41/64
  • Users ask many questions over one big corpus: codebases, legal texts, 10-K filings, medical records.
  • In-context learning (ICL): put the whole corpus in the prompt. Flexible but costly.
  • KV cache grows linearly with input length.
    • LLaMA 8B on one H100: peak throughput drops 77x from 1k to 120k tokens of context
  • Prompt and KV-cache compression: quality drops fast beyond 2x compression (Figure 4).

The idea: train the cache offline

42/64
  • Cartridge: a small trained KV cache Z that stands in for the corpus C.
  • Freeze the LLM; train only the key and value vectors (a simplified prefix-tuning).
  • At question time: load the Cartridge, append the question, decode.
  • Training cost is paid once and shared by every query on that corpus.

What a Cartridge must do

43/64
  • Generality: answer many query types (facts, math, summaries, creative) unknown at training time.
  • Long-range structure: understand how distant parts of the corpus relate.
  • Composition: two Cartridges concatenated should act like two documents in context.

Parameterization

44/64
ICL KV cache Cartridge KV cache
(k[1], v[1]) ... (k[n_C], v[n_C]) for the corpus (z_k[1], z_v[1]) ... (z_k[p], z_v[p]) trainable
then KV pairs for the query then KV pairs for the query
  • Size: Z ∈ R^(L × p × d × 2): L layers, p virtual tokens, d dimension, keys and values.
  • Memory = a KV cache for a p-token prompt. p is the knob.
  • Served like a cached prefix: works with existing servers (unlike LoRA, which needs custom serving).

Initialization

45/64
  • Random init of prefix-tuning is unstable; earlier work used an MLP re-projection.
  • Cartridges: initialize Z to the KV cache of the first p tokens of the corpus.
  • LongHealth accuracy (Section 5.3):
Initialization Accuracy
Random vectors 29.9%
KV of random tokens 51.3%
KV of first p corpus tokens 55.3%
  • Freezing the attention sink (first token) also helps stability.

Naive training fails (Figure 3)

46/64
  • Next-token prediction on the raw corpus:
    • Memorizes with near-perfect perplexity, 107x less memory than ICL
    • Fails to generalize to other query types (synthesis, reasoning, creative)
  • Tested on GenConvo, built from FinanceBench (e.g. AMD's 10-K, almost 100k tokens).

Self-study, step 2: context distillation

49/64
  • Teacher: the model with the chunk in context, F(· | c̃ ⊕ x).
  • Student: the same model with the Cartridge, F_Z(· | x).
  • Formula (Eq. 3): minimize Σ over (x, c̃) Σ over positions i of KL( F(·|c̃ ⊕ x[:i]) || F_Z(·|x[:i]) )
    • KL: how different two next-token distributions are
    • Sum over every token position of every synthetic conversation
  • Result on MTOB: chrF 24.9 (next-token) → 33.5 (distillation), same data.
  • LongHealth: +3.7 accuracy points at equal data (Appendix A).

Quality vs memory (Figure 4)

51/64
  • Baselines: ICL, truncated prompt, GPT-4o summary, DuoAttention (KV compression).
  • Cartridges beat ICL at some cache sizes on LongHealth and QASPER (Llama-3B).
  • Memory savings at similar quality: up to 10x (LongHealth), up to 100x (QASPER).
  • Compression baselines drop at only 2x compression.
  • Average across benchmarks: 38.6x less memory, 26.4x higher peak throughput.

More compute, better Cartridge (Figure 5)

52/64
  • Sizes p ∈ {128, 512, 2048, 8192}; batch 64, max length 1024, one epoch (no data reused).
  • Quality rises steadily with training steps for every size.
  • Larger Cartridges reach higher quality.

Beyond the context window (Section 5.2)

53/64
  • MTOB: full textbook is 484k tokens; Llama-8B window is 128k (356k tokens too long).
  • Chunked self-study builds a Cartridge from the full book anyway.
  • Matches ICL on the hand-curated 60k-token version, with much less memory.
  • Beats ICL on the first 130,000 tokens of the book by 11.0 chrF.
  • Effective context: 128k → 484k tokens.

Prefix-tuning vs LoRA (Figure 6, 8)

54/64
Prefix-tuning Cartridge LoRA Cartridge
MTOB at ∼0.6 GB +4.5 chrF over LoRA baseline
MMLU as size grows 54.7 → 54.3 (0.15 → 0.96 GB) 54.7 → 45.3 (0.15 → 1.06 GB)
  • Prefix-tuning keeps the model's general skills; LoRA damages them as it grows.

Composition (Figure 7)

55/64
  • Train Cartridges on 10-Ks of AMD, Pepsi, AMEX, Boeing; sizes {512, 1024, 2048, 4096}.
  • Concatenate two, no joint training; ask questions needing both (6 pairs per size).
  • Beats one Cartridge alone and truncated ICL on multi-document questions.
  • Example: "Who audited the Boeing and AMD statements?" → Ernst & Young LLP (AMD), Deloitte & Touche LLP (Boeing).

Limitations

56/64
  • Training is far costlier than a prefill: about 30 minutes on one 8×H100 node for an ICL-quality Llama-8B Cartridge.
  • Not a drop-in replacement for ICL; a trade of compute for memory.
  • Pays off when many queries hit the same corpus, and training can run on idle compute (e.g. at night).
  • Room for faster training (better shared-prefix attention kernels).

Common mistakes

64/64
  • Timestamp or request ID at the top of the prompt → the prefix never matches. Put it last.
  • Trusting the agent to save notes → log every message and test recall.
  • Reusing chunk caches with no recompute → cross-attention lost; recompute ~15% (CacheBlend).

Check your understanding

In MemGPT, what are main context and external context?

Main context is the prompt: system instructions, working context and the FIFO queue. External context is recall storage and archival storage, reached only through function calls.

In MemGPT, what survives when old messages are evicted?

The working-context notes, a recursive summary, and the full messages in recall storage, which the agent can search.

Why does changing the first word of a long prompt make it slow again?

Prefix caching only reuses an exact matching start. A change at the start breaks everything after it, so the whole prompt is prefilled again.

What does CacheBlend recompute, and why not nothing?

A small share of tokens (15% per layer by default) with the highest KV deviation. Recomputing nothing ignores how chunks affect each other, and quality drops.

How does CacheBlend hide the cost of recomputing?

It recomputes one layer while loading the next layer's KV cache from storage. If loading is slower, recompute adds no delay.

Why did Cartridges trained with next-token prediction fail?

They memorized the raw text but could not answer other kinds of questions. Self-study conversations plus context distillation fixed this.

Why initialize a Cartridge from the first p tokens of the corpus?

Random vectors trained poorly (29.9% on LongHealth). Real-token KV vectors worked much better (55.3% with the first p tokens).

A model only sees its context window, and long contexts are slow and costly. You can give an agent more memory at three layers: let the agent page facts in and out (MemGPT), let the server reuse work it already did on the same text (KV-cache reuse: CacheBlend, LMCache), or compress a corpus into a small trained memory ahead of time (Cartridges).

The text a model can see in one call. Everything else is invisible to it.Source: general

The papers

Cartridges: Lightweight and general-purpose long context representations via self-study

Eyuboglu, Ehrlich, Arora, Guha, Zinsley, Liu, Tennien, Rudra, Zou, Mirhoseini, Ré · 2025

What
Train a small KV cache (a 'Cartridge') offline for each corpus and load it at question time instead of the whole corpus. Training on the raw text with next-token prediction generalized poorly, so they propose self-study: the model has synthetic conversations about chunks of the corpus (from generic seed prompts such as summarize, structure, ask a question), and the Cartridge is trained by context distillation to match the model's next-token distributions when the chunk is in context.
Result
Matched in-context learning quality on long-context benchmarks with 38.6x less memory and 26.4x higher throughput. Extended effective context on MTOB from 128k to 484k tokens. Distillation beat next-token training on MTOB (chrF 24.9 to 33.5). Initializing from the first p corpus tokens beat random vectors on LongHealth (55.3% vs 29.9%). Prefix-tuning kept MMLU near 54.7 while a memory-matched LoRA fell to 45.3. Cartridges can be composed at inference without retraining.
Takeaway
If one large corpus (a contract archive, a codebase) is queried thousands of times, paying once to train a compact memory can beat re-reading it each time. The training data must be varied synthetic Q&A, not the raw text.

MemGPT: Towards LLMs as Operating Systems

Packer, Wooders, Lin, Fang, Patil, Stoica, Gonzalez · 2023

What
Virtual context management modeled on an operating system's memory hierarchy. Main context = read-only system instructions, a writable working context, and a FIFO message queue headed by a recursive summary. External context = recall storage (all messages) and archival storage (vector-searched text). The model moves data with function calls; results are paginated; a memory-pressure warning fires at about 70% of the window and about half the queue is evicted at 100%.
Result
Deep memory retrieval in multi-session chat: GPT-4 accuracy 32.1% without MemGPT vs 92.5% with it (GPT-4 Turbo 35.3% vs 93.4%; GPT-3.5 Turbo 38.7% vs 66.9%). On nested key-value retrieval, GPT-4 and GPT-4 Turbo alone fell to 0% by 3 nesting levels, while MemGPT with GPT-4 was unaffected by depth. On document QA, MemGPT's accuracy stayed flat as more documents were retrieved, while fixed-context baselines were capped by the retriever.
Takeaway
Give the agent explicit memory tools (search, save a note) and a hard context budget, and keep every message in an append-only store. Check that the agent actually saves what it needs: the model decides what to remember.

CacheBlend: Fast Large Language Model Serving for RAG with Cached Knowledge Fusion

Yao, Li, Liu, Ray, Cheng, Zhang, Du, Lu, Jiang · 2024

What
Prefix caching only helps when a request starts with exactly the same text, which RAG rarely does. CacheBlend reuses each retrieved chunk's precomputed KV cache wherever it sits, and recomputes only a small share of tokens (15% per layer by default) chosen by KV deviation, the tokens whose KV values change most from cross-attention to earlier chunks. Recompute overlaps with loading caches from slower storage.
Result
Tested on Mistral-7B, Yi-34B and Llama-70B over 2WikiMQA, Musique, SAMSum and MultiNews. Versus full KV recompute: time to first token 2.2-3.3x lower and throughput 2.8-5x higher, with quality within 0.02 F1/Rouge-L. Recomputing 5-18% of tokens lost at most 0.002 F1/Rouge-L on Yi-34B. Full KV reuse without recompute was about as fast but lost 0.1-0.2 F1 on QA.
Takeaway
For RAG on your own GPUs, the prefill of retrieved chunks is the main latency cost. Cache chunk KV and use a serving stack that can blend it (LMCache with vLLM). Even without that, put stable text first so plain prefix caching hits.

LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference (background reading, our pick)

Cheng, Liu, et al. (with Junchen Jiang) · 2025

What
The open-source KV cache layer from the guest lecturer's group. It moves KV caches out of GPU memory into CPU, disk or network storage and shares them across vLLM/SGLang engines and queries, supporting both prefix reuse across queries and prefill-decode disaggregation. Not an assigned course paper; added because the guest lecture is about it.
Result
The authors report up to 15x higher throughput when combined with vLLM on workloads such as multi-round QA and document analysis, and observe that context truncation, common in industry, can cut prefix cache hit ratio by half.
Takeaway
If you self-host models for repeated document work, a KV cache layer is often the cheapest speed-up available, before buying more GPUs.

1. MemGPT: an agent that manages its own memory

MemGPT (Packer et al. 2023, MemGPT: Towards LLMs as Operating Systems) splits memory into tiers, like RAM and disk: - Main context (what the model sees): fixed system instructions, a small working context the agent writes notes into, and a FIFO queue (first in, first out) of recent messages. - External context (outside the window): recall storage, every message ever, and archival storage, a searchable store of documents.

The agent moves data between tiers by calling functions. When the prompt reaches about 70% of the window, the system adds a "memory pressure" warning so the agent saves what matters. When it is full, old messages are evicted (they stay in recall storage). Search results come back in pages, so one search can never flood the window.

First the pure-Python parts: an archival store with a small TF-IDF search (a word-overlap score that weights rare words more), and a main context with a character budget.

a09_memory.ipynb · cell 3
def tokenize(s):
    return re.findall(r"[a-z0-9_]+", s.lower())

class ArchivalStore:
    """Archival storage: text passages plus a tiny TF-IDF search. Results come back in pages."""
    def __init__(self, passages):
        self.passages = passages
        self.docs = [Counter(tokenize(p)) for p in passages]
        df = Counter(w for d in self.docs for w in d)
        self.idf = {w: math.log(1 + len(passages) / c) for w, c in df.items()}

    def search(self, query, page=0, page_size=3):
        q = set(tokenize(query))
        named = {w for w in q if re.fullmatch(r"msa_\d+", w)}      # a contract id in the query acts as a filter
        scores = [(sum(d[w] * self.idf.get(w, 0) for w in q) / (1 + sum(d.values())) ** 0.5, i)
                  for i, d in enumerate(self.docs) if not named or named & set(d)]
        ranked = [i for s, i in sorted(scores, reverse=True) if s > 0]
        hits = ranked[page * page_size:(page + 1) * page_size]
        more = len(ranked) > (page + 1) * page_size
        out = "\n".join(f"- {self.passages[i]}" for i in hits) or "(no results)"
        return out + (f"\n[page {page}; more results: call again with page={page + 1}]" if more else f"\n[page {page}; no more results]")

class MainContext:
    """Main context = system prompt + working context + FIFO queue, kept under a character budget.
    The queue holds 'units' (one assistant turn plus its tool results), so we never split a tool call from its result."""
    def __init__(self, system, budget_chars=2500, warn_at=0.7):
        self.system, self.budget, self.warn_at = system, budget_chars, warn_at
        self.working = []          # notes the agent chose to keep (read/write via a tool)
        self.queue = []            # list of units; each unit is a list of messages
        self.recall = []           # recall storage: every message ever, never deleted
        self.evicted = 0

    def size(self):
        return len(self.render_system()) + sum(len(json.dumps(m)) for u in self.queue for m in u)

    def render_system(self):
        notes = "\n".join(f"- {n}" for n in self.working) or "(empty)"
        return f"{self.system}\n\nWORKING CONTEXT (your saved notes):\n{notes}"

    def add(self, unit):
        self.queue.append(unit)
        self.recall.extend(unit)
        while self.size() > self.budget and len(self.queue) > 2:   # keep the task and the newest unit
            self.queue.pop(1)                                      # queue[0] is the user's task: never evicted
            self.evicted += 1

    def messages(self):
        msgs = [{"role": "system", "content": self.render_system()}]
        msgs += [m for u in self.queue for m in u]
        if self.evicted:
            msgs.insert(2, {"role": "user", "content": f"[system note: {self.evicted} older steps were evicted to recall storage. Your notes are in WORKING CONTEXT.]"})
        if self.size() > self.warn_at * self.budget:
            msgs.append({"role": "user", "content": "[system warning: memory pressure. Save any facts you still need with working_context_append now.]"})
        return msgs

SYSTEM = ("You are an agent with a small memory. Facts live in archival storage; search it one contract at a time. "

          "When you have every fact, call finish.")

def memgpt_agent(task, budget_chars=2500, max_steps=14, verbose=True):
    ctx = MainContext(SYSTEM, budget_chars)
    ctx.add([{"role": "user", "content": task}])
    peak = 0
    for step in range(max_steps):
        msgs = ctx.messages()
        peak = max(peak, sum(len(json.dumps(m)) for m in msgs))
        msg = chat(msgs, tools=TOOLS)
        calls = msg.tool_calls or []
        if not calls:                        # the model answered in plain text: treat it as final
            return {"answer": msg.content or "", "steps": step + 1, "peak_chars": peak, "notes": ctx.working, "evicted": ctx.evicted}
        unit = [{"role": "assistant", "content": msg.content or "",
                 "tool_calls": [{"id": c.id, "type": "function", "function": {"name": c.function.name, "arguments": c.function.arguments}} for c in calls]}]
        for c in calls:
            try:
                args = json.loads(c.function.arguments or "{}")
            except Exception:
                args = {}
            name = c.function.name
            if name == "finish":
                return {"answer": str(args.get("answer", "")), "steps": step + 1, "peak_chars": peak, "notes": ctx.working, "evicted": ctx.evicted}
            if name == "archival_search":
                try:
                    result = store.search(str(args.get("query", "")), int(args.get("page", 0) or 0))
                except Exception as e:
                    result = f"ERROR: {e}"
            elif name == "working_context_append":
                ctx.working.append(str(args.get("fact", ""))[:200])
                result = "saved"
            else:
                result = f"ERROR: unknown tool {name}"
            if verbose:
                print(f"  step {step+1}: {name}({c.function.arguments[:60]}) -> {result[:70]!r}")
            unit.append({"role": "tool", "tool_call_id": c.id, "content": result})
        ctx.add(unit)
    return {"answer": "STOPPED: step limit", "steps": max_steps, "peak_chars": peak, "notes": ctx.working, "evicted": ctx.evicted}

2. KV-cache reuse: why CacheBlend and LMCache matter

Before a model writes its first word it must read the whole prompt (the prefill). While reading, it builds a KV cache: key and value vectors for every token at every layer. Prefill time grows with prompt length, so a long prompt means a long wait for the first token (time to first token, TTFT).

If the next request starts with the exact same text, the server can reuse the cached keys and values and skip that work. This is prefix caching. Ollama does it automatically within one model slot. We measure it: 1. a long shared prefix (8 contracts) + question A (cold: nothing cached); 2. the same prefix + question B (warm: the prefix is reused); 3. one changed word at the start of the prefix + question A (everything after the change must be recomputed); 4. one changed word at the end of the prefix + question A (most of the prefix is still reusable).

Caveat: Ollama runs 2 slots here. If a request lands in the other slot, it will look "cold". Run the cell twice if the numbers look odd.

def ttft(prompt, max_tokens=8):
    """Time to the first streamed token, in seconds."""
    t0 = time.time()
    stream = client.chat.completions.create(model=MODEL, messages=[{"role": "user", "content": prompt}],
                                            temperature=0, max_tokens=max_tokens, stream=True)
    first = None
    for chunk in stream:
        if first is None and chunk.choices and (chunk.choices[0].delta.content or ""):
            first = time.time() - t0
    return first if first is not None else time.time() - t0

DOCS = ids()[:8]

QA = "\n\nQuestion: What governing law does msa_03 use? Answer in one word."
QB = "\n\nQuestion: What is the monthly fee in msa_05? Answer with a number."
ask("Say OK.", max_tokens=2)                      # load the model so loading time is not counted
results = {}
results["1 cold: new prefix"] = ttft(PREFIX + QA)
results["2 warm: same prefix, new question"] = ttft(PREFIX + QB)
results["3 changed first word of prefix"] = ttft("NOTE. " + PREFIX + QA)

    print(f"{k:38} TTFT {v:5.2f}s")

What to notice: the warm request should be much faster than the cold one, and changing the very first word should make it slow again. Prefix caching is all or nothing from the point of change: one new word at the start throws away the whole cache.

That is the problem in RAG (retrieval-augmented generation), where each request glues together different retrieved chunks in a different order. Each chunk may have been seen before, but never with the same prefix, so prefix caching misses. CacheBlend (Yao et al. 2024, CacheBlend: Fast LLM Serving for RAG with Cached Knowledge Fusion) reuses each chunk's cached KV even when it is not at the start, and recomputes only a small share of tokens (15% per layer by default), the ones whose KV values would change most because of the text before them. It cut TTFT 2.2-3.3x versus full recompute with about the same quality. LMCache (Cheng et al. 2025, LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference) is the open-source layer that stores these caches outside GPU memory (CPU, disk, network) and shares them across vLLM/SGLang engines and queries.

Builder rule you can use today: put stable text first (system prompt, rules, documents) and changing text last (the question). Never put a timestamp at the top of a prompt.

3. Cartridges: study the document once, answer many questions cheaply

Cartridges (Eyuboglu et al. 2025, Cartridges: Lightweight and general-purpose long context representations via self-study) train a small KV cache for one document collection, offline. At question time the model loads this small cache instead of the whole document. The training recipe is self-study: 1. split the corpus into chunks; 2. the model talks to itself about each chunk: one copy asks (from generic seed prompts like "summarize", "structure", "ask a question"), another answers with the chunk in view; 3. train the small cache with context distillation: make the model with the cartridge produce the same next-token probabilities as the model with the full chunk in context.

The paper reports matching in-context quality with 38.6x less memory and 26.4x higher throughput. Training a cartridge needs gradient access to the KV vectors, which Ollama does not give us. So we build a text analogy: self-study generates Q&A, the Q&A becomes compact "study notes", and we compare answering from notes vs from the full document. The real method trains vectors, not text.

print(len(QS), "questions, e.g.", QS[0])

def answer_with(context, q):
    return ask(f"{context}\n\n{q}", max_tokens=20).strip().lower()

def grade(pred, gold):
    words = re.sub(r"[^a-z0-9 ]", " ", pred).split()
    return gold in words if gold.isdigit() else gold in pred

def run(context):
    with ThreadPoolExecutor(2) as ex:
        preds = list(ex.map(lambda qg: answer_with(context, qg[0]), QS))
    return sum(grade(p, g) for p, (_, g) in zip(preds, QS)) / len(QS), preds

acc_full, _ = run(FULL_DOC)                       # 8 calls
acc_cart, preds_cart = run(CARTRIDGE)             # 8 calls
print(f"full document in context: {acc_full:.0%} | cartridge notes: {acc_cart:.0%} | size ratio {len(FULL_DOC)/max(len(CARTRIDGE),1):.1f}x")
for (q, g), p in zip(QS, preds_cart):
    print(f"  {'ok ' if grade(p, g) else 'MISS'} {q[:55]:55} -> {p[:25]!r} (truth {g})")

What to notice: the notes are several times smaller, and on facts that the generic seeds happened to cover, they do about as well. Facts that self-study never touched are simply missing. The paper saw the same thing in a sharper form: training on the raw text with plain next-token prediction memorized it but generalized poorly, and the varied synthetic conversations of self-study were what made cartridges work across question types. Composition also works there: two cartridges can be loaded together without retraining.

When is each tool right? - MemGPT-style paging: many documents, the agent decides what to look at, and you want an audit trail of what it read. - Prefix / KV caching: the same long text is sent again and again (system prompt, playbook, a contract under review). Free speed-up; just keep stable text first. - Cartridges: one large corpus queried thousands of times (a codebase, a company's contract archive). Pay once to train, then serve cheaply.

Traps
  • Putting a timestamp, request ID or user name at the top of the prompt. It changes the first tokens, so prefix caching never hits.
  • Trusting the agent to save notes. In MemGPT-style paging the model decides what to remember; if it skips a note, the fact is gone from view. Log everything and test recall.
  • Training a compact memory on the raw text with next-token prediction. Cartridges found it memorizes but does not generalize; the varied synthetic conversations are what make it work.
  • Measuring TTFT with the first call after loading the model. Load time swamps everything; warm up first.
  • Assuming two requests share a cache. Servers with several slots or replicas may route them apart; LMCache exists partly to share caches across engines.

Check yourself

Why does changing the first word of a long prompt make it slow again?

Prefix caching only reuses KV for an exact matching prefix; a change at the start invalidates everything after it, so the whole prompt is prefilled again.

In MemGPT, what survives when old messages are evicted from the FIFO queue?

The working context notes, a recursive summary, and the full messages in recall storage (retrievable by search).

What does CacheBlend recompute, and why not nothing?

A small share of tokens (15% per layer by default) with the highest KV deviation; reusing caches with no recompute ignores cross-attention between chunks and loses quality.

How is a Cartridge trained?

With self-study: the model generates synthetic conversations about corpus chunks, and a small KV cache is trained by context distillation to match the model's outputs when the chunk is in context.

Our notebook's 'cartridge' is text notes. What is the real one?

A set of trainable key and value vectors (a prefix-tuning style KV cache), trained with gradients while the model weights stay frozen.
