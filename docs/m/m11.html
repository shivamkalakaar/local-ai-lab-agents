Module 11

Optimization: prompts, then weights

Open in Colab
12 min readPlain-English lesson, then the deeper material

How to make a small local model better at one job by improving its instructions automatically with GEPA, before reaching for expensive training.

The big idea

There are two ways to make a model better at a task. You can change its instructions (the prompt). Or you can change the model itself by training it (changing its weights, the millions of numbers inside it). Changing instructions is far cheaper. Try it first.

GEPA (the GEPA paper, 2026) is a tool that rewrites instructions for you. Picture a junior associate drafting summaries, and a senior partner reviewing them. The partner doesn't just say "wrong". She writes "you said 30 days notice; the clause says 15." Then she rewrites the associate's checklist so the mistake doesn't happen again. Repeat a few dozen times, and the checklist gets very good.

In GEPA, the junior is a small fast model, called the student. The partner is a bigger model, called the reflection model. It reads the student's mistakes and the written feedback, and proposes better instructions. GEPA keeps the best versions and tries again.

In the course demo, this took Gemma 3 12B from 55% to 100% on a held-out set. Only the instruction text changed.

Why it matters for us

  • Small models run fast and cheap on a firm's own computers. But out of the box they make more mistakes. Prompt optimization closes much of that gap without any training.
  • Both models can run locally. In our notebook, the student is Llama 3.2 3B and the reflection model is Llama 3.1 8B. No client data leaves the box.
  • The result is just text. You can read it, version it, and roll it back.

How it works, step by step

  1. Pick a narrow task with exact answers. Ours: read the renewal and liability clauses, and pull out three numbers. Renewal years, notice days, and the liability cap in months.

  2. Write a metric that gives text feedback. A metric is the grading function. Ours returns a score and a sentence like "notice_days: expected 15, got 30." That sentence is what GEPA learns from. A bare score tells the reflection model that something is wrong, not what.

  3. Split the data three ways. Train (GEPA learns from these), validation (GEPA uses these to pick the best candidate), and test (hidden until the end). The test set is the honest score.

  4. Run GEPA with a budget. The budget is how many times the metric may be called. Each attempt on one input is a rollout. GEPA tries the current instructions, collects failures, asks the reflection model for better instructions, and keeps a set of the strongest candidates.

  5. Freeze the winner. Save the optimized instructions to a file, with a version.

  6. Climb the ladder only if needed. If prompts plateau, move to training:

  7. SFT (supervised fine-tuning): train on good examples, keeping only those a checker passes.
  8. On-policy distillation: the student writes, and a teacher model scores every word. This needs a teacher you can run yourself, since closed APIs don't share those scores.
  9. RL with GRPO: sample several answers, push toward the ones that beat the group average. Use it only where answers can be checked automatically.
  10. Then re-tune the prompt on the new model.

Worked example

Take a renewal clause: "renews for successive one (1) year terms unless either party gives at least fifteen (15) days' notice." The right answer is renewal_years = 1, notice_days = 15.

The baseline student, with a plain prompt, gets some fields wrong on the hidden test set. The notebook prints that score first.

Then GEPA runs:

gepa = dspy.GEPA(metric=metric, max_metric_calls=60, reflection_lm=teacher, track_stats=True)
optimized = gepa.compile(program, trainset=train, valset=val)
after = evaluate(optimized, test)
print(f"held-out test: {before:.0%} -> {after:.0%}")

Line by line: the first line sets up GEPA with our metric, a budget of 60 metric calls, and the bigger model as the reflection model. The second line runs the optimization: it learns from the training contracts and picks the winner using the validation contracts. The third line scores the winner on the hidden test set. The last line prints the score before and after.

Finally, the notebook prints the new instructions. You will see plain sentences of guidance, written by the reflection model after reading the student's mistakes. That is the whole change. The model is the same.

The budget of 60 keeps the demo to about 10–15 minutes on a T4 (Colab's free GPU). Bigger budgets usually do better.

Common mistakes

  • Optimizing without a trustworthy metric. The optimizer will find every loophole in your grader. Fix the metric first (see Module 10).
  • Vague feedback. A metric that only says "wrong" leaves the reflection model guessing. Say what was expected and what came back.
  • Looking at the test set during tuning. Then the final score is no longer honest. GEPA uses train and validation only.
  • Jumping to training too early. Training costs far more and can break other skills. In one course example, instruction-following fell from 85% to 45% after narrow training. Always run a general check after training.
  • Picking a teacher from a leaderboard. The strongest model isn't always the best teacher. Judge a teacher by how good the student becomes.

Why does the metric return a sentence and not just a number?

The reflection model needs to see what went wrong to fix the instructions. "Expected 15, got 30" points to the exact mistake; a number alone does not.

Why does on-policy distillation need an open-weight teacher?

It needs the teacher's score for every word the student wrote. Closed APIs don't return those, so you need a teacher you can run yourself.

Key terms, papers, evidence, the full notebook code and worked solutions.

Lecture 9 · GEPA · MIPROv2 · DeepSeekMath (GRPO) · Thinking Machines, on-policy distillation · BetterTogether · FireAct

Improve prompts first; it's fast and cheap. Move to weights when prompts plateau on a small model. On-policy distillation from an open teacher is the most compute-efficient way to make a small model good at one task.

Key terms

Prompt optimization
Automatically improving instructions and examples against a metric without changing weights.Source: Opsahl-Ong et al., "MIPROv2", EMNLP (2024)
GEPA
Reflective prompt evolution: a model reads failures and their text feedback, proposes better instructions, and keeps a Pareto set of candidates. Beat GRPO with far fewer rollouts.Source: Agrawal et al., "GEPA", ICLR (2026)
SFT
Supervised fine-tuning: train the model on example inputs and the outputs you want.Source: Lecture 9
GRPO
Group Relative Policy Optimization: sample a group of answers per prompt, score them, and push toward those above the group average. No value model needed.Source: Shao et al., "DeepSeekMath" (2024)
On-policy distillation
The student generates; a teacher scores every token (reverse KL). Dense feedback at a fraction of RL's cost; needs teacher log-probabilities.Source: Thinking Machines (2025); Lecture 9
Rollout
One full attempt by the system on one input, used to compute a score or a training signal.Source: Lecture 9

The ladder

  1. Prompt optimization (GEPA, MIPROv2). Hundreds to a few thousand runs. Tells you whether you need training at all.
  2. Supervised fine-tuning (SFT) on a strong teacher's outputs, keeping only those your checker passes (rejection sampling).
  3. On-policy distillation: the student writes, the teacher scores every token. Fixes SFT's compounding errors.
  4. RL (GRPO) only where answers can be checked automatically, and the student already succeeds sometimes.
  5. Re-optimize prompts on the new model. Often a few more points.
GEPA > GRPO

On Qwen3-8B, GEPA peaked within a few thousand runs; GRPO was still below it after 24,000 (L9).

1,800 vs 17,920

GPU-hours: on-policy distillation reached 74.4% on AIME'24 vs. 67.6% for RL (Qwen3 report, L9).

85% → 45%

Instruction-following after narrow training on documents. Always run a general check after training (L11).

import random, re
import dspy
from lal.data import contract, sections, labels, ids
from lal.checks import check

student = dspy.LM("openai/llama3.2:3b", api_base="http://localhost:11434/v1", api_key="local", temperature=0)
teacher = dspy.LM("openai/llama3.1:8b", api_base="http://localhost:11434/v1", api_key="local", temperature=1.0, max_tokens=2000)
dspy.configure(lm=student)

1. The task: pull three numbers out of the renewal and liability clauses

Grading is exact, field by field. The metric returns text feedback ("expected X, got Y"), which is what GEPA learns from.

11_optimization_gepa.ipynb · cell 3
class RenewalTerms(dspy.Signature):
    """Extract terms from contract clauses."""
    clauses: str = dspy.InputField()
    renewal_years: int = dspy.OutputField()
    notice_days: int = dspy.OutputField()
    cap_months: int = dspy.OutputField(desc="0 if liability is unlimited")

def example(cid):
    secs = {s["title"]: s["text"] for s in sections(contract(cid))}
    text = "\n".join(f"{t}: {x}" for t, x in secs.items() if t in ("Renewal", "Limitation Of Liability"))
    t = labels()[cid]["terms"]
    return dspy.Example(clauses=text, renewal_years=t["renewal_years"], notice_days=t["notice_days"],
                        cap_months=t["liability_cap_months"] or 0).with_inputs("clauses")

data = [example(c) for c in ids()]
random.Random(0).shuffle(data)
train, val, test = data[:7], data[7:11], data[11:]      # GEPA learns on train, picks candidates on val; test stays hidden
print(len(train), "train /", len(val), "validation /", len(test), "held-out test")

def metric(gold, pred, trace=None, pred_name=None, pred_trace=None):
    wrong = [f"{f}: expected {getattr(gold, f)}, got {getattr(pred, f, None)}"
             for f in ("renewal_years", "notice_days", "cap_months") if getattr(pred, f, None) != getattr(gold, f)]
    return dspy.Prediction(score=1.0 - len(wrong) / 3, feedback="All correct." if not wrong else "Wrong -> " + "; ".join(wrong))

def evaluate(program, ds):
    scores = []
    for ex in ds:
        try: scores.append(metric(ex, program(clauses=ex.clauses)).score)
        except Exception: scores.append(0.0)
    return sum(scores) / len(scores)

2. Baseline: the small model with a plain prompt

5. The ladder from here (from the lecture)

  1. Prompt optimization (this notebook): cheap, tells you whether you need training at all.
  2. Fine-tune (SFT) on a teacher's outputs that pass your checker.
  3. On-policy distillation: the student writes, the teacher scores every token. Needs an open-weight teacher.
  4. RL (GRPO) only where answers can be checked automatically.
  5. Re-tune prompts on the new model.

The core of GRPO in four lines: sample a group of answers to the same prompt, and push toward those that beat the group average.

import numpy as np
rewards = np.array([1.0, 0.67, 0.67, 0.33, 1.0, 0.0])        # 6 answers to one contract, scored by our metric
advantages = (rewards - rewards.mean()) / (rewards.std() + 1e-6)
print(advantages.round(2), "<- raise the probability of the positive ones")

11_optimization_gepa.ipynb · cell 10
# Solution 2: vague feedback. GEPA gets only a score and the word "wrong".
RUN_VAGUE = False
def vague_metric(gold, pred, trace=None, pred_name=None, pred_trace=None):
    s = metric(gold, pred).score
    return dspy.Prediction(score=s, feedback="Correct." if s == 1 else "Wrong.")
if RUN_VAGUE:
    vague = dspy.GEPA(metric=vague_metric, max_metric_calls=60, reflection_lm=teacher).compile(program, trainset=train, valset=val)
    print(f"held-out: specific feedback {after:.0%} vs vague feedback {evaluate(vague, test):.0%}")
# With specific feedback ("notice_days: expected 15, got 30") the reflection model can see WHAT to fix.
# With "Wrong." it can only guess, so gains are usually smaller.
Traps
  • Optimizing without a trustworthy metric. The optimizer finds the loopholes.
  • Picking the teacher by leaderboard. The strongest model isn't always the best teacher; test by student quality.
  • RL against a weak checker. Models learn to fake passing (editable tests, exit codes). Keep checkpoints; RL can collapse late.
