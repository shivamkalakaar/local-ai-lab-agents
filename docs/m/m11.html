Module 11

Optimization: prompts, then weights

Open in Colab
30 min readSlides first, then the deeper material

When to optimize an AI system, and how: tune prompts (GEPA, MIPROv2), then weights (SFT, GRPO, on-policy distillation), or let agents optimize.

Part 1Conditions for optimization

Quick poll: which prompt is best?

3/85
Prompt (math problems, scored on PaLM 2) Accuracy
A. "Let's think step by step." 71.8%
B. "Take a deep breath and work on this problem step-by-step." 80.2%
C. "Let's combine our numerical command and clear thinking to quickly and accurately decipher the answer." 74.5%
  • B wins. Nobody would guess that by hand.
  • Small wording changes move the score by points. A search can find wording people would not.

The idea of optimization

4/85
  • Optimization: you state your intent through data and evals, and a method improves the system to match.
  • You stop hand-tuning prompts. You tune the eval, and the optimizer tunes the system.
  • This lecture: the common algorithms and when to use each.

Three pillars of AI systems

5/85
Data System or model Evaluation + metric
Training data Language model Pass rate
Rollouts Compound AI system / workflow Exact match
Demonstrations Agentic system LLM judge
Human feedback ... Cost / latency
  • To optimize an AI system you need all three.
  • Rollout: one full run of the system on a task, start to finish.

Is context optimization still needed?

6/85
  • "Won't models just get better with scale?"
  • Optimization is for last-mile adaptation.
  • Models give a great general solution. Once we know your exact setting, we adapt to its specifics.
  • Example: a strong model knows contracts. It does not know the firm's rule "liability cap at most 12 months of fees".

When to optimize

7/85
  • You have data and evals that suit your domain.
  • Examples and feedback can say what a prompt can't fully say.
    • Sometimes a good eval conveys intent better than any instruction. Tune the system to the eval.
  • The system has many parts that are hard to tune by hand (several prompts, tools, models).

Benefits of optimization

8/85
  • Greater reliability: fewer repeated errors, more consistent across tasks.
  • Domain adaptation: better on specialized tasks, workflows and rules.
  • Lower cost and latency: same quality with smaller models, shorter prompts or fewer tool calls.
  • Learning from experience: turn good runs and failure feedback into lasting fixes.
  • Adaptability: adjust when models, tools or tasks change.
Part 2Context optimization

Two families of context optimization

9/85
Few-shot optimization Reflective optimization
Pick and order the best examples to show the model Run the task, reflect on what went wrong, rewrite the instruction
Lu et al., STaR, DSPy bootstrapping OPRO, MIPROv2, TextGrad, GEPA

Few-shot prompting

10/85
  • Few-shot: besides the task description, the model sees a few worked examples. No training happens.
  • From the GPT-3 paper (Brown et al., 2020):
Translate English to French:     ← task description
sea otter => loutre de mer       ← examples
peppermint => menthe poivrée
plush girafe => girafe peluche
cheese =>                        ← prompt
  • Open questions: which examples, and in what order?

Order matters: Fantastically Ordered Prompts (Lu et al., 2022)

11/85
  • Same examples in a different order can give very different scores.
  • Method: try many orderings of the training examples.
  • Each ordering labels a probing set: sentences the model generates itself.
  • Ground-truth labels on the probing set are ignored. You only look at what the model predicts.
  • Pick the orderings whose predictions look healthy (next two slides).

Global entropy: are the labels balanced?

12/85
High global entropy (good) Low global entropy (bad)
"the ending is universally panned" → 0 → 0
"features multiple endings" → 1 → 0
"quite hard to sit through" → 0 → 0
"nice movie" → 1 → 0
  • Formula: GlobalE = Σ over labels v of −p(v)·log p(v)
    • p(v): share of probing sentences that got label v.
  • A bad ordering makes the model say the same label for everything. Low entropy flags that.

Local entropy: is the model unsure per example?

13/85
  • Formula: LocalE = (1/|D|) · Σ over examples i of Σ over labels v of −p(i,v)·log p(i,v)
    • p(i,v): the model's probability of label v on example i.
    • |D|: size of the probing set. So it is the average over the probe set.
  • High local entropy: on "the ending is universally panned", 0 and 1 get about equal probability.
  • Low local entropy: one label clearly wins.
  • Pick orderings that score well by global or local entropy.

Bootstrap reasoning: the problem

15/85
Standard prompting Chain-of-thought prompting
Example: "A: The answer is 11." Example: "Roger started with 5 balls. 2 cans of 3 is 6. 5 + 6 = 11. The answer is 11."
Cafeteria question → "The answer is 27." ✗ → "23 − 20 = 3 ... 3 + 6 = 9. The answer is 9." ✓
  • Chain of thought (CoT): the model writes its reasoning before the answer (Wei et al., 2022).
  • But labeled examples usually have answers only, no reasoning. Where do we get the reasoning?

STaR (Zelikman et al., 2022)

16/85
  • Self-Taught Reasoner: mine reasoning traces by rejection sampling.
  • Rejection sampling: generate many tries, keep only the ones that pass a check.
  • Loop:
    • Model writes a rationale + answer for each question.
    • Correct answer → keep (question, rationale, answer).
    • Wrong answer → give a hint (the right answer) and ask it to rationalize; keep if now correct.
    • Fine-tune on what was kept. Repeat.
  • Example: "What can be used to carry a small dog?" → "Baskets are designed to hold things. Therefore, the answer is basket (b)."

DSPy bootstrapping (Khattab et al., 2023)

17/85
  • Same idea, no fine-tuning: just rejection-sample successful reasoning into the prompt.
  • Input → model → reasoning + output → metric.
    • High metric score: keep the trace as a few-shot demo.
    • Low score: discard.
  • Then try combinations of kept demos on the dev set. Keep the best-performing set.
  • "Bootstrap Random Search": (1) bootstrap demos for each module, (2) randomly search combinations.

Reflective optimization: LLMs as Optimizers (OPRO, Yang et al., 2024)

19/85
  • Let the LLM see past instructions and their scores. Ask it to write a new, better one.
  • Meta-prompt holds:
    • Solution-score pairs, sorted from low to high: "Let's figure it out!" → 61, "Let's solve the problem." → 63, ...
    • Task examples with <INS> where the instruction goes.
    • "Write your new text that is different from the old ones and has a score as high as possible."
  • Loop: generate → score → add to meta-prompt → repeat. Return the top instructions at the end.

MIPROv2 (Opsahl-Ong et al., 2024)

21/85
  • Three steps:
  • Bootstrap demonstrations (reasoning + output if the program uses CoT).
  • Propose instructions grounded in the task (reflection).
  • Search the combinations of instructions and demos.
  • Walk-through example: an LM program classify_iris(petal_len, petal_wid, sepal_len, sepal_wid) that predicts the iris species.

MIPROv2 step 1: bootstrap few-shot demos

22/85
  • Run training examples through the program several times.
  • Score each output with the metric.
    • Scores poorly → discard the trace.
    • Scores highly → keep it as a demo.
  • Kept demo: petal_length "1.4", petal_width "0.2", sepal_length "4.6", sepal_width "3.2".
    • Rationale: "...the petal length is 1.4 cm, which is relatively short... we can conclude that the iris species is likely to be setosa."
    • Answer: "setosa".

MIPROv2 step 2: what the proposer sees

23/85
Input to the proposer LM Example
1. Program summary "Classifying iris flowers into one of three species... based on the dimensions of their petals and sepals."
2. Data summary "Each of the classes has a distinct distribution on petal_length and petal_width... sepal variables appear to have less clear cut trends."
3. Successful traces classify_iris(5.1, 1.8, 5.9, 3.0) → step-by-step rationale → "virginica"
4. A prompting tip "Keep the instruction clear and concise."
  • Program-aware and data-aware grounding: the LM reads the code and the dataset, then summarizes.
  • Only one tip is shown at a time.

MIPROv2 step 2: the tips

24/85
  • "Don't be afraid to be creative."
  • "The instruction should include a high stakes scenario in which the LM must solve the task!"
  • "Provide the LM with a persona that is relevant to the task (ie. "You are a …")."
  • "Keep the instruction clear and concise."
  • Different tips push the proposer toward different styles. This gives variety.

MIPROv2 step 2: proposed instructions

25/85
  • "Using the provided petal length, petal width, sepal length, and sepal width measurements in cm, predict the iris species accurately to save a critically endangered species from extinction."
  • "Given the petal length, petal width, sepal length, and sepal width in centimeters, predict the species of the iris flower (setosa, versicolour, or virginica). Provide a step-by-step reasoning..."
  • "Given the critical situation in which a rare species of iris is on the brink of extinction, predict the iris species..."
  • Many candidates. Step 3 decides which one works.

MIPROv2 step 3: search the combinations

26/85
  • Pool: instructions 1..N and demo sets 1..N from steps 1–2.
  • Bayesian surrogate model: keeps a belief of how good each instruction and each demo set is.
  • Loop:
    • Sample an instruction + demo set from the beliefs (e.g., Instruction 1 + Demo Set 2).
    • Slot them into the program.
    • Run a minibatch of training data. Score it.
    • Update the beliefs.
  • Repeat num_batches times. Every few iterations, do a full evaluation.

TextGrad (Yuksekgonul et al., 2024)

28/85
  • Feedback gradients: an LLM says how an output could be better ("this response can be improved by...").
  • That feedback is passed backward through the system to each prompt ("this prompt can be improved by...").
  • Works on systems with many parts: prompt → LLM, query → search engine, tool prompt → tool caller.
Prompt at start (77.8%) Prompt after optimization (91.9%)
"You will answer a reasoning question. Think step by step. The last line ... 'Answer: $VALUE'..." "...List each item and its quantity in a clear and consistent format, such as '- Item: Quantity'. Sum the values directly from the list... Double-check the final count to ensure accuracy."

GEPA: Genetic Pareto prompt evolution (Agrawal et al., 2026)

29/85
  • Keep a pool of candidate programs. While budget > 0:
    • Pick a candidate (Pareto rule, next slide).
    • Propose a new one by reflective mutation or merge.
    • Run a minibatch. Improved? Yes → evaluate on all tasks, add to pool. No → discard.
  • Reflective mutation: run the candidate on a minibatch, collect text feedback from the metric, have an LLM reflect and write a new prompt.
  • System-aware merge: take two candidates; for each module, pick the prompt that evolved in one but not the other.

GEPA: Pareto-based selection

30/85
P0 P1 P2 P3 P4
Task 1 ✗ ✗ ✗ ✓ ✗
Task 2 ✗ ✓ ✓ ✗ ✗
Task 3 ✗ ✗ ✓ ✗ ✗
  • Keep every candidate that is best on at least one task: P3, P1, P2. This is the Pareto frontier.
  • Drop candidates that win nowhere (P0, P4).
  • Why: a prompt that is best on one hard case holds a useful idea, even if its average is lower.

GEPA example: PAPILLON (Siyan et al., 2025)

31/85
  • A privacy pipeline:
  • Prompt creator: turns a private user query into a privacy-preserving request.
  • An API-based LLM answers the request.
  • Information aggregator: combines the answer with the original query.
  • Baseline prompts (from the GEPA paper):
    • Module 1: "Given a private user query, create a privacy-preserving request for a powerful external LLM. The LLM may assist without learning private information about the user."
    • Module 3: "Respond to a user query. For inspiration, we found a potentially related request to a powerful external LLM and its response."

Context optimization summary

34/85
  • Few-shot optimization: bootstrap reasoning/outputs and search for useful demos. A strong pattern.
  • Reflective optimization: run the task, reflect on what to change, put that into the prompt.
  • Evolving the prompt along the Pareto frontier also helps.
Part 3Weight optimization

Three ways to change the weights

35/85
Method Who writes the training text Signal
Supervised fine-tuning (SFT) A teacher (or humans) Copy every token
Reinforcement learning (RL) The student itself One reward per answer
On-policy distillation The student itself Teacher grades every token

Recall: cross-entropy loss

36/85
  • Formula: L = − Σ over every token i in the vocabulary of y(i) · log p(i)
    • y(i): 1 when this is the token in the data, 0 otherwise.
    • log p(i): the model's log probability of that token.
  • So the loss is just "−log probability of the correct next token".
  • SFT minimizes this over your training text.

Recall: instruction fine-tuning (Flan)

37/85
  • Train on many tasks written as instructions:
    • "Please answer the following question. What is the boiling point of Nitrogen?" → "-320.4F"
    • Chain-of-thought fine-tuning: "Answer ... by reasoning step-by-step" → worked reasoning.
  • Multi-task: 1.8K tasks.
  • Result: the model generalizes to unseen tasks ("Can Geoffrey Hinton have a conversation with George Washington?" → reasons → "no").

SFT for agents

38/85
  • Roll out a teacher on agentic tasks.
  • Keep the successful trajectories (trajectory: the full run, every step and tool call).
  • Fine-tune the student on them.
  • Focus on diversity of tasks and environments.
  • The student learns task execution.

What a teacher rollout looks like

39/85
  • Task (OpenThoughts-Agent, task_1087): "Locate all files (case-insensitive) whose names end with .example.com ... but ignore anything inside the beta subdirectory; capture both stdout and stderr..."
  • Agent: runs find . -type f -iname '*.example.com' ! -path './beta/*' > /output/command_capture.txt 2>&1
  • Terminal: 48 /output/command_capture.txt
  • Agent checks the file with cat, sees two files, ends with "task_complete": true.
  • Train on runs like this. You can also verify each output and keep only passing runs (rejection sampling).

42/85

RL for agents

44/85
  • Roll out the student on agentic tasks.
  • Reward it for completing the task.
  • Focus on varying environments and task difficulty.
  • Verifiability is key: you need an automatic check of success.

PPO vs GRPO

46/85
  • PPO (proximal policy optimization): the classic RL method for LLMs.
  • GRPO (group relative policy optimization): from DeepSeekMath (Shao et al., 2024).
  • GRPO drops PPO's value model. It estimates the baseline from the scores of a group of answers instead.
  • That cuts training resources a lot.

How PPO works

47/85
  • Policy model: the model being trained. It writes one output o for question q.
  • Reward model: one reward for the entire output.
  • Reference model: a frozen copy. A KL penalty per token keeps the policy close to it.
    • KL divergence: how different two probability distributions are.
  • Value model: predicts a value for every token.
  • GAE (generalized advantage estimate): how useful was this token compared to other possible tokens?

The cost of PPO

48/85
  • Four models to keep in memory: policy, reference, reward, value.
  • Two models to train every step: policy and value.
  • Several expensive per-token steps: per-token KL, per-token reward, per-token value, GAE.

How GRPO works

49/85
  • Generate a group of outputs o1...oG for the same question.
  • Per-output rewards r1...rG.
  • Group advantage: compare each reward to the group.
  • Token-level KL to the reference model.

The cost of GRPO

50/85
  • Three models in memory: policy, reference, reward.
    • The "reward model" doesn't have to be a model. It can be a checker (like cmp above, or our field-by-field grader).
  • One model to train every step: the policy.
  • Only the KL is per token. Everything else is per sequence.

GRPO advantage: a z-score

51/85
  • Formula: A(i) = (R(i) − mean(R1...RG)) / std(R1...RG)
    • R(i): reward of answer i.
    • mean and std: over the group of G answers to the same prompt.
  • Above-average answers get a positive advantage: make them more likely.
  • Below-average: make them less likely.
  • If every answer gets the same reward, all advantages are 0: nothing to learn.

GRPO advantage in code

52/85
import numpy as np
rewards = np.array([1.0, 0.67, 0.67, 0.33, 1.0, 0.0])        # 6 answers to one contract, scored by our metric
advantages = (rewards - rewards.mean()) / (rewards.std() + 1e-6)
print(advantages.round(2), "<- raise the probability of the positive ones")
  • Line 1: numpy for the math.
  • Line 2: six answers to one contract, scored by our 3-field metric (1.0 = all three numbers right).
  • Line 3: the z-score; 1e-6 avoids dividing by zero when all rewards match.
  • Line 4: positive values are the answers GRPO pushes toward.

The GRPO objective

53/85
  • Formula: J(θ) = E[ (1/G) Σ_i (1/|o_i|) Σ_t min( ratio·A, clip(ratio, 1−ε, 1+ε)·A ) − β·KL(π_θ ‖ π_ref) ]
    • E[...]: average over prompts from the dataset and a group of outputs sampled for each.
    • (1/G) Σ_i: average over the group. (1/|o_i|) Σ_t: average over tokens in each response.
    • ratio = π_θ / π_old: how important this token is under the new policy vs the old one.
    • clip(..., 1−ε, 1+ε): don't over-update on any one token.
    • A: the advantage from the last slide.
    • β·KL: don't drift too far from the reference model.

Real-world example: DeepSeek-R1

54/85
  • DeepSeek V3 Base → RL on reasoning prompts (accuracy & format rewards) → R1 Zero.
  • Sample from R1 Zero; filter by accuracy & format; refine with DeepSeek V3 + humans → "cold start" long-CoT data.
  • V3 Base → SFT on cold start → R1 Dev-1 → RL (rule-based reward + language consistency) → R1 Dev-2.
  • Sample from Dev-2 (reasoning) and V3 (non-reasoning) → SFT on V3 Base → R1 Dev-3.
  • RL on diverse prompts (rule-based + preference reward) → DeepSeek-R1.
  • SFT and RL alternate several times.

On-policy distillation: the idea

56/85
  • Chess analogy: coaching on a game you actually played helps more than reviewing a game you only watched.
  • SFT is "watching": the student copies the teacher's moves, then makes its own mistakes alone at test time.
  • On-policy: the student plays, the teacher comments on each move.
  • From Thinking Machines (blog, "On-Policy Distillation").

SFT vs RL vs on-policy distillation

57/85
Example on "What is 5 + (2 × 3)?"
SFT Train on the teacher's text "2 × 3 equals 6, add 5 to get 11." Student probabilities shown per token (20%, 80%, ...).
RL Student writes "5 + 2 is 7, and 7 × 3 is 21." Reward: 0. One number for the whole answer.
On-policy distillation Same student text. Teacher gives each token a probability: "2" gets 5%, "is" 15%, most others 99%.
  • On-policy distillation shows where the answer went wrong (adding 5 + 2 first).

Sampling and signal

58/85
Method Sampling Reward signal
Supervised fine-tuning off-policy dense
Reinforcement learning on-policy sparse
On-policy distillation on-policy dense
  • On-policy: training text comes from the student itself.
  • Dense: feedback on every token. Sparse: one reward per answer.
  • On-policy distillation gets the best of both.

On-policy distillation loss

59/85
  • Formula: KL(π_θ ‖ π_teacher) = E over x sampled from the student [ log π_θ(x_t+1 | x_1..t) − log π_teacher(x_t+1 | x_1..t) ]
    • E over x from the student: the response is written by the student (on-policy).
    • Student log-prob minus teacher log-prob, for each token.
  • Minimize it: the student moves toward what the teacher would say, on the student's own path.
  • Needs the teacher's probability for every token. So the teacher must be a model you can run (open weights).

On-policy distillation example

60/85
  • Ice-cube puzzle: "Beth places four whole ice cubes in a frying pan ... while it was frying a crispy egg ... how many whole ice cubes can be found in the pan at the end of the third minute?"

  • Teacher shades each token by how much it disagrees.
  • Darkest tokens: "Note:", "removed", "melted", "added": the spots where the student ignores that ice melts in a hot pan.

Reasons to use context optimization

76/85
  • API-only models: some strong models don't offer fine-tuning.
  • You need to rerun optimization often and fast. It runs faster and on simpler infrastructure.
  • Environment interactions are expensive. Context optimization needs far fewer samples.

Reasons to use weight optimization

77/85
  • Context optimization fails. Small models sometimes have weak instruction following.
  • You have a capable teacher and want a cheaper model. Distilling into a student often works well.
  • The context is getting too long. Prompt optimization adds text; training avoids context bloat.

Why this fits a firm's own machine

83/85
  • No client contract leaves the building: student and reflection model both run locally.
  • The result is text: read it, version it (renewal_terms_gepa.json), roll it back.
  • A tuned small model is faster and cheaper to run in-house than a big one.

The ladder for the firm

84/85
  1. Prompt optimization (GEPA): cheap; tells you if you need training at all.
  2. SFT on a local teacher's outputs that pass our checker (rejection sampling).
  3. On-policy distillation: the student writes, the open-weight teacher scores every token.
  4. RL (GRPO) only where answers can be checked automatically, like our 3-field grader.
  5. Re-tune prompts on the new model (prompts → weights → prompts).

Common mistakes

85/85
  • Optimizing on a weak metric → the optimizer (or agent) finds every loophole. Fix the metric first.
  • Feedback that only says "wrong" → say what was expected and what came back.
  • Peeking at the test set → optimize on train, select on validation, report test once.
  • Training too early → prompts are far more sample-efficient. And check general skills after narrow training: in one course example, instruction-following fell from 85% to 45%.

Check your understanding

Our local model gets 70% on clause extraction. What do we try first?

GEPA prompt optimization with a metric that gives text feedback. Build a training set only if that plateaus.

Why does the metric return a sentence, not just a number?

"Expected 15, got 30" shows the reflection model what to fix. A number only says something is wrong.

Why does GEPA keep several candidates instead of only the top scorer?

A candidate that is best on even one task holds a useful idea. Keeping the Pareto frontier avoids getting stuck on one prompt.

What does GRPO remove compared to PPO, and what replaces it?

It removes the value model. The baseline comes from the group: each answer's reward minus the group mean, divided by the group std.

Why does on-policy distillation need an open-weight teacher?

It needs the teacher's probability for every token the student wrote. Closed APIs don't return those.

In the Qwen3 report, how did on-policy distillation compare to RL?

Higher scores (74.4% vs 67.6% on AIME'24) with 1,800 vs 17,920 GPU hours.

In auto-research or the Darwin Gödel Machine, what must you control most carefully?

The metric. Agents chase whatever it rewards, including noise like a lucky random seed.

Key terms, papers, evidence, the full notebook code and worked solutions.

Lecture 9 · GEPA · MIPROv2 · DeepSeekMath (GRPO) · Thinking Machines, on-policy distillation · BetterTogether · FireAct

Improve prompts first; it's fast and cheap. Move to weights when prompts plateau on a small model. On-policy distillation from an open teacher is the most compute-efficient way to make a small model good at one task.

Key terms

Prompt optimization
Automatically improving instructions and examples against a metric without changing weights.Source: Opsahl-Ong et al., "MIPROv2", EMNLP (2024)
GEPA
Reflective prompt evolution: a model reads failures and their text feedback, proposes better instructions, and keeps a Pareto set of candidates. Beat GRPO with far fewer rollouts.Source: Agrawal et al., "GEPA", ICLR (2026)
SFT
Supervised fine-tuning: train the model on example inputs and the outputs you want.Source: Lecture 9
GRPO
Group Relative Policy Optimization: sample a group of answers per prompt, score them, and push toward those above the group average. No value model needed.Source: Shao et al., "DeepSeekMath" (2024)
On-policy distillation
The student generates; a teacher scores every token (reverse KL). Dense feedback at a fraction of RL's cost; needs teacher log-probabilities.Source: Thinking Machines (2025); Lecture 9
Rollout
One full attempt by the system on one input, used to compute a score or a training signal.Source: Lecture 9

The ladder

  1. Prompt optimization (GEPA, MIPROv2). Hundreds to a few thousand runs. Tells you whether you need training at all.
  2. Supervised fine-tuning (SFT) on a strong teacher's outputs, keeping only those your checker passes (rejection sampling).
  3. On-policy distillation: the student writes, the teacher scores every token. Fixes SFT's compounding errors.
  4. RL (GRPO) only where answers can be checked automatically, and the student already succeeds sometimes.
  5. Re-optimize prompts on the new model. Often a few more points.
GEPA > GRPO

On Qwen3-8B, GEPA peaked within a few thousand runs; GRPO was still below it after 24,000 (L9).

1,800 vs 17,920

GPU-hours: on-policy distillation reached 74.4% on AIME'24 vs. 67.6% for RL (Qwen3 report, L9).

85% → 45%

Instruction-following after narrow training on documents. Always run a general check after training (L11).

1. The task: pull three numbers out of the renewal and liability clauses

Grading is exact, field by field. The metric returns text feedback ("expected X, got Y"), which is what GEPA learns from.

11_optimization_gepa.ipynb · cell 3
class RenewalTerms(dspy.Signature):
    """Extract terms from contract clauses."""
    clauses: str = dspy.InputField()
    renewal_years: int = dspy.OutputField()
    notice_days: int = dspy.OutputField()
    cap_months: int = dspy.OutputField(desc="0 if liability is unlimited")

def example(cid):
    secs = {s["title"]: s["text"] for s in sections(contract(cid))}
    text = "\n".join(f"{t}: {x}" for t, x in secs.items() if t in ("Renewal", "Limitation Of Liability"))
    t = labels()[cid]["terms"]
    return dspy.Example(clauses=text, renewal_years=t["renewal_years"], notice_days=t["notice_days"],
                        cap_months=t["liability_cap_months"] or 0).with_inputs("clauses")

data = [example(c) for c in ids()]
random.Random(0).shuffle(data)
train, val, test = data[:7], data[7:11], data[11:]      # GEPA learns on train, picks candidates on val; test stays hidden
print(len(train), "train /", len(val), "validation /", len(test), "held-out test")

def metric(gold, pred, trace=None, pred_name=None, pred_trace=None):
    wrong = [f"{f}: expected {getattr(gold, f)}, got {getattr(pred, f, None)}"
             for f in ("renewal_years", "notice_days", "cap_months") if getattr(pred, f, None) != getattr(gold, f)]
    return dspy.Prediction(score=1.0 - len(wrong) / 3, feedback="All correct." if not wrong else "Wrong -> " + "; ".join(wrong))

def evaluate(program, ds):
    scores = []
    for ex in ds:
        try: scores.append(metric(ex, program(clauses=ex.clauses)).score)
        except Exception: scores.append(0.0)
    return sum(scores) / len(scores)

Traps
  • Optimizing without a trustworthy metric. The optimizer finds the loopholes.
  • Picking the teacher by leaderboard. The strongest model isn't always the best teacher; test by student quality.
  • RL against a weak checker. Models learn to fake passing (editable tests, exit codes). Keep checkpoints; RL can collapse late.
