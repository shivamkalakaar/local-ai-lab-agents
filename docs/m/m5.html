Module 05

Tools and function calling

Open in Colab
9 min readSlides first, then the deeper material

Design tools an agent can use safely. A registry that validates, asks permission, runs and truncates, with rules enforced in code, not the prompt.

Based on CS329Z Lecture 4 · Tool Use · original slides (PDF)

Learning objective

1/13
  • Understand why LLMs need tools, how tools are exposed, and how to build a registry that blocks bad or unsafe calls.

Why tools?

2/13
What LLMs can't do alone What a tool gives them
Arithmetic at scale Calculator, code interpreter
Exact, verifiable operations Deterministic execution
Private and proprietary data Search over internal documents
Live state (time, prices) Clocks, live APIs

What is a tool?

3/13
  • Tool: a function interface to a program that runs outside the LM.
  • The LM writes the function call and its arguments. Your code runs it.
Without a tool With a tool
"What is 17,423 × 892?" → LLM accuracy drops as numbers get longer calculate(17423 × 892) → 15,541,316

Anatomy of a tool call

4/13
Select Arguments Validate Execute
Which tool, from the schemas in context Typed fields, filled from the task Schema check before the call Sandboxed; result returns to context
get_clause {"contract_id": "msa_07", "clause": "7.1"} clause must match ^\d+\.\d+$ Clause 7.1 text, back to the model

Standard interfaces

5/13
REST API Function calling MCP
Endpoints + docs, for humans JSON schema per tool One protocol, any client
Model must hand-write requests Model emits name + args; harness validates Servers list tools at runtime (tools/list, tools/call)
  • Our notebook uses function calling against the local Ollama server.

Our registry: four gates, in order

6/13
  • Validate: arguments match the JSON schema? If not, never run.
  • Permission: tool changes the world (read_only=False)? Ask for approval.
  • Run: call the function; catch any crash.
  • Truncate: output over 1,500 chars → cut it, say how to ask for less.
  • Every outcome is a ToolResult with a status: ok, unknown_tool, invalid_args, tool_error, denied.

Failure modes in tool use

11/13
Where Failure Registry defense
Single call Wrong tool; made-up fields; tool that doesn't exist Schema check; unknown_tool
Multi-step Retries the same failing call Clear error text; stuck detector (module 01)
Conversation Acts where the rules say not to Permission gate
Across runs Passes once, fails on retry (pass^k) Test each task several times

How this applies to us

12/13
  • "Never email a client without approval" must hold every time. Only code can promise that.
  • Small local models make more malformed calls. The schema check catches them before they run.
  • Short, paged output keeps the local model's context small.

Common mistakes

13/13
  • Policy in the prompt → it's a suggestion. Put it in the approval gate.
  • Vague descriptions → the model guesses. Good descriptions are free accuracy.
  • Huge outputs → return pages, with a way to ask for the next one.
  • Raising errors → return them as results so the model can recover.

Go deeper

Key terms, papers, evidence, the full notebook code and worked solutions.

Lecture 4 · Toolformer · Gorilla · MCP spec · BFCL · τ-bench · SWE-agent

Spend more design effort on tools than on the prompt. A good tool is narrow, clearly described, hard to misuse, returns short output, and fails with a helpful message.

Key terms

Function (tool) calling
The model returns a structured request to run a named function with JSON arguments; your code runs it and returns the result.Source: Lecture 4
JSON Schema
A standard way to describe the allowed shape of JSON (types, required fields, patterns, enums). Used to validate tool arguments before running anything.Source: MCP specification (2025-06-18)
Model Context Protocol (MCP)
An open standard for exposing tools, resources and prompts to models through servers, with errors returned as results (isError).Source: modelcontextprotocol.io, spec revision 2025-06-18
Agent-computer interface (ACI)
The design of the tools and outputs an agent sees. Small changes (paged file views, edits that reject syntax errors) changed coding-agent success a lot.Source: Yang et al., "SWE-agent", NeurIPS (2024)
Toolformer / Gorilla
Research showing models can learn when and how to call APIs, and that retrieval of up-to-date API docs reduces made-up calls.Source: Schick et al., NeurIPS (2023); Patil et al., NeurIPS (2024)
τ-bench
A benchmark of tool-using agents talking to simulated users under policies; it popularized pass^k because agents were inconsistent across repeats.Source: Yao et al., τ-bench (2024), cited in Lecture 4

Tool design rules

  • Few and distinct. Overlapping tools confuse the model. The Pi harness used 4 tools and a prompt under 1,000 tokens and was among the most cost-effective.
  • Write descriptions like docs for a new hire. Say what it does, what it returns, and when not to use it.
  • Make misuse impossible. Use enums, required fields, and absolute paths. One fix like that removed a whole class of errors in SWE-agent.
  • Short, paged output. Showing whole files cut SWE-agent's success from 18.0% to 12.7%. Return 100 lines at a time.
  • Validate before running. Check the call against its schema first. Bad calls never execute.
  • Errors are results. Return "ERROR: clause '99' not found; valid clauses are 1–24" so the model can recover. MCP marks these with isError.
  • Allow "no tool fits". BFCL tests this. A model forced to pick a tool will pick a wrong one.
  • Prefer native function calling. On τ-bench it beat ReAct-style text calls for every model. On weak local servers, a strict text format plus a parser can be more reliable.

1. The registry

Order matters: validate → permission → run → truncate. Bad calls never run. Actions that change the world need approval.

05_tools.ipynb · cell 3
@dataclass
class ToolSpec:
    name: str
    description: str
    parameters: dict
    fn: Callable[..., Any]
    read_only: bool = True

@dataclass
class ToolResult:
    status: Literal["ok", "unknown_tool", "invalid_args", "tool_error", "denied"]
    content: str

class Registry:
    def __init__(self, specs, approve=lambda name, args: False, max_chars=1500):
        self.specs = {s.name: s for s in specs}
        self.approve, self.max_chars = approve, max_chars

    def schemas(self):
        return [{"type": "function", "function": {"name": s.name, "description": s.description,
                 "parameters": s.parameters}} for s in self.specs.values()]

    def execute(self, name, args) -> ToolResult:
        spec = self.specs.get(name)
        if spec is None:
            return ToolResult("unknown_tool", f"ERROR: no tool '{name}'. Available: {', '.join(self.specs)}")
        try:
            jsonschema.validate(args, spec.parameters)
        except jsonschema.ValidationError as e:
            return ToolResult("invalid_args", f"ERROR: bad arguments: {e.message}")
        if not spec.read_only and not self.approve(name, args):
            return ToolResult("denied", "DENIED: a person declined this action. Do not retry it.")
        try:
            out = str(spec.fn(**args))
        except Exception as e:
            return ToolResult("tool_error", f"ERROR: {type(e).__name__}: {e}")
        if len(out) > self.max_chars:
            out = out[: self.max_chars] + f"\n[truncated; {len(out)} chars total. Ask for a narrower range.]"
        return ToolResult("ok", out)

2. Three tools: two read-only, one that sends email

Notice the descriptions: what it does, what it returns, when to use it. clause must match a pattern, so wrong formats are rejected before running.

05_tools.ipynb · cell 4
def read_pages(contract_id, start_line=1, n_lines=15):
    lines = contract(contract_id).splitlines()
    return "\n".join(f"{i}: {l}" for i, l in enumerate(lines[start_line-1:start_line-1+n_lines], start_line))

def get_clause(contract_id, clause):
    return clauses(contract(contract_id)).get(clause, "NOT FOUND")

SENT = []
def send_email(to, body):
    SENT.append((to, body)); return f"sent to {to}"

CID = {"type": "string", "pattern": "^msa_[0-9]{2}$", "description": "Contract id like 'msa_07'"}
registry = Registry([
    ToolSpec("read_pages", "Read a contract 15 lines at a time, with line numbers. Use start_line to page.",
             {"type": "object", "properties": {"contract_id": CID, "start_line": {"type": "integer", "minimum": 1},
              "n_lines": {"type": "integer", "minimum": 1, "maximum": 30}}, "required": ["contract_id"]}, read_pages),
    ToolSpec("get_clause", "Read one clause by number like '7.1'. Returns NOT FOUND if it doesn't exist.",
             {"type": "object", "properties": {"contract_id": CID, "clause": {"type": "string", "pattern": r"^\d+\.\d+$"}},
              "required": ["contract_id", "clause"]}, get_clause),
    ToolSpec("send_email", "Email someone. Requires human approval.",
             {"type": "object", "properties": {"to": {"type": "string"}, "body": {"type": "string"}}, "required": ["to", "body"]},
             send_email, read_only=False),
])

4. Now let the model use it

The model asks to email the contract to someone. The registry denies it, the model is told, and nothing is sent.

05_tools.ipynb · cell 6
def run(task, max_turns=6):
    msgs = [{"role": "system", "content": "You help lawyers. Use tools."}, {"role": "user", "content": task}]
    for _ in range(max_turns):
        m = client.chat.completions.create(model=MODEL, messages=msgs, tools=registry.schemas(), temperature=0).choices[0].message
        msgs.append(m)
        if not m.tool_calls:
            return m.content
        for c in m.tool_calls:
            try: args = json.loads(c.function.arguments)
            except json.JSONDecodeError: args = {}
            r = registry.execute(c.function.name, args)
            print(f"  {c.function.name} -> {r.status}")
            msgs.append({"role": "tool", "tool_call_id": c.id, "content": r.content})
    return "turn limit"

print(run("Read clause 7.1 of msa_07 and email it to opposing.counsel@example.com"))
print("emails actually sent:", SENT)

Traps
  • Enforcing policy in the prompt ("only call delete after confirming"). Enforce it in the registry.
  • Dozens of tools loaded up front. Load tools on demand; tool search gave about 3× better tool selection (L6).
  • Testing once. τ-bench shows GPT-4o's success on all 8 repeats (pass^8) was under 25% in retail.

Check yourself

Where should "never email a client without approval" live?

In code: the email tool is not read-only, so the registry calls the approval gate before running it. Prompts are suggestions; the registry is a rule.

Why return errors to the model instead of raising them?

A clear error message lets the model fix its own call ("clause 99 doesn't exist, valid range 1–24"). A crash ends the run.
