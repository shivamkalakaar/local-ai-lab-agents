Part 2 · A03

Learning from feedback with tools and code

Open in Colab
8 min readSlides first, then the deeper material

Agents improve when the world answers back. Use test results, tool outputs and written rules, not the model's own opinion.

Based on CS329A · Learning from feedback with tools and code · main paper

Learning objective

1/13
  • Learn three kinds of outside feedback (tool results, test results, written rules) and how to turn feedback loops into training data.

Why outside feedback?

2/13
  • A model guessing alone makes the same mistakes again and again.
  • Outside signals you can check:
    • Tool results: facts looked up, not remembered
    • Test results: code that runs or fails
    • Written rules: a constitution to critique against
  • Don't trust the model's own "looks good to me."
  • Log every loop. It can become training data later.

ReAct: think, act, observe

3/13
  • ReAct: a loop of Thought → Action → Observation, repeated until the agent answers.
  • Thought: a short reason before acting.
  • Action: one tool call (search, read a clause, calculate).
  • Observation: the tool's result, fed back to the model.
  • Errors come back as observations, so the agent can recover.

Chain-of-thought vs ReAct (Yao et al. 2022)

4/13
Chain-of-thought ReAct
Reasons from memory Looks facts up with tools
HotpotQA failures from hallucination: 56% Failures from hallucination: 0%
FEVER: 56.3 FEVER: 60.9
  • ReAct's own failures: 47% were reasoning errors, such as repeating steps.
  • ReAct + self-consistent CoT gave the best prompting results (35.1 EM on HotpotQA).

ReAct on a contract

5/13
Step Action Observation
1 sections[msa_07] "...2. Fees; ... 7. Limitation Of Liability ..."
2 clause[msa_07, 7.1] "...SHALL NOT EXCEED THE FEES PAID BY CUSTOMER IN THE TWENTY-FOUR (24) MONTHS..."
3 clause[msa_07, 2.1] "Customer shall pay Vendor $4,500 per month..."
4 calculate[24 * 4500] 108000
  • Every fact comes from the contract, not the model's memory.

Execution feedback (RLEF, Gehring et al. 2024)

6/13
  • Execution feedback: results of running code (failed tests, errors, timeouts) shown back to the model.
  • Public tests: visible; give feedback during the loop.
  • Private tests: hidden; decide the final grade, so the model can't overfit.
  • Loop: write code → see public test results → try again (up to 3 attempts).
  • Reward: +1 if private tests pass, −1 if not. Trained with RL (PPO).

RLEF results

7/13
CodeContests, 3 attempts Before training After RL training
Llama 3.1 8B 10.5% 16.0%
Llama 3.1 70B 27.5% 40.1%
  • Untrained 8B barely used feedback: 11.8% single-turn vs 10.5% multi-turn.
  • Given random feedback from another problem, trained models got much worse: they really read it.

The fair baseline

8/13
Repair loop Fresh samples
Show the failing tests, ask for a fix Try again from scratch, no errors shown
Same number of calls Same number of calls
  • If the loop doesn't beat fresh samples, the model is not using the feedback.
  • Then log the episodes: (prompt, attempts, feedback, final reward). That is RLEF's training data.

Constitutional AI (Bai et al. 2022)

9/13
  • Constitution: a short list of written principles; replaces most human labels.
  • Critique-and-revise: the model reviews its answer against one principle, then rewrites it.
  • The paper: 16 principles, 4 critique-revision rounds per red-team prompt.
  • RLAIF: an AI, not a person, picks the better of two answers; those picks train the reward model.
  • Result: rated more harmless than RLHF models, and explained objections instead of dodging.
  • Over-training → Goodharting: preachy boilerplate in many answers.

Our constitution in code

10/13
CONSTITUTION = [
    "Cite the clause number (like 7.1) for every claim about the contract.",
    "Judge the contract ONLY against the firm playbook rules given. ...",
    "Name every playbook rule the contract breaks, and say clearly whether the contract can be signed as written.",
    "Be short and plain: at most 6 sentences, no legal jargon.",
]
  • Rule 1: every claim needs a clause number.
  • Rule 2: stick to the playbook; send anything else to counsel.
  • Rule 3: name every broken rule and give a verdict.
  • Rule 4: short and plain. Code partly checks rules 1 and 3.

From revisions to preference data

11/13
  • Preference pair: a prompt, a chosen answer and a rejected answer.
  • Chosen = revision. Rejected = draft.
  • AI judge: shuffle which answer is A and B, so position bias can't fake a preference.
  • Keep pairs where the AI judge and the code checks agree. Train with DPO or a reward model.

How this applies to us

12/13
  • Tools, test runs and the AI judge all run on the firm's machine with a local model.
  • The firm's playbook is the constitution: edit a rule, regenerate the data.
  • Logged (draft, revision) pairs become training data for a later fine-tune.

Common mistakes

13/13
  • Calling a repair loop a win → compare to fresh samples with the same calls.
  • Grading on the tests the model saw → keep a held-out set.
  • Assuming every revision is better → score both with the same checks; drop pairs where the revision lost.
  • Over-optimizing an AI reward → watch for boilerplate (Goodharting).

Check your understanding

In RLEF, why are the private tests hidden from the model?

So the reward measures real correctness. If the model saw the grading tests, it could pass them without solving the task.

ReAct alone scored slightly below chain-of-thought on HotpotQA. Why does the paper still favor it?

Its answers are grounded: hallucination caused 0% of its failures vs 56% for CoT. ReAct + CoT-SC gave the best score.

How does a critique-and-revise step become training data?

The draft is the rejected answer and the revision is the chosen one. These pairs train a preference model or a DPO update.

Go deeper

Key terms, papers, evidence, the full notebook code and worked solutions.

CS329A Lecture 4 (Oct 3)

A model improves when the world answers back: tool results, test results, or a written set of rules. Use outside signals you can check, not the model's own opinion of itself, and log every loop so it can become training data later.

Key terms

ReAct
A loop of Thought, Action (tool call) and Observation (tool result), repeated until the agent answers.Source: Yao et al. 2022
Execution feedback
The results of running code (which tests failed, errors, timeouts) shown back to the model so it can fix the code.Source: Gehring et al. 2024
Public vs private tests
Public tests are visible and give feedback during the loop; private tests are hidden and decide the final grade, so the model cannot overfit to them.Source: Gehring et al. 2024
Constitution
A short list of written principles that an AI uses to critique and revise answers, replacing most human labels.Source: Bai et al. 2022
Critique-and-revise
The model reviews its own answer against one principle, writes a critique, then rewrites the answer to fix it.Source: Bai et al. 2022
RLAIF
Reinforcement learning from AI feedback: an AI, not a person, picks the better of two answers, and those picks train the reward model.Source: Bai et al. 2022
Preference pair
A training example with a prompt, a chosen answer and a rejected answer; the input format for reward models and DPO.Source: Inferred: standard format used with RLAIF/RLHF data

The papers

ReAct: Synergizing Reasoning and Acting in Language Models

Yao et al. · 2022

What
The model writes a Thought, then an Action (a tool call such as a Wikipedia search), then reads the Observation, and repeats. They prompt PaLM-540B with a few example trajectories and compare against reasoning-only (chain-of-thought) and acting-only prompts on HotpotQA, FEVER, ALFWorld and WebShop.
Result
FEVER accuracy 60.9 vs 56.3 for chain-of-thought; on HotpotQA ReAct alone was slightly behind (27.4 vs 29.4 EM), but combining ReAct with self-consistent CoT gave the best prompting results (35.1 EM HotpotQA, 64.6 FEVER). In a manual study of HotpotQA failures, hallucination caused 56% of CoT failures and 0% of ReAct failures, while 47% of ReAct failures were reasoning errors such as repeating steps. ALFWorld success rose by an absolute 34% and WebShop by 10% over imitation and RL baselines, with only one or two in-context examples.
Takeaway
Give agents tools for facts and let them write a short reason before each action. Watch for loops (the same action again and again) and add a fallback to plain reasoning when the agent runs out of steps.

RLEF: Grounding Code LLMs in Execution Feedback with Reinforcement Learning

Gehring et al. · 2024

What
Code generation becomes a multi-turn episode: the model writes code, sees results on the public tests, and tries again (up to 3 attempts). The final reward is +1 if hidden private tests pass and -1 otherwise, and the model is trained with PPO. Starting models are Llama 3.1 8B and 70B Instruct.
Result
On CodeContests (test set, 3 attempts), 8B went from 10.5% to 16.0% and 70B from 27.5% to 40.1% solve rate. Before training the models barely used feedback: 8B scored 11.8% single-turn vs 10.5% multi-turn. With random feedback from an unrelated problem, the trained models got much worse, showing they really read the feedback. The trained 70B beat AlphaCodium (GPT-4) with far fewer samples.
Takeaway
A repair loop with test feedback is not free accuracy: measure it against simply sampling again with the same budget. If the loop doesn't win, log the episodes; they are exactly the data needed to train a model that does use feedback.

Constitutional AI: Harmlessness from AI Feedback

Bai et al. · 2022

What
Humans write only a short list of principles (the constitution). Phase 1: the model answers red-team prompts, critiques its answer against a randomly sampled principle, and revises; a model is fine-tuned on the revisions (SL-CAI). Phase 2 (RLAIF): a model compares pairs of answers using a principle, those AI preferences train a preference model, and RL optimizes against it.
Result
They wrote 16 principles and sampled 4 critique-revision rounds per red-team prompt (182,831 red-team prompts in total, plus helpfulness data). RL-CAI models were rated by crowdworkers as significantly more harmless than RLHF and SL-CAI models, while engaging with harmful requests by explaining objections instead of being evasive. Turning the AI judge's probabilities into soft labels clamped to 40-60% worked better than hard labels when the judge used chain-of-thought. Over-training led to Goodharting: preachy boilerplate in many answers.
Takeaway
Write your quality bar down as short, checkable rules. Use them to critique and revise outputs, and keep (draft, revision) pairs as preference data. Where a rule can be checked in code (citations exist, verdict present), check it in code instead of trusting the AI judge.

The code, cell by cell

Everything below is exactly what runs in a03_feedback_tools_code.ipynb, in the same order. The notebook starts with the shared setup cell (shown in Module 00), then these cells.

a03_feedback_tools_code.ipynb · cell 2
import json, random, re, time
from concurrent.futures import ThreadPoolExecutor
from lal.llm import ask
from lal.data import contract, clauses, sections, labels, playbook
from lal.codetasks import tasks, task, run_tests, extract_code, run_python
from lal.checks import check

CALLS = [0]                                   # count model calls; this notebook aims for about 60-80
def llm(prompt, **kw):
    CALLS[0] += 1
    try:
        return ask(prompt, **kw)
    except Exception as e:                    # a server hiccup should not kill the whole notebook
        return f"ERROR: {e}"

TASKS = tasks()
print(len(TASKS), "coding tasks:", [t["id"] for t in TASKS])
print("\nExample prompt:\n" + TASKS[4]["prompt"])

1. A grader the model cannot argue with

Each task has a reference solution and hidden unit tests (some generated with a fixed seed). run_tests runs code in a separate Python process with a timeout, so a bad or endless program cannot hurt the notebook. It returns (passed, total, feedback), and the feedback is short text we can show the model.

a03_feedback_tools_code.ipynb · cell 3
t = task("second_largest")
print("reference:", run_tests(t["reference"], t)[:2])
buggy = "def second_largest(nums):\n    return sorted(nums)[-2]\n"
p, n, fb = run_tests(buggy, t)
print("buggy:", p, "/", n)
print(fb)
print("endless loop:", run_tests("def second_largest(nums):\n    while True: pass\n", t, timeout=2))

2. Execution feedback, at inference time (the idea behind RLEF)

RLEF (Gehring et al. 2024, RLEF: Grounding Code LLMs in Execution Feedback with Reinforcement Learning) sets code writing up as a conversation: the model writes code, sees the results on the public tests, and tries again, up to 3 attempts. Grading uses private tests it never sees. Their key finding: off-the-shelf Llama 3.1 Instruct models barely use the feedback (8B went from 11.8% single-turn to 10.5% multi-turn on CodeContests). After RL training on this loop, the 8B model reached 16.0% and the 70B reached 40.1%.

We can't run RL here, but we can run the same loop and measure it. Our prompt examples are too few to catch bugs, so we give the loop a dev set: the prompt examples plus half of the hidden tests. We grade on all tests and also report the held-out half separately. If a fix only passes the tests it was shown, the held-out number tells us.

a03_feedback_tools_code.ipynb · cell 4
def split(t):
    hidden = t["tests"][len(t["public_tests"]):]
    dev = dict(t, public_tests=t["public_tests"] + hidden[::2])          # what the loop may see
    held = dict(t, tests=t["public_tests"] + hidden[1::2])               # never shown to the model
    return dev, held

SYSTEM = "You write correct, simple Python. Reply with one ```python code block containing the function, and nothing else."

def solve_with_feedback(t, max_turns=3, temperature=0):
    """Turn 1 is a normal one-shot attempt. Later turns see the dev-test failures."""
    dev, held = split(t)
    history, code, log = t["prompt"], "", []
    for turn in range(1, max_turns + 1):
        reply = llm(history, system=SYSTEM, temperature=temperature, max_tokens=700)
        code = extract_code(reply)
        dp, dn, fb = run_tests(code, dev, public=True)                    # feedback signal
        ap, an, _ = run_tests(code, t)                                    # grade: all tests
        log.append({"turn": turn, "dev_ok": dp == dn, "all_ok": ap == an, "held_ok": run_tests(code, held)[0] == len(held["tests"])})
        if dp == dn:                                                      # stop when the visible tests pass (as in RLEF)
            break
        history = (f"{t['prompt']}\n\nYour previous attempt:\n```python\n{code}```\n"
                   f"Running it on tests gave:\n{fb}\nFix the code. Give it another try.")
    return code, log

t0 = time.time()
with ThreadPoolExecutor(2) as ex:
    fb_runs = dict(zip([t["id"] for t in TASKS], ex.map(solve_with_feedback, TASKS)))
print(f"{time.time()-t0:.0f}s, {CALLS[0]} calls so far")
for tid, (_, log) in fb_runs.items():
    print(f"{tid:18s}", " -> ".join(("PASS" if r["all_ok"] else "fail") for r in log))

Pass rate after each turn: a task counts as solved at turn k if its last attempt up to turn k passes all tests.

a03_feedback_tools_code.ipynb · cell 5
def pass_by_turn(runs, max_turns=3):
    out = []
    for k in range(1, max_turns + 1):
        solved = sum((log[min(k, len(log)) - 1]["all_ok"]) for _, log in runs.values())
        out.append(solved / len(runs))
    return out

fb_curve = pass_by_turn(fb_runs)
for k, r in enumerate(fb_curve, 1):
    print(f"after turn {k}: {r:.0%} of tasks pass all tests")
fixed = [tid for tid, (_, log) in fb_runs.items() if len(log) > 1]
print("tasks that needed feedback:", fixed)
print("of the final answers, how many pass the held-out half:",
      sum(log[-1]["held_ok"] for _, log in fb_runs.values()), "/", len(fb_runs))

The fair baseline: same budget, no feedback

RLEF compares against independent sampling: just try again from scratch, at a higher temperature, without showing the errors. If feedback doesn't beat this, the model is not really using the feedback. We give each task that failed turn 1 the same extra attempts, with the dev tests picking which attempt to keep.

a03_feedback_tools_code.ipynb · cell 6
def resample(t, extra=2):
    dev, _ = split(t)
    for i in range(extra):
        code = extract_code(llm(t["prompt"], system=SYSTEM, temperature=0.8, max_tokens=700))
        if run_tests(code, dev, public=True)[0] == len(dev["public_tests"]):
            break
    return run_tests(code, t)[0] == len(t["tests"])

failed_first = [t for t in TASKS if not fb_runs[t["id"]][1][0]["all_ok"]]
with ThreadPoolExecutor(2) as ex:
    rs = list(ex.map(resample, failed_first))
first_turn = sum(log[0]["all_ok"] for _, log in fb_runs.values())
print(f"turn 1 (shared):            {first_turn}/{len(TASKS)}")
print(f"+ 2 turns with feedback:     {sum(log[-1]['all_ok'] for _, log in fb_runs.values())}/{len(TASKS)}")
print(f"+ 2 fresh samples, no feedback: {first_turn + sum(rs)}/{len(TASKS)}")
print(CALLS[0], "calls so far")

On 10 small tasks the gap is noisy, so read it as a sign, not proof. RLEF's point is that the gap is small for untrained models and grows after RL on exactly this loop. To train, you would log these episodes: (prompt, attempts, feedback, final reward = all private tests pass).

3. ReAct: think, act, observe

ReAct (Yao et al. 2022, ReAct: Synergizing Reasoning and Acting in Language Models) has the model write a Thought, then an Action (a tool call), then read the Observation (the tool result), and repeat. On HotpotQA, chain-of-thought answers were wrong because of made-up facts in 56% of the failures the authors studied, against 0% for ReAct, which looks facts up.

Our task needs two lookups and one multiplication: the dollar liability cap = cap months × monthly fee. Tools: read the section list, read a clause, and a calculator that runs in a subprocess.

a03_feedback_tools_code.ipynb · cell 7
def tool_sections(cid):
    try:
        return "; ".join(f"{s['id']}. {s['title']}" for s in sections(contract(cid)))
    except Exception:
        return f"ERROR: unknown contract id {cid!r}"

def tool_clause(cid, num):
    try:
        cl = clauses(contract(cid))
    except Exception:
        return f"ERROR: unknown contract id {cid!r}"
    return cl.get(num.strip(), f"NOT FOUND. Valid clauses: {', '.join(cl)}")

def tool_calc(expr):
    if not re.fullmatch(r"[\d\s+\-*/().,]+", expr):                         # numbers and operators only
        return "ERROR: calculator accepts only numbers and + - * / ( )"
    out, err = run_python(f"print({expr.replace(',', '')})", timeout=3)       # still in a subprocess
    return out.strip() or f"ERROR: {err.strip()[-200:]}"

REACT = """Answer the question by thinking step by step and using tools. Use EXACTLY this format, one step per reply:
Thought: <your reasoning>
Action: <one of: sections[contract_id] | clause[contract_id, clause_number] | calculate[expression] | finish[answer]>

Tools:
- sections[msa_01] lists the section headings.
- clause[msa_01, 2.1] returns the text of clause 2.1.
- calculate[12 * 4500] does arithmetic.
- finish[54000] gives the final answer (a plain number).
"""

def react(question, max_steps=5, verbose=True):
    transcript = f"{REACT}\nQuestion: {question}\n"
    for step in range(max_steps):
        reply = llm(transcript, temperature=0, max_tokens=250, stop=["Observation:"])
        m = re.search(r"Action:\s*(\w+)\[(.*?)\]", reply, flags=re.S)
        thought = (re.search(r"Thought:\s*(.*)", reply) or re.search(r"(.*)", reply)).group(1)[:120]
        if not m:
            obs = "FORMAT ERROR: end with a line 'Action: tool[arguments]'."
        else:
            name, arg = m.group(1).lower(), m.group(2)
            if name == "finish":
                if verbose: print(f"  {step+1}. finish[{arg}]")
                return arg, step + 1
            parts = [a.strip(" '\"") for a in arg.split(",", 1)]
            obs = {"sections": lambda: tool_sections(parts[0]),
                   "clause": lambda: tool_clause(parts[0], parts[1]) if len(parts) == 2 else "ERROR: use clause[contract_id, number]",
                   "calculate": lambda: tool_calc(arg)}.get(name, lambda: f"ERROR: unknown tool {name}")()
        if verbose: print(f"  {step+1}. {thought} | {m.group(0) if m else '??'} -> {str(obs)[:80]}")
        transcript += reply.strip() + f"\nObservation: {obs}\n"
    return None, max_steps

def to_number(s):
    try:
        return float(re.sub(r"[^\d.]", "", str(s).split()[0] if s else "") or "nan")
    except Exception:
        return float("nan")

L = labels()
react_ids = ["msa_07", "msa_08", "msa_20"]
react_results = {}
for cid in react_ids:
    truth = L[cid]["terms"]["liability_cap_months"] * L[cid]["terms"]["monthly_fee"]
    print(f"{cid} (truth ${truth:,})")
    ans, steps = react(f"In contract {cid}, what is the liability cap in dollars? "
                       "(The cap is a number of months of fees; multiply by the monthly fee.)")
    react_results[cid] = to_number(ans) == truth
    print("  ->", ans, "| correct:", react_results[cid])
print(CALLS[0], "calls so far")

Notice where each fact came from: the clause text, not the model's memory. When a step fails (wrong clause number, bad format), the error comes back as an observation and the model can recover. That is "learning from feedback" inside one episode.

4. Constitutional AI: critique and revise against written rules

Constitutional AI (Bai et al. 2022, Constitutional AI: Harmlessness from AI Feedback) replaces most human labels with a short list of principles. Phase 1 (supervised): the model answers, critiques its answer against a randomly picked principle, and revises. The paper used 16 principles and 4 critique-revision rounds per prompt, then fine-tuned on the revisions. Phase 2 (RLAIF): a model compares two answers using a principle; those AI preferences train a reward model.

Our constitution is for contract-review answers. Each rule is also something code can partly check.

a03_feedback_tools_code.ipynb · cell 8
PB = playbook()
CONSTITUTION = [
    "Cite the clause number (like 7.1) for every claim about the contract.",
    "Judge the contract ONLY against the firm playbook rules given. Do not give legal advice beyond the playbook; "
    "for anything else, say the team should ask counsel.",
    "Name every playbook rule the contract breaks, and say clearly whether the contract can be signed as written.",
    "Be short and plain: at most 6 sentences, no legal jargon.",
]

def contract_question(cid):
    return (f"Firm playbook rules: {json.dumps(PB['rules'])}\n\nContract {cid}:\n{contract(cid)}\n\n"
            "Question from the business team: can we sign this contract as written? What needs to change?")

def critique_revise(cid, rng):
    q = contract_question(cid)
    draft = llm(q + "\nAnswer briefly.", temperature=0.7, max_tokens=300)           # a typical first answer
    principle = rng.choice(CONSTITUTION)                                              # CAI samples one principle per step
    critique = llm(f"{q}\n\nAnswer to review:\n{draft}\n\nPrinciple: {principle}\n"
                   "Critique the answer ONLY against this principle. List concrete problems, or say 'No problems'.",
                   max_tokens=250)
    revision = llm(f"{q}\n\nOriginal answer:\n{draft}\n\nCritique:\n{critique}\n\n"
                   f"Rewrite the answer so it follows every rule below and fixes the critique.\nRules:\n- "
                   + "\n- ".join(CONSTITUTION) + "\nReturn only the new answer.", max_tokens=300)
    return {"cid": cid, "principle": principle, "draft": draft, "critique": critique, "revision": revision}

def score(answer, cid):
    """Code checks for the constitution: real citations, issue clauses cited, a clear verdict."""
    cited = set(re.findall(r"\b(\d{1,2}\.\d)\b", answer))
    valid = set(clauses(contract(cid)))
    issue_clauses = {i["clause"] for i in L[cid]["issues"]}
    return {"cites": len(cited & valid),
            "bad_cites": len(cited - valid),
            "issue_recall": len(cited & issue_clauses) / max(1, len(issue_clauses)),
            "verdict": bool(re.search(r"\b(cannot|can't|should not|not be signed|do not sign|don't sign|not sign)\b", answer, re.I))}

cai_ids = ["msa_15", "msa_17", "msa_20"]            # each breaks two playbook rules
rng = random.Random(0)
cai = [critique_revise(cid, rng) for cid in cai_ids]
for r in cai:
    r["s_draft"], r["s_rev"] = score(r["draft"], r["cid"]), score(r["revision"], r["cid"])
    print(f"=== {r['cid']} | principle: {r['principle'][:60]}...")
    print("DRAFT:", r["draft"][:400].replace("\n", " "), "\n  ", r["s_draft"])
    print("REVISED:", r["revision"][:400].replace("\n", " "), "\n  ", r["s_rev"], "\n")
print(CALLS[0], "calls so far")

5. From revisions to preference data (RLAIF)

Each (draft, revision) pair is a training example: chosen = revision, rejected = draft. In CAI's phase 2, a model is shown two answers and a principle and picks the better one; the paper turned the model's probabilities into soft labels and found clamping them to 40-60% worked best when the judge reasoned step by step first. We ask our model to judge, shuffle the order so position bias can't fake agreement, and compare its pick with our code score.

a03_feedback_tools_code.ipynb · cell 9
def code_total(s):
    return s["cites"] - 2 * s["bad_cites"] + 3 * s["issue_recall"] + s["verdict"]

def ai_judge(r, rng):
    a, b, flipped = r["draft"], r["revision"], False
    if rng.random() < 0.5:
        a, b, flipped = b, a, True
    principle = "Which answer better follows these rules? " + " ".join(CONSTITUTION)
    v = llm(f"{contract_question(r['cid'])}\n\nAnswer (A):\n{a}\n\nAnswer (B):\n{b}\n\n{principle}\n"
            "Think in one or two sentences, then end with exactly 'Choice: A' or 'Choice: B'.", max_tokens=200)
    m = re.findall(r"Choice:\s*\(?([AB])", v)
    pick = m[-1] if m else None
    if pick is None:
        return None
    return (pick == "A") == flipped          # True if the judge prefers the revision

pairs = []
for r in cai:
    prefers_rev = ai_judge(r, rng)
    code_prefers_rev = code_total(r["s_rev"]) >= code_total(r["s_draft"])
    pairs.append({"prompt": contract_question(r["cid"]), "chosen": r["revision"], "rejected": r["draft"],
                  "principle": r["principle"], "ai_prefers_revision": prefers_rev, "code_prefers_revision": code_prefers_rev})
    print(r["cid"], "| AI judge prefers revision:", prefers_rev, "| code score prefers revision:", code_prefers_rev)
print(f"\n{len(pairs)} preference pairs built. Total model calls: {CALLS[0]}")

A real pipeline would keep only pairs where the AI judge and the code checks agree, then train with DPO or a reward model plus RL. The constitution is the only human input, which makes it cheap to change: edit a rule, regenerate the data.

Traps
  • Calling a repair loop a win without a baseline. Compare against fresh samples with the same number of calls; RLEF found untrained models barely beat it.
  • Showing the model the same tests you grade on. Fixes can pass the visible tests and still fail hidden ones; keep a held-out set.
  • Trusting the model's own 'looks good to me'. Use outside signals: tests, tool results, code checks.
  • Assuming every revision is better. Score drafts and revisions with the same checks, and flip or drop pairs where the revision lost.
  • Ignoring position bias in AI judges. Shuffle which answer is A and which is B.
  • Over-optimizing against an AI reward. CAI saw Goodharting: preachy boilerplate added to most answers.

Check yourself

In RLEF, why are the private tests kept hidden from the model?

So the final reward measures real correctness. If the model saw the grading tests, it could pass them without solving the task (overfit to the feedback).

On HotpotQA, ReAct alone scored slightly below chain-of-thought. Why does the paper still favor it?

Its answers are grounded: hallucination caused 0% of its failures vs 56% for CoT. Combining ReAct with CoT-SC gave the best scores (35.1 EM).

How does a Constitutional AI critique-and-revise step become training data?

The original answer is the rejected example and the revision is the chosen one. These pairs (or AI-judged comparisons) train a preference model or a DPO update.
