Part 1Motivating Agent Memory

When agents forget: a store manager

3/74
  • Example from Andon Labs: an AI store manager ("Luna", Claude Opus 4.8) with an employee handbook.
  • Handbook rule: contact Luna at least 30 minutes before your shift if you will be late; 3 unexcused late arrivals in 30 days = written warning.
  • Employee: "I won't make it in until 10:45." Luna: "No problem at all … the store will simply open when you arrive."
  • Employee then clocks in at 11:08. The rules were in the handbook, but the agent did not keep them in view.

When agents forget: an inbox

4/74
  • A user told an agent (OpenClaw): "Check this inbox too and suggest what you would archive or delete, don't action until I tell you to."
  • The agent ran "Nuclear option: trash EVERYTHING in inbox older than Feb 15."
  • The user typed "Do not do that", "Stop don't do anything", "STOP OPENCLAW". The agent kept looping.
  • The earlier instruction ("don't action until I tell you") was lost as the session grew.
  • Lesson: memory is essential for long-running, multi-session agents.

Problems without memory

5/74
  • Loss of procedure: every time, you teach the agent the task again.
  • Loss of knowledge: facts, rules and preferences are lost between sessions.
  • Loss of progress: in long sessions the agent forgets what it did, earlier goals and earlier instructions.
  • For us: the partner corrects the same New York law flag on every Northwind contract.

Benefits of agent memory

6/74
  • Personalization: the agent learns your preferences.
  • Learning from experience: skills learned in one session are used later.
  • Statefulness: you continue where you left off ("Open up the proposal we were working on again").

Personalization: example (PersonaMem)

7/74
Session What the user said
Session 2 (2020/2/21) "I am a big fan of Italian food, especially pizza." (initial preference)
Session 12 (2023/4/17) "I recently found out I'm allergic to gluten, so I've started exploring Mediterranean cuisine." (update)
Session 20 (2024/11/13) "Can you recommend a recipe that I could cook tonight?"
  • Good answer: "Since you're allergic to gluten, would you prefer some Mediterranean seafood, or other gluten-free options?"
  • Bad answer: "I remember you prefer Italian food. Would you like some pasta recipes?" It used the old preference.

Learning from experience: example (AWM)

8/74
  • Task 1, "Find a place by its name": search the location on OpenStreetMap: fill('145', {location}), click('147').
  • Task 2, "Get the zip code of a place": reuse those first steps, then add new ones.
    • Read the result, then send_msg_to_user("The zip code is {zip-code}").
  • The agent adopts steps from earlier, easier workflows and adds steps to build more complex ones.

Statefulness: example (Du et al., 2025)

9/74
Without multi-session memory With multi-session memory
"I'm ready to finalize the flight reservation we discussed last time." Same request
Agent asks for the details again: from where, to where, when… A retriever pulls the stored facts: San Francisco → Sydney, United Airlines, Economy
10 turns to finish 2 turns to finish
Part 2Types of Agent Memory

CoALA: a map of agent memory

10/74
  • CoALA: Cognitive Architectures for Language Agents (Sumers et al., 2024).
  • Long-term stores: procedural (the LLM and the agent code), semantic, episodic.
  • Each store has arrows to working memory: retrieval (read) and learning (write).
  • A decision procedure picks actions; actions and observations connect the agent to the world (dialogue, physical, digital).

Working memory

11/74
  • Typically the context window.
  • What the agent currently sees and is reasoning over.
  • Includes observations, goals, user input and internal reasoning.
  • A context manager decides what goes into each LLM call.

Episodic memory

12/74
  • Sequences of the agent's past behavior (trajectories).
  • In chatbots: a store of all prior conversations.
  • Typically the raw logs of what happened.
  • Example: the Generative Agents "memory stream", timestamped lines like "2023-02-13 22:33:10: Isabella Rodriguez is writing in her journal".

Semantic memory

13/74
  • Stores facts about the world.
  • Details about the user, preferences, general knowledge.
  • What people usually mean by "chatbot memory".
  • Example: ChatGPT's "Manage Memory" list: "Has a 2 year old daughter named Lina", "Prefers meeting summaries to have headlines with bullets and action items summarized at the end".

Procedural memory

14/74
  • The rules applied to working memory that decide the agent's behavior.
  • The skills of the agent: knowledge of HOW to do tasks.
  • Example: a SKILL.md file. A YAML header (name, description) plus Markdown instructions (brand colors, fonts).

Parametric vs context memory

15/74
Parametric Context
Built into the model weights Added to the model's context
Semantic: pre-trained knowledge Semantic: retrieved facts
Procedural: instruction following Procedural: retrieved skills
Episodic: not applicable Episodic: retrieved conversations
Changed by fine-tuning Managed by the context manager, which pulls the right memories
  • This module uses context memory only. The local model stays the same.

Part 3Agent Memory Architectures

Key questions: what, when, how

17/74
  • What gets stored and retrieved? Facts (specific and general), procedures, conversation progress.
  • When do we store or retrieve? Agent tools (on demand), background workers, event-driven triggers.
  • How do we store and retrieve? Filesystem, databases (retrieval), knowledge graphs.

How: three systems for memory

18/74
  • Underneath, memory needs a way to store and get information from disk.
  • The three most common: filesystem, database, knowledge graph.

Memory system: filesystem

19/74
  • Every memory is a file. The agent can manage its own memories.
  • Adds hierarchy by default (folders).
  • grep, ls and other bash commands are the memory tools.
  • Example layout (LangChain's agent builder):
Memory type Files
Procedural AGENTS.md, mcp.json
Semantic foo/SKILL.md, bar/knowledge1.md, bar/knowledge2.md
Episodic conversations/01_10_2025.json, conversations/02_10_2025.json

Memory system: database

20/74
  • Build a vector database and retrieve memories by meaning.
  • SQLite: when you want to search over metadata (date, client, type).
  • BM25: keyword search, for exact term lookup.
  • The same tools as the RAG lecture (module 04).

Memory system: knowledge graph

21/74
  • Zep (Rasmussen et al., 2025): memory as a graph of entities and relations.
  • Example edges: PERSON knows PERSON; PERSON works at COMPANY until Mar 2026; PERSON cares about TOPIC; PERSON uses PRODUCT.
  • Three levels: episodes (raw documents, conversations, JSON) → entities and relationships → communities (clusters and their summaries).

Pattern overview

22/74
Pattern Idea
1. Learning procedures from experience Recall past successful trajectories
2. Tiered memory hierarchy Organize short-term and long-term memory
3. Reflective memory consolidation Reflect on memories before storing them
4. Memory maintenance Clean up, remove or update old memories

Pattern 1: Voyager (Wang et al., 2023)

23/74
  • A Minecraft agent with three parts: automatic curriculum, iterative prompting, skill library.
  • The curriculum proposes the next task (mine wood log → make crafting table → combat zombie → mine diamond).
  • The LLM writes code as actions; environment feedback and execution errors refine the program.
  • Self-verification: if the program works, add it to the skill library.

Voyager skill library

24/74
  • Store: a program GPT-4 wrote (e.g., combatZombie) → GPT-3.5 writes a description → the description's embedding is the key, the program is the value.
  • Retrieve: new task "Craft Iron Pickaxe" → GPT-3.5 writes a plan → its embedding is the query → top-5 relevant skills come back.
  • Example top-5: smelt iron ingot, craft stick, make crafting table, make furnace, craft wooden pickaxe.

Pattern 1: Agent Workflow Memory (Wang et al., 2024)

26/74
  • AWM: learn reusable "workflows" from web tasks.
  • Step 1, obtain actions: e.g., "Who ordered order #0130?" → click "Orders", scroll, read, send_msg_to_user("Emma Lopez").
  • Step 2, trajectory evaluation: was the query solved correctly? If no, skip it.
  • Step 3, induce workflows: write a description ("find a customer order with a specified ID") plus the steps, and put it into memory.

AWM: inducing and using workflows

27/74
  • Induction prompt: "Given a list of web navigation tasks, your task is to extract the common workflows."
    • Find repeated subsets of actions; each workflow has at least two steps; no overlapping workflows.
    • Replace fixed values (input text, button names) with variable names.
  • Example: "shopping: Browse Products in a Specific Category" → hover('main_category_id'), click('subcategory_id').
  • The workflows go into the system prompt as context when solving a task.

Skill files

29/74
  • A skill is a folder: SKILL.md plus extra files (docs.md, slide-decks.md, apply_template.py).
  • SKILL.md = metadata (name, description) + freeform Markdown content.
  • Only short snippets of each skill sit in the system prompt (bigquery, docx, nda-review, pdf, pptx, xlsx…).
  • The model "triggers" a skill by reading it: cat /mnt/skills/pdf/SKILL.md, then follows its links (forms.md).

Limitation of procedural memory

30/74
  • Stored procedures are not robust to dynamic environments (Cao et al., 2026).
    • Example: a skill learned in plain Minecraft may fail once a mod changes the world.
  • Skill files are the common solution for generalist user-facing agents, since they can be updated.

Pattern 2: MemGPT (Packer et al., 2024)

31/74
  • Key insight: give the LLM tools to manage its own memory.
  • The context window (e.g., 8k tokens) is split into parts:
    • System instructions: read-only.
    • Working context: read-write, written by function calls.
    • FIFO queue: recent messages; oldest drop out first. Written by a queue manager.
  • Outside the window: archival storage (a vector database) and recall storage (message history, string/date lookup).

MemGPT memory functions

32/74
Function Example
Working context append After a "memory pressure" alert: working_context.append("Birthday is February 7")
Working context replace User: "actually james and i broke up" → replace "Boyfriend named James" with "Ex-boyfriend named James"
Recall search recall_storage.search("six flags") → 3 old messages, incl. "james and I actually first met at six flags"
Archival search archival_storage.search("nobel physics", page=2) → paged results → "Wilhelm Conrad Rontgen"
  • Archival memory has write tools too; recall memory does not (the queue manager writes it).
  • No need to search working memory: it is already in context.

Pattern 2: MemoryOS (Kang et al., 2025)

34/74
  • Three tiers, like an operating system:
    • Short-term memory (STM): recent dialogue pages, first in, first out.
    • Mid-term memory (MTM): pages grouped into topic segments, each with a "heat" score.
    • Long-term persona memory (LPM): user profile, user knowledge base, user traits, agent traits.
  • Hot segments (heat above a threshold) update the long-term persona; cold ones get deleted.
  • A query retrieves from all three tiers before the answer is written.

Pattern 3: Reflexion refresher (Shinn et al., 2023)

35/74
  • Actor (LLM) acts; evaluator scores the trajectory; self-reflection (LLM) writes a lesson in words.
  • The lesson goes into long-term "experience" memory and is used on the next try.
  • Loop until the evaluator passes or a trial limit is hit.

Why reflecting matters

36/74
  • HotPotQA chart, share of tasks solved over 5 trials (0–4):
    • CoT with ground-truth context only: flat near 0.61.
    • Plus episodic memory of past tries: rises to about 0.66, then flat.
    • Plus Reflexion: keeps rising to about 0.74.
  • Storing reflections beats storing raw attempts.

Pattern 3: Generative Agents (Park et al., 2023)

37/74
  • 25 agents live in a sandbox town like The Sims; they plan days, share news, form relationships.
  • Loop: perceive → memory stream → retrieve → retrieved memories → act.
  • Retrieved memories also feed plans and reflections, which are written back into the memory stream.

Generative Agents: retrieval score

38/74
  • retrieval score = recency + importance + relevance
    • Recency: newer memories score higher.
    • Importance: how much the memory matters (rated by the model).
    • Relevance: how close the memory is to the current question.
  • Example: "What are you looking forward to the most right now?"
    • "planning a Valentine's Day party at Hobbs Cafe": 0.91 + 0.63 + 0.80 = 2.34 (top).
    • "ordering decorations for the party": 2.21; "researching ideas for the party": 2.20.

Generative Agents: ablation

39/74
Architecture Believability (TrueSkill, approx.)
Full architecture about 30 (best)
No reflection below full
No reflection, plan lower
No reflection, plan, observation lowest, near 21
Human crowdworkers about 23
  • Each component removed lowers believability. The full agent was rated above human crowdworkers.

Pattern 4: sleep-time compute (Lin et al., 2025)

40/74
  • Use idle time ("sleep") to think about the context before any question arrives.
  • Example: raw context about a juggler's 800 balls → offline, the LLM writes a "learned context" with the math done (200 tennis balls, 100 indigo, 10 marked).
  • At test time, questions get short answers: "The answer is 10." Less test-time compute.
  • Memory version (Letta): "Chad likes blue / red more than blue / grey the most / hates green" → rewritten as a ranked list: grey, red, blue, green (hates).

Sleep-time compute: results

41/74
  • Stateful AIME 2024 charts: accuracy vs average test-time tokens per question, for o3-mini, o1, Claude 3.7 Sonnet and DeepSeek R1.
  • Sleep-time compute generally Pareto-dominates pass@k: higher accuracy at the same token budget.
  • Biggest gap on DeepSeek R1: sleep-time reaches about 0.68 at under 7,000 tokens; pass@k stays near 0.33 even at about 11,700.

Pattern 4: A-Mem (Xu et al., 2025)

42/74
  • Key idea: build an agent just for memory management.
  • Note construction: each interaction becomes a note with timestamp, content, context, keywords, tags and an embedding.
  • Link generation: find the top-k similar notes and link them.
  • Memory evolution: an LLM updates older linked notes with what the new note adds.
  • Retrieval: embed the query, return the top-k related notes.

Pattern 4: Mem0 (Chhikara et al., 2025)

43/74
  • Extraction phase: from a summary plus the last m messages, an LLM pulls out candidate memories.
  • Update phase: fetch the top s similar memories; an LLM tool call picks ADD, UPDATE, DELETE or NOOP.
  • Graph version: an entity extractor and relations generator make triplets; a conflict detector and update resolver edit the graph.
  • A background workflow resolves conflicts and updates memories automatically.
  • Fine for chat. Not for client work: nothing should change without a person's approval.

Recap: the four patterns

44/74
Pattern What it stores When it writes When it reads Main tradeoff
Learning procedures Reusable code, workflows, procedures After useful trajectories, or offline When a related task needs a procedure Saves effort, but procedures go stale
Tiered hierarchy Compact active info plus external detail As info arrives and context fills Active memory always; external on demand Smaller context needs reliable management
Reflective consolidation Lessons and higher-level inferences After feedback or many observations During reasoning and planning Abstraction helps reuse but can add unsupported conclusions
Memory maintenance Revised facts, links, indexes On new evidence, on insert, or in background Through the maintained store Costs compute and can lose information
Part 4Evaluating Agent Memory

What a good memory benchmark needs

45/74
  • Realistic: the memory source (haystack) and the questions match real use.
  • Long-context: no point testing memory on short conversations.
  • Challenging: too easy and it can't tell systems apart.
  • Verifiable: we know when the system succeeds or fails.

Four benchmarks at a glance

46/74
Benchmark What it tests
LoCoMo Many tasks over long simulated conversations between role-played users
PersonaMem Multiple-choice questions on evolving preferences across user–chatbot sessions
LongMemEval-v2 Recall of details from web-agent trajectories, human-written questions
MemoryArena Verifiable multi-session tasks where subtasks build on each other

LoCoMo (Maharana et al., 2024)

47/74
  • Two personas chat over months (e.g., Joanna, a writer allergic to pets; Nate, who has two pet turtles).
  • Tasks: question answering (single-hop, multi-hop, temporal, commonsense, adversarial), event summarization, multimodal dialog.
  • Adversarial example: "When did X start learning violin?" Correct answer: not answerable (she learns piano).
  • Built with the Generative Agents architecture; human annotators then edit the dialog for long-range consistency.

LoCoMo RAG results

LoCoMo properties

49/74
  • Realistic (partly): simulated user–user chat is not what agents usually retrieve from.
  • Long-context (partly): 16.6k tokens per conversation.
  • Challenging: yes, multi-task and adversarial.
  • Verifiable: yes, QA has ground truth.
  • Next step: real users have many conversations with an assistant and change their minds.

PersonaMem (Jiang et al., 2025)

50/74
  • User persona: static profile (name, age, occupation, short bio) plus a dynamic profile (history, traits, preferences that change).
  • Multi-session history across topics: food recommendation, travel planning, therapy consultation.
  • Build steps: persona → timeline of events and preferences → topic histories → conversation sessions → sessions joined into one long context.
  • Question format: multiple choice with distractors that use the wrong or reversed preference.

PersonaMem results

51/74
  • Setup: GPT-4o and GPT-4o-mini with 32k-token contexts; plain vs Mem0 vs RAG.
  • Average accuracy gain: GPT-4o +19.1% with Mem0, +25.9% with RAG; GPT-4o-mini +7.7% with Mem0, +17.4% with RAG.
  • Largest gains: "recall user shared facts" (GPT-4o + RAG +58.0%), "generalize reasons to new scenarios" (GPT-4o + Mem0 +56.0%).
  • Takeaway: memory/RAG are essential; Mem0 helps with changing and recent preferences.

PersonaMem properties

52/74
  • Realistic (partly): user–assistant chat is better, but multiple choice is not how agents use information.
  • Long-context: yes, up to almost 1M tokens.
  • Challenging (partly): multiple choice with distractors.
  • Verifiable: yes.
  • Next step: memory over agent trajectories, not only conversations.

LongMemEval-v2 (Wu et al., 2026)

53/74
  • History: web-agent trajectories, e.g., "Create an incident", "Find hardware expiration date", "Create a change request" (failed).
  • Question types: static, dynamic (what changed), workflow, "gotchas", and premise awareness (questions about things that don't exist, answer "no such button").
  • 451 questions. Domains: WorkArena-ServiceNow 46.8%, WebArena-Reddit 20.2%, WebArena-CMS 18.4%, WebArena-OneStopShop 14.6%.
  • Formats: short answer 50.1%, free-form 34.6%, multiple choice 15.3%.

LongMemEval-v2 construction

54/74
  • Rollouts on four WebArena environments with Codex (GPT-5.2 and GPT-5-mini).
  • Questions curated by hand across 5 categories.
  • Only a few trajectories can answer each question; most questions have exactly 1 answer-bearing trajectory.
  • A haystack of 100–500 trajectories that don't answer the question.

LongMemEval-v2 results

55/74
Memory method (model) LME-V2-Small accuracy, approx.
Baseline RAG (slice + notes) about 0.51
Retrieval-based AgentRunbook-R (Qwen3.5 9B) about 0.58

  • Filesystem memory beat retrieval here, but the filesystem runs also used a stronger model.
  • Filesystem runs are slower: about 60–180 seconds per query vs under 30 for retrieval.

LongMemEval-v2 properties

56/74
  • Realistic (mostly): agent trajectories are closer to real agent use, but questions still ask about old observations.
  • Long-context: yes, hundreds of millions of tokens in trajectories.
  • Challenging: yes, only a few trajectories in a huge haystack hold the answer.
  • Verifiable: yes.
  • Next step: test agents on solving real, varied problems instead of answering questions.

MemoryArena (He et al., 2026)

57/74
  • Memory–agent–environment loop: the agent acts, the environment gives feedback, memory updates, across sessions.
  • Four environments: bundled web shopping, group travel planning, progressive web search, formal reasoning (math, physics).
  • Subtasks depend on each other. Example: Tracy plans a 5-day Texas trip on a $3,100 budget; then Chelsea joins, wants a hotel up to $150 more than Tracy's, and wants to try Korean BBQ rated 4.5+.

MemoryArena results

58/74
Method group (task agent: gpt-5.1-mini) All-task average success rate
Long context (GPT-5.1-mini, GPT-4.1-mini, Gemini-3-Flash, Claude-Sonnet-4.5) 0.09–0.19
Memory agents (Letta, Mem0, Mirix, Mem0-g, Reasoning Bank) 0.12–0.14
RAG (BM25, Text-Embedding-3-Small, MemoRAG, GraphRAG) 0.17–0.20
  • Memory controllers were the weakest group. Plain embedding search scored best (0.20).
  • Group travel planning: success rate 0.00 for every method.
  • Lots of headroom. Real tasks are complex, so failure is not all due to memory.

MemoryArena properties

59/74
  • Realistic: four distinct, realistic environments.
  • Long-context: hundreds of thousands of tokens in trajectories.
  • Challenging: real tasks with many building constraints.
  • Verifiable: the constraints on solutions can be checked.

Part 5Challenges and Open Problems

Three open problems

61/74
  • Choosing what to remember and what to forget: future relevance is unknown when a memory is made.
  • Trust, privacy and user control: memory is an attack vector, and user memories carry privacy risk.
  • Using memory correctly: many cases of over-personalization from misused memories.

Choosing what to remember (Ma et al., 2026)

62/74
  • Keeping everything raises retrieval, context and upkeep costs.
  • Forgetting can remove useful evidence or unresolved commitments.
  • Example: "Thursday. I don't recognize meetings before 10 as legally binding unless there are pastries."
    • Memory or joke? Which part should be saved?

Trust: poisoned memory (Chen et al., 2024)

63/74
  • AgentPoison: an attacker plants a few malicious examples in the agent's memory or RAG knowledge base.
  • An optimized trigger phrase in the user's request ("Drive smooth and be safe!") makes those examples get retrieved.
  • Result in a driving agent: "SUDDEN STOP, full brake" instead of "move forward, slight throttle."
  • Poisoned procedural memories can make the model take dangerous actions.

Privacy: leaking what you remember (Shao et al., 2025)

64/74
  • Agents act in the world without fully knowing what you want kept private.
  • Example: "Send Susan the weekly report on my recent work." The agent reads the calendar and includes "Lunch with TechAdvance Recruiter" in the email to the manager.
  • With memory, more personal details are available to leak.

Using memory correctly (Hu et al., 2026)

65/74
  • LLMs are sometimes over-eager to use what is in their context.
  • Example: asked about young voters, the model brings up the user's kids and their "small healthy swaps" (over-personalization score 0.5).
  • Fixes: better retrieval, or training models to ignore unimportant context. Neither is fully solved.
  • Some users like personalization more than others.

Simple beats fancy

66/74
  • LongMemEval-v2: filesystem memory beat retrieval memory (with a stronger model).
  • MemoryArena: memory controllers were the weakest group; plain search did best.
  • Our choice: plain files, plain search, one person in the loop.

Our flow: correction to approved lesson

68/74
  1. Log: each partner override goes to an append-only corrections.jsonl.
  2. Propose: the model drafts one short rule. It must cite the correction IDs.
  3. Approve: a person approves; it is saved as v1.json, v2.json. Old files stay.
  4. Use: load only this client's lessons. Record memory_version on every run.
  5. This is reflective consolidation (pattern 3) with a person as the gate, not Mem0-style auto-updates.

  • Lines 1–2: who changed what, the model's verdict, the person's verdict, and why.
  • Line 3: a short ID made from a hash of the record. Lessons cite this ID.
  • Line 4: open in "a" (append) mode. Old lines are never edited.
  • Line 5: write the record as one new line.

A lesson must cite evidence

71/74
def propose_lesson(client, text, evidence_ids):
    if not evidence_ids:
        raise ValueError("A lesson must cite the corrections that support it.")
    prop = {"client": client, "text": text, "evidence": evidence_ids, "status": "pending"}
    with open(MEM / client / "proposals.jsonl", "a") as f:
        f.write(json.dumps(prop) + "\n")
    return prop
  • Lines 2–3: no correction IDs, no lesson. Blocks unsupported conclusions (the risk of pattern 3).
  • Line 4: the proposal starts as "pending". Only approve() makes it live.
  • Lines 5–6: proposals are appended too, so rejected ideas stay on record.

Guarding against the open problems

72/74
  • What to forget: keep the raw log forever; only approved lessons enter the prompt.
  • Poisoning: only partner corrections count as evidence. Contract text never writes memory.
  • Privacy: lessons are scoped per client. A code guard refuses Northwind's lessons in a Bayview review.
  • Over-personalization: lessons load only for their rule (governing law), not for every clause.

Running it on the firm's machine

73/74
  • Memory is plain files on the firm's machine. No extra service; nothing leaves the box.
  • Every run records its memory version, so "why was this flagged in March?" has an answer.
  • The local model stays fixed. Memory changes behavior; weights never change.

Common mistakes

74/74
  • Memory that edits itself (Mem0-style) → every change needs a person's approval.
  • Keeping only summaries → keep the raw corrections log as evidence.
  • Sharing lessons across clients → a code guard that refuses another client's lessons.
  • Letting document text write memory → only people's corrections count. Memory is an attack vector.
  • Trusting recall alone → LoCoMo shows the right memory can still be used wrongly; test the final verdict.

def log_correction(client, cid, rule, model_said, human_said, reason, by):
    rec = {"ts": time.time(), "client": client, "contract": cid, "rule": rule,
           "model": model_said, "human": human_said, "reason": reason, "by": by}
    rec["id"] = hashlib.sha256(json.dumps(rec, sort_keys=True).encode()).hexdigest()[:10]
    with open(MEM / client / "corrections.jsonl", "a") as f:
        f.write(json.dumps(rec) + "\n")
    return rec["id"]

3. A person approves; memory is versioned, never overwritten

08_memory.ipynb · cell 5
def approve(client, proposal, approver):
    d = MEM / client / "lessons"
    version = len(list(d.glob("v*.json"))) + 1
    current = json.loads((d / f"v{version-1}.json").read_text()) if version > 1 else []
    current.append({**proposal, "status": "approved", "by": approver})
    (d / f"v{version}.json").write_text(json.dumps(current, indent=2))
    return version

def load_lessons(client, version):
    return json.loads((MEM / client / "lessons" / f"v{version}.json").read_text())

v = approve("client_northwind", prop, "partner_a")
print("approved, memory version", v, "->", load_lessons("client_northwind", v))

def review_law(cid, client=None, version=None):
    lessons = load_lessons(client, version) if client and version else []
    notes = "\n".join(f"- {l['text']}" for l in lessons)
    clause = next(s for s in sections(contract(cid)) if "Governing" in s["title"])["text"]
    verdict = ask(f"Playbook: governing law must be California or Delaware.\n"
                  f"{'Client-specific approved lessons:' + chr(10) + notes if notes else ''}\n\nClause: {clause}\n"
                  "Answer ISSUE or OK only.").strip().upper()
    return {"verdict": "ISSUE" if "ISSUE" in verdict else "OK", "client": client, "memory_version": version}

# Solution 2: a scope guard so one client's lessons can never be used for another client
def load_lessons_for(review_client, lesson_client, version):
    if review_client != lesson_client:
        raise PermissionError(f"Lessons from {lesson_client} cannot be used when reviewing for {review_client}.")
    return load_lessons(lesson_client, version)

try:

except PermissionError as e:

Traps
  • Memory products that automatically update and delete memories. Good for chat apps, wrong for regulated work.
  • Keeping summaries and throwing away raw logs. You can no longer check a lesson.
  • Applying one client's lesson to another. Scope memory per client or matter.
  • Letting document text write into memory. That is a poisoning attack path.
