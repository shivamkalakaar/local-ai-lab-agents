Module 08

Memory

Open in Colab
8 min readSlides first, then the deeper material

Let an agent learn from a partner's corrections. Plain files, a cited lesson, a person's approval, and a version number on every run.

Based on CS329Z Lecture 7 · Agent Memory Architectures · original slides (PDF)

Learning objective

1/12
  • Build memory that learns from corrections, cites its evidence, waits for approval, and never silently changes.

Problems without memory

2/12
  • Loss of procedure: you teach the agent the task again every time.
  • Loss of knowledge: facts, rules and preferences are lost between sessions.
  • Loss of progress: in long sessions the agent forgets earlier goals and instructions.
  • For us: the partner corrects the same New York law flag on every Northwind contract.

Types of agent memory (CoALA)

3/12
Type What it holds Our example Who may write
Working What the model sees now (the context window) The contract under review The agent
Episodic Raw logs of what happened "Partner changed our flag on 10.1" Append-only log
Semantic Facts and preferences "This client accepts New York law" Agent proposes, person approves
Procedural Skills: how to do the task Prompts, checklists Change control only

Parametric vs context memory

4/12
  • Parametric: built into the model weights. Changed only by fine-tuning.
  • Context: added to the prompt when needed (retrieved facts, skills, past conversations).
  • This module uses context memory only. The local model stays the same.

Key questions: what, when, how

5/12
  • What to store: facts, procedures, conversation progress.
  • When to store or retrieve: agent tools (on demand), background workers, events.
  • How to store: filesystem, database (vector search, SQLite, BM25), knowledge graph.
  • Filesystem: every memory is a file. grep and ls are the memory tools.

Four memory patterns from the lecture

6/12
Pattern Example system Idea
Learn procedures from experience Voyager, AWM, skill files Save what worked, reuse it
Tiered memory MemGPT, MemoryOS Short-term vs long-term stores
Reflective consolidation Reflexion, Generative Agents Reflect before storing
Memory maintenance Mem0, A-Mem, sleep-time compute Add, update, delete old memories
  • Mem0 updates memories on its own (ADD, UPDATE, DELETE, NOOP). Fine for chat; not for client work.

Simple beats fancy

7/12
  • LongMemEval-v2: filesystem memory outperformed retrieval memory.
  • MemoryArena: memory controllers were the weakest method.
  • Our choice: plain files, plain search, one person in the loop.

Our flow: correction to approved lesson

8/12
  1. Log: each partner override goes to an append-only corrections.jsonl.
  2. Propose: the model drafts one short rule. It must cite the correction IDs.
  3. Approve: a person approves; it is saved as v1.json, v2.json. Old files stay.
  4. Use: load only this client's lessons. Record memory_version on every run.

Same contract, two clients

9/12
Generic client Northwind, memory v1
msa_15, 10.1: "governed by the laws of the State of New York" Same clause, plus the approved lesson from 3 partner corrections
Playbook: California or Delaware only → expected ISSUE Lesson says NY is fine for this client → expected OK, memory_version: 1

Logging a correction in code

10/12
rec = {"ts": time.time(), "client": client, "contract": cid, "rule": rule,
       "model": model_said, "human": human_said, "reason": reason, "by": by}
rec["id"] = hashlib.sha256(json.dumps(rec, sort_keys=True).encode()).hexdigest()[:10]
with open(MEM / client / "corrections.jsonl", "a") as f:
    f.write(json.dumps(rec) + "\n")
  • Lines 1–2: who changed what, the model's verdict, the person's verdict, and why.
  • Line 3: a short ID made from a hash of the record. Lessons cite this ID.
  • Line 4: open in "a" (append) mode. Old lines are never edited.
  • Line 5: write the record as one new line.

How this applies to us

11/12
  • Memory is plain files on the firm's machine. No extra service, nothing leaves the box.
  • Every run records its memory version, so "why was this flagged in March?" has an answer.
  • Lessons are scoped per client. Northwind's lesson never reaches another client's review.

Common mistakes

12/12
  • Memory that edits itself → every change needs a person's approval.
  • Keeping only summaries → keep the raw corrections log as evidence.
  • Sharing lessons across clients → a code guard that refuses another client's lessons.
  • Letting document text write memory → only people's corrections count as evidence. Memory is an attack vector.

Check your understanding

A partner overrides the agent the same way on three contracts. What happens next?

Each override is logged. The agent proposes one lesson citing those three IDs, a person approves it, and it ships as the next version.

Why record the memory version on every run?

So any past decision can be replayed with the exact lessons it used.

Why is procedural memory the riskiest to change?

It is the prompts and checklists behind every review. A bad change hits all clients at once, so test it before release.

Go deeper

Key terms, papers, evidence, the full notebook code and worked solutions.

Lecture 7 · CoALA · MemGPT · Generative Agents · MemoryArena · LoCoMo

Keep memory simple, cited and approved. Plain files and plain search beat fancy memory products, and an agent that silently rewrites its own memory can't be trusted or audited.

Key terms

Working memory
What is in the context right now.Source: Sumers et al., "Cognitive Architectures for Language Agents" (CoALA), TMLR (2024)
Episodic memory
A record of what happened (past runs, corrections). Best kept append-only.Source: CoALA (2024)
Semantic memory
Facts and lessons derived from experience, such as "this client accepts New York law".Source: CoALA (2024)
Procedural memory
How to act: prompts, code, skills, weights. Changing it is the riskiest kind of learning.Source: CoALA (2024)
Memory hierarchy (MemGPT)
Treating the context like RAM and external storage like disk, paging information in and out.Source: Packer et al., "MemGPT" (2023)
Reflection
Periodically summarizing memories into higher-level insights that cite the records behind them.Source: Park et al., "Generative Agents", UIST (2023)

import json, time, hashlib, shutil
from pathlib import Path
# lal.llm = the OpenAI client pointed at the local Ollama server, http://localhost:11434/v1 (see notebook 00)
from lal.llm import ask
from lal.data import contract, sections, labels
from lal.checks import check

MEM = Path("memory_demo"); shutil.rmtree(MEM, ignore_errors=True)
(MEM / "client_northwind" / "lessons").mkdir(parents=True)

1. Episodic memory: an append-only corrections log

08_memory.ipynb · cell 3
def log_correction(client, cid, rule, model_said, human_said, reason, by):
    rec = {"ts": time.time(), "client": client, "contract": cid, "rule": rule,
           "model": model_said, "human": human_said, "reason": reason, "by": by}
    rec["id"] = hashlib.sha256(json.dumps(rec, sort_keys=True).encode()).hexdigest()[:10]
    with open(MEM / client / "corrections.jsonl", "a") as f:
        f.write(json.dumps(rec) + "\n")
    return rec["id"]

# Suppose the agent flagged New York law three times, and the partner overrode it each time.
ev = [log_correction("client_northwind", c, "governing_law", "ISSUE", "OK",
                     "This client has an NY office; NY law is acceptable for them.", "partner_a") for c in ["msa_15", "x_101", "x_102"]]
print(open(MEM / "client_northwind" / "corrections.jsonl").read())

2. Semantic memory: the agent proposes a lesson, citing evidence

08_memory.ipynb · cell 4
def propose_lesson(client, text, evidence_ids):
    if not evidence_ids:
        raise ValueError("A lesson must cite the corrections that support it.")
    prop = {"client": client, "text": text, "evidence": evidence_ids, "status": "pending"}
    with open(MEM / client / "proposals.jsonl", "a") as f:
        f.write(json.dumps(prop) + "\n")
    return prop

corrections = [json.loads(l) for l in open(MEM / "client_northwind" / "corrections.jsonl")]
draft = ask("Write ONE short rule (max 20 words) a contract reviewer should follow for this client, based on these corrections:\n"
            + "\n".join(f"- {c['rule']}: model said {c['model']}, partner said {c['human']} because {c['reason']}" for c in corrections))
prop = propose_lesson("client_northwind", draft.strip(), [c["id"] for c in corrections])
print(prop)

3. A person approves; memory is versioned, never overwritten

08_memory.ipynb · cell 5
def approve(client, proposal, approver):
    d = MEM / client / "lessons"
    version = len(list(d.glob("v*.json"))) + 1
    current = json.loads((d / f"v{version-1}.json").read_text()) if version > 1 else []
    current.append({**proposal, "status": "approved", "by": approver})
    (d / f"v{version}.json").write_text(json.dumps(current, indent=2))
    return version

def load_lessons(client, version):
    return json.loads((MEM / client / "lessons" / f"v{version}.json").read_text())

v = approve("client_northwind", prop, "partner_a")
print("approved, memory version", v, "->", load_lessons("client_northwind", v))

4. Use the lessons, scoped to one client

The same contract, reviewed for two clients. Only Northwind's review uses Northwind's lesson. Each run records the memory version it used, so any decision can be replayed.

08_memory.ipynb · cell 6
def review_law(cid, client=None, version=None):
    lessons = load_lessons(client, version) if client and version else []
    notes = "\n".join(f"- {l['text']}" for l in lessons)
    clause = next(s for s in sections(contract(cid)) if "Governing" in s["title"])["text"]
    verdict = ask(f"Playbook: governing law must be California or Delaware.\n"
                  f"{'Client-specific approved lessons:' + chr(10) + notes if notes else ''}\n\nClause: {clause}\n"
                  "Answer ISSUE or OK only.").strip().upper()
    return {"verdict": "ISSUE" if "ISSUE" in verdict else "OK", "client": client, "memory_version": version}

print("generic client:  ", review_law("msa_15"))
print("Northwind, v1:   ", review_law("msa_15", "client_northwind", v))

# Solution 2: a scope guard so one client's lessons can never be used for another client
def load_lessons_for(review_client, lesson_client, version):
    if review_client != lesson_client:
        raise PermissionError(f"Lessons from {lesson_client} cannot be used when reviewing for {review_client}.")
    return load_lessons(lesson_client, version)

try:
    load_lessons_for("client_bayview", "client_northwind", v2)
except PermissionError as e:
    print("blocked:", e)
Traps
  • Memory products that automatically update and delete memories. Good for chat apps, wrong for regulated work.
  • Keeping summaries and throwing away raw logs. You can no longer check a lesson.
  • Applying one client's lesson to another. Scope memory per client or matter.
  • Letting document text write into memory. That is a poisoning attack path.

Check yourself

A partner overrides the agent on 3 contracts in the same way. What should happen?

Each override is logged as an episodic record. The agent proposes one lesson citing those 3 records. A person approves it, and it ships in the next memory version, after passing the eval.

Why pin a memory version to every run?

So any past decision can be replayed exactly as it was made. An auditor or the client can ask "why did it flag this in March?"
