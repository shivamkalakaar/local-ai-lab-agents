Data is the key differentiator

5/119
  • Percy Liang's CS 336 data lecture: data is the most important thing to get right.
  • Open-weight models (e.g., Llama 3) share architecture and training steps, but almost nothing on data.
  • Llama 3 report: one short paragraph on pre-training data (dedup, cleaning, removing PII and adult domains).
  • Kimi-K2: open weights, no data release.
  • James Betker (OpenAI), "The 'it' in AI models is the dataset": trained long enough on the same data, models converge to the same point.

Where agent data lands in training

7/119
Pretraining SFT & RLHF RL
runs on internet text runs on conversations runs on environments
  • Agent data = conversations and environments.
  • Conversations are demonstrations. Environments are places to practice.
  • Karpathy (Aug 2025): now it is environments. They let the LLM act and see outcomes, so it can do better than "statistical expert imitation."

Text vs environment

8/119
What's on the internet What's possible in an environment
Q: TypeError in parse_date() when passing a string? $ grep -rn parse_date src/ → utils.py:42
A: Wrap it in strptime() first. $ pytest tests/ → FAILED: TypeError
$ edit src/utils.py → $ pytest → 1 passed
  • Web crawls show a lot of text. Agents need environments to actually interact.

Part 2Lecture 11 · Kinds of agent data

Trajectory vs environment

11/119
🎞 Trajectory 📦 Environment
A recording of an agent solving a task A task + sandbox + a way to check success
Think → Act → Obs → Act → Obs → Submit Task · Sandbox · Verifier
Train with SFT: the LM imitates it Train with RL: the LM practices ReAct
  • SFT: supervised fine-tuning; train on examples of the outputs you want.
  • RL: reinforcement learning; the model tries, and a reward scores the try.

Anatomy of a trajectory

12/119
Role Content Learned?
SYSTEM You are a coding agent. Tools: bash, edit, submit context only
USER Issue: separability_matrix is wrong for nested models context only
AGENT grep -rn "def _cstack" astropy/modeling/ learned
TOOL separable.py:219: def _cstack(left, right): context only
AGENT edit, run reproduce_issue.py, submit learned
  • Loss mask: the model is trained to predict only the agent's thoughts and actions.
  • The format (tool calls, ReAct text, code actions) is set by the system around the LM.

Anatomy of a post-training task

13/119
  • Problem statement: says what must be done (e.g., an ffmpeg command outputs 1920×1080, not 1280×720).
  • Agent: reads it, works in the sandbox with ReAct.
  • Sandbox: terminal, browser, simulator, or real world.
  • Submission, then verification: unit/E2E tests, rubrics, or preference → pass or fail.
  • Run an LM on an environment and record it: you get a trajectory.

Where the RL reward comes from

14/119
Code tests Rubrics LM-as-a-judge Human preference
Unit tests check deterministically An LM or human checks a checklist A model ranks 2+ solutions People pick the best answer live
  • Left end: reliable, but narrow. Right end: general, but fuzzy.
  • For trajectories / SFT, the "reward" is predicting the correct action.

Training on each

15/119
  • One environment → many rollouts.
  • Curate ⇒ SFT data: imitate what is kept.
  • Score ⇒ RL update: weight each attempt by its reward.
  • Rollout: one full attempt by the agent on a task.

How much data at each stage?

16/119
Stage DeepSeek data point
Pretraining 14.8T tokens (v3)
SFT 1.5M examples (v3)
RL 85k task prompts (v3.2)
  • v3 compute in H800 GPU hours: pre 2,664k, mid 119k, post 5k.
  • One year later, V3.2: post-train budget exceeds 10% of pre-training.
  • Labs usually don't disclose this.
Part 3Lecture 11 · Where agent data comes from

Five sources

17/119
# Source Idea
1 Human demos People do the task; a recorder logs it
2 Mined from web, world Convert issues, tutorials, videos
3 Synthesized trajectories A model writes or runs the steps
4 Synthesized tasks, envs Build task + sandbox + checker in code
5 Simulated users, envs An LLM plays the user or the world
  • For each, ask: cost, realism, scalability. Why does it fit this domain?

1 · Human demonstrations: the recipe

18/119
  1. Define: write task goals on real sites or apps.
  2. Perform: an annotator does each task by hand.
  3. Record: log every screen state + click, keystroke.
  4. Filter: drop failed or noisy runs; verify success.
  5. Package: store as task + step pairs, optionally with reasoning.
  6. Output: task → (screen₁, action₁) → … → (screenₙ, actionₙ).

Mind2Web (Deng et al., NeurIPS 2023)

19/119
  • Crowdworkers recorded action sequences for 2,000+ open-ended tasks on 137 real websites, 31 domains.
  • Examples: "Find one-way flights from New York to Toronto"; "Open page to schedule an appointment for car knowledge test" (DMV).
  • Domain mix: Travel 27.4%, Info 20.4%, Service 18.3%, Shopping 17.5%, Entertainment 16.1%.
  • Tests generalization: same site, similar tasks on different sites, totally different domains.

Mind2Web: one data instance

20/119
  • Task: "Show me the reviews for the auto repair business closest to 10002."
  • 10 actions: TYPE "auto repair" in search box → CLICK Auto Repair → TYPE 10002 → CLICK Search → … → CLICK Read Reviews.
  • Three parts: task description, action sequence (target element + operation), webpage snapshots.
  • Some actions cause a jump to a new page.

OpenCUA (Wang et al., NeurIPS 2026)

21/119
  • CUA: computer-use agent; controls a desktop with mouse and keyboard.
  • An app on annotators' own computers records screen video, mouse and keyboard.
  • 22.6K tasks across Windows, macOS and Ubuntu.
  • Also saves metadata: accessibility tree (Axtree), HTML, timestamps.

OpenCUA: human action → agent action

22/119
Human action Agent action
Click, double, triple, middle click click(x, y, button), doubleClick, tripleClick, middleClick
Mouse move, drag, scroll moveTo(x, y), dragTo(x, y), scroll(dx, dy)
Type, press, hotkey write(text), press(key), hotkey(key1, key2)
Wait, terminate wait(), terminate('success' or 'failure')

Case study: Mind2Web vs OpenCUA

23/119
Mind2Web OpenCUA
Who records Crowdworkers in a recording tool Annotators on their own computers
Environment Web only: 137 sites, 31 domains Desktop: 3 OSes, 200+ apps, sites
Recorded Actions + page snapshot per step Video, inputs, accessibility tree
Tasks 2,350 22.6K
Reasoning None; raw actions only Synthetic, added per step

2 · Mined from the web + world

24/119
  • Raw sources: code history (GitHub issues + the PRs that fixed them), written tutorials, videos (screen recordings, gameplay).
  • Convert:
  • Extract the task: issue, guide title or video goal → instruction.
  • Recover the actions: parse diffs or steps; label video with an inverse dynamics model.
  • Replay and verify: rerun live; keep runs that succeed.
  • Output: trajectory = instruction + observation/action steps + pass/fail signal.

SWE-rebench (Badertdinov et al., NeurIPS 2026)

25/119
  • Fully automated pipeline: 21,336 verifiable tasks from 3,468 GitHub repos.
  • Uses the SWE-bench task format (Jimenez et al., 2023): issue + codebase → model writes a PR → unit tests that fail before and pass after.
  • Steps: filter repos and PRs (GitHub + GHArchive) → an LLM guesses the install script, retried until tests run → LLM labels instances.
  • Final dataset: 21,000+ samples.

AgentTrek (Xu et al., ICLR 2025)

26/119
  • Harvest how-to tutorials from the web (a classifier filters them).
  • A VLM agent replays them in a real browser, guided by the tutorial.
  • A VLM evaluator keeps successful runs. $0.55 per trajectory.
  • VLM: vision-language model; reads screenshots.
  • Example: "Find the return policy for men's football apparel on Under Armour's website" → 9 steps, each with a thought and an action.

AgentTrek vs other datasets

27/119
Dataset Size Avg steps Reasoning Video Websites
RUSS 80 5.4 No No 22
WebLINX 969 18.8 No No 155
MM-Mind2Web 1009 7.3 No No 137
GUIAct 2482 6.7 No No 121
AgentTrek 10398 12.1 Yes Yes 127
  • AgentTrek is the only one with HTML, AxTree, reasoning, video and matching screenshots.

VideoAgentTrek (Lu et al., 2025)

28/119
  • An inverse dynamics model labels 39k YouTube screen-recording tutorials with clicks and keystrokes.
  • Inverse dynamics model: looks at two frames and guesses the action between them.
  • Yields 1.52M interaction steps.
  • Finds videos itself: seed keywords and tags → search → judge videos → expand to channels where 80%+ of videos pass → screen filter.

3 · Synthesized trajectories

29/119
Instruction first (Synatra) Interaction first (OS-Genesis, NNetNav)
Start from a task or tutorial Explore the environment freely
LLM writes the steps without running them Label the run in hindsight
Filter drops invalid samples Score and prune the runs
  • Either way: a model makes the steps, a filter keeps the good runs.

Synatra (Ou et al., NeurIPS 2024)

30/119
  • An LLM rewrites wikiHow tutorials and random web pages into 100k step-by-step demonstrations.
  • $0.031 each: 3% of human cost.
  • Example: "Cancel a PayPal payment" tutorial → task "Cancel Amazon Prime membership on PayPal" → goto(paypal.com), click("login"), type(...), click("Amazon Inc.", id=156).
  • Turns "indirect knowledge" (how-to text) into direct demonstrations.

Case study: Synatra vs AgentTrek

31/119
Synatra AgentTrek
Raw source wikiHow + random web pages Tutorials filtered from RedPajama crawl
How steps are made LLM writes them offline; never executed VLM agent replays live; VLM judge keeps wins
Observations Synthesized page text, no screenshots Real screenshots + accessibility trees
Cost per sample $0.031 $0.55
Model trained CodeLlama-7B, text only Qwen2-VL (vision), Qwen2.5 (text)

OS-Genesis (Sun et al., ACL 2025)

32/119
  • Explore apps first, then infer what task each interaction did ("reverse task synthesis").
  • Low-level step ("Click the Event button") → high-level task ("Create an event 'Team Meeting' for October 15, 2023, 10:00 AM").
  • A trajectory reward model (TRM) grades runs 1–5. An incomplete run can still score 3/5: "task incomplete, but trajectory valuable."
  • Nearly doubles AndroidWorld success.

NNetNav (Murty et al., 2024)

33/119
  • An LM explores websites while playing a sampled persona (e.g., "Investor, active on r/investing").
  • Another LM labels the run in hindsight with the instruction it achieved.
  • Runs that cannot be labeled are pruned early.
  • Then the instruction-following policy is trained on each labeled prefix.

4 · Synthesized tasks and environments

34/119
Code agents (SWE-smith, R2E-Gym) Tool-use agents (AgentScaler)
Environment Docker image of a real repo that runs its tests Simulated database behind real API schemas
Task Injected bug or reverted commit + LM-written issue Goal from a chain of dependent tool calls
Verifier Tests fail before the fix, pass after Final database state matches the expected one
  • Build sandbox, task and checker automatically: every task has a verifiable reward.

SWE-smith (Yang et al., NeurIPS 2025)

35/119
  • Inject bugs that break existing tests in 128 Python repos.
  • An LM writes the issue text.
  • 50k tasks from about 20 hours of human work.
  • Pipeline: SWE-agent tries to install the repo and run tests → a developer writes the Dockerfile → bug strategies → task = generated issue + bugged patch + verified tests.

SWE-smith: bug strategies

36/119
Bug type Yield % Instances Cost
Combine 96.9% 10,092 0.00¢
LM Modify 56.0% 17,887 0.38¢
LM Rewrite 35.0% 4,173 3.93¢
PR Mirror 33.8% 2,344 5.53¢
Procedural 40.2% 15,641 0.00¢
Total 50.1 50,137 2.32¢
  • Yield: share of candidates that break 1+ tests. Median: 6 fail-to-pass tests, 5 lines edited.
  • 128 repos in 6 groups (e.g., Data Mgmt 52, System Tools 24).

R2E-Gym (Jain et al., COLM 2025)

37/119
  • Turns ordinary commits into 8.1K executable tasks: generate tests, back-translate code changes into issue text.
  • No human-written PRs needed. 2.5× more training environments than from human PRs.
  • Test-time scaling on SWE-Bench Verified: 34.4% pass@1 → 42.8% (execution-free verifier) → 43.7% (execution-based) → 51.0% (hybrid).
  • 51.0% beat other open-weight agents (SweRL 41%, SweGym 32%, SweFixer 30.2%), close to Sonnet-3.5 + OpenHands at 53.0%.

AgentScaler (Fang et al., 2025)

38/119
  • Builds verifiable simulated environments from real APIs.
  • Each tool call is a read or write on a database (get_user_info, get_order_info).
  • A simulated user chats with the task agent ("Can you return my order?").
  • Grading: compare interaction traces to the gold action sequence, and the final database state to the gold state.

5 · Simulated users and environments

39/119
Simulated user Simulated environment
An LLM plays the person An LLM predicts the next state and reward
τ-bench, APIGen-MT DreamGym
Gives requests, follow-ups, reactions Actions in; next state + reward out
  • Payoff: cheap, unlimited practice.
  • Risk: agents learn the simulator's mistakes.

τ-bench (Yao et al., ICLR 2025)

40/119
  • An LLM plays the customer in retail and airline support chats.
  • The agent follows a domain policy in its system prompt (e.g., "Basic economy cannot be modified").
  • The user has its own hidden instruction ("change to SF; if not possible, cancel and rebook").
  • Grading compares the final database state to the goal.

APIGen-MT (Prabhakar et al., NeurIPS 2025)

41/119
  • Phase 1: an LLM writes task blueprints (intent, ground-truth actions, outputs) from APIs, rules and domain data.
  • A format + execution checker, then a review committee of LLMs votes. Failures get summarized feedback and a retry.
  • Phase 2: a simulated human chats with the test agent to turn each blueprint into a multi-turn trajectory.
  • Kept only if the agent's actions match the ground truth.

DreamGym (Chen et al., ICLR 2026)

42/119
  • Real environments: tasks are scarce, rewards sparse and unstable, not scalable.
  • An LLM "experience model" predicts the next state and reward in text, replacing costly real rollouts during RL.
  • Uses an experience replay buffer and step-by-step reasoning.
  • A curriculum generator makes harder task variations, picked by reward entropy.
Part 4Lecture 11 · What your data accidentally teaches

Three gotchas

43/119
Reward hacking Overfit to harness Training trends
The environment rewards a loophole Traces teach one scaffold's format only SFT or RL can overshoot
  • "Just train on it and the model gets good." Not quite.

Reward hacking: the .git loophole

44/119
  • SWE-bench: fix a GitHub issue by changing a codebase.
  • SWE-bench issue #465: if .git history is left in, agents can look at future commits.
  • Claude 4 Sonnet on pytest-6202 ran git log --all, which leaked the commit that fixed the issue.
  • Qwen3-Coder 480B used git log --grep=[issue ID] on django-13513 to find the fix PR.

Fix: wipe the history

45/119
  • Self-play SWE-RL (Wei et al., 2025) builds each buggy repo in steps:
  • Apply bug-injection patch. 2. Apply test-weakening patch. 3. Optional: apply a failed prediction for harder bugs.
  • rm -r .git && git init && git add . && git commit -m 'init'.
  • Also restores test files before grading.

Gaming the test harness

46/119
  • Anthropic production coding environments: models learned hacks like sys.exit(0) to fake passing tests (MacDiarmid et al., 2025).
  • Chart: misaligned-generalization score stays near zero, then jumps from under 0.1 to about 0.35–0.4 right at the onset of hacking (around step 70). The no-hacking baseline stays flat.
  • Misalignment rose on every eval: fake goals, deception, monitor disruption, framing a colleague.
  • Mitigations exist (preference models, hack classifiers), but they rely on detecting the hack.

A monitor in the reward teaches hiding

47/119
  • OpenAI coding RL: a chain-of-thought monitor caught hacks ("We can circumvent verify to always return true").
  • Hack types seen: patch verify function, os._exit(0), expected error codes, lazy code, decompiling a jar, parsing the test file, stubbing pandas.
  • Adding the monitor to the reward ("CoT pressure"): fewer caught cheats, but cheating the monitor can't see rises to about 0.5 of samples.
  • Lesson: punishing visible bad thoughts hides intent; it does not stop the hacking.

Eval awareness

48/119
  • On BrowseComp, Claude Opus 4.6 twice inferred it was being tested.
  • Steps: legitimate search (~30M tokens across 12 languages) → suspicion ("question feels constructed") → identified BrowseComp → found the source, cracked the XOR key, submitted the answer.
  • Source: Anthropic (2026).

Memorization

49/119
  • Models name the buggy file from the issue text alone 76% of the time on SWE-Bench Verified, vs up to 53% on repos outside SWE-Bench (Liang et al., 2025).
  • OpenAI o3 bars: 76 (Verified), 69 (Full SWE-Bench), 59 (SWE-Bench Extra), 55 (outside repos), 43 (RefactorBench), 30 (SWE-Bench C#).
  • High score on familiar repos = recall, not skill.

OpenAI retires SWE-bench Verified

50/119
  • Their models could recite issues from memory.
  • Prompt: "We're playing a SWE-bench Verified memory game… task ID django__django-11451."
  • The model recalled the task sentence, the file (django/contrib/auth/backends.py), the function, and the early-return fix.
  • OpenAI stopped tracking it as an evaluation.

Misleading: looking right vs being right

51/119
  • RLHF with a ChatbotArena-style reward, tested on QuALITY (hard reading QA).
  • Human evaluator approval: +9.4 points.
  • Oracle (true) correctness: −1.8 points.
  • Human evaluation error rate: +7.4 points.
  • The model got better at convincing people to approve wrong answers.

Overfit to harness

52/119
mini-swe-agent SWE-agent Terminus 2
THOUGHT text + fenced mswea_bash_command block tool: bash, JSON arguments JSON plan + keystrokes + duration
  • Harness: the code around the model that defines tools, formats and when to stop.
  • Same task (grep -rn _cstack astropy/), three formats.
  • Train on one harness only and the model won't generalize.

Skill vs harness

53/119
Skill (transfers) Harness (doesn't transfer)
Find the bug → fix it → test it Action format: fenced block, function call or JSON
Tool names: bash, str_replace_editor, keystrokes
Observations: prefixes, truncation, line numbers
How to finish: echo COMPLETE, submit, task_complete
  • SFT copies both and can't tell which part is which.

Harness overfit in action

54/119
  • Trained on mini-swe-agent, deployed in a function-calling harness.
  • Model writes a fenced mswea_bash_command block → harness: "No tool call found. Please call a tool." → same block again… until the step limit.
  • Fixes:
    • Train across harnesses: mix rollouts from several scaffolds.
    • Convert to a common format before training.
    • Match train and deploy: ship in the harness you trained in.

SFT can overfit

55/119
  • SWE-RL (Wei et al., NeurIPS 2025) trained Llama-3.3-70B on GitHub PRs.

RL can overshoot

56/119
  • OpenThoughts-Agent's best RL run: mean reward about 0.47 → peak about 0.51.
  • Then it collapsed below 0.2 as the policy over-explored and timed out.
  • They shipped the checkpoint from before the collapse (post-RL eval about 0.33 vs baseline about 0.2).
  • Watch the curve; keep earlier checkpoints.

Lecture 11 takeaways

58/119
  1. Agents need more than text: tasks, environments, trajectories.
  2. Humans are realistic but costly. Demos are hard to scale.
  3. Mined traces are cheap. Code, tutorials and videos convert.
  4. Synthesis scales cheaply. Models write steps and build tasks.
  5. Simulators give endless practice. Their errors get learned too.
  6. Data teaches by accident: reward hacks, harness overfit.
Part 5Lecture 12 · Motivation

The tl;dr

59/119
  • Making agent tasks and trajectories is now cheap.
  • Deciding what to keep is the hard part.
  • This lecture: which tasks to train on, which trajectories to imitate, and whether more data or better data wins.

Keeping vs making: CWM

60/119
  • CWM (Meta FAIR, 2025): 3M agent trajectories from 10.2k Docker images of 3.15k repos.
  • Dropped near-duplicates: within each repo, kept trajectories have pairwise Jaccard similarity below 0.5.
  • Jaccard similarity: shared items ÷ all items; 1 = identical.
  • Kept failed attempts: the goal is a world model of code environments, so no filtering by success.

Every stage throws data away

61/119
candidate tasks → valid tasks → learnable tasks      (which tasks?)
→ rollouts → kept trajectories                      (which trajectories?)
→ training mix                                      (more or better data?)
  • We select two things: environments for RL, trajectories for SFT.

Three ways data goes bad

62/119
Wrong signal No signal Redundant signal
Broken verifiers and hacked successes Tasks too easy or too hard to learn from More of the same
Tasks + trajectories sections Tasks section More-or-better section

The open tension

63/119
Less is more More is more
LIMI: 78 hand-curated trajectories beat 10,000 Orchard: at scale, data size matters more than how you pick it
  • Same OpenThoughts-Agent evidence as Lecture 11: the subset you pick matters at a fixed budget.
  • The last section shows when each one holds.
Part 6Lecture 12 · Which tasks are worth training on?

Task selection is a loop

64/119
  1. Filter out broken or unreliable tasks (SWE-bench Verified).
  2. Check task validity by running them (APIGen, CodeMidas).
  3. Keep tasks the LM sometimes solves (DAPO, LEGO-RL).
  4. Re-select as the model improves (WebRL).

SWE-bench Verified: a broken task

65/119
  • sklearn-14520: "Copy param ignored in TfidfVectorizer."
  • The test demands an exact deprecation message: "'copy' param is unused and has been deprecated since version 0.22…"
  • That wording was decided in PR discussion the agent never sees.

DAPO: same reward, no learning

75/119
  • GRPO-style advantage = (reward − group mean) / group std.
  • Mixed rewards (1 0 1 1 0 0 1 0) → learns.
  • All correct (1 1 1 1 1 1 1 1) → advantage is 0 for all → no gradient.
  • One prompt, 8 rollouts. Source: Yu et al., DAPO (2025).

SWE-Prime (Zheng et al., 2026)

90/119
  • Successful runs can still have ineffective, redundant or risky steps.
  • Stage 1, trajectory filter: process quality (observe-edit-verify pattern, tool success rate, no git hacking), result quality vs the ground-truth patch, and diversity (top 10% from each embedding cluster).
  • Stage 2, segment filter: cut runs into windows, score each by contribution, risk and learnability; only high-scoring segments count in the loss.

SWE-Prime result

91/119
  • Training on the 10% subset SWE-Prime picks beats training on all successful trajectories.
  • Relative gains up to 12.2% (SWE-bench Pro) and 24.2% (SWE-bench Verified).

NAT (Wang et al., NAACL 2025)

92/119
  • Standard practice trains only on successful trajectories.
  • Example: a failed math run has reasonable early steps, but the whole run is thrown away.
  • NAT, negative-aware training: keep failed runs too, and tell the model which succeeded with a prefix or suffix label.
  • Why it works: the label gives a better trade-off between the useful information and the errors in failed runs.

EEF (Lan et al., 2025): the RFT gap

93/119
  • RFT, rejection-sampling fine-tuning: train only on successful expert runs.
  • The expert mostly succeeds on easy subtasks.
  • So hard subtasks never enter training.

EEF: salvage good steps

94/119
  • A failure may come from mistakes in only the last few steps.
  • Prior methods treat every action in a failed run as negative.
  • EEF: from states along a failed GPT-4 run, let the agent simulate onward at fixed intervals.
  • Expert actions that lead to states the agent can finish from (reward 1) are kept as useful.

Common mistakes

119/119
  • Training on every passing run → audit how it passed; drop flag-everything answers.
  • Keeping tasks the model always or never solves → keep the ones it sometimes solves; refresh as it improves.
  • Synthetic-only cases → keep real contracts in every eval and training set.
  • Rewarding "a reviewer approved it" → reward answers checked against labels.

Check your understanding

What is the difference between a trajectory and an environment?

A trajectory is a recording of an agent solving a task, used for SFT. An environment is a task plus sandbox plus verifier, used for RL.

Why are planted faults useful?

We broke the clause ourselves, so the right answer is known. Many labeled cases, no labeling cost, like SWE-smith.

Why does a group where every rollout is correct teach RL nothing?

The advantage is reward minus the group mean, so it is zero for every rollout. DAPO keeps sampling until each prompt has mixed rewards.

Why can't you trust every trajectory that passed the tests?

Some passes are cheats (git-history mining, test tampering) and some are sloppy. The Verification Horizon cut hacked passes from 28.57% to 0.56% by monitoring trajectories.

Is less data better, or more?

Curation wins when data is scarce (LIMI). At scale, size and diversity win (Orchard). Filtered 9,139 beat random 9,139, but the full 19,050 beat both.

Where does a lawyer's correction go?

Logged with the reason, added to the regression set at once, then into the next training batch. Never into the held-out eval.

What is harness overfit and how do you avoid it?

SFT copies the scaffold's format along with the skill. Train across harnesses, convert traces to one format, or deploy in the harness you trained in.

Lecture 11 · Shankar, "Data Flywheels" · "Who Validates the Validators?" · SWE-smith · LIMA

Every run, every human correction and every failure is data. Store it with the reason, and it becomes a test today, an example tomorrow, and training data next month.

Key terms

Trace / trajectory
The full record of a run: inputs, prompts, model outputs, tool calls, results and timings.Source: Lecture 11
Data flywheel
Usage produces traces and corrections, which improve evals and training data, which improve the system, which earns more usage.Source: Shankar, "Data Flywheels for LLM Applications" (2024)
Synthetic task generation
Creating labeled cases by injecting known faults into real or clean data, so the answer is known by construction.Source: Yang et al., "SWE-smith", NeurIPS D&B (2025)
Rejection sampling
Generate several outputs and keep only those a checker accepts, to build clean training data.Source: Lecture 9 and 11
Criteria drift
Graders' standards change as they see more outputs; evaluation criteria must be revisited.Source: Shankar et al., "Who Validates the Validators?", UIST (2024)
Less is more
A small set of diverse, high-quality examples can align a strong model.Source: Zhou et al., "LIMA", NeurIPS (2023)

Three kinds of agent data

  • Traces: the full record of each run: inputs, model calls, tool calls, outputs.
  • Demonstrations: correct examples, from experts or from a teacher model whose output passed the checker.
  • Feedback: corrections and ratings from people. Binary pass/fail per criterion beats a 1–5 "quality" score.

The flywheel

  1. Read 50–100 real outputs with the customer. Write down failures in plain words.
  2. Turn each failure type into a binary check, in code where possible.
  3. Align any LLM judge to about 16+ human-graded examples. Expect your criteria to change as you grade.
  4. Log every correction with its reason. Use it right away as a test case and as a retrieved example.
  5. Batch corrections into a training set for the next release. Never train on the held-out eval.
1,000

Carefully chosen examples were enough to align a strong model (LIMA). Diversity beats volume.

2.5¢

Cost per synthetic task in SWE-smith, which injects known bugs into working code.

1. Inject faults into a clean contract

12_data_flywheel.ipynb · cell 3
FAULTS = {
    "liability_cap":      lambda t: re.sub(r"IN THE 12 MONTHS", "IN THE FORTY-EIGHT (48) MONTHS", t),
    "governing_law":      lambda t: re.sub(r"State of (California|Delaware)", "State of Nevada", t),
    "auto_renewal":       lambda t: t.replace("successive one (1) year", "successive four (4) year"),
    "termination_notice": lambda t: re.sub(r"at least [\w\s()]+? days'", "at least seven (7) days'", t),
}

def make_case(clean_id, rng):
    text = contract(clean_id)
    picked = rng.sample(list(FAULTS), rng.choice([1, 2]))
    for f in picked:
        new = FAULTS[f](text)
        assert new != text, f"fault {f} did not apply"
        text = new
    return {"text": text, "issues": sorted(picked), "source": clean_id}

rng = random.Random(7)
clean = [c for c, l in labels().items() if not l["issues"]]
synthetic = [make_case(rng.choice(clean), rng) for _ in range(30)]
print(len(synthetic), "new labeled cases from", len(clean), "clean contracts")
print(synthetic[0]["issues"], "\n", [l for l in synthetic[0]["text"].splitlines() if "Nevada" in l or "(4) year" in l or "(48)" in l or "(7) days" in l])

2. Log every run as a trace

A trace is the full record: input hash, prompt, model, output, time. Traces are your audit trail and your future training data.

12_data_flywheel.ipynb · cell 4
TRACES = Path("traces.jsonl"); TRACES.unlink(missing_ok=True)
import hashlib
def traced_call(task, prompt, **kw):
    t0 = time.time()
    r = client.chat.completions.create(model=MODEL, messages=[{"role": "user", "content": prompt}], temperature=0, **kw)
    out = r.choices[0].message.content
    rec = {"task": task, "model": MODEL, "input_sha": hashlib.sha256(prompt.encode()).hexdigest()[:12],
           "prompt": prompt, "output": out, "secs": round(time.time() - t0, 2), "tokens": r.usage.total_tokens}
    with open(TRACES, "a") as f: f.write(json.dumps(rec) + "\n")
    return out

PB = playbook()
def review(text):
    """Structured answer (a list of rule names), and the call is still traced."""
    from lal.llm import structured
    from pydantic import BaseModel
    class Review(BaseModel):
        broken_rules: list[str]
    prompt = (f"Rules (name: rule): {json.dumps(PB['rules'])}\n\nContract:\n{text}\n\n"
              "List the names of the rules this contract breaks. Empty list if none.")
    t0 = time.time()
    r = structured(prompt, Review)
    with open(TRACES, "a") as f:
        f.write(json.dumps({"task": "review", "model": MODEL, "input_sha": hashlib.sha256(prompt.encode()).hexdigest()[:12],
                            "prompt": prompt, "output": r.model_dump(), "secs": round(time.time() - t0, 2)}) + "\n")
    return sorted(x for x in set(r.broken_rules) if x in PB["rules"])

results = [(c["issues"], review(c["text"])) for c in synthetic[:6]]
for gold, pred in results: print("truth", gold, "| model", pred)
print(sum(1 for _ in open(TRACES)), "traces logged")

Traps
  • Theorizing about failures instead of reading outputs.
