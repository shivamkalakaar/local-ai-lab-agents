Module 12

Data and flywheels

Open in Colab
9 min readSlides first, then the deeper material

Turn every run and every lawyer's fix into data. Plant known faults, log traces, make corrections into tests now and training data later.

Based on CS329Z Lectures 11 and 12 · What Data Do Agents Need? · Data Selection & Quality · original slides (PDF)

Learning objective

1/12
  • Build labeled contract cases cheaply, log every run, and turn corrections into tests and checked training data.

Why data matters

2/12
  • Same base model, different post-training data: big difference in results.
  • Making tasks and trajectories is now cheap. Deciding what to keep is the hard part.
  • A firm rarely has hundreds of labeled contracts ready. We have to make them.

Two types of agent data

3/12
Trajectory Environment
A recording of an agent solving a task A task + sandbox + a way to check success
Train with SFT: the model imitates it Train with RL: the model practices
Ours: a trace of one review call Ours: a contract with known issues + the grader

Where agent data comes from

4/12
  • Human demos: realistic but costly.
  • Mined from the web: code history, tutorials, videos.
  • Synthesized trajectories: a model writes or runs the steps; a filter keeps good runs.
  • Synthesized tasks: inject a known fault, so the checker knows the answer.
  • Simulated users or environments: endless practice, but errors get learned too.

Synthesized tasks: SWE-smith

5/12
  • SWE-smith: inject bugs that break existing tests in 128 Python repos.
  • An LM writes the issue text. 50k tasks from about 20 hours of human work.
  • Same idea for us: take a clean contract, break one clause in code.
  • The right answer is known by construction. No lawyer needed to label it.

Planting faults in code

6/12
FAULTS = {
    "liability_cap":      lambda t: re.sub(r"IN THE 12 MONTHS", "IN THE FORTY-EIGHT (48) MONTHS", t),
    "governing_law":      lambda t: re.sub(r"State of (California|Delaware)", "State of Nevada", t),
    "auto_renewal":       lambda t: t.replace("successive one (1) year", "successive four (4) year"),
    "termination_notice": lambda t: re.sub(r"at least [\w\s()]+? days'", "at least seven (7) days'", t),
}
  • Line 1: one entry per playbook rule.
  • Line 2: 12-month cap → 48 months (rule: at most 12).
  • Line 3: California or Delaware → Nevada.
  • Line 4: one-year renewal → four years (rule: at most 1).
  • Line 5: any notice period → seven days (rule: at least 30).

Clean vs planted

7/12
Clean (msa_03) Planted case
"...in the 12 months preceding the claim" "...in the forty-eight (48) months preceding the claim"
issues: none issues: liability_cap (known)
  • The notebook builds 30 cases from the 6 clean contracts, 1 or 2 faults each.

The flywheel

8/12
use → traces + corrections → tests now, training later → better system → more use
  • Trace: the full record of one run: input hash, prompt, model, output, time.
  • Regression set: past mistakes you rerun after every change.
  • Each lawyer's fix is free expert labeling. Save it with the reason.

Rejection sampling for training data

9/12
  • Let the model try each case (up to 2 tries).
  • Keep only answers that exactly match the known issues. Drop the rest.
  • Save as chat-format JSONL (sft_train.jsonl) that TRL or Unsloth can fine-tune on.
  • Never put held-out eval cases in training.

What data teaches by accident

10/12
  • Reward hacking: models faked passing tests with sys.exit(0).
  • Trained on human approval: the model learned to look right, not be right.
  • Overfit to harness: trained in one harness, it keeps that harness's habits.
  • Best model ≠ best teacher.

How this applies to us

11/12
  • Traces and corrections live on the firm's own disk: audit trail and future training set.
  • Planted faults give labeled cases without sending contracts anywhere.
  • Fine-tuning on checked data can run on the same local machine later.

Common mistakes

12/12
  • Guessing why it fails → read 50–100 real outputs with the customer.
  • Synthetic-only cases → keep real contracts in every eval and training set.
  • Rewarding "a reviewer approved it" → reward answers checked against labels.
  • Reusing stored examples unfiltered → one bad example poisons later runs.

Check your understanding

Where does a lawyer's correction go?

Logged with the reason, added to the regression set at once, then into the next training batch. Never into the held-out eval.

Why are planted faults useful?

We broke the clause ourselves, so the right answer is known. Many labeled cases, no labeling cost.

What is rejection sampling?

Let the model try, keep only answers the checker accepts. What is left is clean training data.

Go deeper

Key terms, papers, evidence, the full notebook code and worked solutions.

Lecture 11 · Shankar, "Data Flywheels" · "Who Validates the Validators?" · SWE-smith · LIMA

Every run, every human correction and every failure is data. Store it with the reason, and it becomes a test today, an example tomorrow, and training data next month.

Key terms

Trace / trajectory
The full record of a run: inputs, prompts, model outputs, tool calls, results and timings.Source: Lecture 11
Data flywheel
Usage produces traces and corrections, which improve evals and training data, which improve the system, which earns more usage.Source: Shankar, "Data Flywheels for LLM Applications" (2024)
Synthetic task generation
Creating labeled cases by injecting known faults into real or clean data, so the answer is known by construction.Source: Yang et al., "SWE-smith", NeurIPS D&B (2025)
Rejection sampling
Generate several outputs and keep only those a checker accepts, to build clean training data.Source: Lecture 9 and 11
Criteria drift
Graders' standards change as they see more outputs; evaluation criteria must be revisited.Source: Shankar et al., "Who Validates the Validators?", UIST (2024)
Less is more
A small set of diverse, high-quality examples can align a strong model.Source: Zhou et al., "LIMA", NeurIPS (2023)

Three kinds of agent data

  • Traces: the full record of each run: inputs, model calls, tool calls, outputs.
  • Demonstrations: correct examples, from experts or from a teacher model whose output passed the checker.
  • Feedback: corrections and ratings from people. Binary pass/fail per criterion beats a 1–5 "quality" score.

The flywheel

  1. Read 50–100 real outputs with the customer. Write down failures in plain words.
  2. Turn each failure type into a binary check, in code where possible.
  3. Align any LLM judge to about 16+ human-graded examples. Expect your criteria to change as you grade.
  4. Log every correction with its reason. Use it right away as a test case and as a retrieved example.
  5. Batch corrections into a training set for the next release. Never train on the held-out eval.
1,000

Carefully chosen examples were enough to align a strong model (LIMA). Diversity beats volume.

2.5¢

Cost per synthetic task in SWE-smith, which injects known bugs into working code.

The code, cell by cell

12_data_flywheel.ipynb · cell 2
import json, random, re, time
from pathlib import Path
# lal.llm = the OpenAI client pointed at the local Ollama server, http://localhost:11434/v1 (see notebook 00)
from lal.llm import client
from lal.data import contract, labels, playbook
from lal.checks import check

1. Inject faults into a clean contract

12_data_flywheel.ipynb · cell 3
FAULTS = {
    "liability_cap":      lambda t: re.sub(r"IN THE 12 MONTHS", "IN THE FORTY-EIGHT (48) MONTHS", t),
    "governing_law":      lambda t: re.sub(r"State of (California|Delaware)", "State of Nevada", t),
    "auto_renewal":       lambda t: t.replace("successive one (1) year", "successive four (4) year"),
    "termination_notice": lambda t: re.sub(r"at least [\w\s()]+? days'", "at least seven (7) days'", t),
}

def make_case(clean_id, rng):
    text = contract(clean_id)
    picked = rng.sample(list(FAULTS), rng.choice([1, 2]))
    for f in picked:
        new = FAULTS[f](text)
        assert new != text, f"fault {f} did not apply"
        text = new
    return {"text": text, "issues": sorted(picked), "source": clean_id}

rng = random.Random(7)
clean = [c for c, l in labels().items() if not l["issues"]]
synthetic = [make_case(rng.choice(clean), rng) for _ in range(30)]
print(len(synthetic), "new labeled cases from", len(clean), "clean contracts")
print(synthetic[0]["issues"], "\n", [l for l in synthetic[0]["text"].splitlines() if "Nevada" in l or "(4) year" in l or "(48)" in l or "(7) days" in l])

2. Log every run as a trace

A trace is the full record: input hash, prompt, model, output, time. Traces are your audit trail and your future training data.

12_data_flywheel.ipynb · cell 4
TRACES = Path("traces.jsonl"); TRACES.unlink(missing_ok=True)
import hashlib
def traced_call(task, prompt, **kw):
    t0 = time.time()
    r = client.chat.completions.create(model=MODEL, messages=[{"role": "user", "content": prompt}], temperature=0, **kw)
    out = r.choices[0].message.content
    rec = {"task": task, "model": MODEL, "input_sha": hashlib.sha256(prompt.encode()).hexdigest()[:12],
           "prompt": prompt, "output": out, "secs": round(time.time() - t0, 2), "tokens": r.usage.total_tokens}
    with open(TRACES, "a") as f: f.write(json.dumps(rec) + "\n")
    return out

PB = playbook()
def review(text):
    """Structured answer (a list of rule names), and the call is still traced."""
    from lal.llm import structured
    from pydantic import BaseModel
    class Review(BaseModel):
        broken_rules: list[str]
    prompt = (f"Rules (name: rule): {json.dumps(PB['rules'])}\n\nContract:\n{text}\n\n"
              "List the names of the rules this contract breaks. Empty list if none.")
    t0 = time.time()
    r = structured(prompt, Review)
    with open(TRACES, "a") as f:
        f.write(json.dumps({"task": "review", "model": MODEL, "input_sha": hashlib.sha256(prompt.encode()).hexdigest()[:12],
                            "prompt": prompt, "output": r.model_dump(), "secs": round(time.time() - t0, 2)}) + "\n")
    return sorted(x for x in set(r.broken_rules) if x in PB["rules"])

results = [(c["issues"], review(c["text"])) for c in synthetic[:6]]
for gold, pred in results: print("truth", gold, "| model", pred)
print(sum(1 for _ in open(TRACES)), "traces logged")

3. Corrections become tests immediately

When a reviewer fixes a miss, we store input, wrong output, right output and the reason. It goes into a regression set straight away, and later into a training set (never into the held-out eval).

12_data_flywheel.ipynb · cell 5
REGRESSION = Path("regression.jsonl"); REGRESSION.unlink(missing_ok=True)
misses = [(c, pred) for c, (gold, pred) in zip(synthetic[:6], results) if pred != gold]
for case, pred in misses:
    rec = {"text": case["text"], "model_said": pred, "correct": case["issues"], "reason": "planted fault missed or false flag"}
    with open(REGRESSION, "a") as f: f.write(json.dumps(rec) + "\n")
print(len(misses), "misses saved as regression tests")

4. Build a fine-tuning set by rejection sampling

Keep only outputs that pass the checker. This JSONL file is the standard chat format that TRL or Unsloth fine-tune on.

12_data_flywheel.ipynb · cell 6
sft = []
for c in synthetic[6:16]:
    for _ in range(2):                                          # up to 2 tries per case
        pred = review(c["text"])
        if pred == c["issues"]:                                 # the checker: matches the known answer
            sft.append({"messages": [{"role": "user", "content": f"Review against the playbook:\n{c['text']}"},
                                     {"role": "assistant", "content": ", ".join(pred) or "none"}]})
            break
Path("sft_train.jsonl").write_text("".join(json.dumps(x) + "\n" for x in sft))
print(f"kept {len(sft)} of 10 cases for fine-tuning (only checker-approved outputs)")

# Solution 1: a new fault type (short cure period) plus a playbook rule for it
FAULTS["cure_period"] = lambda t: re.sub(r"uncured \w+(?: \(\d+\))? days", "uncured five (5) days", t)

# Solution 2: one eval that mixes real and synthetic cases, scored per group
real = [{"text": contract(c), "issues": sorted(i["rule"] for i in labels()[c]["issues"])} for c in list(labels())[::3][:6]]
mixed = [("real", c) for c in real] + [("synthetic", c) for c in synthetic[16:22]]
score_by = {"real": [], "synthetic": []}
for group, c in mixed:
    score_by[group].append(review(c["text"]) == c["issues"])
for g, xs in score_by.items():
    print(f"{g:9} exact {sum(xs)}/{len(xs)}")
# If a model only ever sees cases built from your own templates, it can look great on them and still fail on
# real documents. Keep real cases in every eval and in training data.
Traps
  • Theorizing about failures instead of reading outputs.
  • Rewarding "the reviewer approved it". The model learns to look right, not be right.
  • Auto-retrieving stored examples without filtering. A bad example poisons future runs.
