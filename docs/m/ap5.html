Part 1The problem and why it matters

The project at a glance

2/38
  • ARCHON Augmented: Planning and Web-Enhanced Components.
  • Team: Megan Mou, Sherry Xie, Emily Zhang, Andrew Park (CS329A, Winter 2025).
  • Poster title: "Multi-Component ARCHON".
  • Sources: the 11-page report and the poster.
  • Code: github.com/49emily/cs329a-archon.

What Archon is

3/38
  • Archon: a framework that stacks inference-time techniques into a pipeline of model calls.
  • Inference-time technique: a way to spend more compute at answer time (sample more, critique, merge) instead of training.
  • Idea: many LLMs plus many techniques can beat any one of them alone.
  • It picks a good stack for each benchmark by search.

Four gaps they saw

4/38
  • Only seven building blocks; room for more.
  • No web search or tool use.
  • The query category is fixed in advance; no per-query adjustment.
  • Strong results relied on models of about 70B parameters; small open models untested.

Research question

5/38
  • Can more inference-time components improve Archon for both closed-source and open-source models?
  • Their answer, in short:
    • Expander value depends on the benchmark.
    • New blocks let open models rival closed ones.
    • Web search helps instruction following.
    • Reasoning stays hard.
Part 2Background they build on

Archon (Saad-Falcon et al., 2024)

6/38
Block What it does
Generator Writes candidate answers
Fuser Merges candidates into one answer
Critic Notes each candidate's strengths and flaws
Ranker Orders candidates, best first
Verifier Checks the answer is supported
Unit Test Generator Writes tests for a coding answer
Unit Test Evaluator Runs answers against those tests
  • Blocks are stacked in layers.
  • ITAS (inference-time architecture search): searches over stacks and settings.
  • Its own limits section: adding new techniques is "a promising avenue".

Archon's instruction-following stack (poster Figure 1)

7/38
Prompt → Generator (n=10 samples) → Critic → Ranker → Fuser → Output
  • In the Archon paper's all-source version, every block uses Claude 3.5 Sonnet.

Other work they draw on

8/38
Work Idea Use here
Mixture-of-Agents, LLM-Blender Combine many LLMs at answer time Archon's roots; narrower scope
ReAct (Yao et al., 2023) Interleave reasoning and actions Inspired a dedicated planning layer
Toolformer (Schick et al., 2023) Models learn to call tools Inspired the web search block
"LLMs still can't plan" (Valmeekam et al., 2024) Planning is hard even for o1 Why a planner might matter most

The two benchmarks

9/38
Benchmark What it tests How scored
Humanity's Last Exam (HLE) Frontier academic knowledge and reasoning; 2,700 questions, 100+ subjects Accuracy
AlpacaEval Following real-world instructions Win rate vs. a strong reference model, judged automatically
  • They used 500 HLE questions (compute limit). HLE is far from solved by frontier models.
  • LC (length-controlled) win rate: corrects the judge's bias toward longer answers.
Part 3The method, step by step

Three new blocks (Figure 1)

10/38
Block Where What it does
Planner First Rephrases the request, writes a step-by-step plan; the plan is prepended to later inputs
Web Search Tool Call After the Planner, before the Generator Writes q queries from the plan; top 10 Google results per query become context
Expander After each Generator Adds context, detail or clarification so Critics and Rankers can judge
  • Web search block was inspired by the course's Homework 2.

The full pipeline (poster Figure 2, ablation 3)

11/38
Planner → Web Search Tool Call (queries=5) → Generator (n=10) → Expander → Critic → Ranker → Fuser
  • The poster gives 5 queries; the report only says q.

The Planner prompt (A.1.1)

12/38
  • System: "You are an expert at planning and reasoning given a user query."
  • Step 1: "Summarize what the user is asking in a clearer way."
  • Step 2: "Provide a step-by-step reasoning process on what you need to do in order to fully answer the user query."
  • Their hypothesis: the planner would matter most, since reasoning is crucial yet hard.

The Expander prompt (A.1.2)

13/38
  • "Only add information that is directly relevant to the original response."
  • "Maintain factual accuracy and consistency with the original."
  • "Focus on adding valuable context that enhances understanding."
  • "Keep additions clear and well-structured."
  • "Do not contradict or modify the original content."

The search prompts (A.2)

14/38
  • Query writing: given the query and the step-by-step analysis, "output {num_searches} search queries", comma-separated, nothing else.
  • Generation: "Use these search results to improve your answer to the user's query".

Blocks they considered and dropped

15/38
  • Rewriter, summarizer, debugger.
  • Too close to existing blocks (especially the verifier), or too costly for a small gain.

The ablations

16/38
    1. Planner + base Archon.
    1. Planner + Expander + base Archon.
    1. Planner + Tool Call + Expander + base Archon.
  • Each compared with base Archon.
  • Two questions: which blocks help most; how do they change open vs. closed models?

Reading the HLE table

20/38
  • Best: Planner + Expander, closed, 4.2%: 4 more right answers than base Archon.
  • Open version of the same: 3.8%.
  • Search lowered both: back to 3.3% and down to 2.9%.

Caveat: is "open rivals closed" fair?

23/38

  • So it isn't an open-model result.
  • The cleaner evidence: Planner + ARCHON lifted the mixed setup from 57.01% to 67.06%.

Part 6Analysis and discussion

What they conclude (Section 6)

24/38
  • Planner: consistently helps structure answers.
  • Expander: limited on AlpacaEval because length control rewards short answers; helped on HLE via longer reasoning.
  • Tool Call: pushed AlpacaEval above 70%, beyond every original Archon setup.
  • Planner and Tool Call let open models match closed ones on instruction following and retrieval.
  • Block value depends on the benchmark: tailor the stack to the task.

Why search split the two benchmarks

25/38
AlpacaEval HLE
Real-world requests; outside facts help Deep reasoning, not lookup
Search grounded answers, made them more relevant Pages off-topic or cluttered
Score went up Score went down
  • Still, OpenAI's Deep Research reached 26.6% on HLE, so iterative plan-and-search loops may help.

Reasoning remains the bottleneck

26/38
  • Expander gains on HLE were too small to overcome reasoning limits.
  • Adding search did not help hill-climb HLE.
  • Suggested next steps: hierarchical planning, multi-step verification, process reward models.
Part 7Limitations and future work

Limitations

27/38
  • Stated: reasoning still hard; search noise on HLE.
  • Our notes:
    • One run per setup; HLE gaps are 2–4 questions.
    • Configs change more than one block at a time (see appendix diagrams).
    • "Mixed" with search is mostly GPT-4o.
    • No cost or call counts reported.

Future work they list

28/38
  • Query-adaptive planner: build a whole Archon stack per prompt.
  • More tool calls: outside APIs and special databases.
  • Early stopping: fewer calls for the same quality.
  • Model size: can these blocks make up for smaller models (e.g., 7B)?
  • Stronger reasoning methods, such as process reward models.

Our small web

30/38
  • 8 made-up towns, each with founding year, population, river, bridge and bridge year.
  • 3 decoy pages: "New ..." towns with different numbers.
  • 5 clutter pages: travel blogs with filler.
  • 6 questions; most need two pages, some need arithmetic.
  • No model can know these facts, so the value of search is clear.

BM25 scoring, in one line

31/38
  • score = Σ_words IDF(w) · tf·(k1+1) / (tf + k1·(1 − b + b·len/avglen)).
  • IDF: rare words weigh more.
  • tf: how often the word is on the page.
  • k1 = 1.5: caps how much repeats count.
  • b = 0.75: penalty for long pages.

The pipeline

32/38
question → Planner (plan + search queries) → Web search (BM25) → 3 Generators (8B, 8B, 3B)
         → Critic + Ranker → Fuser → Verifier → answer          (7 model calls)
  • Planner: up to 3 queries, one per fact needed.
  • BM25: top 3 pages per query.
  • One call critiques and ranks all three candidates.
  • Fuser: one answer from the top two.
  • Verifier says "not supported" → fall back to the top-ranked candidate.

Solutions: three free or cheap ablations

34/38
  • Stop after the ranker: if it matches the full pipeline, the fuser and verifier add cost, not value.
  • Score each generator alone and the best-of-3 oracle: does the ensemble beat its best member?
  • Noisier web: add "Old ..." and "Upper ..." decoys; does search start to hurt, as on HLE?
Part 9How this applies to us

Search the firm's own files

35/38
  • Contract review needs outside facts: past deals, precedent memos, the playbook.
  • Run search over the firm's own documents, on the firm's machine.
  • No pages leave the building; no web noise.

Decoys are the real risk

36/38
Search finds the right page Search finds a look-alike
"Acme Holdings MSA: liability cap 12 months of fees" "Acme Holdings UK MSA: cap 24 months"
Correct check against the playbook Wrong flag, confidently stated
  • Test search with look-alike names before trusting it.

Start with the cheap blocks

37/38
  • A planner is one call and helped weaker models most.
  • Add generators, critics and fusers only if an ablation shows they pay.
  • Count calls per question next to accuracy.

Common mistakes

38/38
  • Assuming search always helps → check what it returns; on HLE it hurt.
  • Adding blocks without testing → the Expander helped in one setup and hurt in another; ablate.
  • Reading tiny gaps as wins → four questions out of 453 is noise.
  • Changing two things at once → swap one block or one model per ablation.
  • Ignoring cost → 7 calls per question; compare with the 2-call setup.

Key terms, papers, evidence, the full notebook code and worked solutions.

CS329A Winter 2025 · Megan Mou, Sherry Xie, Emily Zhang, Andrew Park

Paper · Poster

Problem
Archon stacks inference-time techniques (generate, fuse, critique, rank, verify, unit tests) but has only seven building blocks, no tool use or web search, and its strong results relied on about 70B models.
Method
Three new blocks: a Planner at the front (rephrase + step-by-step plan passed to later blocks), an Expander after each generator (adds context so critics and rankers can judge), and a Web Search Tool Call (queries from the plan, top 10 Google results per query). Ablations on a closed-source configuration (GPT-4o generate/rank, Qwen2-72B critic/fuser) and an open-source ensemble, on a 500-question subset of Humanity's Last Exam (453 scored) and AlpacaEval (length-controlled win rate).
Results
HLE (closed / open): ARCHON 3.3% / 3.3%; + Planner 3.3% / 2.6%; + Planner + Expander 4.2% (19/453) / 3.8% (17/453); + Planner + Tool Call + Expander 3.3% / 2.9%. Zero-shot GPT-4o 3.1%. AlpacaEval LC (closed / mixed): ARCHON 67.73% / 57.01%; + Planner 69.62% / 67.06%; + Planner + Expander 66.01% / 68.30%; + Planner + Tool Call + Expander 73.40% / 73.92%. Web search hurt on HLE because results were off-topic or cluttered.
Lessons
A planner at the front of a pipeline is cheap and helped weaker open models catch up on instruction following. Search helps only if retrieval is precise; noisy pages can make answers worse. The value of each block depends on the task, so ablate each one on your own data. Small differences on a hard benchmark (a few questions out of 453) are noise.
Our rebuild
Questions about made-up towns (so search is required) over 16 local 'web pages', including look-alike decoy pages and clutter, searched with a 15-line BM25. Compares a single call, single call + search (RAG), planner + search + 1 generator, and the full pipeline: planner (plan + queries) -> BM25 search -> 3 generators (8B, 8B, 3B) -> critic + ranker -> fuser -> verifier with fallback. Reports accuracy and calls per question; solutions ablate the fuser/verifier for free, score each generator, and test a noisier web.

The original project

ARCHON Augmented: Planning and Web-Enhanced Components by Megan Mou, Sherry Xie, Emily Zhang and Andrew Park (Stanford CS329A, Winter 2025; the poster is titled Multi-Component ARCHON). Paper · Poster · code: github.com/49emily/cs329a-archon

Background. Archon (Saad-Falcon et al. 2024, Archon: An Architecture Search Framework for Inference-Time Techniques) has seven building blocks: Generator, Fuser, Critic, Ranker, Verifier, Unit Test Generator, Unit Test Evaluator. It searches for the best way to stack them. Its strong results relied on models of about 70B parameters, and it had no tool use.

Method. Three new blocks: - Planner (first): rephrases the request and writes a step-by-step plan that is passed to every later block. - Expander (after each generator): adds context and detail to each candidate so critics and rankers can judge it. - Web Search Tool Call (after the planner): writes q search queries from the plan, calls the Google Search API, and passes the top 10 results per query to the generators.

Setup. A closed-source configuration (GPT-4o generating and ranking, Qwen2-72B as critic and fuser) and an open-source one (an ensemble including Qwen2-72B, WizardLM-2 8x22B, Llama-3 70B, Mixtral 8x22B and others). Benchmarks: a 500-question subset of Humanity's Last Exam (HLE; 453 scored) and AlpacaEval (length-controlled win rate).

Key results (as reported).

Architecture HLE closed HLE open AlpacaEval LC closed AlpacaEval LC open/mixed
ARCHON 3.3% (15/453) 3.3% (15/453) 67.73% 57.01%
Planner + ARCHON 3.3% (15/453) 2.6% (12/453) 69.62% 67.06%
Planner + Expander + ARCHON 4.2% (19/453) 3.8% (17/453) 66.01% 68.30%
Planner + Tool Call + Expander + ARCHON 3.3% (15/453) 2.9% (13/453) 73.40% 73.92%

Zero-shot GPT-4o scored 3.1% on HLE. On AlpacaEval the new blocks, especially the Planner, lifted the open-source setup from more than 10 points behind to slightly ahead of closed-source. On HLE, web search hurt: results were often off-topic or full of page clutter, which confused the models.

Limitations they state. Reasoning stays the bottleneck; the Expander's value depends on the benchmark; the planner is not yet query-adaptive. (Our note: on HLE the differences are a few questions out of 453, so they are within noise.)

1. A small made-up web

Eight towns, each with a founding year, a population, a river and a bridge. Three decoy pages describe "New ..." towns with different numbers, and five pages are pure clutter. All generated with a seed.

ap5_archon_augmented.ipynb · cell 3
rng = random.Random(5)
NAMES = ["Velmora", "Ostrand", "Brenhollow", "Quillmarsh", "Taversk", "Lunegate", "Corrowind", "Ashby Vale"]
RIVERS = ["Senn", "Ilver", "Draw", "Morrow", "Kesh", "Tull", "Avin", "Pellam"]
BRIDGES = ["Kestrel Bridge", "Lantern Bridge", "Old Mill Bridge", "Heron Bridge", "Copper Bridge", "Saint Ide Bridge", "Gull Bridge", "Iron Fox Bridge"]
TOWNS = {}
for n, r, b in zip(NAMES, RIVERS, BRIDGES):
    y = rng.randint(1100, 1800)
    TOWNS[n] = dict(founded=y, pop=rng.randint(3000, 95000), river=r, bridge=b, bridge_year=y + rng.randint(30, 300))

FILLER = ["The weekly market sells cheese, wool and honey.", "Tourists often visit the old clock tower.",
          "The local football club plays in the regional league.", "Summers are mild and winters are wet.",
          "A folk festival takes place every autumn.", "The town hall was renovated recently."]

def town_page(n, t):
    return (f"{n} is a town on the {t['river']} river. It was founded in {t['founded']}. Today it has a population of "
            f"{t['pop']:,}. The {t['bridge']} in {n} was built in {t['bridge_year']}. " + " ".join(rng.sample(FILLER, 3)))

DOCS = [{"title": n, "text": town_page(n, t)} for n, t in TOWNS.items()]
for n in rng.sample(NAMES, 3):                                    # decoys: similar names, different facts
    fake = dict(TOWNS[n], founded=TOWNS[n]["founded"] + 400, pop=TOWNS[n]["pop"] // 3 + 1000)
    DOCS.append({"title": f"New {n}", "text": f"New {n} is a newer settlement, not to be confused with {n}. It was founded in "
                 f"{fake['founded']} and has a population of {fake['pop']:,}. " + " ".join(rng.sample(FILLER, 2))})
for i in range(5):
    DOCS.append({"title": f"Travel blog {i + 1}", "text": " ".join(rng.sample(FILLER, 4)) + f" We loved our trip to {rng.choice(NAMES)}!"})
print(len(DOCS), "pages. Example:\n", DOCS[0]["text"])

Six questions. Most need two pages, and some need arithmetic on top.

A, B, C, D = rng.sample(NAMES, 4)
QS = [
    (f"How many years passed between the founding of {A} and the building of the {TOWNS[B]['bridge']}?",
     abs(TOWNS[B]["bridge_year"] - TOWNS[A]["founded"])),
    (f"What is the combined population of {A} and {C}?", TOWNS[A]["pop"] + TOWNS[C]["pop"]),
    (f"Which town has more people, {B} or {D}?", max((B, D), key=lambda n: TOWNS[n]["pop"])),
    (f"On which river is the town that has the {TOWNS[C]['bridge']}?", TOWNS[C]["river"]),
    (f"How many more people live in {max((C, D), key=lambda n: TOWNS[n]['pop'])} than in {min((C, D), key=lambda n: TOWNS[n]['pop'])}?",
     abs(TOWNS[C]["pop"] - TOWNS[D]["pop"])),
    (f"Which was founded first, {A} or {D}, and by how many years? Answer with the number of years.",
     abs(TOWNS[A]["founded"] - TOWNS[D]["founded"])),
]
for q, a in QS:
    print(a, "←", q)

def answer_of(text):
    m = re.findall(r"ANSWER:\s*(.+)", text or "", re.I)
    return m[-1].strip() if m else ((text or "").strip().splitlines() or [""])[-1]

def is_right(got, gold):
    got = (got or "").replace(",", "")
    if isinstance(gold, int):
        nums = re.findall(r"-?\d+", got)
        return bool(nums) and (int(nums[0]) == gold or int(nums[-1]) == gold)
    pool = NAMES if gold in NAMES else RIVERS            # the FIRST name mentioned is the answer ("Velmora (52,000 vs Ostrand's 30,000)")
    hits = sorted((got.lower().find(n.lower()), n) for n in pool if n.lower() in got.lower())
    return bool(hits) and hits[0][1] == gold

2. The search tool: BM25 in 15 lines

BM25 scores a page by how often it contains the query words, with rare words counting more and long pages counting less (Robertson & Zaragoza 2009). It is what many search engines started from.

ap5_archon_augmented.ipynb · cell 5
def tokens(s):
    return re.findall(r"[a-z0-9]+", s.lower())

class BM25:
    def __init__(self, docs, k1=1.5, b=0.75):
        self.docs, self.k1, self.b = docs, k1, b
        self.tf = [Counter(tokens(d["title"] + " " + d["text"])) for d in docs]
        self.len = [sum(t.values()) for t in self.tf]
        self.avg = sum(self.len) / len(self.len)
        df = Counter(w for t in self.tf for w in t)
        self.idf = {w: math.log(1 + (len(docs) - n + 0.5) / (n + 0.5)) for w, n in df.items()}

    def search(self, query, k=3):
        q = tokens(query)
        def score(i):
            return sum(self.idf.get(w, 0) * self.tf[i][w] * (self.k1 + 1) /
                       (self.tf[i][w] + self.k1 * (1 - self.b + self.b * self.len[i] / self.avg)) for w in q)
        return [self.docs[i] for i in sorted(range(len(self.docs)), key=score, reverse=True)[:k]]

WEB = BM25(DOCS)
print([d["title"] for d in WEB.search(f"{A} founded")])

def as_context(pages):
    return "\n\n".join(f"[{d['title']}] {d['text']}" for d in pages)

3. Two simple baselines

  • Single call, no search: the model has to guess. Expect near 0, which proves the facts are really unknown.
  • Single call + search on the raw question: classic retrieval-augmented generation (RAG).

FMT = "\nEnd with one line: ANSWER: <short answer>"

def single(q):
    return {"answer": answer_of(ask(q + FMT, max_tokens=300)), "calls": 1}

def single_rag(q):
    ctx = as_context(WEB.search(q, k=3))
    return {"answer": answer_of(ask(f"Web results:\n{ctx}\n\nQuestion: {q}\nUse only the web results." + FMT, max_tokens=400)), "calls": 1}

4. The augmented Archon pipeline

question → Planner (plan + search queries) → Web search (BM25) → 3 Generators (8B, 8B, 3B)
         → Critic + Ranker → Fuser → Verifier → answer          (7 model calls)

If the verifier says the fused answer is not supported by the pages, we fall back to the top-ranked candidate.

ap5_archon_augmented.ipynb · cell 7
class PlanOut(BaseModel):
    rephrased: str
    steps: List[str] = Field(max_length=5)
    queries: List[str] = Field(description="1 to 3 short search queries", max_length=3)

class Critique(BaseModel):
    notes: List[str] = Field(description="one short critique per candidate, in order")
    ranking: List[int] = Field(description="candidate numbers, best first")

class Verdict(BaseModel):
    supported: bool
    reason: str

def plan_and_search(q):
    try:
        p = structured(f"Question: {q}\nRephrase the question, write a short plan, and write 1-3 web search queries "
                       "that will find every fact the plan needs.", PlanOut, max_tokens=400)
    except Exception:
        p = PlanOut(rephrased=q, steps=["answer the question"], queries=[q])
    pages, seen = [], set()
    for query in (p.queries or [q])[:3]:
        for d in WEB.search(query, k=3):
            if d["title"] not in seen:
                seen.add(d["title"]); pages.append(d)
    return p, pages[:6]

def generate(q, plan, pages, model, temperature=0.7):
    prompt = (f"Web results:\n{as_context(pages)}\n\nQuestion: {q}\nPlan:\n" + "\n".join(f"- {s}" for s in plan.steps) +
              "\nFollow the plan. Use only the web results. Watch out for pages about similarly named places." + FMT)
    try:
        return ask(prompt, model_name=model, temperature=temperature, max_tokens=500)
    except Exception:
        return ""

GENERATORS = [MODEL, MODEL, "llama3.2:3b"]          # MODEL is llama3.1:8b on a GPU runtime

def archon(q):
    plan, pages = plan_and_search(q)
    cands = [generate(q, plan, pages, m) for m in GENERATORS]
    listing = "\n\n".join(f"=== Candidate {i + 1} ===\n{c[-1200:]}" for i, c in enumerate(cands))
    try:
        crit = structured(f"Web results:\n{as_context(pages)}\n\nQuestion: {q}\n\n{listing}\n\nCritique each candidate "
                          "(facts used, arithmetic) and rank them, best first.", Critique, max_tokens=500)
        order = [i - 1 for i in crit.ranking if 1 <= i <= len(cands)]
        order += [i for i in range(len(cands)) if i not in order]
        notes = crit.notes
    except Exception:
        order, notes = list(range(len(cands))), []
    top = order[:2]
    try:
        fused = ask(f"Web results:\n{as_context(pages)}\n\nQuestion: {q}\n\nBest candidates:\n" +
                    "\n\n".join(cands[i][-1200:] for i in top) + "\n\nCritiques:\n" + "\n".join(notes[:3]) +
                    "\n\nWrite one final, correct answer. Fix any mistakes." + FMT, max_tokens=500)
    except Exception:
        fused = cands[order[0]]
    final = answer_of(fused)
    try:
        v = structured(f"Web results:\n{as_context(pages)}\n\nQuestion: {q}\nProposed answer: {final}\n"
                       "Is this answer fully supported by the web results, with correct arithmetic?", Verdict, max_tokens=200)
        ok = v.supported
    except Exception:
        ok = True
    used = final if ok else answer_of(cands[order[0]])
    return {"answer": used, "calls": 7, "plan": plan, "pages": [d["title"] for d in pages],
            "cands": [answer_of(c) for c in cands], "order": order, "fused": final, "verified": ok}

def plan_search_single(q):
    """Ablation: planner + search, then one generator. Isolates the value of the generate/critique/fuse layers."""
    plan, pages = plan_and_search(q)
    return {"answer": answer_of(generate(q, plan, pages, MODEL, temperature=0)), "calls": 2}

At most 6 + 6 + 12 + 42 = 66 model calls.

def run(method):
    with ThreadPoolExecutor(2) as ex:
        return list(ex.map(method, [q for q, _ in QS]))

RES = {"single call": run(single), "single + search": run(single_rag),
       "planner + search + 1 gen": run(plan_search_single), "Archon augmented": run(archon)}

    print(f"{name:26s} {ACC[name]:6.0%}    {sum(r['calls'] for r in rs) / len(rs):.0f}")

What to notice. Search is what makes these questions answerable at all; the gap between the first two rows shows it. Planner-written queries usually find both pages a two-hop question needs, which a single raw-question search can miss. Whether the full stack beats "planner + search + 1 generator" is the interesting question: the extra 5 calls only pay off if the candidates disagree and the critic can tell which one is right. Look at the decoy pages in the retrieved lists: if a "New ..." page sneaks in, that is the HLE failure in miniature.
