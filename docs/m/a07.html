Part 2 · A07

Self-improvement with search and deep research agents

Open in Colab
12 min readPlain-English lesson, then the deeper material

Two ways to make an agent better without retraining it. Search over many answers and pick wisely (AlphaCode), or let the model look things up mid-thought (Search-o1).

The big idea

You can make an agent better without changing the model at all. You make it search. There are two kinds of search, and they solve different problems.

The first is search over answers. Think of hiring. You don't interview one candidate and hope. You get many applications, throw out the ones that fail the basic screen, and then pick carefully from the rest. AlphaCode does this with computer programs.

The second is search for knowledge. Think of a lawyer drafting a memo. When they hit a fact they don't know, they stop, look it up, jot down the one line that matters, and keep writing. Search-o1 teaches a model to do this in the middle of its reasoning.

Why it matters for us

  • A small local model often gets things wrong on the first try. But if you can check answers cheaply, drawing many and filtering is affordable on your own machine.
  • A local model knows nothing about the firm's contracts or internal policies. It must look them up. Doing that well is the difference between a useful assistant and a confident guesser.
  • Many firm questions need two facts from two places. "Who must approve this contract?" needs the fee from the contract and the rule from the policy. Searching once rarely gets both.

How it works, step by step

  1. Sample many answers (the AlphaCode paper, 2022). For each coding problem, AlphaCode drew huge numbers of programs, up to millions. More tries means a better chance at least one is right. The share of problems where at least one try is right is called coverage. It is the ceiling for any picking method.

  2. Filter with the examples. Each problem comes with a few example tests. Running every program on them threw away about 99% of samples. This is a cheap, exact check. But passing the examples is not the same as being correct. Many wrong programs still pass.

  3. Cluster by behavior. Run the survivors on fresh inputs. These inputs need no known answers. Group programs that give the same outputs. Then submit one program from each group, biggest group first, with at most 10 submissions. Why biggest first? There are many ways to be wrong, but correct programs tend to agree. So they pile up in the largest group. AlphaCode 2 (2023) kept this pipeline and added a scoring model (a model that predicts how likely a program is correct) to choose inside each group. With a better base model, it needed about 100 samples to match what the original needed a million for.

  4. Search for knowledge: first, RAG from zero. RAG (retrieval-augmented generation) means: before the model answers, a search tool finds relevant documents and pastes them into its prompt. It is like handing the intern a folder before they answer. Naive RAG searches once, with the whole question.

  5. Search-o1: search while thinking (the Search-o1 paper, 2025). The model reasons step by step. When unsure, it writes a search query between special tags, like <search>...</search>. The system pauses, runs the search, and the model continues. This is agentic RAG: the model itself decides when and what to search, possibly several times.

  6. Condense before pasting back. Raw search results are long and noisy. They can pull the reasoning off track. So a separate step, called Reason-in-Documents, reads the results and writes back only the few facts that matter. On a hard science quiz, this setup scored 63.6, against 58.6 for standard RAG with the same model.

model reasons ... <search>fee in Acme contract</search>
     -> search tool -> 3 pages -> Reason-in-Documents -> "Monthly fee is $8,000."
model continues ... <search>procurement approval tiers</search>
     -> ... -> "$5,000 to $15,000: Finance Director."
model: ANSWER: Finance Director

Worked example

The notebook builds this exact case. The corpus has 20 contracts and a few internal policies. One policy, "Procurement Policy PP-4", says who approves vendor spending. Under $5,000 a month, the Department Head. From $5,000 up to $15,000, the Finance Director. Above that, the Chief Financial Officer.

The question: "Who must approve the agreement between this customer and this vendor?"

  • No search. The model has never seen these documents. It guesses.
  • Naive RAG. One search with the whole question. It often brings back the contract or the policy, but not both. Half the facts means a wrong answer.
  • Search-o1 style. The model searches for the contract's fee first. The condensing step returns one sentence with the fee. Then it searches for the approval rule. It now has both hops and can answer.

The search tool itself is plain code:

def search(query, k=3):
    scores = BM25.get_scores(tok(query))
    return [DOCS[i] for i in sorted(range(len(DOCS)), key=lambda i: -scores[i])[:k]]
  • Line 1 defines a search that returns the top k documents, three by default.
  • Line 2 scores every document with BM25, a classic keyword-matching method. More shared words, especially rare ones, means a higher score.
  • Line 3 sorts documents from best to worst score and returns the top three.

The AlphaCode half of the notebook plants a wrong program that passes both example tests. Filtering can't catch it. But on fresh inputs it behaves differently, so it lands in a separate, smaller group.

Common mistakes

  • Treating "passes the examples" as "correct". Many wrong programs pass. Use clustering and hidden tests.
  • Picking survivors at random. You waste your submission budget on programs that look different but behave the same.
  • Searching once with the whole question. For two-step questions, let the model search for each fact on its own.
  • Pasting long raw results into the reasoning. Condense them to a few facts first.
  • Only reading the score. A small model may never search, or may search with vague words. Read the transcripts.

CS329A Lecture 8 (Oct 17)

You can make an agent better without training it by searching. Search over answers: draw many programs, keep the ones that pass the examples, group them by behavior, and submit one per group. Search for knowledge: let the model pause mid-thought, look something up, boil the results down, and keep reasoning.

Key terms

Filtering
Throwing away candidate programs that fail the example tests given in the problem.Source: Li et al. 2022
Clustering by behavior
Running candidates on extra inputs and grouping the ones that give identical outputs; the inputs need no known answers.Source: Li et al. 2022
10@k
Percent of problems solved when k samples are drawn but only 10 may be submitted.Source: Li et al. 2022
Scoring model
A model that predicts how likely a code sample is to be correct, used to rank samples.Source: AlphaCode 2 report, 2023
Agentic RAG
Retrieval where the model itself decides when to search and what to search for, possibly many times.Source: Li et al. 2025
Reason-in-Documents
A separate step that reads retrieved pages and writes back only the useful facts, so noisy text does not derail reasoning.Source: Li et al. 2025
Coverage
Fraction of problems where at least one sample is correct; the ceiling for any selection method.Source: Brown et al. 2024

The papers

Competition-Level Code Generation with AlphaCode

Li et al. · 2022

What
A transformer model sampled up to millions of programs per competitive-programming problem. It filtered them with the example tests from the problem statement, then clustered the survivors by their outputs on new test inputs written by a separate model, and submitted one program per cluster, largest first, with at most 10 submissions.
Result
Average ranking in the top 54.3% in simulated Codeforces contests with more than 5,000 participants. Solved 34.2% of held-out CodeContests problems with up to a million samples and 10 submissions. Filtering on example tests removed about 99% of samples. Solve rate grew roughly log-linearly with the number of samples.
Takeaway
When a cheap exact check exists (example tests), sample a lot and filter. When many candidates survive, group them by behavior and pick from the biggest group, because correct programs tend to agree with each other.

AlphaCode 2 Technical Report

AlphaCode Team, Google DeepMind (Leblond et al.) · 2023

What
The same sample, filter and cluster pipeline, built on fine-tuned Gemini Pro models. It drew up to a million C++ samples per problem with randomized temperature, kept the 10 largest clusters, and added a second fine-tuned Gemini model that scores each sample's chance of being correct to choose the best one in each cluster.
Result
Solved 43% of problems from 12 recent Codeforces contests (77 problems) within 10 attempts, vs 25% for the original AlphaCode. Estimated 85th percentile among participants (AlphaCode: about 46%). Filtering removed about 95% of samples. Needed about 100 samples to match AlphaCode with a million samples.
Takeaway
A better base model makes search far more sample-efficient, and a learned scorer helps choose inside a group. Selection, not generation, is often where the remaining gains are.

Search-o1: Agentic Search-Enhanced Large Reasoning Models

Li et al. · 2025

What
A reasoning model (QwQ-32B-Preview) writes a search query between special tags whenever it is unsure. The system pauses, retrieves the top 10 web results, and a separate Reason-in-Documents step condenses them into the facts that matter, which are inserted back into the reasoning chain.
Result
On GPQA diamond, overall 63.6 vs 58.1 for the same model without retrieval and 58.6 with standard RAG. Averaged over the five reasoning datasets it beat agentic RAG without Reason-in-Documents by 4.7% and no retrieval by 3.1%. On multi-hop QA, average exact match beat standard RAG by 29.6% and agentic RAG by 5.3%.
Takeaway
For multi-step questions, let the model decide when and what to search, one fact at a time, and condense the results before they reach the reasoning. One retrieval with the whole question often misses the second hop.

Part A · AlphaCode at laptop scale

AlphaCode (Li et al. 2022, Competition-Level Code Generation with AlphaCode) drew up to millions of programs per problem, then cut them down to 10 submissions in two steps:

  1. Filter: run each program on the example tests in the problem statement. This removed about 99% of samples.
  2. Cluster: run the survivors on new test inputs (made by a separate model) and group programs that give the same outputs. Submit one program per group, biggest group first.

Why biggest first? The paper's guess: there are many ways to be wrong, but correct programs tend to agree, so they pile up in the largest group. AlphaCode 2 (2023) kept the same pipeline and added a scoring model to pick the best program inside each of the 10 biggest groups.

Our version: 5 small tasks, 6 samples each. Each task has example tests (the model sees them), hidden tests (used only for grading) and an input generator (random inputs with no answers, used only for clustering).

A2. A safe runner

Model code runs only in a separate Python process with a timeout. The runner calls the function on a list of inputs and prints the outputs as JSON. A crash on one input is recorded as "ERROR: <type>" so it still forms part of the program's behavior.

a07_search_deep_research.ipynb · cell 4
RUNNER = r'''
import json, sys, copy
src, fn, inputs_path = open(sys.argv[1]).read(), sys.argv[2], sys.argv[3]
inputs = json.load(open(inputs_path))
ns = {}
try:
    exec(compile(src, "candidate", "exec"), ns)
    f = ns[fn]
except Exception as e:
    print(json.dumps(["ERROR: " + type(e).__name__] * len(inputs))); sys.exit(0)
outs = []
for args in inputs:
    try:
        outs.append(f(*copy.deepcopy(args)))
    except Exception as e:
        outs.append("ERROR: " + type(e).__name__)
print(json.dumps(outs, default=repr))
'''
WORK = tempfile.mkdtemp(prefix="a07_")
RUNNER_PATH = os.path.join(WORK, "runner.py")
open(RUNNER_PATH, "w").write(RUNNER)

def run_outputs(code, fn, inputs, timeout=10):
    """Run `code` in a subprocess and return one JSON-normalized output per input."""
    with tempfile.NamedTemporaryFile("w", suffix=".py", dir=WORK, delete=False) as f:
        f.write(code); src = f.name
    inp = src + ".json"
    open(inp, "w").write(json.dumps(inputs))
    try:
        out = subprocess.run([sys.executable, "-I", RUNNER_PATH, src, fn, inp], capture_output=True, text=True, timeout=timeout)
        res = json.loads(out.stdout.strip().splitlines()[-1])
        if not isinstance(res, list) or len(res) != len(inputs):
            raise ValueError("bad output")
    except subprocess.TimeoutExpired:
        res = ["TIMEOUT"] * len(inputs)
    except Exception:
        res = ["ERROR: runner"] * len(inputs)
    return [json.dumps(r, sort_keys=True) for r in res]       # strings, so outputs compare and hash cleanly

def expected(task, inputs):
    return [json.dumps(json.loads(json.dumps(task["ref"](*json.loads(json.dumps(a))), default=repr)), sort_keys=True) for a in inputs]

# Test the runner and the task set with the reference solutions themselves.
ref_ok = all(run_outputs(REF_CODE, t["fn"], t["hidden"]) == expected(t, t["hidden"]) for t in TASKS)
print("reference solutions pass their own hidden tests through the runner:", ref_ok)
print("a broken program:", run_outputs("def to_roman(n):\n    return 1/0", "to_roman", [[1], [2]]))
print("an endless loop:", run_outputs("def to_roman(n):\n    while True: pass", "to_roman", [[1]], timeout=3))

A3. Why clustering works: a planted wrong answer

A common wrong max_subarray resets the running sum to 0, so it returns 0 when every number is negative. It passes both example tests. Filtering can't catch it, but its outputs on generated inputs differ from the correct program, so it lands in a different cluster.

WRONG_MS = "def max_subarray(nums):\n    best = cur = 0\n    for x in nums:\n        cur = max(0, cur + x)\n        best = max(best, cur)\n    return best\n"
ms = TASKS[3]

A4. Sample many programs

For diversity, AlphaCode sampled half in Python and half in C++, put random problem tags and ratings in the prompt, and used a fairly high temperature. AlphaCode 2 also randomized the temperature per sample. We use a temperature of 0.8 and 6 samples per task (30 calls), 2 at a time.

a07_search_deep_research.ipynb · cell 6
N_SAMPLES = 6

def code_prompt(t):
    ex = "\n".join(f"{t['fn']}({', '.join(map(repr, a))}) == {t['ref'](*json.loads(json.dumps(a)))!r}" for a in t["examples"])
    return (f"Write a Python function `{t['fn']}`.\n{t['spec']}\n\nExamples:\n{ex}\n\n"
            "Return only the code, in one ```python block. No explanation.")

def extract_code(text):
    blocks = re.findall(r"```(?:python|py)?\s*\n(.*?)```", text or "", flags=re.S)
    return max(blocks, key=len) if blocks else (text or "")

def sample(t):
    return extract_code(ask(code_prompt(t), temperature=0.8, max_tokens=600))

jobs = [(ti, k) for ti in range(len(TASKS)) for k in range(N_SAMPLES)]
with ThreadPoolExecutor(2) as ex:
    codes = list(ex.map(lambda j: sample(TASKS[j[0]]), jobs))
SAMPLES = defaultdict(list)
for (ti, _), c in zip(jobs, codes):
    SAMPLES[ti].append(c)
print(SAMPLES[0][0][:400])

A5. Filter, cluster, select

For each sample we record three things: does it pass the examples, its behavior signature on generated inputs, and (for grading only) does it pass the hidden tests.

a07_search_deep_research.ipynb · cell 7
def analyse(ti):
    t = TASKS[ti]
    rows = []
    for code in SAMPLES[ti]:
        rows.append(dict(code=code,
                         ex_ok=run_outputs(code, t["fn"], t["examples"]) == expected(t, t["examples"]),
                         sig=tuple(run_outputs(code, t["fn"], t["gen_inputs"])),
                         hidden_ok=run_outputs(code, t["fn"], t["hidden"]) == expected(t, t["hidden"])))
    return rows

def clusters_of(rows):
    """Group the rows that passed the examples by behavior signature, biggest group first."""
    groups = defaultdict(list)
    for r in rows:
        if r["ex_ok"]:
            groups[r["sig"]].append(r)
    return sorted(groups.values(), key=len, reverse=True)

RESULTS = {ti: analyse(ti) for ti in range(len(TASKS))}
for ti, rows in RESULTS.items():
    cl = clusters_of(rows)
    print(f"{TASKS[ti]['fn']:16} samples {len(rows)} | pass examples {sum(r['ex_ok'] for r in rows)} | "
          f"clusters {[len(c) for c in cl]} | cluster correct? {[c[0]['hidden_ok'] for c in cl]} | "
          f"any sample correct: {any(r['hidden_ok'] for r in rows)}")

A6. Compare selection methods

We have a budget of K submissions per task. A task counts as solved if any submission passes all hidden tests. - random: pick K samples at random (expected value, using pass@k). - filter + random: pick K at random from the samples that pass the examples. - filter + cluster: one sample from each of the K biggest clusters. - oracle: any sample is correct (the ceiling, also called coverage).

a07_search_deep_research.ipynb · cell 8
def solve_rates(K):
    out = defaultdict(float)
    for ti, rows in RESULTS.items():
        n, c = len(rows), sum(r["hidden_ok"] for r in rows)
        f = [r for r in rows if r["ex_ok"]]
        fc = sum(r["hidden_ok"] for r in f)
        out["random"] += pass_at_k(n, c, min(K, n)) if n else 0
        out["filter + random"] += pass_at_k(len(f), fc, min(K, len(f))) if f else 0
        out["filter + cluster"] += float(any(cl[0]["hidden_ok"] for cl in clusters_of(rows)[:K]))
        out["oracle (coverage)"] += float(c > 0)
    return {k: v / len(RESULTS) for k, v in out.items()}

TABLE = {K: solve_rates(K) for K in (1, 2)}
print(f"{'method':20}" + "".join(f"{'K=' + str(K):>8}" for K in TABLE))
for m in TABLE[1]:
    print(f"{m:20}" + "".join(f"{TABLE[K][m]:>8.0%}" for K in TABLE))

What to notice: filtering helps because example tests are a cheap, exact verifier. Clustering helps most when many samples pass the examples but disagree with each other. The gap to the oracle row is the selection problem, which AlphaCode 2 attacked with a learned scoring model.

Part B · Search-o1: search in the middle of reasoning

Search-o1 (Li et al. 2025, Search-o1: Agentic Search-Enhanced Large Reasoning Models) lets a reasoning model write a search query between special tags whenever it is unsure. The system pauses, retrieves documents, and a separate Reason-in-Documents step condenses them into a few useful facts. Only those facts go back into the reasoning, so long noisy pages don't derail it.

We compare three ways to answer questions about our company's contracts and policies: 1. No search: the model alone. It has never seen our data, so it should fail. 2. Naive RAG: retrieve once with the question, then answer. 3. Search-o1 style: the model decides what to search, possibly several times, and each result is condensed first.

B1. The corpus: 20 contracts plus a few internal policies

The questions need two hops: one fact from a contract, and one rule from a policy.

def words(s):
    return re.findall(r"[a-z0-9]+", (s or "").lower())

def is_correct(answer, gold):
    """Lenient grading: a number must appear; for names, every word of the gold name must appear."""
    if gold.isdigit():
        return gold in re.findall(r"\d+", (answer or "").replace(",", ""))
    return all(w in words(answer) for w in words(gold))

def final_answer(text):
    m = re.findall(r"ANSWER:\s*(.+)", text or "")
    return m[-1].strip() if m else (text or "").strip()[-200:]

def no_search(q):

def naive_rag(q, k=4):
    ctx = "\n\n".join(f"[{d['id']}] {d['text']}" for d in search(q, k=k))
    return final_answer(ask(f"Sources:\n{ctx}\n\nQuestion: {q}\nThink briefly, then end with a line 'ANSWER: <short answer>'.", max_tokens=400))

B4. The Search-o1 loop

  1. The model reasons. When it needs a fact it writes <search>query</search>. We pass stop=["</search>"] so generation pauses right there.
  2. We run the search tool.
  3. Reason-in-Documents: a separate call reads the raw pages plus the reasoning so far and writes 1–3 sentences of useful facts.
  4. We paste those facts back inside <result>...</result> and let the model continue. At most 3 searches.
a07_search_deep_research.ipynb · cell 12
S1_SYSTEM = ("You answer questions about our company's vendor agreements and internal policies. You do NOT know these facts yourself. "
             "Think step by step. Whenever you need a fact, write a search query like this: <search>your query</search> and then stop. "
             "Search for one fact at a time, using the names in the question. The results will come back as <result>...</result>. "
             "When you know enough, finish with a line 'ANSWER: <short answer>'.")

from lal.llm import chat
def ask_msgs(msgs, **kw):
    return chat(msgs, max_tokens=400, **kw).content or ""

def reason_in_documents(reasoning, query, docs):
    pages = "\n\n".join(f"[{d['id']}] {d['text']}" for d in docs)
    return ask(f"Reasoning so far:\n{reasoning[-1500:]}\n\nSearch query: {query}\n\nSearched pages:\n{pages}\n\n"
               "Read the pages and write only the facts that help with the search query, in 1-3 sentences. "
               "Copy names and numbers exactly. If nothing helps, write 'No helpful information found.'", max_tokens=200).strip()

def search_o1(q, max_searches=3, condense=True, verbose=False):
    base = [{"role": "system", "content": S1_SYSTEM}, {"role": "user", "content": q}]
    transcript, n_search = "", 0
    while True:
        msgs = base + ([{"role": "assistant", "content": transcript},
                        {"role": "user", "content": "Continue your reasoning from where you stopped."}] if transcript else [])
        out = ask_msgs(msgs, stop=["</search>"])
        out = out.split("</search>")[0]                    # in case the server ignores `stop`
        i_s, i_a = out.find("<search>"), out.find("ANSWER:")
        transcript += ("\n" if transcript else "") + out
        if i_a != -1 and (i_s == -1 or i_a < i_s):         # answered before (or without) asking for a search
            break
        if i_s == -1 or n_search >= max_searches:          # no search and no answer, or out of budget: ask for the answer
            transcript += "\n" + ask_msgs(base + [{"role": "assistant", "content": transcript},
                                                  {"role": "user", "content": "Give your final answer now as 'ANSWER: <short answer>'."}])
            break
        query = out[i_s + len("<search>"):].strip()[:200]
        docs = search(query)
        info = reason_in_documents(transcript, query, docs) if condense else "\n".join(d["text"] for d in docs)
        transcript += f"</search>\n<result>{info}</result>"
        n_search += 1
        if verbose:
            print(f"  search {n_search}: {query!r}\n    -> {info[:160]}")
    return final_answer(transcript), n_search

Traps
  • Passing the example tests is not being correct. Many wrong programs pass them, which is why AlphaCode needed clustering and hidden tests.
  • Random selection wastes your submission budget on programs that are written differently but behave the same.
  • Clustering inputs only need to separate programs. They do not need known answers, and even invalid inputs can help.
  • Naive RAG retrieves once with the whole question. For two-hop questions it often gets one hop and misses the other.
  • Pasting long raw search results into a reasoning chain can push it off track. Condense first.
  • A small model may never emit a search, or may search with vague words. Read the transcripts, not just the score.

There are many ways to be wrong but correct programs tend to behave the same, so they gather in larger clusters.

A fine-tuned Gemini scoring model that picks the best sample in each of the 10 largest clusters.

About 99% of samples.

What does Reason-in-Documents do?

It reads the retrieved documents with the current reasoning and query, and returns only the relevant facts to insert into the reasoning chain.

In our notebook, why can naive RAG fail on the approver question?

The question needs the contract's monthly fee and the procurement policy tiers; one retrieval with the whole question may bring back only one of them.
