Learning objective

1/70
  • Use two kinds of search to make an agent better without training: sample-filter-cluster over answers (AlphaCode, AlphaCode 2), and search in the middle of reasoning (Search-o1).
Part 1Why this lecture: search instead of training

Two kinds of search

2/70
Search over answers Search for knowledge
Draw many programs, keep the good ones Pause mid-thought, look a fact up
Needs a cheap check (example tests) Needs a search tool over your documents
AlphaCode (2022), AlphaCode 2 (2023) Search-o1 (2025)
  • Both make the agent better with no change to the model's weights at test time.
  • Both spend more compute at answer time ("test-time compute").

The three papers

3/70
Paper What it does Headline result
AlphaCode (Li et al., DeepMind, 2022) Sample up to millions of programs, filter on example tests, cluster by behavior, submit ≤10 Top 54.3% in 10 Codeforces contests (Table 4)
AlphaCode 2 (Leblond et al., Google DeepMind, 2023) Same pipeline on Gemini Pro, plus a learned scoring model 43% of 77 problems vs 25% for AlphaCode; about 85th percentile

What ties them together

4/70
  • Generation is cheap; picking the right answer is hard.
    • AlphaCode: millions of samples, only 10 submissions.
    • Search-o1: 10 web pages per search, only a few facts matter.
  • Both add a selection step between "raw output" and "final answer".
    • AlphaCode: filter + cluster (+ scorer in AlphaCode 2).
    • Search-o1: Reason-in-Documents.
Part 2AlphaCode (Li et al. 2022)

The problem: competitive programming

5/70
  • Contest: 5–10 problems, about 3 hours, solutions judged on hidden tests.
  • Competitors learn only pass/fail, not why; wrong submissions cost penalty points.
  • Solving takes three steps:
    • Read a long description (story, task, input/output format, example tests)
    • Invent an efficient algorithm (time limits kill naive attempts)
    • Implement it exactly, often 100+ lines
  • Prior models: low single-digit solve rates on such problems.

Why this is hard for a model

6/70
  • Search space: all programs. Reward: very sparse (pass all hidden tests or not).
  • One character can change behavior without crashing.
  • Correct solutions can look completely different from each other.
  • Earlier code models (Codex) did short, explicit tasks: "translate the spec to code".
  • Contests need "what is the problem" → "how to solve it": a leap of reasoning.

Example problem: Backspace (Figure 2, 3)

7/70
  • Given strings s and t. Type s; instead of any character you may press Backspace.
  • Can you end with t? Output YES or NO. Rated 1500 (medium).
  • Example: s = "ababa", t = "ba" → YES (Backspace instead of 1st and 4th characters).
  • AlphaCode's solution (Figure 3):
    • Reverse both strings; match from the end
    • Mismatch → drop two letters (the one replaced and the one before it)
    • All of t matched → YES

The metric: n@k

8/70
  • n@k: percent of problems solved when the system draws k samples but may submit only n to the hidden tests.
    • Solved if any of the n submissions passes all hidden tests.
    • Choosing which n may use only what competitors see (example tests), never hidden tests.
  • 10@k: the main contest-like setting, 10 submissions.
  • pass@k = k@k: submit everything. An upper bound for k samples.
  • Reported numbers are expectations from bootstrapping over a sample set much larger than k (lowers variance).

How they cut false positives

11/70
  • Generated tests: mutate existing test inputs.
    • Bit flips, +/- on integers, swapping and changing characters in strings
  • Keep a mutated input only if 30 correct solutions all give the same output.
  • Budget: up to 10 CPU hours or 200 tests per problem (failed to reach 200 for 6.3% of problems).
  • Drop validation/test problems with fewer than 5 hidden or generated tests, or fewer than 2 distinct outputs (stops "always print YES").
  • Result: false positive rate 62% → 4%. Slow positives remain common.

The AlphaCode pipeline (Figure 4)

12/70
pre-train on GitHub → fine-tune on CodeContests
  → sample huge numbers of programs per problem
  → filter on example tests → cluster by behavior → ≤10 submissions
  • Pre-training: learn the space of human code (shrinks the search space).
  • Fine-tuning: adapt to contest problems.
  • Large-scale sampling + filtering: the part unique to AlphaCode; it "greatly improves" solve rate.

Pre-training data

13/70
  • GitHub snapshot from 2021/07/14, 12 languages: C++, C#, Go, Java, JavaScript, Lua, PHP, Python, Ruby, Rust, Scala, TypeScript.
  • Dropped files over 1MB or with lines over 1000 characters (auto-generated code).
  • Removed duplicate files (ignoring whitespace).
  • Final size: 715.1 GB of code.

Model architecture (Table 3)

14/70
Model Params Encoder blocks Decoder blocks Training tokens
AlphaCode 300M 284M 4 24 354B
AlphaCode 1B 1.1B 5 30 590B
AlphaCode 3B 2.8B 6 36 826B
AlphaCode 9B 8.7B 8 48 1250B
AlphaCode 41B 41.1B 8 56 967B
  • Encoder-decoder: encoder reads the description, decoder writes the code. Models p(code | description).
  • Asymmetric: 1536 encoder tokens, 768 decoder tokens (descriptions are about twice as long as solutions).
  • Shallow encoder, deep decoder: faster training, same solve rate.
  • 41B was stopped early, so it is under-trained relative to the others.

Built for fast sampling

15/70
  • Multi-query attention: all query heads share one key head and one value head per block.
    • Cuts memory and cache-update cost, the main bottleneck when sampling
    • Allows bigger sampling batches
  • Tokenizer: SentencePiece, 8,000-token vocabulary, trained on GitHub + CodeContests.
  • Pre-training losses: next-token for the decoder, masked language modeling (MLM: predict hidden tokens) for the encoder.
  • Files split at a random pivot: before → encoder, after → decoder.

Fine-tuning tricks (1/2)

17/70
  • Tempering: divide logits by a temperature T before softmax during training.
    • Formula: p = softmax(logits / T), with T = 0.2 at training
    • Makes training sharper so inference is smoother; avoids overfitting
    • Sampling temperature T′ tuned on validation: 0.12 (tempering only), 0.25 (tempering + GOLD)
  • Value conditioning: put "CORRECT SOLUTION" or "INCORRECT SOLUTION" in the prompt during training.
    • At sampling time, always condition on "correct"
    • Lets the model learn from wrong human submissions too
  • Value prediction: an extra small head guesses if a submission is correct (training only).

Fine-tuning tricks (2/2)

18/70
  • Metadata in the prompt (Figure 5): rating, tags (e.g. "dp, implementation"), language, correctness.
  • GOLD (Pang and He 2020): an offline RL objective.
    • Plain likelihood spreads weight over every training solution (like recall)
    • The contest only needs one correct solution in 10 tries (like precision)
    • GOLD learns from tokens the model already likes and ignores tokens far from its distribution
  • Fine-tuning learning rate: 10⁻⁵ cosine-decayed to 10⁻⁶.

Large-scale sampling

19/70
  • Millions of samples per problem. Diversity tricks:
    • Half Python, half C++
    • Random tags (from the 50 most popular) and random ratings (800–3500) in the prompt
    • Fairly high sampling temperature
  • Optimal temperature rises with sample count, but a wide range gives similar solve rates (Figure A5).
  • Top-k and nucleus sampling: no significant gain, so plain temperature sampling.

Step 1: filtering

20/70
  • Run each sample on the example tests in the problem statement. Drop failures.
  • Removes about 99% of samples (exact share depends on problem and model).
  • Can still leave tens of thousands of candidates per problem.
  • On about 10% of problems, no sample passes the examples at all.
  • This sub-task alone is classic program synthesis from input/output pairs.

Step 2: clustering

22/70
  • Problem: random picks from survivors waste submissions on programs that differ in text but behave the same.
  • Fix: run survivors on new test inputs; group programs with identical outputs.
  • Test inputs come from a separate test-input generation model (same architecture, trained to predict test inputs from descriptions).
    • Inputs need no known answers
    • Even invalid inputs can help separate programs
  • Submit one program per cluster, largest cluster first.
  • Fewer than 10 clusters → loop back to the largest, skipping submitted samples.

Why the biggest cluster first

23/70
  • Many ways to be wrong; correct programs tend to behave the same.
  • So correct programs gather in the larger clusters.
  • Different from the dataset's mutation tests: those need correct solutions to check, which do not exist at test time.

Scaling with samples (Figure 6)

27/70
  • Solve rate grows roughly log-linearly with sample count, for both 10@k and pass@k.
    • Each 10x more samples → a similar step up
    • 10@k bends down slightly at very large k
  • Larger models: higher slope. They reach the same solve rate with exponentially fewer samples.
  • Gap between 10@k and pass@k: the value of choosing well.
  • Catch: more solve rate needs exponentially more samples; cost soon prohibitive.

Scaling with compute (Figure 7)

28/70
  • Solve rate also grows log-linearly with training compute (TPU-days).
  • Sampling compute: big models cost more per sample, but win at equal sampling compute once the budget is large enough.
  • Open trade-off: spend compute on training a bigger model or on sampling more.

Policy and fine-tuning

40/70
  • Start: Gemini Pro. Two rounds of fine-tuning with GOLD.
  • Round 1: updated CodeContests, about 15 thousand problems and 30 million human code samples.
  • Vary hyperparameters → a family of fine-tuned models.
  • Round 2: a few more steps on a different, higher-quality dataset.
  • Why a family: maximize diversity, "key to tackling hard problems".

Sampling, filtering, clustering

41/70
  • Up to a million C++ samples per problem; random temperature per sample.
  • Random rating and tags in the prompt, as in AlphaCode. Budget split evenly across the model family.
  • Filter on public tests; drop the under 5% that do not compile. Removes about 95% of samples.
  • About 50 thousand candidates remain per problem on average.
  • Cluster by outputs on generated inputs; keep only the 10 largest clusters.

The scoring model

42/70
  • A second fine-tuned Gemini Pro gives each sample a correctness score from 0 to 1.
  • Pick the highest-scoring sample in each of the 10 clusters → 10 submissions.
  • This is a learned selector on top of filtering and clustering.

Results (Figures 2, 3)

43/70
  • 12 recent contests (division 2 or "1+2"), each over 8000 participants: 77 problems.
  • Solved 43% within 10 attempts vs 25% for AlphaCode (1.7x more problems).
  • Estimated 85th percentile, between "Expert" and "Candidate Master". AlphaCode: about 46%.
  • In its two best contests: better than 99.5% of participants.
  • Log-linear with samples again; about 100 samples match AlphaCode with 1M ("over 10000× more sample efficient").

Limitations and next steps

44/70
  • "Requires a lot of trial and error, and remains too costly to operate at scale."
  • Relies heavily on filtering out obviously bad samples.
  • With a human adding filtering properties: above the 90th percentile.
  • They expect Gemini Ultra as the base would help further.
Part 4Search-o1 (Li et al. 2025)

The problem: reasoning models lack knowledge

45/70
  • Large reasoning model (LRM): a model trained with RL to think in long step-by-step chains (o1, QwQ, DeepSeek-R1).
  • Long chains hit knowledge gaps; one gap can spread errors through the whole chain.
  • Figure 1, QwQ-32B on GPQA diamond: "perhaps" appears over 30 times per answer on average.
  • Uncertain words per output (Figure 1):
Word Direct reasoning Standard RAG Search-o1
perhaps 30.4 26.4 15.8
alternatively 27.1 21.6 11.9

Three ways to reason (Figure 2)

46/70
Vanilla reasoning Agentic RAG Search-o1
Guesses when unsure Searches when unsure Searches when unsure
"Perhaps trans-cinnamaldehyde is C6H5CH=CH-CO-CH3" ✗ Gets long, noisy pages Gets condensed facts

  • Example task: count carbon atoms after a 3-step chemistry reaction.

Why standard RAG is not enough

47/70
  • Standard RAG: retrieve once with the whole question, then answer.
  • In Figure 1, standard RAG barely reduces uncertainty vs direct reasoning.
  • Complex reasoning needs different facts at different steps.
  • Two problems with pasting documents into a chain:
    • Redundant information: long pages add noise and break coherence
    • Weak long-document reading: reasoning-tuned models partly forget general skills

Problem setup

48/70
  • Inputs: task instruction I, question q, retrieved documents D.
  • Output: reasoning chain R and final answer a.
  • Formula (Eq. 1): P(R, a | I, q, D) = Π P(R_t | R_<t, I, q, D_≤t) · Π P(a_t | a_<t, R, I, q)
    • First product: each reasoning token depends on earlier tokens and documents found so far
    • Second product: each answer token depends on the full reasoning
    • Key point: documents arrive during the chain, not only at the start

Agentic RAG mechanism

49/70
  • The model writes a query between <|begin_search_query|> and <|end_search_query|>.
  • Query i depends on the instruction, question and all reasoning so far (Eq. 2).
  • On the end tag: pause, run Search(query) → top-k documents (Eq. 3).
  • Results go back between <|begin_search_result|> and <|end_search_result|>.
  • Can happen many times in one chain (capped by a max search limit).

Reason-in-Documents

50/70
  • A separate generation by the same reasoning model, outside the main chain.
  • Inputs: previous reasoning steps, current search query, retrieved pages.
  • Two stages:
    • r_docs: reason about the pages (Eq. 4)
    • r_final: write the refined knowledge (Eq. 5)
  • Only r_final goes into the main chain (Eq. 6).
  • Prompt asks for output starting "Final Information", or "No helpful information found."

Inference loop (Algorithm 1)

51/70
S = {instruction + question}
while S not empty:
  generate all sequences until EOS or end-of-query tag   # batched
  for each sequence ending in a query: search, build Reason-in-Documents input
  for each sequence ending in EOS: move to finished
  run Reason-in-Documents for all pending searches     # batched
  insert r_final between search-result tags
  • Batching both generation and refinement raises throughput.

Setup

52/70
  • Backbone: QwQ-32B-Preview. Max 32,768 tokens; temperature 0.7, top_p 0.8, top_k 20, repetition penalty 1.05.
  • Retrieval: Bing Web Search (US-EN), top 10 documents; Jina Reader fetches page text.
  • Back-off: if no final answer, use the direct-reasoning answer.
  • Baselines: direct reasoning; standard RAG (top-10 documents for the question); RAgent (model searches, sees snippets, chooses URLs to fetch).
  • Hardware: eight NVIDIA A800-80GB GPUs.

The papers

Competition-Level Code Generation with AlphaCode

Li et al. · 2022

What
A transformer model sampled up to millions of programs per competitive-programming problem. It filtered them with the example tests from the problem statement, then clustered the survivors by their outputs on new test inputs written by a separate model, and submitted one program per cluster, largest first, with at most 10 submissions.
Result
Average ranking in the top 54.3% in simulated Codeforces contests with more than 5,000 participants. Solved 34.2% of held-out CodeContests problems with up to a million samples and 10 submissions. Filtering on example tests removed about 99% of samples. Solve rate grew roughly log-linearly with the number of samples.
Takeaway
When a cheap exact check exists (example tests), sample a lot and filter. When many candidates survive, group them by behavior and pick from the biggest group, because correct programs tend to agree with each other.

AlphaCode 2 Technical Report

AlphaCode Team, Google DeepMind (Leblond et al.) · 2023

What
The same sample, filter and cluster pipeline, built on fine-tuned Gemini Pro models. It drew up to a million C++ samples per problem with randomized temperature, kept the 10 largest clusters, and added a second fine-tuned Gemini model that scores each sample's chance of being correct to choose the best one in each cluster.
Result
Solved 43% of problems from 12 recent Codeforces contests (77 problems) within 10 attempts, vs 25% for the original AlphaCode. Estimated 85th percentile among participants (AlphaCode: about 46%). Filtering removed about 95% of samples. Needed about 100 samples to match AlphaCode with a million samples.
Takeaway
A better base model makes search far more sample-efficient, and a learned scorer helps choose inside a group. Selection, not generation, is often where the remaining gains are.

Search-o1: Agentic Search-Enhanced Large Reasoning Models

Li et al. · 2025

What
A reasoning model (QwQ-32B-Preview) writes a search query between special tags whenever it is unsure. The system pauses, retrieves the top 10 web results, and a separate Reason-in-Documents step condenses them into the facts that matter, which are inserted back into the reasoning chain.
Result
On GPQA diamond, overall 63.6 vs 58.1 for the same model without retrieval and 58.6 with standard RAG. Averaged over the five reasoning datasets it beat agentic RAG without Reason-in-Documents by 4.7% and no retrieval by 3.1%. On multi-hop QA, average exact match beat standard RAG by 29.6% and agentic RAG by 5.3%.
Takeaway
For multi-step questions, let the model decide when and what to search, one fact at a time, and condense the results before they reach the reasoning. One retrieval with the whole question often misses the second hop.

Part A · AlphaCode at laptop scale

AlphaCode (Li et al. 2022, Competition-Level Code Generation with AlphaCode) drew up to millions of programs per problem, then cut them down to 10 submissions in two steps:

  1. Filter: run each program on the example tests in the problem statement. This removed about 99% of samples.
  2. Cluster: run the survivors on new test inputs (made by a separate model) and group programs that give the same outputs. Submit one program per group, biggest group first.

Why biggest first? The paper's guess: there are many ways to be wrong, but correct programs tend to agree, so they pile up in the largest group. AlphaCode 2 (2023) kept the same pipeline and added a scoring model to pick the best program inside each of the 10 biggest groups.

Our version: 5 small tasks, 6 samples each. Each task has example tests (the model sees them), hidden tests (used only for grading) and an input generator (random inputs with no answers, used only for clustering).

    rows = []
    for code in SAMPLES[ti]:
        rows.append(dict(code=code,

    groups = defaultdict(list)

A6. Compare selection methods

We have a budget of K submissions per task. A task counts as solved if any submission passes all hidden tests. - random: pick K samples at random (expected value, using pass@k). - filter + random: pick K at random from the samples that pass the examples. - filter + cluster: one sample from each of the K biggest clusters. - oracle: any sample is correct (the ceiling, also called coverage).

a07_search_deep_research.ipynb · cell 8
def solve_rates(K):
    out = defaultdict(float)
    for ti, rows in RESULTS.items():
        n, c = len(rows), sum(r["hidden_ok"] for r in rows)
        f = [r for r in rows if r["ex_ok"]]
        fc = sum(r["hidden_ok"] for r in f)
        out["random"] += pass_at_k(n, c, min(K, n)) if n else 0
        out["filter + random"] += pass_at_k(len(f), fc, min(K, len(f))) if f else 0
        out["filter + cluster"] += float(any(cl[0]["hidden_ok"] for cl in clusters_of(rows)[:K]))
        out["oracle (coverage)"] += float(c > 0)
    return {k: v / len(RESULTS) for k, v in out.items()}

TABLE = {K: solve_rates(K) for K in (1, 2)}
print(f"{'method':20}" + "".join(f"{'K=' + str(K):>8}" for K in TABLE))
for m in TABLE[1]:
    print(f"{m:20}" + "".join(f"{TABLE[K][m]:>8.0%}" for K in TABLE))

def words(s):

def is_correct(answer, gold):
    """Lenient grading: a number must appear; for names, every word of the gold name must appear."""
    if gold.isdigit():

    return all(w in words(answer) for w in words(gold))

B4. The Search-o1 loop

  1. The model reasons. When it needs a fact it writes <search>query</search>. We pass stop=["</search>"] so generation pauses right there.
  2. We run the search tool.
  3. Reason-in-Documents: a separate call reads the raw pages plus the reasoning so far and writes 1–3 sentences of useful facts.
  4. We paste those facts back inside <result>...</result> and let the model continue. At most 3 searches.
a07_search_deep_research.ipynb · cell 12
S1_SYSTEM = ("You answer questions about our company's vendor agreements and internal policies. You do NOT know these facts yourself. "
             "Think step by step. Whenever you need a fact, write a search query like this: <search>your query</search> and then stop. "
             "Search for one fact at a time, using the names in the question. The results will come back as <result>...</result>. "
             "When you know enough, finish with a line 'ANSWER: <short answer>'.")

from lal.llm import chat
def ask_msgs(msgs, **kw):
    return chat(msgs, max_tokens=400, **kw).content or ""

def reason_in_documents(reasoning, query, docs):
    pages = "\n\n".join(f"[{d['id']}] {d['text']}" for d in docs)
    return ask(f"Reasoning so far:\n{reasoning[-1500:]}\n\nSearch query: {query}\n\nSearched pages:\n{pages}\n\n"
               "Read the pages and write only the facts that help with the search query, in 1-3 sentences. "
               "Copy names and numbers exactly. If nothing helps, write 'No helpful information found.'", max_tokens=200).strip()

def search_o1(q, max_searches=3, condense=True, verbose=False):
    base = [{"role": "system", "content": S1_SYSTEM}, {"role": "user", "content": q}]
    transcript, n_search = "", 0
    while True:
        msgs = base + ([{"role": "assistant", "content": transcript},
                        {"role": "user", "content": "Continue your reasoning from where you stopped."}] if transcript else [])
        out = ask_msgs(msgs, stop=["</search>"])
        out = out.split("</search>")[0]                    # in case the server ignores `stop`
        i_s, i_a = out.find("<search>"), out.find("ANSWER:")
        transcript += ("\n" if transcript else "") + out
        if i_a != -1 and (i_s == -1 or i_a < i_s):         # answered before (or without) asking for a search
            break
        if i_s == -1 or n_search >= max_searches:          # no search and no answer, or out of budget: ask for the answer
            transcript += "\n" + ask_msgs(base + [{"role": "assistant", "content": transcript},
                                                  {"role": "user", "content": "Give your final answer now as 'ANSWER: <short answer>'."}])
            break
        query = out[i_s + len("<search>"):].strip()[:200]
        docs = search(query)
        info = reason_in_documents(transcript, query, docs) if condense else "\n".join(d["text"] for d in docs)
        transcript += f"</search>\n<result>{info}</result>"
        n_search += 1
        if verbose:
            print(f"  search {n_search}: {query!r}\n    -> {info[:160]}")
    return final_answer(transcript), n_search

Traps
  • Passing the example tests is not being correct. Many wrong programs pass them, which is why AlphaCode needed clustering and hidden tests.
  • Random selection wastes your submission budget on programs that are written differently but behave the same.
  • Clustering inputs only need to separate programs. They do not need known answers, and even invalid inputs can help.
  • Naive RAG retrieves once with the whole question. For two-hop questions it often gets one hop and misses the other.
  • Pasting long raw search results into a reasoning chain can push it off track. Condense first.
  • A small model may never emit a search, or may search with vague words. Read the transcripts, not just the score.
