Part 1Why planning?

One straight pass is not enough

2/80
  • A greedy chain commits to its first idea and never looks back.
  • Hard tasks need more than one straight pass.
  • Five papers, five tools:
    • LATS: tree search; back up from dead ends
    • ADaPT: split a task only when a direct try fails
    • AB-MCTS: spend the next call on a new answer or on fixing an old one
    • SPRINT: run independent steps at the same time
    • SWiRL: train on single steps, not whole runs

Greedy chain vs tree search

3/80
Greedy chain Tree search
One next step, no going back Several candidate steps, each scored
Dead end → fail Dead end → back up to a better branch
Fewest calls More calls
  • Tree search: explore several next steps, score them, return to a better branch when one fails.
  • Value function: a score for how promising a half-finished solution is.

How the five papers fit together

4/80
Question Paper Answer
Dead end? LATS Keep a tree; go back
Task too big? ADaPT Try first; split only what fails
New idea or fix the old one? AB-MCTS Let scores decide at every node
Too slow? SPRINT Run steps that don't depend on each other at once
How to train it? SWiRL One training example per step

Our test bed: a number puzzle

5/80
  • Four numbers 1–9, a target; use each number once with + − × ÷.
  • Every middle result must be a whole number, not negative.
  • A brute-force solver keeps only targets that can be reached, so every puzzle has an answer.
  • State: the numbers still left. Step: combine two of them. Four numbers need three steps.
  • With two numbers left, code checks the last step, like a unit test.
Part 2LATS: tree search for agents (Zhou et al. 2023)

The problem LATS solves

6/80
  • ReAct and Reflexion act step by step but never consider several paths or plan ahead.
  • Tree-of-Thoughts and RAP search over reasoning chains, but use no outside feedback.
  • LATS (Language Agent Tree Search): Monte Carlo Tree Search (MCTS) over agent actions, with the environment's feedback inside the search.
  • One LM plays three roles: the agent, the judge of states, and the writer of reflections.

MCTS in one slide

7/80
  • MCTS: build a tree where each node is a state and each edge is an action.
  • Run k episodes. Each one starts at the root and grows the tree.
  • Expansion: sample n actions from a node, making n children.
  • Selection: walk down by picking the child with the highest UCT score.
  • Classic MCTS needs a model to undo steps. Many LM tasks can simply be reset.

A node in LATS

8/80
  • Node: s = [x, a1…i, o1…i]
    • x: the original input (the question or task)
    • a1…i: the actions taken so far
    • o1…i: what the environment returned after each action
  • The tree lives in an outside memory, not in the prompt.
  • LATS does not need a world model. It calls the real environment.

The six operations (Figure 2)

9/80
  • Selection: walk from the root to a leaf by UCT.
  • Expansion: sample n actions; the environment returns n observations; add n children.
  • Evaluation: give each new child a value.
  • Simulation: keep expanding the best child until the end of the task.
  • Backpropagation: send the final reward back up the path.
  • Reflection: after a failure, write what went wrong; use it as context next time.
  • Repeat until success or the budget of k trajectories runs out.

Selection formula: UCT

10/80
  • UCT(s) = V(s) + w · sqrt( ln N(p) / N(s) )
    • V(s): the node's value (expected reward below it)
    • N(s): how often s was visited; N(p): how often its parent was visited
    • w: exploration weight; higher = try rarely visited nodes more
  • First term: go where it has worked. Second term: try what you haven't.
  • Default w = 1 (Appendix A).

Evaluation formula: the value

11/80
  • V(s) = λ · LM(s) + (1 − λ) · SC(s)
    • LM(s): the LM reasons about the state and ends with a score
    • SC(s): self-consistency; actions sampled many times at the same state tend to be right
    • λ: mix weight
  • Key difference from Tree-of-Thoughts: the score comes after the environment's feedback.
  • λ = 0.5 for HotPotQA and Game of 24; λ = 0.8 for programming and WebShop (Appendix A).

Backpropagation and reflection

12/80
  • Backpropagation: for every node on the path, add 1 to its visit count and fold in the reward r.
    • V(s) = (old V · (N − 1) + r) / N, so V stays an average of rewards
  • Reflection: on a failed end state, the LM gets the path and the reward and writes what went wrong plus a better idea.
  • Failed paths and reflections are stored and added to later prompts.
  • The paper calls this a "semantic gradient": learning from trial and error with no weight updates.

LATS limitations

22/80
  • Costs more than ReAct or Reflexion.
  • Needs to return to earlier states. A sent email can't be unsent.
  • Benchmarks are simpler than real-world settings (Appendix B).
  • n (children per step) is the knob between quality and cost.

Our simplified LATS (notebook)

  • Terminal: with two numbers left, code checks the last step.
  • Reflection: code writes dead ends into the next prompt (free, unlike asking the LM).
Part 3ADaPT: decompose only when needed (Prasad et al. 2024)

The problem ADaPT solves

24/80
Iterative executor (ReAct) Plan-and-execute
Picks the next action from the full history Writes a plan once, then runs each step
Long histories confuse it One step it can't do → the whole task fails
No planning Plan never adapts
  • ADaPT (As-Needed Decomposition and Planning for complex Tasks): plan only when the executor fails, and only for the part that failed.

The executor

25/80
  • An LLM that acts step by step in the environment, ReAct style, until done or out of steps.
  • It gets examples of "atomic skills" for the environment (e.g. how to heat an object in ALFWorld).
  • All baselines use the same executor, so the comparison is fair.
  • Self-generated success: the executor ends with "task completed" or "task failed". No gold reward needed.

The planner

26/80
  • Breaks a failed task into a short plan, typically 3–5 steps.
  • Short and abstract on purpose: a 10-step plan made without knowing where the mug is breaks easily.
  • Joins steps with logic:
    • AND: do them in order; all must succeed
    • OR: try one, then the other if needed ("find a mug on the countertop" OR "find a mug in the cabinet")

The controller: a recursive program

27/80
  • ADaPT(task, depth k):
      1. Run the executor on the task. Success → done.
      1. Failure and k < d_max → planner splits the task.
      1. Call ADaPT(step, k + 1) on each step; combine with AND/OR.
  • d_max: 3 for ALFWorld and WebShop, 4 for TextCraft.
  • d_max = 1 is plain ReAct.

Example: "put a clean mug on the desk" (Figure 2)

28/80
Level What happens
Depth 1 Executor tries the whole task; fails
Planner Step 1: find and take a mug AND Step 2: clean it AND Step 3: put it on the desk
Depth 2 Executor runs each step; "clean the mug" succeeds directly
Deeper Only a step that fails gets split again

Part 4AB-MCTS: wider or deeper? (Inoue et al. 2025)

Three ways to spend a budget (Figure 1)

38/80
Method Shape Weakness
Repeated sampling Only wide: n fresh answers Never uses feedback to fix an answer
Sequential refinement Only deep: fix one answer n − 1 times Stuck if the first idea is wrong
Standard MCTS Fixed width (e.g. 5 children per node) Width is a guess set by hand
  • AB-MCTS (Adaptive Branching MCTS) decides at every node: go wider or go deeper.

Setup

39/80
  • The LLM gets a prompt (the task, or an old answer plus feedback) and returns an answer.
  • Score r = R(answer), usually from 0 to 1. Example: share of test cases passed.
  • The true grader may be hidden, so search uses a partial one (like public tests).
  • Goal: find a high-scoring answer within a fixed number of LLM calls.

The algorithm (Algorithm 1)

40/80
  • Each round adds one node:
      1. Select a node to expand
      1. Expand: at the root, write a new answer; elsewhere, refine that node's answer with feedback
      1. Back up the new score toward the root
  • No rollouts: each answer is scored as soon as it exists.
  • GEN node: every node has a special child meaning "make a new child here". Picking it = go wider at that node.

Why Thompson sampling, not UCT

41/80
  • UCT assumes a fixed set of arms. GEN creates new arms on the fly.
  • GEN has no children, so it has no UCT score.
  • Thompson sampling: for each option, draw a random score from its belief; pick the highest draw.
      1. Compute the score distribution for each action (GEN or each existing child)
      1. Draw one score from each
      1. Pick the action with the highest draw
  • Bonus: Thompson sampling lets you expand several nodes in parallel.

AB-MCTS-M: mixed model

42/80
  • r = αj + σy · ε, with αj = µα + σα · ε'
    • αj: quality of the answers under child j (one "group" per subtree)
    • µα, σα: average and spread of quality across groups
    • σy · ε: noise for each new answer
  • Fit with MCMC (random sampling to estimate the unknowns) at each selection.
  • GEN is a new group with no data; its quality is guessed from what the other groups show.
  • Figure 2: a child with high-scoring children gets a peak at high r; more data → narrower curve.

AB-MCTS-A: node aggregation

43/80
  • Simpler and lighter: no shared parameters.
  • CONT node: "keep refining the existing children". GEN: "make a new one".
  • Scores back up to the GEN or CONT node that led there.
  • Two belief types with closed-form updates:
    • Gaussian (normal-inverse-χ² prior) for any score range
    • Beta prior for scores in [0, 1]

AB-MCTS limitations

50/80
  • Needs a reliable scorer. Building one can be hard.
  • Counts only API calls, not real cost (time, GPU, tokens).
  • Repeated sampling is easier to run in parallel and needs no feedback step.

Wider vs deeper in the notebook

51/80
  • Same budget of 3 calls per puzzle for each strategy.
  • Wider: 3 fresh answers at temperature 0.9; keep the best score.
  • Deeper: 1 answer, then 2 fixes with the checker's message ("it equals 30, not 24").
  • Score: 1.0 if correct; partial credit if it uses the right numbers and lands close.
  • 3 puzzles × 3 calls is far too small to pick a winner. The paper used up to 128.
Part 5SPRINT: run independent steps at once (Biju et al. 2025)

The problem SPRINT solves

52/80
  • Reasoning models (like DeepSeek-R1) think in one long sequence. Long = slow.
  • Repeated sampling runs in parallel but the paths don't share work.
  • Tree-of-Thoughts and Graph-of-Thoughts need a hand-made search shape.
  • SPRINT trains the model itself to spot steps that don't depend on each other and run them at the same time.

Inference: plan, run, sync (Figure 1)

53/80
    1. Planning: the planner reads everything so far and writes a plan, with each subtask inside <prompt_i.j> tags.
    1. Parallel execution: one executor per prompt, all running at once, each writing its own reasoning.
    1. Syncing: results go back into the context as <execution_i.j>, in prompt order.
  • Repeat until the planner writes the final answer.
  • Planner and executors are the same fine-tuned model.

Training data: four steps (Figure 2)

54/80
    1. Step extraction: GPT-4o cuts an R1 reasoning trace into steps, each with a plan part and an execution part.
    2. Very short executions are merged into the plan ("plan-only" steps)
    1. DAG creation: GPT-4o-mini marks which steps depend on which. DAG: a graph of steps with arrows, no loops.
    1. Packing: group steps into stages that can run together.
    1. Filter and fine-tune: keep traces with steps/stages ≥ 1.5; SFT the model on the tagged format.

Packing formula

55/80
  • stage(S) = 1 if S has no parents
  • otherwise stage(S) = max over parents P of ( stage(P) + 1 if P has an execution, else + 0 )
    • A step can share a stage with a plan-only parent: no result to wait for
  • Stage k plan = all plans in stage k joined in order.
  • Stage k executions = all non-empty executions in stage k, run in parallel.

Measuring speed: sequential tokens

56/80
  • Sequential tokens = sum over stages of the max over prompts in that stage of (planner tokens up to that prompt + executor tokens)
    • Only the longest branch in each stage counts
  • For normal models: just the number of output tokens.

Part 6SWiRL: train on steps, not runs (Goldie et al. 2025)

The problem SWiRL solves

63/80
  • RLHF, RLAIF and RLEF treat a task as one step: one answer, one reward at the end.
  • Agent tasks take many steps: what to search, when to stop, how to combine.
  • One wrong middle step often ruins the final answer.
  • SWiRL (Step-Wise Reinforcement Learning): make multi-step data, then give a reward to every step.

Stage 1: make synthetic runs (Figure 1)

64/80
  • Gemma 2 gets a tool: a search engine (for QA) or a calculator (for math).
  • Each turn: think, then call the tool or give a final answer.
  • Run: τ = (s1, a1, …, sK, aK)
    • s1: the question; each later state = everything so far plus the tool's reply
    • ai: the model's response; aK is the final answer
  • 50,000 runs from 10,000 HotPotQA questions (5 each; "Easy" ones dropped); 37,500 runs from 7,500 GSM8K questions.
  • Max 5 steps for HotPotQA, 10 for GSM8K.

Part 8Wrap-up

Common mistakes

80/80
  • Searching where actions can't be undone → only search over states you can return to.
  • Planning everything up front → try directly, split only what fails.
  • Trusting self-reported success → use a real checker.
  • Picking wider vs deeper from a tiny budget → gains showed at 2^5–2^9 calls; some gaps were within noise.
  • Parallelizing dependent steps → map dependencies first; the longest chain sets latency.
  • Keeping only successful runs → process filtering beat outcome filtering for RL.

Check your understanding

What does ADaPT do differently from plan-and-execute?

It tries the whole task first and splits it only when the executor fails, recursing on the failed parts. Easy tasks cost one call.

In LATS, what two parts make up the value of a node?

An LM score, given after seeing the environment's feedback, and a self-consistency score. They are mixed with weight λ.

Why can't AB-MCTS use UCT to pick the GEN node?

GEN has no children and adds new arms as it goes, so it has no UCT score. Thompson sampling draws a score from a belief instead.

In AB-MCTS on CodeContests with GPT-4o, which did worse: only wider or only deeper?

Only deeper. Sequential refinement scored 30.1% vs 37.9% for repeated sampling (Table 1).

How does SPRINT count speed?

Sequential tokens: in each stage only the longest parallel branch counts. On long MATH-500 problems this fell by 39%.

Why might SWiRL keep a step from a run whose final answer was wrong?

The step itself was judged reasonable. Process-only filtering gave the best RL results.

CS329A Lecture 5 (Oct 6)

Hard tasks need more than one straight pass. Search a tree of steps and back up from dead ends, split a task only when a direct try fails, spend budget on new ideas or on refining old ones depending on feedback, and run independent steps at the same time. Every step you log can become step-level training data.

Key terms

Tree search
Exploring several possible next steps, scoring them, and going back to a better branch when one fails, instead of committing to one chain.Source: Zhou et al. 2023
Value function
A score for how promising a partial solution is. In LATS it mixes the LM's own rating with self-consistency (how often a state is proposed).Source: Zhou et al. 2023
As-needed decomposition
Split a task into sub-tasks only after a direct attempt fails, and recurse on the failing parts.Source: Prasad et al. 2024
Wider vs deeper
Spending the next call on a new independent answer (wider) or on refining an existing one with feedback (deeper).Source: Inoue et al. 2025
Thompson sampling
Pick the option whose random draw from its score distribution is highest; it balances trying new options with using proven ones.Source: Inoue et al. 2025
Sequential tokens / critical path
The tokens or steps that must happen one after another; parallel steps only count once per round.Source: Biju et al. 2025
Sub-trajectory and process filtering
Cutting a multi-step run into one example per action, and keeping steps a judge calls reasonable regardless of the final outcome.Source: Goldie et al. 2025

The papers

Synthetic Data Generation & Multi-Step RL for Reasoning & Tool Use (SWiRL)

Goldie et al. · 2025

What
Gemma 2 generates multi-step trajectories with tools (a search engine for QA, a calculator for math). Each trajectory with k actions is cut into k sub-trajectories (context so far, then the next action). These are filtered, and the model is trained with step-wise RL where a generative reward model (Gemini 1.5 Pro) judges each action.
Result
Relative accuracy gains over baselines: 21.5% GSM8K, 12.3% HotPotQA, 14.8% CofCA, 11.1% MuSiQue, 15.3% BeerQA. Training only on HotPotQA improved zero-shot GSM8K by 16.9% relative. Process-only filtering (keep steps judged reasonable, even if the final answer was wrong) gave the best results for RL; outcome filtering usually hurt compared with no filter. Smaller 2B and 9B models generalized less consistently than 27B.
Takeaway
Log agent runs step by step and label steps, not only final outcomes. A failed run still contains good steps worth training on.

Language Agent Tree Search Unifies Reasoning Acting and Planning in Language Models (LATS)

Zhou et al. · 2023

What
Monte Carlo Tree Search over agent actions. Each round: select a node by UCT, expand n sampled actions (n = 5 by default) and run them in the environment, evaluate with V = λ·(LM score) + (1-λ)·(self-consistency), simulate to the end, backpropagate, and write a verbal reflection after a failure.
Result
HumanEval pass@1 92.7% with GPT-4 (83.8% with GPT-3.5, vs 68.1% for Reflexion). HotPotQA EM 0.63 vs 0.32 for ReAct (GPT-3.5, 100-question subset). WebShop score 75.9 without gradient training. Game of 24 success 0.44 vs 0.20 for Tree-of-Thoughts. It costs more than ReAct or Reflexion and assumes you can return to earlier states.
Takeaway
When you have a checkable reward (tests, a verifier), search beats a single chain. Only use it where states can be undone, and cap the expansions.

SPRINT: Enabling Interleaved Planning and Parallelized Execution in Reasoning Models

Biju et al. · 2025

What
A data pipeline rewrites long sequential reasoning traces (from DeepSeek-R1 on MATH) into rounds: a plan listing independent subtasks, then parallel execution of those subtasks. GPT-4o and GPT-4o-mini split traces into steps and build a dependency graph; about 1,700 examples fine-tune a 7B distilled reasoning model to plan and run steps in parallel.
Result
Matched reasoning baselines on math (MATH-500 92.5% vs 91.0% for the same model fine-tuned on sequential traces) while cutting sequential tokens by up to 39% on problems needing more than 8,000 tokens. The gains carried over to out-of-domain tasks: up to 45% fewer sequential tokens on GPQA and 65% on Countdown.
Takeaway
Latency is set by the longest chain of dependent steps, not the total work. Have the planner mark which steps are independent and run those in parallel.

ADaPT: As-Needed Decomposition and Planning with Language Models

Prasad et al. · 2024

What
An executor LLM first tries the whole task. Only if it reports failure does a planner split the task into a few sub-tasks joined by AND/OR, and ADaPT recurses on each, up to a max depth (3 for ALFWorld and WebShop, 4 for TextCraft). Success is the executor's own judgment.
Result
With GPT-3.5: ALFWorld 71.6% vs 43.3% ReAct and 57.5% Reflexion; WebShop 44.0% vs 32.0% ReAct; TextCraft (a new compositional dataset) 52.0% vs 19.0% ReAct. The abstract summarizes this as up to 28.3%, 27% and 33% higher success rates than strong baselines. The executor's self-reported success overestimated real success, by more than 30 points on WebShop.
Takeaway
Don't plan everything up front. Try directly, and decompose only the parts that fail. Use a real checker for 'did it work' when you can; self-reports are optimistic.

Wider or Deeper? Scaling LLM Inference-Time Compute with Adaptive Branching Tree Search (AB-MCTS)

Inoue et al. · 2025

What
A tree search where each node can generate a brand-new answer (wider, via a GEN node) or refine an existing child (deeper), chosen by Thompson sampling on feedback scores. Two variants: AB-MCTS-M (a mixed model) and AB-MCTS-A (node aggregation). Tested with GPT-4o and DeepSeek-V3 on LiveCodeBench, CodeContests, ARC-AGI and MLE-Bench.
Result
At 128 calls on CodeContests with GPT-4o: AB-MCTS-M 40.6%, repeated sampling 37.9%, standard MCTS 37.5%, pure sequential refinement 30.1%. AB-MCTS-M had the best average rank across benchmarks. On ARC-AGI at 128 calls repeated sampling was still best, but with up to 512 calls AB-MCTS kept improving while repeated sampling plateaued. Many LiveCodeBench gaps look within the reported standard deviations (our reading of the tables).
Takeaway
Neither 'sample more' nor 'refine more' always wins. Let feedback scores decide where the next call goes, and expect the gains to appear at larger budgets.

1. The puzzle and its checker

Rules: use each number exactly once; + - * /; every intermediate result must be a whole number that is not negative. The puzzles are generated with a fixed seed, and the generator only keeps targets that a brute-force solver can reach, so every puzzle has an answer. The solver is our ground truth; the model never sees it.

a04_planning_search.ipynb · cell 3
OPS = {"+": lambda a, b: a + b, "-": lambda a, b: a - b if a >= b else None,
       "*": lambda a, b: a * b, "/": lambda a, b: a // b if b and a % b == 0 else None}

@lru_cache(maxsize=None)
def solve(values: tuple, target: int):
    """Brute force: return an expression that reaches target, or None. values is a sorted tuple."""
    if len(values) == 1:
        return str(values[0]) if values[0] == target else None
    vals = list(values)
    for i in range(len(vals)):
        for j in range(len(vals)):
            if i == j:
                continue
            rest = [v for k, v in enumerate(vals) if k not in (i, j)]
            for op, f in OPS.items():
                r = f(vals[i], vals[j])
                if r is None:
                    continue
                sub = solve(tuple(sorted(rest + [r])), target)
                if sub is not None:
                    return f"[{vals[i]} {op} {vals[j]} = {r}] then {sub}"
    return None

@lru_cache(maxsize=None)
def reachable(values: tuple) -> frozenset:
    if len(values) == 1:
        return frozenset(values)
    out = set()
    for i in range(len(values)):
        for j in range(len(values)):
            if i != j:
                rest = [v for k, v in enumerate(values) if k not in (i, j)]
                for f in OPS.values():
                    r = f(values[i], values[j])
                    if r is not None:
                        out |= reachable(tuple(sorted(rest + [r])))
    return frozenset(out)

def good_first_steps(nums, target):
    """How many legal first steps keep the target reachable. More = a friendlier puzzle."""
    n = 0
    for i in range(4):
        for j in range(4):
            if i != j:
                rest = [v for k, v in enumerate(nums) if k not in (i, j)]
                for f in OPS.values():
                    r = f(nums[i], nums[j])
                    n += r is not None and target in reachable(tuple(sorted(rest + [r])))
    return n

def make_puzzles(n, seed=7):
    """Random numbers 1-9; the target is one of the friendliest reachable targets (several paths work, but not all)."""
    rng, out = random.Random(seed), []
    while len(out) < n:
        nums = sorted(rng.randint(1, 9) for _ in range(4))
        cands = [t for t in reachable(tuple(nums)) if 12 <= t <= 40 and t != sum(nums)]   # not just "add everything"
        if not cands:
            continue
        ranked = sorted(cands, key=lambda t: -good_first_steps(nums, t))
        out.append({"numbers": nums, "target": rng.choice(ranked[:3])})
    return out

def check_expr(expr, numbers, target):
    """Exact check of a full expression. Returns (ok, value_or_None, message)."""
    try:
        tree = ast.parse(expr, mode="eval")
    except Exception:
        return False, None, "not a valid arithmetic expression"
    used = []
    def ev(n):
        if isinstance(n, ast.Expression): return ev(n.body)
        if isinstance(n, ast.Constant) and isinstance(n.value, int):
            used.append(n.value); return Fraction(n.value)
        if isinstance(n, ast.BinOp) and type(n.op) in (ast.Add, ast.Sub, ast.Mult, ast.Div):
            a, b = ev(n.left), ev(n.right)
            if isinstance(n.op, ast.Add): return a + b
            if isinstance(n.op, ast.Sub): return a - b
            if isinstance(n.op, ast.Mult): return a * b
            if b == 0: raise ZeroDivisionError
            return a / b
        raise ValueError("only numbers and + - * / are allowed")
    try:
        val = ev(tree)
    except Exception as e:
        return False, None, f"could not evaluate: {e}"
    if sorted(used) != sorted(numbers):
        return False, val, f"must use exactly the numbers {sorted(numbers)}, but used {sorted(used)}"
    if val != target:
        return False, val, f"it equals {float(val):g}, not {target}"
    return True, val, "correct"

2. A step, a state, and a greedy chain

A state is the list of numbers still left (each remembers the expression that made it). A step combines two of them. Four numbers need three steps. When two numbers are left, the last step is easy to check in code, like running a unit test, so every method below gets that check for free. The greedy chain asks for one step at a time and never looks back.

a04_planning_search.ipynb · cell 4
class Step(BaseModel):
    a: int
    op: Literal["+", "-", "*", "/"]
    b: int

class Proposals(BaseModel):
    steps: list[Step]

def start(p):
    return [(n, str(n)) for n in p["numbers"]]

def apply(state, s: Step):
    """Return the new state, or None if the step is not allowed."""
    vals = [v for v, _ in state]
    if s.a not in vals:
        return None
    i = vals.index(s.a)
    rest = state[:i] + state[i + 1:]
    j = next((k for k, (v, _) in enumerate(rest) if v == s.b), None)
    if j is None:
        return None
    ea, eb = state[i][1], rest[j][1]
    r = OPS[s.op](s.a, s.b)
    if r is None:
        return None
    return rest[:j] + rest[j + 1:] + [(r, f"({ea} {s.op} {eb})")]

def finish(state, target):
    """Two numbers left: try every last step in code. Returns the full expression or None."""
    (a, ea), (b, eb) = state
    for (x, ex), (y, ey) in (((a, ea), (b, eb)), ((b, eb), (a, ea))):
        for op, f in OPS.items():
            if f(x, y) == target:
                return f"{ex} {op} {ey}"
    return None

def values(state):
    return [v for v, _ in state]

def propose(state, target, k=1, memory="", temperature=0.0):
    prompt = (f"Number puzzle. Numbers left: {values(state)}. Target: {target}.\n"
              "Pick TWO of the numbers and one operation (+, -, *, /) to combine them into one new number. "
              "Results must be whole numbers and not negative. Choose steps that keep it possible to reach the target "
              f"with the numbers that remain.\n{memory}Give {k} different option(s), best first, as a, op, b.")
    out = llm_struct(prompt, Proposals, temperature=temperature, max_tokens=300)
    return (out.steps if out else [])[:k]

def greedy(p):
    state, traj = start(p), []
    for _ in range(2):                                   # 4 numbers -> 3 -> 2
        steps = [s for s in propose(state, p["target"], k=1) if apply(state, s)]
        if not steps:
            return {"ok": False, "traj": traj, "expr": None}
        nxt = apply(state, steps[0])
        traj.append({"state": values(state), "action": steps[0].model_dump(), "next": values(nxt)})
        state = nxt
    expr = finish(state, p["target"])
    return {"ok": expr is not None, "traj": traj, "expr": expr}

3. Tree search with backtracking (LATS, simplified)

LATS (Zhou et al. 2023, Language Agent Tree Search Unifies Reasoning, Acting, and Planning in Language Models) runs Monte Carlo Tree Search over agent steps: select a promising node, expand it with n sampled actions (n = 5 in the paper), evaluate children with a value V = λ·(LM score) + (1-λ)·(self-consistency score), backpropagate, and store a reflection after a failed path. It reached 92.7% pass@1 on HumanEval with GPT-4; on Game of 24 it scored 0.44 against 0.20 for Tree-of-Thoughts.

Our version is a small best-first search, which is the "select the highest value and backtrack" core of MCTS without the visit-count bonus: - expand: one call returns k=3 candidate steps; code drops illegal ones; - evaluate: one call rates the new states 1-10; self-consistency = how many proposals led to the same state; - terminal: with two numbers left, code checks the last step (the environment's reward); - reflection: dead ends are written into the next prompt (LATS asks the LM to write them; we let code write them, which is free).

a04_planning_search.ipynb · cell 5
class Scores(BaseModel):
    scores: list[int]

def rate(states, target):
    lists = "\n".join(f"{i+1}. {values(s)}" for i, s in enumerate(states))
    out = llm_struct(f"Target: {target}. For each list of numbers below, rate from 1 (impossible) to 10 (surely possible) "
                     f"how likely it is to reach the target using each number once with + - * /.\n{lists}\n"
                     f"Return exactly {len(states)} scores in order.", Scores, max_tokens=150)
    s = (out.scores if out else [])
    return [min(10, max(1, s[i])) / 10 if i < len(s) else 0.5 for i in range(len(states))]

def tree_search(p, k=3, max_expansions=4, lam=0.5):
    target, root = p["target"], start(p)
    frontier = [(1.0, 0, root, [])]                     # (value, tie-break id, state, trajectory)
    dead, expansions, uid, last = [], 0, 1, []
    while frontier and expansions < max_expansions:
        frontier.sort(key=lambda x: -x[0])
        v, _, state, traj = frontier.pop(0)             # SELECT the best open node
        memory = ("Dead ends already tried (do not repeat): " + "; ".join(dead[-4:]) + "\n") if dead else ""
        steps = propose(state, target, k=k, memory=memory, temperature=0.7)     # EXPAND
        expansions += 1
        kids = {}
        for s in steps:
            nxt = apply(state, s)
            if nxt is None:
                continue
            key = tuple(sorted(values(nxt)))
            kids.setdefault(key, [nxt, s, 0])[2] += 1     # count duplicates for self-consistency
        if not kids:
            continue
        open_kids = []
        for key, (nxt, s, count) in kids.items():
            t2 = traj + [{"state": values(state), "action": s.model_dump(), "next": values(nxt)}]
            last = t2                                     # keep the latest path, for the SWiRL section
            if len(nxt) == 2:                             # TERMINAL: code checks the last step
                expr = finish(nxt, target)
                if expr:
                    return {"ok": True, "traj": t2, "expr": expr, "expansions": expansions}
                dead.append(str(list(key)))               # REFLECTION (code-written)
            else:
                open_kids.append((key, nxt, s, count, t2))
        if open_kids:
            lm = rate([nk[1] for nk in open_kids], target)                       # EVALUATE
            for (key, nxt, s, count, t2), score in zip(open_kids, lm):
                value = lam * score + (1 - lam) * count / max(1, len(steps))
                frontier.append((value, uid, nxt, t2)); uid += 1
    return {"ok": False, "traj": last, "expr": None, "expansions": expansions, "dead": dead}

The tree spends more calls, but on a dead end it can go back instead of failing. LATS's own limits apply here too: it costs more than a single chain, and it needs states you can go back to. A puzzle can; an agent that already sent an email cannot.

4. ADaPT: decompose only when needed

ADaPT (Prasad et al. 2024, ADaPT: As-Needed Decomposition and Planning with Language Models) first lets an executor try the whole task. Only if it fails does a planner split the task, and then ADaPT recurses on each piece, up to a max depth. With GPT-3.5 it beat ReAct, Plan-and-Execute and Reflexion: 71.6% vs 43.3% for ReAct on ALFWorld, 52% vs 19% on TextCraft.

Here the executor writes a whole expression in one go. If the checker rejects it, the planner picks one step, and we recurse on the smaller puzzle. (ADaPT's executor judged its own success; our checker is stricter and more honest.)

a04_planning_search.ipynb · cell 6
def direct(state, target, temperature=0.0, extra=""):
    nums = values(state)
    reply = llm(f"Use each of the numbers {nums} exactly once, with + - * / and parentheses, to make {target}. "
                f"{extra}Reply with only the expression, for example (8 - 2) * (3 + 1).", temperature=temperature, max_tokens=80)
    return clean_expr(reply)

def substitute(expr, state):
    """Rewrite an expression over the state's values into one over the ORIGINAL numbers."""
    pools = {}
    for v, e in state:
        pools.setdefault(v, []).append(e)
    try:
        tree = ast.parse(expr, mode="eval")
        class Sub(ast.NodeTransformer):
            def visit_Constant(self, node):
                return ast.parse(pools[node.value].pop(0), mode="eval").body
        return ast.unparse(Sub().visit(tree))
    except Exception:
        return None

def adapt(state, p, depth=0, d_max=2, log=None):
    log = [] if log is None else log
    expr = direct(state, p["target"])                                # 1. try directly
    full = substitute(expr, state) if expr else None
    ok = bool(full) and check_expr(full, p["numbers"], p["target"])[0]
    log.append({"depth": depth, "numbers": values(state), "try": expr, "ok": ok})
    if ok:
        return full, log
    if depth >= d_max or len(state) <= 2:
        return None, log
    steps = [s for s in propose(state, p["target"], k=1) if apply(state, s)]    # 2. only now: plan one sub-step
    if not steps:
        return None, log
    return adapt(apply(state, steps[0]), p, depth + 1, d_max, log)              # 3. recurse on the smaller task

adapt_runs = []
for p in P:
    expr, log = adapt(start(p), p)
    adapt_runs.append({"ok": expr is not None, "expr": expr, "log": log})
    print(p["numbers"], "->", p["target"], "|", " -> ".join(f"d{l['depth']}:{'OK' if l['ok'] else 'x'}" for l in log),
          "|", expr or "failed")
direct_only = sum(r["log"][0]["ok"] for r in adapt_runs)
print(f"direct only: {direct_only}/{len(P)} | ADaPT: {sum(r['ok'] for r in adapt_runs)}/{len(P)} | {CALLS[0]} calls so far")

The point is cost: easy puzzles stop after one call; only the hard ones pay for planning.

5. Wider or deeper? (AB-MCTS)

With a fixed budget of calls, you can sample new answers (wider) or refine the best one using feedback (deeper). AB-MCTS (Inoue et al. 2025, Wider or Deeper? Scaling LLM Inference-Time Compute with Adaptive Branching Tree Search) decides at every node, using Thompson sampling on the scores so far. With 128 calls of GPT-4o on CodeContests, pure refinement scored 30.1%, repeated sampling 37.9%, and AB-MCTS 40.6%. Pure "deeper" can be worse than pure "wider".

We give each strategy the same budget of 3 calls per puzzle and score answers with the checker (1.0 if correct, partial credit if it uses the right numbers and lands close).

a04_planning_search.ipynb · cell 7
BUDGET = 3

def score(expr, p):
    ok, val, msg = check_expr(expr, p["numbers"], p["target"]) if expr else (False, None, "empty answer")
    if ok:
        return 1.0, msg
    if val is None or "must use" in msg:
        return 0.0, msg
    return 0.5 * max(0.0, 1 - abs(float(val) - p["target"]) / p["target"]), msg

def wider(p):
    with ThreadPoolExecutor(2) as ex:
        exprs = list(ex.map(lambda _: direct(start(p), p["target"], temperature=0.9), range(BUDGET)))
    return max(score(e, p)[0] for e in exprs)

def deeper(p):
    best = direct(start(p), p["target"], temperature=0.9)
    best_s, msg = score(best, p)
    for _ in range(BUDGET - 1):
        if best_s == 1.0:
            break
        e = direct(start(p), p["target"], temperature=0.7,
                   extra=f"Your last try was {best or '(empty)'}: {msg}. Fix it. ")
        s, m = score(e, p)
        if s >= best_s:
            best, best_s, msg = e, s, m
    return best_s

wd = {"wider": [wider(p) for p in P], "deeper": [deeper(p) for p in P]}
for name, ss in wd.items():
    print(f"{name:7s} solved {sum(s == 1.0 for s in ss)}/{len(P)} | mean best score {sum(ss)/len(ss):.2f}")
print(CALLS[0], "calls so far")

Three puzzles and three calls each is far too little to pick a winner; the paper needed up to 128 calls per problem. What you should take away is the knob itself: when feedback is informative ("it equals 30, not 24"), deeper helps; when the first idea is wrong at the root, only wider escapes it. AB-MCTS learns which one is paying off.

6. SPRINT: run independent steps at the same time

Reasoning models usually think in one long sequence. SPRINT (Biju et al. 2025, SPRINT: Enabling Interleaved Planning and Parallelized Execution in Reasoning Models) fine-tunes a model to alternate a plan (a list of independent subtasks) with parallel execution of those subtasks. It matched its baselines on math while using up to 39% fewer sequential tokens on long problems (and up to 45% on GPQA, 65% on Countdown).

The same idea works at the agent level. A contract review plan has four independent rule checks, then one summary that needs all four. Independent checks can run together.

a04_planning_search.ipynb · cell 8
PB = playbook()

PLAN = {"liability_cap": [], "governing_law": [], "auto_renewal": [], "termination_notice": [],
        "summary": ["liability_cap", "governing_law", "auto_renewal", "termination_notice"]}

def stages(dag):
    """Group steps into rounds: a step runs once everything it depends on is done."""
    done, out = set(), []
    while len(done) < len(dag):
        ready = [s for s, deps in dag.items() if s not in done and all(d in done for d in deps)]
        if not ready:
            raise ValueError("cycle in plan")
        out.append(ready); done |= set(ready)
    return out

def check_rule(cid, rule):
    sec = next((s for s in sections(contract(cid)) if WORD[rule] in s["title"]), None)
    v = llm(f"Playbook rule: {PB['rules'][rule]}\n\nClause: {sec['text'] if sec else contract(cid)}\n\n"
            "Does the clause follow the rule? Answer PASS or FAIL only.", max_tokens=5).strip().upper()
    return rule, "FAIL" if "FAIL" in v else "PASS"

print("plan rounds:", stages(PLAN))
cid = "msa_15"

t_par = time.time() - t0

print(f"sequential {t_seq:.1f}s | parallel(2) {t_par:.1f}s | {summary}")

With 2 parallel slots, 4 checks take about 2 rounds instead of 4. The planner's job is to find the independent steps; here the plan was written by hand, SPRINT trains the model to write it.

7. SWiRL: turn logged runs into step-level training data

SWiRL (Goldie et al. 2025, Synthetic Data Generation & Multi-Step RL for Reasoning & Tool Use) generates multi-step trajectories, cuts each one with k actions into k sub-trajectories (context so far → next action), filters them, and trains with RL where a model judges each step. Two findings worth knowing: with Gemma 2 27B it beat baselines by 21.5% (GSM8K) and 12.3% (HotPotQA) relative accuracy; and process-only filtering (keep steps a judge calls reasonable, even when the final answer was wrong) worked better for RL than keeping only trajectories with correct answers.

We already logged trajectories in sections 2 and 3. Our "process judge" is the solver: a step is good if the target is still reachable after it. (SWiRL used Gemini 1.5 Pro as the judge; a code judge is cheaper when you have one.)

def adaptive(p, seed=0):
    rng = random.Random(seed)
    stats = {"GEN": [], "REFINE": []}
    best, best_s, msg = None, -1.0, ""
    for call in range(BUDGET):
        if best is None:
            arm = "GEN"
        else:
            draws = {a: rng.betavariate(1 + sum(s), 1 + len(s) - sum(s)) for a, s in stats.items()}
            arm = max(draws, key=draws.get)

            break

Traps
  • Searching where you can't undo actions. LATS assumes you can return to earlier states; a sent email or a database write can't be rewound.
  • Trusting the model's value scores alone. Use a real verifier when one exists; LM ratings are noisy.
  • Planning everything up front. A long fixed plan fails when any step fails; ADaPT decomposes only where needed.
  • Trusting self-reported success. ADaPT's executor overestimated success by more than 30 points on WebShop.
  • Judging wider vs deeper at tiny budgets. AB-MCTS's gains showed up at tens to hundreds of calls, and some gaps were within noise.
  • Parallelizing steps that depend on each other. Map dependencies first; the longest chain sets the floor on latency.
  • Keeping only successful runs as training data. SWiRL found process filtering beat outcome filtering for RL.

What does ADaPT do differently from plan-and-execute?

It tries the whole task first and only plans and splits it when the executor fails, recursing on failed parts up to a max depth, so easy tasks cost one call.

In AB-MCTS, what is the choice made at each node, and what decides it?

Whether to generate a new answer (wider) or refine an existing one (deeper); Thompson sampling on the feedback scores decides.

Why might SWiRL keep a step from a trajectory whose final answer was wrong?

Because the step itself was judged reasonable. Process-only filtering gave the best RL results, and failed runs still contain useful good steps.
