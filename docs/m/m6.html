Module 06

Design patterns

Open in Colab
13 min readPlain-English lesson, then the deeper material

The handful of standard shapes most AI systems take, from simple chains to checker loops, and how to pick the simplest one that works.

The big idea

Most AI systems are built from a few standard shapes. Learn them, and you can sketch almost any system on a napkin.

Think of a kitchen. There are a few ways to run it. One cook does steps in order. A host sends each order to the right station. Several cooks work on different dishes at once. A head chef tastes each plate and sends it back if it's wrong. You choose based on the menu, not on what looks fancy.

The five workflow shapes are chaining, routing, parallel, orchestrator-workers, and generator plus checker. On top of these sit a few agent shapes. The rule is always the same. Start with the simplest one that works. Add more only when your tests show it helps.

Why it matters for us

Contract review has known steps, so most of it fits simple shapes. A chain extracts the cap, checks it, then drafts a fix. Parallel checks each playbook rule at once.

Simple shapes suit small local models. Each step asks the model one narrow question. Code handles the rest. Fewer open choices means fewer chances to drift.

One finding matters a lot. Asking a model "is this good?" with no outside signal does not help. It even made GPT-4-class models worse (course Lecture 6). Checkers should be real checks: code, rules, or tools.

How it works, step by step

Shape What it does Contract example
Chaining Fixed steps, with checks between them Extract cap, then check it, then draft a fix
Routing Sort the input, send it to the right handler Easy clause to code, hard one to the model
Parallel Run independent checks at once Check all four playbook rules together
Orchestrator-workers A model splits the job and hands out parts Review a pile of unknown documents
Generator + checker Draft, check, revise in a loop Draft a redline, check it meets 12 months

And the agent shapes:

  1. ReAct. Think, act, look at the result, repeat. This is the basic agent loop from module 01 (the ReAct paper, 2023).
  2. Reflexion. After a clear failure, like a failed test, write a short lesson and retry with it.
  3. CodeAct. Instead of one tool call per turn, the model writes a small Python program that does several steps at once. Good when a task needs loops over data.
  4. Plan then execute. One call writes the full plan. Then code runs each step. The course reports about 40 to 60% fewer tokens. This turns agent work back into a workflow.

Worked example

Chaining. The notebook finds the liability section. The model pulls out the cap and quotes the sentence. Then two code gates run:

if not quote_is_in_doc(cap.quote, contract(cid)):
    return {"status": "HOLD", "why": "quote not found in contract"}
ok = cap.months is not None and cap.months <= PB["max_cap_months"]
return {"status": "OK" if ok else "ISSUE", "months": cap.months}
  • The first line checks the model's quote is really in the contract.
  • If not, the contract goes on HOLD. A person looks at it. We don't guess.
  • The third line applies the playbook rule in code. No cap, or a cap over 12 months, is not OK.
  • The last line returns OK or ISSUE, plus the number.

On msa_07, which has a 24-month cap, the result is ISSUE.

Routing. For governing law, a simple text pattern looks for "State of ...". If it matches, code answers with no model call. Only odd cases go to the model.

Parallel. The four playbook rules don't depend on each other. The notebook checks them for msa_15 at the same time, each asking the model "PASS or FAIL?" for one clause.

Generator + checker. The model rewrites msa_08's cap clause. Code then reads the new text, finds every "N months," and checks the largest is at most 12. If not, it sends back specific feedback, like "the text says 24 months; the playbook max is 12." Note that code checks the text itself, not the model's own claim about it.

CodeAct. Asked which contracts use Texas, Florida or New York law, the model writes a short program that loops over all contracts. The notebook runs it in a limited space, a toy sandbox (a fenced-off area for running untrusted code).

Common mistakes

  • A checker that is just the same model asking "is this good?" Without an outside signal it burns tokens. Use code or rules.
  • Orchestrator-workers for known steps. If you can list the steps, write a chain.
  • Starting complex. Begin with a chain. Add routing, parallel or loops only when tests show a gain.
  • Checking the model's claim instead of its output. Read the draft text yourself, in code.

Check your understanding

When does a generator plus checker loop help?

When the feedback can be stated clearly, something can give it reliably (tests, rules, a tool-using critic), and the generator can act on it.

How does plan then execute help a small local model?

It makes one planning call, then runs simple fixed steps. Fewer open decisions means fewer chances to drift, and it uses fewer tokens.

Why does the chain put a contract on HOLD instead of guessing?

Because the model's quote wasn't found in the contract. That is a sign the answer may be wrong, so a person should look.

Key terms, papers, evidence, the full notebook code and worked solutions.

Lecture 6 · Anthropic, "Building Effective Agents" · ReAct · Reflexion · CodeAct · ReWOO

Five workflow patterns and four agent patterns cover almost everything. Start with the simplest one that works and add complexity only when your eval shows it helps.

Key terms

Prompt chaining
Fixed sequence of calls, each using the previous output, with checks between steps.Source: Anthropic, "Building Effective Agents" (2024)
Routing
Classify the input first and send it to the best prompt, model or code path; easy cases can go to a cheaper path.Source: Anthropic (2024); Lecture 6
Orchestrator–workers
An LLM breaks a task into subtasks at run time and delegates them, then combines results.Source: Anthropic (2024)
Evaluator–optimizer
A generator and a checker in a loop. Works only when feedback is clear, reliable and actionable.Source: Anthropic (2024); Lecture 6
Reflexion
After a failure with an outside signal, the agent writes a short lesson and retries with it in context.Source: Shinn et al., "Reflexion", NeurIPS (2023)
CodeAct
The agent's actions are small programs instead of JSON tool calls, which handle loops and data better.Source: Wang et al., "Executable Code Actions Elicit Better LLM Agents", ICML (2024)
ReWOO (plan then execute)
Plan all steps in one call, then execute them without re-asking the model each step; fewer tokens.Source: Xu et al., ReWOO (2023), cited in Lecture 6

Four agent patterns

  • ReAct: think, act, observe, repeat. The default agent loop.
  • Reflexion: after a failure with an outside signal (a failing test), write a short lesson and retry with it. It added about 8 points over replaying raw history.
  • CodeAct: the model writes code as its action instead of JSON tool calls. Up to 20% higher success with fewer turns across 17 models, when tasks involve loops or data handling.
  • Plan then execute (ReWOO): plan all steps first, then run them. About 40–60% fewer tokens. This turns agent work back into a workflow.
~75 vs ~67

F1 for a critic that used tools (search, code) vs. one that didn't (CRITIC, L6).

Hurts

Self-correction without an outside signal made even GPT-4-class models worse (L6 p.41).

import re, time
from concurrent.futures import ThreadPoolExecutor
from pydantic import BaseModel
from typing import Literal
# lal.llm = the OpenAI client pointed at the local Ollama server, http://localhost:11434/v1 (see notebook 00)
from lal.llm import ask, structured
from lal.data import contract, sections, labels, playbook, ids
from lal.checks import quote_is_in_doc, check

PB = playbook()
def section(cid, word):
    return next(s for s in sections(contract(cid)) if word in s["title"])

1. Chaining: fixed steps with checks between them

06_design_patterns.ipynb · cell 3
class Cap(BaseModel):
    months: int | None
    quote: str

def chain(cid):
    s = section(cid, "Liability")
    cap = structured(f"{s['text']}\n\nExtract the cap in months of fees (null if unlimited) and quote the sentence.", Cap)   # step 1: LLM
    if not quote_is_in_doc(cap.quote, contract(cid)):                                                                     # gate: code
        return {"status": "HOLD", "why": "quote not found in contract"}
    ok = cap.months is not None and cap.months <= PB["max_cap_months"]                                                    # step 2: rule in code
    return {"status": "OK" if ok else "ISSUE", "months": cap.months}

for cid in ["msa_01", "msa_07", "msa_16"]:
    print(cid, chain(cid), "| truth:", labels()[cid]["terms"]["liability_cap_months"])

2. Routing: classify first, then send to the right handler

Easy inputs can go to a cheaper path. Here a cheap regex check handles most cases and the model handles the rest.

06_design_patterns.ipynb · cell 4
def route_law(cid):
    text = section(cid, "Governing")["text"]
    m = re.search(r"State of (\w+(?: \w+)?)", text)
    if m:                                         # easy case: code handles it, no model call
        return m.group(1).split(",")[0], "code"
    return ask(f"{text}\nWhich US state's law governs? State name only.").strip(), "model"

for cid in ["msa_03", "msa_09", "msa_15"]:
    print(cid, route_law(cid))

3. Parallel: independent checks at the same time

Separate checks don't depend on each other, so run them together. Ollama runs them in parallel when OLLAMA_NUM_PARALLEL > 1 (our setup sets 2); otherwise they queue.

06_design_patterns.ipynb · cell 5
def check_rule(args):
    cid, rule = args
    word = {"liability_cap": "Liability", "governing_law": "Governing", "auto_renewal": "Renewal", "termination_notice": "Renewal"}[rule]
    verdict = ask(f"Playbook rule: {PB['rules'][rule]}\n\nClause: {section(cid, word)['text']}\n\n"
                  f"Does the clause follow the rule? Answer PASS or FAIL only.").strip().upper()
    return rule, "FAIL" if "FAIL" in verdict else "PASS"

cid = "msa_15"
t0 = time.time()
with ThreadPoolExecutor(4) as ex:
    results = list(ex.map(check_rule, [(cid, r) for r in PB["rules"]]))
print(results, f"{time.time()-t0:.1f}s")
print("truth issues:", [i["rule"] for i in labels()[cid]["issues"]])

4. Generator + checker: draft, check with real checks, revise

The checker is code first. Asking the same model "is this good?" without an outside signal doesn't help; the course showed it can make results worse.

06_design_patterns.ipynb · cell 6
class Redline(BaseModel):
    new_text: str
    months: int

def draft_redline(cid, rounds=3):
    clause = section(cid, "Liability")["text"]
    feedback = ""
    for r in range(rounds):
        d = structured(f"Rewrite this clause so the liability cap meets the playbook: {PB['rules']['liability_cap']}\n"
                       f"Clause: {clause}\n{feedback}\nReturn the new clause text and the cap in months.", Redline)
        problems = []
        stated = [int(n) for n in re.findall(r"(\d+)\)? months", d.new_text)]       # check the TEXT, not the model's own claim
        if not stated: problems.append("the new text doesn't state the cap as a number of months, like 'twelve (12) months'")
        elif max(stated) > PB["max_cap_months"]: problems.append(f"the text says {max(stated)} months; the playbook max is {PB['max_cap_months']}")
        if not problems:
            return d, r + 1
        feedback = "Fix these problems: " + "; ".join(problems)
    return d, rounds

d, n = draft_redline("msa_08")
print(f"after {n} round(s):", d.new_text)

5. ReAct vs code-as-action (CodeAct)

Instead of one JSON tool call per turn, the model writes a small Python snippet that does several steps at once. Fewer turns when a task needs loops. We run the code in a restricted namespace (a toy sandbox; real systems use containers).

06_design_patterns.ipynb · cell 7
def code_act(question):
    code = ask("You can use these Python functions: contract(cid) -> str, ids() -> list of ids, "
               "sections(text) -> list of {'id','title','text'}.\n"
               f"Write Python that computes the answer and stores it in a variable named result. Question: {question}\n"
               "Reply with only the code, no explanation, no backticks.")
    code = re.sub(r"^```\w*|```$", "", code.strip(), flags=re.M).strip()
    import builtins
    safe = {k: getattr(builtins, k) for k in ("len", "range", "sorted", "any", "all", "str", "int", "list", "set", "dict",
                                              "enumerate", "zip", "min", "max", "print", "isinstance")}
    g = {"__builtins__": safe, "contract": contract, "ids": ids, "sections": sections, "re": re}   # one namespace, so generators and defs see the helpers
    try:
        exec(code, g)
        return g.get("result"), code
    except Exception as e:
        return f"ERROR {e}", code

result, code = code_act("Which contract ids are governed by Texas, Florida or New York law?")
print(code, "\n->", result)
print("truth:", [c for c, l in labels().items() if l["terms"]["governing_law"] in ("Texas", "Florida", "New York")])

# Solution 2: "ask the model if it's good" vs a code checker, on drafts we KNOW are bad (cap > 12 months)
bad_drafts = [
    "Each party's total liability shall not exceed the fees paid in the twenty-four (24) months preceding the claim.",
    "Liability is capped at fees paid during the 18 months before the claim, a market-standard position.",
    "Total liability shall not exceed three (3) years of fees.",
]
def llm_checker(text):
    v = ask(f"Playbook: the cap must not exceed fees paid in the prior 12 months.\nClause: {text}\n"
            "Does the clause meet the playbook? Answer YES or NO only.").strip().upper()
    return v.startswith("YES")
def code_checker(text):
    months = [int(n) for n in re.findall(r"(\d+)\)? months", text)]
    years = [int(n) * 12 for n in re.findall(r"(\d+)\)? years", text)]
    vals = months + years
    return bool(vals) and max(vals) <= 12
print("LLM checker wrongly approved:", sum(llm_checker(t) for t in bad_drafts), "of", len(bad_drafts))
print("code checker wrongly approved:", sum(code_checker(t) for t in bad_drafts), "of", len(bad_drafts))
Traps
  • A generator–checker loop where the checker is the same model asked "is this good?". Without an outside signal it just burns tokens.
  • Using orchestrator–workers for work whose steps you already know.
